## The rules as built

**Rule 1 (M1a) — a whole-note save carries its base.**
- `useNotesStore.save(id, patch, at?, base?)`. With `base` and `patch.blocks`, the blocks are first merged into what the store holds now by `mergeWholeNote(base, mine, theirs)` and only then go through the unchanged protections (highlight groups, `removedEmpty`, `removedStickies`, `stickySaved`).
- `mergeWholeNote` (exported, pure): if the store still equals the base nobody else wrote, and the editor's blocks are returned exactly (its order, its deletions: today's behaviour). Otherwise it is the sticky's own three-way by block id (`mergeStickyContent`, unchanged): a block only the store changed keeps the store's, a block only the editor changed keeps the editor's, a block both changed has both writers' words (`mergeText`, the write being made now is `mine`). Then the editor's own order stands for the blocks it holds, and a block only the store holds sits after its neighbour. A block the editor deleted and the store left alone is gone; one the store changed stays; one the store deleted and the editor left alone stays deleted.
- **Callers with no base (today's replace-wholesale behaviour):** `notes-rail.tsx` (a title save, no blocks, so nothing to merge) and the fixtures of the existing tests. Every block-writing caller in the app now carries one: `NoteEditor` (through `makeDocWriter`: the base of the first write is the blocks it started from, of each later write the blocks it wrote before) and the window's seed (`storeSeed`, base = the stored blocks the merge was made from).

**Rule 2 (M1b) — no loop.** The window's two effects are now two exported functions the component calls.
- `settleWindow(base, mine, stored, seed)` is the reconcile effect's body. After a `merge` verdict `base.current` is the merge itself (what the new editor starts from and the window stores), so the next pass measures the new editor against its own start and the merge in the store is `keep` / `same`. While a seed waits and the note in hand is still the one it was made from (`stored.blocks === seed.from`), no verdict is made: that is the pair that looped (a freshly mounted editor against a note older than itself).
- `storeSeed(noteId, seed)` stores the merge only if the note is still the one it was made from (compare-and-set), with that note as base. **Why not store it always:** the old editor's unmount flush now merges into the note (rule 1), so when it, or a sticky, has written since the look, the note already holds both writers' words and the older merge saved over it counted the window's words a second time (`hello stickyaz bbb bbb`; the first version of this code did that, test "a second sticky flush between the look and the seed"). Then nothing is stored and the effect looks at the note as it is (restart or merge, as any outside change).

## For the manager

1. **A change of outcome the brief did not list: same-words overlap.** When both surfaces rewrite the same words of one block at the same time (not add: rewrite), the window's rewrite now stands; at head the sticky's did. Measured on invented text (`hello sticky` -> window `hello WIN`, sticky `hello STK`): head's seed text is `hello STK` (`reconcileWindow` -> `mergeBlocks`, outside last); the tree at `df9e3791` ends `hello WIN` in both the page-leave and the page-lives order. Cause: the old editor's unmount flush now merges into the note with the writer-last-wins rule the sticky's own write uses (`mine` last), and `storeSeed` then skips the older merge (it would count the window's words twice), where before the flush replaced the note and the seed, written after it, put the outside's rewrite back. One of the two rewrites is lost in either case; the new rule is the same "the write being made now wins" that `setStickyBlocks` has. No test pins the old outcome. If you want the outside's rewrite to stand, that is a decision on `save`'s `later` side (a small, separate change); I did not make it.
