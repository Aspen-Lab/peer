## 1. The rule as built

`placeButton(rect, viewport, paragraph?)` in `explain-box.tsx` (one function, one new optional parameter; the button's size constants unchanged; no new wording, no switch):

1. **The gutter, when there is one.** With `paragraph` given and `viewport.width − paragraph.right ≥ BUTTON_WIDTH + 2·BUTTON_MARGIN` (= 120 + 16 = **136**): `left = clamp(paragraph.right + BUTTON_GAP (6), 8, viewport.width − 120 − 8)`, `top = clamp(rect.top, 8, viewport.height − 32 − 8)`. The right-hand clamp never binds once the room test holds (`paragraph.right + 6 ≤ viewport.width − 130`), the left one only for a paragraph scrolled off to the left, and `left ≥ paragraph.right` holds in both. The viewport the box passes is already `width − DOCK_RESERVE_PX (376)` while the dock stands, so the gutter is the space between the reading column and the dock's reserve. At exactly 136 the gutter is used, at 135 it is not (pinned).
2. **No gutter** (no paragraph reported, a phone, a narrow window, a column flush with the edge): today's placement, line for line — centred on the selection's end, 6 px under it, above it when the foot has no room. The existing tests pin it and stay green.
3. The call in the `ask` button now passes `whereOf(next).paragraph` (read once into `askAt`); `paper-body.tsx` needed nothing (it already reports the paragraph's `<p>` box, P8-02). The header comment of `explain-box.tsx` gains the gutter sentence, and `placeButton` has its own doc comment.

`top` is `rect.top`, and `rect` is where the selection **ends** (`measureRange`: its last line with a width), not its first line — see "For the manager" 2.

## 6. For the manager

1. **The briefed rule does not fix X13 at 1440 for a reader with a key.** The brief's example (a) has a paragraph whose right edge is 900 in a 1064 px viewport; the real layout has it at 1040 (§4), leaving 24 px, not 136. With the dock standing — every reader with a key from 1024 px — the column is laid out to within about 24 px of the dock's reserve at every window from 1024 to about 1700, so the gutter exists only from between 1680 and 1800 up (1680: 84 px, 1800: 144). In that whole range the button is where it was and covers two words of the next line (measured at 1440: the button over "mulch keeps soi…" of the second line in the screenshot). The rule is right and pinned where there is room — the card range (800 and 900 measured; 640 has no room), 1800+, and any window where the dock is not standing — and it is the brief's rule 2 ("a column flush with the edge") that governs the rest. To make 1440 itself work needs a decision outside this item's files: (i) a wider clear margin between the column and the dock in `reader-layout.tsx` / `globals.css` / `explain-dock.ts` (136 px more than today's 24 would take the column from 632 to about 520 px wide at 1440 and below readable at 1280, where it is already 472), (ii) the button in the left margin (at 1440 the sidebar ends at 344 and the column starts at 408: 64 px, not enough either), or (iii) the button inside the dock's own lane (x ≥ 1080) at a height the dock does not occupy (the empty window ends near y 158) — which P8-02 deliberately avoided. P9-04 holds the layout files; I did not touch them.
2. **`rect` is where the selection ends, not its first line.** The brief says "level with the selection's first line … `top = rect.top`"; in `paper-body.tsx` `rect` is the selection's last line with a width and `bounds` the whole. I built `top = rect.top` as the brief's tests state, so on a multi-line selection the button is level with the line the selection ends on (where the pointer let go), which is also where the no-gutter button has always stood. If the first line is wanted, `bounds.top` has to reach `placeButton` (a fourth parameter or a different first argument) and the tests (a), (b) and the runtime ones are re-aimed; the doc comment says "the line the selection ends on" so it does not claim more than the code does.
3. `paper-body.tsx`'s `ViewRects` doc still says `rect` is "what the button stands under"; true only in the no-gutter case now. A one-line comment fix if the manager wants it; I left the file alone (not needed for the item).
