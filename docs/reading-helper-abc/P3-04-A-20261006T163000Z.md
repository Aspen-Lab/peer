### F1 — HIGH, privacy — the paragraph-gist pass sends the paper's text to the model on page open, with no click and no Deep report switch, and /privacy does not say so

- Reproduction (dev server, stub): profile `feedAiProvider: "openai"` with the placeholder key, `deepReportEnabled: false` (the default). Upload a PDF through the UI and open its page; touch nothing. The stub's log for that session holds a `shallow` report call whose prompt does **not** contain the paper's body (marker "Spallation refers to": false, 3,926 characters) and a `gist` call, in the same second, whose prompt **does** (true, 5,675 characters, 14 paragraphs). The browser made one POST `/api/papers/[id]/paragraph-guide` with body keys `llmOverride` and `paper`. The same happens in every run of this review.
- Where the code decides: `app/papers/[id]/page.tsx` `useParagraphGuide({ …, enabled: providerConfigured, … })` (what `briefs/P3-03.md` item 3 asks for: "the reader has a model"); `providerConfigured = aiAvailability(…) !== "none"`; nothing on the path reads `profile.deepReportEnabled`.
- What the product says elsewhere: Profile → Deep report: "Read each paper's full text … before writing the report. Costs more tokens per paper…", off by default; /privacy "Who else sees a request": "Google (Gemini) sees a paper's text when a model report is written."; the new "Explain this" entry says Peer sends a request only on the reader's click; nothing names the gist pass. The upload dialog says "Reports may send article text and figures to your configured AI provider" and asks authorisation to "process this article … including with my AI provider".
- Effect: the body text of a paper — for a private PDF, its text — goes to the reader's own provider, or to Google Gemini on Peer's key for a signed-in reader, the moment the page opens; the call spends the reader's key or Peer's key unprompted, uncharged and without a per-day cap (the 20/hour gate cannot be measured in dev, B3). The shared memory holds only the gists, keyed by document hash; nothing reaches a log (R29, R43).
- Classification (for B): a spec gap and a policy question, not a code slip — the brief ordered the trigger and §1h.6 is silent on it; the upload consent covers "processing … with my AI provider" in general, so this is not an unconsented transfer. It is a disclosure and switch-semantics gap on the privacy-first path. Directions, the manager's call: gate the pass behind the same switch as the report or a click; or keep it and add a /privacy entry and a clause to "Who else sees a request"; either way the page's wording and the code must agree in one commit.

### F2 — LOW to MEDIUM, P2-10 — "nothing is sent from the unloading page" is not true in a real browser

- Reproduction: an init script marks the page unloading on `pagehide` (capture phase, before the app's listener) and logs every `fetch` to `/api/papers/report` with that mark; deep reports on; three questions typed, the box left with a real click, 700 ms later reload (or navigate to `/changelog`). In all 6 runs the log shows, after the mark, two calls with the three settled questions — one with `document.visibilityState` `visible`, one `hidden` — and, for the reload, the new page's own call as the fourth. At the browser level the route handler saw two requests carrying the questions — the dying page's and the returning page's — where the ordinary path has one.
- Measured cost on the real deep-report counter (P2-08c loop; server restarted per run): open only 1 unit; questions settled by the timer 2; questions settled by leaving inside the wait, by navigating away and back 2, by reload 2. The browser cancelled the dying page's calls (the server's own count was one request for the questions each time), so **no double charge was measured**. Whether the dying page's request reaches the server is a race: one that does is charged and answered into nowhere, and the new page asks again (the old page's cache never got the answer).
- Cause (from reading, not rerun): `settle` writes `settled` to the store; `useModelReport` re-keys on it and its effect fetches. The `pagehide` listener itself calls no `fetch` — which is all C's test asserts (`fetch` stubbed, not called by the handler). The ruling's invariant ("nothing is sent from the unloading page") was never pinned across the effect chain.
- R10 (the questions are settled) stands PASS; R11 (nothing sent) FAILS.
