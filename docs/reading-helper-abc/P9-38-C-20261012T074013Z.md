## 3. What `subsets` does in this Next (16.2.3), and why it was never the lever

`node_modules/next/dist/docs/01-app/03-api-reference/02-components/font.md` (l.146–158 and l.436–438): `subsets` names "the subsets you would like to be **preloaded**"; those get a `<link rel="preload">`. The loader agrees (`node_modules/next/dist/compiled/@next/font/dist/google/loader.js` l.102 and `find-font-files-in-css.js`): `findFontFilesInCss(css, subsetsToPreload)` returns **every** font file in Google's response and only flags the ones to preload; every file is downloaded and emitted, and every `@font-face` stays in the CSS. The build output shows it: all six Newsreader faces and files are there, and only the two `latin` ones have the preload marker (`-s.p.`) in their names. So the browser already has the `latin-ext` and `vietnamese` faces available by `unicode-range`; adding a subset to the call would only have added a preload. Had a subset carried the block, the fix would still not have been this call. (It does not, so question 2 does not arise.)

## 5. Question 3 (no subset: name one serif fallback on all four platforms)

**The reading's stack, as built** (`globals.css` l.235; the computed value on the page, with Next's fallback face in it): `Newsreader, "Newsreader Fallback", "Iowan Old Style", Georgia, "Times New Roman", serif`. `"Newsreader Fallback"` is Next's size-adjusted face, `@font-face { src: local("Times New Roman"); size-adjust: 105.48%; … }` (from the built CSS). So Times New Roman is already the first face after Newsreader on any platform that has it, and again fifth; the generic `serif` is last. A glyph Newsreader lacks falls to the first of these that has it, and then to the OS's per-character fallback. That is the rule the brief describes, and it is already in force; the question is only whether a *better* named face exists to add.

**I name none, and here is what I can and cannot say.** What the platforms ship, from memory and not checked against any platform's current font list (names, not coverage):
- Windows: Times New Roman, Georgia, Cambria (with Cambria Math).
- macOS: Times New Roman, Georgia, Times, Palatino, Iowan Old Style, and the STIX set (STIXGeneral).
- iOS: Times New Roman, Georgia, Iowan Old Style, Palatino.
- Android: `serif` is Noto Serif (Droid Serif before Android 5); no Georgia, no Times New Roman, no Cambria, no STIX unless the device maker adds them.

**No serif family is installed on all four.** The one name on three of them (Times New Roman) is already in the stack twice; Android reaches it only through the generic `serif`, which is also already in the stack. For the coverage of U+2070–U+209F by any of these, per platform, I have no list I can cite with the care the brief asks for, and I will not invent one. What I did measure is that even a face built to be Times New Roman's metric twin covers this block partly (§6: Liberation Serif has the digits and not the signs or brackets), so "Times New Roman has it" is not a safe assumption for `⁺ ⁻ ₊ ₋ ₍ ₎` on the real platforms either.

So the rule in the brief's own terms ("one fallback face named, on all four platforms, no new download") has no candidate, and the brief's instruction for that case is to change nothing. A face named only for one platform (Cambria, STIXGeneral, Noto Serif) would be a guess for the other three and, on the others, would be skipped silently; a face named for all four does not exist.

## 9. For the manager

1. **The answer to the brief's question 1 is no, and `subsets` is not the lever** (§2, §3): in this Next it only chooses what to preload; all three of Newsreader's subsets already ship and none has the block. Nothing in `layout.tsx` or `globals.css` should change for this item; I changed nothing.
2. **The item is cosmetic and the choice is the owner's.** The three real routes, none within my files or this brief: (a) accept what shipped (the glyphs always render; weight and face differ from the body, and a formula can mix a serif digit with a sans sign); (b) a render-time `font-variant-position: sub` / `super` over a plain digit in the paragraph renderer (the only way to draw them in Newsreader's own glyphs, since the served files have no `subs`/`sups`; Chromium 141 applies the property, the lowered run measuring 7 px against 10 for the plain digit, which I checked on Liberation Serif only, not on Newsreader and not in Safari or Firefox), at the price of the page's DOM text no longer being the Unicode characters (a copy from the page gives plain digits; the Markdown, Obsidian, email and JSON outputs and the matcher of P9-14 are not touched by a render-time change); (c) a self-hosted woff2 of a serif that holds U+2070–U+209F, declared with `unicode-range: U+2070-209F` after Newsreader (an asset and a licence to choose; the brief forbids a new font download). I would take (a) now, and (c) only if the owner finds the mixed faces in the real papers distracting.
3. **An aside, not this item and not changed:** the comment above the Newsreader call in `layout.tsx` says "Variable font with an optical size axis", but the call passes no `axes`, so the URL has no `opsz`, the served files have the `wght` axis only (read from their `fvar`), and Chromium names the face "Newsreader 16pt": the optical size is fixed at 16 for every size, the 46 px display lines included. `axes: ["opsz"]` would add the axis (and bytes); that is a separate item with its own measurement.
