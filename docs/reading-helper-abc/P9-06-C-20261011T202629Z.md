## 1. Where the newline lives (the investigation, with evidence)

It lives **in the reading itself**: `reading.abstract.sentences`. The writer printed what it was given.

The chain, for a PDF upload: `app/api/papers/upload/route.ts:299` stores `summaryIntro: abstractLine(abstractSection.text)`; the abstract section's text is the extractor's, which keeps the paper's line and paragraph breaks (the comment on `toQuote` in `reading.ts:296` says so: "Section text carries the paper's paragraph breaks since the extractor started keeping them"). `abstractLine` (`lib/papers/skim.ts`) returns the text **as it is** when it fits in 1,200 characters, and when it does not it joins whole `splitSentences` pieces with a space, each piece still holding its own interior breaks. `buildReading` (`reading.ts:703-707`) then does `splitSentences(intro + discussion)`, and `splitSentences` (`skim.ts:109`) splits only at `(?<=[.!?])\s+` and trims the two ends of each piece; a break that follows anything else (a `⟩`, a hyphen, a bracket, a digit) stays **inside** the sentence. `reading.abstract.sentences` is that array, unchanged.

Measured with invented text (a throwaway test, deleted; `\n` shown as the JSON escape): input `"…We index the ⟨003⟩\n\n||ND texture of each film.\nThe ⟨003⟩ peak sharpened by 40 % after\nannealing."` → `abstractLine(raw) === raw` **true**; `splitSentences(raw)` → `["…We index the ⟨003⟩\n\n||ND texture of each film.", "The ⟨003⟩ peak sharpened by 40 % after\nannealing."]`; `buildReading(...).abstract.sentences` → the same two strings; an abstract over 1,200 characters through `abstractLine` still holds the `\n`. (The first piece also swallowed "600 K." because `K.` reads as an initial to the splitter's `ABBREVIATION` — not this item, but it is why the invented example splits in two and not three.) The committed test "the line breaks an upload's abstract carries from the PDF are gone from the copy" runs this very path (`buildReading` on a raw `summaryIntro`) and asserts the copy.

Why the page does not show it: `PaperWords` puts the sentences into `<p>` elements, and HTML collapses whitespace. Why Markdown does: a blank line ends a paragraph, a single break ends the line, and a `**` followed by a break is not an opening bold marker. `abstractParagraphs` makes at most two paragraphs by `introCount`, so every further break in the clip was inside a sentence — the walk's three paragraphs and the `**` that "opened" on a break.

**The other printed paper text** (the brief's question):
- `reading.findings / method / caveats` quotes: `toQuote` (`reading.ts:299`) and `captionFindings` (`reading.ts:404`) already collapse whitespace, so a freshly built reading is clean; a reading cached from an earlier build, or any hand-built one, is not guaranteed.
- A report's evidence (`claim.evidence`, answer evidence): `evidence.ts` `shown()` goes through `shapeEvidenceQuote`, which flattens (`replace(/\s+/g, " ")`), so the normal path is one line — but `shown(...) ?? evidence` falls back to the sanitizer's string when the quote cannot be lined up, and that one is not flattened.
- The TLDR (Semantic Scholar's text), the paper title (`paper.title`; a PDF title the outline joined may carry a break and a `#` heading would end at it), the DOI and a map heading in "Read next" (`§${section.heading}`, the extractor's) were printed as they came.
- Not paper text, not touched (see "For the manager"): the model's own sentences (`claim.text`, summaries, `why`), the reader's own project text (`relation.basedOn`) and the question in the "does not address" verdict.

## 2. The rule as built (`web/src/lib/papers/reading-markdown.ts`)

Every piece of the paper's text the writer prints goes through `oneLine` (`replace(/\s+/g, " ").trim()`, the writer's own, which the questions already used):
- **`abstractParagraphs`**: each sentence is `oneLine`d **before** the `**` wrap, so a marked sentence is `**<trimmed sentence>**` with nothing inside the markers touching whitespace. A sentence with nothing left (blank, or only breaks) is left out, marked or not (never `****`), and a paragraph with nothing in it is not printed. The two paragraphs by `introCount`, the join with one space, the "At most two paragraphs" shape are unchanged.
- **`quoteLine`** (the reading's own findings / method / caveats): the whole `> text — attribution` line is `oneLine`d.
- **`evidenceText`** (every report claim's evidence, a key result's, an answer's — it is also what `questionEntryLines` hands to the page, so the page and the copy still say the same words): the quote is `oneLine`d, an empty one is no quote, and the composed `quote — §Heading · p.N` is `oneLine`d (a heading with a break in it).
- **`questionEntryLines`' Read-next label** `§Heading · p.N · M min — why`: `oneLine`d as a whole.
- **The title** (`# …`), the **DOI** and the **TLDR** line.
- Unchanged: the headings, the order of the sections, the question block, the Decision sentences, the "Copied · N words" count (it counts whitespace-separated words and a break was already a separator). One-line input prints byte-for-byte as before (pinned by the control test).

Two things worth knowing: `oneLine` is `\s+`, so it also collapses a no-break space (U+00A0) and the other Unicode spaces to one plain space — the same rule `toQuote` has always applied to the reading's quotes; and the page's own sentence array is not changed (the page collapses by itself).
