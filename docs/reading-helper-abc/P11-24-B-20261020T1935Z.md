**Head.** Branch: none — my own worktree is detached at `a226914d` (the brief's hash: the P11 round-1 head under test, `2d7a89b9`, plus docs only); the main checkout, which I did not touch, is on `reader-three-pane-p11`. ## 1. Result in six lines

1. **The masthead never moves.** `getBoundingClientRect().top` of the sticky masthead is exactly 0 after every one of 70 Tab stops, in five settled walks of 70 stops (1440 x 900 light, dark and Shift+Tab; 1280 x 720; 1093 x 614) and in an 80-stop walk with 60 ms between stops, and after every click and rail action. No ancestor of the shell is scrolled: the only elements with a non-zero `scrollTop` / `scrollLeft` at any stop are the window (`html`) and the left pane's scroll zone (`.reader-left-scroll`). The pane itself, the fixed zone, the grid, the centre, the margin, `main` and `body` stay at 0; `scrollX` is 0 at every stop.
2. **The blank band is in the picture, not in the page.** A11-tab-end-light.png (masthead at y 180, NOTES edge tab at 630 instead of 450, the dev "N" button and the key legend gone below the window) is what Playwright's `page.screenshot()` returns when it is taken while the window's **smooth scroll is still in flight**. Every fixed and sticky thing in the picture is displaced by the same amount, and the top rows are blank, because the screenshot's clip starts where the main thread said the window was, a moment before the compositor drew a frame further down. The dark shot (masthead at y 74, NOTES tab at about 523 instead of 450) is the same thing with a smaller lag.
3. **What lets it happen** is one rule: `web/src/app/globals.css:865` `html[data-scroll-behavior="smooth"] { scroll-behavior: smooth; }`, switched on by `web/src/app/layout.tsx:95` `data-scroll-behavior="smooth"`. It makes every keyboard focus-scroll an animation, and it ignores `prefers-reduced-motion`.
4. **One real movement exists, and A's dump hid it:** when focus first reaches the **left separator** (Tab stop 57 here; 50 on A's paper) the window scrolls **64 px** (settled), and the same on the way back; A read 0–2 px because it looked 30 ms into a smooth scroll. Rubric A11's evidence line "focusing a separator does not scroll the page" is true mid-page (5000 before and after) and false at the top.
5. **Fix, measured as uncommitted experiments (all restored, sha256 equal):** (a) the harness must let the window settle before a picture (nothing to change in the app for the band); (b) gate the smooth rule behind `@media (prefers-reduced-motion: no-preference)`: with it a reduced-motion context shows 0 displaced pictures in 24 captures (base: 5 in 24) and the focus-scroll is a single step; (c) for the 64-px nudge, `.reader-divider { scroll-margin-top: calc(4rem / var(--page-zoom, 1)); }` removes it at the top at 1440 x 900, 1093 x 614 and 1920 x 1080 (3 px left with Fit on); the obvious `scroll-margin-block` variant is **worse** (it throws Tab from the paper's last link to the margin separator back to the top of the page) and must not be used.
6. **Not reproduced at A's size:** I did not get a 180-px band out of `page.screenshot()` itself on my lighter paper (one 20-px band in about 70 shots, see 5.3); I got A's exact picture deterministically (5.1) and the same two Chromium calls Playwright makes naturally in a loop (5.2, 5.4). The band's height is "how far the smooth scroll advanced between two calls", so it varies from run to run (A: 180 px light, 74 px dark).

## 3. Which container scrolled, and why it can

- **The window** (`html`; `document.scrollingElement`): `body` carries `overflow-x: hidden` (globals.css:882), and because `html` is `overflow: visible` that value is propagated to the viewport; `body` itself never scrolls (its `scrollTop` is 0 in every dump). The window is the one scroller of the page, and the browser's focus-scroll moves it when a focused element is out of view or, for an element taller than the window, when its edge is not aligned (section 4).
- **`.reader-left-scroll`** (`overflow-y: auto`, globals.css:621–626): the map's rows scroll inside it. Its `scrollTop` rises at the rows' stops and is the pane's only scroller; `.reader-left` is `overflow: hidden` in split mode (globals.css:606) and is a scroll container too, but nothing ever scrolled it (its `scrollTop` is 0 at every stop), which fits the focused rows being inside the scroll zone, which takes the scroll first (I did not isolate that further).
- The masthead (`header.sticky top-0`, `z-50`) and the pane (`position: sticky; top: calc(4rem / var(--page-zoom, 1))`, globals.css:593–603) are sticky in the window: their offsets from the window are fixed whatever the window's scroll, so a window scroll cannot "push them down".

## 4. Mechanism

### 4.1 The blank band (file and line)

1. **Enabler, in the app:** `web/src/app/globals.css:865` and `web/src/app/layout.tsx:95` make the root scroll smooth (introduced with `f020a4b3`, "open on a paper, not a form"). A Tab to a far element (here the paper's last link, 18.5k px away) starts a compositor-driven animation of the window of about a second or more. The main thread's view of the window's position (`scrollY`, `visualViewport.pageTop`) trails the compositor's during the animation.
2. **Capture, in the harness:** Playwright's viewport screenshot is two Chromium calls: `Page.getLayoutMetrics` and then `Page.captureScreenshot` with `clip = { x: visualViewport.pageX, y: visualViewport.pageY, … }` and `captureBeyondViewport: false` (`/opt/node-tools/node_modules/playwright-core/lib/server/chromium/crPage.js:208–225`; `screenshotter.js:176–179`). If the window advanced by Δ px between the two calls, the clip's first Δ rows lie above the window, nothing is painted there (blank), and everything that is fixed or sticky to the window is drawn Δ rows lower. That is A's picture: blank band of Δ rows, masthead at Δ, NOTES edge tab at its place + Δ, the "N" button and the legend pushed below the window. When Δ is at least the window's height the whole picture is blank (the "wholly blank" shots).
3. A's `a10-keys.mjs` takes `shot(page, "A11-tab-end-<scheme>")` immediately after the last of 60 Tab presses, 40 ms apart, with no wait — in flight. The page height (33,603 px) made the flights long.

### 4.2 The 64-px nudge at the separators (file and line)

`reader-shell.tsx:291–319` places each `PaneDivider` as a grid item with `align-self: stretch` (globals.css:711–719), so a separator is as tall as the grid (19,365 px here; A: 33,475 px in a 33,603-px document). The divider is `tabIndex={0}` (`pane-divider.tsx:184`). For an element taller than the window that is partly visible, Chromium's keyboard focus-scroll aligns the **edge that is in view** with the window's edge: from the top, the separator's top edge (at 64 px, under the masthead and the article's padding) goes to the window's top (+64); from the page's foot, its bottom edge (64 px above the document's end) goes to the window's bottom (-64). From mid-page the separator covers the window and nothing moves, which is why A's 5000 test showed no scroll.

## 6. Fix proposals, measured

All three were applied in my worktree as uncommitted edits to `web/src/app/globals.css`, measured, and restored from a saved copy: `sha256 b189e8db7dfa0497a2d6ac44268016c3fe3d86ae7a7158609a64d35cb3958d52` before and after; `git status` of the worktree clean; the experiment diff is `out/experiments.diff` in my scratch folder, not committed.

### 6.1 For the band: the harness (A's side, nothing in the app)

Before every picture: poll `scrollY` and `visualViewport.pageTop` until unchanged for three polls of 50 ms (and the pane's `scrollTop`), then `page.screenshot()`. Measured: the settled picture of the 59-stop run and 11 of the 12 pictures of the item-3 series have the masthead at row 0 (the 12th is the wholly blank one of 5.5); instant scrolls: 13 of 13. Setting `reducedMotion: "reduce"` on the context is **not** enough on today's CSS: with it, the base page still computed `scroll-behavior: smooth` and gave 5 displaced pictures in 24 captures (339–762 px).

### 6.2 For the cause: gate the smooth rule on reduced motion (file and rule)

`web/src/app/globals.css:865`:

```css
@media (prefers-reduced-motion: no-preference) {
  html[data-scroll-behavior="smooth"] { scroll-behavior: smooth; }
}
```

This is the file's own convention (the pane's transitions at line 697 use the same media query) and the WCAG 2.3.3 reading of an 18,000-px animated jump. Measured, 1440 x 900 light:

| context | computed `scroll-behavior` | focus-scroll to the paper's end | capture loop (two Chromium calls) |
|---|---|---|---|
| base, reduce | smooth (ignored) | animated | 24 captures, 10 moving, **5 displaced**, 2 blank |
| base, no-preference | smooth | animated | 30 captures, 17 moving, **14 displaced**, 1 blank |
| with the gate, reduce | **auto** | one step (already at 18,593 on the first poll) | 24 captures, **0 moving, 0 displaced, 0 blank** |
| with the gate, no-preference | smooth (unchanged) | animated, 2.4–2.9 s in this loaded sandbox | 24 captures, 7 moving, 2 displaced (35, 521), 1 blank |

So the gate removes the animation for a reader who asked for less motion, and does nothing else; a default-motion context (A's) still needs 6.1. It is **not** a layout fix and must not be sold as "the blank band fixed".

### 6.3 For the 64-px nudge at the separators (optional; the only real movement)

`web/src/app/globals.css`, after `.reader-divider:focus-visible` (line 721):

```css
.reader-divider { scroll-margin-top: calc(4rem / var(--page-zoom, 1)); }
```

It counts the page's own 4rem above the grid as part of the separator, so the browser finds its top edge already on the window's edge. Measured, settled, Tab and Shift+Tab walks:

|---|---|---|
| 1440 x 900, 1093 x 614, 1920 x 1080 (Fit off); 1280 x 720 not run with this rule | left separator: window 64 | window **0** (left separator and, by Shift+Tab, the margin separator and the left separator: 0) |
| 1920 x 1080, Fit on (`--page-zoom` 1.2143) | not measured on the base | window 3 (the article's 16 px is scaled by the zoom, the 48-px masthead is not: 4rem / zoom is 3 px short) |
