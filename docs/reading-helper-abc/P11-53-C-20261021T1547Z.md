## 2. The defect, measured on the base (`62b35aed`)

The paper's paragraphs wrap only at spaces and hyphens (`overflow-wrap: normal`, read back as the computed value on every paragraph); `hyphens: auto` breaks nothing where the browser has no dictionary, as in this Chromium. In Chromium a run of letters joined by slashes has no break opportunity and a hyphen does (checked on a static 100-px column at 17.5 px: a 46-character run of slash-joined letters, a 53-character run of slash-joined digit groups and a 54-character run of dot-joined groups each stay on one line; the same kind of run with hyphens between its groups wraps at the hyphens; a URL-like run with `?`, `&` and `=` in it wraps too, so my URL-like run is slashes only). Since P11-48 scales the paper's own text, such a run grows with the step.

The walk's case rebuilt on an invented paper (one paragraph holding a 43-character run of slash-joined letters, nothing else unbreakable): the run passes the 416-px column (1024 × 768 and 1093 × 614) by **39 / 84 / 136 px at 1.32 / 1.45 / 1.6**, and the 1242 × 698 window by 38 px at 1.6 (the walk's owner run, other glyphs: 30 / 74 / 125 and 27). At 390 × 844 the page's scrollWidth passes its clientWidth by **9 / 44 / 86 / 130 / 182 px at 1.1 / 1.2 / 1.32 / 1.45 / 1.6** (0 at 1.0 and below): wider than the viewport from step 1.1 up, as the walk found. At 1280 × 720 and 1440 × 900 the 43-character run fits at every step (no defect there; the same as the walk).

## 3. The rule, and where it sits

```
.reading-scaled { overflow-wrap: break-word; }
```

In `web/src/app/globals.css`, in the 6-09 region, directly after the nine font-size rules and under a comment of its own (the region's first comment is P11-48's and is unchanged). **One rule on the wrapper, not one per class**, because `overflow-wrap` is inherited: everything inside the three wrappers of `reader-layout.tsx` (`common`, `words`, `additions`) gets it, whatever its class, and a new block added inside a wrapper later gets it without a new line here. A rule per size class would have missed what has no size rule (the paper's paragraphs inside a `div`, the `p` in a list, a `span` in a quote).

**`break-word`, not `anywhere`.** The brief allowed `anywhere` "if `break-word` does not reach a case you measure". It reached every case I measured (section 6: 0 px past the column and 0 past the block in all cells, and the page's scrollWidth equals its clientWidth in all of them), so `break-word` stays: it moves a break only inside a word that cannot fit a line of its own, so a line that fits wraps exactly as before (section 7), where `anywhere` would also change a flex or grid item's min-content width, which nothing here needs. Not `word-break: break-all`, which breaks every line at the edge (my own mutation, section 5, shows the line probe catches it: 12 of 22 paragraphs change).

**It reaches what the brief names** (computed `overflow-wrap`, read back in Chromium at 1280 × 720 with the invented key paper and a question asked): on Paper digestion every element with text of its own inside the wrappers is `break-word` (13 body-text elements, 7 headings (1 h2, 6 h3), the figure caption and its label, 3 others); on the Summary every element with text of its own inside the wrappers is `break-word` (60 elements: the claims and quotes, the evidence quotes, the report lines, the h2 bands, and the answers' text and reasons, which are in the collapsed "Answers generated by AI" block: the element is in the DOM and carries it, and with the block opened the run in an answer's evidence quote is measured at every step in section 6). ## 9. Unsettled — for the manager

1. **The break is the browser's emergency break.** A run too wide for any line is cut where the line ends (in the case I looked at, a word of letters and slashes broke in the middle of its fourth group), not at a slash. A slash is not a break opportunity in Chromium, so I did not try to add one (`<wbr>` after a slash would be a change to the paper's markup, a component change, and is not in the rule). If the owner wants breaks at the slashes of a name, that is a separate rule and a `wbr` or a zero-width space at extraction time.
2. **The line before a broken run can be loose.** When the run starts a new line because it cannot fit on the rest of the previous one, that previous line is justified across the gap (it was before the change too, when the run stood on its own line past the column). `break-word` (and `anywhere`) does not start the run on the line it could fill; only `word-break: break-all` would, and it changes every line (M1 and M6 above). Not changed.
3. **Chromium only.** No Firefox or Safari here. `overflow-wrap: break-word` is the long-standing value in both; with a dictionary for the paper's language (`hyphens: auto` working) the browser should hyphenate a long word before it takes an emergency break (a hyphenation point is an acceptable break), so the owner's browser may show a hyphen where Chromium here shows none; I could not test that here. Both stay inside the column.
4. **Not measured:** Fit to screen on (the page `zoom` composes with the step; this rule reads neither); a margin card's own text (the cards are outside the wrappers and unchanged, and a card standing level with a run no longer has a run under it, because the run now ends inside the column); the lightbox and the left pane (outside).
5. **My two wide stress runs already stood past the column at scale 1.** The 70-character run passes the 416-px column by 109 px at scale 1 at 1024 × 768 on the base, and the 52-character one by 17; they are not the owner's case (that is the 43-character run, which fits at scale 1), so the "unless a word already overflowed at scale 1" exception of the brief is used only on the stress paper, and each use is named in section 7.
6. The dev server's `.next/dev/cache` was deleted before every start, as the brief says. Every non-local request the page made was refused by the harness's route (only local ones pass); the first-visit setup script logged two console errors (one failed request, one 500 from the dev server) before any reading page was open; I did not examine them, and none came from a reading page measurement.
