## Findings, ranked (privacy first)

### SHOULD-FIX

**F1 — `lib/papers/deep-report.ts:889-893` logs a provider's error whole on the no-question path (§3d 17; §1b "nothing per-user … private PDF text … in server logs").**
```
console.error("[papers/deep-report] generation failed:",
  questions.length > 0 ? (err instanceof Error ? err.name : typeof err) : err);
```
The comment above it says an error's message may quote the prompt, "so only its kind is logged" — but only when questions are present. Without questions the prompt still holds the paper's body (for a standalone upload, a private PDF's text). Reproduction (dev server on 3711, key + Deep report on, an upload, no questions): my stub answered the Pass 1 call with HTTP 400 whose body was the first 600 characters of the prompt it was sent (what a provider that echoes its input would do; the OpenAI provider keeps `detail.slice(0, 400)` of an error body in its thrown message). The server's log then held `[papers/deep-report] generation failed: Error: OpenAI API error 400: {"task":"Extract sentences from this paper's body …` — the prompt's first 400 characters, which are the task text and the paper's title (the body follows at about 480 characters, so a provider echoing from further in would log body text). The three catch blocks of the report route itself (`route.ts:270`, `:533`, `:710`) log the kind only, and so do the explain, plain and guide routes and this function's with-questions branch (measured: the same stub on a request with questions leaves no question in the log; M8 below shows the tests that pin that). How likely a real provider is to echo its prompt in an error body is not measured (BLOCKED: no real model). Smallest fix: log `err.name` in both branches (the `questions.length` condition is the only difference). Also noted, same class and not new: the upload route logs `err` whole at three catch blocks (`upload/route.ts:136`, `:157`, `:322`; §1h.13 (g) accepted) and `full-text.ts:231` logs a pdf.js read error whole.

**S1 — mutation M3 survives: the Pass 1q cache key is pinned only against sets whose first sorted question differs (a test gap; the production code is right).** `deep-report.ts:502` builds `` `${docHash}|${sha256(sorted.join("\n"))}` ``. Changed to hash only `sorted.slice(0, 1)`, all 920 tests in `src/lib/papers` and `src/app/api/papers/report` stay green. The counting test (`deep-report.passes.test.ts:430`, "two question sets: Pass 1 once, Pass 1q twice, Pass 2 twice") uses two one-question sets, so a key that ignores every question after the first sorted one passes. In use that would hand a set that merely adds a question the earlier set's relevant sentences, by question index — a later question would get another question's evidence. A key made of the document and the number of questions (M3b) IS caught by that same test, so the guard is half-pinned. Fix: one case in which a set differs from another only by a question added after the first sorted one (Pass 1q called twice). Graded SHOULD-FIX because the cache key is the §3d 11 guard.
