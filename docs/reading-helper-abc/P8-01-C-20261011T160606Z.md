## 2. The cause, as found (lines at `2b22e0ef`)

The manager's reading holds; nothing different was found.

- `web/src/app/page.tsx` 169–186: the auto-load effect returns early only when `!authReady`, `!feedAutoLoadKey`, `isLoading`, or `feedTopicsKey === feedAutoLoadKey`; otherwise it calls `loadFeed({ lanes: ["papers"] })`. Its deps include `isLoading` and `feedTopicsKey`.
- `web/src/store/feed.ts` 2035: `feedTopicsKey: topicsKey` is written inside the papers lane's success `set()` and nowhere else (besides `resetLocal` 3053, which nulls it).
- `web/src/store/feed.ts` 2145–2150: the papers lane's `catch` sets `feedError` only. `fetchRealFeed` (875 on) lets `apiFetch` throw for any non-ok answer (`lib/api.ts` 26–32: `ApiError` for 503 and 404 alike), so both statuses take this one path.
- `web/src/store/feed.ts` 2245–2253: after `allSettled` the load sets `isLoading: false`.

So after a failure `feedTopicsKey` still differs from `feedAutoLoadKey`, `isLoading` goes `true` then `false` (a dep change), and the effect fires again at once, for as long as the page is open. The 404 variant (BACKLOG-22, A P5-03) is the same path: no separate cause.

One detail worth knowing, found while writing the count test: the loop needs a render that *shows* `isLoading: true` between two loads (a real network round trip gives React that render). A load that settled entirely inside one batch would not loop.

## 3. The fix, as built

- `store/feed.ts`: new `feedFailedKey: string | null` (initial `null`; doc comment on `FeedState`). Written in the papers lane's `catch`, next to `feedError`, with the same `topicsKey` that load used (not the profile's key at the time the failure lands), only when the load is still the current one (`requestId === feedLoadSeq`, the existing guard). Cleared: as a papers load starts (same `set` that clears `feedError`, only when `wantsPapers`), in the success `set` next to `feedTopicsKey`, and in `resetLocal`. Not in `partialize` (transient like `feedError`).
- `lib/feed/auto-load.ts` (new, beside the store's `lib/feed/` neighbours such as `empty-reason.ts`): `shouldAutoLoad({ autoLoadKey, topicsKey, failedKey, loading })`, the page's four old conditions plus `failedKey === autoLoadKey → false`; and `useFeedAutoLoad({ ready, autoLoadKey, topicsKey, failedKey, loading, load })`, the effect that applies it (a `useEffect` over the same dependencies as before, `load` being the page's callback).
- `app/page.tsx`: reads `feedFailedKey` from the store; the inline effect is replaced by `useFeedAutoLoad(...)` with `load` a `useCallback` over `[authOutcomeKnown, loadFeed]` that does exactly what the effect body did (sets `provisionalOwnerLoadRef` when the auth outcome is unknown, then `loadFeed({ lanes: ["papers"] })`). The `provisionalOwnerLoadRef`, the correction effect (fires at most once), the "Try again" (`onRetry`, a direct `loadFeed`), `refreshFeed`, and the ledger's rerank (a direct `loadFeed` 400 ms after a change) are untouched.
- **No automatic retry.** A failure leaves the page in its existing error state ("Try again"), or, with papers already on screen, the head's red "failed" line and its Refresh button; both call `loadFeed` directly. A manual retry that fails records the key again: one request per press.

**Could the page be rendered on the hook runtime? No.** `DailyBriefingPage` uses zustand's React binding, `Suspense`, `Link`, the auth gate, the digest loader and more, and the runtime implements only `useState` / `useMemo` / `useCallback` / `useRef` / `useEffect` (existing `page.test.tsx` says the same). So the effect is a hook of its own now (`useFeedAutoLoad`) and the count test mounts that hook, with the page's wiring reproduced in the test by `useHomePage`. The runtime renders once per round and a round outlasts a whole stubbed load, so `useHomePage` hands the hook one distinct store state per render, in order, as the browser's renders do (explained in the file's header); without that the runtime never shows the effect `isLoading: true`, and the loop does not appear even on the old code.

Request counts. Before (measured by others on the old code, in a browser): about 85 a second per tab; 253–265 in 3 s (C P7-16), 301 in 5 s at a 404 (A P5-03). I did not re-measure in a browser (no browser here; A P8-05 does it). On the hook runtime: **30 requests in the 500 ms window before, 1 after**, and 1 again 500 ms later.

If the owner wants one attempt per visit, clear `feedFailedKey` when the page mounts or unmounts; not done, since §1h.41 (a) says no automatic retry.
