## 1. The rule as built (`paper-body.tsx`, `useSelectionListener`, and the comment on `SELECTION_DEBOUNCE_MS`)

- A flag `down` lives in the effect (per mount, reset on remount). `pointerdown` (document, capture) sets it when `event.isPrimary && event.button === 0 && event.pointerType !== "touch"`, and clears the pending timer. A touch pointer, a secondary button and a non-primary pointer do not set it: they keep the 150 ms wait.
- `selectionchange` arms the 150 ms wait only while `down` is false.
- `pointerup` and `pointercancel` (document, capture) and the window's `blur` clear the flag and arm one read with delay 0 (the drag's last `selectionchange` came before the release, so nothing else would schedule it). A click that collapses a selection reports `null` through the same read.
- Keyboard selection (shift + arrows), touch handles and programmatic changes keep the 150 ms. The upstream `sameSelection` goes on dropping duplicates (it is not touched).
- Every listener added is removed in the hook's cleanup, with the same capture flag it was added with: `selectionchange`, `pointerdown`, `pointerup`, `pointercancel` on the document, `blur` on the window, and the timer.
- The two comments in the hook's header and on `SELECTION_DEBOUNCE_MS` now say what the wait is for. The two comments in `explain-box.tsx` / `explain-dock.ts` that describe "settled" are P9-17's.

## 2. One refinement of the brief's wording (one line to revert)

The brief says the release, the cancel and the blur "clear the flag and arm one read". I arm the read only when a press of the primary pointer set the flag (`if (!down) return`). Reason: a release or cancel that follows a touch, a secondary button or a second pointer is not the end of a drag, and an unconditional delay-0 read there would take the wait away from touch ("touch … keeps the debounce", same sentence of the brief); a blur with no button down has nothing to free. Pinned by the three `it.each` tests and "reads nothing for a release, a cancel or a blur that no press … came before". Reverting is deleting that one line.

The head's own read → render was 23.6 … 64.7 ms, so a dev render over 50 ms is not something this change adds.
2. **Unsettled — a lost release.** If the primary release never reaches the document (not `pointerup`, not `pointercancel`, no window `blur`: e.g. a release over a native dialog or a devtools pane in some browsers), `down` stays true and a selection (keyboard too) is not offered until the next pointer event on the page, which clears it. The brief's rule has no timeout and I added none. A later press always resets it; a `pointercancel` (browser drag-and-drop of selected text) and a `blur` free it. Not seen in Chromium.
