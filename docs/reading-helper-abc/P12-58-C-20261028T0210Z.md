## The rules as built

1. **The upload keeps its document.** `full-text.ts` gains `keepUploadDocument(hash16, meta, doc)` and one key function `uploadDocKeyFor` that both `uploadFullText` (the read) and the write use, so the route cannot write under a key the reading does not read. The upload route calls it after the PDF and the record are stored (`if (doc) await keepUploadDocument(hash16, meta, doc)`). Same key as before (owner, hash16, revision, extractor version, figure revision), same owner-private sidecar (digest of the key in the file, 0600). Only a document with sections is kept (a scan is read again, as before). A failed write is `console.warn` with the error's code only (the old message), returns false, and never fails the upload.
2. **"Pending", not "none".** A new module `full-text-pending.ts` documents and spells the value `"pending"` (`markFullTextPending`, `isFullTextPending`). The reading route, in both its upload branch and its public branch, builds `markFullTextPending(buildReading(paper, null))` when its wait ended first or the attempt threw (`readingFor`). A settled "no text" stays `none` / `pdf_empty` / `paywalled`. Headers as today: a private reading is `private, no-store`; a public pending answer is `no-store`, never the day-long cache.
3. **The page keeps asking.** `use-reading.ts`: after a pending answer it waits 2, 4, 8, 16 s, then 20 s, and asks again; one request in flight (a sequential loop); the budget is three minutes from the first ask (the next ask is made only if it would start by 180 s); aborted on unmount and on a change of paper or revision (the wait timer is cleared too); a pending answer is never written to the browser's cache, whatever its headers say. The first ask failing is final as before; a dropped connection or 5xx after a pending answer is a blip in the wait; a 4xx or an unknown shape ends it. New return field `wait: "pending" | "gave-up" | null`; `fromServer` stays **false** while pending or gave-up, so `useRestoreReaderPlace({ ready: fromServer })` keeps waiting for the real reading and its record is not dropped on the abstract. `sentencesWhileWaiting` (pure, exported) puts one line from `copy.ts` `FULL_TEXT_WAIT` in place of the reading's first sentence (the abstract-only notice) while pending, and after the budget a line that says the full text could not be read yet and names the reload; a model's own sentence (a report answered) and any sentence after the first stay. The page calls it in its existing `sentences` memo. When the body arrives `fetched` becomes the settled reading: the same state update the page always had for a first answer; nothing in the hook scrolls or remounts. `full-text.ts` also holds a settled upload reading for 60 s in `uploadsInFlight` (the in-flight attempt): the page asks every 2 to 20 s with an 8 s wait per ask, so an extraction that ends in the gap between two asks, and keeps no document (a scan), would otherwise be started again by the next ask, and again, for as long as the page asked. A read that threw is not held.
4. **Nothing else changes.** The settled reading's shape, `READING_VERSION` (16), the cache keys, Tier 0 / keyed behaviour, the supplement (`?upload=`) branch, the abstract-only notice for a paper that really has no text layer (settled `pdf_empty` / `none` do not poll).
