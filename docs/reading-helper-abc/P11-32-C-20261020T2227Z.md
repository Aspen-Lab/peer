## The rules as built

**1. A quote list never repeats a key (§1h.130).** `quote-list.tsx` keyed each item by ``${heading}\u001f${text}``; it is now ``${index}:${heading}:${text}``. The list is static (a few quotes, drawn in the order picked), so the index is stable; the heading and the words stay in the key so a different quote in the same place is a different item. The words and the order are unchanged.
- *The test.* The server renderer does **not** look for repeated keys (a `console.error` spy around `renderToStaticMarkup` of two identical quotes logged nothing), and the suite has no DOM, so `quote-list.keys.test.tsx` reads the keys off the element tree `QuoteList` returns (it has no hooks, so it is called as a function) — the keys React's reconciler reads: two identical quotes → two different keys; three of one sentence and two of one figure caption → five keys; the same words under two headings and two sentences under one → distinct; the same list gives the same keys twice (stable); both copies are drawn, in the order given; an empty list draws nothing.
- *Every other keyed list in `components/reader/`, read (the grep of `key={` over the folder, 50 matches, two of them in comments):* none can repeat, none changed. `claim-list.tsx` (78, 117), `for-your-questions.tsx` (117, 129), `report-sections.tsx` (183, 185, 327, 392) and `paper-words.tsx` (137) lead with the index already. `for-your-questions.tsx:145` keys the read-next rows by `kind:sectionId`, and `readNextItems` (`lib/papers/report.ts`) keeps one row per section ("a section named twice drew twice and broke React's keys", §1g.19 a). `in-your-library.tsx:60` keys the topics by their label, and `topicsOf` keeps one per normalised label. `question-field.tsx:528, 536` key the chip groups by label and the chips by text: `exampleQuestions` and `cleanQuestions` drop a repeated question (by their `sameKey` / lower-cased text) before the chips are built, and the standing group has its own label. `report-sections.tsx:438` keys the glance's facts by text, and the six facts are different phrases (`GLANCE.preprint`, `journal(venue)`, `code`, the age, `team(n)`, `match(score)`; the first two are an if / else). `explain-box.tsx:479` (three constant column labels), `plain-button.tsx:118` (`PLAIN_LEVELS`), `key-legend.tsx:53` (`entry.action`), `reader-tabs.tsx:70`, `record-block.tsx:85` (`door.href`), `reading-map.tsx:247, 251` (`run.name` / `part.name`: the constants `place`, `size`, `role`, `page`, `words`, `minutes`) are static. `paper-body.tsx` (`eq:i:k`, `label:ordinal`, `section.id ?? i`, `g…`/`p…`/`m…` + a spot id) and the rest are index- or id-keyed.
- *Can the extraction produce two identical quotes, and how often (from the code, `lib/papers/reading.ts`)?* Yes. `pickFindings` / `pickMethod` / `pickCaveats` build their pool from `sectionSentences`, which has no de-duplication, and take the first `MAX_FINDINGS = 3` (by score), `MAX_METHOD = 2` and `MAX_CAVEATS = 3` quotable sentences. The only de-duplication is `taken` in `buildReading`, and it is by text **between** blocks (a sentence already in findings is not taken again for the method, nor for the caveats); within one block nothing stops a sentence that the section says twice (a PDF's repeated line, a legend repeated under two figures) or two sections that share a heading ("Methods" twice) from giving two identical quotes. A scratch probe of `pickMethod` on a document with that shape returned the two identical quotes (not kept as a test: whether both should show is not this item's). How often in real papers is not something the code can say: no count exists in the repo, and I did not measure any; it needs a real section that repeats a sentence, which the invented PDF does on purpose (its paragraphs repeat one filler line, so its keyless "How it was done" is two identical quotes).

**2. Script scrolls respect reduced motion (BACKLOG-107).** One new helper, `web/src/lib/reader/scroll-motion.ts`: `scrollBehavior()` returns `"auto"` while `(prefers-reduced-motion: reduce)` matches and `"smooth"` otherwise (read at the moment of the scroll; `"smooth"` where there is no window or no `matchMedia`, i.e. a server render and the plain-Node suite, which is what these scrolls were). `keyboard.tsx:84` reads the same query inline and is **not exported**, so there was nothing to reuse; it is left as it is (not my file; it could call the helper). `"auto"` rather than `"instant"` because it defers to the stylesheet, whose smooth scrolling is already inside `@media (prefers-reduced-motion: no-preference)` (held by `globals.css.focus-motion.test.ts`), and it is what `keyboard.tsx` passes.
- `evidence-quote.tsx` `followSectionLink` (the "§Heading" link when the body is under the other tab): `behavior: scrollBehavior()`.
- `note-tags.tsx` `goToPassage` (the notes' blue square, the strip's go-to-the-passage; one scroll, two branches — a page block's first mark centred, else the block's top): both branches use one `scrollBehavior()` read.
- `app/papers/[id]/page.tsx` `scrollToBody` ("Read it here" / the `t` key): `behavior: scrollBehavior()`. Its inner "only where it is not already on the screen" rule is untouched.
- *Tests.* `script-scrolls.test.ts` (11): `followSectionLink` and `goToPassage` (a page block's mark, a block's top, a paragraph's top for a body highlight and for a sticky) under a stubbed window that prefers reduced motion (`"auto"`) and one that does not (`"smooth"`); the reading page's `scrollToBody` by its source (it cannot be mounted in this Node-only suite; the repo's `page.*.test.ts` way); a scan of every non-test file under `src` that no other file names `behavior: "smooth"`; and that the three files use the helper. `scroll-motion.test.ts` (4): reduce → auto, no preference → smooth, read each time, no window / no `matchMedia` → smooth.
