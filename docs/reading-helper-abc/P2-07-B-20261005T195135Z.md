### Cause, in the code

`web/src/app/api/papers/report/route.ts` (line numbers at `1887b6e`, unchanged at `2c6b776`):

- **`:662-664`** `const quotaDecision = body.deepReport ? await consumeDeepReport(gate.entitlement) : { allowed: true };` The charge is gated on `deepReport` alone.
- **Stream:** `streamReport` resolves its own provider only afterwards, inside `start()` (**`:417-420`**). The no-provider tier 0 exit (**`:421-431`**) is reached after the unit is spent.
- **JSON:** the deep branch resolves after the charge (**`:679-684`**) and falls to `generateShallowReport` on a null provider (**`:685-694`**).
- `consumeDeepReport`'s own doc comment (`lib/usage/deep-report-quota.ts:196-202`) says "Call it **immediately before** `resolveProvider`". The route follows that comment, and the comment is the root of the ordering.

## 2. The smallest reordering (both transports, one `consumeDeepReport` call site)

**Shape:** resolve the provider once in `handlePost`, after the entitlement gate. Charge only when `body.deepReport` is set **and** the resolved provider has `generateJsonText`. Thread that same provider into `streamReport` instead of letting the stream resolve its own. In the JSON branch, use the threaded provider. `resolveProvider` is synchronous and pure (`registry.ts:182-204`), so it gains nothing by being deferred into the stream.

**Before (`route.ts`, `1887b6e`):**

### What cannot move, and why

1. **The malformed-claim and owner checks (`:613-624`) stay before any provider resolution.** They are F1/P0-05's privacy order, and two existing tests assert `resolveProvider` is not called on a 404. The sketch resolves after them.
2. **The entitlement gate (`:631-636`) stays before the resolution.** That is R-SEC-2 ("one entitlement check, before every `resolveProvider`"), and `providerCtx` needs `gate.entitlement` to mint the `EntitledContext`.
3. **`consumeDeepReport` stays in `handlePost`, above the transport branch, as the only call site** (Ruling 9 point 2). It must finish before `streamReport` builds its `Response`, because:
   - the stream's **first** event (`quota`, `:413-415`) is a function of the decision;
   - the `mode` value (`tier2` vs `tier1`, `:440-441`) is a function of `quotaDecision.allowed`.
   It therefore cannot move into the stream's `start()` (a second call site), and it cannot move after any model call.
4. **A company-budget refusal cannot be known before the charge.** It is decided per model call inside `meterCall` (`metered.ts:119-136`), from the actual prompt (`companyBudgetShapeFor`, `:81-106`). The first such call is Pass 1 or Pass 2, after `getFullText` and after the `mode` event has gone out. Moving the charge after it would break quota-first. It would also spend a company-budget reservation (and on Pass 1, real tokens) before the reader's allowance is checked, which is the wrong direction for a spend cap.
5. **`generateShallowReport`'s own `resolveProvider` (`:245`) stays.** It serves the shallow default and every fallback, and is never charged. R-QUOTA-3's exemption still rests on `body.deepReport` gating the charge.

## 4. Risks and what I could not determine

- **POLICY 1 — a refusal by the company AI budget still charges a unit after the reordering.** It cannot be fixed by order (§2 "cannot move" 4). Options:
  - **(a) Accept (recommended for P2-07).** Treat it like every other attempted deep read that degrades after the charge.   - **(b) Refund.** `consumeDeepReport` returns a handle that applies a negative increment to exactly the keys it incremented, mirroring `settleCompanySpend`'s negative `increment` (`company-budget.ts:593-610`); the Supabase RPC accepts a negative `p_by` (`20260904000000_usage_counters.sql:58-77`, plain `value + excluded.value`).
