## 2. Findings

**F1 — while the empty panel stands, the first Escape of a visit is taken by it: it does not reach the Keyboard-shortcuts dialog, and it hides the window together with whatever else it clears (regression from P8-06, known family — §1h.46 (a) — with a seam the ruling does not name).**
Evidence (1440, key profile, the panel standing): (i) `?` opens the dialog "Keyboard shortcuts" (`dialogs: ["explain", "Keyboard shortcuts"]`); Escape #1 → the panel is hidden, `--explain-dock` removed, **the dialog still open**; Escape #2 closes the dialog. Control, no key (no panel): Escape #1 closes the dialog, Escape #2 goes back to the briefing. (ii) after a question's report, a click on the term "LCO" switches to Paper digestion and marks its first occurrence; Escape #1 clears the mark **and** hides the panel in the same press (`panel` true → false, `--explain-dock` `376px` → empty). So a reader with a key loses the window they asked to have always open the first time they press Escape for anything else, and needs one Escape more for the shortcuts dialog.
Lines: `explain-box.tsx` 863–887 (`useEffect` on `shown`: document capture `keydown`, `preventDefault`, `stopPropagation`, `setSession(null)`, `setHidden(true)`), `shown = open !== null || standing`.
Proposed fix: §1h.46 (a) as ruled (with the empty state showing, Escape does nothing to the window and is not consumed) **and add the shortcuts dialog, and any open `[role=dialog]`, to the follow-up's "a test per seam"** next to the lightbox, the term highlight (measured above: it is hit today) and "back". The lightbox is not measured here (§10).
Regression: yes (P8-06 `d5d9e447`). Already ruled; the follow-up is pending, not on this head.

**F2 — in Fit the foot legend is taller than the 28 px the window leaves for it, so the window's box overlaps the legend's box (low; not new).**
Evidence: Fit's whole-page zoom is applied inside `[data-zoom-root]`, where the legend lives; the window is mounted outside it on purpose. At 1440 × 900 the zoom is 1.142 and the legend measures 868–900 (**32 px**); at 1920 × 1080 it is 1.378 (**39 px**, 1041–1080); at 2560 × 1300 it is 1.838 (**51 px**). The window's lowest extent is `height − 28` (`DOCK_BOTTOM_PX`), so it stands **4 / 11 / 23 px** into the legend's box when it is tall. The legend's text never reaches the window (its right-most text ends at x 1039 / 1345 / 1794, the window starts at 1080 / 1560 / 2200), so nothing readable is covered; only the legend's top edge. Plain, dark, touch: 28 px, no overlap (872 = 872).
Lines: `explain-dock.ts` `DOCK_BOTTOM_PX = 28`; `explain-box.tsx` `placePanel` 288–297 (`top = clamp(…, 48, height − 28 − 160)`, `maxHeight = height − top − 28`).
Proposed fix: take the legend's own height (its rect, or `--legend-h` times the page zoom the box can already read) instead of the constant; or let the box's bottom edge be `height − legendHeight`. The pin that ties 28 to `--legend-h` at a 16 px root stays valid for the unzoomed page.
Regression: no — the constant is P7-15's; P8-02 kept it.

**F3 — in `next dev` a mount that finds a wanted key sends two identical feed requests 1 ms apart; the production build sends one (info; not new).**
Evidence: topic change on the profile, back to Home: dev **2** (same body hash, t = 10514 and 10515 ms), production **1**; a failed topic change with papers already shown: dev 2, production 1. The first load after a fresh page has `ready` false at mount and sends 1 in both. Cause by reading: React Strict Mode runs the auto-load effect twice on mount; the second run's closure still has `isLoading: false`, so it calls `loadFeed` again; the store's request-id guard makes the first result lose, but both requests go out. The inline effect before P8-01 had the same exposure.
Proposed fix (optional, owner's call on "fewer requests"): a same-key in-flight guard in `loadFeed` (or a ref in `useFeedAutoLoad`).
Regression: no.

**F4 — the numbered-equation rule has no real-document witness (info).**
Evidence: mutation 12 (the numbered branch disabled, nothing is ever lifted) changes **nothing** in the extractor run on the owner's paper or the printout (0 equations either way — neither document has a numbered line); only its 7 unit tests go red. The rule's positive side is pinned by unit tests alone. C P8-03 said the same of its set of 13 PDFs.
Proposed fix: none for P8; if a numbered multi-line equation ever matters (§1h.43 (c)) it needs a fixture from a real paper that prints one.
Regression: no.
