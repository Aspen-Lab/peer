## What was built

**The counter — `lib/usage/explain-quota.ts` (new).** `consumeExplainTurn(entitlement, { searched }, now)` → `{ allowed: true }` or `{ allowed: false, reason: "exhausted" | "unavailable", resetsAt }`. Units are tenths of a deep-report unit: `EXPLAIN_TURN_TENTHS = 1`, `EXPLAIN_SEARCH_TENTHS = 10`; caps `EXPLAIN_TENTHS_PER_DAY = 400` per reader per UTC day (key `explain_tenths:<user>:<YYYY-MM-DD>`) and `ALL_USERS_EXPLAIN_TENTHS_PER_DAY = 20000` for all readers (key `explain_tenths:house:<YYYY-MM-DD>`), both incremented on every charge, either can refuse, the house checked first as the deep-report counter does. Fails closed: an unreadable counter refuses with reason `unavailable`, writes the one stable `[quota] store unavailable` line (`logStoreUnavailable("explain", userId)`) and **no** usage row; a real trip writes an error line and the awaited `breaker` usage row (`path: "explain"` / `"explain-house"`); no user id is refused as `exhausted` without touching the store. ## Choices beyond the brief (small readings, consistent with the rulings)

1. **The toggle is on a line of its own above the input, not in the same row.** The brief says "at the start of the control row"; in a 360 px card a 123 px pill, Send and the gaps would leave the input about 147 px. The container is still the one sticky row (`data-explain-controls`, `flex flex-wrap`) and the toggle is its first child (`w-full`), so it is at the start of the row's content, and the textarea and Send are unchanged below it. Without the box's `search` view the row is as it was.
2. **A refused charge is taken back out of the counters** (a negative increment, which the store already supports — the company-spend settlement uses it). The counters are incremented first and read after, so without it a searched turn refused at 395 tenths would leave 405 and shut out the five normal turns the reader still has. Done best-effort: a write that fails leaves the count high, never low (the safe direction).
3. **The two explain requests read their own response** (`postExplain` in `explain-thread.ts`, a plain `fetch`) instead of `apiFetch`: `apiFetch` throws an error that drops the response's body, and the 429's `reason` is what tells a spent allowance from one that could not be checked. `lib/api.ts` is outside the item's files, so I did not extend `ApiError`. Every non-refusal status maps as before (the existing tests are unchanged).
4. **`ReplyResult` / `AskResult` gain two strings, `"exhausted"` and `"allowance_unavailable"`;** `ThreadView` gains two optional fields (`quota`, `search`), so every existing test's view is valid and the toggle exists only where the box gives it.
5. **A usage `breaker` row on a real trip,** for both caps, as the deep-report breakers do (`path: "explain"` / `"explain-house"`; `byok` left unset, "not known"): the brief says "no usage row on an outage", which I read as a row on a trip. The error line names no reader.
6. **The server strips web addresses from a reply** (`https://…`, `www.…`; closing punctuation kept). "No link to a web source is ever shown" is a hard rule and a grounded model may write one into its words; the page never makes a link of text, but the address itself would be a pointer to a source. The quote is not touched (it is the paper's, verified or dropped on its own).
7. **A searched call's ledger path is `json:search`** (the usage row's free-text `path`), so the owner can price searched and plain calls apart from the first real run.
8. **The tooltip is hidden while the toggle is disabled** (`peer-disabled:hidden`): with the day's explanations used up it covered the very line that says so.
9. **The toggle's off state uses the strong border** (`border-border-strong`, as Send does) rather than the gist chip's faint one: at the chip's border it read as text, not as a button.
10. **The first message's request never carries `search`,** and the server ignores it if sent.
11. **The 400 / 40 question (a policy reading — please confirm).** The constants are the brief's, `EXPLAIN_TENTHS_PER_DAY = 400` and `ALL_USERS_EXPLAIN_TENTHS_PER_DAY = 20000`. With a normal turn at 1 tenth and a searched one at 10, that is **400 normal turns or 40 searched turns a reader a day** — but the brief's gloss ("forty normal turns, or four searched, or any mix") and the original §1h.4 ("≤40 explain turns per reader per day") are both 40 tenths. I kept the explicit constant and left the question open: one constant to change, and the counter test reads it, so the 40-turn reading would be a one-line edit plus the two literals in the constants test.
12. **Commit trailers.** The task says to end the message with the two Fable lines; §1c says the attribution follows the committing agent's model, and my harness mandates `Claude Sonnet 5.5`. As in P3-02 and P3-02b, the Sonnet line comes first and the last two lines are exactly the brief's.

## Observations (no change made; for the manager)

- **D2a.** The freemium campaign's standing decision D2a says "the operator never pays for search, for anyone, on any plan"; `lib/search/system-key.ts` freezes Gemini grounding to unavailable for the pool searches. This item, as ruled (§1a.10, §1a.11, §1h.4), sends a searched turn through Gemini's Google Search tool — on Peer's own Gemini key for a reader who has none, so a searched turn can spend the operator's search budget. The ruling is later and explicit, and I built it; it is bounded by ten tenths a searched turn, the per-reader cap and the house ceiling. If D2a should hold, the smallest change is that `supportsWebSearch` is true only for a reader's own key (BYOK) — the route already treats "cannot search" as a plain turn with the note.
- **The company-spend estimator and the ledger price tokens only.** `companyBudgetShapeFor` ignores `webSearch`, and `logGemini` does not read `toolUsePromptTokenCount` or the number of search queries, so with the company cap on a searched call is reserved and settled as a plain one, and the first real run's ledger row will under-state its cost. Reading those two numbers is the follow-up that makes the price (and the cap) true; it touches `gemini.ts` and `company-budget.ts`.
- **`REPLY_MAX_TOKENS` is 400 for a searched reply too.** Without JSON mode the model may add words around the object (the route finds the object and strips a fence); a truncated one is "unavailable" and, by the ruling, still charged. Worth a look at the first real run.
- **A hit is served to a reader whose day is spent** (the charge is after the memory, as ruled). A refused first message does not remember a refusal client-side: the next passage's click asks again (a 429 costs nothing).
- **Facts for P3-02d's privacy entry, as landed:** what is sent is as in the P3-02 and P3-02b checkpoints plus, with the toggle on, `search: true` and the provider's Google Search for that one message; the server keeps the one-hour memory (hash keys, verified turns only; a searched reply under its own key), one debug line per model turn (`userId` hashed to 12 hex characters, `tenths`, `promptChars`, `answerChars`, `cached`, `thread`), the explain counters (`explain_tenths:<user>:<day>` and the house's, tenths, never any words), and — as for every model call — the usage ledger's row per provider request (provider, model, token counts, path; no text). The browser keeps the passage, the answer and the thread, with `searched` and `searchUnavailable` marks; the toggle's state is never kept.
