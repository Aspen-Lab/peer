## The rules as built

1. **A tie weighs both intents by half** (`reading-map.ts`). `questionIntent` still returns `none` for a tie (its test stays), but the route no longer reads that as no intent: `tiedIntents(question)` names the intents that share the most counts (two or more), and `intentWeights(question)` is the one clear intent's `ROLE_WEIGHTS` row, whole; or, for a tie, the product over the tied intents of each row's weights at the square root; or all ones for no cue. `routeQuestion` multiplies a leaf row's score by `intentWeights(question)[role]`. A tie takes **no strong slot** (`favouredRoles` still reads `questionIntent`, so `keepRoleSlot`, which is not mine, is untouched): a half boost only moves scores. `ROLE_WEIGHTS`' values are not touched.
2. **The cue words that misfire.** `current`, `time`, `rate`, `model`, `role` leave `INTENT_WORDS`; `EVERYDAY_CUES` holds each with its phrases (one count however many phrases name it; a phrase matches whole words, and its last word in the plural too):
   - `current` (parameter): applied / plating / deposition / pulse / constant / limiting / galvanostatic current, what current;
   - `time` (parameter): how long, time constant, reaction / growth / deposition / annealing / heating / residence / holding / soaking time;
   - `rate` (parameter): what rate, growth / deposition / plating / scan / sweep / heating / cooling / ramp / flow rate;
   - `model` (mechanism): theoretical / physical / mechanistic model, model of the, model for the;
   - `role` (mechanism): the role of, role of, role in, roles of, plays / play / playing / played a role, key role.
   The three parameter words also count **beside another process variable in a list** (`besideVariable`: a comma, slash, "and" or "or" between them, either order; the variables: temperature, voltage, potential, concentration, pressure, thickness, pH, current, time, rate), which keeps the owner's second question ("… temperature, current, etc.") a parameter question; "current density" after `current` is not the word. Never as bare words: "the current literature", "at the same time", "time-resolved", "rate capability", "machine learning model", "model system", "role model", "role-based" are no cue.
3. **The overlay agrees with the body** (BACKLOG-73). When the strong-group cap lowers a part, its row stays medium (the cap's) but its paragraph lines are drawn at the tier the body draws the paragraph: `reading-map.tsx` reads a part's line tiers from `sectionMark(route, <the trunk's id>)` (the body's own mark), falling back to the row's mark for anything else. `reading-partition.ts` changed in its doc comment only; its test file gained the pure pin that a lowered group keeps its `paragraphs` and `topParagraphs` whole beside the trunk's strong tier.
