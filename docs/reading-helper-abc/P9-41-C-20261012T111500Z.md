## 1. The rules as built

**Rule 1 — below 768 px the control is the bar's cell (commits 2 and 3).** `thumb-bar.tsx`: `Rail` reads `useExplainOffer()`; while it is true the rail's centre cell (where "3 of 10" stands) renders `<ExplainCell />` instead of the position text. `ExplainCell` is a `<button type="button" data-explain-ask>` whose text is `EXPLAIN.ask` ("Explain this?" — the pill's accessible name), classes `col-start-2 justify-self-center inline-flex min-h-11 items-center rounded-full border border-border-strong bg-surface px-4 font-mono text-caption text-heading …`: **44 px (`min-h-11`), bare — not behind `hover:none`, because the bar is a touch surface by its place** — in the 56-px rail's middle. Its press is `readerActions()?.explain?.()`: the page's own `explain` action, which is `explainOpen.current` = the box's `openBox`, **the same function the `e` key and the pill's press called** (`start(next)`), so the window opens for the same selection and then sits where P9-20 and P9-17 put it. Its mouse-down is cancelled (as the pill's: the press must not take the selection with it). ← Briefing (column 1) and Next → (column 3) keep their places and sizes (§6 b); the tabs mode (Today · Search · Saved · You) never carries the cell. `explain-box.tsx`: `askAt` is null under 768 px (`viewport.width >= MASTHEAD_MIN_VIEWPORT_PX` joins `next && !docked`), so **no floating pill is rendered below 768**, whatever the paragraph's right edge (a gutter that exists at 767 gets no pill either).

**The signal (commit 2).** `web/src/lib/reader/explain-offer.ts` — a module-level store of one boolean: `explainOffered()`, `setExplainOffer(next)` (tells nobody for an unchanged value), `subscribeExplainOffer(listener)`, `useExplainOffer()` (`useSyncExternalStore`, the server snapshot is the live value: nothing sets it on a server, so server markup has no cell and hydration agrees). **Chosen over the `readerActions` channel** because that channel is a registry of imperative handlers read at the moment of a press: it holds no state and tells nobody when it changes, and the bar must draw differently while a selection stands; so the *state* is this boolean and the *action* stays the channel's `explain`. It holds nothing about the selection (not its words, not its place). The box is the only writer; the bar the only reader.

**Rule 2 — the cell goes with the selection (commit 3).** `explain-box.tsx` computes `inBar = nextAt !== null && viewport.width < 768 && nextAt.bounds.bottom > 0 && nextAt.bounds.top < viewport.height`, where `next` is the settled selection that has a control on offer (a key, or a defined term of the paper: the pill's own condition) and `nextAt` is where it was last measured (the box already re-measures on every scroll frame and resize, `measured`), and publishes it in an effect (`setExplainOffer(inBar)`); a second effect takes the offer back when the box unmounts. So the cell goes (a) when the selection collapses (`next` is null), (b) when the selection's whole box is outside `[0, innerHeight)` — scrolled above or below the screen (**the stale-pill case P9-20 left**) — and returns when it is scrolled back, (c) when the window opens on the selection (`offered` is null once the passage is the window's), (d) when the window is resized to 768 px or more (the pill is the control again), (e) when the page is left. A selection partly in view (its last line at the head, or hidden under the bar's 56 px but inside the viewport) keeps the cell.

**Rule 3 — from 768 px with no gutter, the pill is 44 px under hover:none (commit 3).** `ask`'s class list gains ` [@media(hover:none)]:min-h-11` **only when its place is the legend's** (`"bottom" in askPlace`); otherwise the pill is as P9-20 built it (same place, `bottom: legend + 8`, right edge on the column's). `placeButton` loses its thumb-bar branch (the strip above the bar's 56 px and the safe area) with the pill it placed: with no gutter it returns the legend's strip at every width the box asks about; `explain-dock.ts` loses its copy of the bar's height (`THUMB_BAR_PX`), which nothing clears now, and its comment says so.

**Rule 4 — a mouse at ≥ 768 px with a gutter: nothing changes (commit 3).** The gutter pill's class list is the head's (pinned: the legend's is the gutter's plus the touch class, nothing else differs); with a mouse neither pill changes; from 1024 px the control is the window's header control and the box offers nothing to the bar. Measured identical at 1024 and 1440 (§6 d).

b. **The width test is `viewport.width` (`window.innerWidth`), not a `matchMedia` call.** The brief's test line says "a matchMedia stub"; the box has no other `matchMedia` and reads `innerWidth` everywhere (`placeButton`, the dock's 1024), and its tests stub `window.innerWidth`. So on a tablet of 768 to 1023 px with a key (a gutter, hover:none) the pill is still 34.1 px tall (measured, §6 e). Follow-up in §7 item 3.

e. **"Scrolled out of view" is the selection's whole box outside the viewport**, as the box measures it (`bounds`); a selection under the bar's strip but inside the viewport keeps its cell.
f. **`data-explain-ask` is on the bar's cell** too, so every consumer of "the Explain control" selects the same attribute.
g. **The red commit keeps `tsc` at 0 with `// @ts-expect-error` lines** on its three imports of the not-yet-existing module/export (`explain-offer`, `ExplainCell`); commit 2 removes exactly those lines (it is the only edit to the tests in commit 2 besides the bar test's feed-store stand-in, see §3).
