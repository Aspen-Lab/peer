## 0. The answer in eight lines

1. **Seven model calls touch an uploaded paper's reading** (§1). The one that runs once per paper, early, and already addresses every paragraph is the **gist call** (`paragraph-guide/route.ts:204`).
2. **The skeleton is a real saving only when the parse is sound.** The mode-A review prompt is 3,378 / 1,988 / 5,651 tokens (P1 / P2 / P3) against 8,767 / 8,970 / 7,243 for the whole text: 61 % / 78 % / 22 % saved (§2.3).
3. **The answer is corrections only** (`move_start`, `set_role`, `split`, `unsure`), in a fixed JSON object numbered against the draft as given. Every index and role is checked. An unusable answer, a refusal or a timeout leaves the rules' draft exactly (§3). `merge` is not needed; `split` is.
4. **A disputed part gets one more look at its own text:** a correction against a high- or medium-confidence part, or a part listed in `unsure`. At most 3 looks per paper, at most 6,000 characters (about 1,650 tokens) each (§3.5).
5. **Cache the corrections, not the structure.** Key: `docHash | rules version | skeleton version | prompt version`. The model is recorded, not keyed. Nothing of the paper is in the entry (§4).
6. **Piggyback on the gist call:** +574 / +491 tokens. **Separate call:** +3,378 / +1,988. But the gist call is skipped above 120 paragraphs (P3), runs only on the deep-report switch, uses the small tier, and its prompt is pinned byte for byte by tests (§5).
7. The stub cannot judge structure. A test double that reads the skeleton's invented heads can, and a prototype round trip on an invented paper reaches the truth (§6).
8. **C1's 100 % can be shown only by a real model.** §7 is the protocol: 6 papers, 6 arms, 5 runs each on the natural drafts, seeded draft errors, about 360 calls and 1.6 million input tokens. The key stays in the test server's environment only.

**The candidate to ride on is the gist call.**
- It runs once per document, early (the hook fires as soon as the reading has a body).
- It sends every paragraph under an address (`sectionId`, `paragraphIndex`) the map already uses.
- It returns an object with a per-paragraph list, and the route already merges a structural answer (`partition`) beside it.
- Truncation is guarded by a token allowance that grows with the paragraphs.

**Why not pass 1:**
- It addresses sections, not paragraphs, and a corrected start needs a paragraph.
- It exists only inside the report stream, and only above 10,000 body characters.
- Its output feeds the report's evidence chain, so a prompt change risks the deep report, which the owner reads first.
- Its cache is memory-only for an hour.

The explain call also sends structure (`explainMapLines`), but per passage, not once.

## 2. The skeleton (step 2)

### 2.1 What it is built from

The app's own parse: `readableSections(doc)` (`reading-map.ts:95`; abstract dropped, empty sections dropped, equations lifted) and `readingMapOf` (`reading-map.ts:274`), which already gives a row's `level`, `page`, `canonical`, `role` and `openingOf`.

Paragraph ordinal `i` is **global** over that list (0 … N−1), so a correction is one integer. `(sectionId, paragraphIndex)` is recovered from the section header's `from-to`. The same list is what the body renders (map row k = body section k), so the browser and the server number paragraphs alike.

**Finding: the app's parse has no page per paragraph.** `ExtractedSection.page` is the page the section's *heading* sits on (`html-text.ts:17`); `ExtractedDocument` carries nothing finer. The skeleton puts the page on the section header line. A per-paragraph page would need the extractor (`pdf-outline.ts`) to carry it; nothing in this design needs it.

### 2.2 Grammar (normative; one line per item, as strings in a JSON array)

```
## <sectionId> L<level> p<page|-> <bucket> "<heading, 60 characters at most>" <from>-<to>
<i>[ <counts>] | <head>              mode A: the first H words of the paragraph, "…" when cut
<i>[ <counts>]                       mode B: an interior paragraph, counts only
fig <label> p<page> | <first 8 words of the caption>
```

**Counts.** `F` figure refs, `T` table refs, `C` citations, `N` numbers with a unit, `V` procedural verbs ("was/were" + a lab verb), `W` first-person signposting ("we show/find …", "this work"). Each is followed by its integer, in that order, with zeros left out. The regexes are Appendix B. **They must be one function shared with the Tier-0 rules** (`paragraphFeatures(text)`), so the model sees the very counts the rules used.

**Draft lines.** The draft goes beside the skeleton, one line per part: `<k> <from>-<to> <role> <high|medium|low> <evidence tags>`. The tags are rule names and counts ("heading:methods", "V-run", "inherited"), never paper words, so the draft may be logged and stored.

**Interface assumed from B P12-40:**
- Parts cover 0 … N−1 contiguously.
- Roles are always one of the five: `setup`, `method`, `evidence`, `interpretation`, `apparatus`. `body` never appears in a draft.
- Each part has a confidence and short evidence tags.
- There is a `rulesVersion` string.

**The prompt** is Appendix B: system + user JSON (task, `paper {pages}`, `roles` with a one-line definition each, the counts key, `skeleton`, `draft`, `outputSchema`, six rules). Its **fixed part is 2,413 characters (about 600 tokens)**. The title is not sent (the review needs none), and nothing about the reader is.

**Modes.**
- Mode A (every paragraph has its head) is the default. The head length is a knob (8 / 12 / 16 / 20 words, table below).
- Mode B is the over-budget fallback. Heads appear only for the first two and the last paragraph of each part, every paragraph of a part the rules are unsure of, and the first paragraph of each section. Counts appear everywhere.
- If mode A exceeds **24,000 characters (about 6,000 tokens)**, use B. If B still does, cut heads to 8 words and drop `fig` lines. If that still does, do not review: the draft stands and a `too_large` count is logged.
- All of P1–P3 fit in mode A.
- A section with a single paragraph may fold its header onto the paragraph line (saves about 15 characters each). That is worth doing once the parse stops producing 99 of them.

### 2.4 Two findings about the input, not about the design

* **P3's parse (at this head) makes the skeleton almost as big as the paper.**
  - It has 100 "sections". 56 of their headings are 15 words or longer, and none ends in a full stop (sentence-shaped lines are read as headings).
  - 14,950 of its 25,996 characters sit in headings. Its 194 paragraphs average 55 characters. Mode A's per-line overhead then exceeds the text it summarises.
  - This is a parse defect (extraction or Tier-0, B P12-40), and the skeleton must be built from the **repaired** paragraphs.
  - The same defect costs elsewhere: `explainMapLines` for P3 is 24,123 characters (about 6,000 tokens) on **every** explain turn, against 3,098 / 2,184 for P1 / P2.
* **P1 and P2 are two-column papers whose columns are welded in places.**
  - A paragraph's head can hold a line of the left column and a line of the right.
  - Page-footer and affiliation lines sit in or as paragraphs. About nine of P2's 40 paragraphs begin with or consist of a footer line, and they carry stray `F`/`C` counts.
  - The review corrects part boundaries and roles; it cannot repair paragraph text. Its evidence is as noisy as the parse. The real-model run (§7) will show this as a ceiling that Tier 0's parse sets.

## 3. The response (step 3)

### 3.1 Schema

One JSON object. The OpenAI provider forces `response_format: json_object` (`openai.ts:84`), so a bare array would fail.

```json
{ "corrections": [
    { "op": "move_start", "part": 1, "toParagraph": 41 },
    { "op": "set_role",   "part": 2, "role": "method" },
    { "op": "split",      "part": 3, "atParagraph": 77, "role": "apparatus" } ],
  "unsure": [4] }
```

Part numbers are the **draft's** and paragraph numbers the skeleton's. Nothing is renumbered after a correction; the application order is fixed (§3.2). `corrections` is always present, empty when the draft is right. Output allowance: **600 tokens** (40 corrections at about 14 tokens each).

**Why these three, and why not `merge`.**
- `move_start` and `set_role` cannot create a boundary. A draft that under-segments (a methods run inside a results part, or a trailing run of references inside a conclusion) could never be repaired, so `split` is needed.
- `merge` is not needed. The structure already merges neighbours of one role (`mergeNeighbours`, `reading-partition.ts:152`), so a spurious part is removed by giving it its neighbour's role.
- There is no `move_end`, because a part ends where the next begins (`sanitizePartition` rule 7). There is no `delete`, for the same reason as merge.
- There is no confidence or free text: it costs output tokens, and the ruling shows an inferred role exactly like a named one (§1h.424 (a)).
- `unsure` is the only extra: it drives the second look.

### 3.2 Validation (a reference implementation, tested, is Appendix A)

1. The answer parses (`parseModelJson`, `explain.ts:931`, as the gist route does) as an object with an array `corrections`. Anything else is **not an answer**: the draft stands and nothing is cached.
2. Per correction, against the draft as given:
   - `op` is one of the three (exact).
   - `part` is a whole number with `0 ≤ k < parts`.
   - Paragraph numbers are whole numbers with `0 ≤ i < N`. A digit string is accepted; a float or a negative is not.
   - `role` is one of the five after trim and lower-case. There are **no aliases** (the old `method → experimental` alias map belongs to the old role names), and `body` is refused.
3. `move_start`: `k ≥ 1` (part 0 starts at paragraph 0 and never moves). The new start lies after the previous part's first paragraph and no later than this part's last, differs from the current start, and occurs at most once per part.
4. `set_role`: a role different from the part's own, at most one per part.
5. `split`: `at` strictly inside the part (after its first paragraph, up to its last). A role is required. At most 3 per part, all distinct.
6. At most **40 corrections** are read; the rest count as rejected. A rejected correction never invalidates the others.
7. `unsure`: unique valid part numbers.
8. Application, in fixed order:
   - All `move_start`, each only if the starts stay strictly ascending against the starts so far (otherwise dropped, never repaired).
   - Then all `set_role`.
   - Then all `split`, each only inside the part's current range.
   - Then neighbours of one role merge, the first start is set to 0, and each part ends where the next begins.
9. The result must be **sound**: starts at 0, contiguous, ends at N−1, roles in the set. The check cannot fail after steps 1–8; it is kept so a future edit cannot ship an unsound structure.

### 3.3 Fallback (Tier 0 never breaks)

The draft is computed by pure code from the document **before** any call and is what the reader sees at once. The review only replaces it when a valid answer arrives.

Every failure below returns the draft unchanged and writes nothing to any cache:
- **No key or no provider.** The client never asks (as the gist hook); the route answers `{unavailable:true}`.
- **A provider error:** an HTTP error, an empty reply (the OpenAI provider raises "empty content"), or an abort.
- **A timeout.** The providers' own guards differ (OpenAI 15 s, `openai.ts:86`; Qwen and DeepSeek 20 s; Anthropic 60 s; Gemini 120 s), and the route's `maxDuration` would be 60. So the review wraps the call in its own `Promise.race` of **30 s** (precedent: `fullTextWithin`, `app/api/papers/[id]/reading/route.ts:32`), and a late result after the race is ignored.
- **An unusable answer** (§3.2 step 1).
- **A skeleton over budget** (`too_large`).
- **An upload that changed meanwhile** (`410`, as `paragraph-guide/route.ts:237`).

A reply that is usable but has some rejected corrections applies the valid ones and counts the rest. The client keeps a failed or unusable attempt for **1 hour** (so a broken key does not re-bill every open) and a network failure not at all.

### 3.4 Where the answer meets the draft

The route returns the **corrections** (plus `unsure`, the second-look verdicts, `rulesVersion`, a `draftDigest` and the model id), not the structure. The browser runs the same pure `applyCorrections` on the draft it computes itself. If the digest does not match its draft (rules changed), the review is ignored and asked again. So the server never ships a structure, and a stored entry can never outvote the current rules.

### 3.5 The second, targeted look

* **Trigger:**
  - (a) A correction (any op) on a part whose rule confidence is `high` or `medium`.
  - (b) A part in `unsure`.
  - A correction against a `low` part triggers nothing: the rules already said they were unsure.
  - Order: high, then medium, then unsure, then part number. **Cap: 3 looks per paper.**
* **Text:** only the disputed span, each paragraph clipped to 600 characters, **6,000 characters in all** (outer paragraphs dropped first).
  - For `move_start`: the paragraphs 3 either side of the old and the new start (not leaving the two parts).
  - For `set_role` and `unsure`: the part, thinned to its first 3, last 2 and every fourth between.
  - For `split`: the 4 either side of the point.
* **Prompt:** a short system line, the roles, the paragraphs as `{n, text}`, the two readings (draft, review) as plain statements ("paragraphs a–b are R, c–d are S"), and `{ "verdict": "draft" | "review" }`. 60 tokens out; the review's tier.
* **Outcome:**
  - `review` keeps the correction; `draft` drops it.
  - An invalid or failed second look drops the correction when it contradicted a high or medium part (the rules stand), and keeps it when the part was low.
  - An `unsure` part stays as the draft.
* **Cost:** one look is at most 6,000 + 600 characters, about **1,650 tokens** (P1, P2) or 739 (P3, whose largest part is 2,355 characters). Three at most: 4,950 / 2,217. Expected: 0 or 1.

## 4. Cache and privacy (step 4)

**Entry (small, no paper text):** `{ v, docHash, rulesVersion, skeletonVersion, promptVersion, draftDigest, corrections[], unsure[], secondLooks[{part, verdict}], model: "<provider>/<model id>", reviewedAt }`, about 1 KB. It holds indices, role names and rule tags; never a head, a heading or a sentence.

**Key:** `docHash | rules:<STRUCTURE_RULES_VERSION> | skel:<SKELETON_VERSION> | prompt:<REVIEW_PROMPT_VERSION>`.
- `docHash = explainDocHash(doc)` (`explain.ts:1320`, `sha256(JSON(doc))`) is the paper version. For an upload the document already changes with the upload's `revision` and extractor version (`upload-store.ts:359`).
- **The model is recorded in the entry, not in the key.** Switching provider must not re-bill a reviewed paper; an explicit "review again" overwrites (decision D5).

**Where it lives, following how the other model results are kept today:**

**Privacy:**
1. The order of checks is the gist route's (`paragraph-guide/route.ts:130–245`): malformed claim and `ownedUpload` (incl. `paperIds`), then `requireAiRequest("paper-structure", 20)`, then provider, then `getFullText` (owner-scoped), then cache.
2. The skeleton **is paper text**: about the first 16 words of each paragraph, 15–35 % of the words. It therefore leaves for a model only on the switch that sends the other texts, `providerConfigured && deepReportRequested` (`page.tsx:823`; P3-05 §1h.8 (1)). This is decision D1.
3. The prompt carries no title and nothing about the reader.
4. Logs hold sizes and counts only (`console.debug` as `paragraph-guide/route.ts:224`: prompt and answer characters, parts, corrections, rejected, second looks, fell-back kind). Errors log `err.name`, never a message, which can echo the prompt.
5. Headers are `PRIVATE_UPLOAD_HEADERS` for an upload, `no-store` otherwise.
6. The key is the request's `llmOverride` or the local developer opt-in. It is never in a prompt, an entry or a log line.

At the repository's own listed Gemini prices (`provider-models.ts` comment: 3.1 Flash-Lite 0.25 / 1.50, 3.6 Flash 0.75 / 3.75 dollars per million input / output), a separate large-tier review is about 0.3 cent on P1 and 0.2 cent on P2. Piggyback on the small tier is a few hundredths of a cent. The money is small either way; **the argument is coupling, not cost**.

**For piggyback:**
- It is nearly free where the gist call runs.
- The model reads the full 1,200-character paragraphs instead of 16-word heads, so it is better informed.
- It satisfies ruling §1h.424 (b), "rides on that call if it saves tokens".

**Against:**
1. The gist call does not run above 120 paragraphs: P3 here, and a long article soon. A second path is needed anyway.
2. It runs only on the deep-report switch.
3. Its tier is small, and 100 % is the requirement. The repository's own measure (`provider-models.ts`, comment on `reportModelTier`) found the larger model clearly better for report quality.
4. The call's prompt is pinned byte for byte for headed papers (`paragraph-guide.partition.test.ts`: `HEADED_USER`, `HEADED_MAX_TOKENS`). The change must be gated to leave the no-review prompt identical.
5. A truncated answer loses everything. `corrections` must go **before** `gists` in the schema (the `partition` precedent) with added allowance, and a failure of either feature then costs the other.
6. A stub or test branch must answer both keys at once.

**Recommendation.** Build the **separate** call: own route `POST /api/papers/[id]/structure`, own hook, own cache, one stub kind. It works for every paper length, never touches the gist call's output, and can run on the large tier over a short prompt.

Keep **piggyback** as an A/B arm in the real-key run (§7). If the small-tier full-paragraph review is as exact as the large-tier skeleton review on all papers, move to it where the gist call runs and keep the separate call as the fallback (cap exceeded, gist unavailable).

When Tier 0 divides every paper, retire the model's own `partition` request from the gist prompt (P10-07a: `partitionRules`, `PARTITION_TOKENS` at `paragraph-guide.ts:229`). That saves about 600 characters and 300 allowed tokens and moves two pinned test goldens.

## 6. How a C tests it without a real model (step 6)

**Three layers; nothing calls a model.**

1. **Pure functions on invented fixtures** (the repository's pattern: "Invented paragraph k about tide pools …").
   - A builder `inventedPaper([[role, count], …])` makes paragraphs whose first words name their role and whose body carries the role's counts (method: "were heated at 120 °C for 2 h"; evidence: "Fig. 2 shows a rise of 14 %").
   - The skeleton, sanitizer, applier, second-look chooser and keys are tested directly.
2. **A truth-reading test double** (`modelDouble(userPrompt)`).
   - It reads only the prompt it is given (the skeleton's heads and the draft's lines) and infers each paragraph's role from the invented head.
   - It diffs the runs against the draft and returns the minimal corrections: `set_role` where a part's start matches, `move_start` where one is within 3 paragraphs, else `split`.
   - This is the analogue of the stub answering "from the paper's own sentences": the stub *reads the prompt*, never the world.
   - **Prototyped and green in scratch** (`measure/double.test.ts`). A draft with a boundary off by two and a wrong role, and a draft that fused two roles, both end equal to the truth. A right draft draws no correction. The prompt holds the heads only, not the paragraph tails.
3. **Route tests with an in-test provider** (the `route.partition.test.ts` pattern: `vi.hoisted` mocks for `resolveProvider`, `ownedUpload`, `getFullText`; `generateJsonText: vi.fn`), scripted per case:

| Case | Provider returns | Expect |

| Invalid answer rejected | Out-of-range part, unknown role `"banana"`, op `"delete"`, 60 corrections, `{}`, prose, `[]` | The valid ones applied or, if none, `fellBack`; draft unchanged; **no entry written** |

## 7. What only a real model can show, and the protocol (step 7)

**Only a real model can show:**
- (a) Recall: does it find the errors a draft really has?
- (b) Damage: does it leave a right draft alone (no false corrections)?
- (c) Whether 16-word heads and counts suffice, against the full paragraphs.
- (d) JSON compliance, refusals and latency of the owner's provider (the OpenAI path aborts at 15 s).
- (e) Run-to-run stability.
- (f) The second look's net effect.
- (g) The true token cost against the 4-characters estimate. The server already prints `[llm] provider/model in= out=` per call (`usage-log.ts:27`).
- (h) Whether the prompt's role hints help or only repeat the rules' own mistakes.

**Papers.** P1–P3 are the development set, on which the rules and the prompt may be tuned. P4–P6 are held out: once the Tier-0 rules have landed and been scored first-sight, a new worker (not this one) opens them. They inform nothing until the first-sight score is reported.

**Truth.** For each paper, over the Tier-0 paragraph ordinals the reader sees: parts and roles written independently by two blind readers who see the rendered body, then adjudicated. They are stored in the harness, not in Git. C1 (ruling §1h.424 (c)) is: every part right (role and start) and none extra. Report **exact** (start equal) and **±1 paragraph** where the adjudicators marked a boundary soft. The owner's 100 % is the exact figure.

**Inputs per paper.** The natural draft, plus **10 seeded drafts**, because a right natural draft shows nothing. The seeds are:
- a boundary moved by 1, 3 and 8 paragraphs;
- a role flipped;
- two parts fused;
- one part split wrongly;
- a trailing apparatus run swallowed;
- a leading run shifted;
- a role swapped between two adjacent parts;
- one random.

**Arms** (each a flag of the same harness):
- S-A: separate, mode A, large tier.
- S-B: separate, mode B.
- S-small: mode A, small tier.
- S-A + second look.
- PB: piggyback on the gist prompt, small tier, only where it runs.
- FT: oracle, the whole parsed text instead of the skeleton, large tier.

Prompt variants: with and without the "judge by heads and counts" hint.

**Runs.** 5 per arm on every natural draft (the same prompt and key each time, no seed control: `generateJsonText` exposes none, so the spread is real), and 3 per seeded draft on S-A only.
- Natural: 6 papers × 6 arms × 5 runs = 180 calls, about 1.0M input tokens (3.4k, 1.6k, 3.4k, about 5k, 10k and 9k per call by arm).
- Seeded: 6 × 10 × 3 = 180 calls, about 0.6M.
- Total about **360 calls, 1.6 million input tokens, a dollar or two at the repository's listed prices**.

**Pass bar.** An arm passes C1 when, on every natural draft of every paper, all 5 runs end exactly equal to the truth. The damage rate on right drafts must be 0 in every run. The exact repair rate on seeded drafts is reported, not a bar. Anything less is not "100 %": the failures are read, and the rules or prompt change on P1–P3 only. The held-out papers are measured once, first-sight, before any change informed by them.

**Reported**, per paper and arm:
- Exact C1 and ±1.
- Precision and recall of corrections.
- Rejected-correction rate and fell-back rate.
- Second looks asked and their verdict flips.
- Measured tokens in and out (from the `[llm]` lines) and latency.
- The ratio of measured tokens to the full-text arm. This is the number the owner asked to see.

**How the key stays in the server's environment only:**
- The owner hands it over out of band.
- A launch script reads it from a file outside the repository with permissions 0600 into the environment of **one** process: `PEER_DIGEST_PROVIDER=<provider>` and that provider's variable (`OPENAI_API_KEY`, …) on `npx next dev -p <port>`. This is the local-development opt-in (`registry.ts`, `env/local-dev.ts`); a deployed runtime ignores it.
- It is never on a command line, never echoed (`set +x`), never in the page, a cookie, `localStorage`, a request body (`llmOverride` is not used), a prompt, a log line or this repository.
- The server runs **without** the stub (the stub refuses any non-local host with 503).
- The harness runs outside vitest (`vitest.setup.ts` strips model keys from every test).
- It prints sizes and booleans only, counts its calls against a ceiling and stops at it, and begins with a dry run that prints prompt sizes and calls nothing.
- Before any commit: `grep -rlF -- "$KEY"` over the worktree and the scratch (file names only, never the line). Afterwards the file and the process are removed.

## Appendix A — reference sanitizer / applier (scratch prototype; 9 cases + 5 double round trips pass; 4 mutations caught)

Scratch only (`measure/review.ts`, `review.test.ts`, `double.test.ts`); no paper text in it. A mutation check removed in turn the neighbour merge, the role-set check, the part-0 guard and the start move. Each broke at least one test, and the unmutated files pass 14 of 14.

```ts
export const ROLES = ["setup", "method", "evidence", "interpretation", "apparatus"] as const;
export type Role = (typeof ROLES)[number];
export type Conf = "high" | "medium" | "low";
export interface DraftPart { from: number; to: number; role: Role; conf: Conf }
export type Correction =
  | { op: "move_start"; part: number; toParagraph: number }
  | { op: "set_role"; part: number; role: Role }
  | { op: "split"; part: number; atParagraph: number; role: Role };
export interface Answer { corrections: Correction[]; unsure: number[] }

export const MAX_CORRECTIONS = 40;
const isRec = (v: unknown): v is Record<string, unknown> => typeof v === "object" && v !== null && !Array.isArray(v);
const whole = (v: unknown): number | null =>
  typeof v === "number" ? (Number.isSafeInteger(v) && v >= 0 ? v : null) : typeof v === "string" && /^\d{1,9}$/.test(v) ? Number(v) : null;
const roleOf = (v: unknown): Role | null => {
  const r = typeof v === "string" ? v.trim().toLowerCase() : "";
  return (ROLES as readonly string[]).includes(r) ? (r as Role) : null;
};

/** 1. The answer, per correction, against the DRAFT as given. null = not usable at all (the draft stands). */
export function sanitizeReview(raw: unknown, draft: readonly DraftPart[], paragraphs: number): { answer: Answer; rejected: number } | null {
  if (!isRec(raw) || !Array.isArray(raw.corrections)) return null;
  const out: Correction[] = []; let rejected = 0;
  const moved = new Set<number>(); const roled = new Set<number>(); const splits = new Map<number, Set<number>>();
  for (const c of raw.corrections as unknown[]) {
    if (out.length >= MAX_CORRECTIONS) { rejected++; continue; }
    if (!isRec(c)) { rejected++; continue; }
    const k = whole(c.part);
    if (k === null || k >= draft.length) { rejected++; continue; }
    if (c.op === "move_start") {
      const i = whole(c.toParagraph);
      // part 0 never moves; the start stays in the draft's own room: after the previous part's first paragraph, up to this part's last
      if (i === null || k === 0 || i >= paragraphs || i <= draft[k - 1].from || i > draft[k].to || i === draft[k].from || moved.has(k)) { rejected++; continue; }
      moved.add(k); out.push({ op: "move_start", part: k, toParagraph: i });
    } else if (c.op === "set_role") {
      const role = roleOf(c.role);
      if (role === null || role === draft[k].role || roled.has(k)) { rejected++; continue; }
      roled.add(k); out.push({ op: "set_role", part: k, role });
    } else if (c.op === "split") {
      const at = whole(c.atParagraph); const role = roleOf(c.role);
      const seen = splits.get(k) ?? new Set<number>();
      if (at === null || role === null || at <= draft[k].from || at > draft[k].to || seen.has(at) || seen.size >= 3) { rejected++; continue; }
      seen.add(at); splits.set(k, seen); out.push({ op: "split", part: k, atParagraph: at, role });
    } else rejected++;
  }
  const unsure = Array.isArray(raw.unsure)
    ? [...new Set((raw.unsure as unknown[]).map(whole).filter((n): n is number => n !== null && n < draft.length))]
    : [];
  return { answer: { corrections: out, unsure }, rejected };
}

export interface Part { from: number; to: number; role: Role }
/** 2. Starts first, roles next, splits last; any that breaks order is dropped, never repaired. */
export function applyCorrections(draft: readonly DraftPart[], paragraphs: number, answer: Answer): { parts: Part[]; applied: number; dropped: number } {
  const starts = draft.map((p) => p.from); const roles: Role[] = draft.map((p) => p.role);
  let applied = 0; let dropped = 0;
  for (const c of answer.corrections) {
    if (c.op !== "move_start") continue;
    const k = c.part;
    if (starts[k - 1] < c.toParagraph && c.toParagraph < (starts[k + 1] ?? paragraphs)) { starts[k] = c.toParagraph; applied++; } else dropped++;
  }
  for (const c of answer.corrections) if (c.op === "set_role") { roles[c.part] = c.role; applied++; }
  const list = draft.map((_, k) => ({ start: starts[k], role: roles[k] }));
  const extra: { start: number; role: Role }[] = [];
  for (const c of answer.corrections) {
    if (c.op !== "split") continue;
    const lo = starts[c.part]; const hi = starts[c.part + 1] ?? paragraphs;
    if (c.atParagraph > lo && c.atParagraph < hi && !extra.some((e) => e.start === c.atParagraph)) { extra.push({ start: c.atParagraph, role: c.role }); applied++; } else dropped++;
  }
  const all = [...list, ...extra].sort((a, b) => a.start - b.start);
  const merged: { start: number; role: Role }[] = [];
  for (const p of all) if (merged.length === 0 || merged[merged.length - 1].role !== p.role) merged.push(p);   // neighbours of one role are one part
  merged[0] = { ...merged[0], start: 0 };
  return { parts: merged.map((p, i) => ({ from: p.start, to: i + 1 < merged.length ? merged[i + 1].start - 1 : paragraphs - 1, role: p.role })), applied, dropped };
}

/** 3. Whole-structure invariants; anything else falls back to the draft. */
export function sound(parts: readonly Part[], paragraphs: number): boolean {
  if (parts.length === 0 || parts[0].from !== 0) return false;
  let next = 0;
  for (const p of parts) { if (p.from !== next || p.to < p.from || !(ROLES as readonly string[]).includes(p.role)) return false; next = p.to + 1; }
  return next === paragraphs;
}

/** The whole step: never throws, never returns an unsound structure. */
export function reviewStructure(raw: unknown, draft: readonly DraftPart[], paragraphs: number): { parts: Part[]; answer: Answer | null; fellBack: boolean } {
  const base: Part[] = draft.map((p) => ({ from: p.from, to: p.to, role: p.role }));
  try {
    const s = sanitizeReview(raw, draft, paragraphs);
    if (!s) return { parts: base, answer: null, fellBack: true };
    const r = applyCorrections(draft, paragraphs, s.answer);
    return sound(r.parts, paragraphs) ? { parts: r.parts, answer: s.answer, fellBack: false } : { parts: base, answer: null, fellBack: true };
  } catch { return { parts: base, answer: null, fellBack: true }; }
}

/** 4. Second look: a correction against a high or medium confidence part, or a part listed unsure; at most three, strongest contradiction first. */
export const MAX_SECOND_LOOKS = 3;
export function secondLookTargets(draft: readonly DraftPart[], answer: Answer): { part: number; why: "contradicts-high" | "contradicts-medium" | "unsure" }[] {
  const rank = { "contradicts-high": 0, "contradicts-medium": 1, unsure: 2 } as const;
  const seen = new Map<number, keyof typeof rank>();
  for (const c of answer.corrections) {
    const conf = draft[c.part].conf;
    if (conf === "low") continue;
    const why = conf === "high" ? "contradicts-high" : "contradicts-medium";
    if (!seen.has(c.part) || rank[why] < rank[seen.get(c.part)!]) seen.set(c.part, why);
  }
  for (const k of answer.unsure) if (!seen.has(k)) seen.set(k, "unsure");
  return [...seen].map(([part, why]) => ({ part, why })).sort((a, b) => rank[a.why] - rank[b.why] || a.part - b.part).slice(0, MAX_SECOND_LOOKS);
}
```
