## 2. The rule, as built — and why it is not the rule the brief expected

**The two scores did not differ by summation order. They differed by the wall clock.** The state's BACKLOG-48 (and the test's own comment) read a 5.85e-10 gap as float noise. A last-bit float difference is about 1e-16; 5.85e-10 is six orders larger, which was the first sign. The cause, read from the code and then measured:

- `runFeedPipeline` passes its `now` option to the pool build only. Read-time scoring is `scorePaperCandidates(...)` → `scoreItems(items, profile, weights)` with `scoreItems`' fourth parameter left at its default `now = Date.now()` (`lib/scoring/combine.ts`), and `scoreRecency` is `exp(-ageDays / 14)` of that clock.
- The test runs the pipeline twice in sequence, so run 2 scores recency against a clock a few ms (under load, a few hundred) later than run 1. For this fixture one millisecond moves the score by about 4.3e-12 (recency weight 0.1, recency about 0.05 for a 2026-09-01 paper on 2026-10-12).
- Everything else is identical in the two runs: the same ranked order, and the terms are added in the same order (`buildIdf` counts integers; `cosine` iterates each item's own vector in token order; `poolPercentile` is a ranked lookup). A `Promise.all` settling order, a `Map`/`Set` order over a pool built in another order, and a non-total sort were each checked and none reaches the score.

Measured with a scratch probe (`scratchpad/p9c43/p943-probe.test.ts.txt`, not committed), the same two runs as the test, with a deliberate pause between them:

| clock | pause between runs | score(rollover) − score(live) |
|---|---|---|
| real | 0 ms (three runs) | −1.3e-11, −4.3e-12, −3.0e-11 |
| real | 20 ms | −9.4e-11 |
| real | 200 ms | **−8.6e-10** (outside the old 5e-10 tolerance) |
| real | 1000 ms | −4.3e-9 |
| `Date` frozen | 0 / 20 / 1000 ms | **0, exactly equal** (all three) |

The old tolerance holds only while the second run starts within about 116 ms of the first, which is why it failed once under load in P9-33 and never alone. Order of the two result lists is identical in every row.

So the sum is **not** the thing to order, and nothing in `lib/feed/` needs changing: there is no function to name. The fix is in the test file only, and it is stricter than the brief's "keep the 9 digits":

1. **The test freezes `Date` for both runs** — `vi.useFakeTimers({ toFake: ["Date"] })` and `vi.setSystemTime(new Date(2026, 8, 24, 9, 0))` (the same instant as the pipeline's `now` option) at the top of "gives a rollover candidate no special boost or penalty…". Only `Date` is faked, so the source-timeout timers and the promises are real. `vi.useRealTimers()` is added to the file's existing `afterEach` (a no-op for every test that never froze the clock; it restores the clock even if an assertion throws).
2. **The assertion is `toBe(bScoreAsLive)`**, replacing `toBeCloseTo(bScoreAsLive!, 9)`. The test's own name already says "byte-identical". With the clock frozen the computation is pure, so exact equality is deterministic (it held with a real 1 s pause between the runs), and it leaves no tolerance for a boost or penalty to hide in (the 9-digit version could not see anything under 5e-10).
3. The comment that blamed summation order is replaced by the true cause and the measured figures above.

No tolerance, skip, retry or looser digit count is used anywhere.

## 7. For the manager

- **BACKLOG-48 can be closed as "clock drift, not summation order".** The cause is `scoreItems`' `now = Date.now()` default, reached because `scorePaperCandidates` (`lib/feed/pipeline.ts`) does not pass the pipeline's `now` on to it. That is a product-code observation, not a defect I fixed: passing `now.getTime()` there would make read-time recency follow an injected clock (one source-level fix for every test that compares two runs), but it moves recency in every existing pipeline test whose fixture dates are fixed and whose `now` is not, so it is a separate, larger item. `lib/scoring/` was not touched and the file I changed in `lib/feed/` is the test only.
- The brief's premise ("the order of a sum differs") did not hold, so there was no function in `lib/feed/` to name; the brief's rule 1 and rule 2 (a stable tiebreak, or a relative tolerance) were both unnecessary, and I did not use either.
- Other tests that run the pipeline twice and compare scores would have the same drift. I did not look for them (not in my files); a search for `toBeCloseTo` next to two `runFeedPipeline` calls is the cheap check.
- The scratch probe stays in the scratch directory, uncommitted. Nothing here needs a dev server, a model or a key.
