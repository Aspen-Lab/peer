## 2. The rules and the trigger

**Rule 1 (§1h.171):** whenever the bar's content box changes width, or the reading scale changes, a non-empty bar refits to its content (`fitHeight`). **Rule 2:** nothing else changes: an empty bar stays one row (P11-55's rule), a keystroke grows the bar as before, the 48-px minimum, Submit, the dropdown and the counter are untouched, the refit never scrolls the page.

What I chose (`refitOnReflow(el)`, run by one `useEffect(() => refitOnReflow(input.current), [])`; it returns its own clean-up):

- **Width: a `ResizeObserver` on the textarea.** It sees every way the column moves (a drag, the separator keys, a pane collapsed or pinned, the window, the page's own 0.3-s width/track transition) and reports the content width; only a change of that width asks for a refit. A change of height alone (the refit's own) is not a width, so there is no loop. The first report is the size the bar starts from and refits nothing. The refit is **not run inside the observer's callback but on the next animation frame** (many widths in one frame, a drag's, ask for one refit): a height written inside the callback is a size change for the page's other observers (keep-place's column among them) in the same frame, which a browser reports as a "ResizeObserver loop completed with undelivered notifications" error. None of the 80 matrix pages and none of the frame runs recorded a page error or a console message of it.
- **Scale: a `MutationObserver` on the `style` of the `.reading-scaled` wrapper the bar is in** (`reader-layout.tsx` sets `--reading-scale` there). When the value of `--reading-scale` changes the bar is refitted **on the spot, then on every animation frame for `FOLLOW_MS` = 400 ms** (the 0.3-s `.zoom-transition` and its 50-ms margin, `theme.ts`), the last frame being the settled one. I chose per frame, not only at the end: the font size is a 0.3-s transition, and a refit only at its end would leave the question cut for 0.3 s and then leap. A width observer alone would not do: at 1024 and 1093 the column is a fixed width and only the font size moves. Under reduced motion the change is at once and so is the one refit.
- An empty bar: `fitHeight`'s empty branch (clear the height, one row) is what every one of these refits calls, so nothing is measured or grown.

## 7. Unsettled

- **A width change is refitted one frame late.** Painted frames during a separator drag can show the new width with the old height for one or two frames (36 px at worst in the runs above) before the next frame fits it; the settled bar is whole. The alternative, a refit inside the observer's callback, is a loop error against keep-place's observer (M5 pins the choice). Text steps have no such lag (the refit runs after the frame's animation update, on the animated font size).
- **Chromium only was measured.** `ResizeObserver`, `MutationObserver` and `requestAnimationFrame` are standard; Firefox and Safari were not run.
- A bar left taller than its question (a column widened after a long question) is now shortened to it at once. That is the bar showing its whole question and no more, but it is a visible change from the old stale height and is the only place a reader will see the bar move that the ruling did not name.
- The matrix reads the Summary tab's place by `scrollY` only (it shows no paragraph); the paragraph and character checks are for Paper digestion.
