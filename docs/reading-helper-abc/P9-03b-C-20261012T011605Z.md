## 1. The rules as built

**Where "a window stands"**: `docked` — from 1024 px, `open !== null || standing` (a reader with a key: the empty window from the mount, or one holding a passage; a reader with no key: the Tier 0 definition window once opened). Everything below is for `docked`; the card (640–1023), the sheet (< 640), no key and no definition, and a window hidden with Close are as P9-03 left them.

1. **The window follows the selection.** The box keeps `followed`, the last settled selection the page handed it (state, set while rendering like `stale`, so the move is in the same paint), and `stand = target ?? followed`. `placePanel` is called with `stand`'s paragraph top (`paragraph?.top`, else `bounds.top`, the selection's own first line) and its existing clamp (`DOCK_TOP_PX` … `height − DOCK_BOTTOM_PX − DOCK_MIN_VISIBLE_PX`); the empty window uses it too (48 only while nothing was ever selected). Nothing else moves: no close, no reflow (`docked` does not change, so the layout effect and `reserveDock` do not run; `removeProperty` is never called), the content is what the session holds — the open thread of the passage explained earlier, or the empty state. `stand` is watched like the explained passage (`[placed, stand]`, the scroll / resize measure), so the window follows its paragraph as the page scrolls. The card and the sheet keep following the explained passage (`placedAt`).
2. **When the selection goes away the window stays** where it moved (a click in the window collapses the selection: it must not jump from under the pointer); selecting the explained passage again moves it back to that paragraph. Explaining replaces the thread in place as before; the window is already level with the passage it takes in.
3. **The window carries the control.** `ExplainCard` gets one optional prop, `onExplain`; the box passes `() => start(next)` while `next` (the offered selection worth a button: not the passage the window explains; with no key, one the paper defines) exists and `docked`. The control is a `<button type="button" data-explain-ask="">` with the words `EXPLAIN.ask`, label face, pill, `onMouseDown` cancelled (it does not take the selection), pressing = what the floating button did (`e` unchanged: `openBox` → `start(next)`). **In the empty state it stands where the title is** (the same words, now a button; the hint line `EXPLAIN.empty` stays under it); **with a passage it stands in the sticky header under the quote**.
4. **No floating button while the window stands**: `askAt = next && !docked ? … : null`; the `DOCK_RESERVE_PX` narrowing of the button's viewport (P8-02 §3 b) is gone with it (the import is removed).
5. **First line, everywhere (commit 2)**: `placeButton(rect, viewport, paragraph?, bounds = rect)`; in the gutter its top is `clamp(bounds.top, …)` — the selection's FIRST line — instead of `rect.top`, the line the selection ends on; with no gutter it is as it was (under where the selection ends, `rect`). ## 2. Departures and judgment calls (each is one line to revert)

a. **The window stays where it moved when the selection goes away** (rule 2). The brief says the window moves on an offered selection and is silent on what happens when it goes away. A naive `offered ?? placed` jumps the window back to the explained paragraph 150 ms after any click inside it (a click collapses the selection), under the pointer of a reader who is going for the input. Pinned: "stays where it moved when the selection goes away…", "goes back to the explained paragraph when the reader selects its passage again", and the same for the empty window.
b. **The window follows any settled selection, also one it has nothing to offer for** (no key and a passage the paper does not define: the Tier 0 window moves, no control appears). The brief's rule 1 says "offered" in P8-02's sense (the selection other than the explained one), and the owner's words are about the selected paragraph, not about what can be explained. Pinned: "a Tier 0 window (no key) follows a selection too, whether or not the paper defines something in it". To follow only `next` is one expression (`stand = next ?? followed`).
c. **"Offering a selection inside A shows no header button"** read as: the selection is the explained passage itself (same passage). A different passage inside A's paragraph is offered (rule 2 of the brief: "not the passage the window explains") — its control shows, and the window does not move (it is already level with that paragraph). Both pinned.
d. **The empty state's control replaces the title** instead of standing beside the hint line: the title and the control are the same words, so both would say "Explain this?" twice in a 360 px header. The hint line stays under it; Close stays at the right. With a passage the control is under the quote (a sticky header, so it is always in view).
e. **Settled** = what the page hands the box: `useSelectionListener`'s 150 ms debounce (P8-02's `offered`). See §6 item 1 for what that means for a drag that pauses.

## 8. For the manager

1. **"Settled" is not "mouse-up"** (§4, last paragraph; the brief's rule 1 and the ruling say "never during a drag"). The box can only act on what the page hands it, and `useSelectionListener` (`paper-body.tsx`) reports after 150 ms of no `selectionchange` — a drag that pauses 150 ms with the button down offers the selection, so the window moves and the control appears under the pointer's hand before the reader lets go (the floating button has done the same since P3-02). It is a small jump of a fixed window, no reflow, nothing lost; but if the ruling is to hold to the letter, the fix is in `paper-body.tsx`: hold the report while a primary pointer is down and report on `pointerup` / `pointercancel` (one listener pair in the hook, plus a test with a held pointer). It is outside this item's files (only a doc comment there); I did not touch it. I did not add a pointer listener to the box: three existing pins say the box registers no `pointerdown` while the empty window stands.
2. **The window now sits low whenever the reader selects low on the screen, so the 160 px floor (`DOCK_MIN_VISIBLE_PX`, P8-02 §7 item 1) is reached far more often** — it was only reached by explaining a passage low on the screen. At the floor the window is 160 px tall and its sticky header and sticky controls row fill it: measured at 1440 (`w1440-2-follows-thread-kept.png`) the header is 118 px with the control (about 80 without it) and the controls row 85 px, **203 px against the 160 floor** — the thread cannot be seen without scrolling, and with the control standing the header alone is two thirds of the window. I did not render the floor itself. One constant (`DOCK_MIN_VISIBLE_PX`; ≈ 280–300 px would show a line or two of the answer) and `explain-dock.test.ts`'s pin; the cost is that a selection in the last fifth of the screen keeps the window a little above its paragraph.
3. **The control in the header adds ≈ 38 px to the sticky header while a passage is open** (the pill and its margin); the empty state's header is unchanged in height (the control takes the title's place). Easy to move beside Close if the owner prefers a one-row header; the quote would then wrap in 150 px.
4. **Judgment calls to confirm** (§2): the window stays where it moved when the selection goes away; it follows any settled selection, also one with nothing to offer (Tier 0, undefined passage); "inside A" means the explained passage itself.
