## Result in one paragraph

All six PDFs were **accepted** (HTTP 200, no refusal message, in every run, with and without the key); P5 (25,587,250 bytes) is 627,000 bytes under `MAX_UPLOAD_BYTES` (`web/src/app/api/papers/upload/route.ts:45`, 26,214,400) and passed both the client-side check and the dev server's 30 MB body limit. The reading page opened for every paper within 1–2 s of the POST's answer. **What breaks is the reading that follows**: for P5 and for P2, P3, P4, P6 in all 15 runs, and for P1 in 2 of 3, the **first reading answer was abstract-only** (`fullText: none`), the page showed a short reading with no body and a line saying no abstract is published, **nothing retried**, and one manual reload brought the body for P1–P4 and P6 (2–16 s after the reload) but **not for P5 within 90 s** (3 of 3 runs). The abstract-only state is the 8 s wait in the reading route (`reading/route.ts:22`) meeting a second, full extraction of a PDF the upload route had already read once. For P5 that extraction costs 31 CPU seconds, so the wait is missed on any machine; for P4–P6 it is at or beyond 6–10 CPU seconds, so probably also on a quiet one (inferred); for P1–P3 (2.3–4 CPU seconds) the load is what pushes it over. Pictures: P1's six figure requests all answered 404 (B P12-39's finding, confirmed on this head); P3, P4, P6 had one or two 404s each. Memory: P5 took the server from about 1.0 GB to 2.2–2.3 GB (+1.2 GB; the other five +0.15–0.37 GB). The page stays responsive (scroll, figure card) on every paper whose body loaded.

## Defects, costed as the rubric would

**D1. A reader who has just uploaded a PDF is shown an abstract-only reading, and the page never asks again. UNUSABLE for P5 (no body in any run, 90 s after a reload); MISLEADING for P2–P4, P6 and P1-under-load (the body is there one reload later, and nothing says so).** Mechanism: the reading route waits `FULL_TEXT_TIMEOUT_MS = 8_000` ms for the full text (`web/src/app/api/papers/[id]/reading/route.ts:22`; `fullTextWithin` `:32-51`; the upload branch `:92-98`) and otherwise answers with the abstract alone while the extraction runs on; `use-reading.ts` asks **once** per page open (`web/src/components/reader/use-reading.ts:142-163`) and has no retry or poll, and a private reading with `fullText: none` is deliberately not kept (`:157`), so only a manual reload re-asks; the abstract-only copy says "No abstract is published where Peer can read it — only the record. Open it at the source to judge it." (`web/src/lib/papers/reading.ts:896-897`), which for a file the reader has just uploaded neither says that the PDF is still being read nor that a reload will show it. The timer is also not a bound: a dev-log line from run A shows a reading request of P6 that took 55 s although the route's own wait is 8 s, so the 8 s timer evidently could not fire while the in-process extraction held the event loop. **Cause of that last point: unknown, a B needed.**

**D2. The upload route reads the PDF in full and throws the document away; the first reading request reads it again.** `upload/route.ts:204` calls `extractPdfTextFromBytes(bytes)` (pdf.js text plus the MuPDF figure measuring of `pdf-text.ts:243-277`), keeps only the title, DOI, abstract line, page count and concept signals in the meta, and never stores the document: `writeUploadDoc` is called from one place only, `full-text.ts:366`, inside `uploadFullText` (`:353-379`), which re-extracts (`:235`). Measured as server CPU seconds from the click to the POST's answer, which is the route's own extraction: **P1 2.5 (4.1 in run C at load 92), P2 2.3–2.4, P3 3.4–4.0, P4 5.3–6.0, P6 9.7–10.0, P5 31.1–31.2**; of the rest of each run's CPU (P5: 36 s of 67.6) most is, inferred, the second extraction at the first reading. **That second extraction is what meets the 8 s wait in D1: inferred, not measured on a quiet machine, P5 (31 CPU s) and P6 (10 CPU s) miss it on any machine, P4 (6) is at the edge, P1–P3 (2.3–4) make it unless the machine is loaded.** Cost: cosmetic for the small papers, the direct cause of D1 for P5. A reader would be waiting for the first extraction to end anyway (the POST) so it is the second that is avoidable.

**D3. P5 is expensive and the server keeps what it took. Not scored as a reader defect by itself: the reader's cost is the wait (the upload POST is 31 CPU s, so at least 31 s on a quiet core, inferred; 42–58 s measured at load 27–28; I did not look at what the upload square shows meanwhile); the server's cost (+1.2 GB retained) is a risk for a small host and is a dev-server number only, nothing measured on a production build.** Server `ps` RSS in run B: 1,032 MB at the click, **2,118 MB when the POST answered**, 2,194 MB at the first reading answer, peak **2,308 MB** (62 s after the click), 2,295 MB at the end; run C: 972 → 2,087 → 2,305 peak → 2,039; run A 982 → 1,935 → 2,215 peak → 2,100. Whole dev-server session (npm, sh, `next` launcher, `next-server`, a worker) peaked at 2,369–2,565 MB. The other five papers: +145 to +187 MB (P1–P4) and +365 MB (P6); after the run the memory stays (it is not released within the 3 s after, nor, in the first single-process batch, between papers: that server went 2.2 → 3.3 GB across the six uploads and was then OOM-killed in the next batch at 3.0 GB anonymous). Whole-run server CPU: P5 67.6–79.8 s against 9–26 s for the others. **Cause unknown, a B needed** (pdf.js page cache, MuPDF WASM heap, and the 25 MB `Buffer` copies in `upload/route.ts:150-158` and `readUploadPdf` are the candidates; none was tested).

**D4. Figures. P1: all six `figure-image` requests answer 404 and the six figure blocks stay caption-only (MISLEADING, or UNUSABLE for P1's figures: six figures promised, none shown, and no message at the block).** Already found and dated by B P12-39 (the engine's caption has no "Fig. N" and the route filters on the label, `figure-image/route.ts:107-122`; regression from the P12-28 caption change); **confirmed here on this head through the UI, 3 of 3 runs**. P3 one 404 in seven blocks, P4 two, P6 two of four (counts only; I did not judge which figure or whether the picture the page did show was the right one). The figure card opened in 0.2–2.8 s for the first figure with a visible button; on P1 no block's own "Open Fig N in the margin" button was left to click (the 404s leave the button empty and invisible), only the one "Enlarge figure" button.

**D5. The page title of P1 and of P3 is not the paper's title (MISLEADING).** P1's title is a three-word journal-name shape; P3's is the first ten words of a body sentence. Mechanism candidates: the step-(a) title is accepted when it has three or more words and is not a stamp (`upload/route.ts:76-90`, `resolveUploadTitle` `:93`), so any three-word line the extractor's largest-font rule picks passes; why the extractor picked these lines is **unknown, a B needed**. P2's and P5's titles look right on the page; for P4 and P6 a title was shown and I did not judge it.

**D6. Cosmetic: the reading page's second look.** After the reload that brings the body, `figure-image` pictures load lazily and, at 1440 × 900 on the 18–34k px pages, only those scrolled into view are fetched; the "figures listed" time is therefore the figure *blocks* (with the body), not the pictures. Nothing wrong; recorded so the next measure does not read a 0 "loaded" at t = body as a failure.

**Environment noise, not product, so nobody chases it:** (a) `POST /api/read` → 500 in every run with the dev log "Your project's URL and Key are required to create a Supabase client!" (`web/src/app/api/read/route.ts:10`) and the browser warning "[feed] cloudMarkRead failed": no Supabase configuration here; (b) `va.vercel-scripts.com` is refused by the sandbox proxy (a console error, 1–3 times per run); (c) the stub answers every public source API (openalex, arxiv, dblp, pubmed, semantic-scholar) with 503, logged by the dev server on the home page's feed call; (d) "[feed] fetch failed … Failed to fetch" twice in the key runs of P4–P6, at the moment the run reloaded the page (an aborted request); (e) an "uncaughtException … aborted … ECONNRESET" line in the dev log when the browser aborted an in-flight request (a reload during the reading) — a Next-dev log line, harmless to the reader; (f) in key mode the model text on screen is the stub's canned words, not a model's reading. **No page exception (`pageerror`) in any of the 18 runs.**

## What I did not do, and the limits

- **No quiet-machine run.** The load never fell below 20 for more than the first minutes of a batch, so every wall-clock number is inflated by an unknown factor; the quiet-machine statements above (D1, D2) are inferred from CPU seconds and labelled so. A re-run on an idle machine would settle whether P4 and P6 get their body on the first reading, and how long a patient reader waits for P5's.
- **No P5 "wait until the body comes" run** (reloading every 15 s until it appears). I wrote it and started it once; at load 70 the upload POST alone took 3.3 minutes and the run timed out with no reading; later the container's memory was at its limit (under 1 GB free) and another 2–3 GB would have risked more OOM kills of other workers' processes, so I did not repeat it. How long P5 takes to show a body is **unmeasured**; the CPU figures say the second extraction needs about 31 CPU s.
- Dev server only; a production build, Vercel's Supabase upload path (`upload/ticket`), a phone width and dark mode were not run (not asked).
- Whether the three Chromium renderer crashes were page crashes is not established.
- P4–P6: no section, structure or role statement anywhere in this report (held out). P1–P3 content is described by shape only.
