## What was built

**`web/src/lib/papers/explain.ts`** (pure, server-side; the browser imports its types only). `clipPassage` (whitespace collapsed, ≤1,200 chars, cut at a word); `locatePassage(doc, passage, hint?)` (the hinted paragraph first, then its section, then the body in reading order; the paragraphs are `readableSections`' own, so a hit's `sectionIndex` is `reading.body[k]`; the abstract is not searched; `before`/`after` are the neighbours within the section); `explainMapLines` (heading + `openingOf` of the first paragraph, per rendered section); `buildExplainPrompt` (title, abstract, map lines, the paragraph and its neighbours, the passage, the schema and the rules — every piece bounded before it is serialised; no reader parameter exists, so nothing about the reader can be in it); `sanitizeExplainAnswer` (both parts ≤2 sentences / ≤420 chars, the quote ≤400, every model-sent place, page or `peer` flag dropped); `verifyExplainAnswer` (the quote must be a whole substring of one section through P2's `locateSection`; found → section id, heading and page from the document; not found or absent → quote and places removed, `here.peer = true`); `explainCacheKey` (sha256 of doc hash, normalised passage and a hash of the thread — `[]` now, P3-02b's turns change it); `createExplainCache` / `explainCache` (64 entries, 1 h, oldest out; holds verified answers under hash keys only); plus `explainDocHash`, `parseModelJson`, `explainDayKey`, `shortHash`, and the `ExplainResult` wire type.

**`web/src/app/api/papers/[id]/explain/route.ts`**: `POST`, `force-dynamic`, `maxDuration = 30`. In order: JSON, paper, the `[id]` param equals `body.paper.id`, `passage` is text → the upload owner checks as the report route does them (a malformed claim, an unowned upload, an attachment that does not list the paper: one 404 with `PRIVATE_UPLOAD_HEADERS`) → `requireEntitledAiRequest("paper-explain", 40)` → `resolveProvider(override, entitledContext(…, "paper-explain", byok))`; no provider that can write → `200 { unavailable: true }` before any text is read → `getFullText` as the report route calls it; no document or sections → unavailable → `clipPassage`, `locatePassage`; not found → `422 { error: "not_in_paper" }` → the memory by `explainCacheKey(explainDocHash(doc), passage, [])`; a hit answers `{ answer, cached: true }` with no model call and no count → else one `generateJsonText({ maxTokens: 600, tier: "small" })`, `parseModelJson`, sanitize, count, verify, the upload-revision re-check (410 with the private headers, nothing cached), cache, `{ answer, cached: false }`. A model failure, nonsense or an unusable answer is `200 { unavailable: true }` with nothing counted or remembered; `CompanySpendCapRefusedError` adds the `companyBudgetQuotaSignal`. Every answer is `Cache-Control: no-store` (an upload's: `PRIVATE_UPLOAD_HEADERS`). Counting, not charging: one increment of `explain_turns:<user>:<UTC day>` per delivered model turn, and ONE `console.debug("[papers/explain] turn", { userId: short hash, count, promptChars, answerChars, cached })` — sizes only, no passage, no answer, no paper word; a failed model call logs the error's name alone.

## Choices beyond the brief (small readings, consistent with the rulings)

1. **The passage's opening is an `EvidenceQuote`, not a label-face line.** The brief says "a label-face line"; the standing rule (§1f.17; the task's hard rule) is that the paper's words render only through `EvidenceQuote`. The card's first element is that quote, with the section's heading (no page — the section's first page would not be the passage's).
2. **The counter is a day key of its own, `explain_turns:<user>:<UTC day>`** (`explainDayKey` in `explain.ts`), not `rateKey("explain-turns", …)`: `rateKey` is an hour segment, so with `endOfUtcDay` it would count per hour, not per day. `counters.ts` is untouched.
3. **Counted on a delivered turn only.** The brief says "on every model call" and "a model failure or an unparseable answer → … (nothing counted)"; I read the second as the rule: the increment follows a sanitised answer, before the revision re-check. A cache hit logs a `cached: true` line with `count: null`.
4. **`thread` is accepted and not read** (the first message has none); the cache key is built with `[]`.
5. **Two small helpers live in `explain.ts`** (`parseModelJson`, `explainDocHash`): the report passes' `safeJson` and the hash are private to `deep-report.ts`, so they are repeated rather than that file touched. The report route's three small identifier helpers and the upload checks are repeated in the new route with a comment naming the source; extracting them would have touched a route whose tests pin it.
6. **The located paragraph itself is in the prompt** (clipped to 2,000 chars) beside the paragraph before and after: the passage is a slice of it, and the model needs the sentences around the passage to name a verifiable one.
7. **The button offers when the paper itself defines a term inside the passage (an evidence-carrying term), or `canAsk`** — a model-only term without a sentence of the paper's does not offer a button on its own (a stale cached report must not produce a button over an empty card). A term is "inside" when it is a whole word or words, any case ("DM" is not found in "admission").
8. **Selection details found in the browser.** (a) A triple click ends at offset 0 of the next paragraph: `readSelection` reads the range's own two ends and takes such an end as the first paragraph's when the words carry no break inside them; a drag that really runs on carries one and is refused. (b) A selection with a drawn formula (KaTeX markup, or the TeX in `<code>`) is no target: its text is not the paper's. (c) The button stands under where the selection **ends** (the last line with width), the card stands clear of the **whole** selection, so `ExplainSelection` carries `rect`, `bounds` and a `measure()` that looks again as the page scrolls.
9. **The popover is mounted outside the zoomed `PageContainer`** (the page returns a fragment), so its pixel positions are the window's under Fit's `zoom`; inside `SectionLinks` so the quotes' "§Heading" links work as everywhere.
10. **Store bounds beyond the brief:** the answers of at most 24 papers are kept (oldest out), so 32 passages × many papers cannot fill the browser's storage; `passageHash` is in the store file, not `lib/`.
11. **Files outside the brief's list, each for one line:** `components/store-hydrator.tsx` (registering the persisted store, as the questions store is) and, for tests, `route-tint.test.tsx`, `spend-scans.test.ts`, `page.terms.test.ts` (see above). `EXPLAIN` has three strings the brief did not list: `card` (the dialog's name), `defines(term)` and `close`.
12. **Commit trailers.** The task says to end the message with the two Fable lines; §1c says the attribution follows the committing agent's model, and my harness mandates `Claude Sonnet 5.5`. As in P3-01, the message ends with the Sonnet line, then the two Fable lines, so the last two lines are exactly the brief's.
