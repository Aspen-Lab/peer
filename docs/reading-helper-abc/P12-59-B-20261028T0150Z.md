## Result in one paragraph

(1) **The 55 s is not confirmed and not reproduced.** The dev-log line is not retained, and the retained per-run JSON of A-smoke bounds every first reading request at 35.3 s at most (P1, placeholder-key run, load 92) and P6's run A at 20.3 s; **53.9 s is P6 run A's click-relative time of the first reading answer (Table A), which is the likeliest source of "55 s"**. What the code does: the 8 s timer is real (it fired 8 to 170 ms late in every run, including one with the process starved to 1/38 of a core), the request answered in 8.1 to 9.6 s five times out of five in that starved run; on a quiet machine P5's first reading is 7.5 s and carries the full text. The route's own pieces cost under 0.3 s each (table in 1.3). What *can* put a delay beyond 8 s is the same-process extraction that keeps running behind the answer: its loop stalls are 0.1 to 0.3 CPU seconds each on a quiet machine, and a loop stall in wall-clock time is its CPU time times the machine's load factor (14 to 17 s of wall for 0.3 CPU s in the starved run). (2) **P5's 2.3 GB is not the code's own.** In a bare process the real routes take P5 from 75 MB to a peak of 395-465 MB; the dev server took it from 1.0 GB to 2.1 GB. By stage the code's own memory is the multipart parse (+105 to +205 MB, transient), pdf.js (+50 MB live, +100 MB resident), one more 25 MB buffer and one more pdf.js pass at the first reading; pdf.js spends 8.2 of its 9.0 CPU seconds on **one page** (page 7), and the engine refuses P5 (25.6 MB is over its 18 MB cap) so MuPDF is never loaded for it. Tested and excluded in bare Node: bundling pdf.js as Turbopack does, `AsyncLocalStorage`, Next's own body-clone code, repeated passes (no live growth), releasing the multipart objects early. The remaining ~1 GB appears in the dev server in step with the pdf.js pass (A-smoke's 250 ms RSS series) and is not reproduced here; it needs one `next start` measurement. (3) **The titles**: both come from one function, `titleOf` (`pdf-outline.ts:1702-1714`), which takes the largest *line size* on page 1, where a line's size is its **tallest run** (`:745`). P1: the journal's masthead is set larger than the paper's title, so its second masthead line (3 words, 20.9 pt against the title's 15.9 pt) wins and passes the route's 3-word bar (`upload/route.ts:76-82`). P3: a 41.6 pt drop cap shares a baseline with the third line of the first paragraph and makes that line "the biggest", so ten words of body text are the title (the title is 24 pt). Recommended: **R3+R1**, a drop-cap-proof title-only size plus the PDF's embedded title used as a witness to choose among the page-1 candidates (right on P1, P2, P3 and on all three controls). (4) Recommended for the 55 s / D1 / P5 time at once: **keep the document the upload route already read** (`writeUploadDoc` at upload) so the first reading is a sidecar read (69-224 ms measured instead of 1-7.5 s of extraction). Commit hash is in the hand-back message.

### 1.3 Does anything starve the 8 s timer? Measured: no, and the delay beyond 8 s is load times a short stall

- Event-loop stalls (the loop unavailable for more than 100 ms, with the CPU the process burned in the gap): quiet P5, first reading: largest 274 CPU ms; the largest of the whole run is 852 CPU ms at the very start (the multipart parse and the hash). pdf.js hands the loop back inside a page, so even page 7 does not hold it. A bare-Node run of the upload steps with the loop ticker: max 1.7 CPU s in a loaded run, 0.28 quiet. The timer fired 164 ms late (P1, loaded) and 8-171 ms late (P6, five requests, process at 1/38 of a core).
- The starved run (24 busy loops at nice 19 against the harness at nice 19, load 28; P6, timing only): the upload POST took 172 s for 4.5 CPU s; five readings in a row each answered in **8.1 to 9.6 s** (timer 8-171 ms late), each abstract-only because the extraction could not finish in 45 s of wall; loop stalls of **14.0, 17.4 and 14.0 s of wall for 0.2-0.3 CPU s** each. So a request can lose at most one stall per loop hop after the timer, and a stall of 0.3 CPU s is 17 s at that load. A request at 55 s needs three or four such hops in its tail; the route has two awaits after the race (`ownedUpload`, the response write). I could not make it happen in a bare process.
- What I cannot test without a dev server and name as the remaining candidates for a long dev-log line: Turbopack's compile of anything first imported inside the request (the dynamic `import("unpdf")` in `pdf-text.ts:131` and `import("@/lib/figures/pdf-engine")` at `:250` are first reached in the **upload** request in A-smoke's protocol, not the reading; the warm-up hit the reading route with a junk id, `a44/scripts/fresh.sh`), and Next's per-request dev work under the same load factor.
- **The 55 s itself**: from A-smoke's per-run JSON (`a44/results/*/P*-*.json`, `navMs` and the reading answer time) every first reading request was at most `answer - nav` long: P6 run A 20.3 s, P6 run B 11.0 s, P6 run C 10.5 s; P1 run C 35.3 s (load 92) is the longest of all 18; the others 10.3 to 19.2 s. P6 run A's reading answer is at **53.9 s since the click**, the same number Table A prints as "First reading answer s". A dev-log "in 55s" line for that request cannot be reconciled with a request that began after the page opened at 33.6 s. I could not find the line (dev logs were deleted), so: **not confirmed; most likely a click-relative time read as a duration.**

### 2.2 Dev-mode artifact or the code's own?

**Mostly not the code's own.** A-smoke's dev server grew 1.0 to 2.1 GB at the POST's answer for P5 (+1.1 to 1.3 GB) and +145 to +187 MB for P1-P4. In a bare process the same code grows +118 MB (P1) and +330 to +390 MB (P5). The surplus for P5, about 0.8 to 0.9 GB, is not in the extraction. What A's 250 ms RSS series shows (`a44/results/heavy-load-run/P5-key.json`, `run4-nokey-load25-34/P5-nokey.json`): the growth is **not at the body's arrival** (+70 MB in the first 3 s) but **in step with the pdf.js pass's CPU** (942 MB at the click, 1,898 MB 24 s later with 22.6 CPU s spent, 2.1 GB by 36 s), then a plateau, and a further +0.2 GB at the second pass. Tested in bare Node and **excluded** as the cause (each against P5): unpdf bundled into the server module graph as Turbopack does (peak 369 against 347 MB, same CPU within noise); `AsyncLocalStorage.run` around the pass, plain and with an `async_hooks` init hook (RSS 278 / 298 / 305 MB; CPU 7.1 / 8.8 / 9.5 s: +25-35% CPU, no memory); Next's own `getCloneableBody` / `requestToBodyStream` code with the proxy stream unread (`proxy.ts` matches the upload path; +74 MB over the raw body for P5, 160 to 234 MB total; P1 +15, 77 to 92); repeated passes (above); releasing the multipart objects before the pass (patched copy of the route: peaks 440 and 395 MB against 421 and 438 for the unpatched, i.e. within the ±30 MB run-to-run noise). What is left is dev-server specific and unproven: Turbopack dev's runtime for a module graph that is not external (`next.config.ts` lists only `mupdf` as external, `serverExternalPackages: ["mupdf"]`; unpdf is bundled), Next's dev-only instrumentation, V8 heap growth on a loaded machine. **The one measurement that decides it** is a single P5 upload through `next start` (a production build) on a machine with memory to spare, logging `process.memoryUsage()` (rss, heapTotal, external, arrayBuffers) from inside the route at the POST's answer. It was not possible here (no dev server, no build in a container at its limit).

| rule | saving | cost |
|---|---|---|
| **M1 = F1**: keep the upload's document, no second read of the PDF | no second 25 MB buffer and pass: the process peak falls from 395-465 to the POST's 368-413 MB (inferred), 6.8 CPU s less at the first reading | as F1 |

## 3. The two page titles

### 3.1 Mechanism (file:line)

- `lineOf` makes a line's size the **tallest run in it**: `pdf-outline.ts:745` `size: round(Math.max(...runs.map((i) => i.height)))`.
- `titleOf` (`:1702-1714`): page-1 lines above 1.25 times the body size and not a stamp; the **biggest** size wins; every line within 0.6 of it is joined; at least 6 characters. Called at `:1730`.
- It reaches the page through `normalize` (`pdf-text.ts:196`), `resolveUploadTitle` (`upload/route.ts:93-100`), whose only test is `looksLikeUsableTitle`: at least 3 words, at most 200 characters, not stamp-shaped (`:74-82`); otherwise the file name (`:62-65`). The same string also enters the preference signals with weight 4 (`upload-concepts.ts:136`), so a wrong title also skews what the upload says about the reader's interests.

P1 (body 9 pt, bar 11.25): page-1 lines above the bar by size: 20.9 pt (1 line, 3 words, the journal's masthead, second line), 18.9 pt (1 line, 2 words, masthead first line), 15.9 pt (3 lines: a one-word article-type label and the **two lines of the paper's title, 13 words**), 13.9 (a heading). The masthead is larger than the title, so `titleOf` returns the 3-word 20.9 pt line, which clears the 3-word bar. Embedded title: present, 13 words, equal to the title.

P3 (body 7.5 pt, bar 9.38): 41.6 pt (1 line, 10 words, 60 characters: **a drop cap and the rest of the line it sits on**, the third line of the first paragraph, the cap welded to its first word), 24 pt (2 lines, the real title, 10 words, 80 characters), 20 pt (one word, the section label), 12 pt (authors). The drop cap's run is 41.6 pt tall, so the whole line is "41.6 pt" and wins; it is also why that line is missing from the body (the page-1 skip at `:1846` drops every page-1 line above the bar). Embedded title: present, 10 words, equal to the title.

P2 is right because its title is both the largest line (19.9 pt, 4 words) and the only line in its class. The public IEEE control shows the same drop-cap defect (title 23.9 pt, a 29.9 pt drop-cap line: the current rule returns 18 words / 115 characters).

All three owner papers carry an Info title equal to the title in the file name (Info: 13, 5 and 12 words; XMP also on P1 and P3); the IEEE control carries "Title - Journal" (15 words); the other two controls carry none (`h-meta`).

### 3.2 Candidate rules, scored (precision / recall of the words against the title in the file name for P1-P3; the controls by their known titles; `h-title2`)

| rule | P1 | P2 | P3 | public controls (conference, 5-word, IEEE) | cost |
|---|---|---|---|---|---|

| **R1** title-only size = the size most of the line's characters are set in (a new `titleSize` on `PdfLine`, read only by `titleOf`) | unchanged, wrong | right | **right** | right, right, **right** | fixes the drop cap only. Doing it to `size` itself changes the outline of all three (P1 16 to 15 sections, P2 -1,205 characters, P3 100 to 97 sections), so it must be a separate field |
| R2 R1 + take the largest size class that has 4+ words, drop all-caps labels | **right** (96 characters: the title plus the trailing dagger) | right | right | right x3 | **breaks short titles**: a 3-word title above a 7-word author line returns the author line (synthetic page, `h-synth`); and a 4-word masthead above the title stays |

**Choice: R3 over R1 lines, falling back to R1, then to T0** (`R3+R1`): P1, P2, P3 and the three controls all come out right (13, 4, 10, 7, 5, 5 words). R4 can be added at no cost where the name carries a title. What it still gets wrong: a paper with an oversized masthead, a title not larger than it, **and no embedded title**, which is today's P1 without its metadata. An R3 with the embedded title also needs a test fixture: a synthetic page 1 with a masthead above the title and a drop cap, in the style of `pdf-text.test.ts`'s synthetic layouts; the owner's PDFs cannot be committed.

## 4. Decisions for the manager

1. **55 s**: do not chase a timer bug; the timer is correct. Mark it "not confirmed (likely the 53.9 s click-relative time)". If the owner has the dev log line, its `compile:`/`render:` split settles it.
2. **C P12-58 should carry F1** (keep the upload's document at upload) in addition to the page's retry: it is the only change that makes the first reading complete for P5 in the dev server and removes the second extraction for everything; cost small and measured.
3. **Memory**: M1 now; one production-build measurement of P5 before M2/M3. Do not describe 2.3 GB as the code's own in the digest.
4. **Titles**: implement R3+R1 (`titleSize` on `PdfLine`; embedded title through `readPages`/`buildOutline`; leave `size` alone); do not adopt R2.
5. **Noticed, not examined**: (a) P3's outline has 100 sections for 11,054 characters of text at this head (`h-title2`), which looks wrong and is a separate item; (b) the drop cap also removes the first paragraph's third line from P3's body (above); (c) `pdf-engine.ts:98` caps the figure engine at 18 MB while the upload cap is 25 MB (`upload/route.ts:45`), so a 18-25 MB paper gets no figure sizes and, in the figure route, no pictures: P5 would have none even once its body arrives; (d) `readPages` never destroys the pdf.js document (`pdf-text.ts:131-157`); I found no live growth from that.

## Limits

No dev server: the dev-mode memory surplus and any compile time are unmeasured; one quiet window of about 20 minutes after the container restart gave the quiet CPU figures, the rest ran at load 25-50 (wall figures are labelled); the starved-run load was my own niced busy loops, killed afterwards (none left); the 55 s line is not retained; the title rules were scored on three owner papers and three public controls only.
