## 2. The rules as built (§1h.59)

1. **The route** `GET /api/papers/[id]/figure-image?page=N&fig=K`.
   - `page` and `fig` are plain digits (page 1–300, fig 1–999); anything else (missing, `0`, `2.5`, `1e1`, `3a`, "Figure 3") is **400** before any lookup, privately for an upload id. **A missing `fig` is a 400**: the old `?page=N` shape no longer answers (see "For the manager" 2).
   - An id that claims to be an upload (`claimsUploadId`) never reaches the public lookup. A spelling `bareUploadId` does not accept (`UPLOAD:<hash16>`, ` upload:…`) is 404. The canonical id goes through `ownedUpload` (the same capability-cookie check `/api/figure` and the reading route use): another reader's upload, a browser with no cookie, an expired or taken-down record: **404 `Upload not found.`**, `private, no-store`, before a byte of the PDF is read (`readUploadPdf` is not called). Then `meta.pageCount` bounds the page (404), `readUploadPdf` gives the bytes (404 if gone).
   - A public paper resolves as before (`fetchPaperById` → `getFullText` → its PDF link → `getPdfBytes`; 404 unknown paper / no PDF / page past the document, 502 when the PDF cannot be fetched).
   - Both then call **`extractPdfFigures(bytes, { maxPages: 300, maxFigures: 1, onlyPage: page, label: "Figure K" })`** and answer the first region: the figure whose caption opens "Figure K" on page N, **not** "the largest raster". `unpdf`'s `extractImages` and the route's size filters are gone from this route. No region → **404** with the engine's own reason ("Peer opened the PDF, but found no region captioned "Figure 5" on page 1."); the engine will not load → **502** `Could not read the page`.
   - **Headers.** 200: `image/png`, `Content-Length`, the body is the PNG's bytes (`Buffer.from(png)`), never a `data:` URL. A public paper: `Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800` (unchanged). An upload: `PRIVATE_UPLOAD_HEADERS` (`private, no-store`, `Vary: Cookie`, `nosniff`, `noindex`) on the 200 and on every error. `X-Peer-Figure-Engine: mupdf` on every answer that ran the engine (200, the figure-not-found 404, the 502) — a route-local constant, as `/api/figure` has its own. Errors from a public paper: `no-store`.
2. **`placeFigures`** gives every "Figure N" caption that has a `page` the URL `/api/papers/<encoded id>/figure-image?page=<page>&fig=<N>`. The "exactly one caption on the page" rule (`perPage`) and the upload skip (`claimsUploadId`) are gone. `pdfFigureUrl(paperId, page, fig)` takes the number (its two callers are in `reading.ts` and `reading.test.ts`). The number is read from the label with `/^fig(?:ure)?\.?\s*([1-9]\d{0,2})$/i`, so "Fig 2" (what the outline writes for "Fig. 2") → 2; **"Figure IV", "Figure S3", a table, a caption with no page, a paper with no PDF behind it get no URL**; a caption that came with its own `imageUrl` keeps it.
3. **Nothing else changes.** The caption text, `after`, `page`, the order of the figures and the tables left out are as they were (tests below pin them). **`PaperReading.version` is not bumped.** The URL shape changed: `?page=N` → `?page=N&fig=K`.

A one-line compatibility (an absent `fig` → the page's first region) would avoid even that; I did not add it, because "a wrong picture under a caption is worse than none" was the old rule's reason and a 400 is the honest answer.
3. **A pre-existing hazard that this widens, in `buildReading` (not `placeFigures`, so not mine):** for a *supplement* reading (`/reading?upload=<id>`: a public paper with the owner's private PDF attached) `buildReading(paper, fullText)` calls `placeFigures(…, { paperId: paper.id })` with the **public** paper's id, so the picture URL points at the public paper's own PDF while the captions and pages were read from the owner's attachment. If the two PDFs are the same paper the pictures match; if the attachment is another version (preprint against published), a caption can get another version's figure. Before this item it applied to single-caption pages only; now to every captioned figure. The fix is to pass the supplement's `upload:` id as the figure source (the route then serves the owner's PDF). Found by reading `reading/route.ts` and `reading.ts`; not exercised.
4. **No sign-in or rate gate on this route** (it had none before; `/api/figure` has `requireAiRequest("figure", 60)`). A public answer is edge-cached for a day and the engine runs at most two at a time per instance with a 25 s budget, so a cold public request costs a render (0.2 – 0.6 s warm here). An upload's answer is `no-store` by rule, so each view of an upload's Reading re-draws every figure it scrolls past; a short per-owner in-memory cache of the PNG would remove that, and is not done (the brief names none, and it is per-user state).
5. The engine matches only numeric labels ("Figure 3", "Fig. 3"). A PDF whose captions are "Figure IV" (the outline reads Roman numerals) keeps its caption without a picture, as before.
