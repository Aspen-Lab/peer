I opened P5 through a `mupdf.Stream` over the file descriptor (mupdf.js `Stream` + `StreamHandle {fileSize, read(memory, offset, length, position), close}`, `mupdf.js:3146`, `mupdf.d.ts:841-849`) and counted what the library asks for:

| P5 page 5 Figure 3 | 767 | 6.3 MB | 2.5 MiB | 10 % |

| P1 page 5 Figure 3 | 196 | 1.6 MB | 0.5 MiB | 20 % of 2.5 MiB |

After `openDocument` with a stream the WASM heap is still 22 MB (the empty module); with the whole file in a `Buffer` it is 37 MB (the file's 25 MB is in the heap, plus the xref). So mupdf does **not** parse the other pages: opening costs the trailer and cross-reference, `loadPage` walks to one page object, and its fonts, images and content stream are fetched when used. The owner's "only open the page the figure is on" is already what the library does with the objects. What is whole is **the file in memory (up to four times) and the download of it**, which is before mupdf.

What the page's own decoded images cost: for the three ordinary P5 pages and P1 the render is +14 to +16 MB of resident memory (+7 to +16 MB of heap: the pixmap 860x466x3 = 1.2 MB and the decoded raster); the store of decoded images is not a factor at this size. The dense page 7 is the exception: +100 MB (the stext pass +39, the path walk +27 with 36,350 path boxes, the render +34; heap 22 → 45.8, or 77 with the whole file in the heap).

### 1.5 The bucket read is the largest single item in production

Production reads uploads from the bucket (`upload-backend.ts:136-143`: storage-js `download()`, then `blob.arrayBuffer()`). I modelled that with a local HTTP server and `fetch` → `res.blob()` → `blob.arrayBuffer()` → `Buffer.from`: **the read alone peaks at 215 MB** (56 → 166 after `blob()`, → 215 after `arrayBuffer()`) for P5, before the route's copy and before mupdf. ## 2. Is there a cache of the cut figure images or sizes today?

- **No image cache on the server.** The route has none (`figure-image/route.ts` reads the PDF on every request that reaches it). For an upload the answer is `private, no-store` (`upload-access.ts:8-13`), so **every view, reload and re-render of an upload's figure reads the whole stored PDF and runs the engine again**. For a public paper the answer is `public, s-maxage=86400, stale-while-revalidate=604800` (`route.ts:35`), URL-keyed with `v=FIGURE_EXTRACTION_REVISION` (`reading.ts:624`): only the CDN edge caches it; a miss at an edge (a new region, after the day, a cold key) runs the route again: `getPdfBytes` (in-memory, six papers, 15 minutes, `pdf-text.ts:104-125`) or a new download, then the engine.
- **Sizes are cached, images are not.** `measured` (`pdf-text.ts:218`), keyed by `FIGURE_EXTRACTION_REVISION|sha256(bytes)` then `page/figure`, 32 papers, in memory, lost on restart (`MEASURED_KEEP` `:217`; read at `:247`); and the upload's extracted-text sidecar `<hash16>.doc.json` is keyed `owner|hash16|revision|extractionVersion|figures:<REVISION>` (`upload-store.ts:359-365`) and carries each caption's width and height. Neither holds a picture.
- The report-figure path has its own in-memory pool, `candidatePoolCache` (`extract.ts:1267-1270`, key `FETCH_VERSION|REVISION|itemId|url|doi`, 30 minutes, 10 minutes when empty): whole-document extraction, `data:` URLs, 427 MB in B P12-41. A different consumer; none of the candidates changes it except (c).
- **A second view of the same figure opens the PDF again**, for an upload every time; for a public paper whenever the CDN misses.
- Another place that opens the whole file once per figure: the sizing in the reading build, `withFigureSizes` (`pdf-text.ts:243-262`): up to `MEASURE_MAX = 24` captions, each `measurePdfFigure` → `extractPdfFigures` → a new `mupdf.Buffer` of the whole file and a new open (the sizes are then cached by the Map above). A reading of a paper with five to fifteen captions makes five to fifteen opens of a 25 MB file in sequence.

### (a) a per-page file, made once

- **Making it** (`PDFDocument` + `newGraftMap()` + `graftPage(-1, src, i)` + `saveToBuffer("garbage=compact,compress")`, `split.mts`): P5, all 21 pages from one open of the file: 2.9 to 3.3 s wall unloaded (13 s under load 50), CPU 1.4 to 1.5 s, **peak 246 to 296 MB** (the dense page 7 alone makes 241 MB: its page file is 11.4 MB and the writer's heap goes to 114 MB), `emptyStore()` between pages and the writer options (`garbage=compact`, none, `clean`) change nothing material. With a stream over the Buffer the peak is 266 MB. Sizes: page files from 0.16 to 11.4 MiB, median about 0.7 MiB; **total 28.1 MiB against the PDF's 24.4 MiB (+15 %; shared fonts and images are copied into each page)**. P1: 10 files from 34 KiB to 1 MiB, 2.8 against 2.5 MiB (+12 %). Deterministic: two runs give identical files.
- **Using it**: the route reads 0.04 to 2.7 MiB instead of 24.4 MiB (11.4 MiB for the dense page), opens a one-page document, calls the same `extractPdfFigures` with `onlyPage: 1` (no engine change at all for the read side).
- **Parity**: the engine on the page file against the engine on the whole file, byte-identical PNG, caption and box: **P1 6 of 6** (pages 2, 3, 5, 6, 7, 8), **P5 3 of 3** (pages 3, 5, 7) and page 11 label-less, in the matrix 8 of 8 groups.
- **A fidelity hazard, tested on an invented file**: `graftPage` does not copy the catalog's `/OCProperties`, so **a layer that the whole PDF hides by default is visible in the page file** (invented PDF: pixel in the hidden layer's area 255,255,255 in the original, 255,0,0 in the page file). The fix works and is small: graft the page and the source's `OCProperties` through **the same graft map** (`dst.newGraftMap()`; `map.graftPage(...)`; `dst.getTrailer().get("Root").put("OCProperties", map.graftObject(ocp))`): pixel 255,255,255 again. A new test with that invented file belongs with the cut.
- **What it does not do**: it does not shrink the work of a dense page (page 7: 242 against 273, because the page file is itself 11.4 MB); it cannot exist for an upload made before it, nor for a public paper; it adds a second stored object per page and a cut step to a path whose memory is already the tightest (the upload route, P12-59).

### (b) a cached figure image

- A stored cut is **0.07 to 1.3 MB** (P5: 66,669; 281,427; 293,762; 555,513 bytes; P1: 329,129 to 1,323,832; the engine's own 4.5 Mpx cap bounds a PNG). Reading one: the process stays at node's floor, **45 MB with 0.4 MB read, mupdf never imported** (the module and its 22 MB heap, 26 MB steady and 38 MB at the instantiation peak, are not loaded at all by a cached answer). In this scratch process a cached view is about 5 times below today's peak (221) and 2 times below the smallest uncached one (103); the Next runtime around it is a constant that is not in these numbers. Its time is a storage read.
- **It does not change the first view of each figure.** A reading with N figures still pays the full price N times, once each, and again after every revision bump.
- Key: `hash16 | page | fig | FIGURE_EXTRACTION_REVISION`; the size is in the PNG's IHDR (bytes 16 to 23), no sidecar is needed. A failed cut is not stored (the route returns 404 or 502 as today).
- **For a public paper fetched by URL** the CDN already is this cache (24 h, then 7 d stale), and a server-side store would be a shared copy of a derived publisher image: not owner-private, a rights and operations decision I would not take. Leave it as it is.

### (c) no whole in-memory copy

mupdf 1.28.1 **allows it**: `new mupdf.Stream({ fileSize(), read(memory, offset, length, position), close() })` with `memory` the live WASM heap; `Document.openDocument(stream, "application/pdf")`; destroy the `Stream` object after opening as the engine already does with its `Buffer`. Measured above: c-file 105 to 133 MB for P5 (49 to 105 below today), the heap stays at 22 MB, 5 concurrent calls 145 to 148 MB (against 351 to 372). Variants:

- from a file path (the disk backend, where the stored object *is* a file; `withUploadPdfFile` `upload-store.ts:209-222` already hands out the path, in place on disk, a private `mkdtemp` 0o600 copy for the bucket);
- from a Buffer (`stream-buf`: a public paper's downloaded bytes, or the bucket read): drops copies 2, 3 and 4 (the engine's `Buffer` constructor copy and the heap copy); measured 127 to 169;
- for the bucket, **stream the body to a private temp file** (`fetch(signedUrl)` → `pipeline` → file; `c-tmp` above, 169 to 176 MB production-shaped against 257 to 292): the only variant that never holds the object in JS. That is a temp file, which `pdf-extract.ts` (`extractPdfCandidatesFromPath` comment: "no second copy on disk, no temp directory") deliberately avoided for the pool path, while `withUploadPdfFile` already does it for the figure extractor on the bucket backend; a manager decision.
- Cost to be honest about: a stream is slower on a page that re-reads a large content stream. P5 page 7: 193,356 callbacks, CPU 4.2 to 4.8 s against 3.5 s with the whole file in memory (+20 to 30 %); the three ordinary pages show no CPU difference. A 256 KiB read-ahead block in the handle did not help (4.8 s; 1 MiB blocks, 9.1 s, with the machine loaded; I would not build it). On a damaged cross-reference mupdf repairs by reading the whole stream: still correct, just not lazy.
- A smaller change that needs no stream: pass an exact `ArrayBuffer` to `new mupdf.Buffer` (`bytes.buffer` where `byteOffset === 0` and `byteLength === buffer.byteLength`, else one copy) and delete `route.ts:79` / `:100`: the c0 row (14 to 49 MB lower from the disk, 11 lower production-shaped, where the download dominates).

## 4. Recommendation (they combine)

1. **(b), now, as in C P12-61 part 1.** An upload's repeat views stop reading the PDF and stop loading mupdf. Smallest risk, no engine change.
2. **(c), part 3.** It is the one candidate that lowers the *first* cut of every figure, every pool/measure path that still opens the whole file, a public paper, and an upload made before any new object existed. In production use the **streamed-to-a-temp-file** source for the bucket (the Buffer-based stream stays under the download's own 215 MB peak and gains only 28 to 52 MB), the path source for the disk, and the Buffer source for a public paper (the bytes are already held by `getPdfBytes`). Do `route.ts:79` / `:100` first: it is inside the C's own file and is worth 25 MB alone.
3. **(a), part 2, last, and lazily.** It is the only candidate that makes the first view of an upload read less than the whole object (the download is 215 MB of the 267 MB in production) and it matches the owner's sentence literally (the figure's page file). I recommend building it **on the first miss for a page, not at upload**: the first cut of any figure on a page opens the whole object once through (c), writes that page's file (`graftPage` + `OCProperties`, keyed `hash16|page`, revision-free: a page cut does not depend on the figure rules) and the PNG; later figures on that page, and a revision bump, open the page file. This keeps the upload route (C P12-58's, 246 to 296 MB for 3 s if it split all 21 pages) unchanged and pays only for pages that are viewed; the cost is that the first view of the first figure on each page still reads the whole object. If the manager wants zero whole-object reads for new uploads, the split goes into the upload route (D3).
4. Not recommended: a server cache of public papers' images or page files; a read-ahead cache in the stream handle; lowering the 4.5 Mpx cap (the render is 14 to 16 MB for these pages).

## 5. Decisions for the manager

- D1. The order (b) → (c) → (a-lazy), as recommended, or (a) at upload for new uploads. At upload: 246 to 296 MB for about 3 s and +15 % stored bytes in the function that is already the tightest; lazily: only viewed pages, one whole-object open per viewed page.
- D2. The engine slot for C P12-61 (additive: a source type, `cutPdfPage`), or a later C after P12-47/54/55/56 land. Without it parts 2 and 3 can only do `route.ts:79`/`:100` and the page-file read side (`onlyPage: 1`).
- D3. A private temp file for the bucket's whole-object stream (c-tmp: 169 to 176 MB against 229 to 240 for a Buffer stream). It contradicts the pool path's "nothing touches the disk" stance, and follows `withUploadPdfFile`.
- D4. The 215 MB bucket read is the largest single cost in production and no engine change touches it: only (a), (c-tmp) or a ranged read do. Whether the owner's deployed function (2 GB) is dominated by one call or by concurrency I cannot say from here: one call peaks at 190 to 290 MB, five at once 350 to 370 MB in this process before Next's own runtime and the reading build's caches (P12-59).
- D5. Public papers: leave the CDN as the cache; no stored derived images or page files of publisher PDFs.
- D6. Old uploads (no page file, no cut): the first view takes the whole-object path through (c) and writes both objects; nothing is backfilled.

## 6. What this does not show

- The deployed function's memory and Supabase's real `download()` were not measured; section 1.5 and the production-shaped table use a local HTTP server with `fetch` → `blob()`. Wall times are not given as results (load 25 to 56 on four cores; one run took 56 s for a 3 s call): CPU and resident memory are.
- The peak has a 15 to 30 MB collector spread; where I give two numbers they are two runs. P1 differences between variants are inside it.
- One dense page (P5 page 7) is the only heavy case; a paper with several would show the page-work column (+100 MB, and the heap stays at its high mark) more often.
- Encrypted files, damaged cross-references, rotated or cropped pages, annotations and links in a cut page file were not tested (only the optional-content hazard was, on an invented PDF); a cut that fails returns null and the route should fall back to the whole object.
- No test of the repository was run, no code of the repository was changed, and the scratch engine differs from the real one only by the ceiling, the budget and the hooks.
