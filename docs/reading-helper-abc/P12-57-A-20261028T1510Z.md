## 4. What the review did on the page

- **Fallbacks: 11 of 30 runs, all `unusable`** (no `timeout`, `provider_error` or `too_large`; no HTTP error). By paper: P4 5/5, P3 4/5, P1 1/5, P6 1/5, P2 0/5, P5 0/5. In a fallback the page keeps the rules' draft, and the browser keeps a failure for an hour. The size of the model's reply in a fallback was the same in every fallback of a paper (P3: 82 characters, 23 output tokens, in all 4; P4: 95 characters, 28 tokens, in all 5; the single fallbacks of P6 and P1: 75 and 127 characters), so a given paper tends to draw the same reply. **The `unusable` branch is two things in the code** (a reply that is not an answer; an answer whose every correction was refused, `reviewStructure`, `sanitized.read > 0 && corrections.length === 0`), and the server logs only the prompt and reply sizes on it (`rejected` is logged on the success path only), so which of the two happened cannot be told from `dev.log`. The one P3 run that reviewed also had a 23-token reply.
- **A review with corrections changed no row in 9 of the 10 runs that had one** (P2 ×3, P3 ×1, P5 ×5 changed nothing; P6 run 3 changed row 3's role). Where the harness recorded what the browser keeps (P4 runs 2–5 and all of P5 and P6): P5 ×5 and P6 run 3 hold a review with the corrections counted above (P6 runs 2, 4 and 5 a review with none), P4 runs 2–5 and the P6 fallback hold a failure; so where corrections were made, the review had reached the browser and been kept for the page's draft, and these are not lost answers. From reading `applyStructureReview` (not a measurement): the layer only sets a row's role, from the majority role of the row's paragraphs under the corrected parts; a split or a moved start inside a row, or a role that matches the row's majority, shows nothing on the map. So the corrections' indices (in `structure.entry`) say more than the rows do.
- Each run sent one `/structure` request; nothing else model-backed happened beyond the report route's call.
