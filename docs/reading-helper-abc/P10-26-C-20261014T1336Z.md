## 2. Rule 1 — where the dimensions are, and what is carried (disclosure first)

**The extractor's dimensions are not available when the reading is built.** The reading is built from the *text* extractor (`pdf-text.ts` / `pdf-outline.ts`, unpdf); its figure captions carry only `ordinal / label / caption / page / at`. A picture's box is known only to the MuPDF figure engine (`lib/figures/pdf-engine.ts`: `box` in points and the PNG's pixel size, in `renderRegion`), which runs when the browser asks `/api/papers/[id]/figure-image` for the picture — that is, when the picture itself arrives. Carrying the numbers earlier would need a measuring pass of the engine at reading-build time (`pdf-engine.ts` / `pdf-text.ts` / the extraction cache's version), which is not a file this brief names, so I did **not** do it. What is built: the record carries the numbers if a source gives them (`ExtractedFigureCaption.width/height` → `placeFigures` → `ReadingFigure.width/height`, kept only as a pair of positive whole numbers), `Figure` draws them. **On the owner's paper, 0 of the 10 figures have a size today** (`peer-reading-v2` in the browser: all ten `width/height` null); they keep the fixed 32rem room, so for this paper rule 2 is what stops the twitch. HTML sources could carry `<img width height>` the same way (`html-text.ts` `imageInBlock`) — not done, not mine.

As built: `figureBoxStyle(figure)` → `{ aspectRatio: "w / h", width: "min(100%, wpx, calc(32rem * w / h))" }` — the picture's own size, never wider than the mat's column nor taller than the img's `max-h-[32rem]` at its ratio; `Figure` draws the box (`mx-auto`) inside the unchanged mat, the img fills it (`h-full w-full object-contain`). The first paint is the box (no state, no guess). A figure with no size is byte-identical to before (the two exact-markup tests untouched). `width` / `height` are the picture's **pixel** size (the route's PNG), because the picture is shown at its natural size when it is narrower than the column.

**Measured with the sizes injected** (Playwright rewrites the reading response with each picture's own natural size, taken from the first load of the owner's pictures; this simulates the extractor carrying them, it is not the product's data): the ten mats **544 / 544 / 544 / 544 / 538.9 / 544 / 513.3 / 441.5 / 544 / 544 px before and after every picture arrives — delta 0 on all ten at both 1440 × 1000 and 1280 × 720; page 33,186 px before and after.** Unsized (as shipped): 544 each before; after 544 / 544 / 544 / 544 / 538.9 / 544 / 513.3 / 441.5 / 544 / 544 → deltas 0 / 0 / 0 / 0 / −5.1 / 0 / −30.7 / −102.5 / 0 / 0, page 33,324 → 33,186 (the X-A8 shrink).

## 3. Rule 2 — the settle

`SettleEnv.pendingAbove?(target)`: in the browser, the `<img>`s in `document.images` with `complete === false` that precede the heading in document order (`compareDocumentPosition`). `settleOnSection`: (a) while any is pending (after the first rest, inside the 10-s late cap) the watch by frames goes on, a second at a time, so the landing is not final; it ends a second after the last one has settled; (b) a heading found moved on a frame where a picture above is pending or has just settled is landed again at once (no wait for three still frames — the movement is the picture's, not the reader's scroll). The reader's input still ends it; the 10-s cap is the existing one; an env without `pendingAbove` behaves as before (the existing 12 tests untouched). Cost: a frame loop of up to 10 s while a lazy picture above the heading has not loaded (a lazy picture far above the viewport is never loaded and counts as pending until the cap or the reader's first input).
