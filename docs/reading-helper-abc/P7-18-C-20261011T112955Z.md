## Each fix as built

**F1 — the abstract line (`d3b25fbe`).** New `abstractLine(text, max = ABSTRACT_LINE_MAX = 1_200)` in `lib/papers/skim.ts`, built on `splitSentences` (so `Fig.`, `et al.`, initials and decimals such as `0.5` are not sentence ends): an abstract that fits comes back untouched; otherwise the whole sentences that fit, joined by one space; a first sentence that alone exceeds the limit is cut at the last space that leaves room for the ellipsis and ends with `…` (a token with no space in the window — not an abstract, a garbled extraction — is cut at the window's edge; a cut between the halves of a surrogate pair drops the half). `upload/route.ts` stores `abstractLine(abstractSection.text)` instead of `.slice(0, 400)`. Rendering checked: `summaryIntro` reaches the reading's abstract (`buildReading` → `splitSentences` → `AbstractToggle` → `Paragraph`s); there is no `truncate` or line-clamp class on that path, and the other consumers (`paper-card` word count, `tile-lines`, `notes-rail`, `cite`, `plate-terms`, the explain/report abstract) take the string whole.
  *Two surviving tests pinned the 400 and are re-aimed to the new contract under §1c (the only test lines removed in the whole item):* the route's "capped to 400 chars" (now: an abstract that fits comes through whole) and the `/privacy` test (see "For the manager" 1).

**F2 — end matter (`f8bfff41`).** `endsTheArgument(heading, canonical, afterBody)` in `pdf-outline.ts`, on the heading's own words (a case-sensitive section-number lead stripped first, then case-insensitive):
- always ends the argument: `associated content`, `author information`, `author contributions?` (prefix, word boundary) and `supporting information` (the heading alone, with an optional `available` / `statement`, so "Supporting information retrieval" is a body heading);
- ends it **only after the body's last numbered section**: `funding` (the heading alone, optional `sources` / `information` / `statement` / `support`, so "Funding models for research" is a body heading), `conflicts? of interests?`, `declarations? of (competing )?interests?`, `competing (financial )?interests?`, `data availability`;
- `Notes` is not in any list: it is cut because it stands after one of the above and everything from the first end-matter heading on is out already (`done`); a "Notes" section or "Notes on the method" earlier in the body stays.
"The body's last numbered section" is found by a backward pass over the page's lines (`headingOf` + `sectionNumberOf`, skipping furniture, margin print and the date box, and skipping numbered headings that are themselves end matter, so "6. Funding" ends the argument as the last numbered thing). A paper with no numbered section has no such line, and there those five headings stay sections, as before.

**F3 — the subsections' buckets (`48b142fd`).** The cause is not in `pdf-text.ts`: the empty parent is dropped earlier, in `buildOutline`'s `flush()` (it writes no section for a heading with nothing under it — a surviving test pins that), so `withInheritedBuckets` in `normalize` never saw "2." or "4.". Fix: `html-text.ts` gains `bucketInheritor()` (the same inheritance, one heading at a time, with the document's numbering as its state; `withInheritedBuckets` is now a `map` over it, same answers); the outline's `flush()` tells it every heading, text or not, and writes the section with the inherited bucket. A subsection whose own heading names a strong bucket keeps it; a subsection with no numbered ancestor and an unnumbered paper are untouched; `normalize`'s own `withInheritedBuckets` pass stays (idempotent). The no-key Decision sentence reads `provenance.buckets`, so it follows with no change of its own (tested through `buildReading` + `describeAvailability` on a real PDF read by pdf.js).

**F5 — the section key (`cdfd6411`).** `paper-body.tsx`: `key={section.id ?? \`${i}\`}`. This project's Vitest has no DOM and `react-dom/server` never checks keys (only the client reconciler does), so the new `paper-body.keys.test.tsx` runs `PaperBody` on `test-support/hook-runtime` and reads the keys off the element tree it returns (equal to the ids, no key twice; the fallback is the index for a section with no id), plus a server render under a `console.error` spy that must see no key or other error.

**F6 — Submit (`6d124061`).** `question-field.tsx`: `[@media(hover:none)]:min-h-11` on the Submit button; desktop unchanged.

## For the manager

1. **`/privacy` copy changed (user-visible).** The page told the reader "an excerpt of its abstract up to 400 characters"; the record now carries up to 1,200, so the sentence says **1,200** (`app/privacy/page.tsx`, one number) and the two tests that pin the sentence and the route source line were re-aimed. Outside the letter of the brief but a direct consequence of F1 (a false privacy sentence otherwise, and a red test); veto it if the sentence is yours to word.
2. **The position guard is wider than the brief's "funding only".** P0-01's own comment in `pdf-outline.ts` names Funding, Data availability and Competing interests as headings some templates print on page 1; an unguarded `data availability` / `competing interests` printed on such a first page would end the argument there and empty the body. So all five are guarded by "after the body's last numbered section"; `associated content`, `author information`, `author contributions`, `supporting information` are not. Cost: in a paper with **no numbered sections** (Nature-style) those five stay sections, exactly as before this item. A numbering-free rule (for instance "after a methods / results / conclusion heading has been seen") would cover those papers; I did not add it without a second sample.
3. **Matching is whole-heading for `supporting information` and `funding`, prefix for the rest.** Reason: a body heading such as "Funding models for research" or "Supporting information retrieval" must stay. Consequence: if a template sets two end-matter headings in one face and size a leading apart, `wrapsHeading` joins them into one heading ("ASSOCIATED CONTENT Supporting Information"); `associated content` still matches by prefix, but a joined "Funding …" would not. Not seen on the owner's paper.
4. **A leading glyph defeats the word match** (pre-existing for `APPARATUS_HEADING`): the owner's 52-page printout has "■ ACKNOWLEDGMENTS" and the paper has "*sı Supporting Information". On the paper this is moot (ASSOCIATED CONTENT ends the argument first); on the printout the rows "Authors" and "Notes", which that layout prints before the acknowledgements, stay in the map (only "AUTHOR INFORMATION" and "Corresponding Authors" left). Stripping leading non-letters from a heading's own words would fix both; not done (outside the brief).
5. **The HTML extractors have the same drop-before-inherit order** (`if (!text) continue` before `withInheritedBuckets` in the LaTeXML / JATS / PMC paths): a numbered parent with no text loses its children's bucket there too. Not touched (the brief is the PDF; no HTML paper of the owner's is in evidence); `bucketInheritor` is exported, so the fix is a few lines if you want it.
6. **The frozen abstract line.** `summaryIntro` is computed at upload and stored in the upload's record: the version bump (4 → 5) retires the cached *text*, but an upload made before this item keeps its 400-character line until the owner re-uploads it (the note of §1h.39 a stands).
7. **F5's test reads the element tree**, not React's warning: no DOM in this Vitest, and only the client reconciler emits "same key". A real-browser confirmation (21 console errors per load before, none after) is A's to repeat if wanted.
