# P9-07 — B: two questions settled with Enter became ONE line (`…cycles?How does…`)

Role B (investigator, read-only). Source read: `origin/deep-report-reading-helper-enhancement` at 6957f800 (`web/src` identical to fd47c672; only docs above it). Nothing under `/home/user/peer` changed; the experiments ran in a detached scratch worktree (`scratchpad/p9/b07/wt`, nothing committed) and in real Chromium with real React. No key, no network, no model.

## 1. The answer in one paragraph

Nothing in the field or the store ever joins two lines. Enter had added line 2 but **the focus stayed on line 1**, so the next question was inserted at the end of line 1 (the textarea caret is there; `oneLine` only touches line breaks, so no separator). The hand-off of focus is a ref (`pendingFocus`) read by a `useEffect` with no dependency; when Enter arrives after the page's debounced render has committed but before that commit's passive effects have run, React runs those older effects first, they read the new request, find no line 2 yet (`inputs.current[1]` unset) and clear it, so the render that adds line 2 has nothing to focus. It **reproduces** deterministically (forced interleave, and by plain timing: Enter 250 ms to 250 ms + page-render after the last keystroke), in the project's runtime (3 red tests, exact merged text), and on real React 19.2.4 and Next's vendored 19.3.0-canary in Chromium; it is fixed by three variants, the one I recommend being state-keyed focus (section 4).

### Every path by which two lines could become one string (question 1), and what the code does

- `oneLine` (:54-56, called in `onChange` :444): a pasted break becomes a *space*. Cannot produce `?How`.
- `commit` (:370-375) is the only caller of `setLines`; its call sites are `onMark` :388 and `onGist` :394 (lines unchanged), `onChip` :401 (`fillNextLine`, fills an *empty* line or pushes a new one), `onChange` :452 (one index), Enter :461 (`addLineAfter` inserts `""`), × :480 (`removeLine`, a filter). None appends one line's text to another.
- `addLineAfter` (:105-112): when another empty line exists, Enter focuses it instead of adding one (that is what the second Enter did in the walk: line 1 now held both questions, line 2 was empty, so it only moved focus; the third Enter, on the empty last line, settled the merged text).
- `cleanQuestions` (`store/reading-questions.ts:99-112`), called from `set` :128 and `settle` :157: per item `trim`, `slice(0, 500)`, drop empty, drop case-insensitive duplicates. The 500 clamp is per item, never on a joined text; the browser's `maxLength={500}` caps one textarea.
- `useDebouncedQuestions` (`use-debounced-questions.ts`) **never writes to the store**: it subscribes, and after 250 ms does `setByPaper(getState().byPaper)` — React state of the *page*. The field writes the store synchronously on every change (`commit` :374). So no stale debounced write can overwrite a two-line state with a one-line value.
- Settle on blur racing settle on Enter: gone since P7-13 (the section's `onBlur` :416-421 only `setFocused(false)`; the line's `onBlur` only `trackLine`). Enter on the empty last line settles through `submit` :365 (`enterEndsTheBox` :236).
- Stale-closure `onChange`/`onKeyDown` (they close over the render's `lines`): React flushes a discrete event's render before the next event, so each handler sees the latest `lines`. Not the cause; the instrumented trace shows `lines.length=1` only inside the *stale effect*, not in a handler.
- React batching of `setLines`/`setGist`/`setMarked`/`setUnsettled`: one batch per event; fine.

What is left is that the typed text lands in the wrong textarea. In the walk's first run the result was line 1 of 118 characters (59 + 59), line 2 empty, settled `[merged]` — exactly what the forced interleave below produces, and not what any other path yields.

## 4. The rule and the fix

**Rule.** A request to focus a line belongs to the render that adds that line. It must travel with the lines (state set in the same batch), not sit in a ref that any render's effect may read and clear.

**Sketch (variant B, state-keyed, 12 lines changed in `question-field.tsx`; the patch is `fix/fixB-state-keyed.diff`):**

```tsx
// replaces `const pendingFocus = useRef(...)` and the no-deps effect (:338-348)
const [focusLine, setFocusLine] = useState<{ index: number; caretAtEnd: boolean } | null>(null);
useEffect(() => {
  if (!focusLine) return;
  const input = inputs.current[focusLine.index];
  if (!input) return;
  input.focus();
  if (focusLine.caretAtEnd) input.setSelectionRange(input.value.length, input.value.length);
}, [focusLine]);
// :400  setFocusLine({ index: filled.focus, caretAtEnd: true });     (onChip)
// :460  setFocusLine({ index: added.focus, caretAtEnd: true });      (Enter that adds a line)
```

An older commit's effect holds an older `focusLine` and, its dependency unchanged, does not run again; the effect that runs is the one of the commit where `focusLine` changed, together with the lines and after the refs are attached. The direct `inputs.current[added.focus]?.focus()` :463 for an existing empty line stays.

**Two smaller alternatives, both verified the same way (`fix/fixA-layout-effect.diff`, `fix/fixC-clear-when-found.diff`)**: A: `useLayoutEffect` instead of `useEffect` for that effect (2 lines; runs inside the commit that adds the line; `components/notes/note-editor.tsx:503` already does this). C: move `pendingFocus.current = null` below `if (!input) return` (2 lines; the request survives until its line exists; `note-editor.tsx:516-517` already clears only after finding the element). I recommend B because no ordering of effects can matter; C is the smallest diff if the owner prefers it. Do not combine; pick one.

### Risk

Low. B adds one state value set in the batch that already exists (no extra render); a repeated request is a new object, so it re-fires; at mount the value is null. A discrete event's render runs its passive effects before the next event, so the focus lands before the reader's next key; if effects ever lagged, the line still exists, so the right line is focused (only characters typed in the meantime stay in line 1). The fix changes nothing for Enter on a full box or onto an existing empty line (direct `focus()`). Residual: the box still cannot tell a reader that a question went into the wrong line; with the focus right there is no longer such a case from this cause. A's risk: none known; the app already uses `useLayoutEffect` in `note-editor.tsx` (:223, :503, :603, :1137). C's: a request for a line that never appears would linger until a later render; none of the call sites can produce one.
