## The rule, and what was decided

**A term and its count never part.** Cause: the fact line was one plain string (`ROUTE.mentions`), so the browser could break at the space before "×". On the owner's row at the default pane (my invented paper: "2. RESULTS AND DISCUSSION", "1. INTRODUCTION") the line read "strongest · mentions film ×6, growth" and the next line "×6, LCO ×6".

Means: `MentionsLine` (`reading-map.tsx`) draws each stated term in two pieces. What stands before the term's last word (the first words of a multi-word term) is plain text, so a break may fall inside the term. The last word, the space, the "×" and the count, with the comma after them, are one `inline-block max-w-full` span, which the line breaker takes whole. The line is `wrap-anywhere` (inherited by the span), so a unit longer than the line wraps inside itself and nothing runs past the pane. Inside the span the last three letters of the word, the space and the count are one `whitespace-nowrap` piece (`COUNT_COMPANY = 3`): a term that fits a line alone but not with its count (a 31-letter term on a pane of about 282 to 316 px; "polytetrafluoroethylene" at 240, in the test) first broke at the space and left the count alone on the next line; now it breaks inside the word and the count follows its last letters. The one plain space after each comma is where the line may break. A static Chromium probe (`h/css-probe2.mjs`) showed this clean at every line width from 8 to 40 characters for a 31-letter, a 23-letter and a 6-letter term; without the nowrap piece it parted at 4 to 10 of those 33 widths for each (`h/css-probe.mjs` and `h/css-probe2.mjs`; every script of this checkpoint is in `/tmp/claude-0/-home-user-peer/9602921a-6ac5-5952-88ce-8364fcd8f733/scratchpad/p11c35/h/`, the JSON in `../out/`).

Why not a no-break space: it would put U+00A0 into the line's text, and a selection copied from the page (Firefox keeps it), a screen reader's string and the export path are the rule-2 concern. The spans carry the "cannot break"; the characters stay plain. (`for-your-questions.tsx` does use ` ` in `readNextLabel`; it was not followed, for that reason.)

**What leaves the page stays plain (rule 2). Where `ROUTE.mentions`' string goes, from the code:** `ROUTE.mentions` is defined in `components/reader/copy.ts` and used by exactly one non-test file before and after this change: `reading-map.tsx` (before: `ROUTE.mentions(mark.hits)` built the `fact` string drawn in the row's `<p class="annotation pl-5 …">`; after: `MentionsLine` draws the same words from `ROUTE.mentionsLead` and `ROUTE.mentioned(hits)`, which `ROUTE.mentions` itself is built from). It is not the row's `title` (that is `ROUTE.questions`, "Q1, Q3", `paper-body.tsx`), not in `lib/papers/reading-markdown.ts` (the Markdown export writes `MAP.page` and `MAP.minutes` only), not in any feed, route, store or notes code (a source scan over `src/` finds `ROUTE.mention*` in `copy.ts` and `reading-map.tsx` alone). So no export, copy, feed or JSON carries it, and the string is unchanged: `ROUTE.mentions` returns the same bytes as on the base, and the line's DOM text is that string with plain spaces (the test compares them in full and rejects U+00A0, U+202F, U+2007, U+2060, U+200B to U+200D and U+FEFF). `reading-map.fact.test.tsx` pins the one caller.
