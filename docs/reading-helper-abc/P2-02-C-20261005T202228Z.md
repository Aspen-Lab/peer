## What changed

### `web/src/lib/papers/report.ts`

**Types.**
- `Claim` gains optional `sectionId` and `page`.
- New exported types:
  - `QuestionVerdict`: `answered`, `partly`, `not_addressed`;
  - `ReadNextItem { sectionId, why, kind: "answer" | "background" }`;
  - `QuestionAnswers { question, verdict, answers: Claim[], readNext: ReadNextItem[] }`;
  - `PaperTerm { term, definition, evidence?, evidenceWhere?, sectionId?, page?, peer?: true }`.
- `PaperReport` gains `forYourQuestions?: QuestionAnswers[]` and `terms?: PaperTerm[]`.

**Caps.** `REPORT_CAPS` gains questions 5, answers 3, answerChars 360, readNext 4, whyChars 160, terms 8, termChars 60, definitionChars 160.

**Sanitizer.** `sanitizePaperReport(raw, { questions }?)`. The second argument is optional, so every existing call is unchanged.
- With questions:
  - Entry *i* answers question *i*, and its `question` is overwritten with the request's own `questions[i]`.
  - Entries beyond the request's count (and beyond 5) are dropped.
  - An entry is dropped if its `verdict` is not one of the three names.
  - Answers are capped at 3 claims, `text` ≤ 360 and `evidence` ≤ 400, each with an optional `sectionId` (a valid id string).
  - `readNext` is capped at 4 items, and each needs a valid id, a `why` (≤ 160 characters) and a `kind` from the enum.
  - Terms are capped at 8, with `term` ≤ 60 and `definition` ≤ 160. A term without `evidence` gets `peer: true`.
  - Either key is absent when empty.
- Without questions, both keys are dropped, including ones the model volunteers.

### `web/src/lib/papers/evidence.ts`

**Lookup.**
- `CorpusEntry` gains `sectionId` (the section's own id, or `s<index>`) and `page`. The abstract and figure captions have neither.
- New `locateEntry(evidence, entries, preferId?)`: it tries the model's section first, then falls back to corpus order (abstract, sections, captions).
- `locate` is now `locateEntry(...)?.where`, so its behaviour is unchanged.
- New `placed(entry)`: `evidenceWhere`, plus `sectionId` and `page` when the quote sits in a section.

**Verification in `verifyReportEvidence`.** The added part runs only when the report carries `forYourQuestions` or `terms`.
- **Each answer.**
  - The evidence is located with the model's `sectionId` preferred. The answer is rebuilt as `{ text, evidence, …placed }`: the model's id is kept when right and corrected when wrong. A quote that sits only in the abstract carries `evidenceWhere: "abstract"` and no id or page.
  - An answer whose evidence is not found is dropped and counted.
- **Each question.**
  - A `not_addressed` verdict carries no answers; any it had are discarded, not counted.
  - A question with no verified answer becomes `not_addressed`, whether every answer failed or none was given.
- **Each `readNext`.** One whose `sectionId` is not a body section of the document is dropped and counted. The abstract section counts as not a body section.
- **Terms.**
  - A term with `evidence` is verified like an answer. It is placed if found, and dropped and counted if not.
  - A term without `evidence` keeps `peer: true`.
  - `terms` is absent when none survives.
- All drops go into `provenance.droppedClaims`.

### `web/src/lib/papers/deep-report.ts`

**Schema, only with questions.** The `outputSchema` gains `forYourQuestions: [{ question, verdict, answers: [{ text, evidence, sectionId }] (max 3), readNext: [{ sectionId, why, kind }] (max 4) }]` and `terms: [{ term, definition, evidence }] (max 8)`.

The rules gain:
- one entry per question, in order, with `question` copied back;
- answer evidence is copied character-for-character, or the answer is omitted;
- every `sectionId` is the `id` of a section as given in `body`;
- `not_addressed` means the paper does not address the question, and then `answers` is empty;
- the meaning of `readNext.kind` "answer" versus "background";
- a term's definition is the paper's own (with `evidence`) where the paper defines it, and otherwise Peer's own words (no `evidence`);
- where to quote from: on a long paper, "`questionRelevant` holds sentences of the paper chosen for each question…"; on a short one, "The whole paper is in `body`; quote from there."

Without questions none of these keys, inputs or rules is in the prompt.

**Budgets (§1g.10 a).**

- `fitCut` was taken out of `fitTexts`. The body is fitted against the prompt as it would be **without** questions (`assemble(texts, false)` ≤ `PASS2_MAX_INPUT_CHARS`), so questions never cost the body a character. The questions, their schema and rules, and the evidence come on top.
- New `fitRelevant`: while the serialised `questionRelevant` is over 12 000, the question with the longest list loses its last sentence. Only whole sentences are removed, and an emptied list goes.

**No Pass 1q on a short paper (§1g.10 b).** `runsQuestionPass = runsPass1 && questions.length > 0`.
- On a short paper `questionRelevant` is absent from Pass 2, and the rules say "The whole paper is in `body`; quote from there."

**Wiring.** `runPass2` calls `sanitizePaperReport(parsed, { questions })`, then `generateDeepReport` verifies as before. Questions now reach every step.

## Choices beyond the brief

1. **Rule wording.** The short-paper rule names `body` rather than `sections`, because that is where Pass 2's sections are: `body: [{ id, heading, text }]`. On the long path the section outline is `body.sections`.
2. **Not answered is not invented.** An entry with an unknown verdict is dropped rather than given one. A request question with no model entry stays without an entry; no verdict is invented for it.
3. **Strict `readNext`.** An item with an unknown `kind` or an empty `why` is dropped by the sanitizer. That is not counted, because the item fails the schema rather than the verification.
4. **`readNext` and the abstract.** A `readNext` that names the abstract section is treated as not in the body: dropped and counted, since the map has no abstract row.
5. **`not_addressed` answers.** Answers given with a `not_addressed` verdict are discarded uncounted, so the page can show exactly one sentence.
6. **Term ids.** A term may carry a `sectionId`. The schema does not ask for one; it is used only as the preferred section when locating the term's evidence.
