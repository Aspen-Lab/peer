## B finding (read-only, before any change)

**What the label waits on.** `PROGRESS_LABEL` ("loading report...", `copy.ts`) is drawn by `DecisionBlock` only while `useModelReport`'s `stage` is non-null; `stage` is the stream's `buildup` for the current report key while there is no report. So it waits on exactly one request: the NDJSON stream of `/api/papers/report` (the deep report: full text, the question pass, Pass 2, figure binding). It does **not** wait on the per-question pass as a separate request (it is inside that stream), nor on the paragraph guide (`use-paragraph-guide`, a different hook that draws no label). The answers ("For your questions") come from the same `report`, so the label and the answers cannot both be drawn: `stage` is null whenever `report` is.

**Request log** (stub delays pass1q 3 s, pass1 3 s, pass2 8 s, figbind 2 s, gist 5 s; Submit at 0). One question, earlier report finished: `pass1q` +0.9 s (3.0 s), `pass2` +3.9 s (8.0 s), `figbind` ×2 +11.9 s (2.0 s); the label stood 0.66 s → 14.01 s and the answers appeared at 14.01 s. The label cleared in the same 50 ms sample as the answers (lag 0). A question submitted while the question-less request was still running: that request ran to +8.2 s with **no label and no answers on the page** (7.5 s of nothing: the label is keyed to the new key and the request in flight is the old one), then the new request's label stood 8.25 s → 18.28 s and cleared with the answers.

**Whether it ever clears.** In every stubbed run the label cleared within one 50 ms sample of the report, of a failure (the "Your model could not finish" line) or of Tier 0. The reported "past 121 s with the answers shown" **was not reproduced**, and by construction cannot be drawn while a report is: if it was seen, the answers on the page were not this key's report. What the head does allow, and what I measured: (1) a model call that never answers keeps the label up as long as the call holds — 1.25 s → 281.4 s with the stub holding Pass 2 for 280 s, no deadline, no line; on the platform the stream is cut at the route's `maxDuration = 180` s, the client then asks the **whole report again as JSON** (a second full request, with the label frozen on the last stage), so up to about 2 × 180 s; (2) the label names nothing (a fixed string; the server's own stage labels, "Reading it" / "Writing the report", are in the sentence's suffix only); (3) 7.5 s of silence while an earlier request finishes ahead of a new question; (4) no label before the server's first stage. Which of these the key session met is not decidable from its note; (1) and (3) are the ones that fit a long wait with answers elsewhere on the page.
