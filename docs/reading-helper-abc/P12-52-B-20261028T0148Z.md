# P12-52 B — can the sticky card and the notes window lose an edit on the same note? (the real page)

Head: `d8a8197a77c513af829d4806139ce236e83533f9` (branch `update-on-paper-digest`, detached worktree; no product file touched). Model: Claude Sonnet. Read-only; this file is the only commit. Written 2026-10-28 (UTC stamp in the file name).

## Setup and limits (read first)

- Real page, real Chromium (Playwright, `chromium.launch()`), real timers, real mouse and `keyboard.type`. Dev server `next dev -p 4243` from the worktree with the model stub (`PEER_PRIVATE_UPLOAD_DIR`, `P602_DIR`, `model-stub.cjs`); no key. Input: only the invented `invented-stress.pdf`, uploaded once through the upload UI; the browser state was kept in a Playwright `storageState` (scratch, not committed).
- One note, one sticky ("Note 1", anchored on `paper-section-0-p1`) holding the block `hello sticky`; the notes window opened on the same note ("Open your notes", the edge tab). At 1440x900 both cards stand whole side by side. Tokens appended at the end of that block: sticky `" aaa"` (4 keys), window `" bbb"` (4 keys), 40 ms per key (`keyboard.type` delay; 10 ms in the pagehide-tight runs). Clicks on the other surface are real mouse clicks (`page.mouse.click`), the block is made live by the click, `Control+End`.
- Instrumentation is browser-side only (`addInitScript`): it logs every keydown with the surface it landed in (`S1` sticky, `W` window, `page` = no editor focused), pointerdown, focus moves, and every write of `localStorage` key `peer-notes` with the call stack of the writer (dev build keeps function names). Reads after each trial: the stored note (`peer-notes`), the sticky's and the window's DOM, then after a reload "Open your notes" and `/notes/<id>` (the notes page).
- **Load was not controlled.** The machine was shared by about 13 workers: load average 23-55 for most trials (1.7 for one), so every latency below (render, remount) is inflated and the exact gap widths are not the quiet-machine values. The container ran out of memory twice during the run (Chromium renderer crashes, a killed server); trials that errored (server dead, `Target crashed`, 170 s watchdog) are **excluded** and counted as "errors". The order of events is reliable; absolute milliseconds are not.
- Gaps below are the **measured** ones (last keydown of the first surface to the pointerdown on the other, from the in-page log), not the intended ones: Playwright round trips add 50-300 ms.
- Counts are small (most rows 1-6 trials). "0 of n" is not a proof of absence.

What was **not** seen in about 45 usable trials outside the pagehide-tight row: a store write that lost a writer's text. Whenever both surfaces held text and the page lived on, the merge (window `reconcileWindow` + sticky `mergeStickyContent`) kept both. The losses are (i) keystrokes that never entered an editor (rows b, c, e6, h2), (ii) the pagehide-tight row, and (iii) text typed into the wrong surface (rows h, h2).

Order: in every row where both tokens survived, the order was the **typing order** (`aaa bbb` when S typed first, `bbb aaa` when W first). Two same-position inserts are ordered by "stored first" (`mergeText`, `notes.ts:257-260`), which in these timings equalled typing order; I did not find a timing that inverted it (not shown absent). One alteration: a sticky key typed with no space before it (`a`) is stored as ` a` when merged after the window's text (`hello sticky bbb a`; the join rule `notes.ts:258` adds a space the reader did not type).

## 2. Mechanisms (with file:line at the head)

### M1 — pagehide: the window's stale whole-note save lands after the sticky's flush, and what follows can run away

Minimal sequence: type in the notes window on a block (window dirty: its 500 ms save pending), click the sticky and type one key in the same block (writer pending: 150 ms), then leave the page (tab close, reload, navigation that commits) before the sticky's 150 ms. In my runs the leave came 20-60 ms after the sticky key and about 250-300 ms after the window's last key. Window of exposure: the sticky's last key is less than `STICKY_SAVE_MS = 150` (`sticky-note.tsx:42`) before `pagehide` **and** the window's last key is less than 500 ms before it. With a slower leave (`reload` that took 1.5 s; client route change) the sticky's timer had fired first and nothing was lost (e3, e5, 0 of 7).

Order of writes, taken from the call stacks (`e6 tight`):
1. `StickyNotes` registered its `pagehide` listener when the page mounted (`sticky-note.tsx:612-619`), so it runs first: `removeEmptyStickies` -> the writer's `flush` (`sticky-note.tsx:146-158, 207-215`) -> `setStickyBlocks` (`notes.ts:605-616`). Store: `hello stickya`.
2. The window's `NoteEditor` registered its listener when the window opened (`note-editor.tsx:766-778`), so it runs second: `flush` -> `saveNote(note.id, docRef.current)` (`note-editor.tsx:770`) -> `save` (`notes.ts:529-554`). `docRef` holds `hello sticky bbb` and **no base**: `save` replaces the block wholesale. Store: `hello sticky bbb`; the sticky's `a` is gone. This is the "case 2" of P12-36 B, reached on the real page: the window's flush ran 43 ms after the sticky's writes (a React render of the first store change ran in between), and the reconciliation of its case 1 (`notes-window.tsx:346-373`) had only queued its `setFresh`, which renders later, so the stale save came before the seed.
3. In 10 of 11 runs the page then entered a loop whose every later write has the same writer: `NotesWindow.useEffect` = the seed save at `notes-window.tsx:367-373`, alternating two forms (`hello stickya bbb...` and `hello sticky bbb a bbb...`), the text doubling each pass because `mergeText` keeps both tails when two same-position inserts differ (`notes.ts:257-260`: `t.text + join + m.text`). The first seed is the correct merge (`hello stickya bbb`, the sticky's `a` is back), then each store change makes `reconcileWindow` return `merge` again: `base.current` is not advanced after a `merge` verdict (`notes-window.tsx:354-360` only sets it on `same`/`restart`/`keep`), so every pass merges against the original base. Why `mine` and `theirs` differ on every pass (the new editor's `onDoc` has not yet set `doc.current` when the seed's store change is reconciled) is **inferred** from the stack order, not isolated by a mutation.
4. The loop ran inside the `pagehide` dispatch itself (the last `pagehide` listener I added, which runs after the app's, saw 4,356,629 characters), not after the page survived: in the first trial of the series (machine idle, load 1.7) it ran too. How long a real browser lets a `pagehide` handler spin before killing the page, and so how many doublings would be persisted on a real tab close, I did not measure; in this harness it ran until the 5 MB localStorage quota stopped it (the single `peer-notes` key then holds a 4.3 MB block; every later write of the store is at risk).
5. The one clean overwrite (1 of 11) is the same step 2 without step 3 (the tab was cut off before the scheduled render).

Stale base: the window's `docRef` base is the note as the window last saw it; the sticky's write after that is not in it. Last writer: the window's `flush` (second listener).

### M2 — the sticky "follows" the window's save by remounting its editor with `autoFocus`: focus is taken from the window

Sequence: the notes window and a sticky are open on the same block; the reader types in the window and pauses 500 ms (rows h, h2). The window's save changes the stored block; the sticky is not pending, so `stored !== seen` and `stored !== JSON.stringify(content)` (`sticky-note.tsx:525-533`) -> `setContent`, `setEditorVersion(v+1)` -> `<NoteEditor key={editorVersion} ... autoFocus>` (`sticky-note.tsx:579`) mounts again and its mount effect focuses its first block at the end (`note-editor.tsx:838-841`). Focus leaves the window. The rest of the reader's typing goes to the end of the sticky's block (4 of 4 in h, 5 of 5 in h2), not to the window's caret: no text is lost, but it is placed wrongly (`hello bbb  stickyccc`) and, in h2, once a key fell in the gap (M3) it was lost. Timing window: any pause of 500 ms or more in the window's typing while the sticky is open on that block; the sticky need not have been touched. Last writer: not a store race; the writer is whichever surface has focus after the remount.

### M3 — a focus gap after the sticky's own merged flush (keystrokes go to `page`)

Sequence (rows b at ~340 ms, c with Escape at 40 ms, one e6, one h2): W typed, S clicked, S typed; the window's save landed while the sticky was pending (no follow, base not synced: `sticky-note.tsx:528`), then the sticky's own flush wrote the merge (`...bbb aa`) and its result differs from the sticky's local content (it holds the window's `bbb`): the same follow branch (`sticky-note.tsx:525-533`) remounts the editor. Between the old editor's removal and the new one's passive effect focusing it (`note-editor.tsx:838-841`: `useEffect`, after paint) the document has no focus: the next key is delivered to `page`. Seen in 5 of 18 usable trials of the rows that can produce it (b 1 of 4, c 2 of 4, e6 loose 1 of 6, h2 1 of 4; one more in an errored e3 run); the gap measured 50-370 ms at load 23-50 (one render plus effect; not measured on a quiet machine). The key is lost; and `keyboard.tsx:130-240` runs single letters as commands when no typing target has focus (`s` save, `l` like, `n` notes, `h` highlight, `e`, `c` copy ...). I typed `a`, `b`, `c` only (one lost key was `c` = copy; I did not look for its effect) and did not run a trial with `s`/`l`/`n`: the consequence "a letter typed in the gap runs as a shortcut" is read from the code, not observed.

### M4 — a click on the window eaten by its own restart (seen once, not counted)

In the first, early-harness run of row a (gap 60) the sticky's 150 ms write landed during the click on the window: the window was clean, so `reconcileWindow` returned `restart` (`notes-window.tsx:357-359`), the editor remounted (`notes-window.tsx:418`) and the click left no caret (5 s of waiting); the reader's typing went to the sticky. Not reproduced in the later runs (the click landed after or before the write); listed for completeness.

## 3. Candidate rules, with cost against the existing tests

Existing tests that pin behaviour a rule may touch: `notes-window.merge.test.tsx` (181 lines; pure `mergeBlocks`/`reconcileWindow`, and the case "the window's whole write — its stale flush, then the merge", lines 167-181, which saves the stale copy then the merge, both without a base); `sticky-note.writers.test.tsx` (145; `makeStickyWriter` with `sync`, "two writers on one block within half a second" lines 48-69, and source-text assertions at 127-135 that `sticky-note.tsx` contains `addEventListener("pagehide"` and `removeEventListener("pagehide"`); `notes.writers.test.ts` (145; `mergeText`, `setStickyText` against a stale base, `removeEmptySticky` and "a stale copy saved after the removal"); `notes.structured-sticky.test.ts` (53); `sticky-note.test.tsx` (898; `stickyFollowText` 699-711, which is a pure function). None of them mounts React: the real-page sequences above have no test at all (the gap P12-36 B named).

### For M1a (stale whole-note save at pagehide / unmount)

1. **Whole-note saves carry a base; the store merges by block id** (`save(id, patch, { base })`, `NoteEditor` passes the blocks it last saw stored; same three-way as `mergeStickyContent`, `notes.ts:308-332`). Cost: touches the one `save` that the notes page, window and highlight protections share (`notes.ts:529-554`); `base` optional keeps `notes.writers.test.ts` and the merge test at 167-181 green unchanged; new store tests for stale save vs newer sticky block, deletion vs edit (the `removedStickies`/`removedEmpty` rules), highlight groups; the open question is a deliberate block deletion by the editor versus a block it never saw.
2. **Fix the leave order: all `NoteEditor` flushes first, sticky writers last** (a small registry like `openWriters`, `sticky-note.tsx:192-200`). Cost: lowest; the sticky's `setStickyBlocks` then merges three-way into the window's save. The `sticky-note.writers.test.tsx` 127-135 string assertions must be kept or re-aimed (re-aiming is a named change). Covers `pagehide` only, not unmount, and not the reverse order if a third writer is added.
3. **`NoteEditor.flush` re-reads the store and merges before it saves** (client-side `mergeBlocks`, the window's own logic moved into the editor). Cost: duplicates `NotesWindow`'s reconcile in the editor, so the notes page editor gains it too; the merge test is reusable as is; needs a mounted test.

Choice: 1. It closes the overwrite for every stale editor (pagehide, unmount, timer, notes page) at the store boundary where the missing information (the base) is lost; 2 is the cheapest interim.

### For M1b (the merge-seed loop)

1. **Advance the base and ignore the store change a seed save caused** (`base.current = seed` before `save`, a ref carrying the seed's identity so the reconcile effect treats that change as `same`). Cost: a few lines in `notes-window.tsx:346-373`; the pure-function tests do not exercise it, so a mounted test (React plus the real store) is required.
2. **Bound the merge**: refuse a `mergeText`/`mergeBlocks` result longer than the sum of its inputs' growth over the base (or make same-position inserts idempotent when one tail contains the other). Cost: `notes.writers.test.ts` and `notes-window.merge.test.tsx` "keeps both when each added words at the end of the same block" must still hold; a guard that is a symptom filter, not a cause fix.
3. **Never reconcile inside a store notification**: run the reconcile on a scheduler task. Cost: changes the order the existing flush-then-seed comment depends on (`notes-window.tsx:365-366`).

Choice: 1, with 2 as a backstop only if the owner wants a hard cap.

### For M2 and M3 (sticky remount with `autoFocus`)

1. **The follow remount autofocuses only when the sticky already held focus, and keeps the caret** (`autoFocus={editorVersion === 0}`; on a re-key restore focus only if `document.activeElement` was inside the sticky, in a `useLayoutEffect` so there is no frame without focus). Cost: `note-editor.tsx:838-841` is shared (window, notes page, sticky); `sticky-note.test.tsx:79` asserts `autoFocus` on the legacy `StickyWindowView` field only; no mounted test covers either.
2. **Update the editor's content in place instead of remounting** (a controlled external-value path in `NoteEditor`). Cost: the largest; the editor keeps its document in refs and `initial` is read once (`note-editor.tsx:673-684`).
3. **Hold the follow while the sticky was typed in within N ms** (or while it has focus) and apply it when idle. Cost: small, but it lets the two surfaces differ for longer, which the three-way write already tolerates; `stickyFollowText` (pure, `sticky-note.test.tsx:699-711`) is the natural place and its tests would gain cases.

Choice: 1 for M2 (it removes the focus theft at its cause) and its layout-effect half for M3 (it closes the gap in the same commit).

## 4. Decisions asked of the manager

- A5/A8 ("a saved note keeps exactly what the reader wrote") **does not hold on the real page** for: leaving the page within 150 ms of a sticky keystroke while the window is dirty (M1: overwrite, or runaway duplication); typing in a window while a sticky is open on the same block (M2: text lands in the other surface and not at the caret); and a keystroke after a merged sticky flush (M3: dropped, possibly a shortcut). It holds, in about 45 usable trials, for every sequence that keeps both surfaces alive and gives the writers more than 150 ms.
- Recommended: rule 1 for M1a, rule 1 for M1b, rule 1 for M2/M3, and a mounted-component test for each of the six rows marked in section 1 before any fix is accepted (the pure-function suites cannot see any of them).
- Not established: what a real browser leaves persisted when it closes a tab inside the M1 window (my harness kept the page alive until the quota); the exact quiet-machine width of the M3 gap; whether the shortcut consequence of M3 occurs; that the cause of the loop's non-convergence is the ordering of `doc.current` (inferred, not mutated); cross-tab writes; the notes page (`/notes/<id>`) as a third live writer.

Evidence (scratch, not committed): per-trial JSON lines with the in-page timelines and writer stacks under `scratchpad/p12/b52/out/` and the driver under `scratchpad/p12/b52/scripts/`; the server and the uploaded-PDF directory were removed when the run ended.
