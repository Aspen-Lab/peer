## 2. The rules as built (§1h.59)

1. **`web/src/lib/figures/pdf-engine.ts`** exports `extractPdfFigures(bytes: Uint8Array, { maxPages, maxFigures, onlyPage?, label? }): Promise<{ figures: { ordinal, page, caption, kind, png: Uint8Array, box? }[]; reason: string | null }>` — the signature the brief fixed. `caption` is `""` where the helper had `null`. `onlyPage` is 1-based and must be within `maxPages`. `label` ("Figure 3", "Fig. 3", "3", "3a", any case) returns every region whose caption opens with that number (exact: "Figure 1" never takes "Figure 10"), in document order, and stops after the first page that has one; no match → no figures and a reason that names the label. `ordinal` is the index in the answer (document order for a whole-document call, the helper's own numbering; 0 for a single label). `box` is the region in points from the page's top-left before the 10 pt padding. A bad document never throws: not a PDF, encrypted, over 18,000,000 bytes, a page past the end, nothing found → `figures: []` and a reason (the helper's own text for "nothing found"). It rejects only when the engine itself will not load.
   - **Port.** The helper's rules line for line (text and image blocks, caption matching 220 pt below / 110 pt above, de-dup at 0.85, un-stretching, `cluster_drawings` at 3 pt, ≥ 120 × 120 pt and ≥ 20,000 pt², 10 pt padding, 2.8× stepped down by 0.2 to the 1.6× floor). **Two places follow PyMuPDF rather than MuPDF.js**, found by comparing with the helper's output (B's port differed there): (a) a path's box is its walked points through the matrix, a Bézier's control points included and the stroke's width not (PyMuPDF's line-art device, read in the installed source); `Path.getBounds` widens a stroke by up to its miter limit, which made B's crop of the curved synthetic chart 840 × 547 px against the helper's 812 × 504 — now 812 × 504 exactly. (b) A clip becomes pixels by MuPDF's `fz_round_rect` (outward, 0.001 slack), not `Math.round`; with it the owner's paper is **pixel-identical** to the helper on 12 of 12 (B's port: 6 of 12).
   - **Destroys.** Every `Document`, `Page`, `StructuredText`, `Pixmap`, `Device`, and also the `Buffer` it makes (so a failed open does not leave one), the `Font` MuPDF.js wraps for every character it walks, the `Path`/`StrokeState`/`ColorSpace` handed to the line-art callbacks, and each `Image` block. (`ColorSpace.DeviceRGB` is a shared singleton and is not.) MuPDF's own stderr chatter (a line per repair of a sloppy PDF) is muted with `setLog`; failures still come back as a reason.
   - **At most 2 extractions at once** in one instance: a small semaphore (`MAX_CONCURRENT_EXTRACTIONS = 2`; a slot is handed straight to the longest waiter). Between pages the engine hands the event loop back (`setImmediate`), so the limit is a real one and a request that arrives mid-extraction is served.
   - **Caps.** 18,000,000 bytes (`MAX_PDF_BYTES`, now exported from the engine and imported by `pdf-extract.ts`; **the engine enforces it itself — an upload of 18–25 MB is now refused for figures, where the helper took it; see §7.2**), `maxPages` (24 from the caller), `maxFigures` (12), 4.5 Mpx. Past the helper's 1.6× floor the helper rendered whatever size the region came to; here the ceiling holds, so a region too big for 1.6× is rendered smaller (only a page larger than a poster gets there). A drawing-count ceiling per page (12,000 distinct path boxes; more than 60,000 raw are not collected): clustering grows with the square of the count, and a page past the ceiling loses its vector analysis, not its rasters (the helper would have been killed at 25 s and lost the whole PDF).
   - **Timeout design: in-process, with a budget.** `EXTRACTION_BUDGET_MS = 25_000` (the helper's own `timeout`), counted from the call (waiting for a slot included), checked between pages and before each render; what is found by then is returned, with a reason ("stopped … after 25 s, with N figures found so far"). Measured against a `worker_thread` with `terminate()` (§6.3): the worker kills a hang outright (a `terminate()` at 300 ms ended it by 383 ms and the main process stayed at 62 → 82 MB), but costs **1.57–1.68 s on every call** against **0.31–0.39 s warm in-process** (each call instantiates the WASM again; B measured the same, +0.5–0.7 s on a page render), needs a worker file named by a computed path under `/*turbopackIgnore: true*/` and traced by hand into every function (a file outside the five I own), and `/api/figure` caches the pool for 30 minutes so a hang is a rare event. Chosen: in-process. **What it cannot do:** stop a single page that hangs inside MuPDF before the function's own `maxDuration`; the byte, page and drawing ceilings are what make that unlikely.
2. **`pdf-extract.ts`** calls the engine on bytes: `resolveHelperScript`, `runExtractor`, `execFile`, `PYTHON_BIN`, the `mkdtemp`/`writeFile`/`rm` of both temp directories, `supportedMimeType` and the helper's JSON types are gone. `extractPdfCandidatesFromPath(path, source)` keeps its contract (`readFile` → bytes → the same candidates); a new exported `extractPdfCandidatesFromBytes(bytes, source)` is what `tryPdfCandidates` calls now, so a fetched PDF no longer touches the disk at all. The data-URL mapping is the same (`data:image/png;base64,…`, `qualityHint: "high"`, `cleanDisplayText(caption)`), and `extract.ts`, `figure-binding.ts` and the report are unchanged (`extract.ts` was not touched; its imports did not change).
3. **`next.config.ts`**: `serverExternalPackages: ["mupdf"]`; the `outputFileTracingIncludes` entry for the script and its comment are removed (the new comment says why the package stays external).
4. **`/api/figure`** answers with `X-Peer-Figure-Engine: mupdf` and `Server-Timing: extract;desc="extractFigure";dur=<ms>` (the time of the `extractFigure` call) on every answer that ran the extractor, GET and POST, public and private; a 401/404 that never reached it claims no engine. The cache headers are unchanged. (A day-cached public GET replays the Server-Timing of the answer that was cached.)

## 7. For the manager

1. **Licence (the owner's, unchanged by this item).** `mupdf` is `AGPL-3.0-or-later` (Artifex dual licence, the same terms as PyMuPDF); it is now a declared dependency of `web/package.json`. `README.md:339` and `docs/PRIVATE_PDF_UPLOADS.md:150-156, 176` still say PyMuPDF's terms are unresolved; they now apply to `mupdf`. I did not touch them (not mine).
2. **A behaviour change to know.** The engine refuses a PDF over 18,000,000 bytes itself (brief rule 1). The upload route accepts 25 MB, and the helper had no byte cap of its own, so an uploaded paper of 18–25 MB now gets no figures (reason: "too large … safely"). If that is not wanted, raise `MAX_PDF_BYTES` in `pdf-engine.ts` (memory: 14.5 MB peaked at ~280 MB; a 25 MB file untested) — one constant, which `pdf-extract.ts` also reads for its fetch check.
3. **A temp file remains upstream of me.** `withUploadPdfFile` (`papers/upload-store.ts:208`), which `extract.ts:1282` uses for an upload, still writes the bucket backend's bytes to a `peer-upload-read-*` temp directory before `extractPdfCandidatesFromPath` reads them. The engine takes bytes, and `extractPdfCandidatesFromBytes` is exported, so C P9-29 (or you) can read the upload with `readUploadPdf` and skip the file; not mine (`extract.ts` only if imports change).
4. **Found in passing, not touched.** (a) Every route function that imports the upload store traces the whole web root — `upload-backend.ts:50` `resolveWebRoot(cwd = process.cwd())` is the likely cause — so `/api/figure`, the report and the figure-image route each carry `scripts/`, `supabase/migrations`, `src/**` tests and the docs: 18 MB before the engine.
