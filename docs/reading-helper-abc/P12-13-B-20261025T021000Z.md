## Finding and scope

Two producing mechanisms are confirmed, not one:

1. **Side-layout resize can overcorrect a temporary narrow column, then lose its saved anchor when browser scroll clamping arrives before the final observer callback.** The intended final reading position is legal. Suppressing only the keeper callback in a separate diagnostic browser comparator removes this original side-to-side loss; disabling native CSS scroll anchoring does not.
2. **Crossing side/one-column mode replaces the paper DOM and destroys/recreates the shell-owned keeper.** No controller spans the move, and the new controller reads the already-moved page. Paragraph IDs and text remain the same, but DOM nodes, browser text selection and question-field focus/caret do not.

The first issue can affect the final wide position; the second can move the reading point offscreen on narrowing even when returning wide happens to restore the same pixel offset. Retained cards and identical paper words do not establish reading-place retention.

## Three candidate rules and consequences

These are candidate designs for the manager's ruling, not authorized implementation.

### 1. Explicit responsive transaction with a durable logical text token — recommended

Maintain the last stable text position before reflow at a lifetime that spans ReaderLayout's two branches. A resize callback occurs after CSS may already have reflowed: do not capture the original by reading the new DOM in that callback. Use the previously maintained paragraph ID plus canonical text-node/character offset and glyph fraction; retain paragraph gap/fraction only as the no-caret fallback. Start a bounded transaction for responsive changes; observe final shell geometry/commit and re-resolve the token in the current paper DOM. Keep the original through transient layouts and browser clamps; release or replace it only for actual reader input or a completed transaction. Restore only when a measured key/mode changes, never on every render.

Give the transaction explicit user-input/cancellation semantics. Record correction-origin and possible browser clamp without swallowing a wheel/key/touch/scrollbar move. Preserve text selection endpoints and a remounted stable-ID input's focus/caret in memory, restoring only if the old node disappeared and no intervening user focus/selection replaced it; use preventScroll for focus. Do not refocus stable card editors or touch portal nodes. Keep top/foot behavior and clamp only where the requested final location is truly unreachable.

Consequence: directly covers both confirmed mechanisms and the focus/range seam, retains the useful existing keeper arithmetic, and makes transient-versus-user semantics testable. Requires careful endpoint serialization for inline markup and backward/cross-block selections; fallback must be honest when a paragraph/character no longer exists. Do not invent a neighbouring passage or persist a DOM node/user text in shared state.

Minimal product scope: `lib/reader/keep-place.ts`, `components/reader/reader-layout.tsx`, `components/reader/reader-shell.tsx`. Put the long-lived owner/ref on ReaderLayout, remove the duplicate shell-owned controller, and add a narrowly signaled layout transaction/handoff. Existing stable question IDs suffice. If a separate pure ephemeral token helper materially simplifies this, authorize that helper explicitly; no persistent store/schema is needed.

### 2. Store/commit-driven layout changes using the existing keeper

Make shell measured-width/mode changes an atomic planned operation: take the prior keeper token before committing new pane geometry, hand it across ReaderLayout's branch, then restore in a layout effect. Eliminate stale measuredWidth geometry where feasible. Give reading-scale/Fit and sidebar commits the same before/after seam, while preserving the current successful controls.

Consequence: fewer generic observers and clear causes for each correction. However fixing shell width atomically alone cannot preserve one-column reading place, selected text or remounted field focus. A resize-event DOM capture alone is already too late. This option still needs a logical token and a lifetime above the branching shell; planning every independent useSpread/usePageZoom subscription increases coupling and risks changing197's calibrated budget/Fit behavior.

Minimal product scope: the same three files; `pane-layout.ts` only if the manager explicitly authorizes changing measurement arithmetic, with its budget tests rerun. No need to change question-field, card geometry, Figure or Explain.

### 3. Persistent observer-driven bookmark, without explicit store transactions

Move one controller above both layouts; continuously maintain a logical text bookmark on real reading scroll/selection, dynamically resolve the active column and observe stable reader ancestry. Any actual layout-key/mode change starts the existing bounded600ms hold. Preserve correction provenance through subsequent clamps and restore from the same token until settling ends. Native anchoring may be suspended only for that bounded hold and then restored, never globally.

Consequence: avoids wiring every layout-changing store, and can cover narrow-to-narrow reflow too. It is the smaller conceptual extension of existing keepPlace, but correct event provenance and settling boundaries become harder to prove; an observer-only implementation that simply rereads on all scrolls reproduces today's bug. Global overflow-anchor:none or a longer timer alone are ruled out by the comparator and remount trace. No indefinite/every-render correction loop is acceptable.

Minimal product scope: keeper plus ReaderLayout/shell hook relocation; focused tests below. No CSS/policy change is justified merely by choosing this candidate.
