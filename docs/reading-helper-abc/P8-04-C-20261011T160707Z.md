## The change, per extractor path (`web/src/lib/papers/html-text.ts`)

New `sectionDrafter()` next to `shouldKeepSection`: it makes one `bucketInheritor()` and returns `(heading, text) => DraftSection | null`. For every heading it asks the inheritor first (`inherit(heading, own)`), and only then drops a heading whose text is empty. Each build makes one drafter per document and hands it every heading in document order:

- **LaTeXML (`extractLatexml`, arxiv.org/html and ar5iv).** The loop over `heads` no longer has `if (!text) continue` before the canonical; it calls the drafter with the heading and its (possibly empty) text. The abstract section, pushed before the loop, is unnumbered and untouched.
- **PMC (`extractPmc`).** Same: the loop over the section matches calls the drafter; the two `continue`s that stay are for a section with no heading element or an empty heading, which have nothing to number.
- **bioRxiv / medRxiv section blocks (`extractBiorxiv`, the `found.length > 0` branch).** Same, one drafter for the branch.
- **The heading walker (`walkHeadings`), which both `extractGeneric` and bioRxiv's no-section-blocks fallback build through.** One drafter inside the walker, so those two get the inheritance from one place, and neither return runs a second pass over the walker's output.

**`withInheritedBuckets` in each of the four returns: gone.** Reason: the build now inherits while it still sees every heading, and a second, stateless pass over only the kept sections could hide a wiring regression (it would fix some of what a broken first pass missed). It is idempotent over what the builds now produce, and each path's first test asserts exactly that (`withInheritedBuckets(doc.sections)` gives the same canonicals). It stays exported and tested; `pdf-text.ts` `normalize()` still calls it.

**`shouldKeepSection`** is judged as before, on the heading's own bucket. One choice to see: an end-matter heading (own bucket `references` / `acknowledgments`) is dropped before the inheritor and so does not enter the numbering. Had it entered, a numbered subsection under an empty "3 Acknowledgments" would have come out kept but filed `acknowledgments`; as built it reads as it did before this item (kept, own bucket). The brief says a subsection under end matter "is not the question", so I kept today's answer and pinned it with a test, which the manager can re-aim if that is ruled differently (see "For the manager" 2).

Every existing fixture gives the same answers (the 44 tests that were in the file pass unchanged; none deleted or edited).

## The tests (`html-text.test.ts`, 35 new)

`describe("an empty numbered parent — every HTML extractor")`, a table of five builders of the page the way each host writes it (LaTeXML with its `ltx_tag` spans; PMC `<section id="secN">`; bioRxiv `<div class="section">` inside `<article>`; bioRxiv with no section blocks; generic `<article>` with h2/h3), each run through `chooseHtmlExtractor` on a URL of that host. Seven tests per path:

1. **gives a subsection the bucket of a numbered parent that holds no text of its own** — "2 Results" empty + "2.1 Growth" with text, "4 Methods" empty + "4.1 Samples" with text → exactly `[2.1 Growth, results]`, `[4.1 Samples, methods]`; texts kept; ids `s0`, `s1`; the second-pass idempotence.
2. **lets a subsection that names a structural bucket keep it under an empty parent** — "2.2 Limitations" stays `limitations` beside "2.1 Growth" → `results`.
3. **reaches a grandchild through two headings that hold no text** — "2 Results", "2.1 Growth" both empty, "2.1.1 Dynamics" → `results`.
4. **leaves an unnumbered document alone** — "Results" empty, then "Growth" (`body`), "Methods" (`methods`), "Sample notes" (`body`).
5. **treats a parent with text as it always has** — "2 Results" with text, "2.1 Growth", "2.2 Method details" (its own heading says methods, the parent's `results` wins, as before).
6. **still drops end matter, and an acknowledgments subsection with it** — "3 Acknowledgments" and "3.1 Funding" with text are out.
7. **does not let end matter hand its bucket down** — "3.1 Notes" under an empty "3 Acknowledgments" is kept as `body`, as before (the choice above).

## The cache (item 3 of the brief)

**The HTML extraction has no version of its own, and nothing persists its text.** `full-text.ts` keeps a public paper's extracted document in a module-level in-memory `Map` keyed by `paperId`, `CACHE_TTL_MS` = 1 hour, per server instance; no constant, no disk, no database. `UPLOAD_CONCEPT_EXTRACTION_VERSION` keys only `uploadDocKey(...)`, the uploads' owner-scoped store (`uploadFullText`); a public HTML paper never goes through it. So the brief's third case applies: **a cached copy is re-read by expiring** — within the hour, or at once when the instance is replaced (a deploy) — and **I bumped nothing** (the upload version stays 5 for P8-03).

One layer downstream does keep a derived copy, and I report it rather than touch it: the **reading** (`PaperReading`, `version: 6`), built from those sections. It carries each body section's `canonical`, the `buckets` list, and the findings / method / caveats chosen by bucket, so for an HTML paper with an empty numbered parent its content changes with this fix. It is served by `/api/papers/[id]/reading` with `Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800` and kept in the reader's browser (`use-reading.ts`, `peer-reading-v2`, 24 h), and both gate only on `version === 6`. So a reading built before the fix stays as built for up to a day in a browser that has it; whether the host's shared cache survives a deploy I cannot tell from the code. The version's own comment says to bump it "whenever … the way any field is derived changes"; it was last bumped in P1-04, and P7-18's change to the PDF outline's buckets did not bump it either. Bumping 6 → 7 would touch `reading.ts` (the type literal and the builder), `use-reading.ts`, `reading.test.ts:298` and `reading/route.test.ts:93`, and would retire every cached reading of every paper at once. That is the manager's call (see "For the manager" 1).
