### SHOULD-FIX

**S1 — /privacy "What your questions teach Peer" says the words reach Peer's server only when signed in; they also leave in every feed, jobs and events request, signed in or not.** The sentence (`web/src/app/privacy/page.tsx:67-70`): "…it is kept in this browser and, when you are signed in, sent to Peer's server and stored against your account…". The request builders put the whole ledger in the body: `web/src/store/feed.ts:766` / `:816` (papers) and `:935` / `:950` (jobs and events); the server reads it with `cleanPreferenceLedger` (`web/src/app/api/feed/route.ts:664`), which keeps the `questions` record. Captured in Chromium with a **signed-out** reader whose ledger held question terms: the page's `POST /api/feed` body (1,707 bytes, identical in every send; my stub answered 404 and the page re-sent it 301 times in 5 s, see N11) carried `preferenceLedger` with 5 entries holding `questions` evidence — the terms in lower case, no question text, no standing-question text, no `standingQuestions` key, no paper id (the request was answered by my browser-side stub; nothing reached the server). At unit level `paperFeedRequestBody` and `opportunityRequestBody("jobs"|"events")` carry the same. Server side: nothing logs it (`console.` in the feed pipeline are three advisor / semantic lines; none prints a ledger) and the pool cache is keyed without it (`web/src/lib/feed/pipeline.ts:838-845`: the ledger is applied at read time). So the terms are not stored for a signed-out reader; the sentence is incomplete where it says they travel only with the account's sync. `page.questionterms.test.tsx` pins the PUT line and the cleaner but nothing on the request builders (C's checkpoint: "the terms DO leave the browser with the ledger when signed in" — the second path was missed).

**S2 — a key-shaped value or an address typed or pasted into a question enters the ledger whole and travels with it.** `questionTerms` (`web/src/lib/preferences/question-terms.ts:12-27`) takes `specificTerms` (`web/src/lib/papers/reading-map.ts:334`) over `tokenize` (`web/src/lib/scoring/tokenize.ts:14`), which keeps every token of 3 or more characters with no upper bound and no shape check. Unit probe: two settled questions, one carrying a 40-character key-shaped token and one an address, gave 9 terms with a **40-character label** (the key body, lower-cased) and 4 address fragments in the ledger; the key body is in `remoteProfilePayload(...)` (so in the account row and in every feed body, see S1). The stored credential fields themselves are out of the payload (`feedAiApiKey` / `jevApiKey` value absent, checked). Graded SHOULD-FIX on the privacy-first rule: before P5-02 a pasted secret stayed in this browser until a deep report; now a derived copy persists against the account. The question text already goes to the reader's own model provider by design, so this is a grading call the manager may lower to NOTE.

**S3 — the terms of a question deleted with the × button stay in the ledger (and the sync) until the box is next left.** Browser, 1440 light: settle one question (5 terms held), press × on its line, click elsewhere, wait 2.5 s → **5 terms remain**; reload / leave the page → 5; return to the paper, focus the box and leave it → 0. Clearing the text with the keyboard (Ctrl+A, Backspace) and leaving → 0. Cause lines: the × handler (`web/src/components/reader/question-field.tsx:409-416`) calls `commit`, which stops the idle wait and never re-arms it; the focused button is removed, so no blur reaches the box; the unmount cleanup returns when `idle.current === null` (`:304`). C's checkpoint says "a removed or edited question's terms leave at the next settle"; that settle can be many visits away, and the Profile summary (by design, see below) shows nothing the reader could use to find them. No /privacy sentence claims removal takes them out, so this is not a false sentence; it is a declared-intent control that does not reach the derived words.

**S4 — "so one question changes nothing you can see" is true for one term, not for a question.** The weight is a fifth of a like per term (0.2 → 0.0128 boost against a like's 0.0531, specificity 0.75), but `scorePreferenceMatch` sums the matching terms (`web/src/lib/preferences/ledger.ts:789`, capped only at 0.18, `:824`) and question terms match free text in a candidate's title, abstract and tags (`:769`), where a like needs a tag. Measured on invented candidates (no document-frequency, so specificity 0.75; with real IDF up to ×1.33): a 5-term question gives a candidate carrying all five words **0.0642 — above one like (0.0531)**; 4 words give 0.0514; on a fixture where a like flips the top result (gap 0.0478), the one-term question does not flip it (C's test, which only has one term) and the 5-term question **does**. Five settled questions of one paper gave 21 terms; a candidate carrying them all reaches the 0.18 cap, 3.4 likes. The constant at 0.9 and at 0.3 both turn C's two guards red (below), so the per-term number is pinned; the aggregate is not. This is the product rule "never overreact to one signal" read against the copy's own claim; whether declared intent should count in full for a candidate that matches the question is the manager's call.

**S5 — a ticked question that is then edited can be let back in by ticking a different line, until the next settle.** Browser, run twice (no key; key + Deep report): settle two questions; tick question 2 (its 4 own terms leave, ledger 10 → 5); edit question 2; tick question 1's box → the ledger now holds the **old** text of question 2 (3 of its words back) and none of question 1's. Cause: `syncQuestionTerms` reads `notForRecommendations(entry)` = live marks + marks as at the last settle (`web/src/store/reading-questions.ts:53-55`); a mark made after the last settle exists only in `notForRecs`, and an edit moves it to the new text, so the settled old text is no longer named (`question-field.tsx:321-325` calls the sync). It closes at the next settle (box left and 1.5 s idle: 0 terms, measured) and is not reached without ticking a second box; a tab closed before that settle keeps the wrong state. C's test covers the case with a settle in between (my A4 mutation turns it red); this order is not covered.

**S6 — the guard that keeps other signals when a question's terms are removed is unpinned on two of its three clauses.** `removeQuestionTermSignal` deletes an entry only when `!entry.positive && !entry.negative && !entry.facetPositive && !uploads` (`web/src/lib/preferences/ledger.ts:422`). Dropping the **uploads** clause (A1) or the **dislike** clause (A1b) survives the 1,417 tests of the touched directories and the **whole suite (360 files, 7374 tests)**; a behavioural probe on the mutated file shows each really deletes the entry (an upload-only entry and a dislike-only entry that also held question evidence), and on the real file both survive removal. The code is right; the pin is missing (the "takes out exactly" test holds a like on the shared word, so it never reaches the other clauses). Guard-path survivor, tests only, graded like P4-05's S1.
