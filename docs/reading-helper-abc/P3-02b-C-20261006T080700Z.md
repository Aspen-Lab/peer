## What was built

**The rename.** `git mv` of `explain-popover.tsx` and its two tests to `explain-box.tsx`, `explain-box.test.tsx`, `explain-box.flow.test.tsx`; `ExplainPopover` is `ExplainBox`, every other P3-02 export keeps its name; the page's import follows. Git sees the two test renames at 97 % and 98 % and the component at 51 % (see choice 4: the component grew to twice its size, so its new pure code lives in `explain-thread.ts` to stay above git's 50 % rename threshold — measured with `git diff --cached -M50% --summary`).

**Server (`lib/papers/explain.ts`, the route).**
- `readThread(value)`: an array of `{ role: "reader" | "peer", text }`, each text whitespace-collapsed and clipped to 400 characters, at most 17 messages; anything malformed (not an array, not objects, another role, a text that is not words) is **no thread at all**, never a partial one. It also reports the reader's message count, so more than eight is `400 { error: "thread_full" }`.
- `buildExplainReplyPrompt({ paper, map, located, passage, thread })`: P3-02's context (one shared `promptContext`, so the first message's prompt is byte-for-byte what it was), then the thread in order (each message labelled by `role`; the last 17, each ≤400), then `lastReaderMessage` naming the one to answer; rules: ≤3 sentences in plain words, `evidence` copied character-for-character from `context.before/paragraph/after` only when the reply rests on the paper (else omitted), no web, no advice, no verdict. Nothing about the reader is a parameter.
- `sanitizeExplainReply` (≤3 sentences, ≤560 characters, the quote ≤400, a place, page, section or `peer` claim from the model dropped); `verifyExplainReply` (the whole quote through `locateSection`, via a shared `placeQuote` that `verifyExplainAnswer` now uses too; found → `evidenceWhere`, `sectionId`, `page` from the document; not found or absent → `peer: true`). `ExplainReplyTurn`, `ExplainMessage`, `ExplainReply` types; `ExplainResult` grows `{ turn, cached }` and `{ error: "thread_full" }`.
- Route: the thread is read right after the passage check (before any owner or entitlement work, like the other 400s): `thread_full` for >8 reader messages; `400 { error: "thread must end with the reader's message" }` for a non-empty thread that ends with Peer. With a thread: reply prompt, `generateJsonText({ maxTokens: 400, tier: "small" })`, sanitise, verify, count on the same `explain_turns:<user>:<UTC day>` counter, ONE debug line (the same fields plus `thread: <message count>`; the first answer's line has no `thread` key), re-check of the upload's revision (410, nothing cached), cache under `explainCacheKey(docHash, passage, thread texts in order)`, answer `{ turn, cached: false }`; a hit answers `{ turn, cached: true }` with no call and no count. Nothing per-reader is in the memory. One memory (≤64, 1 h) holds both kinds of verified turn.

**Store (`store/explain-threads.ts`).** `ExplainTurn` gains `evidence?`, `evidenceWhere?`, `sectionId?`, `page?`, `peer?`; `MAX_EXPLAIN_TURNS = 8`, `MAX_EXPLAIN_MESSAGE_CHARS = 400`; `threadFull(thread | turns)`; `addTurns(paperId, hash, turns, at?)` appends a reader message and Peer's reply together and stops at the first reader message past the eighth (nothing beyond the cap is stored; an unanswered passage or no turns changes nothing; `at` is stamped so the newest conversation outlives the oldest); `resetThread(paperId, hash)` empties `turns` and keeps the first answer.

**The box (`explain-box.tsx`, `explain-thread.ts`).** Under the first answer, each reader message under the label-face line `EXPLAIN.you`, each Peer reply under `EXPLAIN.peer` (the prose in the reading face; a verified `evidence` as an `EvidenceQuote` with section link and page; otherwise `PEERS_READING` beside the label and no quote); then a control row with a one-row `textarea` (grows to three; `placeholder` and `aria-label` `EXPLAIN.placeholder`; `maxLength` 400) and a `Send` button; Enter sends, Shift+Enter is a newline, an IME composition never sends (`keyToSend({ key, shiftKey, isComposing })`, with keyCode 229 read as composing); `EXPLAIN.thinking` under the thread and the input disabled while a reply is pending; a failed reply shows `EXPLAIN.unavailable` under the thread and keeps the typed words; at eight reader messages the input and Send are disabled under `EXPLAIN.threadFull`, and opening the passage again drops the full thread through `onResetThread` (the page's `resetThread`) and opens with the first answer and an empty thread. The input exists only with `canAsk`, a first answer and an `onReply`. The send is the only request (`onReply(target, thread, message)`, `thread` = the first answer as the first `peer` message, then the turns); the reply joins the session's thread, with the reader's message, only once it arrives (the page persists the pair with `addTurns`). A reply that arrives for a passage the reader has left is ignored. After a reply the input is handed back to a reader who sent from it.

**Layout.** `placePanel(bounds, viewport, column)` (pure, tested): ≥1024 wide with ≥376 px between the column's right edge and the window's: `side` — 360 wide, 16 px right of the column, top at the selection's top clamped inside the window, as tall as the room under it (min 280); below 640: `sheet` — full width, on the bottom edge, ≤60 % of the height; everywhere else P3-02's `placeCard`, unchanged. The page passes `column={measureBodyColumn}` (a measure function in `paper-body.tsx` that reads `#paper-body`'s bounding box on every render, scroll and resize). The card is the one thing that scrolls; its passage-and-Close header is `sticky` at the top and the control row `sticky` at the foot (offset by the card's padding). On a phone, `revealShift` (pure) scrolls the page just far enough that the selection ends above the sheet as it opens and the thread grows, never so far that the selection's top leaves the window.

**`e`.** `ReaderAction` gains `"explain"`; `PAPER_KEYS` gains `{ keys: ["e"], action: "explain", label: "Explain the selected passage", short: "explain" }` before `back`; `paperKeysFor` keeps it on every page; `readerHelpItems` and `KeyLegend` pick it up from the table (the legend shows `E EXPLAIN`). The box exposes its `open` through an **`openRef`** prop (a `{ current }` the box fills in an effect and clears on unmount); the page registers `explain: openExplain` in its `actions` block (with the body, as `read` and `ask` are) and `openExplain` calls `explainOpen.current?.()`. `open` does what the button's click does on the current selection: the Tier 0-only box without a key; nothing at all with no term and no key, and nothing with no selection; with the box already open it moves to the input.

**Copy.** `EXPLAIN` gains `you` "You", `peer` "Peer", `placeholder` "Ask about this passage…", `send` "Send", `thinking` "Peer is thinking…", `threadFull` "This thread is full. Select the passage again to start a new one." The existing copy grep (`route-tint.test.tsx`) already scans every `EXPLAIN` value; a new test also pins the six strings and the banned-word rule.

## Choices beyond the brief (small readings, consistent with the rulings)

1. **At 1440 the rule gives P3-02's placement, not the panel** (measured above); the brief's look asked for the panel "beside the text column" at 1440, which this layout cannot give under a ≥376 px rule. I kept the rule, looked at 1920 for the beside-the-text panel, and report it.
2. **`openRef`, not an imperative `open()`** (the brief asked me to say which). The page calls `explainOpen.current?.()`.
3. **`e` with the box already open goes to the input.** The brief has `e` open the box; once it is open, a keyboard reader otherwise has no short way to the input (the box is last in the page's tab order), and focusing the input on open would have dropped the selection's highlight. So the second `e` focuses the input.
4. **A new module, `components/reader/explain-thread.ts`**, holds `ReplyResult`, `keyToSend`, `firstAnswerMessage`, `asTurn` and `requestReply` (pure, no JSX). Reason: with everything in `explain-box.tsx` its similarity to the old file was 43 % and git would not follow the rename; at 51 % it does. The page imports `requestReply` from the new module; nothing else changed for it.
5. **The card is the one thing that scrolls, with a sticky header and a sticky control row** (offset by the card's own padding, `-top-4` / `-bottom-4`) instead of splitting the card into three flex children: it keeps the old blocks' lines unchanged (the rename above) and lays out the same.
6. **The passage's quote and Close are pinned at the top of the card** so the passage stays in view as the thread scrolls (§1h.3 has the passage "at the top").
7. **A thread of more than 17 messages is no thread** (unless it has more than eight reader messages, which is `thread_full`); an empty-text message is malformed; whitespace in every message is collapsed (the reader's own newline is kept in what the box shows).
8. **`onReply` is optional** and the box has no thread without it (so the existing box tests, which pass none, are untouched). The page always passes it.
9. **The box keeps its own copy of the session's turns** and the page persists the pair with `addTurns`: a click in the input collapses the page's selection, which would otherwise drop the page's per-selection lookup of the thread.
10. **`column` is a measure function, not a rectangle** (`column?: () => { right } | null`, the page passes `measureBodyColumn`): it is read on every render, and the box already re-renders on scroll and resize, so it is never stale; `measureBodyColumn` is one exported function added to `paper-body.tsx` (the body's markup is unchanged), with its own test file.
11. **A phone's sheet scrolls the page** (`revealShift`) so the selection stays above it "where it can"; the brief left how open.
12. **The input is handed back to a reader who sent from it** after the reply (a disabled input drops focus), and it grows to three lines by script (not `field-sizing`).
13. **Commit trailers.** The task says to end the message with the two Fable lines; §1c says the attribution follows the committing agent's model, and my harness mandates `Claude Sonnet 5.5`. As in P3-02, the Sonnet line comes first, then the two Fable lines, so the last two lines are exactly the brief's.
