## 1. The behaviour as built

From **1024 px**, for a reader with a key (`canAsk`), on a paper with a readable body (`reading.body` not empty — the Paper digestion tab exists):

- **Present from the start.** `ExplainBox` renders the window from its first render, with no selection: the same `ExplainCard` in its new `empty` state, as a dock — right edge, 360 wide, **top 48** (`DOCK_TOP_PX`), height its content (111 px measured), `maxHeight = height − 48 − 28`. `reserveDock` runs at **mount** (the layout effect keyed on `docked`, which is now `(open || standing) && width ≥ 1024`), so the page keeps its 376 px clear from the first paint. **Empty state** = the header (the title "Explain this?" in the label face, `text-heading`, where the quote of the passage goes, and Close) and **one line** of label-face copy, `EXPLAIN.empty` = "Select a passage in the paper, then press Explain this? or e." (`copy.ts`, the one new string). No input, no quote, no "You" / "Peer", no search toggle, no word about a key, a plan or a price (pinned by a test on the string). The dialog's accessible name is `EXPLAIN.ask` (the existing `EXPLAIN.card` — "Explanation of the selected passage" — would be wrong with nothing selected); the element carries `data-explain-empty`.
- **The rule in one place.** `emptyDockStands({ canAsk, hasBody, hidden, width })` in `explain-dock.ts`; the box adds "and no passage is open" (`standing`). `waiting` is the same without the width: with it, and nothing open, the box watches a **resize alone** (one new effect, no scroll listener), so the width is given back below 1024 and taken again from there — before this item nothing watched the window unless a selection existed.
- **Without a key: unchanged.** `canAsk` false → `standing` false: nothing renders at mount, nothing is reserved, no Escape is swallowed. The Tier 0 definition opens on a defined-term selection as before and stays open per P8-02 (measured at 1280 × 800: no panel at load, container left 104 as ever; the "dry spell" selection opens the Tier 0 window at the paragraph's top with `--explain-dock` set then, Escape releases it).
- **Below 1024 and a phone: unchanged.** Nothing renders at mount at 1023, 800, 640, 390 (a test per width); the card and the sheet open on the press only, the new-selection-closes rule is as it was.
- **Close and Escape hide it for the page visit.** One new `hidden` state in the box (component state, never stored — a test stubs `localStorage` / `sessionStorage` and asserts neither is touched; the box is keyed by `paper.id`, so a reload, and the next paper, show the empty panel again). Escape (document capture, `preventDefault` + `stopPropagation`, as for an open window) and Close both do `setSession(null); setHidden(true)`, for the empty state and for a window holding a passage alike; the properties are removed, the keydown / pointerdown / resize listeners go (only a resize watcher stays while it could stand again — and not once hidden). A later selection's button (or `e`) re-opens it **with that passage** (`start()` sets the session; `hidden` stays true and is irrelevant while a session is open) and reserves the width again.
- **The first selection.** The button appears beside the words, outside the dock's 376 px (P8-02's `placeButton` rule, now also with the empty state standing: measured x 776 … 891.7 at 1280, the window at 920). `start()` replaces the empty state **in place**: the same `ExplainCard` element at the same place in the tree, `docked` true before and after, so the layout effect does not run again — `removeProperty` is never called, `scrollBy` never called, and in Chromium the very DOM node is the one that holds the passage afterwards (tagged before the click, found after). Its top then goes from 48 to the paragraph's (P8-02's rule, unchanged). `e` with nothing selected and the empty state showing does nothing (`openBox` only focuses an input when `open`; a test plants an input and asserts `focus` is never called; measured: no request, no focus, same top). `e` with a selection explains it, in place.
- **Tabs.** The tab state is the page's (`useReaderTab`) and **not reachable from the box**; the box is mounted outside the tab content (`page.explain.test.ts` pins it: once, keyed by the paper, outside the zoomed container) and a tab switch reaches it only through the page's `clearExplain` (selection → null). Tested at that seam: with the empty state, a selection and then null leaves it standing; with a passage explained, a null target leaves the passage, the thread's turns, the draft and the top as they were, `removeProperty` never called. In Chromium: Summary then Paper digestion with a passage explained — the window and its passage stayed, same top, `--explain-dock` never changed (§4).
- **Comments** in `explain-box.tsx` (header: the window is present from the start with a key; `ExplainCard`'s `empty` doc; the box's state, effects and the layout effect's `docked`), `explain-dock.ts` (header and `emptyDockStands`), `copy.ts`. `page.tsx`, `paper-body.tsx`, `explain-thread.ts` untouched.

## 7. For the manager

1. **Escape now means "hide the panel" first, for every reader with a key and a body, from 1024 px** — the brief's item 3, with one consequence worth the owner's eye. The box's Escape handler is document-capture with `stopPropagation` (as it always was while a window was open). With the panel always there it pre-empts, on the first press of a visit: the page's own Escape = "back to the briefing" (and its help-sheet close and "blur the focused field" steps, `components/keyboard.tsx`, window bubble); the React `onKeyDown` Escape handlers of the notes editor (`note-editor.tsx` title input and menus, `notes-rail.tsx`), which `stopPropagation` themselves; and it **also runs alongside** the figure lightbox's and the term-highlight's own capture handlers (`figure-lightbox.tsx`, `terms-strip.tsx`: they register later on the same node, so `stopPropagation` does not stop them): Escape closing a lightbox, or clearing a term highlight, also hides the panel. All read from the code; the page's "back" is the one I would call the owner's: the second Escape goes back. **Not browser-verified except Escape on the empty state and on a window.** A small follow-up C item would make the *empty* state yield (leave the key alone) when the event's target is a typing field or another dialog / menu is open; I did not build it — the brief says Escape hides it and a yield is a rule the owner has not seen. It would not touch an open window's behaviour.
2. **"From the body's first paint" holds where the auth outcome is known at mount.** `canAsk` is `providerConfigured = aiAvailability(profile, authOutcome) !== "none"`, and `byok` needs `authOutcome` to be `"signed-in"` or `"unconfigured"` (`lib/feed/ai-tier.ts`); `useSyncGate` starts at `"unknown"` (`profile-sync.tsx`). Here (no Supabase) it is `unconfigured` at once and the window was in the same paint as the body (§4). On a deployment with Supabase the key holder's window — and the 376 px reserve, so a reflow — appears when the sign-in check resolves, a round trip after the first paint; a signed-out reader with a stored key gets none (as `canAsk` says). `page.tsx` is not in this item's files; if the owner wants it at the very first paint, the page would hand the box `canAsk || (key held and outcome unknown)` — a page change and a decision. Not measured against a configured Supabase.
