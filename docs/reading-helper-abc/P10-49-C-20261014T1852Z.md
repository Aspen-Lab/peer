## The rules

1. **One post per paper, none for a paper already read.** `markRead` on an id in `readItems` changes nothing and posts nothing. The sync design (`feed.ts` top comments, `lib/feed/sync-status.ts`) was read first: a repeated `markRead` was in fact a retry path (the existing test "the SAME item's failed save and failed read are tracked, and cleared, independently" re-sends it after a 500). The retry is kept: while the item's `read:<id>` key is pending in `useFeedSyncStatus.pendingKeys` (the key `cloudMarkRead` sets on failure and clears on success, mirrored in `pendingPushByOwner`), a repeated call posts; once a post lands and clears the key it stops. The outbox retry (`retryPendingPushes`) and the sign-in batch call `cloudMarkRead` directly and are untouched. A signed-out reader never has a pending key, so a repeat posts nothing for them either.
2. **The observer does not re-arm for a paper already decided.** The observer is now the exported `watchForDecision(el, decide, alreadyDecided)` in `page.tsx`; the effect hands it `() => Boolean(useFeedStore.getState().readItems[paper.id])` (and `paper.id` joins the effect's list). Attaching again when the reading arrives stays; for a read paper it watches nothing. A paper un-read is not decided, so the next attach watches it again, as before. The page cannot be mounted in this suite (no jsdom), so the test is on the exported function, headless, with a fake IntersectionObserver and clock against the real store, plus a source check of the one join (`page.decided.test.ts`).
3. **Nothing else changes.** Read stays "decided"; the first read's day, the library entry, undo (`markUnread` then `markRead` posts again, measured above: 1 DELETE then 1 POST) and Tier 0 are as they were (tests below).
