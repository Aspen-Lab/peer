## The rules

1. Every wait in `drive` is a condition (`requestsEnded`, `requestHeld`, `actAndSettle`, `waitFor`), polled on real timers, with a 20 s ceiling. A wait that runs the ceiling out ends the run, unmounts the page and fails the test naming what it waited for. No wait is a number of milliseconds or of ticks. `vi.setConfig({ testTimeout: 60 s })` keeps the runner's 5 s from cutting a slow machine off before the ceiling speaks.
2. The stubs send each event only after the page has drawn the one before (`drawn`), instead of sleeping between events. The order of events each test asserts is the order they are drawn in.
3. A request held in flight is held until the test lets it go (`staged(stages, release)`, `firstThenQuestion(release)`), not for a number of milliseconds. Where the test needs the request to stand until the page is let go, `release` is never true and the unmount's abort ends it.
4. The deadline test keeps its `setTimeout` fake. The fake no longer fires after a fixed 60 ms: it fires the deadline once the page has drawn the stage the deadline cuts short.
5. The JSON ask (the stream broke) is held until the page has drawn the line that says it was made (`net.jsonPaced`), not for 60 ms.
6. Streams are counted when they end (`counted`), and every test's `afterEach` waits for its requests to wind down, so none outlives its test and decrements the next test's `net.open`.

`actAndSettle` takes a change up the way the page does: the render that carries it, the effects of that render, the render of what they set (`history.length >= mark + 2`). Negative assertions ("no `Reading the paper`", "nothing names a new request") are unchanged and run over the whole `history`, which records every render.
