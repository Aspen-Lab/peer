### Path and timing

`takeStickyNote` ensures a paper reading note and appends a numbered anchored header plus blocks. StickyWindow's transient NoteEditor emits structured blocks through `onDoc`; the writer captures its last synchronized base, holds the last pushed value, waits 150 ms, then calls `setStickyBlocks`, which merges by block ID against the current span. While pending, it does not replace its local content with external store updates; when not pending it synchronizes and restarts the transient editor. It flushes on becoming inactive, Save, close/Escape and unmount; Save then marks the header saved, Delete cancels and removes the span. Page leave calls registered writers then removes empty unsaved stickies. Escape routes to close: close preserves nonempty content, removes empty unsaved content, and does not mark it saved.

The aggregate NotesWindow mounts ordinary NoteEditor with a local `docRef`; edits schedule 500 ms, pagehide and unmount flush dirty data. The store's `save` replaces the passed whole blocks array, preserving explicit group/empty/deleted/saved protections, but has no base argument. NotesWindow watches stored blocks and compares its base, its last `onDoc` snapshot, and store: same/keep/restart/merge. For a merge, it changes the editor key, old editor unmounts and flushes, then the parent effect stores the computed seed. `mergeBlocks` uses stable IDs and calls `mergeText(..., "theirs")`, so overlapping rewrites choose the outside/stored value, while `setStickyBlocks` uses `mergeText` default `mine`, so a sticky write arriving last wins overlap. This is write/effect order, not a captured user-action timestamp. `mergeText` recognizes one contiguous changed span per side, combines separated changes and same-position insertions, and resolves overlaps by that precedence; text/structure semantics cannot be inferred generally from such a heuristic.

Other producers include notes page NoteEditor, notes rail add/delete/title, highlight single/group creation, colour/remove/restore, anchor repair, and `setStickyText` (existing callers/tests); identity-based guards matter for all. `persist` stores notes under `peer-notes`, version 2, with explicit hydration in `store-hydrator`; in-memory deleted/empty sets are not persisted. NotesWindow exports its local `doc.current` merged with current note via plain text, Markdown, Word HTML or print/PDF; NoteEditor exports its own doc as copy/Markdown/BibTeX; notes rail exports the stored note as Markdown. These can differ while either editor has pending state. Reload/export behavior was not executed in this Node probe.

### Controlled sequence matrix

All outcomes below are for invented inputs, exact release functions, and supplied ordering; counts are 11 probes, not UI tests. Base means a common stored version; S is sticky and A aggregate, both targeting the same block unless specified.

1. A dirty overlap; S writes; reconcile(base,A,S) returns merge; simulate old A unmount flush then seed save: final S. This disproves a blanket claim that the aggregate always overwrites a newer sticky when the reconciliation sequence completes.
2. S writes; direct stale A whole-block `save` follows without executing reconciliation: final A. This demonstrates a possible overwrite at the store boundary, not that the page actually reaches it.
3. A saves; S writes overlapping replacement with shared base: final S. Same result whether S's input was prepared before or after A's save, because the store receives no user-action ordering.
4. S pending input is pushed first; A's overlapping save is called later; S flushes last: final S. This is a concrete counterexample to last *reader action* wins, although actual focus/flush ordering remains unmeasured.
5. A saves a separate edit and S flushes a disjoint edit of the same base block: both edits remain in this input.
6. S writes while A is clean: reconcile returns restart on stored S.
7. S delete then stale A whole save: deleted span stays absent due to in-memory deletion set.
8. S pending, cancel, delete, flush: deleted span stays absent.
9. S pending, flush, Save: pending content survives and header is marked saved (content assertion executed; marker follows source path).
10. Update same-note S then stale A save while a separately identified foreign note exists: foreign note is byte-equivalent to its prior store object in this single probe. It is not evidence about every cross-note path.
11. Real timer observation: zero writes at 80 ms, one at 200 ms after a single push. This bounded observation is consistent with 150 ms, not a clock-precision guarantee.

Escape/close, unmount, pagehide and reload are traced above but not executed as mounted-component sequences. The function simulation of unmount flush then seed save does not demonstrate React scheduling. Browser restart reinitializes in-memory deletion sets and rehydrates stored notes; no claim is made about stale editors across tabs or interrupted saves. The available locked toolchain has no jsdom, happy-dom or react-test-renderer; adding one or using an undocumented browser harness was prohibited. A real-page walk remains necessary to establish whether the observed hypothesis occurs, especially before/after a dirty editor unmount, overlapping edits, pagehide, export and reload.

### Three candidate general rules for manager decision, not recommendations or acceptance

1. **One per-note action stream.** Assign order at reader actions, serialize edits and deletes, derive each view from the authoritative document. Cost: structural operations, selection/caret, undo and transient editors need coherent operations; multiple tabs need an explicit boundary. Hard case: older pending sticky action vs newer aggregate action, plus concurrent split/merge and Delete. An arrival-time queue alone fails the older-pending case.
2. **Versioned three-way save with explicit conflict.** Each writer carries a base revision and changes; merge only defensible independent edits, detect overlap and preserve both versions for the reader to resolve. Cost: revisioning and a clear conflict UI, including Save/Delete/reload handling. Hard case: repeated text, two inserts at same offset, formatting and nested list restructuring; character overlap or a finite example list cannot establish intent. Delete-vs-edit needs an explicit policy and must not silently resurrect.
3. **Single active editor for a note.** Before granting the other surface ownership, flush/synchronize or hold the other draft without allowing silent overwrite. Cost: changes simultaneous workflow and may interrupt focus; pagehide/unmount during transfer and a second tab remain hard cases. A failed flush cannot be called a successful transfer.

For any rule, when a conflict cannot be safely merged, preserve both drafts durably and make the unresolved choice visible; do not silently assert one is correct. Relevant regression coverage should include both action orders and both debounce orders, overlapping and disjoint content, repeated text/Unicode/marks, insert/delete/split/list reorder, pending Save/Delete/Escape, clean/dirty unmount/pagehide/reload, foreign-note isolation, and each export from both pending and settled states. Tests must cover real mounted behavior as well as store functions; current Node probes do not close that gate. No production patch or acceptance ruling is made here.
