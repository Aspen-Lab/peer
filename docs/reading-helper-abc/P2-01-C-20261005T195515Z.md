## What changed

### `web/src/lib/papers/deep-report.ts`

**Pass 1 input (§1g.1).** `bodySections(doc)` gives every non-abstract section in document order as `{ id, heading, text }`.
- The id is `section.id ?? s<index>`, the same rule as `withSectionIds` and the reading map.
- A section with empty text is skipped.
- The old `{ canonical: text }` buckets (`sectionsByCanonical`, `nonAbstractSections`) are gone, and so is their abstract-as-introduction fallback. The abstract still reaches Pass 2 as `paper.abstract`.

**Pass 1 output.**
- The schema asks for `[{ text, sectionId }]` in each of the four lists, and the rules gain "`sectionId` is the `id` of the section the sentence was copied from".
- `signalItems` parses both the old bare-string form and `{ text, sectionId }`. A `sectionId` that is not one of the document's body section ids is dropped and the sentence kept. The old ≥ 12-character, 6-item and 360-character clamps are unchanged.
- `CompressedSignal` items are `SignalItem { text; sectionId? }` (exported type).

**Clipping (§1g.2).** `fitTexts(texts, build, size, budget)` rebuilds the finished prompt from cut body units, and the schema, rules and questions are appended whole.
- When the whole prompt is over budget, every unit longer than a common cap is cut to that cap, from its start. The cap is the largest that fits, found by binary search on the real serialised size. This is water-filling: the longest are cut first and furthest, and short sections are untouched.
- The old `prompt.slice(0, MAX)` calls in `runPass1` and `runPass2` are removed.
- Per pass:

| Pass | Body units | Budget |
|---|---|---|
| Pass 1 | sections | whole prompt ≤ `PASS1_MAX_INPUT_CHARS` (400 000) |
| Pass 2, short path | sections | whole prompt ≤ `PASS2_MAX_INPUT_CHARS` (24 000) |
| Pass 2, signal path | Pass 1's sentences | whole prompt ≤ 24 000 |
| Pass 1q | sections | serialised sections ≤ 60 000 |

- If even an empty body is over budget, the prompt goes out with an empty body rather than a cut schema.

**Pass 1q, `runQuestionPass` (§1g.1).** It runs only when at least one question survives the defensive cap.
- **Input.** The sorted, de-duplicated questions, plus the sections the Tier 0 route marks `read` or `skim` for any question. The route is `routeByQuestions(readingMapOf(rendered), rendered, questions)` with `rendered = readableSections(doc)`; this is exactly `buildReadingMap(doc)`, built from one split. When nothing is marked, every section goes. The sections are clipped to 60 000 serialised characters.
- **Call.** Small tier, `maxTokens: 3000`.
- **Output.** `questionRelevant: { [index]: [{ text, sectionId }] }`, keyed by the index in the sorted list. Each sentence is verified against the document with `locateSection`, which uses the same forgiving verbatim match as `evidenceSupported` and tries the model's id first:
  - a sentence no section holds is dropped and counted;
  - a wrong id is corrected to the section that does hold the sentence;
  - a repeated sentence is kept once;
  - at most 8 per question; sentences are clipped to 360 characters after verification;
  - an index outside the question list is ignored.
- **Result.** Mapped back to the request's own question order, and only questions with at least one sentence get a key.
- **Failures.** Pass 1q never throws. A failure or a non-JSON answer leaves `{}` and is not cached.

**Caches (§1g.4).** Two in-process `Map`s, each with a 1-hour TTL and at most 32 entries; the oldest entry is evicted first.

| Cache | Key | Value |
|---|---|---|
| `PASS1_CACHE` | `docHash` = sha256 of `JSON.stringify(doc)` | Pass 1's sentences only |
| `PASS1Q_CACHE` | `docHash` + `"|"` + sha256 of the sorted questions joined by `"\n"` | sentences in sorted order, no question text |

- A non-JSON answer is not cached in either.
- `docHash` is computed only when Pass 1 or Pass 1q will run.

**`generateDeepReport({ …, questions? })`.**
- Defensive cap on the questions: trimmed, empties dropped, the first 5 kept, each cut to 200 characters.
- Pass 1 and Pass 1q run side by side (`Promise.all`); they are independent.
- When questions exist, Pass 2's prompt gains `readerQuestions` (the request's order) and `questionRelevant` (by request index), placed before `outputSchema` and `rules`. There is no schema change; that is P2-02.

**Logs.**
- The Pass 1q drop count is logged as "`<paper.id>`: question pass dropped N sentence(s) without verbatim support".
- A Pass 1q failure logs only the error's `name`.
- The catch-all "generation failed" line logs only the error's `name` when questions exist; without questions it logs as before.
- No log line carries a question.

## Choices beyond the brief

1. **Pass 2 gets the ids.** Signal items go to Pass 2 as `{ text, sectionId? }` (`{ text }` when the id was unknown). An outline `body.sections: [{ id, heading }]` sits beside them, so an id names a part of the paper; P2-02's `readNext` and answers will need that. On the short path, Pass 2's `body` is now the section list `[{ id, heading, text }]` instead of the `{ canonical: text }` map.
2. **Pass 1q runs for short papers too.** It runs whenever questions exist, even when Pass 1 is skipped (body ≤ 10 000 characters). §1g.1 names no length condition. It costs one extra small call for a short paper with questions.
3. **Questions are de-duplicated for Pass 1q** before sorting, so a repeated question is asked once. The request's indices are kept, and a duplicate shares the same sentences.
4. **Logging.** Errors with questions present are logged by kind only (see Logs above).
5. **The abstract-as-introduction fallback is gone**, per §1g.1 ("every non-abstract `doc.sections` entry"). It only mattered for the old bucket list.
