What to build:

1. **The rename.** `git mv components/reader/explain-popover.tsx components/reader/explain-box.tsx` and its two tests with it (`explain-box.test.tsx`, `explain-box.flow.test.tsx`); `ExplainPopover` becomes `ExplainBox`; every other export keeps its name; the page's import follows. The popover of P3-02 is the box's first state.

2. **The thread, server side** (`lib/papers/explain.ts`, the route):
   - The request's `thread` is read: an array of messages `{ role: "reader" | "peer", text: string }`, at most 17 (the first answer as one `peer` message, then up to 8 reader / peer pairs), each `text` clipped to 400 characters by the server, anything malformed (not an array, a message without a role or a text) treated as `[]`. A non-empty thread whose last message is not the reader's is 400 `{ error: "thread must end with the reader's message" }`. The client sends the first answer as the thread's first `peer` message (`meaning` + " " + `here.text`) so the server never has to remember it.
   - `buildExplainReplyPrompt({ paper, map, located, passage, thread })`: P3-02's context (the same bounded pieces) plus the thread in order, each message labelled by role, and the reader's last message named as the one to answer; the rules: answer the reader's last message about this passage in plain words, ≤3 sentences; `evidence` is one sentence copied character-for-character from `context` when the reply rests on something the paper says, else omitted; no web, no advice, no verdict on reading on; nothing about the reader is a parameter.
   - The reply schema `{ reply: string, evidence?: string, evidenceWhere?: string }`; `sanitizeExplainReply` (≤3 sentences, ≤560 characters; the quote ≤400; everything else dropped) and `verifyExplainReply` (the quote located with `locateSection` as `verifyExplainAnswer` does; found → `evidenceWhere`, `sectionId`, `page` from the document; not found → the quote and places removed and `peer: true`). The wire shape of a reply turn: `{ role: "peer", text, evidence?, evidenceWhere?, sectionId?, page?, peer?: true }` (`ExplainTurn` grows these optional fields).
   - The route: with an empty thread everything is as it is; with a thread it builds the reply prompt, calls `generateJsonText({ maxTokens: 400, tier: "small" })`, sanitises, counts the turn on the same day counter, writes the same one debug line plus `thread: <message count>`, verifies, re-checks the upload's revision, caches under `explainCacheKey(docHash, passage, thread texts in order)` and answers `{ turn, cached: false }` (a hit `{ turn, cached: true }`, no call, no count). A thread with more than 8 reader messages is 400 `{ error: "thread_full" }`.

3. **The store** (`store/explain-threads.ts`): `ExplainTurn` gains the optional evidence fields above; `addTurns(paperId, passageHash, turns: ExplainTurn[])` appends (a reader message and Peer's reply together, after the reply arrives — a failed send leaves the thread as it was); `resetThread(paperId, passageHash)` empties `turns` and keeps the first answer; the cap: 8 reader messages per passage (`MAX_EXPLAIN_TURNS = 8`, exported; `threadFull(thread)`), nothing beyond it is stored.

4. **The box** (`explain-box.tsx`): under the first answer, the thread — each reader message under the label-face line `EXPLAIN.you` = "You", each Peer reply under `EXPLAIN.peer` = "Peer" (the prose in the reading face; a verified `evidence` as an `EvidenceQuote` with its section link and page; otherwise `PEERS_READING` beside the label and no quote); then a control row with a one-line input (`textarea`, one row growing to three, `placeholder` `EXPLAIN.placeholder` = "Ask about this passage…", `aria-label` the same): Enter sends, Shift+Enter is a newline, Escape closes the box (the existing capture listener) — through a pure `keyToSend({ key, shiftKey, isComposing })` helper (an IME composition never sends); a `Send` button (`EXPLAIN.send`) beside it for touch; while a reply is pending the input is disabled and `EXPLAIN.thinking` = "Peer is thinking…" shows under the thread; a failed reply shows `EXPLAIN.unavailable` under the thread and keeps the typed text in the input. At 8 reader messages the input is disabled under the line `EXPLAIN.threadFull` = "This thread is full. Select the passage again to start a new one." — and selecting the passage again after closing a full box opens it with the first answer and an empty thread (the full thread is dropped at that opening through `resetThread`). The send is the only request: `onReply(target, thread, message)` from the page, as `onAsk` is now. The input only exists when `canAsk` (a Tier 0-only box has no thread). The thread persists per paper and passage in the store and nothing is sent until Enter or Send.

5. **Layout.** On the spread (viewport width ≥ 1024): a floating panel 360 px wide, `fixed`, its top aligned with the selection's top (clamped inside the viewport), to the right of the text column when the column's right edge leaves ≥ 376 px of room, else P3-02's placement; its height bounded by the viewport less margins, the thread scrolling inside with the input pinned at the panel's foot. Between 640 and 1024: P3-02's placement unchanged. Below 640 (a phone): a bottom sheet — full width, anchored to the bottom, at most 60 % of the viewport's height, the thread scrolling inside, the input pinned at its foot; the selection stays visible above it where it can. `placePanel(bounds, viewport, column: { right: number } | null)` is a pure function with tests; the page passes the text column's rectangle (measure `#paper-body`'s bounding box the way the selection is measured, re-measured on scroll and resize). The box follows a scroll as now.
