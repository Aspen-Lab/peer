## The symptom

`docs/reading-helper-abc/P12-44-A-20261027T2050Z.md` D1: after an upload the page shows an abstract-only reading ("no abstract is published") and never asks again; the body comes only after a manual reload (2–16 s later for P1–P4, P6) and for a 25.6 MB paper not within 90 s. The upload route already extracts the whole PDF (`upload/route.ts` about 204) but discards the document; `writeUploadDoc` is called only by `full-text.ts` (about 366); the reading route waits `FULL_TEXT_TIMEOUT_MS` = 8 s then answers with the abstract (`fullText: "none"`); `use-reading.ts` (about 142–163) fetches once.

## The rules

1. **The upload keeps its document.** When the upload route's extraction succeeds, it writes the document with `writeUploadDoc` under the same key `getFullText` reads (owner-private, as today), so the first reading reads it instead of extracting again. A failed write never fails the upload.
2. **"Pending", not "none".** When the reading route answers before the full text settles, the reading's provenance says the full text is pending (a distinct value, documented), not that there is none; a settled "no text layer" stays "none". Private and public caching as today (a pending answer is never kept).
3. **The page keeps asking.** While the reading is pending, `use-reading.ts` asks again with a bounded backoff (about 2, 4, 8, 16 s, then every 20 s, for up to 3 minutes; aborted on unmount or paper change; one request in flight at a time), and the page shows one calm pending line instead of the abstract-only notice. When the body arrives it replaces the abstract without moving the reader's scroll; after 3 minutes the page says the full text could not be read yet and offers the existing reload.
4. Nothing else changes: the reading's shape for a settled answer, Tier 0 / keyed behaviour, the abstract-only notice for a paper that really has no text layer.
