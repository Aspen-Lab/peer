## The rules

1. **The core, pure** (`structure-review.ts`): `paragraphFeatures(text)` (Appendix B's counts: figure refs, table refs, citations, numbers with units, procedural verbs, first-person signposting) exported for the Tier-0 rules to share later; the skeleton (B §2.2 grammar; mode A 16-word heads; mode B above 24,000 characters); the draft from the map's top-level rows (role, confidence high when the heading names the role, medium otherwise; evidence tags are rule names and counts, never paper words); the prompt (Appendix B); the sanitizer / applier (Appendix A: `move_start`, `set_role`, `split`, `unsure`; at most 40 corrections; indices in range and monotonic; five roles only; an unusable answer → the draft unchanged); the second look (at most 3 per paper, at most 6,000 characters each, only for a correction against a high / medium part or a part in `unsure`).
2. **The route** `POST /api/papers/[id]/structure`: runs only when a model key is configured (§1h.428 (a)); report tier; returns the corrections (or none); every failure, timeout or refusal returns none — the page keeps the rules' draft; the server cache keyed `docHash | rules | skeleton | prompt` holds indices, roles and tags only (no paper text); uploads stay owner-scoped like the other model results of uploads (B §4 names the pattern).
3. **The client**: asks once per paper when a key is configured; remembers an answer 30 days and a failure 1 hour (the gist hook's pattern); applies the corrections to the displayed map; part ids stay stable and the scroll position does not move; **no mark** on a corrected role; without a key nothing changes (test it).
4. **The stub**: a `structure` kind that returns a valid empty answer (plumbing); unit tests use a test double that reads the invented skeleton's heads (B §6).
5. Nothing else changes: the gist call and its pinned prompt goldens, Tier 0, the map without a key.
