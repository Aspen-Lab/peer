What to build:

1. **`lib/papers/explain.ts`** (pure, server-side logic without I/O):
   - `clipPassage(passage: string): string` — trimmed, whitespace collapsed, at most 1,200 characters (cut at a word boundary).
   - `locatePassage(doc, passage, hint?: { sectionId; paragraphIndex })` → `{ sectionId, sectionIndex, paragraphIndex, paragraph, before: string | null, after: string | null } | null` — the paragraph (from `sectionParagraphs`) whose normalised text (`normalizeForMatch`) contains the normalised passage; the hinted paragraph is tried first, then the hinted section, then the whole document; null when nowhere (the selection is not the paper's text).
   - `buildExplainPrompt({ paper: { title, abstract }, map: { heading, opening }[], located, passage })` → `{ systemPrompt, userPrompt }`: the system prompt in `PASS2_SYSTEM`'s voice ("Peer, a calm reader …"); the user prompt carries the title, the abstract, one line per section of the map (the heading and the first paragraph's opening from `openingOf`), the paragraph before and after the located one (when they exist), the passage, and the schema below with the rule that `here.evidence` is one sentence copied character-for-character from the paper near the passage. Nothing about the reader (no profile, no project, no questions) goes into it.
   - The answer schema `ExplainAnswer = { meaning: string; here: { text: string; evidence?: string; evidenceWhere?: string; sectionId?: string; page?: number } }`; `sanitizeExplainAnswer(raw: unknown): ExplainAnswer | null` — strings trimmed, `meaning` and `here.text` each clipped to two sentences (reuse the sentence splitter the report sanitizer uses, or the simplest regex that `report.ts` already relies on), anything else dropped, null when either text is empty.
   - `verifyExplainAnswer(answer, doc, preferSectionId)` — `here.evidence` located with `locateSection(evidence, sectionCorpus(doc), preferSectionId)`; when it is found, `sectionId`, `evidenceWhere` (the section heading) and `page` are set from the document; when it is not, `evidence`, `evidenceWhere`, `sectionId` and `page` are removed and the answer carries `here.peer = true` (the prose renders under the `PEERS_READING` label).
   - `explainCacheKey(docHash, passage, thread: readonly string[])` → `sha256` of `docHash|normalizeForMatch(passage)|sha256(JSON.stringify(thread))` — the thread is `[]` in this item and the key already allows for P3-02b.
   - A tiny memory `explainCache` (same file or `explain-cache.ts`): ≤64 entries, 1 hour, oldest evicted; keyed by `explainCacheKey`; holds the verified answer only (§1g.4: nothing about the reader is in it).

2. **`app/api/papers/[id]/explain/route.ts`** — `POST`, `dynamic = "force-dynamic"`, `maxDuration = 30`. Body `{ paper: PaperReportRequest["paper"], passage: string, sectionId?: string, paragraphIndex?: number, thread: [], llmOverride?: ProviderOverrideConfig }`. In order: the `[id]` param must equal `body.paper.id` (else 400); the upload owner checks and the revision re-check exactly as the report route does them (an upload id that `bareUploadId` rejects is 404; an unowned upload is 404; a revision change during the call is 410, with `PRIVATE_UPLOAD_HEADERS`); `requireEntitledAiRequest("paper-explain", 40)`; `resolveProvider(body.llmOverride ?? null, providerCtx)` with path `"paper-explain"` — no provider that can write → 200 `{ unavailable: true }` (the client never asks in that state; this is the stranger's answer); `getFullText` as the report route calls it; no document or no sections → 200 `{ unavailable: true }`; `clipPassage` then `locatePassage` — null → 422 `{ error: "not_in_paper" }`; the cache by `explainCacheKey(docHash, passage, [])` with `docHash = sha256(JSON.stringify(doc))` → a hit answers `{ answer, cached: true }` with no model call and no count; else one `generateJsonText({ systemPrompt, userPrompt, maxTokens: 600, tier: "small" })`, `safeJson` → `sanitizeExplainAnswer` → `verifyExplainAnswer` → cached → `{ answer, cached: false }`; a model failure or an unparseable answer → 200 `{ unavailable: true }` (nothing counted). Counting, not charging (§1h.2): on every model call the route increments `rateKey("explain-turns", userId, now)` with `endOfUtcDay(now)` through `getCounterStore()` when there is a user id (the local dev user counts too) and logs ONE `console.debug("[papers/explain] turn", { userId: hashed or absent, count, promptChars, answerChars, cached })` — never the passage, the answer or any paper text. A company-budget refusal (`CompanySpendCapRefusedError`) answers `{ unavailable: true, quota }` with `companyBudgetQuotaSignal`, as the report route does. Headers: `Cache-Control: no-store` on every answer; `PRIVATE_UPLOAD_HEADERS` for an upload.

3. **`store/explain-threads.ts`** (zustand persist, key `peer-explain-threads-v1`, the `reading-questions` pattern): `byPaper[paperId][passageHash] = { passage, sectionId, paragraphIndex, answer: ExplainAnswer, turns: [] /* P3-02b */, at: ISO }`; `passageHash = sha256(normalizeForMatch(passage))` computed client-side with the hashing helper the client already has (find it; if none, the Web Crypto `SubtleCrypto` with a synchronous fallback is not acceptable — use a small FNV/`djb2` string hash in `lib/` and say so); ≤32 passages per paper, oldest dropped; `remember(paperId, entry)`, `forget(paperId, passageHash)`, `clearPaper(paperId)`; nothing in it is ever sent anywhere but the explain route (P3-02b sends the thread).

4. **Selection → affordance** (`components/reader/paper-body.tsx` + `components/reader/explain-popover.tsx`):
   - A pure helper `selectionTarget(input: { anchorParagraphId: string | null; focusParagraphId: string | null; text: string })` → `{ sectionIndex, paragraphIndex, passage } | null` (same paragraph id on both ends, parsed from `paragraphAnchor`'s shape; text non-empty after `clipPassage`-style trimming and ≤1,200 characters) — tested without a DOM. `PaperBody` listens to `selectionchange` on `document` (debounced ~150 ms), reads `window.getSelection()`, resolves each end's closest `[id]` ancestor inside `#paper-body` whose id matches `paragraphAnchor`'s pattern, and calls `onSelect(target & { rect: DOMRect })` or `onSelect(null)`; it adds nothing else to the body's markup.
   - `ExplainPopover` props: `{ target, terms: PaperTerm[] (P3-01's, as the page holds them), canAsk: boolean, onAsk: () => Promise<ExplainAnswer | "unavailable" | "not_in_paper">, cached?: ExplainAnswer }`. States: (a) closed — nothing; (b) button — a small floating "Explain this?" (`EXPLAIN.ask`, label face, `position: fixed`, just below the selection's rect, inside the viewport) shown when `target` is set and either a P3-01 term lies inside the passage (case-insensitive) or `canAsk`; with no term and `!canAsk` nothing shows (§1h.2's locked-block rule); (c) open — a card (≤ 360 px wide on the spread, beside the selection; full-width under the selection at phone width) with the passage's first ~80 characters as a label-face line, then: the term's definition as an `EvidenceQuote` when a term lies inside the passage (Tier 0; with `!canAsk` that is the whole card), then, when `canAsk`, the two parts under the label-face lines `EXPLAIN.meaning` = "What it means" and `EXPLAIN.here` = "Why it is here": the prose in the reading face; `meaning` carries the `PEERS_READING` label once beside its heading; `here.evidence` as an `EvidenceQuote` (section link and page as the question answers do), or, when `here.peer`, `here.text` with the `PEERS_READING` label; while waiting, `EXPLAIN.loading` = "Peer is reading this passage…" in the label face; `"unavailable"` → `EXPLAIN.unavailable` = "Peer could not explain this just now."; `"not_in_paper"` → `EXPLAIN.notInPaper` = "Select text from the paper itself."; Escape, a click outside, or a new selection closes it. Nothing is sent before the reader clicks "Explain this?" (the click is the send); a cached answer for the same passage (the store) opens at once with no request. No external links.

5. **The page** (`app/papers/[id]/page.tsx`): `canAsk` = the hook's `aiMode !== "none"` (the same test `use-model-report` makes for a provider, without `deepReportEnabled`: one explanation is a small call, not a deep read — a manager reading, flagged in the §5 row); `onAsk` posts `{ paper, passage, sectionId, paragraphIndex, thread: [], llmOverride }` (the `llmOverride` exactly as `use-model-report` builds it for a BYOK reader, else absent) to `/api/papers/${encodeURIComponent(paper.id)}/explain`, remembers the answer in the store, and resolves; the popover is mounted once, beside `PaperBody`. `sectionId` is the id the server's `sectionCorpus` would give the section (`section.id ?? s<index>`); C says in the checkpoint how the client gets it from `reading.body`.
