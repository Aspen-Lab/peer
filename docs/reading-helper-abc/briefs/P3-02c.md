Rulings for this item (the manager's, binding):

- **The charge is a parallel explain counter, not a fraction on `consumeDeepReport`** (the deep-report counters are integers and their tests pin them). New `lib/usage/explain-quota.ts`: `consumeExplainTurn(entitlement, { searched }, now)` → `{ allowed: true } | { allowed: false; reason: "exhausted" | "unavailable"; resetsAt }`. Units are tenths of a deep-report unit: a normal turn costs 1, a searched turn costs 10 (`EXPLAIN_TURN_TENTHS = 1`, `EXPLAIN_SEARCH_TENTHS = 10` — the placeholder prices from the user's chat estimate, to be re-set by a dated amendment once real token counts exist). Caps: per reader per UTC day `EXPLAIN_TENTHS_PER_DAY = 400` (forty normal turns, or four searched, or any mix), key `explain_tenths:<user>:<YYYY-MM-DD>`, window `endOfUtcDay`; a house ceiling for all readers `ALL_USERS_EXPLAIN_TENTHS_PER_DAY = 20000`, key `explain_tenths:house:<YYYY-MM-DD>`, both incremented on every charge, either can refuse (`breakerTripped`-style: fail closed on an unreadable counter with reason `unavailable`, `logStoreUnavailable("explain", userId)`, no usage row on an outage). No user id → refused `exhausted` (as `consumeDeepReport` does). Every plan is charged the same (a BYOK reader included, as the report route does); the `tiered` entitlement mode changes nothing here. `explainDayKey` and the count-only increment of P3-02 go: the charge replaces the count (the debug line keeps its sizes and gains `tenths`).
- **When the charge is taken:** in the route, after the owner checks, the gate and the provider check, after the cache lookup (a hit costs nothing), before the model call — the report route's order. A refusal inside the model call (the company budget) still costs the tenths. A charge refused → `429 { error: "explain_exhausted", reason, resetsAt }` and no model call.
- **The provider flag.** `DigestProvider.generateJsonText` gains an optional `webSearch?: boolean` and `DigestProvider` gains an optional `supportsWebSearch?: true`. Both Gemini providers set `supportsWebSearch: true` and, when `webSearch` is true, call the model with `tools: [{ googleSearch: {} }]` and WITHOUT `responseMimeType` (Gemini refuses JSON mode together with a grounding tool; the text is parsed by the route's `parseModelJson`, which strips a fence) — add the `webSearch` branch to `genConfig` and both call paths; every other provider ignores the argument. The route sets `searched = body.search === true && provider.supportsWebSearch === true`, charges 10 tenths only when `searched`, passes `webSearch: searched`, and the reply turn carries `searched: boolean`; with `search: true` and a provider that cannot, it is a normal turn (1 tenth) with `searched: false`. `meterProvider` must pass the new argument through (confirm; fix if not — one line).
- **The prompt with search:** `buildExplainReplyPrompt` takes `search?: boolean`; with it the rule "Do not search the web…" becomes "You may use web search for general background. The paper's own words still come only from `context`; `evidence` is still one sentence copied from it. Name no URL and no source by name." Evidence verification is unchanged (the paper only). The first message never searches (the toggle is for a message in the thread).
- **The UI (§1a.11).** At the start of the control row, a small toggle button `EXPLAIN.searchToggle` = "Search the web" (label face, `aria-pressed`, a bordered pill like Send, off whenever the box opens or a passage is opened — session state, never persisted). On hover and on keyboard focus a tooltip `EXPLAIN.searchWarning` = "Web search costs many times more than a normal reply. On for this message only." (a `role="tooltip"` element the button `aria-describedby`; shown by CSS `:hover` / `:focus-visible` plus a `data-tooltip-open` attribute for touch); on a touch pointer (`pointerType === "touch"`) the first tap shows the tooltip and the second enables. When on, the next send carries `search: true`; the reader's message in the thread then carries `searched: true` (stored in `ExplainTurn`) and renders the label-face mark `EXPLAIN.searchedMark` = "searched the web" beside "You"; the toggle resets to off after the send (sent or failed). When the reply comes back `searched: false` for a message sent with `search: true`, the mark is not shown and the one-line note `EXPLAIN.searchUnavailable` = "Web search is not available with this provider." shows under that reply (label face). The toggle is absent without `canAsk` and disabled while a reply is pending or the thread is full.
- **Over the cap.** A 429 `explain_exhausted` from a send: the box shows `QUOTA.explainExhausted` = "Explanations are used up for now." under the thread, the input and the toggle disabled, the typed words kept; from the first message (the button click): the same line in place of the loading line. Reason `unavailable`: `QUOTA.explainUnavailable` = "Peer could not check the explanation allowance just now. Nothing was spent." (the outage principle of §1g.14). Both strings in `QUOTA`, covered by the copy grep in `quota-notice.test.tsx` (extend its scan if it enumerates keys).
