## The defect

The button stands just below the selection's end, centred on `rect.right`: on a spread that is the next line of the same paragraph, so it covers words the reader is reading (shot: the button over "…" at (535,317) at 1440). The owner's reading of the page: a control must stand beside the words, never on them.

## The rule to build (`placeButton(rect, viewport, paragraph?)`)

1. **The gutter, when there is one.** When the paragraph's rect is known and there is room to its right — `viewport.width − paragraph.right ≥ BUTTON_WIDTH + 2·BUTTON_MARGIN` (the viewport passed in is already narrowed by `DOCK_RESERVE_PX` while the dock stands, so the gutter is the space between the reading column and the dock) — the button stands **in the gutter, level with the selection's first line**: `left = paragraph.right + BUTTON_GAP`, `top = rect.top`, both clamped inside the viewport (`BUTTON_MARGIN`; the top so that the button's foot stays above `viewport.height − BUTTON_MARGIN`). It never overlaps `paragraph` (assert in the test: `left ≥ paragraph.right`).
2. **No gutter (a phone, a narrow window, a column flush with the edge):** today's placement (below the selection's end; above when there is no room below) — unchanged, so the card and sheet cases keep their tests.
3. The button's own size constants stay; no new wording; the header comment of `explain-box.tsx` gains one sentence on the gutter rule.
