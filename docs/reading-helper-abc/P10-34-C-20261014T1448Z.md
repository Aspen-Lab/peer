## 2. What is carried, and two disclosures

- **Rule 1.** Each `Figure N` caption that has a page gets the picture's width and height as two positive whole numbers: `pdf-text.ts` asks the figure engine, from the bytes already in hand, for the same region the route would draw (the same call the route makes: one page, label `Figure N`) and reads its size without drawing. A figure the engine finds nothing for, a caption with no `Figure N` number or no page, a paper past a 10-s measuring budget (at most 24 figures), an engine that will not load: no size (P10-26's 32rem room), never a failed reading. Never a new fetch. For a link and an upload alike (both go through `normalize`); `placeFigures` already kept the pair (P10-26), `reading.ts` needed only the export.
- **Disclosure 1 — pixels, not PDF units.** The brief says "PDF units"; I carry the **picture's own pixel size** (the PNG the route returns), because P10-26's `figureBoxStyle` (unchanged, `paper-body.tsx` not mine) reads `width` / `height` as pixels (`ReadingFigure` / `ExtractedFigureCaption` doc comments, P10-26 checkpoint §2): `width: min(100%, wpx, calc(32rem * w / h))`. In points a 400-pt figure would be drawn 400 px wide instead of filling the column. The ratio is the same either way and is exact in pixels (below).
- **Disclosure 2 — the engine file.** The brief allowed "a measuring helper it already has"; it has none (the box and the pixel size exist only inside `renderRegion`). `pdf-engine.ts` gets, additively: a `measureOnly` option (`renderRegion` returns the pixmap's size, computed from the same clip / scale / stretch / `roundOut`, and draws nothing), `width` / `height` on `PdfEngineFigure` (the PNG's own size), and an exported `measurePdfFigure(bytes, page, fig)`. What the engine finds, draws and returns without `measureOnly` is unchanged (its 30+ tests, the route's tests: green).
