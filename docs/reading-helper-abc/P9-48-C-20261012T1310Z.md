## 2. The rules as built

**Rule 1: no figure by value in the cache.** `withoutFigureData(report)` (exported, pure) returns the very report when no `figureImageUrl` is a `data:` URL, else a copy in which every `data:` URL, on `whatItProposes` and on each `keyResults[i]`, has its `figureImageUrl` field **deleted** (absent). `writeCached` stores that copy. `figureLabel`, `figureCaption` and `figureSource` stay (a few words; the key, the TTL and the entry's `{ report, savedAt }` are unchanged). An `https:` URL or the figure route's own URL is already small and is kept. The report handed to the page in this visit is not touched (`settle` caches a copy and sets the original into state), so the visit that generated the report still draws its figure; a test pins that. A cache an earlier build wrote (entries of 1.08 M each) is rewritten without the figures on its next write, its reports kept rather than evicted.

- **How the figure is carried: it is not, from this file.** The preferred branch (the figure-image route's URL, so the browser never holds the data URL) needs the figure's **page**: `/api/papers/<id>/figure-image?page=&fig=` names it, and the report carries none; only the reading does (`ReadingFigure.page`, from `ExtractedFigureCaption.page`), and `useModelReport` is given a paper, not a reading. So the else-branch of the rule applies: **the field is dropped**.
- **Can the server send the route URL in the first place? Yes, but not from my files.** `bindFiguresToReport` has each caption's `page` (`ExtractedFigureCaption.page`, PDFs only) and label, so `resolveImage` could answer `pdfFigureUrl(id, page, n)` instead of the pool entry's `data:` URL; it is not given the paper's id (`paper: { title }` only), and the two call sites are in `app/api/papers/report/route.ts` (l.514, l.694), not mine. So `figure-binding.ts` was not changed (a half built there would be dead code until the route passes the id). See "For the manager" 1.
- **What a reload draws with the field dropped.** The page's `boundFigure` is null, so `PaperPlate` draws `useResolvedFigure`'s pick (`POST /api/figure`, which the page runs on every open and the card primed) with that resolver's caption, or the plate of terms where it finds none (`hideFigure`); each key result's section, no longer "bound elsewhere", renders `SectionFigure` and asks the same service with its own query (up to four more requests, no model, no key). That is **the paper's figure by the resolver's pick, not necessarily the figure the report bound**; this item does not restore the identical picture, and this file says why it cannot (the page is missing from the report). Item 1 below gives the two ways that would.

**Rule 2: a character budget.** `REPORT_CACHE_BUDGET_CHARS = 1_500_000` (exported; the brief's ceiling), beside `MAX_ENTRIES = 40` (unchanged). Why 1.5 M: a browser gives one origin about 5 M characters in all (5.24 M in A's walk), shared by the feed, the profile with the key a reader stored, the reading preferences, the question store and the reading cache; the cache alone filled it at four entries. A report without its figure is a few KB to some tens (`REPORT_CAPS` bounds every field; A's totals, 4.34–4.44 M for four 1,081,390-char figures, put the rest at 3.6–29 KB per entry), so 1.5 M holds the forty the count allows with room, and is under a third of the smallest quota.

`writeCached` now: builds the new entry (figure dropped); if the cache holding it alone would pass the budget, it is **not cached**, the cache is left as it was, and one line is logged, `[report-cache] a report over the cache budget was not cached: <chars> characters, budget 1500000` (two numbers, nothing of the report, its key or its project); else takes every other entry (figures dropped from old ones, a malformed entry dropped), sorted oldest first (ties keep write order), and evicts from the front until `1 + Σ entryChars` (the exact length of the serialized cache: braces, keys, values, commas) is within the budget **and** the count is within 40; then writes. The replaced key is not counted twice, and the new entry is never the one evicted, even when every entry has the same `savedAt` (the head's sort put a tied new entry last in the keep-list). The quota error is still swallowed, but it is no longer the only limit.

**Rule 3: nothing else changes.** Key (`buildReportKey`), `STORAGE_KEY`, the entry's `{ report, savedAt }`, `DEEP_TTL_MS` / `ABSTRACT_TTL_MS`, `readCached`, `rememberReport`, the request, the stream, the legacy-key sweep: unchanged. The reader's key reaches the request body only; a test asserts the placeholder key is in no cached byte.

## 7. For the manager

1. **A reload draws the resolver's figure, not the report's, until one of two things is built outside my files.** (a) *Server (best: the browser never holds the data URL, and the stream's 1.08 M shrinks to one URL):* `app/api/papers/report/route.ts` passes `paper: { title, id: body.paper.fullTextUploadId ?? body.paper.id }` at its two `bindFiguresToReport` calls (l.514, l.694), and `figure-binding.ts`'s `resolveImage` answers `pdfFigureUrl(id, caption.page, n)` (exported by `lib/papers/reading.ts`; its `pictureNumber` is private there) where the pool entry's `imageUrl` is a `data:` URL and the label's caption has a `page` and a plain number. The relative URL is not re-sanitized after binding (`report.ts`'s `FIGURE_URL` runs on the model's output; `report-stream` does not sanitize). Check before building: the pool entry is picked by caption tokens and the route draws the region whose caption opens "Figure K" on page P, so the two should agree but are not the same code path; for a public paper the route resolves `getFullText`'s PDF and the pool may have used `arxiv.org/pdf/<id>`; an upload's route is owner-only and `private, no-store` (one MuPDF render per request, as the reading's ten already are). (b) *Render time (`papers/[id]/page.tsx`, no server change):* when `report.whatItProposes.figureImageUrl` is absent and `figureLabel` is set, take the `imageUrl` of the reading's figure with the same label (`reading.sections[].figures[]` carry `label`, `page`, `imageUrl` = the route URL), for the plate, the proposal and each result; the label survives in the cache for exactly this. About six lines; also covers every cached report from today on. Both can stand together.
2. **`use-reading.ts` (`peer-reading-v2`): no figure by value, the budget hazard in a milder form; not changed.** `imageInBlock` refuses `data:` images, and a PDF's pictures are route URLs (`placeFigures`), so a reading never holds one (a synthetic 12-section reading of a 74,916-char body serialized to 91,039 characters, no `data:`). It has the same *shape* as the old report cache: `MAX_ENTRIES = 40`, a count with no budget, and a `catch` that swallows the quota error. Its cost is lower: one entry per paper (not per question set), a 24 h TTL, and a miss costs one GET (a public paper's is edge-cached) with **no model call and no key**. In the long tail (40 long papers in a day, 150 K characters each) it could still take 6 M; the same constant-and-eviction in its `writeCached` (about 15 lines, plus the same kind of test) would close it. With a 1.5 M budget on each, the two caches together would stay under 3 M of the ~5 M.
