## Each rule as built

**BACKLOG-32 — `equationOf` (`91cd6c83`, `pdf-outline.ts`).** A PDF line is a display equation only when it ends in `(n)` / `(3a)` (one to three digits, an optional lower-case letter) and carries at least one maths symbol; its text is the line without the number, `number` is `"(n)"`. The unnumbered branch is gone (three symbols, under three real words, under half its characters in words), and with it its two helpers, `realWords` and `EQUATION_PROSE_WORDS`, which nothing else used (dead code otherwise, and a lint warning). `MATH_SYMBOL` lost its `g` flag: it is only ever `.test`ed now, and a global pattern keeps its place between calls. `EQUATION_MAX` (120), `MATHS` (headings), the `OutlineEquation` type, `blockMarker` and the marker paragraph in `buildOutline` are as they were. An unnumbered symbol-heavy line goes through `held.push(line)` like any line and joins its paragraph under `joinProse`'s own rules (rhythm, indent).

**BACKLOG-34 — `endsTheArgument` (`c5572e8e`, `pdf-outline.ts`).** New `GLYPH_LEAD = /^[^\p{L}\p{N}]+(?:\p{Ll}{1,3}\s+)?/u`: a leading run of characters that are neither letters nor digits (a box, a bullet, an asterisk), and, only behind such a run, up to three lower-case letters standing apart (see "For the manager" 2). `endsTheArgument` strips it first (`heading.trim().replace(GLYPH_LEAD, "")`), then runs the `APPARATUS_HEADING` test on what is left, then strips `SECTION_LEAD` for the end-matter tests: glyphs first, then the number, so `■ 5. Funding` still reads as the numbered Funding. A digit is never part of the glyph run, so a section number is still `SECTION_LEAD`'s. A heading that starts with a letter is read as it was. `canonicalizeHeading` is untouched (it is `html-text.ts`, P8-04's): `• References` is already `references` there (the match is by substring), so it was terminal before and stays so.

**Version (`062d8f19`).** `UPLOAD_CONCEPT_EXTRACTION_VERSION` 5 → 6 with its history line; the same number keys the server's cache of an upload's extracted text (pinned by the P7-18 test that reads `full-text.ts`).

## For the manager

1. **The printout is 23 → 18, not 23 → 21.** "Authors" and "Notes" are gone, as expected, and so are three more rows: `*sı Supporting Information`, `4.4. Raman Spectroscopy` and `■ ACKNOWLEDGMENTS`. It follows from the rule the brief set: `*sı Supporting Information` now ends the argument, so it is dropped like its plain twin, and everything after it in reading order goes with it. In the printout (the owner's print of the app's earlier, scrambled rendering of the paper) the body sections run `… 4.3 (cont.) → *sı Supporting Information → 4.4 Raman Spectroscopy → Authors → Notes → ■ ACKNOWLEDGMENTS`, so the real 4.4 section stands after the Supporting Information heading in that file and goes too. In the paper itself (the file this reading is for) the order is right and the map is unchanged (12 rows, the same headings). To get exactly 21 the `*sı …` heading would have to stay a section, which contradicts the brief's own test list ("`*sı Supporting Information` ends it"); I followed the test list. If A's P8-05 expects 21 on the printout, that expectation needs correcting; an A re-measure through the real route on the paper is the better check.
2. **"`*sı`" is two letters, not a glyph.** The brief says the heading's own words are matched "after a leading run of non-letters is stripped"; the text layer gives the journal's Supporting Information icon as `*` + `s` (U+0073) + `ı` (U+0131, dotless i) + space, so stripping non-letters alone leaves `sı Supporting Information`, which does not match. `GLYPH_LEAD` therefore also takes, only behind a non-empty run of non-letters, up to three lower-case letters standing apart by whitespace. The price: a heading such as `• a Funding` loses its `a` — not seen anywhere; a bare `sı Supporting Information` (no glyph in front) stays a section (pinned). Other icon fonts that map to non-letters need nothing more. A narrower alternative (the exact token `sı`) would be one regex alternative if you prefer it.
3. **A numbered equation printed over several lines keeps its number on one line only.** The number stands on the last (or the middle) printed line and that line alone is lifted; the lines above and below it are prose, so a displayed fraction becomes a lifted middle line plus fragment paragraphs (pinned in `takes the last line of a numbered equation printed over two lines…`). The set of 13 PDFs has no numbered equation at all (34 candidates before, 0 after), so this was not measurable here. If a numbered multi-line equation matters, the fix is a rule to gather the lines above a numbered line at the equation's own indent — a separate item.
4. **The cheap rule's other edge**: a prose line that ends in `(n)` and contains a symbol (for instance `… = 3 (2)`) is still lifted, as before this item; none occurs in the set (the 0 after). The unnumbered branch is the only thing removed.
5. **A pre-existing quirk not touched**: `lastNumbered` (the body's last numbered section) reads a heading through `sectionNumberOf`, which needs the heading to start with a digit, so a glyph-led numbered heading (`■ 5. Funding`) is not counted as numbered there. It does not matter for end matter (an end-matter heading is skipped there anyway) and no body heading carries a glyph in the set; noted only.
6. **The HTML extractors are untouched** (`html-text.ts` is P8-04's); the equation rule here is the PDF's only.
