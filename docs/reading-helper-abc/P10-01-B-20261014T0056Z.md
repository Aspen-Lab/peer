## 1. Certain from the code and from React

1. **The line.** `web/src/components/reader/explain-box.tsx:1044` is `setViewport((previous) => (sameViewport(previous, size) ? previous : size))` inside the no-dependency `useLayoutEffect` that starts at line 1038 (the "after every commit" effect). Its sibling `setCardHeight` is at 1051. The first state write in that effect is the viewport one, so it is where React's counter trips first after a commit whose effect already queued an update.
2. **React's rule (19.2.4, `react-dom-client`).** `getRootForUpdatedFiber` throws when `nestedUpdateCount > 50`; the counter goes up by one at the end of a commit that began with a sync-lane render AND leaves a sync update pending (the layout effect queued one), and resets to 0 on any commit that leaves none. So the throw needs **51 consecutive commits, each of whose layout effect queued a real update**. A no-op update (state unchanged) bails out in render and resets the counter, so it does not count. A state write that React can bail out of eagerly (`fiber.lanes` empty and equal value) never reaches the check at all.
   - Consequence: either `viewport` or `cardHeight` had to take a different value on every one of 51 consecutive commits. The attribution to line 1044 does not prove it is `viewport`: if `cardHeight` alternates, the `setViewport` call is simply the first write after the 51st commit (the eager bail is skipped when the alternate fiber still carries lanes, a known React quirk; I did not test this).
3. **Production too.** The throw is unconditional in the production build (minified React error 185, `formatProdErrorMessage(185)`, the same `getRootForUpdatedFiber`); only the passive-effect variant ("calls setState inside useEffect ...") is dev-only. The overlay the owner saw is Next's dev display of that thrown error.
4. **Question 4, the boundary.** "This view hit a snag." is `web/src/app/error.tsx:24` (the root segment boundary, `ErrorBoundary`; `app/global-error.tsx` is the fallback above the root layout and has different words). There is no `app/papers/[id]/error.tsx`. The thrown error is raised while committing, inside the reader page, so the nearest boundary is `app/error.tsx`: it replaces the whole page (page.tsx and the box with it). In dev the overlay appears first and, once dismissed, the boundary shows (the owner's 8.1); **in production the boundary shows at once, with no overlay**, so the owner's key-holding readers would see "This view hit a snag" and lose the paper view. "Try again" (`reset`) remounts the page and, if the cause is still there, loops again.
5. **What feeds back into the layout the effect reads.**
   - `reserveDock` (explain-dock.ts:164) writes `--explain-dock` / `--explain-dock-width` on the root; `.peer-main-content` pads by it. It changes the page's width, not `window.innerWidth/innerHeight` and not the card.
   - `currentViewport()` (explain-box.tsx:454) = `{innerWidth, innerHeight, legend: 28 * zoom}` where `zoom` is the computed `--page-zoom` of `[data-zoom-root]`. The legend is **not measured from the DOM**: it is `legendHeightPx(pageZoom())`, and the page's zoom is computed from `window.innerWidth`, the reading scale and the spread media query (`usePageZoom`, reader-layout.tsx:148; `fitZoom`, store/reading-prefs.ts:119). None of those reads the dock's reserve. **Candidate (a) of the brief (legend wrap/unwrap oscillation) is therefore false by construction**: the legend's height is arithmetic, not a layout read.
   - The card height read (line 1049) is `card.scrollHeight + (offsetHeight - clientHeight)`. The card is `overflow-y-auto` (line 701), so `scrollHeight` is the natural content height whatever `max-height` clips; `place.maxHeight` = `needed` when bottom-clamped (explain-dock top rule, `placePanel` line 405), so the card is sized to exactly its last reading when the paragraph is low on screen. That is a zero-slack feedback (height -> max-height -> height); it converges unless the reading itself changes with the card's size (a scrollbar that appears and disappears and so re-wraps the text; sub-pixel overflow). See 2.4.

## 4. The fix guide for C P10-08 (in order; containment that ends ANY loop of this shape, since the cause is not found)

The shape is certain even though the trigger is not: an effect with no dependency list writes state on every commit, and the write feeds the next read through layout. The fix is to make that effect unable to run away, not to guess which number moves.

1. **Make the after-every-commit effect converge by construction** (`explain-box.tsx:1038-1052`). Keep a ref with the last two values written (`{viewport, cardHeight}` of the previous two commits). If the value about to be written equals the value written two commits ago (an A, B, A pattern) or the number of consecutive writes in this burst exceeds a small cap (say 8), stop writing for this commit and settle on the larger `cardHeight` (taller never hides content: P9-17's window stays inside the screen because `placePanel` clamps the top). Reset the counter in a `requestAnimationFrame`, so the next real change (a reply, a resize) gets a fresh budget. This ends a 2-cycle of either state and is the only change that is correct whatever the cause turns out to be.
2. **Take the viewport read out of the every-commit effect** (line 1043-1046). The comment says it exists so P9-20's Fit toggle (no scroll, no resize) is seen. Replace it by reading the inputs that change the legend: subscribe the box to `useReadingPrefsStore((s) => s.fit)` and `.scaleIndex` (and the resize listener it already has) and re-read `currentViewport()` when they change. Then the viewport can no longer be written by an arbitrary commit. Keep the `sameViewport` bail; round `legend` to 0.01 px in `currentViewport` so a differing last bit cannot count as a change.
3. **Height read with a tolerance and a floor on slack** (line 1049-1051). Treat a reading within 2 px of the previous one as equal (it is 1 today), and when the dock is bottom-clamped give `maxHeight` 2 px of slack (`needed + 2`) so the card never sits at the exact fit boundary where one rounding flips overflow. P9-17 keeps holding because the extra 2 px stays above the legend's reserve only if `placePanel`'s clamp uses the same `needed + 2`.
4. **Do not rely on removing the standing empty window and the floating pill (P8-06) to end it.** The throw's effect has `docked || target !== null` and `docked && card` guards; with a passage open `docked` is true on the owner's laptop (width >= 1024, a key), so the same effect runs with the same inputs. Removing the empty window only removes the not-yet-open case. It would not end a loop that can happen with a passage open (which is what the owner hit, mid-Explain). If C removes the empty window, do 1 to 3 as well.
5. **A boundary that does not strand the reader.** In any case give the reader page its own `app/papers/[id]/error.tsx` (a small copy of `app/error.tsx`'s shape with "Back to the paper's list" and a retry that keeps the paper), so a future throw in the box does not take away the whole page's route; and consider rendering `ExplainBox` inside a local error boundary that falls back to no box. (Product direction: Tier 0 stays useful without the box.)

Invariants that must hold after the change: P9-17 (the window's whole height stays in view; `placePanel` clamp, `DOCK_THREAD_FLOOR_PX`), P9-20 (the legend's height follows Fit without a scroll or resize: test that toggling Fit with a window open updates `viewport.legend` within one frame), P7-15 (the reserve effect holds the selection in place across the reflow: `explain-box.dock.flow.test.tsx`), P8-02 / P9-03b (the window follows the selected paragraph without close and reopen).

Tests at risk (named, from `web/src/components/reader/`): `explain-box.dock.flow.test.tsx` (the hook-runtime flow: it counts reserve/unreserve and the placement for each step), `explain-box.card.test.ts` and `explain-dock.test.ts` (the `placePanel` / `legendHeightPx` numbers; a `needed + 2` slack in step 3 changes `maxHeight` in them), `globals.css.test.ts` (the `--page-zoom` and `.peer-main-content` pins), and `store/reading-prefs.test.ts` if step 2 adds a selector there.

## 5. How the box is rendered in tests, and the harness text

- Tests run in plain Node with **no DOM**: `explain-box.dock.flow.test.tsx` mocks `react` with `hookRuntime.hooks` (`web/src/test-support/hook-runtime.ts`: render, run effects, re-render on state change until quiet; its `useLayoutEffect` is at line 102) and inspects the returned element tree. A reproduction of the real cause needs a browser (the scripts below).
- Scripts (under `/tmp/claude-0/-home-user-peer/9602921a-6ac5-5952-88ce-8364fcd8f733/scratchpad/p10b01/h/`, not committed; copy them, they import `lib.mjs` from p9c20's harness with the port set to 4001): `lib.mjs` (launch; env `SB=1` keeps classic scrollbars, `DSF=1.25` sets the device scale factor), `upload.mjs` (uploads the invented PDF with the invented key state), `drive.mjs` (the full flow, 6 selections, per-step read bursts), `hsweep.mjs` (open once, then resize the height one pixel at a time), `frac.mjs` (fractional padding), `mouse.mjs` (double-click path), `flip.mjs` (spread query straddle). The instrument shared by all of them, whole:

```js
await ctx.addInitScript(() => {
  window.__reads = [];
  const d = Object.getOwnPropertyDescriptor(Element.prototype, "scrollHeight");
  Object.defineProperty(Element.prototype, "scrollHeight", {
    configurable: true,
    get() {
      const v = d.get.call(this);
      if (this.hasAttribute && this.hasAttribute("data-explain-card")) window.__reads.push([Math.round(performance.now()), v]);
      return v;
    },
  });
});
// per step: const reads = await page.evaluate(() => { const a = window.__reads; window.__reads = []; return a; });
// a loop = a burst of dozens of reads inside a few milliseconds; the throw comes at the 51st nested commit.
```

- **Log per commit** (what the next B should add, in a throwaway copy of the component, not in production code): inside the every-commit effect log `[docked, viewport.width, viewport.height, viewport.legend, cardHeight, card.scrollHeight, card.offsetHeight, card.clientHeight]` to `window.__log`, and print the last 60 entries when the page error arrives. That names the oscillating value in one run.
