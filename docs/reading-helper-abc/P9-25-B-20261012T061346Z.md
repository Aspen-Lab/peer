## 2. The options

Reference for every comparison: the **unchanged helper** run in a scratch venv (`pip install pymupdf` → 1.28.2) on the owner's paper.

### (a) A Vercel Python Function beside the Next app — feasible in principle, dominated; Vercel side UNVERIFIED

Measured here (the engine half): the wheel is `pymupdf-1.28.2-cp310-abi3-manylinux_2_28_x86_64.whl`, **25.76 MB** (25,762,500 bytes, PyPI); installed **65 MB** (`libmupdf.so` 36.2 MB, `_mupdf.so` 15.5 MB, `libmupdfcpp.so` 3.1 MB); `import pymupdf` 0.17–0.27 s and 47 MB RSS; the whole paper in the unchanged helper 5.0–7.7 s wall, 167–184 MB peak (§4). `requires_python >=3.10`, abi3, so any current runtime takes it.

From memory, UNVERIFIED (docs blocked): Python functions live in `api/*.py` (with Root Directory `web/`: `web/api/`) with a `requirements.txt` beside, and coexist with a Next.js project (the `nextjs-fastapi` example uses a rewrite from `/api/py/*`); a Python bundle limit well above 65 MB; default memory ≥ 1–2 GB; durations of minutes. These do not make (a) fail. **What makes it a poor fit are four things I can state from the repo and the measurements:**
1. **The PDF cannot be posted to it.** The repo's own comment: "A Vercel function refuses a request body much over 4 MB, and a paper's PDF is often larger" (`lib/papers/upload-store.ts:235-236`); the owner's paper is 14.5 MB, the cap is 18 MB. The function would have to fetch the PDF itself: for a public paper by URL, for an upload through a signed Supabase URL Node mints and hands over (a private PDF crossing to a second function).
2. **The answer cannot come back whole.** The helper's output for this paper is **8,875,634 bytes** of JSON (12 PNGs, 6.65 MB, base64) against the same 4–4.5 MB body limit → one call per figure, or write to the bucket and return keys. Both are new design.
3. **Preview-to-preview call.** The Node route would call `https://$VERCEL_URL/api/…` on the same deployment; a preview is normally behind Deployment Protection, so the call needs a bypass secret (a dashboard setting plus an environment variable) — UNVERIFIED, from memory.
4. **Dev parity.** `next dev` serves no `api/*.py`, and this container has no PyMuPDF; the loop's own walks (A) would still see captions only, because nothing in the container gets installed by `npm`. Two build pipelines, and `api/figure.py` would collide with `src/app/api/figure/` in one URL space.

Cold start on Vercel: not measurable without a deploy (the preview measures it). Locally the import is 0.2 s.

### (b) MuPDF's own WASM build in Node (`mupdf@1.28.1`) — recommended; works, measured

`mupdf` on npm: 14.32 MB unpacked, 11 files, ESM only, no dependencies, `"license": "AGPL-3.0-or-later"`; `dist/mupdf-wasm.wasm` 10,409,826 bytes (3.63 MB brotli in the package). It is the same MuPDF C library PyMuPDF wraps (both by Artifex). The API covers what the helper needs: `page.toStructuredText(...).walk({beginTextBlock, beginLine, onChar, onImageBlock(bbox, transform, image)})`, `image.getWidth/getHeight/getXResolution/getYResolution`, `new mupdf.Device({fillPath, strokePath, …})` + `Path.getBounds(stroke, ctm)` for the drawing rects, `new mupdf.Pixmap(DeviceRGB, bbox, false)` + `DrawDevice` + `page.run(dev, matrix)` for the clipped render, `pixmap.asPNG()`.

**Prototype**: a line-for-line port of the helper (text blocks, image blocks, `placed_image` stretch, caption matching, de-dup, `cluster_drawings` ported from the installed PyMuPDF source, clipped render) in `scratchpad/p9b25/proto-mupdf/extract.mjs` (~250 lines). Result on the owner's paper in §4: **12 of 12 regions, 12 of 12 captions character-identical to the helper, boxes within 1–2 px.** On a synthetic PDF I generated (`p9b25/synth/make.py`: a vector bar chart with a Bézier curve on one page; two vector panels with captions on another) it finds all 3 vector figures with the right captions, **two on one page separately** (the existing figure-image route's rule would refuse that page); its box is slightly roomier than PyMuPDF's on the curved chart (840×547 px against 812×504; +3% wide, +9% high; the cause — stroke width or the curve's control hull — I did not isolate) and within 2 px on the two plain panels.

**Under Next 16.2.3, as a deployment would carry it** (scratch app `p9b25/nextapp`, same Next version, Turbopack, `output: "standalone"`, then the standalone folder **copied elsewhere** and run alone on port 3924, so only traced files exist):
- bundled (no config): builds; the function's trace is 100 files / **12.1 MB** and contains `.next/server/assets/mupdf-wasm.<hash>.wasm` (10.4 MB); first request (import + open the 14.5 MB PDF + render page 4 at 2×) **2.06 s** (import 236 ms), warm 0.89 s; RSS 189 → 230 MB.
- with `serverExternalPackages: ["mupdf"]`: builds; the trace holds `node_modules/mupdf/dist/mupdf-wasm.wasm`; 1.79 s cold, 0.79 s warm. The package then stays a separate file instead of being compiled into the server chunks.
- in a `worker_thread` (a hard timeout; the Python helper had `timeout: 25_000`, `pdf-extract.ts:211`): `new Worker(new URL("./w.ts", import.meta.url))` **fails the Turbopack build** ("Can't resolve") — a worker file must be named by a computed path under `/*turbopackIgnore: true*/` (the pattern `resolveHelperScript` already uses) and listed in `outputFileTracingIncludes` together with `./node_modules/mupdf/**`; so done, it ran from the traced copy, and a 150 ms limit killed it (`timedOut` at 222 ms); in plain Node the memory came back with the worker (RSS 243 MB → 100 MB after a normal exit, 68 MB after a `terminate()` at 200 ms). Cost: each call instantiates the WASM again, 1.3–1.6 s for the page render against 0.8 s warm in-process.

The Vercel Node runtime allows WebAssembly (the Edge runtime is the restricted one; these routes are `runtime = "nodejs"`, `figure/route.ts:29`, `figure-image/route.ts:23`) — from memory, UNVERIFIED; the preview proves it.

### (c) pdf.js + `@napi-rs/canvas` — works, 4× slower, no AGPL; measured

`pdfjs-dist` is **not** a direct dependency: `unpdf` ^1.8.1 is, and it bundles pdf.js (6.1.200, `dist/pdfjs.mjs`); `unpdf.renderPageAsImage(…, { canvasImport: () => import("@napi-rs/canvas") })` exists for exactly this. `@napi-rs/canvas` 1.0.11 (MIT): the main package 0.13 MB plus the platform package `@napi-rs/canvas-linux-x64-gnu` **34.85 MB** (`skia.linux-x64-gnu.node`).

**Prototype** (`p9b25/proto-canvas/extract.mjs`): the same rules, with the geometry from pdf.js — text blocks grouped from `getTextContent()` items (pdf.js has no block layer, so the grouping is mine), image boxes from `getOperatorList()` under a tracked CTM, drawing rects from `constructPath`'s min/max, clip render with `page.render({ viewport: offsetX/offsetY, transform })` into a clip-sized canvas. Finds the same 12 regions; **captions identical to the helper for 5 of 12** (Figures 1–10 are found, but a block boundary of my own grouping differs on the others, and on the two non-figure items the wrong block is taken); renders 4–15 mean-abs-difference from the helper's pixels (a different rasteriser). It also found the 3 synthetic vector figures (the box of the curved chart 6% shorter than the helper's, 476 against 504 px, the whole chart inside).

**Under Next 16.2.3**: with no config the build **fails** — `./node_modules/@napi-rs/canvas/js-binding.js: non-ecmascript placeable asset` — and needs `serverExternalPackages: ["@napi-rs/canvas"]`; then the route's trace is 106 files / **38.0 MB** (the `.node` 34.8 MB), runs from the traced copy: 4.46 s cold, 3.45 s warm for one page at 2×; RSS 354–382 MB. `png.ts`'s header claims "the deployed runtime has none of them" (no canvas / sharp): that is a dependency statement, not a platform limit; whether Vercel's runtime loads the prebuilt `linux-x64-gnu` Skia binary is UNVERIFIED (the preview proves it).

### (d) What the code already has: `unpdf.extractImages` + `encodePng` + a route for uploads — works for this paper, not for vector figures; measured

No new dependency. Prototype `p9b25/proto-unpdf/extract.mjs` runs the figure-image route's own rule (largest raster ≥ 120 px, aspect ≤ 6, ≤ 12 Mpx) per page on the owner's paper. Result in §4: **a picture for all 10 figure pages**, at the **embedded resolution** (up to 2058×1612, no re-render, no crop). Limits that are the route's by design: a **vector** figure (a plot drawn as paths) has no raster and is missed; a figure made of several rasters returns only the largest; a page with two captions cannot be told apart (`reading.ts:625-640`); and it needs the upload wiring §5.3 anyway. As an engine for "the images" in general it does not reach what the owner asked for; as the no-licence-change first step it works today.

**Ruled out:** nothing is ruled out as impossible. (a) is dominated for the four reasons above; (c) and (d) are the AGPL-free fallbacks.

## 5. The recommendation

**Option (b): replace the Python helper with `mupdf@1.28.1`, in-process, inside the Node functions.** Why it decides: it is the helper's own engine, so the output on the owner's paper is the helper's output (12/12 captions identical, boxes ±1–2 px); it costs no more time than the helper (3.7–5.3 s against 5.0–6.4 s) and 12 MB per function; it needs **no second runtime, no HTTP hop, no 4.5 MB payload problem (the bytes never leave the function) and no dashboard setting**; and it runs under `next dev` and in this container with one `npm install`, so A's walks can finally *see* the figures, which (a) cannot give. Its one cost the others do not have is the AGPL question, shared with PyMuPDF (§3).

**If the owner will not accept the AGPL**: (d) is the no-new-dependency step that already gives all 10 figures of this paper (§4) once the upload wiring in §5.3 is done; (c) adds the vector figures at 4× the time and +38 MB per function, with a `serverExternalPackages` entry and an unverified native binary. Neither is as good; both are open to the manager.

### 5.1 Files a C changes

- `web/package.json`, `web/package-lock.json` — add `"mupdf": "1.28.1"` **exact** (1.28.1 already warns that the stext option `mediabox-clip` is deprecated in favour of `clip`; the API is young). After the install, check the lockfile's new `resolved` is `registry.npmjs.org` (three existing entries are not, BACKLOG-40).

### 5.4 Risks

- **Cold start**: +~1.0–1.2 s on the first request of a cold function (2.06 s cold against 0.89 s warm for a page render in the traced copy); the preview measures it on Vercel.
- **Size**: +12.1 MB per function that imports the engine (`/api/figure`, `/api/papers/report`, the figure-image route); against the platform limit (UNVERIFIED: I recall 250 MB for a Node function) that is small; (c) would be +38 MB.
- **Memory**: 150 MB for one figure, 266–279 MB for the whole 14.5 MB paper; a WASM heap grows and does not shrink inside a warm instance, and Fluid-style concurrency can run several extractions in one instance — hence the limit of 2.
- **No kill switch in-process.** The Python helper was killed at 25 s; a WASM call that hangs on a hostile PDF blocks its event loop until the function's own `maxDuration`. The existing caps (18 MB, 24 pages, 4.5 Mpx) bound it; a `worker_thread` gives a hard `terminate()` (measured, §2 (b)) at the price of ~0.5–0.7 s per call and the computed-path + `outputFileTracingIncludes` form; the C chooses and measures on the preview.
- **Inline `data:` URLs in the report**: the report's bound figures travel as `data:image/png;base64,…` (`report.ts:101`); 12 figures here are 8.9 MB; the non-streamed branch `NextResponse.json(bound)` (`report/route.ts:709`) meets the 4 MB body limit the repo itself cites (`upload-store.ts:235`) from about three figures on; the streamed NDJSON branch is probably not subject to it (UNVERIFIED). Check on the preview with a deep report on this paper; if it bites, `figureImageUrl` becomes the figure-image URL (a small change in `figure-binding.ts`), which §5.3 makes possible.
- **The port's boxes for curves**: on the synthetic curved chart the port's box ran +3% wide and +9% high against PyMuPDF's (a roomier crop, nothing cut); the cause is not isolated. The helper's rules (padding, caps) still bound every crop.
- **Licence**: §3; a decision before merge, not a technical risk.
- **A found-in-passing note, outside this item**: `vercel.json` with the cron sits at the repo root (`/vercel.json`), while the brief says the project's Root Directory is `web/`; I recall Vercel reads `vercel.json` from the Root Directory (UNVERIFIED) — the manager may want that checked against the purge-uploads cron.
