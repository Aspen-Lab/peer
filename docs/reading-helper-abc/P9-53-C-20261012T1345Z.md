## 2. The rules as built

**Rule 1: a bound figure of a PDF is its route URL.** `BindArgs.paper` is `{ title?, id? }`. `id` is the id of the PDF the captions and the pool were read from, and the route passes `body.paper.fullTextUploadId ?? body.paper.id`, the very id it already hands `getFullText` and `getFigurePool` at both call sites (the NDJSON stream and the JSON path), so the text, the pool and the URL name one PDF. A reader's attached PDF is named by its upload id (the figure route answers it to its owner only); a public paper by its own. `resolveImage` takes a fourth argument, `{ paperId, captions }` (null when there is no usable id), and when the conditions below hold it returns `imageUrl = pdfFigureUrl(paperId, page, N)` (imported from `reading.ts`, unchanged) in place of the pool entry's `data:` URL:
- the **number** N is what the section's label names ("Figure N", "Fig. N", "Fig N", "fig.N", any case; one to three digits, no leading zero), by a private copy of `reading.ts`'s `pictureNumber` (that one is not exported and the brief forbids touching it; a test pins that the reading and the binder offer a route URL for exactly the same twelve labels);
- the **page** is the `page` of the document's first caption whose own label names the same picture number (the one `placeFigures` places), which must have an integer page ≥ 1;
- the **id** is one the route can find: a canonical `upload:<hash16>` (`bareUploadId`) or `arxiv:` / `openalex:` (the two ids `fetchPaperById` looks up). A paper from another source (`semantic_scholar:`, `pubmed:`, `dblp:`, `hn:`, `web:`) has a report but no route, so its figures stay by value rather than turn into a 404; no id, an empty one, `UPLOAD:…` in capitals: today's behaviour.
Where any condition fails, today's behaviour stays: the pool's URL, or none. "Figure S3", "Figure 3b", "Figure IV", "Table 1": the pool's URL. Where the pool gave no entry (no pool, an empty pool), the section has a label and no picture, exactly as before: the set of sections that carry a figure is unchanged by this item.

**Rule 2: an HTML source's own picture stays.** The swap happens only where the pool's pick is a `data:image/` URL (the one thing the figure engine produces; an `https:` entry is an HTML or publisher picture) and only for a caption with no `imageUrl` of its own (the test `placeFigures` applies). A caption with no page (every HTML source) never reaches the route.

**Rule 3: the figure drawn is the same figure.** The swap happens only where the pool's pick is the figure the label names: the pool entry's caption opens the same figure number as the label (the pool's own `explicitFigureNumber` reading, so "Figure 2a" is not "Figure 2"). Where the pool had no such figure and picked by words (its Phase 2), the pick keeps its picture and its caption together, as before, because the route may not find what the pool could not. Where the swap happens, the route draws the region the pool drew: both call `extractPdfFigures` (same region finder, same renderer); the pool over the whole document's first 24 pages (12 figures), the route over the one page with the label. Shown below: byte for byte the same PNG, on a real PDF, in a test and on the dev server.

**Rule 4: nothing else changes.** `figureLabel`, `figureCaption` and `figureSource` are the pool entry's, as before (a test builds the report with and without the id and compares everything but the two URLs); the order, the shared-figure grouping (`allocateUniqueFigures`), the upload's owner-only rule (the route enforces it; the stream carries a URL, never the bytes) are untouched.

## 7. For the manager

1. **Only `arxiv:`, `openalex:` and canonical `upload:` ids get the route URL; every other source keeps its figures by value.** The figure-image route finds a public PDF through `fetchPaperById`, which knows those two prefixes; a `semantic_scholar:`, `pubmed:`, `dblp:`, `hn:` or `web:` paper has a deep report (the report route takes the links from the request) but the route would answer 404, so turning its figure into a route URL would lose the picture. They stay 1 MB a figure in the stream and cannot be reduced without a different mechanism (a figure store keyed by the report, or the route resolving from the request, which it must not: the address is the caller's). If the manager wants those too, that is a design decision, not a line.
2. **`pictureNumber` is copied, not imported** (it is private in `reading.ts`, which the brief forbids touching): 3 lines in `figure-binding.ts`, pinned to the reading's by the parity test over twelve labels. Exporting it from `reading.ts` and deleting the copy is a follow-up in a file that is not mine.
3. **Two choices where the brief was open, both toward "the set of sections that carry a figure does not change":** (a) with no pool entry for a section (pool failed, empty), the section keeps a label and no picture and the client falls back to the resolver, as before, instead of getting a route URL with no caption; (b) where the pool's pick is not the figure the label names (picked by words), the pick keeps its picture and caption. The brief's "whatever the pool would have given" can be read as (a) too; if the manager wants it, it is dropping the pool-entry condition in `resolveImage`, and the section would then carry a route URL with a null caption.
4. **Where the route and the pool can differ, when they are asked the same question:** the pool reads the first 24 pages and at most 12 figures, the route reads the one page named (up to 300). So a figure the pool missed is not swapped (rule 3), and a figure both have is drawn by the same code (shown byte for byte). A number repeated in the document (a "Figure 3" in a supplement) goes to the **first** caption's page, the one the reading places; the pool, which picks the highest quality among same-numbered entries, could in principle have drawn the other. For a **public** paper the route resolves its PDF with `fetchPaperById` + `getFullText` while the report used the links the client sent; they are the same links in practice (both come from the same paper), but not the same code path. A public answer is edge-cached for a day (`s-maxage=86400`); an upload's is `private, no-store`, one MuPDF render per request (measured 0.3 to 1.1 s on the owner's 19-page paper by P9-29; this item adds at most the proposal's and four results' pictures per report, drawn lazily by the browser as before).
5. **What a reload now draws, and one thing not looked at.** P9-48's `withoutFigureData` keeps any non-`data:` URL, so a new report is cached with its route URLs and a reload draws the same bound figure (P9-48's "For the manager" 1(a) is done; its option (b) is not needed for new reports). A report cached before this ships still has its `data:` figures dropped on its next write, and keeps the resolver's pick until it is regenerated. An upload's cached report holds an owner-only URL: once the upload expires (30 days) or the capability cookie is gone, the picture answers 404. I did not run a browser to see how each place that draws a bound figure (plate, proposal, results) shows a 404; `paper-plate.tsx` has an `onError` fallback, I did not read the others (not my files).
