## 1. Path enumeration — every place duplicates are detected or merged

Single pipeline, three files, one call chain. There is no other dedup/merge path in the codebase (grepped `web/src/lib` for `dedup`/`merge` — the only production clustering logic is this one).

1. **`web/src/lib/feed/dedup.ts`, `dedupItems()` (91-191)** — the only call site invoked from the feed pipeline. Builds one `CanonicalIdentity` per raw candidate (94, via `identityForRawItem`) and one `WorkMatchInput` per candidate (95-99: identity + `publishedYearOf(publishedAt)` + `firstAuthorSurnameOf(authors)`), then calls `clusterCanonicalWorks(matchInputs)` (101) to get the final partition. For each group of size > 1 it picks a survivor (103-111, by `SOURCE_PRIORITY` then id-form-key count then lexicographic id) and unions `mergedFrom`/`mergedAliases`/`admissionChannels` (113-189) onto it. **This file never compares two records directly** — all matching logic lives in file 3 below.

2. **`web/src/lib/utils/canonical-identity.ts`, `canonicalPaperKey()` (147-178)** — builds a record's identity: `key` = the first available id-form in priority order doi (148-149) → s2 (150) → openalex (151) → arxiv (152, version-suffix stripped) → pmid (153) → title (167), everything else becomes an `alias` (163-166). `normalizeDoi()` (82-91) lowercases and requires the CrossRef shape `10.NNNN/suffix`; it does **not** know about dual-edition journals — `10.1002/anie.5600863` and `10.1002/ange.5600863` normalize to two different, unrelated-looking `doi:` strings. `idFormKeys()` (194-203) is what pass-1 clustering unions on — it returns `key` + every non-`title:` alias.

3. **`web/src/lib/feed/paper-identity.ts`, `clusterCanonicalWorks()` (306-433)** — the actual matching engine, two passes:
   - **Pass 1, strong link (314-336)**: a plain O(n) union over `idFormKeys()` — any two records sharing a real id-form value (DOI, S2, OpenAlex, arXiv, PMID) are unioned transitively, no further checks. This is where a same-DOI or same-arXiv-id version pair merges today.
   - **Pass 2, weak link (338-430)**: pass-1 clusters (not raw records) are bucketed by shared `title:` alias (344-359), candidate cluster-pairs are tested by `weakPairMatch()` (150-163: normalized title equal AND a qualifying ≥4-token title alias AND same first-author surname AND published years within ±1), unioned into "components" (361-389) if ANY member pair matches — but a component only actually **collapses** into one final group if `clustersFullyMatch()` (211-218) returns true for **every pair of pass-1 clusters in the component**, checked over the full member cross-product (416-424, called from the component loop 410-430). One failing cross-cluster pair blocks the **whole component** — every pass-1 cluster in it becomes its own separate final group.

### The exact check that keeps W7213890479 and W7213912992 apart

It is **not** `weakPairMatch` between the two reported records. Reproduced by execution (see below): `clusterCanonicalWorks` given only these two records **merges them** — normalized titles are byte-identical, author arrays are byte-identical, `publishedAt` is byte-identical (`"2026-09-21"`), so `weakPairMatch` (paper-identity.ts:150-163) returns `true` for the pair.

The blocker is `clustersFullyMatch` (paper-identity.ts:211-218), invoked at 416-424. The real record W7213890479 carries `"metadata.mergedFrom":[{"source":"pubmed","id":"pubmed:42765143"}]` in the live response — proof that, in the real ~111-candidate pool this page was drawn from (`meta.beforeDedup:111` / `afterDedup:106`), W7213890479 was already pass-1-strong-linked to a PubMed record (call it X) inside the same `dedupItems()` call, before pass 2 ever ran. That makes W7213890479's pass-1 cluster `{openalex:W7213890479, pubmed:X}`, not a singleton. `clustersFullyMatch` then requires **both** cross-cluster pairs — (W7213890479, W7213912992) **and** (X, W7213912992) — to satisfy `weakPairMatch` before the component may collapse. The first pair passes (shown above); production's outcome (both cards shown separately) is only possible if the second pair, (X, W7213912992), fails — most likely because PubMed's own indexed title/date for X differs enough from the OpenAlex "ange" record's fields to miss the ≥4-qualifying-token title-alias-equality or exact-year-window test. **This last part is inferred, not directly observed**: fetching the real `pubmed:42765143` record was outside this investigation's allowed external calls (OpenAlex only), so X's exact fields were never read, and nothing was fabricated in their place — see the confound reproduction below, which uses a synthetic stand-in explicitly labelled as such.

## 2. Design options with costs

### (a) RECOMMENDED — finite dual-edition DOI-pair table, added as an extra alias in `canonicalPaperKey`

Add one small pure helper in `canonical-identity.ts`, e.g. `dualEditionDoiKey(doiValue: string): string | undefined`, backed by a finite, hardcoded table of `{registrant, codeA, codeB}` triples. For a normalized DOI matching `^10\.1002\/(anie|ange)\.(\d+)$`, it returns a shared synthetic id-form, e.g. `` `dual-edition:wiley-angewandte:${suffix}` ``, for **both** editions. Wire it in as one more entry pushed onto `idCandidates` inside `canonicalPaperKey` (147-178) — additive only: the real `doi:10.1002/anie...`/`doi:10.1002/ange...` values are kept exactly as they are today (still the `key`/still an alias, still used for survivor DOI backfill in dedup.ts:161-177), this just gives the two editions one more **shared** alias so pass-1 (paper-identity.ts:314-336) unions them transitively — the same, already-hardened code path that already merges e.g. two Zenodo DOIs sharing one arXiv id. **`clustersFullyMatch`/`weakPairMatch`/`clusterCanonicalWorks` are not touched at all.**
- Cost: one ~15-line pure helper + a 1-entry table + a 1-line call-site addition + tests. No change to the three-times-hardened weak-link/clustering code.
- Risk: very low. The table is an explicit whitelist of exact `(codeA, codeB)` pairs under one exact registrant, requiring the numeric suffix to match exactly — it cannot fire on two unrelated Wiley journals that happen to share a registrant (e.g. `10.1002/adma.100000` vs `10.1002/smll.100000` never match: the codes `adma`/`smll` are not in the table).
- Also fixes P4 delivery-exclusion for free (isDeliveredIdentity reads the same aliases, canonical-identity.ts:180-191/28-31) — a user who already saw the anie edition won't be re-shown the ange edition later.
- Limitation, accepted: a suffix with a trailing letter (e.g. a supporting-information DOI) would not match `\d+$` and stays unmerged — safe-direction failure, not a false merge.

### (b) Title + full author list + exact date, DOI never consulted (as literally specified)

Two readings:
- **(b-i) Tighten `weakPairMatch` itself** (full author-array equality + exact date instead of first-author-surname + ±1 year): **does not fix this bug**. Proven above that the existing, looser `weakPairMatch` already returns `true` for the real A/B pair — the pairwise rule was never the problem. Tightening it only shrinks what pass-2 will ever consider, it doesn't touch `clustersFullyMatch`'s all-cross-pairs requirement that actually blocks the merge.
- **(b-ii) Promote an exact (title, full author list, exact date) match to a new strong-link-style alias**, mechanically identical to option (a) but with a general content-hash trigger (e.g. `` `content-hash:${sha1(normalizedTitle+'|'+authors.join('|')+'|'+publishedAt)}` ``) instead of a DOI lookup table. This **would** fix the reported bug (same additive mechanism as (a)) and generalizes to any future publisher doing the same dual-DOI trick, not just Wiley.
- Cost of (b-ii): similar shape to (a) (one helper, one call-site addition, tests), but the trigger condition is broader — it fires on every record, not just DOIs matching a known table, so it deserves more adversarial testing before shipping (same class of review DEDUP-FIX3 needed: same-author consecutive-year same-title pairs, hub/bystander cases already covered by the pass-1/pass-2 split still need re-confirming against this new alias path).
- Risk: low but higher than (a) — exact title AND exact full author list AND exact date is a strict AND, but it is a **general** trigger with no publisher-specific guardrail, so it is one step closer to the shape of false-merge DEDUP-FIX/FIX2 already got burned by twice. Recommend as a **follow-up**, after (a) ships and is proven, not as the first fix.

### (c) Other options considered and rejected

- **Loosen `clustersFullyMatch` to only require the originally-linking pair to match** (i.e. go back to per-anchor matching): rejected outright — this is exactly the "hub" false-merge shape (`{P1,P2}` sharing a DOI despite unrelated titles, pulled together with an unrelated `Z`) that DEDUP-FIX2's own review caught and DEDUP-FIX3 was built specifically to close (paper-identity.ts:250-295's worked example). Do not touch this function's semantics again outside a full, independently-reviewed round like DEDUP-FIX3's own 41-case adversarial suite.
- **Strip any alphabetic journal-code segment from any DOI suffix generically**: rejected — this is the dangerous generalization of (a); it would treat `10.1002/adma.100000` and `10.1002/smll.100000` as the same work purely by coincidence of numeric suffix. Only ship a finite, explicit table.

### What must never merge

Two genuinely different papers that happen to share a title-alias bucket or a coincidental DOI-suffix number. Concretely: (1) two unrelated Wiley papers in different journals sharing a registrant and a coincidental numeric suffix (option (a)'s table guards this by requiring the exact `{anie,ange}` code pair); (2) an erratum/correction/retraction notice that repeats the original title verbatim but was published on a different date (both options require exact date equality, which protects this — confirmed no such case exists in the measured data, §3); (3) the pre-existing, already-accepted DEDUP-FIX3 cost, unchanged by either option: two distinct same-author papers sharing an identical long title in two different years within the ±1 window.
