## Check 2 — Regex reach (false-merge surface)

Pattern (canonical-identity.ts:100): `const DUAL_EDITION_DOI_RE = /^10\.1002\/ange\.(\d+)$/;` — applied only to `doiValue`, the return of `normalizeDoi()`, never to the raw input string directly.

`normalizeDoi()` (same file, 124-133) already: trims -> strips a `doi:`/`https?://(dx.)doi.org/` prefix (case-insensitive) -> lowercases -> requires the whole string to match `^10\.\d{4,9}\/\S+$` or returns `undefined`. So by the time `dualEditionDoiAlias` runs, case and URL-form/`doi:`-prefix variants are already collapsed — I traced this by hand and confirm it is correct, not merely asserted:
- `10.1002/ANGE.5600863`, `doi:10.1002/Ange.5600863`, `https://doi.org/10.1002/ange.5600863`, `http://dx.doi.org/10.1002/ANGE.5600863` all normalize to the identical `10.1002/ange.5600863` before the alias regex ever sees them — one test (`canonical-identity.test.ts`, "case/prefix-insensitivity") covers the URL+uppercase combination; I additionally hand-traced the `dx.doi.org` and bare `doi:` prefix cases through `DOI_PREFIX_RE` myself since no test exercises those two specifically — both strip correctly.
- Other 10.1002 journal codes containing "ange" as a substring: the pattern is fully anchored (`^...$`) with a literal `/ange.` segment, so `10.1002/orange.N` (tested), `10.1002/angew.N` (an alphabetic char immediately after "ange" where the regex needs a literal `.`) and `10.1002/langer.N` all fail to match — confirmed by hand-tracing the regex engine (anchored, no wildcard before or inside "ange", so there is no other position for it to retry). Only C's "orange" case is asserted in a test; "angew"/other adjacent codes are not asserted, but the regex mechanics make them unreachable by construction, not by convention.
- Non-1002 registrant: `10.9999/ange.N` correctly excluded (tested; also my own trace).
- Trailing-letter/compound suffix (e.g. supporting-info DOI `10.1002/ange.5600863.s1`, or a hypothetical `...5600863a`): `(\d+)$` requires the string to end on a digit, so both fail to match — tested (`...s1` case) and hand-traced for the bare-trailing-letter shape. This is a safe-direction miss (stays unmerged), not a false merge, exactly as documented.
- No case found, by construction or by test, where two DIFFERENT real papers (different numeric suffix under 10.1002/ange or 10.1002/anie) could collide — the alias is keyed on the exact captured suffix digits, so it is precise per-article, not a blanket journal-level rule.

One thing I could not independently verify (flagged, not a defect): whether Wiley's `ange.<N>`/`anie.<N>` numeric suffix is ALWAYS an exact match between an article's two editions with no exceptions across the journal's history (e.g., an older or irregular DOI scheme). B's investigation flagged the same limit (OpenAlex verification call 400'd, 9/10 allowed calls unspent) and I had no additional external-call budget to check further (already used both of my ≤2 allowed local calls elsewhere — see Check 7). This is a real, inherited unknown, not a new gap I introduced. Given the pattern requires an EXACT suffix match plus the exact `{anie,ange}` code pair under one exact registrant, the worst case of this unknown is a safe-direction miss (an edition pair that doesn't share a literal numeric suffix stays unmerged), not a false merge — consistent with every other edge case above.

Verdict: LOW. The regex's reach is exactly what C and B claim: precise, anchored, cannot false-merge two different papers by construction. The one open unknown (suffix-matching reliability across Wiley's full historical DOI scheme) is inherited from B's investigation, already accepted by the manager's ruling ("Entries are added only with real evidence... no research pass now"), and fails safe in every case I could construct.
