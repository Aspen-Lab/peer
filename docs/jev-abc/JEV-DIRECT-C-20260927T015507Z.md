## HOW THE USER RUNS THE JEV SMOKE TEST LATER

Nobody ran the smoke test live this round — it is built, unit-tested with fakes, and its environment isolation is proven, but it has never made a real call. To actually run it once you are ready and have stated a Jev budget in chat (ABC-JEV-INTEGRATION.md §1aa point 6):

1. **One line in `web/.env.local`** (create the file if it does not exist yet; never commit it):
   `JEV_API_KEY=<your real Jev key>`
   Nothing else is required — `PEER_RUN_JEV_SMOKE` is set automatically by the command below, not by you.

2. **The command**, run from `web/`:
   `npm run test:jev-smoke`

3. **What a pass looks like:** the command exits 0 and prints a normal vitest summary (1 test file, 1 test, passed). The real evidence is written to `web/output/jev-smoke/<a timestamp>/` — a `summary.json` listing all 4 fixed inputs with their status, latency, and (for a successful call) the model id Jev echoed back, plus one JSON file per input with the same detail. This folder is already excluded from git (the repo's `.gitignore` already covers `/output/` and `/web/output/`), so it never gets committed by accident.

4. **What a contract mismatch looks like:** any input whose `status` in `summary.json` is something other than `"ok"` — most informatively `"invalid_response"`, which comes with a `detail` sentence naming exactly which check failed (e.g. a model-id mismatch, or an answer shape Jev's real response didn't match). This is not a crash and the command still exits 0 — the whole point of this runner is to surface a mismatch clearly in the written files, not to fail loudly or assume success. A `"rate_limited"`/`"overloaded"`/`"timeout"`/`"network_error"` status is an ordinary network/availability hiccup, not a contract problem.

5. **The cost ceiling:** a hard ceiling of 10 attempts (only 4 will actually run today, since there are only 4 fixed inputs). Using Jev's own published price ($0.042 per 1,000,000 input tokens, output free) and its documented 32,000-token worst-case request size, a full 10-call run costs at most about **$0.013** — in practice, with these short synthetic inputs, more like **one to six hundredths of a cent total**. The ceiling exists to bound an accidental repeated/looped run, not because one run could plausibly cost anything worth budgeting.

### Design decisions beyond the guide's literal text (recorded for the reviewing A)

The guide's §3/§"Deliverable" left the exact caps/transport plumbing through
`shadow.ts`/`route.ts` to C ("hook-input plumbing" — its own words). Read the
full source of `shadow.ts`, `shadow.test.ts`, `route.ts`'s gate, and
`flag.ts` before deciding these; none change a cap VALUE, the reservation
order, the shadow eligibility conditions, or the broker wire contract — they
only decide how the (unchanged) caps/transport reach a second transport.
Judged as in-scope generalization, not a POLICY stop, because:

1. **Found during implementation, not anticipated by the guide:** the
   `server-only` package's `package.json` picks its no-op `empty.js` under
   Next's own `"react-server"` build condition and its throwing `index.js`
   under every other condition (including plain Node/vitest, which has no
   such condition). Without a fix, importing `jev-direct-client.ts` under
   `npx vitest run` throws immediately ("This module cannot be imported from
   a Client Component module...") even though vitest's `environment: "node"`
   is server-equivalent. Fixed with one line in `vitest.shared.ts`'s
   `resolve.alias` (`"server-only" -> node_modules/server-only/empty.js`) —
   applies uniformly to every vitest config (default, live-channels, the new
   smoke config), touches no test file, and does not affect Next's own real
   build (which resolves this package itself, independently of vitest).
   Verified immediately after adding it: full `npx vitest run` still 262
   files / 4784 passed + 5 skipped (261/4751/5 baseline + this item's 33
   cases at that point) — zero collateral change to any pre-existing test.
2. **`readJevCaps()` (new, additive, in `flag.ts`).** `readJevShadowConfig()`
   only returns caps bundled INSIDE its `"configured"` branch, which requires
   the broker URL+secret env vars to be set. A direct-only deployment (key in
   Vercel, broker URL/secret never set) would then have NO way to read the
   real caps for its hook input, and the hook would silently never build —
   defeating JEV-DIRECT's whole point. `readJevCaps()` parses the same two
   cap env vars with the same `parseCap` fallback, independent of broker
   config. `readJevShadowConfig()` itself is untouched (still used verbatim
   for the broker's URL/secret when transport is `"broker"`).
3. **`dispatchJevCall`'s `transport` is a REQUIRED input field, not
   self-resolved via a fresh `resolveJevTransport()` call inside
   `jev-dispatch.ts`.** Reason, found by reading `shadow.test.ts`:
   ~30 existing green cases set `PEER_JEV_BROKER=on` and pass `brokerUrl`/
   `brokerSecret` as plain function options, but NEVER set
   `PEER_JEV_BROKER_URL`/`PEER_JEV_BROKER_SECRET` as environment variables
   (today, only `route.ts`, via `readJevShadowConfig()`, ever reads those two
   names — `broker-client.ts`/`shadow.ts` never have). If dispatch re-derived
   transport from env internally, every one of those cases would flip to
   `"disabled"` (no key, and `readJevShadowConfig()` would report
   `"unconfigured"`), breaking ~30 verified tests for no reason tied to this
   item. So `route.ts` resolves transport ONCE (`resolveJevTransport()`,
   already needed for the gate condition) and threads it down through
   `JevShadowHookInput` -> `ShadowRunnerOptions.transport` ->
   `dispatchJevCall`'s options, exactly like `entitled`/the caps already are.
   This also preserves `shadow.ts`'s own documented invariant ("never reads
   process.env itself... resolved by flag.ts and handed in by the caller").
4. **`JevShadowHookInput` (route.ts) drops its `config: Extract<JevShadowConfig,
   {status:"configured"}>` field** for flattened `transport`/`perUserCap`/
   `globalCap`/`brokerUrl?`/`brokerSecret?` fields, and the gate no longer
   requires `readJevShadowConfig().status === "configured"` before building
   the hook (that check only makes sense for the broker transport; requiring
   it unconditionally would block every direct-only deployment). `resolveJevTransport()
   !== "disabled"` replaces `jevBrokerEnabled()` as the one changed condition
   among the existing 7; the other 6 are byte-identical.
5. **P4 alias placement:** `export type JevCallResult = BrokerCallResult;`
   is added in `jev-dispatch.ts`, NOT in `broker-client.ts` — `broker-client.ts`
   already imports the name `JevCallResult` (unaliased) from `jev-client.ts`
   for its own `BrokerCallResult` union, so declaring a second, different
   `JevCallResult` there would be a duplicate-identifier compile error.
   `jev-dispatch.ts` never imports `jev-client.ts`'s `JevCallResult` by that
   name, so no collision. Comment at the alias site warns a future reader
   that `jev-client.ts` separately exports its OWN, narrower `JevCallResult`
   (the raw Jev fault-table type, no `disabled`/`not_entitled`/
   `reservation_refused`) — never import both unaliased in the same file.
6. **`evaluation/jev-smoke/gate.ts`'s `credentialPresence()` delegates to
   `jevDirectConfigured()`** (`decisions/jev-direct-client.ts`) instead of
   reading `process.env.JEV_API_KEY` itself, even though the guide's own §7
   text describes a direct one-line read (mirroring the S2/OpenAlex gate's
   own pattern literally). Reading it directly here would have made TWO
   files read the name, breaking this same item's own placement scan
   (`spend-scans.test.ts` "scan 7": exactly one file). Delegating returns the
   identical boolean with no drift risk and keeps that invariant intact.
