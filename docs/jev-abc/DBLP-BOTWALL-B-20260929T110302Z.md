## 3. Cost today

- **Latency per pool build:** ~0. dblp's own queries run concurrently with each other (`Promise.allSettled` inside `fetchImpl`) and concurrently with every other source (the outer `Promise.allSettled` in `buildPaperPool`). At ~0.6s per call, dblp settles well before the 6s/8s walls and well before slower sources (web search, up to 25s). The cost is wasted work, not added wait.
- **Wasted calls:** 2 calls per build at ≤2 Required tags, rising to 5 at ≥5 tags (`effectiveQueryCap`) — all guaranteed to fail. Add up to 3 more retry rounds per local day (30 minutes apart, only ever triggered by an actual reader's feed read landing after the window — not a background cron), each re-spending the same 2–5 calls: up to ~20 wasted HTTPS round trips per distinct reader-profile-day, every day, for as long as the wall is up. `sourceFetch`'s `revalidate: 900` (15-minute Next fetch-cache hint) does not meaningfully reduce this: queries within one build are already deduped by the adapter itself, and retries are spaced 30 minutes apart — longer than the 15-minute cache window — so each retry round is a fresh set of real outbound calls regardless. Neither observation GET was rate-limited (no 429), so there is no evidence of ban risk from this volume — it is pure waste, not a risk multiplier.
- **Noise in logs/diagnostics:** one `console.error("[dblp] fetch error: ...")` per failed query (2–5 per build/retry round) carrying a raw JSON-parse `SyntaxError` message, not one that names the real cause. `meta.errors.dblp` in the raw `/api/feed` JSON repeats the same cryptic message to anyone probing the API directly — every manual academic-source census a reviewer runs (e.g. this loop's own "signed-out controls" checks) has to mentally discount dblp's line every time.
- **Reader impact:** none directly, confirmed in §1 — the product cost is strictly "one fewer source's worth of candidates per pool." dblp's actual contribution volume while healthy was not measured here (out of scope, and not comparable since dblp has been down since 2026-09-28).

## 4. Design options with costs

**Option A — detect the non-JSON response, fail fast/honest, no parse attempt. (Recommended.)**
In `fetchOne()`, check `res.headers.get("content-type")` before calling `res.json()`; if it does not include `"json"`, throw a purpose-built error immediately (e.g. `dblp HTTP 200 but content-type "text/html" — not JSON (likely a bot/anti-automation challenge page)`) instead of letting `res.json()` throw its own cryptic `SyntaxError`.
- *Cost to build:* minutes — one content-type check, no new state, no new imports.
- *Effect:* identical outcome to today (throws → `sourceStatus.dblp = "failed"` → `fetched.dblp = 0`, the existing P2-S2 contract preserved exactly) but with an honest, specific message, and zero attempted parse work on a body already known to be wrong.
- *Does not* reduce the wasted-call count (still 2–5 HTTPS round trips per build/retry) — only makes the already-correct failure detection cheaper and clearer.
- Nothing else changes: `MAX_QUERIES`/`RISE_CEILING`/`effectiveQueryCap`, the retry system, the cache contract, and every other adapter are untouched.

**Option B — a short circuit-breaker so a confirmed-bad source is skipped for a while.**
Once Option A's content-type check recognizes a bot-wall-shaped response, store a longer dblp-specific cool-down (e.g. skip real fetch attempts for N hours) instead of relying on the existing 30-minute/3-per-day self-heal cadence.
- *Cost to build:* moderate — new persisted state (or repurposed `SourceStatusEntry` fields), a scope decision (per-pool like today's retry counter, vs. global/cross-profile so one detection protects every reader's build that day), and new boundary tests.
- *Benefit:* cuts wasted calls roughly in proportion to how much longer the cooldown is than today's cadence (e.g. a 24h global breaker could push dblp's daily call volume across all readers to near-zero after the day's first detection).
- *Risk:* over-engineering for a currently small, unthrottled waste (§3); too long a cooldown delays noticing dblp's own recovery unless paired with an occasional real probe.

**Option C — an honest source-status surface for the reader.**
Show "dblp unavailable" somewhere a reader sees it, wired to the `sourceStatus`/`meta.errors` data that already exists.
- *Cost:* this is a new UI feature, not a bug fix — §1 confirmed nothing today reads this data outside logs and raw API probes. Real product-design + UI work, well beyond this item's scope. Not recommended as part of this fix.

**Option D — remove dblp from the default source mix.**
Drop `"dblp"` from `ACADEMIC_PAPER_SOURCES` (`pipeline.ts:63–69`).
- *Cost to build:* trivial (one line), but it is a product/coverage decision, not a mechanical one: it silently drops whatever unique candidates dblp contributes when healthy, and — unlike A/B — Peer would never self-detect dblp's recovery; a human would have to notice and manually re-add it.
- Zero wasted calls, zero log noise, immediate — the strongest cost-cutter of the four, traded for coverage + a manual re-enable step later.

**Recommendation: ship Option A now. Options B and D are manager POLICY calls (§5), not bundled into this fix.** Option A is the minimal, safe change that delivers exactly the "fast, honest, no parse attempt" goal, fully honors the HARD RULE (identical request shape — it only reads the response more cheaply and honestly), and touches only `dblp.ts`'s own failure path.
**What must not change for the other sources:** `openalex.ts`, `semantic-scholar.ts`, `arxiv.ts`, `pubmed.ts`, `web-search.ts`, `hn.ts` keep their own parse/error logic untouched; `sourceFetch`/`searchHttpFailure`/`collectSearchResults` keep their current signatures; `pipeline.ts`'s `sourceStatus`/retry/cache contract (`SOURCE_RETRY_INTERVAL_MS`, `MAX_SOURCE_RETRIES_PER_DAY`) is unchanged unless the manager separately authorizes Option B.
