## 0. MANAGER UPDATE FOLD-IN — live server log, every PUT /api/profile → 409 (2026-09-28)

The manager's new evidence: the local dev server log shows 6 consecutive `PUT /api/profile` calls from the user's signed-in browser, all returning HTTP 409, browser console `[ProfileSync] PUT failed ApiError: PUT /api/profile → HTTP 409`. Traced to ground:

**Root cause, exact.** `web/src/app/api/profile/route.ts` `PUT` handler (lines 250-354) builds `row` via `profilePatchToRow(body, user.id)` (line 309), then does one `upsert`. If `row.feed_intent` is present and the DB lacks that column, `isMissingFeedIntentColumn(error)` (line 154) is true and the handler returns 409 `feed_intent_schema_unavailable` **immediately, with no retry** (line 317-319). Contrast with the two branches right below it: the `digest_email` (line 324-331) and `preference_ledger` (line 333-340) missing-column cases each `delete row.<field>` and **retry the same upsert** — so the rest of the row still saves. `feed_intent` is the only optional-column case that hard-fails the *entire* write instead of degrading gracefully.

Why this fires on **every** real push, not an edge case: `remoteProfilePayload` (`web/src/components/profile-sync.tsx` lines 118-132) always sets `feedIntent: profileFeedIntentCard(profile)` when that function returns non-undefined, and `profileFeedIntentCard` (`web/src/lib/feed/intent.ts` line 239) returns a real card whenever the profile has *any* of `currentProject`, `currentChallenges`, `researchTopics`, `preferredMethods`, or `softTopics` set — i.e. whenever the profile has the kind of content this user reported having. So the same PUT body that would carry the user's real fields also always carries `feedIntent`, and the whole upsert dies, atomically, before any column is written (an upsert that errors writes nothing — Postgres/PostgREST do not partially apply a failed statement).

Confirms the user's Supabase project has never had `web/supabase/migrations/20260922010000_profile_feed_intent.sql` applied (schema.sql itself has no `feed_intent` column — it was added later, in that dated migration).

**Manager's four questions, answered:**

**(1) How does ProfileSync behave after a failed PUT?** No retry logic exists anywhere in the push path. `pushRemote` (profile-sync.tsx lines 151-163) catches, `console.warn`s, and returns `false`; on `false` the caller (both the sign-in-time push and the debounced steady-state push, lines 244-245 and 289-296) simply does **not** advance `lastPushedRef.current`. Because `lastPushedRef.current` stays `null` forever, `diffPayload(next, null)` (line 138-139: `if (!baseline) return next;`) keeps returning the *entire* current payload on every subsequent profile change, so every further edit re-attempts a full push — and 409s again, forever, silently (`console.warn` only; nothing reaches the UI). This is the mechanism behind "6 times" in the log. **A later GET does not overwrite local data in this specific failure mode** — see (2).

**(2) Is the wipe the GET/merge, the failed PUT, or both — and for which data kind?** For **profile fields**, under this exact bug, neither destroys the browser's own copy. Trace: `hasAnySignal(local)` on the user's real local profile is `true` (they had real fields), so the sign-in effect (profile-sync.tsx lines 241-246) takes the "server empty → push local" branch, not the "hydrate from remote" branch — `hydrateFromRemote` (which *would* overwrite local fields) is never called for this user, because the server row never accumulates any of the six fields `hasAnySignal` checks (`researchTopics`/`preferredMethods`/`locationPreferences`/`currentProject`/`currentChallenges`/`feedIntent` — see §3 for why the row stays at defaults). So: **the account stays permanently empty (nothing the manager's evidence shows destroys the browser's own `peer-profile` localStorage copy)** — the correct framing is "nothing is reaching the account," not "the local copy was overwritten." That said, §3 below documents a separate, provable latent defect in the same merge boundary that *would* overwrite local fields once the server row ever does acquire signal by any means (a later device, or a partial fix) — this is exactly what §4a's merge-rule redesign must close, independent of the 409 bug.
For **saved papers / reading history / feedback**, the mechanism is different and *does* directly overwrite the browser's own copy — see §1.2/§1.3 below; that defect fires on ANY silently-failed push-or-pull for that data kind, migration-column issues or otherwise, and is not mitigated by anything in profile-sync.tsx.

**(3) What must the fix guarantee while the column is missing?** Two independent guarantees:
- *Correctness*: `PUT /api/profile`'s `feed_intent`-missing branch must degrade like its two siblings — strip `feed_intent` from `row` and retry the same upsert — so `research_topics`, `current_project`, `digest_*`, etc. (all set independently of `feed_intent` in `profilePatchToRow`, lines 111-152) still reach the account even when this column is absent. This is a small, precedented change (mirrors the existing `digest_email`/`preference_ledger` branches) and is the single highest-leverage fix available before the migration is even applied.
- *Honesty*: a failed push must become visible to the user, not just a `console.warn`. Nothing today tells the user "your changes are not saved to your account." This is required independent of the specific 409 cause, per §4a/§5.

**(4) Dependency on the migration.** Confirmed: the merge/restore design in §4 only reaches the account once pushes actually succeed. Recommend **both**: (a) the user applies `20260922010000_profile_feed_intent.sql` now (the manager is already asking), and (b) C ships the graceful-degradation fix in (3) regardless, so the flat legacy columns sync even for any user whose project lags a future optional-column migration — this class of bug (client sends a field the DB doesn't have yet) will recur with every future optional column unless the pattern is made uniform. ## 1. Sign-in path, per data kind

### 1.1 Profile (research topics, current project/challenges, career fields, digest prefs, color theme, etc.)

File/function: `web/src/components/profile-sync.tsx`, the `onSession` closure (lines 196-263), gated by `hasAnySignal` (lines 72-81) and `web/src/store/profile.ts`'s `hydrateFromRemote` (lines 706-756).

Exact behavior at sign-in:
1. `fetchRemote()` → `GET /api/profile`. `web/src/app/api/profile/route.ts` `GET` (lines 163-209) does `.maybeSingle()` against `profiles` — **it does not create a row**; if no row exists it returns `{ profile: null }`. (A row does already exist by the time this runs, for every user — see §3, the `on_auth_user_created` trigger.)
2. `const local = useProfileStore.getState().profile` — the in-memory profile, which is the rehydrated `peer-profile` localStorage copy once `<StoreHydrator/>` (`web/src/components/store-hydrator.tsx`) has run its `useProfileStore.persist.rehydrate()` effect (the store uses `skipHydration: true`, so this is a distinct, unordered-relative-to-ProfileSync effect on the same mount — see §3 for the race this can open).
3. Decision: `if (!remote || !hasAnySignal({ ...local, ...remote }))` → **push local up** (`remoteProfilePayload(local)` via `PUT`). Else → **`hydrateFromRemote(remote)`: server wins on every field it defines** (`!== undefined`, not "non-empty").
4. **Provable defect in the decision boundary itself**, independent of the 409 bug: `profileRowToProfile` (route.ts lines 63-109) always returns an object literal with all six of `hasAnySignal`'s checked keys present as *own properties*, even when their value is `undefined` (e.g. `currentProject: ... ?? undefined`). Object spread copies own properties regardless of value, so `{ ...local, ...remote }` always ends up with `merged.currentProject === remote.currentProject`, `merged.researchTopics === remote.researchTopics`, etc. — **local's values for exactly the six checked fields are unconditionally clobbered by remote's before the check runs.** `hasAnySignal({...local, ...remote})` is therefore always mathematically equal to `hasAnySignal(remote)` alone; the merge-with-local inside the *condition* can never detect "local has signal remote lacks." Once the server row acquires *any* of those six fields by any means (a fixed push, a different device, a future partial-degradation retry), a fresh mount on a device whose local copy has independent, newer, or richer data will take the `hydrateFromRemote(remote)` branch and that function's own logic is a per-field "install if defined" (lines 706-756), not a merge — so local values genuinely get overwritten by whatever the server has, even if it's a worse/older/emptier value than what's on this browser (e.g. remote's `researchTopics: []` from a legitimate empty push replaces a local, populated array the moment `merged.currentProject !== undefined` happens to be true for an unrelated reason). **This is the mechanism §4a's redesign must close for the general case.**

### 1.2 Saved papers (`savedPapers`/`savedEvents`/`savedJobs`)

Files/functions: `web/src/components/feed-sync.tsx` `onSession` (lines 104-152), `web/src/store/feed.ts` `hydrateFromRemote` (lines 2344-2431), `web/src/lib/feed/session-step.ts` `sessionStep`.

Exact behavior at sign-in (`sessionStep` returns `"sync"` for a first-time local-only browser signing in, since `syncedUserId` is `null` and `signedOut` is false — confirmed by reading `session-step.ts` lines 45-57; `"reset"`/`"reset-then-sync"` do not apply here):
1. Push every local item up first (`pushSaved`/`pushRead` for each entry in `local.savedPapers`/`savedEvents`/`savedJobs`/`readItems`, lines 122-127) — each call independently wrapped in try/catch, failures `console.warn`-only, **`Promise.allSettled` result is never inspected** (line 127).
2. Pull `fetchSaved()`/`fetchRead()` (lines 36-58) — each returns `null` on **any** failure (network, 500, missing table).
3. `savedRows ?? []` / `readRows ?? []` (lines 135, 141) — **collapses "the request failed" and "the server legitimately has zero rows" into the same empty array**, before `hydrateFromRemote` ever sees the difference.
4. `useFeedStore.getState().hydrateFromRemote({ savedPapers, savedEvents, savedJobs, readItems })` is called **unconditionally**, always with concrete (possibly-empty) arrays, never `undefined`.
5. Inside `hydrateFromRemote` (feed.ts): `const nextSavedPapers = remote.savedPapers ?? s.savedPapers;` (line 2346) — this fallback to `s.savedPapers` (keep local) can only fire when `remote.savedPapers` is literally `undefined`. Because step 3/4 never passes `undefined` — it always passes at least `[]` — **this fallback can never actually engage from this caller.** The result: `savedPapers`/`savedEvents`/`savedJobs`/`readItems` are unconditionally replaced by whatever the pull returned, including an empty result caused purely by a failed request.

**This is a real, direct, unconditional local-overwrite mechanism — a different and more serious defect than the profile one (1.1), independently sufficient to explain "previously saved papers were gone" the instant sign-in completes, regardless of which specific server-side error caused the push or pull to fail.** I do not have log access to confirm the exact HTTP status `/api/saved`/`/api/read` returned for this user's session (no live calls, no log-reading tool available to me) — recommend the manager/C check the dev server log for those two routes the same way it was checked for `/api/profile`. Plausible trigger, by analogy with §0: this user's Supabase project may predate commit `653d0d4b` (which added the `saved_items`/`read_items` tables directly into `schema.sql`, not a dated migration) — if their `schema.sql` run was older, those tables simply don't exist, and `POST`/`GET /api/saved`/`/api/read` (`web/src/app/api/saved/route.ts` lines 29-37, 68-80) 500 on every call, silently swallowed exactly as traced above.

Note: `web/src/store/feed.ts`'s `resolveOwnerKeyForLoad`/`ANONYMOUS_OWNER_KEY` (lines 235-337) — the only owner-keyed local storage in this file — governs the **delivered-batch anti-redelivery ledger** (`deliveredLocalByOwner`), a different concern (which papers have already been shown, so they're never redelivered). **`savedPapers`/`savedEvents`/`savedJobs`/`readItems`/`paperFeedback`/`eventFeedback`/`jobFeedback` are NOT owner-keyed** — there is exactly one copy of each in the `peer-feed` store, and switching from anonymous to signed-in reuses and overwrites that same copy via `hydrateFromRemote`. So the task's "hidden under a different owner key" possibility does **not** apply to saved papers/reading history/feedback — it is simpler and more destructive than hiding: there is only one bucket, and it gets replaced.

## 3. Why the account came back empty

**Schema/trigger** (`web/supabase/schema.sql` lines 58-76): `handle_new_user()` (`security definer`) runs `insert into public.profiles (user_id) values (new.id) on conflict (user_id) do nothing;` on an `after insert on auth.users` trigger (`on_auth_user_created`). So a `profiles` row is created **the moment the GitHub OAuth exchange creates the `auth.users` row** — before the client ever calls `GET /api/profile` — with every other column at its SQL default: `research_topics`/`preferred_methods`/`location_preferences`/`authorised_countries`/`disliked_topics` default `'{}'` (empty array, NOT NULL — schema.sql lines 9-13, 92); `current_project`/`current_challenges` have **no default**, i.e. SQL `NULL` (lines 84-85); `digest_*`/`feed_*`/`color_theme` all have real non-null defaults (lines 104-137, e.g. `digest_enabled default true`).

**Client logic on top of that** (`profileRowToProfile`, route.ts lines 63-109): `current_project`/`current_challenges` map `null ?? undefined` → `undefined`; the array columns map straight through (`[]`, defined, not undefined). Feeding this into `hasAnySignal` (§1.1) evaluates to `false` for a genuinely fresh row — so, **absent the 409 bug**, the architecture's intent is correct for a true first sign-in (push local up). The account came back empty here specifically because §0's bug means the push that *should* have populated the row on this user's very first sign-in has been failing (409) on every attempt since — the row is not "empty by design," it is "empty because nothing has ever successfully written to it." Once the graceful-degradation fix (§0(3)) or the migration lands, the very next successful push will populate it — provided the local browser copy is still intact (§2) and the general merge-boundary defect (§1.1's point 4) does not get triggered by some other device or partial state in the meantime.

## 4. Design (the fix)

### 4a. First sign-in must carry local data into the account — merge rules

**POLICY — manager decides**, proposed by B:

- **P1 (profile scalar/list-field merge).** Replace the current "any of six fields defined on remote ⇒ install every field remote defines" boundary with a genuine per-field rule:
  - *Account has no real data yet* (the current true-empty-row case) → push local wholesale, as today's "if" branch already intends.
  - *Both sides have independent real data* (returning user on a second device, or a local edit made while a push was failing) — **list fields** (`researchTopics`, `softTopics`, `preferredMethods`, `locationPreferences`, `authorisedCountries`, `dislikedTopics`, `preferredJournals`) → **union, deduped**, never drop either side's entries. **`preferenceLedger`** → merge per concept-key; POLICY: for a key present on both sides with different counts, sum the decayed evidence or keep the higher confidence value — needs a manager ruling, not a B guess. **Single-value fields** (`currentProject`, `currentChallenges`, `displayName`, `careerStage`, `industryVsAcademia`, `school`, `phdYear`, `advisorName`, `colorTheme`, `digestHourLocal`/`Timezone`/`Channel`/`Frequency`/`Email`) — POLICY: on a genuine conflict (both non-empty, different), does local (the device the user is looking at right now) win once at merge time, or does the manager want a "most recently edited" rule (would need a client-side per-field or per-profile edit timestamp that does not exist today — `updated_at` is a DB-side, row-level touch, not usable to compare against a local edit)? B's recommendation: local wins on this one-time sign-in reconciliation only; ongoing steady-state after that is naturally "last device to edit wins" via the existing debounced push.
  - **Credentials** (`tavilyApiKey`, `adzunaAppId`, `adzunaAppKey`, `usajobsApiKey`, `usajobsUserAgent`, `feedAiApiKey`, `feedAiProvider`) are local-only by design and the server never holds them (see §4b) — never part of any merge direction, never pushed, never pulled.
  - `feedIntent` — recompute from the merged flat fields after the merge rather than merging the nested structure directly (avoids stale cross-references between e.g. merged `researchTopics` and an un-merged old `feedIntent.requiredConcepts`).
- **P2 (saved papers / events / jobs / read items).** Always **union** on sign-in, never a replace — this directly closes §1.2/§1.3. Concretely: a pull result must never be allowed to *shrink* what's locally held; only a **confirmed successful push** of a given local item may retire it from "must still reach the account." A failed push or a failed/ambiguous pull must leave every currently-held local item exactly as it is. (Sub-point, optional POLICY: if the same paper was saved both locally and on the server with different `savedAt` timestamps, which timestamp wins for display ordering — cosmetic, low stakes, B recommends "keep the earlier one" as a default rather than escalating.)
- **P3 (push-failure guarantee, general).** No sync path (profile or feed) may treat a pull's result as authoritative-enough-to-shrink-local unless it can also account for every local item it might be about to drop having either (a) already been successfully pushed, or (b) still being present in the pull result. This is the general form of the manager's requirement (3).
- **P4 (restore-from-file merge — see 4b).** POLICY: should a signed-out restore of an old backup **union** with whatever local data already exists in this browser (e.g. the user browsed anonymously, saved a few papers, *then* restores an old profile export), or **replace** local wholesale? B recommends union, for the same "never silently discard" reason as P2, but this is the manager's call to make explicit.

### 4b. "Restore from a backup file" control

Flow: file picker → `JSON.parse` → `parseExportedProfile` (`web/src/store/profile.ts` lines 359-388) → **explicit strip step (new, required)** → `importProfile` (lines 758-764) → for a signed-in account, push through the same merge path as P1/P3 (never a bare `PUT` of the raw imported object) → for signed-out, local-only, with an on-screen line saying so plainly.

**Why the explicit strip step is required and cannot be skipped:** `parseExportedProfile`'s `known` allow-list (line 373) is `Object.keys(defaultProfile)` — and I confirmed by reading `web/src/types/index.ts` (lines 519-524, 592-598) that **`defaultProfile` still contains `tavilyApiKey`, `adzunaAppId`, `adzunaAppKey`, `usajobsApiKey`, `usajobsUserAgent`, and `feedAiApiKey`** (all defaulted to `""`, all still live fields of `UserProfile`). So `parseExportedProfile` does **not** drop these — if a backup file contains them, `importProfile` installs them into local state exactly as-is. A bare `importProfile(document)` call, without an explicit additional filter before it, would let obsolete credentials back into the running profile — violating the binding "never restored" requirement.
Additionally, **`remoteProfilePayload`'s own redaction list is incomplete** (profile-sync.tsx lines 118-132): it destructures out and excludes `tavilyEnabled`/`tavilyApiKey`/`feedAiProvider`/`feedAiApiKey` from what gets pushed to the server, but **not** `adzunaAppId`/`adzunaAppKey`/`usajobsApiKey`/`usajobsUserAgent`. Today this gap is inert (no screen calls `updateAdzunaKeys`/`updateUsajobsKeys` any more — events/jobs UI was removed — so these fields never carry a real value in practice). But a restore control that imports a file containing them would immediately make the gap live: those four values would ride along in the very next debounced `PUT /api/profile` body (they don't reach a DB column — `profilePatchToRow`, route.ts lines 111-152, has no branch for any of these four — but they *would* leave the browser in plaintext over the wire and appear in a request body/Vercel function log, which the binding requirement's "never uploaded" plainly means to prevent). **The restore control must strip exactly these six fields (`tavilyApiKey`, `adzunaAppId`, `adzunaAppKey`, `usajobsApiKey`, `usajobsUserAgent`, `feedAiApiKey`) before calling `importProfile`**, and C should also close `remoteProfilePayload`'s gap (add the four `adzuna*`/`usajobs*` fields to its exclusion list) as defense in depth so this can never leak by any other path either.
Interaction with §4a: once imported locally, the signed-in push must go through the same P1/P3-safe merge path, not a raw overwrite PUT — otherwise the restore control reintroduces exactly the "server-wins, local/just-restored-data-loses" risk this whole item exists to close.

### 4c. Interaction with GOOGLE-SIGNIN

Both `profile-sync.tsx` and `feed-sync.tsx` key everything off `supabase.auth.getUser().id` / the session's user id — never the provider. So once GOOGLE-SIGNIN confirms Supabase's identity-linking-by-verified-email actually lands the user on the **same** `auth.users.id` (and therefore the same `public.profiles` row) regardless of whether they used GitHub or Google, the merge/restore logic built here needs **no provider-specific changes** to also work correctly for Google sign-in — it is already keyed at the right level. The one required coordination is file-level, not logic-level: `web/src/components/account/*` gets both this item's "Restore from a backup file" control (§4b) and GOOGLE-SIGNIN's "Sign in with Google" button; whoever's C lands second should re-read the file fresh rather than assume the layout from a stale read (already flagged by the manager in the task brief).
