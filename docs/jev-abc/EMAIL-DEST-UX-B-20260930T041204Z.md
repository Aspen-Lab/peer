## Root cause summary (read this first)

**EMAIL-DEST-UX** is not one bug, it is one *design gap* (the button and the summary line never name a destination) plus three separate, confirmed-by-reading *copy bugs* that would make naming the destination actively misleading if done naively:

1. The one sentence on the page that currently claims a destination ("Sending daily at … to …") reads from `addressDraft` — the text box the reader is typing in — not from the address the server actually resolved (`web/src/app/profile/page.tsx:1431`, `:1440`). A half-typed or unconfirmed address can be shown as if it were live.
2. The "Confirmed — daily emails will go to …" banner also reads from live `addressDraft`, not from the address that was actually just confirmed (`page.tsx:1498`), so it can go stale if the reader edits the box while waiting for the confirmation email to land.
3. The small caption under the input has no state for "this address is already the confirmed, active one" — it only distinguishes "is the account email" / "is pending" / (fallback) "Confirm to start sending here." (`page.tsx:1478-1484`). On every normal page load with an already-confirmed custom address, the fallback fires and wrongly implies nothing has been confirmed yet.

**Send test email** and **the daily scheduled email** both resolve the destination identically and correctly on the server — confirmed `digest_email`, else the account's sign-in email (`send-test-email/route.ts:161`; `dispatch-digests/route.ts:648-653`) — and **never** read the typed draft. The user's reported experience ("expected the work address, got the Gmail") is the direct, reproducible consequence of bug 1 above: they typed the work address, it showed in the box (and, once they turned the toggle on, in the misleading "Sending daily … to workaddress" sentence), but the server-side `digest_email` was never actually set to it (the confirmation send itself failed — see below), so both the test button and the real daily job kept using the old fallback, the account Gmail.

**EMPTY-TEST-EMAIL** is a single, precise ordering bug: `send-test-email/route.ts` increments the 3/day counter (line 182) *before* it runs the feed pipeline (line 199) and *before* it knows whether the pipeline found anything. A 0-item result still consumes a try. A failed send (line 221) also is not refunded, by explicit design (comment at line 222-224) — that part is intentional and should stay. The email's own 0-item *wording* is already fixed and live (EMPTY-EMAIL-REASON, merged PR #25, `briefing/copy.ts:138-168` `DIGEST_EMPTY`) — what's still wrong is that the button pretends a 0-item run is exactly as "successful" as a 10-item one, and charges the reader for it either way.

## Task 1 — Full state path: address field, confirmation, and what each send actually uses

STATUS: done

### How the destination is actually resolved (ground truth, both send paths)

| Sender | Resolution | File:line |
|---|---|---|
| "Send test email" button | `typedProfile?.digest_email?.trim() \|\| user.email \|\| ""` (server reads the `profiles` row fresh on every click) | `web/src/app/api/profile/send-test-email/route.ts:161` |
| Daily scheduled email (dispatch-digests cron) | `row.digest_email?.trim() \|\| null`, else looks up the Supabase auth user's email | `web/src/app/api/jobs/dispatch-digests/route.ts:648-653` |

Both paths are identical in shape and both read the **server-stored, confirmed** `digest_email` column — never anything the client is currently typing. `digest_email` can only be written server-side by:
- `POST/GET /api/profile/confirm-email`'s token flow (`confirm-email/route.ts:262`, after `verifyConfirmToken` succeeds), or
- the same route's "already-confirmed short-circuit" for an address that equals the account email or the already-stored value (`confirm-email/route.ts:151-157`), or
- `PUT /api/profile`, but **only** if the submitted `digestEmail` equals `""`, the account email, or the already-stored value — anything else is silently dropped and reported in `ignored` (`app/api/profile/route.ts:296-327`).

So there is **no server-side concept of "typed but unconfirmed"** — it exists only in the browser, as `addressDraft` (component state). This is the structural reason the destination can't be "wrong": it's always one of exactly two values (confirmed custom address, or account email). The bug is that the **page's own copy doesn't reliably say which one it currently is.**

### The state table

`accountEmail` = the signed-in Google/GitHub account's email. `confirmed` = the server's current `digest_email` value (`profile.digestEmail` once hydrated client-side). `addressDraft` = the live text-box value. `pendingAddress` = set only while a non-account address's confirmation email is in flight.

### Two additional confirmed-by-reading findings, both load-bearing for any fix

- **Account-email short-circuit never confirms anything server-side at click time.** `handleAddressSubmit`'s early branch for `candidate === accountEmail` (`page.tsx:1626-1632`) calls `updateDigestEmail(candidate)` — a pure local Zustand-store write, no network call (`web/src/store/profile.ts:666-667`) — and shows no banner at all (`confirmedBanner` is never set `true` on this branch). The server's `digest_email` only catches up once the profile-sync debounce later pushes it via `PUT /api/profile` (allowed there because it equals the account email, `route.ts:301`). Until that push lands, `Send test email` and the cron still read whatever `digest_email` was *before* — which can be a **previously confirmed custom address**, not the account email the UI now implies is active. Narrow window, but real, and it is exactly the "typed a different thing than what's used" shape this item is about.
- **`send-test-email` never writes a `briefing_deliveries` row** (route header, `send-test-email/route.ts:13-14`), so an empty (or any) test send leaves no trace in "Past briefings" (`page.tsx:1226` `slice(0, 20)`) — the reader's only way to learn a test send was empty is to open the email itself.

## Task 2 — The try counter: exactly when it is spent

STATUS: done

`send-test-email/route.ts`'s check order (comment block at lines 21-27 documents the intent; code at 131-234 is what actually runs):

1. Not signed in → `401` — **not spent** (before any counter code).
2. `RESEND_API_KEY` missing → `200 {sent:false, reason:"unavailable"}` — **not spent** (line 140-147).
3. No destination at all (`digest_email` empty and no account email) → `400 {reason:"no_address"}` — **not spent** (line 161-167).
4. No research focus yet (`testDigestFeedRequestFromProfile` fails) → `400 {reason:"intent_required"}` — **not spent** (line 169-179). This ordering — cheap profile-shape checks before the counter — is deliberate and dated: §1al POLISH-1-EMAIL (e) moved it here specifically so a reader who fails one of these for free never burns a try (ABC-JEV-INTEGRATION.md §1al, ruling text quoted in the route's own header).
5. **Counter increment — unconditional from here on:** `getCounterStore().increment(testEmailDayKey(...), ...)` (line 182-187). `CounterReading.value` is the count **after** this call's increment (`lib/usage/counters.ts:55-57`); `breakerTripped(reading, 3)` is true when `value > 3` (`counters.ts:434-440`, fail-**closed** by design — an unreadable counter also counts as tripped). If tripped → `429 {reason:"rate_limited"}`. **The increment already happened even on this 4th-and-blocked call** — harmless (the reader is blocked either way and the raw count is never shown to them), but confirms the spend is unconditional past step 4, not contingent on anything that follows.
6. Feed pipeline runs (line 199-206) — **regardless of the try already being spent in step 5**, so its outcome (10 items or 0) cannot un-spend anything.
7. `sendDigestEmail` runs (line 210-219). **If the send itself fails** (502, `sender_not_verified` or `send_failed`) — **still spent, explicitly no refund** ("No counter refund (the daily send was already spent above)", comment at line 222-224).
8. Success (`sent:true`) — spent, as expected.

**Net: only steps 1-4 are free. Every outcome from step 5 onward — including a 0-item pipeline result and a failed send — burns one of the 3.** This is precisely the reported bug: the user's test send reached the account Gmail with "0 items" and that counted as one of today's 3 tries.

**What the reader sees**, via `testSendMessage()` (`page.tsx:1352-1382`, keyed on `reason` only, never raw provider text — §1al (g)):
- The six failure reasons each get a fixed, distinct sentence (`page.tsx:1357-1371`).
- Success (`sent:true`) always renders `` `Sent just now to ${body.to}.` `` (`page.tsx:1375-1377`) — **identical text whether the pipeline found 10 papers or 0.** There is no item count in the response at all (`send-test-email/route.ts:234` returns only `{sent:true, to}`), so the client has no data to say otherwise even if someone wanted to.
- **There is no proactive "N of 3 used today" indicator anywhere in `EmailSettingsView`** (confirmed by its full prop list, `page.tsx:1384-1402` — no such prop exists) — the reader only learns the count is exhausted after the 4th click, via the `rate_limited` sentence.

## Task 3 — Options

STATUS: done

### (a) Show "Sends to `<address>`" next to the button

**What the reader sees:** a small line at or near "Send test email" (and ideally reusing the same string for the toggle's own summary line), e.g. "Sends to `<address>`" with a short qualifier for *why* — confirmed custom address vs. account address as the fallback.

**Must be sourced from `profile.digestEmail || accountEmail`** — exactly mirroring the server's own resolution (`send-test-email/route.ts:161`) — **never from `addressDraft`**. This is not optional polish: Task 1 finding #1 is that the page's *only* existing "destination" sentence today already does this wrong (reads the draft). Shipping (a) without first fixing that source would just add a second, differently-wrong sentence next to the first.

**Cost:** small. Every value needed (`profile.digestEmail`, `accountEmail`) is already in scope inside `EmailSettings` (`page.tsx:1521-1543`); this is a derived string, not a new API call.

**Risk:** privacy — none new. This renders only on the signed-in reader's own `/profile`, from data the client already holds for that reader; it must stay off any URL, query string or log (consistent with EMAIL-TOKEN-PRIVACY's standing constraint, ABC-JEV-INTEGRATION.md §1as) — a plain page render carries no such risk by construction, but the implementer should not be tempted to thread the address through a route/query param to reuse code between server and client.

### (b) A notice when the typed address differs from the confirmed one

**What the reader sees:** while `addressDraft` (normalized) ≠ the address that (a) reports as active, something like an inline note under the input clarifying the typed text is not live yet.

**Cost:** small — a client-side string comparison, no new API.

**Risk / design overlap:** (a) and (b) both want to name the same "currently active" address in two different places (near the button, and near the input). Shipping both as independent sentences risks the page repeating itself or, worse, drifting (one gets updated later and the other doesn't — exactly how bug #1 in Task 1 was born in the first place, when the "Sending daily to X" line and the confirm-flow's own `pendingAddress` caption were written to different sources of truth by different rounds of work). **Recommend unifying (a) and (b) into one sentence/spot, not two.**

(b) also exposes the third Task-1 bug directly: the input's caption today (`page.tsx:1478-1484`) has no "this is already the confirmed, active address" branch. Implementing (b) *requires* adding that branch anyway (otherwise every already-confirmed reader sees a false "differs from confirmed" notice on every visit), so (b) and the caption fix are effectively the same change.

### (c) An empty test result does not send and does not spend a try, with an honest sentence

**What the reader sees:** instead of "Sent just now to `<address>`", something that (i) says plainly that nothing matched and nothing was sent, (ii) says explicitly this did not use one of the 3 tries, and (iii) is *true* — reusing the already-shipped, already-reviewed `DIGEST_EMPTY` sentences (`web/src/lib/briefing/copy.ts:138-168`) keyed by the same `FeedEmptyReasonCode` the pipeline already computes (`feed.meta.emptyReasonCode`, `lib/feed/types.ts:125,134`) rather than inventing new wording. Note the email's own 0-item *content* is not this item's problem — EMPTY-EMAIL-REASON already shipped and is live (PR #25, merge `aea1ef30`) with an honest sentence inside the email itself for exactly this case. What's left here is purely: don't send it at all, and don't charge for it.

**Cost — this is a real code change, not just copy:** the route currently spends the try (line 182-187) *before* running the pipeline (line 199-206) specifically so the pipeline can never run more than 3×/day per user unconditionally. Shipping (c) means checking `feed.items.length === 0` **before** the counter is touched, which means running the pipeline first and the counter second — the opposite of today's order.

**Risk, named explicitly because it's a real trade-off, not a detail:** the pipeline makes real outbound calls to external paper sources (OpenAlex, Semantic Scholar, arXiv, PubMed, DBLP) even at `aiTier 0` — confirmed by the manager's own diagnostic probe in ABC-JEV-INTEGRATION.md's "EMPTY-HOME diagnosed" entry (fetched openalex 5 / semantic_scholar 50 / arxiv 1 / pubmed 40 for a single request). Today the 3/day breaker caps how many times one signed-in reader can trigger those calls through this button, full stop. Under a naive version of (c), **any attempt whose result happens to be empty costs nothing and doesn't count against the limit** — so a reader (or anyone scripting against their own signed-in session) could trigger unlimited pipeline runs by ensuring the result stays empty (e.g., an unusual Required-topic combination). This doesn't cost Peer money (Tier 0, no model calls) but it does uncap load against the source adapters' own request budgets, which is exactly the kind of "wallet-breaker" concern §1z P1 named for this same counter (ABC-JEV-INTEGRATION.md §1z: "protect the sending budget and stop the button being used to spam"). Two ways to close this gap, both real design forks for the manager (not decided here):
  - keep counting *attempts* (today's behavior) but track sends and empty-non-sends as two different tallies, so "spent" in the user-facing sense means "actually sent," while a separate, more generous ceiling still bounds raw pipeline invocations; or
  - accept the cost as low-risk (Tier 0 is free in dollars, and the source adapters already have their own per-call pacing/backoff), and revisit only if it's ever observed as abuse.

**Privacy:** the response must stay reason-coded, the same pattern already established for every other outcome on this route (`reason: "unavailable"|"no_address"|"intent_required"|"rate_limited"|"sender_not_verified"|"send_failed"`, `send-test-email/route.ts` throughout) and for `classifySendFailure` (`lib/email/send-failure.ts:39-47`) — a fixed enum value out, never pipeline internals or provider text. `feed.meta.emptyReasonCode` is already exactly such a fixed enum (`FEED_EMPTY_REASON_CODES`, `lib/feed/types.ts:148`), so reusing it costs nothing on the privacy axis.

### (d) Anything else

- **(d1) A standing "`N` of 3 used today" line**, visible before the reader clicks, not just after the 4th click fails. Needs the route (or a small new read) to expose the current count — none of today's responses carry it. Pairs naturally with (c): once empty results stop counting, "used" becomes an honest, meaningful number.
- **(d2) The three Task-1 copy bugs, as prerequisites, not optional cleanup:** (i) the toggle's own "Sending daily at … to …" line must read `profile.digestEmail || accountEmail`, not `addressDraft` (`page.tsx:1431,1440`); (ii) `confirmedBanner`'s "…will go to `{addressDraft}`" must be sourced from the address that was actually just confirmed, not live draft state (`page.tsx:1498`); (iii) the input's caption needs an "already confirmed, this is active" branch (`page.tsx:1478-1484`). Shipping (a)/(b) without these just adds a fourth, competing sentence to a page that already has three inconsistent ones.
- **(d3) Minor:** the account-email short-circuit (`page.tsx:1626-1632`) shows no confirmation feedback at all today (no banner, no message), unlike the token-click path. Low priority, noted only because a reader could reasonably expect symmetric feedback for what the destination line will now claim is a "confirmed" state.

### Recommended combination

Ship **(d2)'s three fixes as the foundation**, unify **(a) + (b)** into one destination line (near the button, sourced the corrected way, doing double duty as the "differs from what you typed" notice — no separate second sentence), and ship **(c)** with the pipeline-before-counter reorder, reusing `DIGEST_EMPTY` wording, **on the "accept the cost, revisit if observed" side of the (c) risk fork** unless the manager wants the two-tally version instead. Defer (d1) and (d3) — genuinely optional, neither is needed to close either named bug.
