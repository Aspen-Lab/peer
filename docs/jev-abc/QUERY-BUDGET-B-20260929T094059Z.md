## 2. Design — a structural slot-allocation rule (no stop-list)

### 2.1 The rule

Replace `baseQueries`'s flat concatenation (Step 4 above) with **tiers**, each tier fully
exhausted before the next is considered, still ending in the same `cleanList(...).slice(0, cap)`
(Step 6, unchanged):

```
Tier 0   interleaved Required tags + exact-sense queries (guarantee — see 2.2)
Tier 1   bare project phrases (multi-word projectTerms entries, original order)
Tier 1b  one tag-anchored combination per tag: `${tag} ${strongestProjectPhrase}`
           (REVISED — see below: measurement (§3.2) found this can EITHER sharpen a
           source's results (fixture B: qualify rate nearly 4x the bare phrase's own)
           OR collapse them to near-nothing (fixture A: 58 candidates down to 1) —
           demoted below the bare phrase as the risk-averse default given that
           asymmetry, not because the evidence favours it, pending a targeted
           follow-up measurement)
Tier 2   bare single-word projectTerms entries (today's fallback, unchanged content —
           this is where "research" already lives; it only moves LATER)
Tier 3   remaining combinations: topic×method (unchanged), plus topic×projectTerm
           combos beyond the one already spent in Tier 1b
```

This is a **pure reordering of the exact same query strings** `baseQueries` already produces
today — Tier 1b's combo is already one of Step 4's own topic×projectTerm combos (the one using
`projectTerms[0]`), just moved earlier. No new query text is invented; nothing is removed.
Confirmed by direct execution (§3.1): for both fixtures, today's and the proposed 9-entry lists
are the same 9 strings, reordered.

**This tier order (bare phrase ahead of its own tag-anchored combo) is the REVISED design,
written after §3.2's live measurement, not the investigation's starting assumption.** Going in,
the expectation was the opposite (a tag-anchored combination should out-rank a bare phrase — the
ticket's own suggested example). §3.2 measured that assumption on 2 fixtures and got a genuinely
mixed result: fixture B's combo qualified at nearly 4x its own bare phrase's rate (the expected
outcome, strongly confirmed); fixture A's combo collapsed an already-narrow 58-candidate pool to
1 (a near-total failure). This tier order is the risk-averse response to that asymmetry — a
wasted-but-harmless bare phrase costs less than a collapsed-to-1 combo — not a confident claim
that combos under-perform; §3.2 has the full evidence and reasoning, and this is called out
explicitly as a POLICY item (§4.3) rather than shipped as a settled conclusion.

**Focus modes (Step 5) are untouched.** Tight focus reconstructs its own list independently
(`[...exactSenseQueries, ...baseQueries.filter(...)]`) and does not read `baseQueries`'s internal
tag/sense ordering — confirmed by re-deriving `profile-compiler.test.ts`'s tight-focus pinned
tests by hand against this design (§4 pins). Exploratory's two appended per-tag combos are
unaffected (they come after Tier 3 either way).

### 2.2 Guarantee: Required tags must never be pushed out by senses

Measured (§3, zero network cost, direct execution of the REAL `compileSearchBrief`): a profile
with 2 selected senses and 2 Required tags sends `dblp`/`pubmed` (cap 2) **`["role conflict",
"conflict of interest"]` — both Required tags absent, 0 of 2** under TODAY'S code. This is worse
than the ABBREV-RECALL-A LOW finding's "could crowd out" — it is a full displacement, reproduced
live by execution, not hypothetical.

Two structural options, both bounded and list-based (no per-source awareness needed in
`profile-compiler.ts`, since guaranteeing something within the SMALLEST cap in the system, 2,
automatically guarantees it for every larger cap too):

- **Option R1 — round-robin interleave** (`sense0, tag0, sense1, tag1, ...`, leftover appended
  in its own order). A sense query always leads when senses exist (preserves the literal text of
  ABBREV-RECALL §1av: "exact-sense queries... first"), and **at least one** Required tag always
  lands inside the smallest cap regardless of how many senses exist (position 1). Does not fully
  protect a SECOND+ tag from a large sense count — degrades the same, already-accepted way a
  sense-free multi-tag profile already degrades against a 2-cap source today.
- **Option R2 — tag-priority within the smallest-cap window.** Within the first `smallestCap`
  (2) positions, Required tags claim slots first (`min(tagCount, 2)` of them), senses fill only
  what tags leave unclaimed; senses beyond that move to right after the tag block. **Fully**
  guarantees `min(tagCount, cap)` tags survive every source, every time. Cost: for a profile with
  >=1 tag and >=1 sense in DEFAULT (non-tight) focus, the very first query is no longer
  guaranteed to be a sense query — a genuine, if narrow, reinterpretation of §1av's literal
  ordering text for exactly this intersection. Verified this does not conflict with any EXISTING
  pinned test: the one sense+topic pinned test
  (`profile-compiler.test.ts:92-109`, `"keeps selected senses alongside topic-anchored tight
  queries"`) is a TIGHT-focus test, which (2.1) reconstructs its list independently of this
  ordering; no DEFAULT-focus pinned test currently combines senses and tags (confirmed by
  reading the full test file).

**Recommendation: R2.** "Required" tags are the product's own declared name for the reader's
non-negotiable filter (REQUIRED-GATE, ABBREV-RECALL both treat them this way already); a sense
selection is a disambiguation refinement layered on top, not a competing must-have. R2 is the
only option that actually satisfies this item's charter verbatim ("guarantee that Required tags
are never pushed out by senses" — R1 only raises the floor from 0 to 1, it does not guarantee).
**Flagged on the POLICY list (§4)** because it does narrow §1av's literal wording and deserves
explicit sign-off, not a silent reinterpretation by C.

### 2.3 Is a slot reserved for project context?

**Recommendation: no separate hard reservation.** The tiering in 2.1 already gives project
context (Tier 1/1b) unconditional priority over single generic words (Tier 2) for every source —
that priority ordering IS the reservation, expressed structurally rather than as a slot count.
A hard reservation (e.g., "the last slot of every source's cap is always a project phrase, even
if it displaces a Required tag") would trade guaranteed tag recall for guaranteed context recall
— the wrong trade, for two reasons: (a) it directly undermines 2.2's guarantee for the same
reason senses do; (b) project text is **not only useful as a literal query string** — every
fetched candidate, however it was retrieved, is still ranked against the reader's full project
text via the pool-wide TF-IDF (`combine.ts`'s `pText`/`scoreTfidf` at `:169,321`) and can still
qualify a tag-anchored candidate through T4 (`combine.ts:289-311`, `simProject` against the SAME
`pText`) — so project context already has a second, retrieval-independent channel into ranking
and gating that a Required tag's own retrieval does not have. When nothing survives Tier 1/1b at
all (a profile whose project text produces zero usable phrases — no comma-shaped clauses, no
non-stopword tokens), there is nothing genuine to reserve a slot FOR; falling through to Tier 2
is correct, not a bug (this is the accepted, measured QQ-A-1 residual — see §3.2).

### 2.4 Do caps rise with tag count (bounded)?

Today `MAX_QUERIES` is a fixed constant per source (3 or 2) regardless of how many Required tags
a reader declares — so with more tags than a source's cap, the excess tags get **zero**
representation on that source, silently, every day (the same shape of gap ABBREV-RECALL fixed
for the 1-vs-many-slots case, just not yet fixed for the many-tags case). A bounded rise is
possible and structurally simple, entirely inside the 5 adapter files' own `MAX_QUERIES`:

```
effectiveCap(baseCap, tagCount) = min(baseCap + max(0, tagCount - baseCap), baseCap + RISE_CEILING)
```
with `RISE_CEILING = 3` (bounded — cap can never rise more than 3 above today's baseline, so an
unusual 50-tag profile cannot open the budget unboundedly).

**Cost in source calls per pool build** (sum across all 5 sources; a call = 1 outbound HTTP
request per surviving query, Step 8):

| Tag count | openalex/S2/arxiv cap (each) | dblp/pubmed cap (each) | Total calls | vs today's constant (13) |
|---|---|---|---|---|
| 1 (today's common case) | 3 (unchanged) | 2 (unchanged) | **13** | +0% |
| 3 | 3 (unchanged — exactly fits) | 3 (+1 each) | **15** | +15% |
| 6 | 6 (+3 each, hits ceiling) | 5 (+3 each, hits ceiling — 1 of 6 tags still lost) | **28** | +115% |

Today's cost is a flat 13 regardless of tag count — the trade a rising cap makes is a bounded,
quantified call-count increase in exchange for guaranteed per-tag retrieval coverage up to the
ceiling (recall today is already silently lost past the fixed cap; this trades an invisible
recall loss for a visible, budgeted call-count cost). At 3 tags the cost is modest (+2 calls,
+15%); at 6 tags it more than doubles (+15 calls, +115%) and starts to matter for latency and,
concretely, for the ANONYMOUS-tier rate limit this very investigation was rate-limited on twice
in §3 while measuring under the SAME keyless constraint this item is scoped to (production uses
`OPENALEX_EMAIL`/optionally `OPENALEX_API_KEY` — `openalex.ts:10,28-31` — so production's actual
ceiling is the "polite pool"'s, materially higher than what this investigation could exercise;
still, the direction of the risk is real and worth weighing explicitly, not assumed away).
**Recommendation:** raise dblp/pubmed's cap for tag counts above 2 (cheapest, matches ABBREV-RECALL's
already-accepted precedent that "more tags than the smallest cap already lose some tags" is a
known gap); leave the 3-cap sources' rise as an explicit **POLICY** choice for the manager (§4),
since it touches 5 already-hardened adapter files (each independently tested, each carrying its
own `MAX_QUERIES`-shape regression tests) for a benefit that only matters to profiles with 4+
Required tags — a real but narrower population than every profile with a project paragraph.

bare phrase A: 58 narrow, topically-concentrated candidates, 0 of which happen to contain the
literal string "LCO") is a real limitation of this probe's methodology (shared with
QUERY-QUALITY-B's own, by design — T4 needs a pool-wide index a single-query probe does not
build): a pool this narrow and topically concentrated is a plausible T4 (topic-anchored
similarity) admission in the real, pool-wide pipeline, which this measurement cannot see. Bare
phrase B's own 12% T1-T3 qualify rate is itself evidence this isn't purely theoretical — some
genuinely narrow, phrase-driven pools DO contain literal tag hits.

**The two combo results (#4, #6) point in opposite directions — a genuinely mixed result, not a
clean confirmation either way.** Going in, the expectation (the ticket's own suggested example)
was that a tag-anchored combination should out-rank a bare phrase. Fixture B's combo strongly
confirms this: **151 in-window, 44% T1-T3 qualify — nearly 4x the bare phrase's own 12% qualify
rate**, exactly the re-ranking-toward-the-tag effect expected. Fixture A's combo contradicts it
just as strongly: the tag collapsed an already-narrow 58-candidate pool to **1**, too small a
sample to show any benefit (0/1 is not evidence of a 0% rate — it is one coin flip). Reasoned from
the numbers (not confirmed with additional calls, to conserve the remaining budget): the most
likely difference between the two is that fixture A's phrase leads with "PhD research on," an
AUTOBIOGRAPHICAL frame describing the READER's situation that real paper text essentially never
contains verbatim, while fixture B's "Investigating single-cell transcriptomics..." opens with
language genuinely common in real paper abstracts ("Investigating the role of X in Y..." is a
familiar abstract opening). If OpenAlex's unquoted multi-word `search` weights coverage of ALL
distinctive terms fairly heavily (consistent with the generic-word/bare-phrase progression in the
table above), then adding one more specific token (the tag) to a phrase that ALREADY contains a
word absent from real target text can crash an already-narrow pool to near-zero, while the same
addition to a phrase built entirely from real target-domain vocabulary sharpens precision instead
(fewer, more relevant results — exactly fixture B's 12% → 44% jump). This is a plausible,
evidence-consistent explanation, not a confirmed mechanism (would need its own dedicated
measurement, e.g. testing "single-cell transcriptomics in tumor microenvironments" without
"Investigating" against the same combo).

**Design implication: ship the risk-averse ordering, not a confident directional claim.** Two
fixtures, one clean win for combos (B) and one near-total collapse (A), is not enough evidence to
confidently rank combo-before-phrase OR phrase-before-combo as a general rule. What IS clear is
the asymmetry of the failure modes: a redundant-but-harmless combo (worst case if B's pattern
generalizes badly) wastes little; a collapsed-to-1 combo (worst case if A's pattern generalizes)
wastes an entire query slot on almost nothing, and does so silently, with no signal to the reader
or the system that it happened. **Recommendation: keep the bare phrase ahead of the combo (§2.1's
Tier 1 before Tier 1b) as the safer default**, not because the evidence shows combos are worse
(it does not — B's numbers argue the opposite) but because the downside of getting the order wrong
is asymmetric, and this investigation cannot yet predict from a project text alone which case
(A's or B's) a given profile will land in. **Flagged explicitly as a POLICY item, not a settled
recommendation** (§4.3, revised) — the manager may reasonably weigh B's strong result differently,
and a small follow-up measurement (a handful of calls, isolating whether the leading word of the
phrase is real-abstract vocabulary) could resolve this with much more confidence than this
investigation's 2-fixture budget allowed. The core, high-confidence part of this item's design —
demoting bare single generic words below both phrase-shaped tiers — is unaffected and independently
confirmed twice over (fixtures A and B, two different generic words, two different fields, both
~10^5 in-window candidates vs two-to-three-orders-of-magnitude narrower, topically concentrated
pools for every phrase-shaped query measured, bare or combo).

**Rate-limit ledger (for §2.4's cost discussion).** The very first 2 calls of this investigation's
own live measurement, made under the same keyless/anonymous constraint this item is scoped to,
were both 429'd — the first immediately (12s after the previous, unrelated B item's own calls
earlier this session), the second after a 50s backoff. Only widening the wait to 170s let calls
succeed. This is first-hand, same-day, same-session evidence that the anonymous OpenAlex tier is
a shared, easily-exhausted resource under this loop's cumulative daily call volume — direct
support for §2.4's caution about raising the 3-cap sources' `MAX_QUERIES` (more calls per pool
build = more exposure to exactly this).
