## Task 1 — the whole path, every 404 (and non-404) branch

**Page → fetch → route, in order** (`web/src/app/papers/[id]/page.tsx`):
- The reading page takes the URL id (shape `upload:<16-hex-char-hash>`, e.g.
  the user's saved upload's id) and sets `isUploadId = id.startsWith("upload:")`
  (line 156).
- **Important architectural fact, confirmed by reading, central to this bug:**
  for a normal (non-upload) paper, the page prefers data already sitting in
  the local app store (`feedPapers`/`savedPapers`) when the store's copy
  already has an abstract, and only falls back to a network fetch otherwise
  (line 189, the `storePaperIsEnriched` branch). **For an uploaded paper it is
  the opposite: `baseContent = isUploadId ? fetchedPaperForId ?? undefined :
  ...`  (line 189) — the store's copy of a saved upload is NEVER used to
  render the page, even when it is sitting right there in `savedPapers`.**
  Every single open of an uploaded paper's page, cold load or not, MUST get a
  200 from `GET /api/papers/upload/<hash16>` (lines 207-227) or the page
  cannot render the paper at all — it falls through to the generic "not
  found" branch (line 247, the `NOT_FOUND` string) once the fetch resolves
  with no paper. This is not a bug in the fetch itself; it is a design choice
  that removes the one fallback (the locally cached save) that could have
  covered for a route failure.
- The fetch URL is built at line 215:
  `` `/api/papers/upload/${encodeURIComponent(id.slice("upload:".length))}` ``
  — this strips the `upload:` prefix correctly (verified against the shape:
  `"upload:" + <16-hex-chars>`, `.slice(7)` removes exactly `"upload:"` and
  leaves the bare, valid 16-hex-char id; `encodeURIComponent` of a plain hex
  string is a no-op). The URL construction itself is not the bug.

**Route `GET /api/papers/upload/[id]`** (`web/src/app/api/papers/upload/[id]/route.ts:10-25`):
1. `isValidHash16(id)` false → **400** "Not a valid upload id." (not the
   reported 404; listed for completeness — e.g. a literal `upload:`-prefixed
   string reaching this route, wrong length, non-hex characters).
2. `ownedUpload(id)` returns null → **404** "Upload not found." — this is the
   ONE branch that produces exactly the reported symptom, and it hides
   several different underlying reasons behind one identical response
   (`web/src/lib/papers/upload-access.ts:49-64`, `ownedUpload`):
   - **2a. No record at all** — nothing was ever written for this hash16
     (never uploaded on this store, or the JSON was already purged/deleted).
   - **2b. Record purged/expired** — `meta.expiresAt` is missing, unparsable,
     or `<= now` (line 54-55). Checked BEFORE any purge job runs — an
     unpurged-but-expired record already reads as not-found; the nightly job
     later removes the files, which is a second, permanent version of the
     same symptom.
   - **2c. Wrong owner** — `meta.ownerKey !== key` (line 54), where `key` is
     whoever the CURRENT request resolves to (see "ownership" below). This
     covers: signed out when the paper was saved while signed in (or vice
     versa); a different account; and, in local dev specifically, a
     different browser/profile/cleared-cookie session that never had the
     original per-browser upload cookie.
   - **2d. No caller identity at all** — `uploadOwner()` resolves to `null`
     (signed out, no Supabase session, AND no pre-existing local dev cookie —
     the read route never creates one; only the upload/POST route does, via
     `createLocalSession=true`). `ownedUpload` short-circuits to null before
     even reading the file (`upload-access.ts:50-51`).
   - **2e. Status not exactly "ready"** — `"pending"` (a write that crashed
     or was interrupted between the meta-write and the PDF-write, see
     `route.ts:316-336`), `"deleted"`, or `"blocked"` (operator takedown) all
     read as not-found (line 62). Only a record with NO `status` field at all
     (legacy, pre-dates this field) or an explicit `"ready"` passes.
   - **2f. Different machine/deployment/checkout** — `UPLOAD_DIR` is local
     disk, resolved once at process start from `PEER_PRIVATE_UPLOAD_DIR` or a
     default under the running process's own working directory
     (`upload-store.ts:28-38`); it is explicitly `.gitignore`d (never
     travels with the repo) and is never itself synced or shared. A saved
     item opened from a second worktree, a fresh checkout, a wiped
     `.local-data`, or (in principle) a dev server started from an unexpected
     working directory hits an empty or different directory and gets 2a.

**File-bytes route `GET /api/papers/upload/[id]/file`**
(`web/src/app/api/papers/upload/[id]/file/route.ts:15-19`): same
`isValidHash16` / `ownedUpload` / `uploadFileExists` triple-check, same 404
causes as above (2a-2f), plus its own 2g: meta says ready and owned but the
PDF bytes specifically are missing (meta and PDF are two separate files;
`deleteUpload` removes both, but a crash could in principle leave one
without the other). Not the route the symptom named, but on the same paper's
page a second, later 404 from this route is the same family of cause.

**DELETE route** (`[id]/route.ts:27-43`): same `ownedUpload` gate; a 404 here
just means "already gone," not a new cause.

**Saved-item side** (`web/src/store/feed.ts`): `savePaper` (line 2298) writes
the FULL paper record (title, abstract, etc. — the `Paper` shape from
`uploadMetaToPaper`, `upload-store.ts:193-215`) into `savedPapers`, which is
persisted locally AND pushed to the cloud (`cloudSave`, line 2318).
`hydrateFromRemote` (line 2913) merges local and cloud saved lists by union,
never by replacement (line 2921, `unionById` — this was itself a prior fix,
per the surrounding comment, for "saved papers gone the instant sign-in
completes"). **Consequence: the saved pointer (`upload:<hash16>` + its cached
title/abstract) is durable and can cross devices/sessions via the cloud sync;
the upload's backing files are not.** These two storage systems have
independent lifetimes by design — nothing keeps them in lockstep — which is
the structural reason a saved item can outlive what it points to.

**Purge job** (`web/src/app/api/jobs/purge-uploads/route.ts` + `vercel.json:2-7`,
schedule `17 3 * * *` = 03:17 UTC daily): requires a bearer `CRON_SECRET`
match (timing-safe compare) or **401**; on success calls
`purgeExpiredUploads()` (`upload-store.ts:270-281`), which walks every file in
`UPLOAD_DIR`, and for every `<hash16>.json` whose `expiresAt <= now`, deletes
both the JSON and the PDF (`deleteUpload`, lines 240-253) — across ALL
owners, not scoped to one. The same sweep also runs synchronously at the end
of **every** successful `POST /api/papers/upload` (`upload/route.ts:338`), so
a purge is not only a once-a-day event — any upload by anyone on the server
can trigger it.

**Retention/expiry settings found:** `expiresAt = uploadedAt + 30 days`,
computed fresh every time a meta record is written (`upload/route.ts:289`,
`new Date(Date.now() + 30 * 86400_000)`), including on an idempotent
re-upload of the same bytes (extends the deadline) — but merely OPENING the
reading page never touches this value (the GET routes only read, never
write). No other retention/TTL setting exists in the upload path. No
override of the 30-day constant was found anywhere else in `web/src/`.

## Task 2 — cause, found by execution

**Existence check (scoped to the symptom's own id only, per the hard
constraint — no content read):** in this checkout's local upload-storage
folder, the two files for the symptom's id (a metadata record and the PDF
bytes) **both still exist**, last modified 2026-09-16 (the metadata record
slightly later than the PDF — consistent with one initial upload followed by
a later re-save/attach event that only rewrote the metadata, which is exactly
what the code does: `writeUploadPdfIfAbsent` skips rewriting bytes that are
already on disk, `upload/route.ts:330-331`). Today is 2026-09-29. That is
about 13 days old, well inside the 30-day retention window
(`upload/route.ts:289`). **This directly rules out "already expired/purged"
as the cause of the recorded 404** — the file was not gone. (Caveat: this
checked the default storage path; if this dev server's environment sets
`PEER_PRIVATE_UPLOAD_DIR` to something else, I could not know — reading env
files is off-limits — but nothing else in this repo or its docs references
that variable for local dev, and the project's own file `upload-store.ts:6-10`
documents the default path as the real one.)

That leaves the **ownership check** (branches 2c/2d) as the leading
candidate, and it is independently well-motivated: the ABC log's own
timeline (§1 of `ABC-JEV-INTEGRATION.md`) shows Google sign-in
(`GOOGLE-SIGNIN`) and a saved-data restore (`SIGNIN-MERGE`) landing on
2026-09-28 — the SAME day the 404 was hit. `uploadOwner()`
(`upload-access.ts:27-46`) resolves "who is asking" two different ways
depending on auth state: a Supabase-account hash when a real session exists,
otherwise (local dev only) a hash of a private per-browser cookie that is
**only ever minted by the upload/POST route**, never by a read. `ownedUpload`
then requires an EXACT match against whatever owner key was stored on the
record at upload time (`upload-access.ts:54`, `62`). Signing in (or out),
switching browsers/profiles, or losing that cookie between the upload and the
re-open all change which key the server computes — with no path today that
reconciles the two.

  project's own existing test (`upload-access.test.ts`, "requires explicit
  production enablement and storage outside the app", included in the 28/28

- `ABC-JEV-INTEGRATION.md` §1's own go-live environment-variable inventory

  lists exactly 7 Secret + 5 Config variables by name; **neither
  `PEER_UPLOADS_ENABLED` nor `PEER_PRIVATE_UPLOAD_DIR` appears in it,** and I
  found no other mention of either name anywhere else in the state file. This
  is a strong signal, not proof — the manager's own inventory could be stale

- Standard Vercel serverless hosting also has no writable, persistent
  directory outside the deployed bundle in the first place (only an
  ephemeral `/tmp`, not guaranteed to survive between invocations or to be

- No client-side check gates the upload button on `hostedUploadsEnabled()` —

  (`upload/route.ts:142`, a 503 with the honest message "Private PDF storage
  is not configured on this server."). A reader on production can see and
  click "Upload PDF" regardless.

**Conclusion (inferred, not verified):** production most likely cannot
create a hosted upload at all today — a click gets an immediate 503, not a
saved item that 404s later. That is a DIFFERENT symptom from the one
recorded (which needs a saved item to already exist), so THIS EXACT
symptom — a saved upload's page 404ing — probably cannot happen fresh on
production right now, for the mundane reason that no upload can be created
there in the first place. But there are two ways production is still exposed
to the same underlying failure, and both matter:
1. **If a saved-upload pointer ever reaches an account on production** — e.g.
   a `savedPapers` entry with an `upload:` id, synced up from local dev via
   the same cloud sign-in/merge path documented in Task 1 (`store/feed.ts`'s
   `cloudSave`/`hydrateFromRemote`) — opening it on peer.homes would 404 for
   the most basic reason of all (branch 2a: no record ever existed on that
   deployment's storage), with the exact same generic "Paper not found."
   page, because Task 1's structural gap (the page never falls back to the
   store's cached copy) is not specific to local dev at all — it is the same
   file, same code, same behavior on every deployment.
2. **If storage were ever turned on for production** (the two env vars set,
   and some real persistent volume attached) without also changing anything
   else, it would likely 404 users MORE often than local dev's 30-day story,
   not less — ordinary serverless instances recycle and don't share a local
   disk, so a file written answering one request is not reliably readable by
   the next one.

Either way, the fix in Task 4 (make the reading page honest about a saved
item it cannot currently back up with a live file) helps production exactly
as much as it helps local dev — it does not depend on which of these causes
is in play.

## Task 4 — fix options

**Option A — the reading page falls back to the saved copy instead of a dead
end (RECOMMENDED, do this now).**
Today, for an uploaded paper only, `web/src/app/papers/[id]/page.tsx:189`
throws away whatever is already sitting in `savedPapers`/`feedPapers` and
insists on a fresh, successful fetch to `GET /api/papers/upload/<hash16>` or
the page shows nothing but "Paper not found." — even when the very thing
being opened is a saved item the reader already has, with its title and
abstract already on the device (and already synced to the cloud). Change it
so a saved copy in the store is used to render the page whenever the live
fetch comes back empty (regardless of which Task-1 branch caused that), with
an honest, on-brand inline note — the product already has the right voice
for this (`PrivatePdfStatus` today tells every successful visitor "Private
PDF · retained for 30 days after upload…", `private-pdf-status.tsx:21`; a
short cousin of that same sentence — e.g. "This PDF isn't available here
anymore. Showing what was saved." — replaces it when the live copy is gone).
The PDF-specific actions (open the PDF, "read the paper" jump) are hidden or
disabled rather than left to fail separately when clicked.
- **What the reader sees:** the paper's title, abstract, and any notes —
  exactly what "saved" means to them — with one honest sentence explaining
  the PDF itself is gone, instead of a blank "not found" page that looks like
  their save vanished.
- **Cost:** small-to-moderate. Confined to the client: the `baseContent`
  logic in `page.tsx` needs a third state (fetch failed BUT a store copy
  exists) distinct from today's two (loading, and truly nothing anywhere);
  one new copy string; `PrivatePdfStatus`/the decision block need to hide
  PDF-only actions when there is no live upload. No server, schema, or infra
  change. No user decision needed.
- Still shows today's plain "Paper not found." when there is truly nothing
  in the store either (a bad link, a paper the reader never actually saved)
  — that case is already honest and is not changed.

**Option B — refresh `expiresAt` on read, not only on write.**
Today `expiresAt` only moves forward when the file is (re-)uploaded
(`upload/route.ts:289`); simply reading/opening a saved upload never extends
its life, so a paper the reader keeps revisiting can still silently cross the
30-day line. Add a refresh in the page-data GET route specifically
(`upload/[id]/route.ts`), not inside the shared `ownedUpload` helper — that
helper is called from at least 9 other sites across figures, full-text
extraction, and report generation (`figures/extract.ts:1413`,
`papers/[id]/reading/route.ts` × 4, `papers/report/route.ts` × 2,
`full-text.ts:328`, `figure/route.ts:30`), several of them per single page
load; adding a write inside `ownedUpload` itself would turn a shared
read-only check into a surprise write fired many times per view.
- **What the reader sees:** nothing when it works — a paper they keep
  opening simply keeps working. Does not, by itself, change what they see
  when a record HAS already expired (that is still Option A's job).
- **Cost:** small. One additional guarded write on one route; needs a test
  that it never revives an ALREADY-expired/purged record (only extends a
  still-valid one). No user decision needed.
- Does not address ownership mismatches (2c/2d) or the missing-directory
  case (2f) at all — it only narrows how often 2b/purge fires.

**Option C — reconcile ownership across a sign-in/out transition.**
When a Supabase session starts, look for any of this browser's
cookie-owned upload records and re-key them to the account owner (mirrors
the existing `SIGNIN-MERGE` fix already shipped for `savedPapers` itself,
per `ABC-JEV-INTEGRATION.md` §1af/§1aj — same shape of problem, one layer
down).
- **What the reader sees:** an upload saved while signed out keeps working
  after they sign in on the SAME browser.
- **Cost:** the largest of the four. New migration/claim logic touching the
  sign-in flow, idempotency questions (the account already owns a
  same-document upload — which wins?), and it only closes the
  same-device sign-in case — it does nothing for a different browser,
  a cleared cookie, or a different device, which stay covered only by
  Option A. Recommend as a follow-up item, not bundled into this fix, unless
  the manager wants ownership itself fixed now rather than just made honest.

**Option D — move upload storage to a real durable, multi-instance store in
production (Supabase Storage or Vercel Blob) instead of local disk — NEEDS
THE USER.**
This is the only option that could make production actually support saved
uploads reliably at all, per Task 3. It is explicitly out of scope for "fix
the 404": it is a new service or a schema/storage migration, has a cost, and
changes what "production data" means for this feature — exactly the kind of
call the role brief says is always the user's, never assumed. Recommend
surfacing it as an explicit open question rather than leaving it silently
unresolved, but not acting on it in this round.

**Recommendation: ship Option A now** (it is the only option that directly
satisfies "a stale saved upload must never produce a blank or broken page;
an honest message beats a guess," for every cause in Task 1's enumeration at
once, on every deployment, with no user decision required). **Bundle Option B
into the same round** if the manager agrees — it is small and directly
reduces how often readers hit the fallback at all. Leave Option C as a
clearly-scoped follow-up. Put Option D to the user as an explicit question,
not a silent gap.
