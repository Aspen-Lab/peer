## DESIGN (test-first; see DONE below for RED/GREEN/mutation evidence)
Replaced the two polarity-specific repository queries (`recentPositiveFeedback`/`recentNegativeFeedback`, each pre-filtered to its own polarity at the query layer — which is WHY the bug existed: neither resolver could ever see the other polarity's rows to know it had been superseded) with one `recentFeedback(ownerId, windowSize)` returning the owner's most recent PAPER-kind rows across ALL 4 feedback values, ordered `created_at desc, id desc` (reliable tie-break), bounded to `windowSize`. Added a pure, exported `latestEventPerPaper(rows)` that collapses an already most-recent-first list to one row per stored `itemId` (first occurrence wins). Both resolvers now: fetch `repo.recentFeedback(ownerId, limit * RESOLUTION_WINDOW_MULTIPLIER)` -> `latestEventPerPaper` -> filter to their OWN polarity -> existing dedup (by `identity.key` for positive, by resolved `s2PaperId` for negative, UNCHANGED) -> slice to `limit`.

**Bound used and why it can't (practically) starve the 10 most recent seeds:** `RESOLUTION_WINDOW_MULTIPLIER = 20`, so window = `limit * 20` (200 raw rows for the default `limit` of 10). Disclosed reasoning (in the source's own doc comment on `RESOLUTION_WINDOW_MULTIPLIER`, not just here): a legitimate top-`limit` paper is missed only if at least `window - limit` OTHER raw events (from other papers' history, or repeated toggling on a small number of papers) rank more recent than it — ordinary explicit-feedback usage never approaches that volume. This is a disclosed PRACTICAL bound, not a mathematical guarantee: a finite window cannot be airtight against UNLIMITED repeated toggling on one paper, because the simple `eq/in/order/limit` query shape available here (mirroring this module's/`dashboard/rollover-store.ts`'s existing hand-rolled `SelectQuery` discipline) has no server-side "distinct paper" grouping to lean on instead — raw rows, not distinct papers, are what bound the query. Same class of accepted, disclosed bounded-window trade-off as this codebase's other bounded reads (e.g. the P4-S5b-FIX3 ruling's 800-id device-local exclusion cap, read in ABC-JEV-INTEGRATION.md during earlier research this session).

**"Same paper" grouping — disclosed scope choice:** `latestEventPerPaper` groups by the raw stored `item_id` (exactly as written by the feedback route), NOT by cross-source canonical identity (`canonicalPaperKey`'s alias matching). This directly and completely fixes the finding's own concrete example (one card's Save clicked, later the same card's Not-interested clicked — necessarily the same `item_id`, since a feedback click always resends the rendered item's own id) and matches this module's PRE-EXISTING same-item_id dedup test (unchanged, still passing). A narrower residual case is NOT covered: two DIFFERENT `item_id`s that both resolve (via `payload.resolvedIds` cross-referencing) to the SAME underlying S2 paper — e.g. an openalex-sourced Save and a semantic-scholar-sourced "Not interested" on what is, at the S2 level, the same paper — could still, in principle, produce that one S2 id in both `positivePaperIds` and `negativePaperIds`. Judged out of THIS fix's scope: grouping by full canonical identity instead of raw `item_id` would require resolving every row's identity BEFORE the latest-event computation (a materially larger change, not clearly demanded by the ruling's own text, which says "per paper" without specifying cross-source unification), and this fix is scoped "Small, test-first" to `positive-seeds.ts` alone. Flagging for a fresh A to judge whether this residual deserves its own follow-up ruling, the same pattern the original cross-filtering gap itself followed.
