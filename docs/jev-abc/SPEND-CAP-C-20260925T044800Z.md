## R10 finding (checked by execution)

CONFIRMED — `logGemini()` (`web/src/lib/llm/providers/gemini.ts`) is called once per chain
attempt inside `callModel`/`callApiModel`/`callVisionModel`/`callApiVisionModel`, each a
single iteration of the `for (const { id, ... } of fallback)` loop in `generateDigest`/
`generateJsonText`/`generateVisionJsonText` (both the Vertex and reader's-key providers).
Each iteration's `try`/`catch` calls `logGemini` -> `logLlmUsage` exactly once, on BOTH the
success and failure branch. So one `generateJsonText()` call that falls back from model A to
model B legitimately fires `logLlmUsage` TWICE (already documented behaviour, ABC-freemium
2-05/R-METER-1's "never two rows for one PROVIDER REQUEST, one row per attempt").

Consequence for design: settling inside `logLlmUsage` itself (B's original proposal) would
refund one reservation up to 4 times per call (once per chain attempt), most of which would
be spurious (only the FIRST refund is against a real still-open reservation; later ones
would refund an already-settled reservation or double-refund). Built per R10's directed fix:
`usage-log.ts`'s `logLlmUsage` now calls `recordCompanySpendAttempt` (company-budget.ts) to
ACCUMULATE each attempt's actual micro-USD cost onto `scope.companyReservation.settlement`
(a mutable object living on the `AsyncLocalStorage` scope `meterCall` already threads) —
no counter write happens there. `metered.ts`'s `meterCall` then calls `settleCompanySpend`
exactly ONCE, in its own `finally`, after `fn.apply` (every chain attempt) has finished.
Refund = max(0, reserved - sum(actual per attempt)), fired only when EVERY attempt that ran
reported finite usage (`settlement.allReported`); one attempt with missing/non-finite usage
(a provider that threw before `usageMetadata` existed) permanently latches `allReported` to
false for the whole reservation, so nothing refunds and the full worst-case reservation
stands — matches this codebase's existing fail-safe-toward-the-wallet direction.

RED-demonstrated by execution (temporarily broke the implementation, confirmed the specific
test failed for the stated reason, then restored — see "RED evidence" below): overwriting
`actualMicroUsdSum` instead of accumulating it made the "accumulates across MULTIPLE chain
attempts" test fail (expected 130, got 80 — only the last attempt's cost survived).

  `generateVisionJsonText` conditionally (only when the underlying provider actually has the

  unmodified by this pass, still green). No streaming method exists on this interface.
- **`testConnection` gap, found and recorded, not silently patched:** wrapped, but has no
  production call site anywhere (grepped) and sends no output-token ceiling in its own
  implementation — structurally unbounded, same shape as the already-known
  `gemini-fallback.ts` gap. This design fails it closed (new `unestimable_call` reason)
  rather than guessing a price. See POLICY item 1.
- **Digest dispatcher concurrency:** `api/jobs/dispatch-digests/route.ts` processes every
  due-this-hour user in one sequential `for` loop with an `await` inside — confirmed by
  reading the route directly, never `Promise.all`. The cron cannot race itself; real
  concurrency against the shared global counter comes only from ordinary overlapping web
  traffic, correctly serialized by the atomic `increment_usage_counter` RPC.
- **Worst-case burst vs. the $5.00/day default global cap:** the most expensive single call
  (digest, full 4-model chain, 20-paper input) is ≈$0.15/call by B's own sourced/proposed
  per-model prices — bounds any accepted reservation from overshooting the cap by roughly one
  worst-case call's width (≈3%), the standard reserve-then-check breaker shape (same as
  `reserveJevCall`'s own global counter). At the default cap this is roughly 33 worst-case
  digest calls before the breaker trips for the rest of the UTC day. Full math in
  `docs/JEV-RELEASE-READINESS.md` §1a.
