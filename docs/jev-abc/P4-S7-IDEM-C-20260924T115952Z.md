Resolution, and why it is correct on the merits (not merely test-compatible): every new DB call I add (the conflict-row SELECT, the pre-send UPDATE, the post-send UPDATE) is wrapped in its own local try/catch and is explicitly best-effort / never fatal, never blocking the actual send, and never promotes a row into the `failed` bucket by itself. If the bookkeeping write fails, the send still proceeds, still carries the deterministic key, and is still exactly as safe against a double send as if the write had succeeded -- the only thing lost is this specific row's ability to be usefully retried if the send ALSO then fails, which degrades to exactly today's pre-existing accepted trade-off (F-A-P4S7-01), never to a new failure mode and never to a double send.
