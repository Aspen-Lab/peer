Job record (new, authored-only migration, following `dashboard_batches`'s exact conventions, E16):

```
dashboard_prepare_jobs
  id               uuid primary key default gen_random_uuid()
  owner_id         uuid not null
  local_date       text not null
  intent_version   text not null        -- fencing token; same serializeFeedIntent() fingerprint route.ts already computes as todayIntentVersion

                     check (status in ('pending','leased','done','failed','dead'))
  lease_owner      text                 -- opaque worker-instance id; null when unleased
  lease_expires_at timestamptz
  heartbeat_at     timestamptz

  last_error       text
  created_at       timestamptz not null default now()
  updated_at       timestamptz not null default now(),

```

**The "stale job cannot overwrite a new intent" guarantee, in two independent layers (defense in depth, not one mechanism):**
1. *Fencing at claim/publish time*: the row's captured `intent_version` (set when the job was queued) is compared, by the worker, against a FRESH recomputation of the owner's current intent (same call site pattern as `route.ts`'s existing `todayIntentVersion = serializeFeedIntent(pipelineReq.intent)`, E-citations above) taken immediately before the worker would write a `prepared` batch. A mismatch means the user's intent changed after this job was queued — the worker discards its own selection and marks the job `done` with `last_error: "intent_changed"` rather than publishing. This is the SAME rule §3c's "Snapshot identity" already states in prose ("Worker must recheck current intent before publication") — this design is not inventing a new guarantee, only giving the existing stated one a concrete mechanism.
2. *Structural backstop at the batch layer*: even if the fencing check above had a bug, `dashboard_batches`'s own `unique(owner_id, local_date)` plus `prepareBatch`'s idempotent insert-conflict-then-getBatch-retry fallback (already VERIFIED_OFFLINE_BOUNDED by P4-S3, E16) means a stale worker's write can NEVER overwrite an already-served/acknowledged batch for that (owner, local_date) — the worst it can do is lose its own race and have its selection discarded, exactly like a losing concurrent POST /api/feed call already does today (`route.ts`'s `wonMintRace` check).

**Claim function**, same atomic-UPDATE idiom as `increment_usage_counter`/`claim_briefing_delivery` (E10/E12): a single `UPDATE dashboard_prepare_jobs SET status='leased', lease_owner=$1, lease_expires_at=$2, heartbeat_at=now(), attempts=attempts+1 WHERE id=$3 AND (status='pending' OR (status='leased' AND lease_expires_at < now())) RETURNING *`. The `OR lease_expires_at < now()` clause is the CRASH-RECOVERY path: a worker that dies mid-job simply lets its lease expire; the next claim attempt reclaims the row with no separate "detect a dead worker" step needed.

**Due-time computation (the offline-provable half of acceptance 14):** pure, and should REUSE — not re-derive a third time — the exact `Intl.DateTimeFormat`-based `hourInTimezone`/`dateInTimezone` helpers `dispatch-digests/route.ts` already has and P4-S7-T already proved DST-correct (E10, and the round log's P4-S7-T entry).
