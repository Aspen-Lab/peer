## Part 1 — root cause, found by reading Next's own server source (not guessed)

Read (all under `web/node_modules/next/dist/`, Next 16.2.3, React/React-DOM 19.2.4 — confirmed via `web/package.json` and `node_modules/react-dom/package.json`):

- `server/app-render/metadata-insertion/create-server-inserted-metadata.js` (server-inserted-HTML path — not the mechanism; ruled out, this is for the Pages-router-style streamed-HTML path, unrelated to App Router client navigation).
- `lib/metadata/metadata.js` — `createMetadataComponents()`. This defines the `Metadata` async Server Component (`Metadata.displayName = 'Next.Metadata'`) and `createMetadataElements(metadata)`. The icon block (lines 1636-1682) does exactly this for our `app/icon.svg`:
  ```
  if (icon) {
    for (const ic of icon) {
      const { url, rel, ...props } = ic;
      tags.push(jsx("link", { rel: rel || 'icon', href: url.toString(), ...props }, i++));
    }
  }
  ```
  This function is re-invoked, and a brand-new `<link>` React element is created, **every single time `Metadata` renders** — not once per app lifetime.
- `server/app-render/app-render.js`:
  - `getRSCPayload()` (~line 941-1007): builds the **initial full-document** head — `createElement(Metadata, null)` (no key) — used exactly once, for the first HTML response.
  - `generateDynamicRSCPayload()` (~line 288-349), doc comment verbatim: **"This is used by server actions & client-side navigations to generate RSC data from a client-side request."** It builds `rscHead` with `createElement(Metadata, { key: getFlightMetadataKey(requestId) })` (line 324-326).
  - Line 153 (line 152 is its sibling `getFlightViewportKey`): `getFlightMetadataKey = (requestId) => requestId + 'm'`.
  - `requestId` (line ~1322-1330) is minted **fresh per request** — from a request header if present, else `crypto.randomUUID()` / `nanoid()`.

**This is the mechanism, confirmed by reading the code rather than inferred from behaviour:** every client-side (soft) navigation is served by `generateDynamicRSCPayload`, which mints a brand-new React `key` for the `Metadata` element on every single navigation request, because that key is derived from a per-request random id. React treats an element at the same tree position but with a **different key** as a different component identity — it does not update the old one, it mounts a new one. The new `Metadata` instance renders its own fresh `<link rel="icon" href="/icon.svg?hash">` (verified: the href value itself is unaffected by route — it's static — only the React key changes).

Confirmed this is NOT deduplicated by React DOM itself: `node_modules/react-dom/cjs/react-dom-client.development.js`, function `isHostHoistableType` (~line 23109-23167). For `<link>`, only `rel === "stylesheet"` (with a `precedence` prop) gets React's globally-deduplicated "Resource" treatment (tracked in a `hoistableStyles` Map keyed by href, reused across renders — this is what stylesheets/preloads get). Every other `rel` value, including `"icon"`, falls to `default: return true` — it is a plain **Hoistable**, not a Resource: React hoists it to `<head>` but does **not** dedupe it against other `<link>` elements anywhere in the document by href/rel. Each mounted instance gets its own real DOM node, full stop.

So: our own code (`tab-icon.ts`) mutates the ORIGINAL `<link>` node's `.href` directly (a plain DOM write, not through React). That desyncs the node from React's bookkeeping — React still thinks its own last-rendered props for that fiber are the original `/icon.svg?hash`, it just never has a reason to touch that DOM node again once mounted (Hoistables aren't re-diffed against a route change unless their owning fiber re-renders). Then a navigation happens, `generateDynamicRSCPayload` mints a new key, React mounts a **second**, fresh, un-mutated `<link rel="icon" href="/icon.svg?hash">` Hoistable, appended into `<head>` — landing after the first (matches A's observed order exactly). The first (mutated) node is not necessarily cleaned up in the same tick — Next's client Router Cache is designed to keep prior segments' rendered output (including their head content) around for a period (for instant back-navigation / to avoid a refetch flash), so the orphaned node can persist rather than being torn down immediately. I have not traced the exact client-side eviction/GC path for the OLD Hoistable instance into Next's router-cache source (out of budget; flagged rather than overclaimed) — but the cause of the NEW one appearing is fully sourced above, and is sufficient to design against: **the fix cannot assume "insert once, mutate forever" is safe, because Next will keep minting brand-new icon `<link>` Hoistables on every client-side navigation, for the life of the tab.**

## Part 2 — which link does the browser actually use, when two exist

Could not observe this directly: this in-app browser tooling does not fetch favicons at all. I tested it rather than assuming so: created two synthetic `link[rel="icon"][type="image/svg+xml"][sizes="any"]` elements with distinct, real (non-`data:`) hrefs (`/icon.svg?probeFIRST_<ts>`, `/icon.svg?probeSECOND_<ts>`, appended 400ms apart, matching our real order) and checked both `read_network_requests` and the page's own `performance.getEntriesByType('resource')` after an 800ms wait — **zero requests for either href, from either source.** This automation/pane context suppresses favicon fetching entirely (no OS tab strip to display one in), so I have no way to directly confirm what a real Chrome tab would render — same limitation A already stated, now further confirmed by an actual (failed) attempt at an indirect signal, not just an assumption.

Cited instead (MDN, reflecting the WHATWG HTML living standard's favicon-selection algorithm — https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel): the browser picks using each `<link rel="icon">`'s `media`, `type`, and `sizes` attributes; **"If several icons are equally appropriate, the last one is used."** (11-word direct quote, attributed.)

Applying that rule to our exact case: our maintained link and Next's freshly-reinserted one are **identical** in `rel`, `type`, and `sizes` (confirmed: both `rel="icon" type="image/svg+xml" sizes="any"` — only `href` differs, which isn't one of the three deciding attributes) — so per this rule they are "equally appropriate," and the tiebreak is document order. In A's observed (stuck-duplicate) variant, Next's fresh, unpainted, default-coloured link lands **second** (after ours) — so per this rule it is the one a real browser would show. In my observed (clean-swap) variant there's only one link left at any moment anyway, and it's the wrong (unpainted/default) one — no tie-break question even arises.

**Confidence:** high that the cited rule is accurate and applies to this exact pair (identical deciding attributes, well-documented, spec-derived); cannot push higher than that because I cannot directly observe a real Chrome tab's rendered icon through any tool available to me, and neither could A. Net effect either way: after the very first ordinary navigation, the real user's browser tab is very likely showing the plain, un-themed default icon, not Peer's colour — silently, matching A's "this entire feature silently stops working" framing.

## Part 3 — design options

Read for this section: `web/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/app-icons.md` (file conventions only — no mention of a runtime/client-driven favicon anywhere) and `01-app/01-getting-started/14-metadata-and-og-images.md` (confirms metadata exports/`generateMetadata` are Server-Component-only, i.e. cannot read `localStorage`; nothing about client-updatable icons). Favicons are modeled by Next purely as static-or-server-resolved; a theme-following tab icon is inherently an escape hatch the docs don't cover, in either direction. That rules out "whatever the docs recommend" as a distinct option — there isn't one — which is itself useful to know before picking between DIY approaches.

**Option 1 — keep mutating Next's own link, but reconcile continuously instead of trusting it to stay put.**
Add a second observer — `MutationObserver` on `document.head` with `{ childList: true }` (not just the existing attribute observer on `<html>`) — whose callback, on ANY change, converges `<head>` back to exactly one `link[rel~="icon"]`: keep the most-recently-inserted node, copy the current tokens onto it, remove any others. Optionally also key off `usePathname()`/`useSearchParams()` (the framework's own "a navigation completed" signal) as a second trigger, belt-and-suspenders.
- Keeps the literal wording of §1ae's constraint (2) ("updates the link Next's file-based icon.svg metadata emits").
- But it's fighting the framework: it adds a permanent reconciliation subsystem that must keep working correctly for every future kind of head-mutation Next might ever do (not just this one), it has to run in Node-stubbed unit tests via more elaborate DOM-shape mocking, and it never structurally guarantees "no flash" — there's a real (if small) window between Next's insert and our observer callback where the wrong icon is what's in the DOM.

**Option 2 — own the `<link>` directly, outside Next's Metadata system entirely. RECOMMENDED.**
Move `web/src/app/icon.svg` → `web/public/icon.svg` (`git mv`, preserves history) so Next no longer treats it as file-based metadata at all (confirmed via `app-icons.md`: the convention is purely path-based — `app/icon.svg` is metadata, `public/icon.svg` is just a static asset served at the same `/icon.svg` URL, with no functional difference to any consumer). Then render one literal, hand-authored tag directly in `web/src/app/layout.tsx`'s existing JSX — e.g. right beside `<TabIconSync />`:
```
<link rel="icon" type="image/svg+xml" sizes="any" href="/icon.svg" id="peer-tab-icon" />
```
React 19's built-in tag hoisting (confirmed by reading `isHostHoistableType`, Part 1) physically moves this to `<head>` regardless of where in `<body>`'s JSX it's written — this file already relies on that exact behaviour today for its inline boot `<script>`, so it's a proven-safe pattern in this exact file, not a new risk. `tab-icon.ts`'s `ICON_LINK_SELECTOR` changes from guessing at Next's auto-generated attributes to targeting our own stable id (`'#peer-tab-icon'`).
Why this fixes it structurally rather than reactively: `layout.tsx`'s own returned JSX is the part of the tree that is **already proven, by both A's and my own repeated-navigation testing, to never remount across client-side navigations** (that's the entire reason the existing `data-mode`/`data-accent` MutationObserver already survives navigation reliably today). A `<link>` rendered there is therefore never a Next Metadata Hoistable subject to the per-navigation-rekeyed remount from Part 1 — there is nothing left to reconcile against, because nothing ever inserts a competitor. This also makes Option 1 entirely unnecessary as a *requirement* (it could still be added later, cheaply, as extra insurance against some future second icon source, but isn't needed for correctness).
Named trade-offs: (a) loses Next's automatic build-time content-hash query string on the icon URL (`?icon.<hash>.svg`) — a real but minor and already-precedented cost, since every other file already in `web/public/` (`favicon.ico`, `logo.png`, etc.) is served unhashed today; (b) is a deliberate, evidence-based **deviation from §1ae's constraint (2) as literally worded** ("updates the link(s) Next's file-based icon.svg metadata emits") — constraint (2) was written before this exact defect was root-caused; I'm recommending the manager/C treat its *intent* (exactly one effective icon, ever) as binding and its literal mechanism as superseded by this finding, but that's a call for the manager to bless, not one I can make unilaterally as B.
Verified against all four required properties: (i) exactly one link, always — nothing else can ever insert a second one; (ii) survives arbitrary navigation and theme changes — same already-tested attribute-observer logic, now pointed at a node that never disappears; (iii) no-JS/first-paint fallback preserved exactly — the tag is still literal SSR'd HTML pointing at the same static file with the same `prefers-color-scheme` CSS; (iv) no hydration warning — server and client's *first* render both say `href="/icon.svg"`; our effect mutates only after hydration settles (same two-rAF timing already built and tested), so React's hydration diff never sees a mismatch, and no layout shift since `<link>` never renders visibly.

**Option 3 — move the icon into the Metadata API's `icons` field instead of a file. Considered and rejected, not just deprioritized.**
Traced all the way through: `metadata.icons` flows through the exact same `createMetadataElements()` (`web/node_modules/next/dist/lib/metadata/metadata.js:1636-1682`) as the file-based convention — same `Metadata` component, same per-navigation `key={requestId + 'm'}` from `generateDynamicRSCPayload` (Part 1). Switching conventions changes zero code paths relevant to the bug; it would still be re-minted on every client-side navigation. It also can't solve the actual client-state problem anyway: Metadata resolution is server-only (confirmed in the getting-started doc) and Peer's colour theme lives in `localStorage`, not a cookie the server could read. Ruled out on evidence, not preference.

**Side-observation, not part of this ticket's fix:** `web/public/favicon.ico` already exists and is currently unreferenced by any metadata (Next's file-based favicon convention only reads `favicon.ico` from `app/`, confirmed in `app-icons.md`; there is no `app/favicon.ico`). It's dead weight today, harmless either way, and Option 2 doesn't change that fact. Worth a manager/C glance separately; not blocking, not touched by me.
