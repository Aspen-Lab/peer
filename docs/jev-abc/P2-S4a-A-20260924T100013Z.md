## NEW FINDINGS (cost/key first)

**#1 — MODERATE, cost/key-related. The keyed fetch path silently drops the `revalidate` (Next.js data-cache) option that `sourceFetch` would otherwise apply, in both pre-existing files.**
`web/src/lib/sources/openalex.ts` L32-39 and `web/src/lib/affiliation/openalex.ts` L30-37 both define:
```ts
async function openAlexFetch(url, options: { timeoutMs: number; revalidate?: number }) {
  const headers = openAlexAuthHeaders();
  if (!headers) return sourceFetch(url, options);              // unchanged — passes `options` (incl. revalidate) through
  return fetch(url, { signal: AbortSignal.timeout(options.timeoutMs), headers });  // drops `options.revalidate` entirely
}
```
Confirmed via `git diff` (EVIDENCE #5), not just the final file — this is genuinely new code in this slice, not a pre-existing bug. Every call site passes a real `revalidate` value today (`openalex.ts`: 300s; `affiliation/openalex.ts`: 86,400s / 21,600s / 86,400s across its 3 sites), meaning once `OPENALEX_API_KEY` is set, EVERY OpenAlex request from these two files stops using Next's fetch data-cache and becomes an uncached request — a real behavior and cost/latency change from "before this slice," beyond the single difference (429 retry-with-backoff) that C's checkpoint DID disclose. Severity is capped today because no deployment sets `OPENALEX_API_KEY` yet (confirmed: this is opt-in, keyless is the only path exercised in production), so nothing is currently affected — but the very next person who adds a key inherits this silently, with no test catching it (none of the 8 key-handling tests assert anything about `revalidate`/caching). **Recommend:** either thread `options.revalidate` into the keyed `fetch()` call too (`next: { revalidate: options.revalidate }`, trivial one-line fix, same file, no `_fetch.ts` change needed), or explicitly disclose the omission alongside the 429-retry one if it's intentional. This also strengthens the case for the cleanup item C already flagged (fold all 4 helper copies into one additive `headers` option on `sourceFetch` itself) — that fix would have prevented this specific drift by construction.

**#2 — LOW-MODERATE, observability. A semantic/topic-field channel failure is invisible in `meta.errors`/`sourceStatus` — completely silent beyond a server-side `console.error` line.**
`semanticPromise`/`topicFieldPromise` (`pipeline.ts` L364-366, L383-386) are both wrapped `.catch(() => [])`, same as the pre-existing `affiliationPromise`. Unlike the 5 `ACADEMIC_PAPER_SOURCES` (openalex, semantic_scholar, arxiv, dblp, pubmed), which run through `Promise.allSettled` and populate `errors[sourceId]`/`sourceStatus[sourceId]` per P2-S2's ruling (§1p.B(2)), these two new channels are NOT keyed by any `SourceId` and never touch `errors`/`sourceStatus`/`meta.errors` at all — a real OpenAlex outage on the semantic or topic-field channel produces exactly the same response shape as the channel simply finding nothing, distinguishable only by grepping server logs for a `console.error` line nobody reading the HTTP response ever sees. This exactly mirrors the pre-existing `affiliationPromise`/citation-neighborhood behavior (not a regression introduced by this slice), and B's own guide design for these channels (F-A-P2-04 point 3) explicitly specified only "`.catch(() => [])`, its own timeout" with no status-reporting requirement — so this is not a violation of the guide or of §1p.B(2) (which scopes "per-source status" to the 5 registered academic sources). It is, however, a real, currently-undisclosed gap relative to a plain reading of "failure... is reported in per-source status," worth a POLICY note for the manager: either accept that non-`SourceId` discovery channels (affiliation, semantic, topic-field, and future positive-seed/S2-recommendation channels) are permanently exempt from status reporting, or extend `sourceStatus`'s key space to cover them in a later slice.

**#3 — Scope-relevant, not a defect. A real OpenAlex-topic-id-bearing data trail already exists in this codebase and was not investigated by either B or C before concluding "no upstream topic id source exists."**
Every OpenAlex-sourced `RawItem` already carries real OpenAlex `T`-ids today, via `utils/openalex.ts`'s `openAlexWorkToRawItem` (L124-149): it builds `preferenceSignals` entries keyed `preferenceKey(topic.display_name, "openalex_topic", topic.id)` from each work's `primary_topic`/`topics` fields — this is the SAME mapping function both new P2-S4a adapters reuse. `feed/mapper.ts` L144 passes `item.metadata.preferenceSignals` through to the client on every paper. `store/profile.ts` L434-448's `recordPaperPreference` — the actual paper like/save/"more like this"/not-interested handler — calls `applyPreferenceSignal(ledger, conceptsFromPaper(paper), signal, ...)`, which persists those `openalex_topic:<T-id>` keys into the user's `profile.preferenceLedger`, client-side, today, for real. It is not available at the point `topicIds` is assembled only because `pipeline.ts` L488 deliberately keeps `preferenceLedger` OUT of build-time (`buildPaperPool`) and supplies it only at read-time scoring (L815-816) — an architecture choice made for reasons this review did not investigate (likely pool-cache-key stability across a shared per-day pool).
