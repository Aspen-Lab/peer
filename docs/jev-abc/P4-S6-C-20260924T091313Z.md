DESIGN CHOICES (binding for this slice, will detail evidence/rationale in the final checkpoint update):
1. `FINAL_POOL_SIZE = 30` in pipeline.ts. `finalPool = fresh.slice(0, FINAL_POOL_SIZE)` (post all exclusions, pre-topN-slice — `returned` is `finalPool`'s own prefix when topN ≤ 30, which display counts 5/10 always are). Exposed on `runFeedPipeline`'s return value ONLY when a new opt-in `FeedPipelineOptions.includeFinalPool` is true (mirrors the established `ledgerExclusions`/`counterStore` "absent = byte-identical to every caller that doesn't ask" idiom) — guarantees it can never leak into the flag-off/no-scope pass-through JSON response in route.ts, since that path never sets the option. The owner-scoped mint path in route.ts sets it, uses `result.finalPool` purely server-side to compute the rollover remainder, and never spreads `result` into the client response (it always builds a fresh `frozenFeedResponse` object) — so `finalPool` structurally cannot reach the HTTP JSON from either path.
2. New `FeedPipelineOptions.rolloverCandidates?: readonly RawItem[]`. Merged into `pool.items` via the SAME `dedupItems` already used by the in-request retry-merge path (`pipeline.ts`'s `retryFailedSources`), right before `dropStale` — i.e., as early as possible in the read-time chain — so every subsequent step (date window, current-intent scoring, tier1 rerank, journal boost, ledger/excludeIds exclusion, topN slice) treats a rollover candidate identically to a freshly-fetched one, with no code path capable of special-casing it after the merge point. Never written back to the pool cache (`cache.set` is not called for the rollover-merged set) — rollover is a per-request, mint-time-only augmentation of a specific owner's read, not a shared day-pool fact.
3. New module `web/src/lib/dashboard/rollover-store.ts`: `RolloverCandidateStore` interface (`list(ownerId, now)`, `upsert(ownerId, localDate, candidates)`), `MemoryRolloverCandidateStore` (exported reference impl) and `SupabaseRolloverCandidateStore` (service-role admin client, constructor-injectable for tests, mirrors `delivery-ledger.ts`'s degrade-to-fallback-when-unconfigured shape). Deliberately keeps `payload` opaque (`unknown`), same "never import a feed-specific shape" discipline `delivery-ledger.ts` already documents for `servedItems`.
4. Failure-mode asymmetry vs. the ledger (documenting explicitly because it is easy to get backwards): the ledger's exclusion READ fails CLOSED (`"unavailable"` blocks minting) because a false negative there risks re-showing a delivered paper — a safety property. Rollover has no such safety property in either direction: losing rollover data (read OR write failure) only ever means fewer candidates compete tomorrow, never a delivered paper returning (that guarantee is enforced entirely and independently by the ledger's own exclusion filter, which rollover candidates pass through unmodified per design choice 2). So BOTH `list` and `upsert` on `RolloverCandidateStore` are contractually never-throwing / fail-soft-to-empty-or-noop, and route.ts calls them with a defensive `.catch(() => [])` at the read call site purely as cheap extra insurance (safe to double-guard here, unlike the ledger's exclusion read).
5. Migration `web/supabase/migrations/20260924000500_dashboard_rollover.sql` (authored-only, same header convention): dedicated table `dashboard_rollover_candidates` (owner_id, canonical_key, aliases text[], payload jsonb, first_seen_at timestamptz default now(), last_pool_date text; primary key (owner_id, canonical_key); RLS owner-select-only + revoke/grant symmetry, no insert/update policy). A single atomic `upsert_rollover_candidates(p_owner_id, p_local_date, p_candidates jsonb)` RPC (one round trip for up to ~30 rows, mirrors `acknowledge_dashboard_batch`'s `jsonb_array_elements` idiom) does `insert ... on conflict (owner_id, canonical_key) do update set aliases=excluded.aliases, payload=excluded.payload, last_pool_date=excluded.last_pool_date` — `first_seen_at` is deliberately NOT in the `do update set` clause, so it survives every subsequent upsert untouched (this is the ONLY reliable way in this codebase's own established style to get partial-column-preserving upsert semantics — a generic PostgREST `.upsert()` was considered and rejected because this codebase consistently uses a dedicated plpgsql RPC whenever a write needs precise atomic/partial semantics, e.g. `increment_usage_counter`, `acknowledge_dashboard_batch`). Retention (30 days from `first_seen_at`) is enforced at READ time only (`list`'s `now`-based cutoff filter) — no purge/delete job, matching the brief's explicit "no purge job authorized."
6. Race safety for the mint-path upsert: on two concurrent first-of-day requests, `prepareBatch`'s own documented contract already discards a losing call's `servedItems`/`papers` and returns the winner's stored batch (existing P4-S3 behavior) — but a naive rollover implementation could still let the LOSING call compute a remainder from ITS OWN discarded `result.finalPool` and upsert garbage. Fix: after `prepareBatch` returns `minted`, compare `minted.papers` (identity keys, in order) against this call's own locally-computed `papers` array (built before the `prepareBatch` call) — only proceed to compute+upsert a rollover remainder when they match (i.e., this call's selection is the one that actually got frozen). A losing call skips rollover upsert entirely; the winner's own execution already performs it correctly. Will add a concurrent-requests test proving only one remainder (the winner's) is ever stored.
