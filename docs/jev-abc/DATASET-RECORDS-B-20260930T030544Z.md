## Task 1 — Path: how a non-paper record reaches the Papers feed

**OpenAlex — the path of the reproduced bug.** All three OpenAlex adapters (`web/src/lib/sources/openalex.ts:73`, `openalex-topic.ts:47`, `openalex-semantic.ts:39`) send an identical `select` parameter ending `...,type_crossref`. None select OpenAlex's own normalized `type` field, and none send a `type`/`is_paratext` filter — `openalex.ts`'s only `filter` entry is `from_publication_date` (`openalex.ts:84-87`; its own comment there records that a *venue* filter was tried once before and rejected by OpenAlex with an HTTP 400 that broke every query — relevant precedent for Task 3). All three route every result through the same `openAlexWorkToRawItem` (`web/src/lib/utils/openalex.ts:104-185`), which reads `w.type_crossref` into `metadata.workType` (`utils/openalex.ts:181`); `w.type` is never read, and the `OpenAlexWork` interface (`utils/openalex.ts:69-85`) doesn't even declare a `type` field.

Live-probed 2026-09-30 (unauthenticated `GET https://api.openalex.org/works/<id>?select=id,title,type,type_crossref,doi,primary_location`, 6 of the allowed 10 calls; raw responses saved as `<scratchpad>/b-probe-openalex-<ID>.json`): `type_crossref` was **absent from every one of the 6 responses**, including an ordinary journal article (`openalex:W7213451091`, `type:"article"`, no `type_crossref` key at all in the response). OpenAlex's own `type` field, by contrast, was present and correctly discriminating on all 6:

| Work | title | `type` | `type_crossref` | doi | venue |
|---|---|---|---|---|---|
| W7212231591 | O2-LCO-DATA | `dataset` | *(absent)* | 10.6084/m9.figshare.33608659 | Figshare |
| W7214074445 | O2-LCO-DATA | `dataset` | *(absent)* | 10.6084/m9.figshare.33608659.**v4** | Figshare |
| W7213505302 | TRFC Topological Crystallography and Solid-State Hydrodynamics | `preprint` | *(absent)* | 10.5281/zenodo.22813654 | Zenodo |
| W7214345696 | Lithium batteries of the Future | `conference-abstract` | *(absent)* | 10.6084/m9.figshare.33993697.v1 | Figshare |
| W7213599599 | Solid and Liquid Electrolytes for Li-ion Batteries | `book` | *(absent)* | 10.6084/m9.figshare.33931417 | Figshare |
| W7213451091 | LiCoO2/LiMn... Composite Cathode... (real journal paper, contrast case) | `article` | *(absent)* | 10.1002/smll.75564 | Small |

So today `metadata.workType` is a **dead field** for every OpenAlex-sourced item Peer fetches — confirmed independently on the actual saved local data too (Task 2: 0 of 636 OpenAlex item-occurrences across 44 saved snapshots carry any `workType` value, paper or not). Note also: a Figshare/Zenodo DOI prefix does **not** reliably mean `type: "dataset"` — the same registrant produced `book` and `conference-abstract` too, and Zenodo produced `preprint` (a type Peer plausibly wants to keep) — evidence used in Task 3's comparison of a `type`-filter vs a DOI-prefix filter.

Nothing downstream ever gates admission on `workType`. Repo-wide, the only production reader of `RawItem.metadata.workType` anywhere in `web/src/lib` is `isReviewLike` (`web/src/lib/scoring/review-policy.ts:89-90`), which uses it only as one signal to flag a review-shaped paper for scoring — never to exclude anything. A search for `is_paratext`/`paratext`/`figshare`/`zenodo`/`dryad`/`mendeley`/`dataset` under `web/src/lib/feed/` and `web/src/lib/scoring/` turns up only comments about the already-known version-dedup problem and synthetic test fixtures (e.g. `web/src/lib/scoring/__fixtures__/pool-2026-09-07.json`'s own Zenodo "Reservoir: A Large-Scale Simulated Dataset..." fixture item) — no exclusion logic anywhere.

Full path of the reproduced item: `fetchOne` (`openalex.ts:64-110`) → `openAlexWorkToRawItem` → `fetchImpl`'s `uniqueById(...).slice(0, limit)` (`openalex.ts:61`) → `buildPaperPool` (`feed/pipeline.ts:581`), which calls `bySourceId[s].fetch(...)` for every configured source (`pipeline.ts:631-634`) and merges results into `paperItems`, then `dedupItems(paperItems)` (`pipeline.ts:893`). This is not a one-off call site: the identical `bySourceId[sourceId].fetch(...)` shape recurs at the source-retry path (`pipeline.ts:1282`), and `dedupItems` recurs at 3 more merge points (cache-refresh `1345`, offline-retry `1860`, rollover `2022`/`2049`) — every build-time AND read-time path that (re)fetches or (re)merges OpenAlex results is equally exposed, since all of them share the one conversion function.

**Why the two versions were not deduped into one card (the other half of the symptom).** `dedupItems` (`feed/dedup.ts`) only merges two records via (i) a shared "strong" id-form key — DOI/S2/OpenAlex/arXiv/PMID, `canonical-identity.ts:189-230` — or (ii) a "weak" link requiring a shared **title alias** + published year within 1 + matching first-author surname (`paper-identity.ts:150-163`, `weakPairMatch`). Neither fires here:
- The two DOIs differ as strings (base vs `.v4`), so `doiCandidate` differs; each record's own OpenAlex work ID also differs (OpenAlex mints a separate Work per DOI version) — no strong link.
- `computeTitleAlias` (`canonical-identity.ts:151-156`) only produces a `title:` alias when the normalized title has >= 4 qualifying tokens (length >= 3 each). "O2-LCO-DATA" normalizes to "o2 lco data": "o2" is 2 chars (doesn't qualify), leaving only "lco" + "data" = 2 qualifying tokens — under the 4-token bar. `titleFormOf` (`canonical-identity.ts:258-261`) therefore returns `undefined` for **both** records, and `weakPairMatch`'s first check (`paper-identity.ts:153`, `if (!aTitle || !bTitle || aTitle !== bTitle) return false;`) fails immediately, independent of author/year. This is the same generic-title guard the codebase deliberately built to stop "Editorial"-style false merges (`canonical-identity.ts:150-156`'s own doc comment) — correctly conservative in general, but it means a short, machine-generated dataset title can never be recognized as a version pair by the existing weak-link rule.

**Other sources (same "path" question, less exposed in practice, evidence-scoped honestly):**
- **arXiv** (`sources/arxiv.ts`): no `workType` is even computed; arXiv's corpus is preprints by construction. Negligible/unevidenced risk.
- **Semantic Scholar** (`sources/semantic-scholar.ts:67,121`): `select`s `fieldsOfStudy` only; S2's own `publicationTypes` field is never selected or read, so `workType` is never set — same "field not fetched" shape as OpenAlex, but no non-paper example found in the local sample.
- **DBLP** (`sources/dblp.ts:178,181`): **does** set `metadata.workType = info.type` from DBLP's native type field (which does separate e.g. "Journal Articles" from "Informal and Other Publications") — but exactly like OpenAlex, nothing downstream ever reads it to exclude anything. No DBLP item appears anywhere in this investigation's local sample (battery-materials queries apparently never reach DBLP, a CS bibliography) — structurally identical risk, unconfirmed by sample.
- **PubMed** (`sources/pubmed.ts:183,186`): sets `metadata.workType = summary.pubtype?.[0]` from PubMed's own `pubtype` array, which legitimately includes non-article values ("Dataset", "Comment", "Published Erratum", "Retraction of Publication", ...) — never filtered downstream. In this investigation's local sample, all 16 observed PubMed occurrences carry `workType: "Journal Article"` uniformly (see Task 2 script output) — no non-article example was actually sampled, so (like DBLP) this is a structurally-identical, currently-unconfirmed-by-sample risk, not a reproduced one.
- **Web search / Hacker News** (`web-search.ts`, `hn.ts`): not paper-metadata sources at all — a different, pre-existing, already-understood product characteristic; out of scope.

**Client-side compounding gap.** Even where `metadata.workType` IS populated (DBLP/PubMed today; OpenAlex after any fix), it never reaches the reader. The only conversion from the internal `RawItem`/`ScoredItem` to the client-facing `Paper` shape, `rawItemToPaper`/`scoredItemToPaper` (`web/src/lib/feed/mapper.ts:95-154`), builds the returned object field-by-field and does **not** copy `workType` (it does copy `doi`, `preferenceSignals`, etc. — `workType` is simply omitted at lines 124-145). `Paper` itself (`web/src/types/index.ts:82+`) declares no `workType`/`type` field at all. So today the reader's only type-like signal on a card is the plain `venue` string (`<Tag>{paper.venue}</Tag>`, `web/src/components/cards/paper-card.tsx:57`) — "Figshare" is shown, but nothing marks it as "not a paper." There **is** an existing, reusable "eyebrow" label slot directly above the title for exactly this purpose (`paper-card.tsx:24,31-37`, `typeLabel = reviewPaperLabel(paper)`), modeled on `reviewPaperLabel` (`web/src/lib/papers/report.ts:200-203`) — today that function is purely a title-text regex match for "review"/"survey"/"meta-analysis", unrelated to `workType`; it is not itself a dataset-label mechanism, but it is the closest existing precedent/anchor point for one (used in Task 3, option b).

## Task 3 — Options

### (a) Exclude non-paper OpenAlex types

**(a-query) at the query**, via an OpenAlex `filter=type:...` (or its documented negation form, e.g. `!dataset`) added to the 3 adapters' `params.filter`.
- Reader sees: the excluded item never appears at all; one fewer feed slot spent on it.
- What could be lost: a reader who wants to see the excluded record types loses that visibility entirely and silently (see POLICY 1). A `type`-based filter (unlike a repo-DOI-based one) does *not* lose a legitimate Zenodo-hosted `preprint` — Task 1's probe shows `preprint` is a distinct, non-excluded value.
- Cost: touches 3 files (`openalex.ts`, `openalex-topic.ts`, `openalex-semantic.ts`) — a small filter-string change to each (the 3 files currently hardcode an identical `select` string separately; centralizing it would be a nice, optional, pre-existing-duplication cleanup while in there).
- Risk: **this codebase has already been burned once** by an unverified OpenAlex filter parameter taking down every query with an HTTP 400 (`openalex.ts:78-83`'s own comment, about a rejected venue filter). This investigation's network budget covers only single-work `GET /works/<id>` lookups, not a `/works?filter=...` search call, so the exact filter syntax (does `type:!dataset` really work; can it combine with `from_publication_date` in one `filter=` string) is **unverified** here and must be confirmed against OpenAlex's docs or a real filtered call before shipping — flag as a CONTRACT ASSUMPTION, matching this codebase's own convention for exactly this kind of not-independently-re-verified vendor behavior (see `openalex-topic.ts`'s own OR-pipe filter comment).
- Cache-version bump: **yes** — changes which items are admitted into the pool at all; bump `PAPER_CACHE_KEY_VERSION` (`web/src/lib/opportunities/pool-cache.ts:343`, currently 18).

**(a-post) after fetch**, dropping any item whose `type` is in a small excluded set once `openAlexWorkToRawItem` (or each adapter's own `.map(...)` step) has built it.
- Reader sees: same as (a-query) — the item never reaches scoring/dedupe/the feed.
- What could be lost: same as (a-query), plus a strictly-worse efficiency trade-off vs (a-query): a dropped item still consumed one of that call's `per_page`/`perQuery` result slots (`openalex.ts:38`) before being discarded, so a call whose top OpenAlex results happen to include several datasets returns fewer real candidates than requested. The pipeline pools multiple queries/channels before scoring, so this is a minor efficiency cost in practice, not a correctness bug — but it is real and worth naming.
- Cost: same 3 files; needs `type` added to `OpenAlexWork` (`utils/openalex.ts:69-85`) and to each adapter's `select` string (all 3 currently omit it), and `workType` repointed to prefer `w.type` over the dead `w.type_crossref` (`utils/openalex.ts:181`) — e.g. `workType: cleanDisplayTextOrUndefined(w.type ?? w.type_crossref)` (keeps the old fallback harmlessly, in case OpenAlex ever repopulates it for some record type this investigation didn't sample). Then a plain filter after the `.map()` — no new query parameter, so no 400 risk.
- Cache-version bump: **yes**, same reasoning as (a-query).
- **Given the codebase's own burned history with query-time filters and this investigation's inability to verify the filter syntax within its network budget, (a-post) is the safer sub-option to ship first; (a-query) can follow later as a verified optimization.**

### (b) Keep datasets, but label them

- Reader sees: the record stays in the feed (still costs a slot) but now carries a visible, honest marker — e.g. reusing the existing eyebrow-label slot already wired above the title (`paper-card.tsx:24,31-37`), modeled on the sibling `reviewPaperLabel` (`papers/report.ts:200-203`).
- What could be lost: nothing hidden — this is the option that loses the *least* information. The trade-off runs the other way: `docs/PRODUCT_DIRECTION.md`'s own stated hard rule ("ten precise items are better than one hundred noisy items") cuts toward not spending a scarce slot on a non-paper at all, labeled or not.
- Cost: three small, precise touch points, all newly threading a value that would already exist server-side once (a-post)'s `select`/mapping half is done: (i) `web/src/lib/feed/mapper.ts:124-145` — add `workType: item.metadata?.workType` to the object `rawItemToPaper` returns (it currently copies `doi`/`preferenceSignals` but omits `workType` entirely); (ii) `web/src/types/index.ts:82+` — add the field to `Paper`; (iii) `web/src/components/cards/paper-card.tsx` — a sibling to `reviewPaperLabel` returning e.g. "Dataset" when `workType === "dataset"`. None of this touches retrieval, scoring, or dedupe.
- Cache-version bump: **no**, if purely additive metadata + a UI label with no ranking change — the same shape as every other additive `metadata` field already documented as safe without one (`admissionChannels`/`mergedFrom`/`mergedAliases`, `sources/types.ts:83-150`'s own doc comments: absent on an already-cached item, degrades gracefully). If paired with any ranking/inclusion change, that part needs the same bump as (a).
- Genuine alternative to (a), not strictly weaker — see POLICY 1.

### (c) Version-DOI alias for repository DOIs (the DEDUP-ANGEW pattern) — independent of (a)/(b)

- Mechanism: exactly analogous to `dualEditionDoiAlias` (`canonical-identity.ts:113-117`) — a small, additive, named regex that, for a DOI shaped `<registrant>/<suffix>.v<N>`, also emits a `doi:<registrant>/<suffix>` alias (the base work's own key), so `canonicalPaperKey` (`canonical-identity.ts:189-230`) adds it to `aliasSet` and pass-1 **strong-link** clustering transitively merges the two versions via the already-hardened shared-id-form-key path — no change to `clustersFullyMatch`/`weakPairMatch`/`dedup.ts`'s survivor-selection loop (same "purely additive, nothing else touched" property DEDUP-ANGEW's own comment block emphasizes, `canonical-identity.ts:94-99`). Empirically verified shape: Figshare's version convention IS a plain textual `.v<N>` suffix on the same DOI (confirmed live on both W7212231591/W7214074445) — a clean, safe regex target, same idea as arXiv's existing `stripVersionSuffix` (`canonical-identity.ts:172,178`).
- Scope limit, evidenced not assumed: this only helps repositories that version this way. **Zenodo does not** — it mints a fully separate numeric DOI per version (a "concept DOI" vs per-version DOIs), no shared textual suffix a regex could derive one from the other. No Zenodo version-duplicate pair was found in the local sample (Task 2), so this isn't evidenced as an active bug the way Figshare's is. Dryad/Mendeley Data/OSF's own version conventions are **unverified** here — none of the three appeared in the local sample.
- Reader sees: the two versions collapse into one card (`mergedFrom`/`mergedAliases` record the loser, same as any other merge), freeing the slot the duplicate wasted — but the surviving card is still a dataset record, unlabeled, unless (a)/(b) are also done.
- What could be lost: nothing new — a merge never silently drops information, same guarantee every existing dedup rule already gives.
- Cost: one file (`canonical-identity.ts`), purely additive, small — same size/shape as DEDUP-ANGEW's own diff.
- Cache-version bump: **yes** — same reasoning as DEDUP-ANGEW's own "cache 12 → 13" (any canonical-identity/clustering change invalidates old cached pools built under the old identity rule); bump `PAPER_CACHE_KEY_VERSION` (currently 18, will have moved again by the time C implements this — re-check the live value, don't assume 18).
- Narrow, defense-in-depth fix, **not** a substitute for (a)/(b): even a perfectly-deduped O2-LCO-DATA is still a dataset occupying a Papers-feed slot.

### (d) Other options considered

- **Blunt repo-DOI-prefix/venue exclusion** (skip the `type` question, just drop anything whose DOI starts with one of the 5 named prefixes or whose venue matches): **rejected** as the primary mechanism. This investigation's own probes show a Figshare-hosted record can be `type: "book"` or `"conference-abstract"`, and a Zenodo-hosted record can be `type: "preprint"` — so a DOI-prefix rule both under-excludes (any `dataset`/`report`/`grant`/etc. hosted on a registrant *not* in the 5-name list, e.g. a university institutional repository, sails through untouched) and over-excludes (a legitimate Zenodo preprint dropped only because of *where* it's hosted, not *what* it is). `type` is the principled signal; DOI-prefix/venue was only ever this investigation's local-data stand-in for `type`, because `type` isn't saved locally today.
- **Scoring-only demotion** (leave a `dataset`-typed item in the candidate pool, but heavily down-rank it instead of excluding or merely labeling it): a middle ground between (a) and (b); needs the same `type`-selection fix as (a)/(b), lives in scoring rather than fetch/mapper, and does need a cache-version bump (it changes ranking). Not explored in the same depth as the 3 named options here — flagged as a POLICY-adjacent alternative to a hard in/out binary.

### Recommendation

Ship **(a-post) + (c) together**. (a-post) is the root-cause fix — a non-paper record stops occupying a Papers-feed slot at all, regardless of whether it's ever duplicated — and is the cheapest, lowest-risk option (no new query parameter, no UI work, no repeat of the codebase's own past OpenAlex-filter 400 incident). (c) is small, additive, and independently worth having as defense-in-depth for whatever non-paper types POLICY 1 decides to keep, or for any repository/type (a)'s exclude-list doesn't (or can't yet) catch. (b)'s UI labeling is a reasonable alternative-or-addition to (a) if POLICY 1 decides datasets should stay visible — sequence it after (a-post)+(c) land and POLICY 1 is actually decided, rather than building it speculatively.

### POLICY list for the manager

1. **Do datasets (and other non-paper OpenAlex/DBLP/PubMed types) belong in the Papers feed at all** — excluded entirely (option a), kept but honestly labeled (option b), or kept and down-ranked (option d's scoring-demotion variant)? This is the product/UX call this investigation was told to measure and not decide. `docs/PRODUCT_DIRECTION.md`'s "ten precise items are better than one hundred noisy items" cuts toward exclusion, but a materials researcher plausibly wants to know about a relevant public dataset too — this specific record's own abstract calls it "the training dataset and ML predicted result in the submitting paper," i.e. a companion artifact to an actual paper a reader might separately want to find.
2. **If (a)/(d) is chosen, which OpenAlex `type` values count as "not a paper"?** This investigation empirically probed only 6 records, covering `dataset`, `preprint`, `conference-abstract`, `book`, `article`. `preprint` looks like something Peer wants to *keep* (a Zenodo-hosted preprint is still a paper draft); `conference-abstract` and `book` are genuinely borderline (arguably still "research," just not a journal article). This needs an explicit include/exclude ruling per value, not a blanket guess — and the full OpenAlex `type` vocabulary should be confirmed against OpenAlex's current docs (this investigation's network budget covered only single-work lookups, not the docs site) before any exclude-list is finalized.
