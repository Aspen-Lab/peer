**Result: CONFIRMED FAIL.** `dedupItems([A, B, C])` returns **1** item, not 2 or 3. Root cause, precisely: `dedup.ts`'s pass 2 (lines 123-132) evaluates each pair within a title bucket independently via `sameCanonicalWork`, then unions the ones that return true. `sameCanonicalWork(A,B)` returns true (B carries zero id-form keys, so the conflict guard `aIds.length>0 && bIds.length>0` never fires — it falls straight through to the title/year/author check, which matches). `sameCanonicalWork(B,C)` returns true for the identical reason. `sameCanonicalWork(A,C)` correctly returns **false** (both carry a real, disagreeing DOI — the conflict guard fires as designed). But `DisjointSet.union(A,B)` followed by `union(B,C)` makes `find(A) === find(C)` transitively regardless of the direct pairwise verdict — union-find has no notion of "these two are explicitly forbidden from joining." The direct-conflict check the module correctly implements pairwise is silently bypassed by composition. This is a real, realistic failure mode (dblp entries missing DOIs are common), not a contrived edge case, and it directly contradicts §1p.A's "on conflict... keep both" and the F-A-P2-01 finding's own concern (F-A-P2-01 was explicitly "acceptance 6b" — silently merging distinct papers).

## NEW FINDINGS (ranked)

**F-A-P2S1-01 [INCORRECT DATA — acceptance 6b, 6d — HIGH SEVERITY] `dedupItems`'s union-find composition can transitively merge two papers that directly conflict, silently dropping one, when a third bridging record with no ID-form key is present.**
Reproduction: item A (DOI `10.1111/aaa`) and item C (DOI `10.2222/ccc`, same title/year/author as A — these two, compared directly, correctly stay 2 per `sameCanonicalWork`'s conflict guard) both title/year/author-match a third item B that carries **no DOI or other ID-form key at all** (realistic: this is an ordinary shape for a dblp record). `dedupItems([A, B, C])` returns **1** survivor, discarding one of A or C with zero trace beyond the internal `mergedFrom` list of the survivor no one else is holding a reference to. Cause: `dedup.ts:110-132`'s title-bucket pass runs `sameCanonicalWork` pairwise and unions on every `true`, but a pairwise `false` (the correctly-detected A-vs-C conflict) carries no weight once both A and C are separately, correctly unioned with B — transitive closure erases the conflict signal the pairwise function computed correctly. Fix direction (not implemented — this is a review, not a fix): before folding a group at the end of pass 2, or instead of blind pairwise union, detect when a candidate union would join two SUBGROUPS that each already contain a mutually-conflicting real ID-form key pair, and refuse that specific union (keep the conflicting subgroups separate, each still absorbing the harmless bridge on whichever side it was first attached to, or split the bridge itself rather than the two ID-bearing records) — a graph-coloring/conflict-aware union rather than plain union-find. This needs a design decision, not a one-line patch; flagging for B/manager rather than prescribing the exact algorithm.

**F-A-P2S1-02 [CONTRACT-TEXT GAP — acceptance 6d — MEDIUM SEVERITY] Survivor's own metadata does not carry a union of the merged records' IDs/aliases, only a `{source,id}` reference list.**
§1p.A: "the survivor carries `mergedFrom` provenance **and the union of IDs/aliases**." `dedup.ts:167-173` only does the first half. Empirically confirmed (Probe 3): merging a DOI-only S2 survivor with an arXiv-ID-carrying loser (same DOI) leaves the survivor's own `metadata.externalIds` without the arXiv id, and re-deriving `canonicalPaperKey` from the survivor RawItem alone (as any future consumer reading only the returned pool would) produces **no** `arxiv:` alias. Matters directly for §1p.A's own stated reuse: the P4 delivery ledger is specified to match on "key or ANY alias" (`isDeliveredIdentity`) — a merged item that lost an alias along the way is a candidate for exactly the false-non-exclusion the P4 design is trying to prevent, once P4 is built on top of this. Low blast radius today only because P4-S1+ hasn't been wired to read this yet.

**F-A-P2S1-03 [SCOPE NOTE — acceptance 6d — LOW SEVERITY, may be intentional] `mergedFrom` provenance does not reach the mapped API/UI response.**
`feed/mapper.ts` field-maps explicitly and never forwards `metadata.mergedFrom`/`externalIds`. This is correct and desired from a leak-prevention standpoint, but it also means "provenance preserved through dedupe" is true only inside the internal pool, never externally observable. The task itself flagged this as a possible, acceptable gap to simply document — doing so here. Manager should confirm whether P2-S1 was ever expected to wire this further, or whether it is deliberately deferred (no slice in B's guide currently assigns it).

**F-A-P2S1-04 [MINOR — determinism smell, not a 6a-6d failure] Survivor selection on a same-source-priority tie (dblp vs pubmed, both weight 2) is input-array-order-dependent.**
Group membership itself is order-independent (verified by reasoning + spot-checked); only WHICH tied-priority record represents an already-correctly-merged group depends on array position. Low real-world impact today since `allItems`'s order is itself deterministic per a fixed `req.sources` ordering, but worth a documented, explicit tie-break (e.g., lexicographic on id, or a a richer-metadata heuristic) rather than implicit first-wins, especially once RRF (P2-S6) or additional channels (P2-S4) make item order less predictable.
