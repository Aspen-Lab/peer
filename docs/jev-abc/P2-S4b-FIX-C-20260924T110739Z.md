## DESIGN CHOICES / ASSUMPTIONS (disclosed, not silently decided)
1. **Negative-seed bound reuses `POSITIVE_SEED_LIMIT`'s value (10) as `NEGATIVE_SEED_LIMIT`.** §1p.B(5) only specifies "most recent 10" for positive seeds explicitly; it says "'Not interested' supplies negative seeds" with no explicit number. Chose the same bound for symmetry and because it's a defensible, conservative default — not a re-derivation from a cited source. A fresh A should judge whether this needs an explicit ruling or is fine as a disclosed default.
2. **Negative-seed resolution gated on `channelS2RecommendationsEnabled()` specifically, not `anyPositiveSeedChannelEnabled()`.** Deliberate and narrower than the positive resolver's gate: negative seeds have exactly one consumer (S2's `negativePaperIds`) in this codebase, so resolving them whenever only OpenAlex-similarity or citation-neighbours is on would be a wasted Supabase round-trip for data nobody would ever use. Proven by a dedicated route.test.ts case ("a positive-seed channel is on (similarity) but S2 specifically is off...").
3. **Two separate `SupabasePositiveSeedFeedbackRepository` constructions per request when both resolvers fire** (`resolvePositiveSeedsForRequest` and `resolveNegativeSeedPaperIdsForRequest` each construct their own), rather than sharing one instance. Chosen for structural symmetry/reviewability with the pre-existing positive-only pattern over a micro-optimization; the repository constructor is cheap (no network call, per `configuredFeedbackClient`'s own contract), and query COUNT (2 Supabase reads when both fire) is identical either way — only object construction is duplicated, not I/O.
4. **No cross-filtering between positive and negative resolution.** If an owner both "liked" AND, at a different time, marked the SAME paper "Not interested" (feedback is append-only, so both rows can coexist), that paper's S2 id could appear in both `positivePaperIds` and `negativePaperIds` in the same S2 request. Not resolved by this slice — out of the 5-item scope, and how the S2 API itself would resolve that conflict is unverified. Disclosed here for a fresh A to judge, not silently handled either way.
5. **`fetchPositiveSeedCandidates`'s existing early return (`seeds.length === 0 -> return {items:[], errors:{}}` before ever looking at negative ids) means negative-only feedback (no positive feedback at all) produces zero S2 calls.** This is not a gap — S2's Recommendations API fundamentally needs a positive example to recommend from — but it means a user who only ever clicks "Not interested" and never Saves/Likes/"More like this" gets no benefit from their negative signal in THIS channel (there is no channel in this codebase that consumes negative-only signal). Matches the adapter's own pre-existing contract; disclosed, not a regression this slice introduced.
