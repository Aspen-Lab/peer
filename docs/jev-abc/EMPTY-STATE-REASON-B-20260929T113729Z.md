# EMPTY-STATE-REASON — investigation guide (agent B)

Scope reminder: the ask is to make the home page's empty state name its cause honestly, from a small fixed set of reasons the pipeline can compute from facts it already touches — never a guess. This guide covers only that. It does not touch product code.

## §1. Path enumeration — every way the returned list ends up empty

The live incident this item exists to fix is already recorded: ABC-JEV-INTEGRATION.md §4 "EMPTY-HOME diagnosed" (2026-09-28 ~06:15-06:35Z) — a temporary `console.log` probe in `pipeline.ts` (since removed) measured, for the real user's home load, `pool=1 inWindow=1 scored=1 excludeIds=1 fresh=0 returned=0` (i.e. the Required gate let exactly one paper through and the delivery exclusion then removed it), and for the manager's own signed-out controls, a case where the same chain hit zero at `scored` (Required gate rejected everything). ```

## §2. Reason codes and their sentences

A small, fixed set — four new codes, computed only from a strict waterfall over facts the pipeline already touches (extended per §3), evaluated **only when `returned.length === 0`**, checked in this order (first match wins; each check is a plain zero-comparison, never a heuristic):

1. `everySourceFailed(pool.sourceStatus)` (existing helper, `pipeline.ts:1032-1039`, restricted to the 5 registered `ACADEMIC_PAPER_SOURCES` on purpose — it already ignores the optional semantic/citation channels, and that scoping should be reused, not re-derived) → **`sources-unreachable`**
2. else `inWindow.length === 0` → **`no-results`** (folds in paths #2 and #3 — "nothing came back" and "nothing was recent enough" get the same honest, non-actionable sentence, because neither has a specific fix to suggest)
3. else `scored.length === 0` → **`no-required-match`** (folds in paths #4, #5, #6 — see the POLICY note below on whether #5 should split out)
4. else (only possible when `scored.length > 0` but `returned.length === 0`, i.e. `journalRanked`/`fresh` lost everything to the exclusion filter — `scored`, `tier1Ranked`, `aiRanked`, `journalRanked` are all same-length reorderings of one another, so this branch is exact, not a guess) → **`already-delivered`**

| Code | Draft title | Draft line | Next step offered | Maps to path(s) |
|---|---|---|---|---|
| `sources-unreachable` | "Couldn't reach today's paper sources." | "This isn't the same as finding nothing — Peer wasn't able to search at all. Refresh to try again." | Refresh (existing action, existing handler) | 1 |
| `no-results` | "Nothing new for these topics today." *(verbatim reuse of today's title)* | "Peer only sends what is new and relevant. Refresh to look again, or widen your topics." *(verbatim reuse of today's line)* | Refresh / Widen topics (existing actions) | 2, 3 |
| `no-required-match` | "None of today's papers matched your Required topics." | "Try a broader topic in Profile, or review your excluded terms." | Widen topics → /profile (existing action) | 4, 5, 6 |
| `already-delivered` | "You're caught up on these topics." | "Every match for today was already in your feed. Check back after it refreshes, or widen your topics." | Refresh / Widen topics (existing actions) | 7 |

These titles/lines are drafts for the manager, not final copy — see the POLICY list in §4. `no-results` is deliberately identical to today's existing default: the value of giving it its own code is future precision (tests, telemetry, room to word it differently later), not a copy change this round.

**Where the copy must stay silent rather than guess** (return no code — the page falls back to today's generic `"empty"` sentence, unchanged):
- Any response replayed from a frozen batch (§1 path #11) whose stored row has no saved reason (every batch minted before this ships, and — see §3 — the `resolveServedItems()` reconstruction-fallback branch, which re-runs the pipeline under deliberately *loosened* filters (`excludeIds: undefined`, no `ledgerExclusions` — `route.ts:144-146`) to replay an already-decided batch, not to re-decide membership; if that reconstruction itself comes back empty, the true cause is "a source stopped carrying these specific papers by today," which fits none of the four codes and must not be forced into one).
- Any response where the four-way waterfall in §2 does not cleanly resolve (should be unreachable given the invariants above, but the implementation must return `undefined`/omit the field rather than throw or default to a specific code if it ever is).
- Never invent a count-based sentence ("3 papers were filtered by your exclusions") from data the pipeline does not exactly have — e.g. do not attempt to separately blame path #5 (reader's own exclusions) vs #4 (Required gate) vs #6 (review filter) unless POLICY explicitly asks for the extra counter described below, because today's code cannot honestly tell them apart.

## §3. How the reason travels

**Compute it once, server-side, at the tail of `runFeedPipeline`** (`pipeline.ts`, right where `errors`/the final `return` are already assembled, `pipeline.ts:2116-2154`) — not inside `buildPaperPool`. Reasoning: the read-time chain (`inWindow`, `scored`, `fresh`/`returned`) already runs fresh on *every* request, cache hit or miss (`pipeline.ts:1983-2094`), and reflects *this* request's own topics/window/exclusions — exactly the property that made the EMPTY-HOME probe's numbers trustworthy. `buildPaperPool`'s own counters (`beforeDedup`/`afterDedup`) do not have this property: on a cache hit they collapse to `pool.items.length` for both (`pipeline.ts:2126-2127`, a pre-existing, documented, accepted trade-off — out of scope, do not "fix" it as part of this item). `pool.sourceStatus`, by contrast, **does** survive a cache hit (it is stored on the cached pool and already used for `meta.errors` on a cache-hit response via `errorsFromSourceStatus`, `pipeline.ts:2106-2108`), so it is safe to reuse for the `sources-unreachable` check regardless of cache state.

Concretely (illustrative, not prescriptive — C decides exact form): a small pure helper colocated near `everySourceFailed`/`errorsFromSourceStatus` (`pipeline.ts:~1040-1064`), taking `pool.sourceStatus`, `inWindow.length`, and `scored.length` (already in scope at `pipeline.ts:2015-2016`), returning one of the four §2 codes or `undefined`; called at the final return only when `returned.length === 0`.

**Response shape** — one new, small, additive field. `FeedMeta` (`types.ts:69-114`) gains:
```
emptyReasonCode?: "sources-unreachable" | "no-results" | "no-required-match" | "already-delivered";
```
present only when `returned.length === 0` and the waterfall resolved (structurally absent otherwise — same conditional-spread convention this file already uses for `rrf`/`finalPool`, `pipeline.ts:2148`, `2153`). Recommend naming the union type `FeedEmptyReasonCode` and defining the existing client-side `EmptyReason` (`empty-reason.ts:24`) as `"intent-required" | "error" | FeedEmptyReasonCode` so the four strings are declared once. No other existing `FeedMeta` field changes shape or meaning. Do **not** add `afterWindow`/`afterGate` themselves to the wire format — they are local to the computation, not needed by the client, and keeping them server-internal keeps the diff small (a POLICY option below if the manager wants them for future telemetry).

**Cached pools** — the shared per-day `CachedPaperPool`/`PoolCache` (`pool-cache.ts`) must **not** store a reason code. The Required gate is part of a pool's cache-key identity (a pool is only ever shared between readers who declared the same topics that day), but the reason is still fundamentally a per-reader, per-read computation (it depends on *this* reader's exclusions/delivery history too, which are never part of the shared pool) — it must be computed at read time on every non-frozen read, never baked into the shared pool object.

**The frozen batch is the one place this needs a real design decision**, because of path #11 in §1: a replay has no pipeline run to compute anything from. Two options, in increasing order of cost — this is a POLICY call, not mine to make:
- **(a) Live-only (cheap, recommended for this batch):** compute and return `emptyReasonCode` only on paths that actually run `runFeedPipeline` this request — signed-out, `PEER_DASHBOARD_LEDGER` off, the GET route, and the first mint of a signed-in reader's batch each day. Leave it structurally absent on every frozen-batch replay (`frozenFeedResponse`, `route.ts:96-118`) — a signed-in reader's first load of an empty day sees the specific reason; their second-and-later loads that same day keep seeing today's generic sentence, exactly as now, until the next local day mints a fresh batch. No schema change, no migration.
- **(b) Full coverage (real cost):** persist `emptyReasonCode` on `DashboardBatch` (`delivery-ledger.ts:110-133`) at mint time, the same way `servedItems` was added (P4-S3, `delivery-ledger.ts:204/340`, `route.ts:348-354`) — a new optional trailing parameter on `prepareBatch()`, a new nullable column on the Supabase-backed implementation (`delivery-ledger.ts:~480-490` row mapping, `~600-625` write), read back in `frozenFeedResponse`/`resolveServedItems` (`route.ts:96-155`) and passed through untouched. A legacy batch with no stored value simply has the field absent on replay (§2's "stay silent" case) — never guessed retroactively. This needs an actual migration, mirroring `servedItems`' own (referenced in DESIGN §5 of `docs/jev-abc/P4-B-20260924T0338Z.md`).

**The digest email's own empty case** — `renderDigestHtml()` (`web/src/lib/email/digest-template.ts:139-149`) has the identical structural gap: one generic sentence ("No items matched your topics today. Try adjusting your signals.") for every cause, called from `dispatch-digests/route.ts:144` and `send-digest.ts:82` with only `{firstName, items, originUrl}` — no `meta` reaches it today. Recommend leaving it untouched this round (§1ao.7, the ruling that opened this item, named only the home empty state) and threading the same `emptyReasonCode` through as a small, low-risk follow-up once the page-side plumbing exists and is verified. Flagged as a POLICY item in §4, not decided here.

**What must not change** (explicit, for C and for the fresh A that reviews this):
- `ledgerUnavailableResponse()`'s 503 (`route.ts:61-75`) stays a distinct, uncached error — never folded into any `emptyReasonCode`.
- The 429 rate-limit response (`ai-request.ts:165-180`) stays a distinct `feedError` — never folded in.
- `"intent-required"` stays entirely client-derived (`page.tsx:266`) and untouched.
- Every existing `FeedMeta` field (`fetched`, `errors`, `beforeDedup`, `afterDedup`, `returned`, etc.) keeps its exact current shape and meaning — this is a purely additive field.
- The cache-hit degradation of `beforeDedup`/`afterDedup` to `pool.items.length` (`pipeline.ts:2126-2127`) is pre-existing and out of scope.
- The two-button action row in `BriefingEmpty` (Refresh / Widen topics, `page.tsx:653-666`) stays wired exactly as today for every non-error reason — only the title/line text above it changes per code. `BriefingEmpty`'s `reason` prop (`page.tsx:628`) widens from `"intent-required" | "error" | "empty"` to the fuller `EmptyReason` union; its `copy` lookup (`page.tsx:633`, into `BRIEFING_EMPTY` / `copy.ts:25-38`) gains the four new keys, falling back to the existing `empty` entry whenever `emptyReasonCode` is absent.
- `emptyReason()` (`empty-reason.ts:26-36`) keeps its exact existing precedence — loading/non-empty beats everything (returns `null`); `intentRequired` beats everything else; `feedError` beats a reason code (a thrown error and a server-computed empty-reason code can never both be live for the same load, since a code only ever arrives on a *successful* 200 response, but the precedence must still be coded explicitly, not left to accident) — and only then falls through to a new optional `reasonCode` input, defaulting to `"empty"` when absent. On the client (`store/feed.ts`), `RealFeedResult` (`store/feed.ts:731-735`) gains `emptyReasonCode?: FeedEmptyReasonCode`, forwarded from `data.meta?.emptyReasonCode` in `fetchRealFeed` (mirrors how `batchId`/`batchStatus` are already forwarded, `store/feed.ts:776-777`) and written into a new store field in the *same* `set()` call as `papers`/`papersLoading` (`store/feed.ts:~1789`, matching the existing "set everything about one response together" discipline already documented there for `renderedBatchId`) — never read stale across loads, exactly like `feedError` already isn't.

## §4. Tests for C, and the POLICY list

**Tests (pipeline-level, constructed pools — no network):**
1. `sources-unreachable`: every attempted academic source's fetch promise rejects (reuse `pool-degraded.test.ts`'s existing failure fixtures rather than inventing new ones) → `meta.emptyReasonCode === "sources-unreachable"`, `items: []`.
2. `no-results` (empty fetch): every source resolves to `[]`, no rejections → `"no-results"`.
3. `no-results` (stale): candidates fetched and deduped, but every `publishedAt` is outside `staleAfterDays()` for the request's window → `"no-results"`.
4. `no-required-match`: in-window candidates whose title/abstract/tags share no content word with any Required topic (T1-T4 all miss — reuse a confirmed non-match fixture from `required-gate.test.ts`/`admission.test.ts` if one exists) → `"no-required-match"`.
5. `no-required-match` (exclusion variant): a candidate that would otherwise match a Required topic, but also contains a reader-declared exclusion term → still `"no-required-match"` under the recommended folding (§2) — or its own assertion if POLICY splits it (see POLICY 3 below).
6. `already-delivered`: a candidate that clears the Required gate, then is removed via `excludeIds` — separately, a second case removing it via a constructed `ledgerExclusions` set → both `"already-delivered"`.
7. **Precedence guard (mutation-style):** a pool with *partial* source failure (some sources fail, at least one succeeds-empty) plus zero in-window candidates → must be `"no-results"`, not `"sources-unreachable"` — proves the waterfall checks "every" source, not "any." A second case: a candidate that clears the gate then gets excluded must report `"already-delivered"`, not `"no-required-match"` — proves the order is gate-before-exclusion, not the reverse.
8. **Frozen-batch replay:** a batch minted with a stored `emptyReasonCode` → a same-day replay (GET or POST) returns the identical code without a second `runFeedPipeline` call (mirror the existing "no pipeline call on replay" assertions already in `route.test.ts`'s ledger-aware block). A batch with no stored code (constructed to simulate a pre-existing row) → replay's `meta.emptyReasonCode` is absent, never guessed.
9. **Non-empty regression:** any response with `items.length > 0` → `meta.emptyReasonCode` is structurally absent (`.not.toHaveProperty("emptyReasonCode")`, matching the existing `finalPool` test's style), and every existing `FeedMeta` assertion in the current suite still passes unmodified.
10. **Client store (`feed.test.ts`):** a mocked `/api/feed` 200 response with `items: []` and `meta.emptyReasonCode: "already-delivered"` → after `loadFeed`, the new store field equals `"already-delivered"`. The same with the field omitted (older/un-migrated server) → the store field is `null`/`undefined`, no crash, no invented value.
11. **`empty-reason.ts` unit tests** (extend `empty-reason.test.ts` in place, same `describe`/`it` style already there): each of the four new codes, passed through a new `reasonCode` input, is returned verbatim when `papersCount === 0`; `feedError` still wins over any `reasonCode` (extend the existing "reports a failed fetch as an error" case); `intentRequired` still wins over any `reasonCode`; `isLoading`/`papersCount > 0` still short-circuit to `null` regardless of `reasonCode`; an absent/unrecognized `reasonCode` with everything else empty still returns `"empty"` — this last one is the literal "stay silent rather than guess" contract and deserves its own named test.
12. **Ordinary non-empty page unchanged:** whatever render-level test harness exists for `BriefingEmpty`/`empty-state.tsx` (note: the repo has none for `page.tsx` itself — see the standing comment at `page.tsx:154-155`) should confirm the two action buttons render identically across every non-error reason code, and that a normal papers response never shows `BriefingEmpty` at all.

**POLICY — manager decides:**
1. Exact wording of all four title/line pairs in §2 (drafts only).
2. Whether to ever show counts in the sentence (e.g. "12 papers didn't match") — today's copy never shows numbers anywhere in the empty state; recommend keeping it that way for consistency with `docs/PRODUCT_DIRECTION.md`'s "calm, not noisy" rule, but it's a real option.
3. Whether to split path #5 (reader's own exclusions) out of `no-required-match` into its own 5th code. Doing so needs a new counter inside `scoreItems()`'s loop (`combine.ts`) separating the two `continue` sites at lines 195 and 316, which today share one `passed`/`scored` array. Recommend **not** splitting for v1 — both cases are equally well served by "review your topics and exclusions in Profile," and the counter adds real complexity to a hot scoring loop for a distinction the reader may not care about.
4. Frozen-batch coverage: ship §3 option (a) "live-only" first, or go straight to (b) "persist on `DashboardBatch`" (real migration cost, mirrors `servedItems`'). Recommend (a) for this batch.
5. Whether the digest email (`digest-template.ts`) gets reason-specific sentences in this same batch, or stays generic with its own follow-up item. Recommend deferring — this item's own opening ruling (§1ao.7) named only the home empty state.
6. The four reason-code string values themselves (`sources-unreachable`/`no-results`/`no-required-match`/`already-delivered`) are a naming proposal, not final — bikeshedable, but keep it a small, fixed, closed set (resist adding a 5th/6th without a fresh measured incident the way `EMPTY-HOME` justified this item).
7. Whether to also expose the two new internal counters (`inWindow.length`, `scored.length`) on the wire for future debugging/telemetry, or keep them fully server-internal as recommended in §3.
