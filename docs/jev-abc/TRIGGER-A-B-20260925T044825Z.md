### 1.3 Prepared ≠ served — proof, not assertion

`web/src/lib/dashboard/delivery-ledger.ts` (module header + interface, lines 1-226): batch statuses are exactly `'prepared' | 'served' | 'acknowledged'`. `prepared`: "selected, never sent to a client." Only `acknowledgeBatch` copies papers into the permanent lifetime ledger (`listDelivered`). `prepareBatch` is idempotent — first writer for an `(ownerId, localDate)` wins, a losing call's `papers`/`servedItems` are discarded and the existing batch is returned unchanged.

`web/src/lib/dashboard/prepare-worker.ts`: `PrepareWorkerDeps.ledger: Pick<DashboardDeliveryLedger, "getBatch" | "prepareBatch">` — **structurally**, not just by convention, this file cannot call `markServed` or `acknowledgeBatch` even by mistake; TypeScript won't compile a call to a method the `Pick` doesn't expose. `runPrepareJob`'s only ledger write is the single `deps.ledger.prepareBatch(...)` call (line ~187), and its own regression-guard throws if that call somehow doesn't return `status === "prepared"`.

The only place `markServed` is ever called is `web/src/app/api/feed/route.ts`'s `runLedgerAwareFeed` (line ~284 for an existing `'prepared'` batch found by a real request, line ~351 for a freshly-minted one) — both call sites are inside a function that only runs when an actual `POST`/`GET /api/feed` request arrives with a resolved `paperCacheScope` (i.e., a real, authenticated visit). **This is the structural proof, not a promise: a batch minted by the prepare-ahead worker sits at `status: 'prepared'` until a real visit's own call to `runLedgerAwareFeed` finds it and transitions it to `'served'`.** TRIGGER-A's design (§2) preserves this by construction: the new endpoint only ever constructs a `Pick<..., "getBatch"|"prepareBatch">`-typed ledger for the worker, exactly like the existing (inert) `PrepareWorkerDeps` contract already requires.

### 1.4 Rollover interaction — a gap TRIGGER-A's design must name, not silently fix

`runLedgerAwareFeed`'s mint path (route.ts, ~lines 294-396) does five things in order after finding no existing batch: (a) `ledger.readExclusions` (fail-closed on `"unavailable"`), (b) read yesterday's rollover remainder (`SupabaseRolloverCandidateStore.list`, fail-soft), (c) `runFeedPipeline(...)` with `ledgerExclusions`, `rolloverCandidates`, `includeFinalPool: true`, (d) map `result.items` → `PaperIdentity[]` via `identityForRawItem` (`web/src/lib/feed/paper-identity.ts`), (e) `prepareBatch` + `markServed`, then **only if this call's own selection actually won the mint race** (`wonMintRace` check comparing `minted.papers` to the just-submitted `papers`), write today's un-selected remainder to the rollover store for tomorrow.

`prepare-worker.ts`'s `runPrepareJob` does NOT do step (e)'s rollover write — its `buildPool` dependency only returns `{papers, servedItems}`, and nothing in `PrepareWorkerDeps` exposes a rollover store. **This is a real, named gap, not yet decided:** should a prepare-ahead-minted batch also write tomorrow's rollover remainder? See §2.10 (what stays unwired) and POLICY item 7.

### 1.5 The refresh action today, and where the cooldown gate actually belongs

Client: `web/src/store/feed.ts` — the "Refresh now" affordance calls `loadFeed({poolRefresh: true})`; the request body carries `poolRefresh: true` **only when `entitlement.poolRefreshAllowed`** (comment at feed.ts:861-870: *"This is what keeps the existing 'Refresh now' button honest... the route forwards it only when poolRefreshAllowed"*). Per `docs/jev-abc/MERGE-B-FEED-20260924T164419Z.md` (merge-conflict record, both sides' designs described, main's side landed): the pool cache (`web/src/lib/opportunities/pool-cache.ts`) takes a `forceRebuild` parameter that **skips the cache read but keeps the write and the single-flight coalescing** under the same key. P4-S8a (already shipped, `docs/jev-abc/P4-S8a-A-20260924T142734Z.md`, VERIFIED_OFFLINE_BOUNDED) fixed the signed-in coalescing bug so two concurrent refreshes for the same owner+intent never double-build.

So today, "refresh" = **synchronous, in-request** forced rebuild of the underlying pool cache — nothing async, nothing queued, no cooldown anywhere in that path.

Under the ledger (`PEER_DASHBOARD_LEDGER=on`), this synchronous path is moot for a signed-in owner once a batch exists for today: §1p.C.8 is explicit — *"Signed-in manual refresh re-reads today's frozen batch and never rotates it... if C finds such a control [load more/second batch today], it stops and records."* `docs/jev-abc/P4-S8-B-20260924T115008Z.md` independently confirmed (CURRENT BEHAVIOUR A2) no such rotate-control exists in the live code. **So a manual refresh, once a batch is minted for the day, structurally cannot trigger new work — cooldown or not.**

`refresh-cooldown.ts`'s own header explains why it was built anyway: "It has something to limit once P4-S8b's refresh-triggered prepare jobs exist" — i.e. its intended use is gating a **new, not-yet-built** action: a signed-in user asking to prepare their (not-yet-existing-today) batch sooner than the passive due-time schedule would. `docs/jev-abc/P4-S8-B-20260924T115008Z.md` (line ~120) is explicit that wiring into `page.tsx`'s `refreshFeed`/the "Refresh now" button is **out of scope** for the slice that built the cooldown, "doubly true... since page.tsx is [a different C's] live file."

**Conclusion for TRIGGER-A:** the cooldown gate does not belong in the existing synchronous `poolRefresh`/`forceRebuild` path (out of scope, and structurally inert once a batch exists anyway). It belongs in front of a **new** call to `jobs.enqueue(...)` — the same `dashboard_prepare_jobs` table and worker the due-selection scheduler uses. A "refresh job" is not a different kind of row: the migration has no job-kind/source column, so a cooldown-gated manual request and a scheduler's own due-selection enqueue are indistinguishable once in the queue, and the hourly drain does not need to know which produced a given row. This means "processes cooldown-gated refresh jobs" (item 15) is satisfied **structurally** by draining the one shared queue — no second code path is required on the drain side. What remains genuinely unbuilt is the enqueue-time caller that would call `claimManualRefresh` then `jobs.enqueue(...)` — see §2.10 and POLICY item 5 for whether TRIGGER-A should build that caller now.

### 1.6 Due-user selection and the lead-time/cadence mismatch (the most consequential finding)

Only per-user time signal available: `digest_hour_local` + `digest_timezone` (defaults 8, `'UTC'` — §1.2). `docs/jev-abc/P4-S8-B-20260924T115008Z.md` DESIGN B4 already assumes reusing these as the "expected check-in" proxy, and `prepare-due.ts`'s header confirms it: *"compute the target instant for digest_hour_local in digest_timezone... and that's the job's next_attempt_at/due time."* No separate "expected check-in"/"last visit" tracking exists anywhere (grepped `expected_checkin`, `checkInHour`, `last_visit`, `lastSeen` etc. across `web/src` — no relevant hits).

**The mismatch, derived from the actual numbers in this repo, not assumed:**

Let `T` = the UTC instant of a user's `digest_hour_local` today. `computePrepareDueAt` gives `dueAt = T − lead` (default lead 45 min). The hourly workflow only runs at `HH:05` UTC (digest-cron.yml's cron string, §1.2). A pending job becomes claimable at the **first** `HH:05` run with `now ≥ dueAt` — i.e. the smallest grid point at or after `dueAt`. Because grid points are 60 minutes apart, that claim instant falls somewhere in the half-open window `[dueAt, dueAt + 60min)`, which means:

**realized lead time (`T − claim instant`) falls in the range `(lead − 60, lead]` minutes.**

With the current default `lead = 45`: realized lead ranges from **−15 minutes to +45 minutes** depending purely on where `T`'s minute-of-hour happens to land relative to the `:05` grid. Worked example (whole-hour UTC offset, e.g. America/Chicago in CDT, `digest_hour_local = 8` → `T = 13:00 UTC`): `dueAt = 12:15`. The run at `12:05` is too early (`12:05 < 12:15`); the next run, `13:05`, is the first with `now ≥ dueAt` — **claimed 5 minutes AFTER the user's target hour, not 45 minutes before it.** A half-hour-offset example (e.g. `digest_hour_local = 8` IST → `T = 02:30 UTC`) lands better (`dueAt = 01:45`, claimed at `02:05`, 25 min early) purely by coincidence of alignment. **The realized lead is not just "sometimes less than 45 minutes" — for a large, common class of timezones (any whole-hour UTC offset, which includes UTC, most of Europe outside DST edges, US zones, China, Japan) it is negative: the batch becomes ready minutes *after* the check-in it was supposed to precede, which directly contradicts acceptance 14's own wording ("ready ahead of your reading time... honest status").**

This is a pure consequence of choosing an hourly-only trigger (user decision #3 = A) for a sub-hour lead time — not a coding bug, and not something a B guide should quietly "fix" by picking a number. It is exactly the kind of number decision that belongs on the POLICY list (§5 item 1): the fix requires no new infrastructure, only raising the default lead. To guarantee a positive realized lead of at least `K` minutes regardless of a user's timezone offset, `lead ≥ K + 60` is required (e.g. `lead ≥ 75` guarantees ≥15 min real lead in the worst case; `lead ≥ 90` guarantees ≥30 min). There is no engineering cost to a longer lead — a `pending` job with a far-future `next_attempt_at` just waits; it never expires.

A prepared build is one full `runFeedPipeline` call — same cost shape as dispatch-digests' own daily run: at `aiTier: 0` (recommended, §2.6), cost is bounded to OpenAlex/S2 fetch volume only (the pipeline's own "4 web searches" unit cost, per `docs/jev-abc/P4-S8-B-20260924T115008Z.md` E7's citation of `pipeline.ts`'s "THE AI TIER IS PART OF THE KEY" comment), reusing whatever per-owner daily channel-candidate cache already exists (`docs/JEV-RELEASE-READINESS.md` §2 Group A4 — VERIFIED, per-owner-per-day). **No paid-AI cost at `aiTier: 0`.** If a future round raises prepare-ahead's `aiTier` above 0, two things change: (a) it starts spending through `meterCall` (`web/src/lib/llm/providers/metered.ts`, per `docs/jev-abc/SPEND-CAP-B-20260925T042147Z.md` §2.3 — this hook is automatic/structural, at the provider-resolution layer, for **any** caller of `resolveProvider`/`generateJsonText`/etc., so TRIGGER-A would not need to build anything new to be covered by the dollar cap once it ships); (b) it walks directly into the scoped gap `ABC-JEV-INTEGRATION.md` §1v names explicitly: *"threshold — when the prepare-ahead worker (TRIGGER-A) goes live or per-user abuse through the feed path is observed, B is authorised to design ownerId threading with a cache-key-invariance test."* Recommending `aiTier: 0` for this slice (§2.6) is specifically what avoids triggering that threshold now. ## 2. Design

### 2.1 New CRON_SECRET-authenticated endpoint

One new route, `GET /api/jobs/prepare-dashboards` (`web/src/app/api/jobs/prepare-dashboards/route.ts`), mirroring `dispatch-digests/route.ts` exactly for auth/shape: same `Bearer ${CRON_SECRET}` check → `401 {error:"unauthorized"}` with **zero Supabase calls before the check** (order matters — the check must be the first thing the handler does, same as today's file), `export const dynamic = "force-dynamic"`, `export const maxDuration = 300`.

Internally it runs three independently-try/caught phases and reports all three in one JSON body (mirrors dispatch-digests' own multi-bucket `{dispatched, skipped, failed, emails_sent, emails_failed}` convention):

1. **Prepare-ahead due-selection + enqueue** (acceptance 13/14) — gated on `PEER_DASHBOARD_PREPARE === "on"` AND `dashboardLedgerEnabled()` (see §2.3).
2. **Drain the queue** (bounded by the per-run ceiling, §2.5) — same gate as phase 1; covers both scheduler-enqueued and any future refresh-enqueued rows (acceptance 15), since the queue does not distinguish them (§1.5).
3. **Digest email retry** (user decision #5) — gated on its own flag AND `isDigestDedupeEnabled()` (§2.3), independent of phases 1/2.

A phase's failure is caught **inside the endpoint**, not just at the workflow-step level, so e.g. a Supabase outage during phase 1 does not prevent phase 3 from running in the same invocation — this is the fine-grained half of "a failed prepare doesn't block the email step"; §2.2 is the coarse-grained (workflow) half.

For testability (dispatch-digests only partially does this — `digestFeedRequestFromProfile`/`digestIdempotencyKey` are exported, the rest is inline in `GET`), **extract the orchestration into a plain, dependency-injected, exported function**, e.g. `runDashboardPrepareCycle(deps, now): Promise<PrepareCycleReport>`, that the route handler thinly wraps after the auth check. This is what makes the RED tests in §3 possible without a live Next request or a real Supabase instance.

### 2.2 Workflow change

Add a **second job** to the existing `.github/workflows/digest-cron.yml` (same file, same top-level `on: schedule`/`workflow_dispatch` — satisfies "same schedule" without a second cron string to keep in sync), not a second step in the existing `dispatch` job. Reasoning: GH Actions jobs (unlike steps) get independent `timeout-minutes`, independent `concurrency` groups, and independent pass/fail status by construction — a slow or failing new job cannot skip or fail the existing `dispatch` job's steps, and vice versa, with no `if: always()` bookkeeping required anywhere. This is the coarse-grained half of "independent failure handling."

Illustrative shape (for C to adapt, not applied by B):

```yaml
  prepare:
    runs-on: ubuntu-latest
    timeout-minutes: 7
    steps:
      - name: GET /api/jobs/prepare-dashboards
        env:
          CRON_SECRET: ${{ secrets.CRON_SECRET }}
          ENDPOINT: https://hermes-flax-six.vercel.app/api/jobs/prepare-dashboards
        run: |
          set -euo pipefail
          if [ -z "${CRON_SECRET:-}" ]; then
            echo "::error::CRON_SECRET secret not set in repo Actions secrets"
            exit 1
          fi
          status=$(curl -sS -o /tmp/body.json -w '%{http_code}' -m 360 \
            -H "Authorization: Bearer ${CRON_SECRET}" \
            "${ENDPOINT}")
          echo "HTTP ${status}"
          if [ -s /tmp/body.json ]; then jq . /tmp/body.json 2>/dev/null || cat /tmp/body.json; fi
          if [ "${status}" != "200" ]; then
            echo "::error::prepare-dashboards returned HTTP ${status}"
            exit 1
          fi
```

with its own `concurrency: {group: dashboard-prepare-cron, cancel-in-progress: false}` at the job level (GH Actions supports a `concurrency` block per-job, not only per-workflow) — same reasoning as the existing `digest-cron` group: overlapping scheduled runs of this specific job queue rather than pile up, independent of the `dispatch` job's own group. **C must not touch `vercel.json`** — this stays a GitHub Actions-only trigger (§1p.C.3, reconfirmed live in this file, §1.2).

### 2.3 Flags and defaults

- **`PEER_DASHBOARD_PREPARE`** (new, server-only, trim+lowercase `"on"`-only, default off) — master switch for phases 1+2 (due-select/enqueue/drain). Follows the exact convention every existing flag in `web/.env.example` uses.
- **Hard dependency on `PEER_DASHBOARD_LEDGER`, enforced in code, not just documented.** Finding: a batch minted with `PEER_DASHBOARD_LEDGER` off is never read by `runLedgerAwareFeed` (that function's own first line is `if (!paperCacheScope || !dashboardLedgerEnabled())` → skip the ledger entirely). If `PEER_DASHBOARD_PREPARE` were ever turned on while `PEER_DASHBOARD_LEDGER` stays off, **100% of prepare-ahead's spend is wasted** — batches get written that nothing will ever serve. Phase 1 must check `dashboardLedgerEnabled()` (reuse `ledger-flag.ts`, do not re-implement) in addition to its own flag, and report a truthful no-op reason (`"ledger_disabled"`) rather than silently doing the wasted work — mirrors this codebase's own established "truthful unavailable, never silent" convention (§1p.F).
- **`PEER_DIGEST_EMAIL_RETRY`** (new, same convention, default off) — gates phase 3, in addition to (not instead of) the existing `PEER_DIGEST_DEDUPE` flag it structurally depends on (no `payload.email` records exist to retry when dedupe's claim path is off). Two flags is slightly more ceremony than strictly required (phase 3 is already a structural no-op with dedupe off), but matches "everything stays behind default-off flags" literally and lets the manager disable retry specifically without touching the unrelated dedupe flag. **Minor design choice, not POLICY-critical** — folding it into `PEER_DIGEST_DEDUPE` alone is a reasonable simplification if the manager prefers fewer flags.
- No new blanket "is this endpoint allowed to do anything" flag beyond `CRON_SECRET` — every existing flag in this codebase gates a specific feature, not a nested master switch (SPEND-CAP's `PEER_COMPANY_SPEND_CAP` is the one exception, justified there by a fail-closed/fail-open tension that doesn't apply here).

### 2.4 Due-user selection

Reuse `dispatch-digests`' exact profile columns and its `digestFeedRequestFromProfile`/`feedControlsFromRow`/`seedTextsFromRow`/`frequencyAdmitsToday` helpers (the latter three are currently module-private — add `export`, purely additive, zero behaviour change, same treatment `digestFeedRequestFromProfile` itself already got "for reuse"). SQL pre-filter: same `digest_enabled = true AND digest_frequency != 'off'` (§1.6's finding: this currently matches ~every profile row; the real narrowing happens in-process below). Skip a row exactly where `digestFeedRequestFromProfile` returns `{ok:false, reason:"intent_required"}`, same as dispatch-digests already does.

Per-row: compute `dueAt = computePrepareDueAt({localDate: dateInTimezone(now, row.digest_timezone), hourLocal: row.digest_hour_local, timezone: row.digest_timezone, leadMinutes: LEAD_MINUTES})` (reuse `timezone.ts`/`prepare-due.ts`, never a second date computation — this codebase's own repeatedly-stated rule). **Enqueue defensively, not narrowly:** every run, enqueue (upsert) a job for every due-soon row whose `dueAt` falls within `[now, now + LOOKAHEAD_MS)` for a generous `LOOKAHEAD` (recommend 3 hours) — not just "exactly one hour before." Reasoning: `enqueue_prepare_job` is a cheap idempotent upsert (refreshes `intent_version`/`next_attempt_at` to the same computed values on a repeat call — no cost to calling it from several consecutive hourly runs for the same user), and GH Actions' own scheduled triggers are documented best-effort/delay-prone (digest-cron.yml's own comment). A wide, repeated enqueue window is self-healing against a missed or delayed run; a narrow one is not. The DRAIN phase (§2.5) is what actually needs a tight per-run bound, not the enqueue phase.

`readCurrentIntentVersion` (the fencing dependency `PrepareWorkerDeps` requires): re-fetch the single profile row fresh by `user_id`, re-run `digestFeedRequestFromProfile`, `serializeFeedIntent(request.intent)` if `ok`, else `undefined` (treated by `runPrepareJob` as "cannot verify → retry," never as "changed," per its own existing logic — no new logic needed here, just correct wiring).

### 2.5 Per-run ceiling

`drainPrepareQueue(deps, {leaseDurationMs, maxJobs})` already has this parameter — **do not invent a second mechanism**, pass an explicit `maxJobs`. Sizing: within the 300s `maxDuration` budget, and treating one pipeline build as roughly the same order of magnitude as `warm-pool.yml`'s own documented cold-build cost ("20-30s on a cold morning" for the shared anonymous pool; a private per-owner build likely costs more, calling more channels), a ceiling in the 10-20 range leaves comfortable margin (10 × 30s = 300s worst case is already tight; recommend starting at `drainPrepareQueue`'s existing default of 10, i.e. no override, as the conservative starting point). **This number should scale with real signed-in user count, which B has no visibility into** — see POLICY item 2. Because due-selection now enqueues broadly (§2.4) and a `pending` job never expires, a backlog beyond the ceiling simply drains across more hourly runs — never lost, never double-built (idempotent upsert + lease fencing), only delayed, which directly interacts with §1.6's lead-time finding (a deeper backlog erodes whatever lead time was configured).

### 2.6 aiTier for prepare-ahead builds

Recommend **`aiTier: 0`**, explicitly borrowing dispatch-digests' own "D9" rationale verbatim: a user who has not visited yet must cost nothing beyond deterministic source fetches, because — per this feature's own product rule — a prepared-but-never-visited batch is not a delivery and may simply be wasted work. This also keeps prepare-ahead outside `meterCall`'s reservation path entirely for this slice (§1.7), sidestepping the SPEND-CAP `ownerId`-threading gap `§1v` R2 names as TRIGGER-A's own trigger condition. Raising this tier is a real product/cost decision for a later round, not something to default higher silently now. **POLICY item 8.**

### 2.7 Idempotency / lease / fencing — 100% reuse, nothing new

- Debounce: `enqueue_prepare_job`'s `unique(owner_id, local_date)` + upsert (existing migration).
- Cross-worker mutual exclusion: `claim_prepare_job`'s `FOR UPDATE SKIP LOCKED` + lease expiry (existing migration) — true concurrent-Postgres proof stays BLOCKED per §1k (no isolated DB available to this campaign), exactly as `prepare-worker.ts`'s own header already states; C's tests exercise the **logic** via `MemoryDashboardPrepareJobRepository`, not real concurrent connections.
- Two overlapping *hourly runs* of the new GH job: `concurrency: {group: dashboard-prepare-cron, cancel-in-progress: false}` (§2.2) already serializes them at the CI level — a second layer on top of the DB-level lease, not a replacement for it.
- Intent-change fencing: `runPrepareJob`'s existing re-check-immediately-before-write (§1.1/§1.3) — reused unmodified via §2.4's `readCurrentIntentVersion` wiring.

### 2.8 Retry/backoff

Job-level (whole pipeline build failing): reuse `prepare-due.ts`'s `nextAttemptDelayMs`/`nextAttemptAt` unmodified (1 min base, 30 min ceiling, exponential, `max_attempts` default 5 — labelled PROPOSED in the migration's own comment, not sourced; not re-litigated here). Per-HTTP-call retry (429s etc. against OpenAlex/S2) is already handled one layer down by `web/src/lib/sources/_fetch.ts`'s `sourceFetch` (P4-S8-B's own POLICY E6 flags this exact layering and instructs a future builder not to duplicate it) — `buildPool`'s implementation (§3 Step 2) must call the existing pipeline/source adapters as-is and must not add a second per-HTTP retry loop, per `prepare-worker.ts`'s own header warning.

### 2.9 Email-retry semantics

Extract (§3 Step 1) `handleConflictingEmailClaim` + its private helpers out of `dispatch-digests/route.ts` into a new shared module, `web/src/lib/email/digest-retry.ts` — behaviour-preserving, `dispatch-digests/route.ts` imports it back. New retry-candidate SELECTION query (does not exist today, since today's ladder only ever runs reactively on a same-day second claim): `briefing_deliveries` rows where `channel IN ('email','both')`, `payload->'email'->>'sent'` is not `'true'`, `payload->'email'->>'attemptedAt'` is present and **between 10 minutes and 23 hours old** (the 10-minute floor is a deliberate, cheap defense-in-depth margin against racing a same-hour dispatch attempt still in flight — not required for correctness, since Resend's own idempotency key is the actual safety net per `handleConflictingEmailClaim`'s existing `"concurrent_idempotent_requests"` handling, but avoids a pointless simultaneous-retry attempt). For each candidate, call the extracted `handleConflictingEmailClaim({admin, userId, localDate, idempotencyKey: digestIdempotencyKey(userId, localDate), now})` unchanged — it already re-reads the row and only ever calls Resend with the same stored render + same idempotency key, so a "sent twice" outcome would require Resend's own key window to fail, not anything new this slice adds. This entire phase is a structural no-op today given §1.2's finding that no user can reach `digest_channel: 'email'|'both'` from the UI yet — worth stating plainly in the readiness doc update (§4) so it isn't read as "email now works."

## 5. POLICY — manager decides

1. **Lead time.** The current PROPOSED default (45 min) can realize a *negative* lead (batch ready minutes after the target hour) for a large class of timezones, given the hourly-only trigger (§1.6, derivation shown). Recommend raising to **≥75 minutes** (guarantees ≥15 min real lead in the worst case) or **≥90** (≥30 min). No infrastructure cost either way. This is the same kind of number as the original 45-minute figure — a product timing choice, not an engineering fact.
2. **Per-run drain ceiling.** Recommend starting at `drainPrepareQueue`'s existing default (10, no override) — B has no visibility into real signed-in user count to size this against actual due-population, and §1.2's finding that the due-filter currently matches ~every profile row makes this more than a formality.
3. **Due-selection filter.** Reuse dispatch-digests' exact `digest_enabled=true AND digest_frequency != off` (recommended — respects a future opt-out, consistent with the existing due-time design), or apply prepare-ahead to every signed-in user regardless (since these are conceptually email-settings fields, and §1.2 shows the filter isn't narrowing anything today anyway).
4. **`PEER_DASHBOARD_PREPARE` hard-depends on `PEER_DASHBOARD_LEDGER`** (§2.3) — confirm enforcing this in code (truthful no-op) rather than relying on activation-order discipline alone.
5. **Build the user-facing manual-refresh-enqueue endpoint now, or leave it fully unwired this slice?** Recommend: leave unwired (§2.10) — matches the existing P4-S8-B guide's own explicit boundary, and avoids the SPEND-CAP per-user-attribution gap (§1v R2) until that's separately resolved. 7. **Rollover-remainder write for a prepare-ahead-minted batch** (§1.4/§2.10) — skip as a named accepted cost (recommended — avoids widening the `VERIFIED_OFFLINE_BOUNDED` `PrepareWorkerDeps` contract), or extend `prepare-worker.ts` for parity.
