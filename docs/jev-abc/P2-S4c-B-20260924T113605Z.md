## B. RECOMMENDED DESIGN

**Ship (a) now, at READ TIME, exactly mirroring how P2-S4b resolved positive seeds — never baked into the shared per-day pool.** Concretely:

1. New pure helper, `web/src/lib/preferences/topic-seeds.ts`: `topPositiveOpenAlexTopicIds(ledger, limit)` — filters `cleanPreferenceLedger(ledger)`'s entries to `source === "openalex_topic"` and `positive - negative > 0`, sorts by net-positive descending (tie-break: `lastPositiveAt` descending), strips the `"openalex_topic:"` prefix from each surviving entry's `key`, **re-cases the tail to the adapter's expected uppercase `T…` form** (the EVIDENCE #19/#20 case-mismatch fix — this is the one genuinely new, non-obvious piece of logic in this whole design), and returns at most `limit` (recommend 5, matching `MAX_TOPIC_IDS_PER_CALL` in `openalex-topic.ts` so nothing supplied is silently truncated a second time). Pure, synchronous, no I/O, trivially unit-testable.
2. In `pipeline.ts`, add a small async step next to (not nested inside) `fetchPositiveSeedCandidates`, called from `runFeedPipeline`'s read-time section (near current L1271): call `fetchOpenAlexTopicField` with the ids from step 1 when `channelOpenAlexTopicEnabled()` is true and the list is non-empty; tag results `"topic-field"` via the existing `tagAdmissionChannel`; merge into the pool items the same way `poolItemsWithSeeds` does; capture any failure and merge it into `meta.errors.openalex_topic` unconditionally (the same mechanism `positiveSeedErrors` already uses at L1379-1382) — cache-hit or fresh-build, this channel now re-runs and re-reports on every request, exactly like its three read-time siblings.
3. **Retire the dead build-time scaffold** (L459-487, L550-555, L588-590) rather than leaving it inert-but-present alongside a new live read-time path under the same flag name — a permanently-unreachable branch sitting next to a real one, both gated by the same-looking flag, is a latent confusion/regression risk in a file this actively edited. This does move `"openalex_topic"` out of the "pool-level, build-time" bucket the `BuiltPaperPool.sourceStatus` doc comment currently describes (EVIDENCE #8) into the read-time bucket the other three channels already occupy — that comment needs a one-line update.

**Why read time, not build time, and why this design needs NO `pool-cache.ts`/`derivePoolCacheKey` change:** `buildPaperPool`'s own comment (EVIDENCE #9, L609-613) states the whole reason the ledger is excluded from build time: one pool must serve a whole day regardless of what a user does after it's built, or every like immediately invalidates the shared cache entry. `uploadInterests` is the one existing precedent for folding a ledger-derived signal into the cache key (EVIDENCE #12, #27) — but it only reflects the rare "uploaded a PDF" signal, not the much more frequent like/save signal my design would consume if run at build time. Using the far-more-frequently-changing signal at build time would either (i) make the cache churn dramatically more (defeating the pool cache's entire cost-saving purpose — its own doc comment already names this exact failure mode, "a page reload rebuilt the feed and re-spent the tokens", `pool-cache.ts` per EVIDENCE #27's file) or (ii) require decoupling "what's in the key" from "what actually changed the fetch," which is a much bigger, riskier redesign than this slice's scope. Read time avoids the question entirely, at the cost that a topic-field candidate is never part of the SHARED pool payload other requests might see — exactly the same, already-accepted trade-off P2-S4b made for the other three non-literal channels.

**Respecting every hard constraint in the brief:** flag stays `PEER_CHANNEL_OPENALEX_TOPIC`, read only from `process.env`, unreachable from any request body (unchanged — `channelOpenAlexTopicEnabled` already lives in `pipeline.ts` and nothing here adds a new client-facing field). Bounded exploration: capped at 5 topic ids feeding `fetchOpenAlexTopicField`'s own existing `TOPIC_FIELD_DEFAULT_LIMIT`/`OPENALEX_TOPIC_MAX_RESULTS` caps — never a whole-field dump, matching §3.2 of the retrieval plan. "Keyword admission still needs the literal gate, topic-field doesn't" — unchanged, `combine.ts`'s `admittedByNonLiteralChannel` already lists `"topic-field"` (EVIDENCE #16) and needs no edit. Tier 0: the channel is additive and flag-gated off by default; with it on, it is simply empty (not broken) for any user with no positive `openalex_topic` ledger entries yet, identical in kind to how the other three read-time channels already degrade for a user with no positive seeds.

### D-ADD.2 Which existing store/key to reuse — evaluated and decided

The manager's extension named three options; here is the evidence for each, fresh-read 2026-09-24T11:55-11:56Z:

- **`PrivatePaperPoolCache` reused as-is: rejected.** Its `get()` hard-rejects any key not starting with `"peer-pool-v6-papers-"` (`private-paper-cache.ts:134`) and additionally validates `payload.surface === "papers"` (`:147`); `set()` repeats the same prefix guard (`:158`). - **`derivePoolCacheKey` with a distinct `surface`, and/or `CachedPool`/`OpportunitySurface` widened to a 4th member: rejected for this slice.** `OpportunitySurface` is a closed 3-value union (`pool-cache.ts:13`, `"papers" | "events" | "jobs"`) shared by the papers/events/jobs pipelines; `derivePoolCacheKey`'s own version-selection is a 2-way ternary keyed on `surface === "papers"` (`:193`); `CachedPool` (`:101-104`) and its three type-guard siblings (`isCachedPaperPool`/`isCachedEventPool`/`isCachedJobPool`, `:140-150`) would all need a 4th branch. The table's own columns (inferred from `PrivatePoolClient`'s row shape, `private-paper-cache.ts:107-111,160-167`: `owner_id`, `scope_key`, `payload jsonb`, `created_at`) are generic — nothing in the SQL schema itself enforces "surface must be papers," only `PrivatePaperPoolCache`'s own TypeScript guards do.     legs: [...input.enabledLegs].sort(),
```ts
  });
  return `peer-channels-v1-${input.ownerId}-${input.date}-${createHash("sha256").update(sig).digest("hex").slice(0, 32)}`;
}
```
No raw seed titles, no owner id inside the hashed signature itself (the id-form keys already carry no titles — `ResolvedPositiveSeed.identity.key` is a canonical id, not a title, per the original EVIDENCE #29/positive-seeds.ts read), matching the "no seed titles or owner id in any log" requirement; the owner id appears once, in the clear, as the Supabase row's `owner_id` column and a key-string segment — the same place it already appears for the day-pool's own private cache (`private-paper-cache.ts:162`, `owner_id: this.scope.ownerId`), not a new disclosure.

**Gating and wiring** (inside `runFeedPipeline`, replacing the current unconditional `fetchPositiveSeedCandidates` call at pipeline.ts:1328-1331 and folding in the new topic-field fetch from P2-S4c-1):
1. `privateScope` (already computed earlier in `runFeedPipeline` from `req.paperCacheScope`, exactly the same trust boundary the day-pool cache itself uses — `route.ts:532-543`'s `privatePaperScope` proves this is populated **only** for a real, authenticated `supabase.auth.getUser()` result) is the single gate: `if (!privateScope) return { items: [], errors: {} };` — zero fetch, zero cache read/write for anonymous or auth-not-configured requests. This directly satisfies ruling 3 and the brief's "anonymous path (no call, no cache)" with no new plumbing — reusing a value already in scope at this exact point.
2. Compute `enabledLegs` from the four flag getters (`channelS2RecommendationsEnabled`, `channelOpenAlexSeedSimilarityEnabled`, `channelPositiveSeedCitationsEnabled`, `channelOpenAlexTopicEnabled` — all already exist). If empty, return `{items:[],errors:{}}` immediately — nothing to do, no cache needed at all (matches today's exact behavior when every flag is off, byte-for-byte).
3. Derive the key; construct `new PrivateChannelCandidateCache(privateScope)`.
4. Try `cache.get(privateScope.ownerId, key)`. **On a genuine read failure** (the `try/catch` inside the new class's `get()` throws internally and returns `null`, indistinguishable at this call site from "no entry yet") — **recommend: treat exactly like a cache miss for THIS read, but additionally record a synthetic truthful error for every enabled leg** (e.g. `"channel candidate cache unavailable"") in the returned `errors` map, and **do not perform a live fetch in this branch** — see the explicit reasoning below.
5. On a real cache hit: for each enabled leg whose stored `legStatus[leg].status === "failed"` and `isEligibleForRetry(legStatus[leg], now)` (reused as-is, zero changes), attempt exactly that one leg's live call, claimed first via `claimSourceRetry` (widened to accept `FeedChannelId`, reused as-is) keyed by `hashCacheKey(key)` — same "claim before fetch, fail closed if the counter store is unreachable" discipline the day-pool's own `retryFailedSources` already uses, just scoped to channel legs instead of academic sources. Merge any recovered items, update `legStatus`, write back via `cache.set`, return.
6. On a cache miss (and only then): run the real fetch — this is `fetchPositiveSeedCandidates` (unchanged internals) plus the new P2-S4c-1 topic-field leg, combined into one `{items, legStatus}` value — then `cache.set(...)` it (fire-and-forget-safe, wrapped in try/catch exactly like `PrivatePaperPoolCache.set` already is, so a write failure never blocks the response) and return it.
7. A small local single-flight map (mirroring `withCacheSingleFlight`'s shape, D-ADD.2) coalesces concurrent requests for the same `(cache-instance, key)` within one process, so a burst of near-simultaneous tabs/reloads for the same owner+signature triggers at most one live fetch, not N.

**Why "cache unreadable → skip the legs, don't fetch-without-caching" (the brief's explicit either/or):** the entire point of this addendum is to bound how often these legs can fire live. Fetching anyway when the cache can't be verified/written would silently reintroduce the exact unbounded-per-open-call problem F-M-P2-02 exists to close — if the cache is down for an extended window, "fetch every time, cache nothing" degrades to exactly today's uncached behavior for that whole window, uncapped. Skipping instead is cost-safe by construction (zero live calls fire when we cannot record that we won't immediately re-fire on the very next request) and matches this exact area's own established precedent — `SupabasePositiveSeedFeedbackRepository`'s own reads already degrade to "no seeds" on any failure, never to "try harder." The one refinement over that precedent: report the degrade truthfully in `meta.errors` (a synthetic per-leg message) rather than letting it look identical to "no positive feedback yet," consistent with this whole campaign's "truthful `meta.errors`" theme (§1p.B(2)).

**Invalidation:** by construction, not by any explicit eviction — any change to the owner's positive seeds, negative seeds, or topic ids (a new like/save/dismiss since the last cached read), or to which legs are enabled, produces a different key and therefore a guaranteed miss. Stale rows for an old signature are simply never read again; no retention/cleanup logic is invented beyond whatever (undocumented, out of this addendum's scope) policy already governs `private_paper_pools`' own row growth, since this shares that table.

**Ledger-mode interaction:** none needed — confirmed in D-ADD.1, a served batch never reaches this code path at all (`resolveServedItems` returns `batch.servedItems` directly). This cache only ever matters on a path that calls `runFeedPipeline`: every batchless read today, and once per mint in ledger mode.
