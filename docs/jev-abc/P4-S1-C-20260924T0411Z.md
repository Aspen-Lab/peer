DESIGN CHOICES:
- Batch statuses `prepared | served | acknowledged` per binding ruling §1p.C.5 (NOT the guide draft's `presented_pending_ack`). `served_at` column/field name chosen (not the guide draft's `presented_at`) for consistency with the `served` status value — `served` means "returned to an authenticated client, possibly presented", so the timestamp column is named to match.
- `prepareBatch(ownerId, localDate, papers: {key, aliases}[], intentVersion?)` — per the task brief's interface (supersedes the B guide's `canonicalIds: string[]`-only draft), matching ruling §1p.C.6 ("the batch row stores per-paper identity (key + aliases)").
- `papers` stored as a single **jsonb array of `{key, aliases}` objects**, not parallel arrays. Justification (also in the migration's own comment): `aliases` is itself variable-length per paper, so a parallel-array shape would need an awkward array-of-arrays column with index-alignment discipline between it and a separate keys array, for no real benefit; a jsonb array keeps each paper's key and aliases atomically paired and round-trips directly to/from the TS `PaperIdentity[]` shape with no reconstruction step.
- `listDelivered`/`listServedUnacknowledged` both return a single flattened `Set<string>` of keys UNION aliases (not separate key/alias sets) — matches the task brief's explicit doc ("(keys ∪ aliases)") and ruling §1p.A's asymmetric-exclusion rule (a candidate is excluded if ITS key or ANY of its aliases intersects this flattened set — the intersection-side logic belongs to the future pipeline caller, P4-S2, not this module).
- `listServedUnacknowledged` includes only `status === 'served'` batches, excluding both `prepared` (never sent to a client, so §1g's "possibly presented" concern does not apply) and `acknowledged` (already covered by `listDelivered`, and must not double-count).
- `MemoryDashboardDeliveryLedger` is **exported** from the module, not confined to the test file. Justification: unlike the codebase's existing `MemoryPoolCache` doubles (trivial get/set), this class IS a non-trivial state machine (idempotent prepare, ack transitions, owner-mismatch/not-found handling) that P4-S2's future pipeline tests will also need; exporting one reference implementation avoids duplicating that state machine's logic across files, where it could drift. Explicitly documented as non-durable/never-production in the module's top comment and the class's own doc comment. Permitted by the brief ("An exported in-memory implementation is acceptable if documented as non-durable and justified").
- `SupabaseDashboardDeliveryLedger` reuses a private internal `MemoryDashboardDeliveryLedger` instance as its unconfigured-degrade fallback, rather than re-implementing synthetic-batch logic a second time.
- **Read/write failure asymmetry on a CONFIGURED-but-failing client** (beyond what the brief explicitly asked to test, but necessary for internal consistency — documented at length in the module's top comment): reads (`listDelivered`, `listServedUnacknowledged`, `getBatch`) degrade to empty/null on a live error, matching `pool-cache.ts`'s existing "an outage is a miss, not a feed outage" convention. DESIGN CHOICES (migration-specific, added after SQL authored):
- Static self-review caught and fixed a real edge case before finishing: `jsonb_array_elements_text(paper -> 'aliases')` would raise "cannot extract elements from a scalar" if a per-paper `aliases` field were ever a JSON `null` (distinct from SQL NULL in jsonb). Guarded with `case when jsonb_typeof(paper -> 'aliases') = 'array' then ... else '[]'::jsonb end` rather than relying on `coalesce`, which only catches SQL NULL, not JSON null.
- `dashboard_batches_papers_is_array` check constraint (`jsonb_typeof(papers) = 'array'`) added defensively at the column level, beyond what either guide or ruling explicitly asked for, since nothing else stops a stray direct write from storing a non-array `papers` value that would later break the acknowledgment function's `jsonb_array_elements` call.
- `revoke all ... from anon, authenticated` then `grant select ... to authenticated` (not `anon`) on both tables: neither `private_paper_pools.sql` nor `briefing_deliveries` (schema.sql) uses explicit revoke/grant for their owner-read tables (they rely on RLS alone), but the brief's steps explicitly ask for "revoke ... where appropriate", and `usage_counters.sql` sets the belt-and-suspenders precedent for a table that wants zero anon/authenticated access. Since these two tables want RLS-gated authenticated reads but zero anon access ever (no anonymous owner_id can match `auth.uid()`), the explicit revoke-then-grant-select-only-to-authenticated is the more defensible middle ground and is documented as such in the migration's own comment.
- `key_version smallint not null default 1` — the RPC always inserts `1` explicitly (matches the guide's note that P4-S1 ships only v1 of the canonical-key algorithm); the column default is an extra safety net, not load-bearing.
