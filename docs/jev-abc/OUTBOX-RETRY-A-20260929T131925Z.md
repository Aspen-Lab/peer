**Two tabs:** `pendingRetryInFlight` is a module-level variable, scoped per JS module instance — i.e. per tab, not cross-tab. Two tabs signed in as the same reader can each independently run their own retry pass over the same persisted keys (each tab's own localStorage-hydrated copy), so the SAME feedback key could get POSTed twice concurrently from two tabs. This duplicate is exactly ruling point 5's "duplicate feedback rows (POLICY 6): accepted... no schema change" — already ruled on, not a new gap. saved/read dimensions are idempotent upsert/delete (confirmed in route.ts, §2.4 of B's guide), so a two-tab double-retry there is a harmless redundant call. No new finding.

**Sign-out during a retry pass — HIGH, evidence-backed, not disclosed anywhere in B's guide or C's checkpoint.** Traced through the actual code:
1. `retryPendingPushes`'s `run()` captures `ownerId` ONCE (`const ownerId = useSyncGate.getState().authUserId;`, read before `run()` is defined) and never re-reads or re-validates it for the rest of the pass. Inside the loop, `const state = get();` IS re-read fresh per key — by design, so a genuinely new interactive action mid-pass wins (comment: "an earlier await in this same pass could have raced against a genuinely new interactive action").
2. `feed-sync.tsx`'s `onSession` fires `void retryPendingPushes()` WITHOUT awaiting it, then continues into the (also unrelated, separately awaited) migration push/pull. Meanwhile Supabase's `onAuthStateChange` can independently fire `SIGNED_OUT` → a SEPARATE `onSession(null, true)` call → `sessionStep` returns "reset" → `store.resetLocal()` runs, which is fully synchronous: it sets `savedPapers`/`savedEvents`/`savedJobs`/`readItems`/`paperFeedback`/etc. back to empty/default AND clears `pendingPushByOwner[thatOwner]`/`pendingFeedbackPayloadByOwner[thatOwner]` to `{}` — all in one `set()` call, no await.
3. If this happens while the EARLIER `retryPendingPushes` pass is still mid-loop (awaiting a `cloudX` call for an earlier key), the NEXT iteration's `const state = get();` now reads the just-WIPED state, using the STALE (pre-sign-out) `ownerId` captured in step 1. For an unprocessed `saved:<kind>:<id>` key where the item was genuinely still saved: `findSavedItem(state, kind, id)` now returns `undefined` (savedPapers was just emptied by resetLocal, not because the reader unsaved anything) → the code calls `await cloudUnsave(itemId, itemKind)` — a real DELETE fires against `/api/saved` for an item the reader never unsaved. Same mechanism can flip a read key to a spurious `cloudMarkUnread`, or resend a feedback POST using a wiped/stale value read.
4. None of the 5 `cloudX` helpers check auth state before firing their `apiFetch` call (confirmed by reading all 5 in full — no guard exists anywhere in any of them); they only consult `useSyncGate.getState().authUserId` AFTERWARDS, inside `updateFeedPushFailedFlag`, purely to decide whether to touch LOCAL bookkeeping (this now-null check makes the post-hoc flag update a no-op, so the local pending-key state is not further corrupted — but the outbound HTTP request has already been sent).
Whether the in-flight DELETE/POST actually lands server-side (vs. getting a 401 because the session cookie was already invalidated by `supabase.auth.signOut()`) is a timing question I could not settle without a live execution, which the brief prohibits. But the CLIENT-SIDE logic is a confirmed defect independent of that: the loop computes and attempts the WRONG direction (an unsave/mark-unread the reader never requested) using data invalidated by a concurrent `resetLocal()`, under a stale owner context, with no guard anywhere. The P6 warning (which offers "Sign out anyway") is shown exactly when pending keys exist — precisely the condition under which a retry pass has the most work to do — so the timing overlap is plausible in real use, not a contrived nanosecond race. Untested: no test in the new suite exercises `resetLocal`/sign-out concurrently with an in-flight `retryPendingPushes` pass.

## 2. The two deviations

**(a) Payload fallback for pre-existing keys — best-effort recompute from current item data.**
Ruling §1bc point 2, verbatim: "a small persisted field captures the payload inside cloudFeedback's own failure branch, per owner, cleared with its key — **retry never reconstructs it from item data that may be gone**." This sentence is the manager's ruling on B's own POLICY 2 question, which explicitly offered two options: (1) the persisted field, or (2) "the lighter-weight best-effort recompute only... alternative instead (§2.3 layers 2–3 alone, no new field)." The ruling's closing clause uses the same word ("reconstructs"/"item data") B used to describe the option it did NOT recommend as primary — reading it as picking option 1 **and ruling out** the recompute fallback, not merely stating that the primary path doesn't need it.
C's `retryPendingPushes` implements all three of B's original layers anyway: captured-map first, then `recomputeFeedbackPayload(state, kind, id)` (reads `state.savedPapers`/`state.papers`/`state.savedEvents`/`state.savedJobs` — i.e. reconstructs from current item data), then `undefined`. This directly contradicts the literal ruling text. C's own PLAN document never surfaces or discusses this tension — it states the three-layer order as settled fact, without flagging it back to the manager despite the binding ruling using an unqualified "never."
Can it send anything false/harmful? No — traced precisely: the feedback *value* is always read fresh from `<kind>Feedback[id]` (never reconstructed), only the `{title, concepts}` *metadata* is recomputed, from the SAME item (matched by exact id) currently held locally; worst case (item genuinely gone from every local pool) it silently falls through to `undefined`, identical to today's existing total-loss behavior. So the risk is not data corruption or a wrong item — it is a plain textual violation of an explicit "never" in a BINDING ruling, done silently. **Verdict: a violation, not a disclosed compatibility path** — it should have been flagged to the manager as a P2-reopening question (especially since it is completely untested: grepped `recomputeFeedbackPayload` in feed.test.ts — zero hits; none of the 13 new tests exercises this fallback at all, so it is both a ruling violation and untested dead-in-tests logic). MEDIUM-HIGH: low practical safety impact, but a clear, silent, unflagged deviation from explicit binding text on the exact question the manager was asked to decide.

**(b) 4xx-drop applied to a FIRST-time feedback failure, not only retries.**
Confirmed: `cloudFeedback` is one shared function called by both interactive sites (savePaper/notInterestedPaper/moreLikePaper/commitDismiss) and `retryPendingPushes`; C's PLAN correctly notes cloudFeedback "never exposes the failure's status code to its caller," so the branch had to go inside cloudFeedback itself, uniformly. Reader loses: for a first-time (non-retry) 4xx, the write is dropped immediately — no pending key is ever added, so the P6 "Some changes on this device haven't reached your account yet" sign-out warning never fires for that item, and the feedback event is silently lost forever with zero user-visible signal, no different from a successful send from the reader's point of view.
Checked against route.ts: `/api/feedback`'s ONLY 400 path is a missing `itemId`/`itemKind`/`feedback` field; every interactive call site always supplies all three from a real item object, so a genuine first-time 400 is effectively unreachable today — this part of deviation (b), as literally posed, is low-risk in practice.
**Sharper, evidence-backed issue found while checking this:** the implemented condition is `err.status >= 400 && err.status < 500`, which also catches **401**. The SAME FILE already has an adjacent, tested precedent for exactly this distinction — `acknowledgePendingBatch`'s ApiError handling (feed.ts ~line 1755-1768): `if (err.status === 401 || err.status === 503) { /* retry once signed in, keep pending */ return; }` vs. a separate branch for 400/404 ("can never succeed differently") that clears pending. A 401 from `/api/feedback` (session cookie not yet propagated, a brief expiry/refresh gap, etc.) is plausible for both an interactive call and a retry, and — unlike a true 400 — **can** succeed on a later attempt once re-authenticated. C's cloudFeedback code does not carve out 401 the way the file's own sibling code does, so a transient 401 now permanently drops the pending key + payload and silently discards the feedback event, with no test anywhere covering a signed-in 401 on cloudFeedback (grepped: the only two 401 fixtures in the whole test file are the pre-existing signed-out test at L1102, where the branch is a no-op regardless because `authUserId` is null, and the sibling `acknowledgePendingBatch` test at L2570 which is for a different code path entirely). **Verdict: does not match the ruling's own stated rationale** ("it can never succeed") **for the 401 case specifically** — this is a real gap, not merely a documented trade-off. HIGH.
