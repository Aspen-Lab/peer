## Why the shared route.test.ts fixture changed (not a weakening)

The file's `beforeEach` previously defaulted `runFeedPipeline` to `items: []`. Under the OLD route
behaviour item count never mattered (a 0-item result still sent), so this was a convenient placeholder.
Under the new behaviour `items: []` now means "send nothing" — so every pre-existing test that relies on
reaching `sendDigestEmail` (destination resolution, the 3/day rate limit, send-failure handling, the
Tier-0 plumbing check) would have started hitting the NEW empty-result branch instead and failed for a
reason unrelated to what each test actually checks. The default was changed to one non-empty item so
those tests keep testing exactly what they always tested; the empty-specific describe block explicitly
overrides back to `items: []` per case. Verified: full suite passed test count moved from 5519 to 5545,
exactly +26 — the number of tests actually added (24 in page.test.tsx + net 2 in route.test.ts after
2 old EMPTY-EMAIL-REASON tests were replaced by 4 new EMAIL-DEST-UX ones) — with 0 unexplained deltas.

## Design

- **Destination source of truth (§1bm point 1):** `resolveActiveEmailDestination(confirmedEmail,
  accountEmail) = confirmedEmail.trim() || accountEmail.trim()` — byte-for-byte the same rule the two
  senders already use server-side (`send-test-email/route.ts:161`,
  `dispatch-digests/route.ts:648-653`). `confirmedEmail` is `profile.digestEmail`, the store's mirror of
  the server's `digest_email` column — never `addressDraft`.
- **One destination sentence, three call sites, one source value (§1bm point 2):**
  `emailDestinationSentence(activeDestination, addressDraft)` is called once per render and its output
  (and the `activeDestination` value itself) is reused in: the daily-summary line, the new paragraph
  next to "Send test email", and the confirmed banner — so the three cannot drift apart the way the two
  pre-existing sentences already had.
- **Caption's 4th state (§1bm point 1, copy bug 3):** `isConfirmedActive` — true only when the draft
  (trimmed, case-insensitive) equals `confirmedEmail` and is neither the account email nor pending.
- **Empty test result (§1bm point 3):** the counter increment (`route.ts`, `getCounterStore().increment`)
  is untouched and still runs before `runFeedPipeline` — the ruling explicitly rejected the guide's
  suggested reorder. Only the post-pipeline branch changed: `feed.items.length === 0` now returns
  `{ sent: false, reason: "empty_result", emptyReasonCode? }` at 200 instead of calling
  `sendDigestEmail`. `emptyReasonCode` is included via conditional spread (present only when the
  pipeline supplied one — always true in production per `computeEmptyReasonCode`'s exhaustive branch,
  possibly absent in a test fixture) — matching the existing `rrf`/`emptyReasonCode`-on-`FeedMeta`
  structurally-absent idiom already used elsewhere in this codebase. No `error` string field — mirrors
  the existing 502 send-failure branch's minimal, reason-only shape (EMAIL-TOKEN-PRIVACY, §1as).

## Deviations / notes for the reviewer

- `TEST_EMAIL_EMPTY` mirrors `DIGEST_EMPTY`'s typing shape (`Record<FeedEmptyReasonCode, {sentence}>`,
  no baked-in fallback key) rather than `BRIEFING_EMPTY`'s (`+ "empty"` key baked into the same Record) —
  chose the `DIGEST_EMPTY` precedent since both are "a specific sender's adapted wording for the same 4
  codes"; the fallback lives as a sibling constant (`TEST_EMAIL_EMPTY_GENERIC`) plus a
  `FEED_EMPTY_REASON_CODES.includes(...)` runtime guard at the call site, the same idiom
  `digest-template.ts`'s `resolvedEmptyEntry` already uses.
- The `sendDigestEmail` call in route.ts still receives `emptyReasonCode: feed.meta.emptyReasonCode`
  (now always `undefined` in practice, since the empty-result branch above it always returns first when
  that field would be set) — left in place rather than removed, for shape parity with the other
  `sendDigestEmail` call sites and because deleting a provably-inert parameter felt like scope creep
  beyond this item; comment at the call site now says so explicitly. Flagging in case the reviewer wants
  it removed instead.
- No STOP condition was hit — the ruled design did not conflict with any ordinary valid case encountered.
