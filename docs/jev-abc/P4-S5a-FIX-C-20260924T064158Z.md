DESIGN CHOICES:
1. **New field `renderedBatchId: string | null`**, added (not a rename of the pre-existing `batchId`/`batchStatus` fields, which keep their current, narrower, still-transient "last response's metadata" meaning and are left behavior-unchanged). `renderedBatchId` is set in the exact SAME `set()` call as `papers` inside `papersLane`, unconditionally, every time, to `realFeed.batchId ?? null` (computed once into a local const also used for `batchId`, so the two can never drift apart in that call). Reset to `null` in `resetLocal` (the only other place `papers` is wholesale-replaced; every other `papers`-touching call site — `undoDismiss`, `hydrateFromRemote`'s `syncSavedState`, save/unsave/feedback mutators — mutates items WITHIN the current batch and correctly leaves `renderedBatchId` alone). UNLIKE `batchId`/`batchStatus`, `renderedBatchId` IS added to `partialize` (persisted) — deliberately, so it is available as soon as the persisted `papers` rehydrate, before the next `loadFeed`'s fetch resolves; this also avoids the accepted-but-avoidable "very-first-paint" regression the reviewing A flagged against the narrower fix direction (a) (gating on plain `batchId`, which stays unpersisted).
2. **`acknowledgePendingBatch` (the store action the action's own doc comment already calls "the ONE place that ever performs that POST") gates on `pending.batchId === get().renderedBatchId`**, checked once, synchronously, before any fetch. This single chokepoint protects BOTH trigger paths at once — the hook's mount/visibilitychange effects AND `loadFeed`'s reconcile-before-load step — without duplicating the check at each call site, and without weakening it to only "clear the pending record when it doesn't match" (which the manager's design explicitly rejected: a stale pending ack for another batch is KEPT, not cleared, so it can still be sent if that batch's cards are ever rendered again).
3. **Defense in depth at the hook layer too**: `shouldAttemptBatchAcknowledgement`'s exported signature changes `hasPendingAck: boolean` to `pendingBatchId: string | null` + `renderedBatchId: string | null`, comparing actual IDs instead of a bare existence flag, per this slice's explicit brief ("the hook passes (or reads) the rendered batch id, not a boolean"). `useBatchAcknowledgement`'s OWN exported signature is unchanged (`cardsRendered: boolean`, still `papers.length > 0`) — it now also reads `renderedBatchId` from the store directly, the same pattern it already uses for `pendingBatchAck`.
