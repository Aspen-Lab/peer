DESIGN CHOICES (recorded before writing tests, per the brief's write-as-you-go instruction):
1. **Store gets three new fields**: transient `batchId: string | null`, transient `batchStatus: "prepared"|"served"|"acknowledged"|null` (both re-derived every load, NOT persisted), and persisted `pendingBatchAck: { batchId: string; localDate: string } | null`. `pendingBatchAck` is set (in `papersLane`'s `set()`, alongside `papers`) whenever a response carries a `batchId` with status `served` or `prepared` (not yet acknowledged); left untouched when the response carries no batch at all (so an unrelated response never wipes a still-outstanding pending ack); cleared when the response's OWN batch id matches an existing pending entry and is now reported `acknowledged`.
2. **`fetchRealFeed` changes return shape** from `Promise<Paper[]>` to `Promise<{ papers: Paper[]; batchId?: string; batchStatus?: FeedMeta["batchStatus"] }>` — single call site (papersLane), safe.
3. **New store action `acknowledgePendingBatch(): Promise<void>`** is the ONE place that POSTs `/api/feed/ack`. Module-level in-flight promise guard (same idiom as the file's existing `feedLoadSeq` module-level token) so two concurrent callers (the hook's mount-effect and `loadFeed`'s reconcile step) never fire two overlapping requests for the same pending batch. Status handling: 200 -> clear; 404 (`not_enabled`/`batch_not_found`, indistinguishable and both terminal) -> clear; 400 -> clear + `console.warn`; 401 -> keep; 503 or thrown/network error -> keep. Uses `apiFetch`/`ApiError` (existing import already used elsewhere in this file) rather than raw `fetch`, for consistent status-code handling.
4. **`loadFeed` calls `await get().acknowledgePendingBatch()` as its very first statement**, before the `set({isLoading:true,...})` — satisfies "before a new loadFeed, retry a pending ack first, then load" (ABC-JEV-INTEGRATION.md §1p.C.7) without touching a Zustand `set` updater (the action is a plain async store method, not a `set()` callback). No-ops instantly (no fetch) when `pendingBatchAck` is null, so every existing test that never sets it is unaffected.
5. **New hook `useBatchAcknowledgement(cardsRendered: boolean)`** in `web/src/lib/dashboard/use-batch-acknowledgement.ts`, `"use client"`. Two `useEffect`s: (a) fires `acknowledgePendingBatch()` when `cardsRendered && pendingBatchAck && document.visibilityState === "visible"`, re-running only when `cardsRendered`/`pendingBatchAck`/the action reference change (React's own dependency-array gating — NOT a manual in-flight ref — is what prevents a second fire for the same still-pending batch, since `pendingBatchAck` only changes reference on a genuine state transition); (b) a `visibilitychange` listener (added once per `cardsRendered` value) that re-attempts on the hidden->visible transition, reading fresh state via `useFeedStore.getState()` rather than a stale closure. "Acknowledges once" is enforced primarily by the STORE's in-flight guard + status-driven clearing (design choice 3), not by hook-local state — deliberate, since the hook itself has no independently meaningful state machine to unit-test, matching this repo's established "thin client wrapper, tested logic lives below it" pattern.
6. **Because this repo has no RTL/jsdom-mounted-effect tests anywhere**, `use-batch-acknowledgement.test.ts` does NOT attempt to mount the hook and observe a live effect (would be new, unprecedented test infrastructure, explicitly out of step with every existing client-behavior test in this repo).
