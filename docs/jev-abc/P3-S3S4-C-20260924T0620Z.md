DESIGN CHOICES (recorded before writing code, so a fresh A can audit the reasoning, not just the result):
1. **paper-content-hash.ts hashes the PRE-truncation abstract, not the literal truncated text**, despite the task text's literal "title + truncated abstract + venue" wording. Reasoning: (a) `jev-contract.ts`'s truncation function is a private, unexported implementation detail of that snapshotted file — I cannot import or duplicate it without either modifying a file I'm forbidden to touch or hand-copying private logic that can silently drift out of sync with the real truncation behavior; (b) more fundamentally, a cache LOOKUP must happen BEFORE deciding whether to call Jev at all — at lookup time there is no wire request yet, so "the literal truncated text" is not actually available to hash without redundantly re-deriving it; (c) truncation is a pure, deterministic function of (full abstract, fixed budget), so hashing the full abstract is at least as discriminating as hashing the truncated text for every case that matters, and strictly MORE conservative in the one case where they differ (an edit entirely past the truncation cutoff triggers an unnecessary cache miss, never a wrongful cache hit) — matching this campaign's established "accept the safe-direction cost, document it" pattern (e.g. counters.ts's own count-based-reservation trade-off). Documented inline in `paper-content-hash.ts` and flagged here for fresh A review.
2. **`ownerId` IS included inside the decision-cache hash** (per this task's literal key-shape instruction), which at first read appears to contradict B's guide finding F-A-P3-03 ("owner_id is a separate, non-hashed filter column, never folded into the hash alone"). This is strictly MORE defensive than B's original recommendation, not less: a cross-owner read now requires both a SHA-256 collision AND passing the separate column filter, instead of just the column filter alone.
3. **`private_decisions` RLS grants owner SELECT only, no owner INSERT/UPDATE policies** — a deliberate, literal-instruction-driven difference from `private_paper_pools` (which grants owners direct insert/update too). Task text: "RLS owner-read, service-role writes." Reasoning: `TrustedPaperCacheScope`'s capability wrapper exists because the paper-pool key hash does NOT bind the owner, so an unforgeable mint-time check is the only thing preventing owner-mixing at the call site. Here, `deriveDecisionCacheKey` already takes `ownerId` as an explicit, required argument that is baked into the hash (design choice 2 above), so the same protection already exists at the key-derivation call site without needing a second wrapper type. 5. **Reservation rollback policy (`reserveJevCall`): accept over-reservation, no rollback.** Both the per-user and global counters are incremented unconditionally and in parallel (`Promise.all`) before either reading is inspected. If one exceeds its cap and the other does not, the one that did NOT exceed its cap keeps its increment (no compensating decrement). Reasoning: (a) a rollback is a second round-trip that can itself fail, which would then need its own fallback decision — net more complexity for a marginal benefit; (b) the failure direction is safe: a counter that is very occasionally over-charged by a refused call can only make FUTURE calls MORE likely to be refused, never less — fully consistent with this codebase's established fail-closed-for-breakers philosophy (`counters.ts`'s own module doc); (c) it mirrors `usage/counters.ts`'s own accepted-limitation precedent (conservative estimate, no corrective true-up required for safety) cited in the B guide §0.3.
