**Finding F1 (MEDIUM — flagged, not swept under the rug) — the tab icon did
not follow a live OS-scheme flip while `mode=system`, across repeated
trials, though the masthead Mark (CSS-only) did every time.**

Procedure: with `data-mode=system`, `data-accent=indigo` set (OS reporting
light, confirmed via `matchMedia('(prefers-color-scheme: dark)').matches
=== false`), flipped the emulated OS scheme with `resize_window

a wait (up to 3 s) and, once, a real mouse click elsewhere on the page (in
case event delivery needed a UI tick). Result every time: `matchMedia(...).
matches` correctly flipped (proving the emulation is real at the engine
level) and the CSS-driven Mark correctly repainted to the new scheme's
colours — but the tab-icon `<link>`'s href never changed; it stayed frozen
at whatever it was last explicitly painted (light+indigo), even while the
Mark showed dark+indigo alongside it. Same result across 2 separately
fronted mount contexts (mid-session, and again immediately after a fresh
`location.reload()` while the emulated scheme was already dark, followed by
toggling to light).

**Control test, to separate "tool limitation" from "code defect":**
attached a plain, app-independent `window.matchMedia('(prefers-color-scheme:
dark)').addEventListener('change', …)` listener directly in the page
console (nothing to do with `tab-icon.ts`) at three different points
(mid-session, and twice fresh after reload) and toggled the scheme
repeatedly. That listener **never fired either**, while `.matches` on the
very same `MediaQueryList` object read correctly on each toggle. This is
strong (not certain) evidence that this specific browser-automation tool's
`resize_window` colour-scheme emulation updates the value CSS/JS reads but
does not dispatch the DOM `change` event to already-registered listeners —
a tooling ceiling of the kind this whole investigation has repeatedly hit
(round-1 A: cannot fetch favicons or see the real tab strip; round-2 B: the
same). `tab-icon.ts`'s listener code
(`media?.addEventListener("change", onSchemeChange)`) is the
textbook-correct, spec pattern and is unchanged in logic from round 1.
Separately confirmed the **on-mount** path is correct: a fresh
`location.reload()` taken while the emulated scheme was dark painted
`#f3f3f3`/`#7a90f2` (dark+indigo) immediately and correctly, matching the
Mark — so a real user who has their OS set to dark and opens/reloads Peer
gets the right tab icon immediately; what is unverified (in either
direction) is specifically the **live, no-reload** path while a tab stays
open and the OS scheme changes underneath it.

**Why this is flagged rather than silently marked PASS:** round-1 A's own
checkpoint claimed the opposite outcome under what should be the same
mechanism ("OS scheme emulated dark via resize_window colorScheme →
repainted unprompted... matchMedia listener fired correctly") — I cannot
fully reconcile that with what I measured now, and I am not certain which
account reflects a real end-user's browser. Given the brief's own rule

resolving the ambiguity in the implementation's favour on my own authority.
Recommend a future round either (a) get an independent confirmation using a
real (non-automated) browser with the OS appearance actually toggled, or
(b) harden `tab-icon.ts` to not rely solely on the `change` event — e.g. also
re-paint `onSchemeChange`-style whenever the tab regains visibility/focus
while `mode=system` (a cheap, defensible addition that would make this
correct regardless of which explanation is true).
