## 2. Caps — how reservation works today, and how the direct path must reuse it unchanged

**Next-side reservation** (`web/src/lib/security/jev-broker-auth.ts`, `reserveJevCall`): before any Jev/broker HTTP attempt, atomically increments `jev:<ownerId>:<UTC-day>` (via `usage/counters.ts`'s `CounterStore.increment`), checked against `perUserCap`; only if that is within cap does it then increment `jev:all:<UTC-day>` against `globalCap`. Order matters and is deliberate (Round-3 fix, `docs/jev-abc/P3-S4-A-20260924T0905Z.md` Finding 2): reserving per-user first, in isolation, means an owner already over their own cap can never also burn a unit of the shared global cap on a refused retry ("budget griefing"). Both directions fail CLOSED — an unreadable counter refuses the call (`breakerTripped`), never fails open. No rollback on a later refusal (accepted, bounded by the ordering above). `callJevViaBroker` calls this exactly once per attempt, strictly before building the wire request or touching the network.

**Edge-side reservation** (`web/supabase/functions/jev-broker/index.ts`'s `reserveBoth`, keys from `counter-keys.ts`): a SEPARATE, disjoint namespace — `jev-edge:<ownerId>:<UTC-day>` / `jev-edge:all:<UTC-day>` — added after manager finding F-M-P3-01 discovered the Edge Function used to reserve the SAME keys as the Next side, silently halving every cap (one brokered call incremented each real counter twice). This is now fixed by namespace separation, not shared logic: the Next side's count is what bounds real end-to-end spend for a normal request; the Edge side's own independent count only bounds what a leaked `PEER_JEV_BROKER_SECRET` could spend entirely on its own (defense-in-depth, §1p.H(2)), and only matters when the broker is actually deployed and reachable.

**Consequence for JEV-DIRECT (§1aa point 2 — "stay exactly as they are"): the direct path must call `reserveJevCall` exactly once per attempt, using the SAME `jev:<owner>:<day>`/`jev:all:<day>` keys, in the SAME order, with the SAME fail-closed behavior — nothing new to build here, only reuse.** It must NOT also touch the Edge's `jev-edge:*` counters: those exist solely to bound a leaked broker secret's blast radius when a request actually flows through the Edge Function; a direct call never reaches the Edge Function, so incrementing `jev-edge:*` for it would be meaningless (nothing is protecting anything by doing so) and would desynchronize that counter from what it is actually supposed to measure. **No double reservation is possible if the transport switch (§3) picks exactly one branch per call** — direct calls reserve only `jev:*`; broker calls reserve `jev:*` (Next side) and, once actually deployed, `jev-edge:*` (Edge side, unaffected either way, since JEV-DIRECT does not touch the Edge Function).

Default caps unchanged: `PEER_JEV_PER_USER_DAILY_CAP` (50), `PEER_JEV_GLOBAL_DAILY_CAP` (2000), both read the same way on the Next side regardless of which transport is selected (`flag.ts`'s `readJevShadowConfig` today; see §3 for how this is generalized without changing the numbers or their source).

## 3. Transport switch — design

**Call graph today (exhaustive — grepped `callJevViaBroker|jevBrokerEnabled|readJevShadowConfig` across all of `web/src`):** exactly 4 non-test files touch this path — `app/api/feed/route.ts` (the gate + hook builder), `decisions/shadow.ts` (the one runtime caller of `callJevViaBroker`), `decisions/flag.ts` (config), `decisions/broker-client.ts` (the broker transport itself). **"Any non-shadow decision path" does not exist today**: `decisions/types.ts`'s `DecisionProvider` interface (the general "something you can `.decide()` a paper against" abstraction) is declared and never implemented or consumed anywhere (grepped `DecisionProvider` repo-wide: 1 file, the declaration itself). So the only real call site to migrate is `shadow.ts`; the switch just needs to be written so a *future* non-shadow caller does not have to duplicate the routing.

**The Gemini decision fallback (`decisions/gemini-fallback.ts`) is unaffected and must stay unaffected.** It never calls Jev; it is a separate, company-funded `DigestProvider` call triggered by `shadow.ts` AFTER a Jev result comes back `"ok"` with ≥1 `unknown` answer (§1p.H(5)), gated by its own flag (`PEER_JEV_GEMINI_FALLBACK`) and its own injected capability (`GeminiFallbackProviderCapability`, structurally unreachable in production today since nothing mints one — confirmed by `shadow.ts`'s own doc comment and `app/api/feed/route.ts` passing no such field). Whichever transport produced the `"ok"` Jev result, the merge logic (`shadow.ts`'s `mergeFallbackAnswers`) runs identically. Nothing here changes.

**Proposed switch** (new, in `decisions/flag.ts`, alongside the existing `jevShadowEnabled`/`readJevShadowConfig`/`geminiFallbackEnabled` — this file is already the single home for every Jev-related env-var read):

```
export type JevTransport = "direct" | "broker" | "disabled";
export function resolveJevTransport(): JevTransport
```

Logic: one new, optional, literal-value env var, `PEER_JEV_TRANSPORT` (trim + lowercase, same convention as every flag here), accepting exactly `"direct"` or `"broker"` as an explicit override; anything else (unset, blank, a typo) is treated as "no override," never a crash and never a silent third meaning.
- No override → **direct when `JEV_API_KEY` is set** (§1aa point 3's own stated default), else **broker when `PEER_JEV_BROKER` is `"on"` AND `readJevShadowConfig()` reports `"configured"`** (URL+secret both present), else `"disabled"`.
- Override `"direct"` → `"direct"` if `JEV_API_KEY` is set, else `"disabled"` (an override cannot fabricate a missing key).
- Override `"broker"` → `"broker"` if broker is configured (as above), else `"disabled"` (an override cannot fabricate a missing broker config).

Why an explicit override at all, beyond bare presence-detection: the rollback runbook (`docs/JEV-RELEASE-READINESS.md` §3.1) cares about fast, secret-untouched rollback during an incident — `PEER_JEV_TRANSPORT=broker` lets an operator force the dormant broker path back on without having to unset `JEV_API_KEY` in Vercel (which may be wanted for other reasons, or slower to change than an env flag flip + redeploy). This is a genuine design trade-off, not dictated by the spec text — see POLICY item 3.

**`PEER_JEV_BROKER`'s existing meaning is untouched.** It still means "the broker path may be used at all"; the new switch only decides which of the two independently-gated paths (broker already gated by its own flag+config, direct gated by key presence) wins when more than one could apply. Nothing about today's broker behavior changes.

**Dispatcher (new, proposed file `decisions/jev-dispatch.ts`):** one function, `dispatchJevCall(request, options) → Promise<JevDispatchResult>` (the result type broker-client.ts today calls `BrokerCallResult` — same shape, see POLICY item 4 on the name), that reads the resolved transport and calls exactly one of `callJevViaBroker` (existing, unchanged) or `callJevDirect` (new, §4) — never both, never neither-then-guess. `shadow.ts`'s `runOne` changes its one call site from `callJevViaBroker(...)` to `dispatchJevCall(...)`; everything else in `shadow.ts` (cache-key derivation, concurrency, deadline, Gemini-fallback trigger, logging) is untouched, since it only ever consumed the result shape, never the transport. `app/api/feed/route.ts`'s 7-condition gate (~line 740) replaces its `jevBrokerEnabled()` condition with `resolveJevTransport() !== "disabled"`, and its `readJevShadowConfig()`-based hook input adds a resolved-transport field alongside the existing broker URL/secret/caps (still needed verbatim when transport is `"broker"`; simply unused when `"direct"`).

## 7. Opt-in live Jev smoke runner — design (C builds it; nobody runs it live without a stated budget)

**Mirror of `web/src/lib/evaluation/live-channels/*`**, adapted for a single provider with its own internal retry/pacing already built in (`jev-client.ts`'s bounded 429/529 backoff), so the S2/OpenAlex ledger's multi-provider pacing machinery (`call-budget.ts`'s `CallBudget`, `waitForS2Slot`, per-provider cool-offs) has no Jev equivalent to copy — a plain call counter is enough here, and building the heavier ledger anyway would be unjustified complexity, not thoroughness.

Proposed layout, `web/src/lib/evaluation/jev-smoke/`:
- **`gate.ts`** — mirrors `live-channels-gate.ts` exactly: `canRunJevSmoke()` reads the one opt-in literal (§6); `credentialPresence()` returns `{jevApiKey: boolean}` only — `Boolean(process.env.JEV_API_KEY?.trim())`, value discarded immediately, same one-line pattern `credentialPresence()` already uses for the S2/OpenAlex trio.
- **`inputs.ts`** — a handful of FIXED, checked-in, non-secret synthetic `DecisionRequest`s (no user data, ever): (1) a clear-match case (fabricated ML-ish title/abstract against a fabricated matching intent) exercising a confident, non-`unknown` Choice+Score answer; (2) a clear-mismatch case (same shape, deliberately unrelated field) exercising a confident "does not match" answer — still not `unknown`; (3) reuse the EXISTING fixture `web/src/lib/decisions/__fixtures__/cjk-paper.json` (title "锂离子电池正极材料的循环稳定性研究" — already checked in, already used by `jev-contract.test.ts`'s CJK path) wrapped in a fixed synthetic intent, exercising the CJK truncation-budget path live (§1p.H(9)'s actual concern) instead of inventing a new CJK fixture; (4) an ambiguous/thin-abstract case designed to plausibly produce a low-confidence or `insufficient_information` answer, so the runner can prove it observes and reports an `unknown` result too, not only the happy path. 4 inputs, well under any sane ceiling.
- **`runner.ts`** — `runJevSmoke(options)`: for each input (up to the ceiling), calls `callJevDirect` DIRECTLY (not the transport switch — the whole point of this runner is confirming the direct path specifically) using a **throwaway in-memory `CounterStore`, created fresh for the run and discarded after** — never the real Supabase-backed store. This is not a shortcut, it is required by the spec's own allow-list: item 7 says the smoke config's exact-name allow-list is "JEV_API_KEY only," meaning no Supabase credentials are available to this process at all, so a real reservation is structurally impossible here and must not be attempted. A synthetic fixed `ownerId` (e.g. `"jev-smoke"`) and generous caps on the in-memory store mean reservation always succeeds and this run never touches, or is bounded by, any real user's or the real global daily cap.
- **Hard ceiling:** a plain counter, default 10 (the spec's own suggested number), incremented once per LOGICAL smoke input attempted (i.e., once per `callJevDirect` call — jev-client.ts's own internal 429/529 retries inside that one call do not count again, mirroring how `reserveJevCall` itself reserves one unit per logical call regardless of that call's internal retries).
