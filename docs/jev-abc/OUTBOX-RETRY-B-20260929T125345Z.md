## 1. Path enumeration

### 1.0 The pending-key machinery today (context, unchanged by this item)

Three key builders in `feed.ts` (L178–186):
- `pendingSavedKey(itemKind, itemId)` → `` `saved:${itemKind}:${itemId}` `` — shared by `cloudSave` **and** `cloudUnsave` (deliberate: §1aq point 1, "a failed save followed by a successful unsave is consistent").
- `pendingReadKey(itemId)` → `` `read:${itemId}` `` — shared by `cloudMarkRead` **and** `cloudMarkUnread`. No kind segment.
- `pendingFeedbackKey(itemKind, itemId)` → `` `feedback:${itemKind}:${itemId}` `` — only ever a POST (no "un-feedback" action exists — confirmed by `positive-seeds.ts` L18–20's own note that the stored `feedback` union has no undo-type value).

**Parsing gotcha for the retry design (important, not yet needed by any existing code):** `itemId` for papers is itself of the form `"source:nativeId"` (e.g. `"openalex:W2005027801"` — confirmed by `web/src/app/api/feedback/route.ts` L32–50's `resolvedIdsFromItemId`, which splits on the *first* `:`). So `pendingSavedKey("paper","openalex:W123")` = `"saved:paper:openalex:W123"` — **4 colon-separated segments, not 3.** A naive `key.split(":")` to recover `(kind, id)` breaks the id. Any parser must split only on the first one or two colons (see §2).

`updateFeedPushFailedFlag(ok, key)` (L219–225) is the *only* place any helper marks/clears a key: `ok=false` → `markFeedPendingKey(key)` (sync-status.ts L75–79) + `setPendingPushPersisted(ownerId, key, true)` (feed.ts L204–217); `ok=true` → `clearFeedPendingKey(key)` (sync-status.ts L84–90) + `setPendingPushPersisted(ownerId, key, false)`. Gated on `useSyncGate.getState().authUserId` (L220–221) — a signed-out write touches neither map, proven by existing tests (feed.test.ts L1092–1134).

### 1.1 The five write kinds

For each: trigger(s), what the reload migration batch (`feed-sync.tsx` L201–235) does with it today, and exactly what state a retry needs.

**1. `cloudSave`** (POST `/api/saved`, upsert on `(user_id, item_id)` — `api/saved/route.ts` L68–76) — fired from `savePaper`/`saveEvent`/`saveJob` (feed.ts L2072, L2156, L2245) after the item is already in `savedPapers`/`savedEvents`/`savedJobs`.
- *Retried today?* Yes, if the item is **still** saved locally at the next reload — the batch re-POSTs every entry currently in `local.savedPapers`/`savedEvents`/`savedJobs` (feed-sync.tsx L206–208), payload = the item object itself.
- *What a retry needs:* `itemId`, `itemKind` (both recoverable from the key), and the **payload** = the current item object. Already fully available, no new storage: `state.savedPapers`/`savedEvents`/`savedJobs` (persisted, `partialize` L2901–2903) hold the exact same shape the interactive call site and the migration batch both already send.

**2. `cloudUnsave`** (DELETE `/api/saved?itemId=` — route.ts L84–108) — fired from `unsavePaper`/`unsaveEvent`/`unsaveJob` (L2326, L2367, L2405) and from `commitDismiss` when `pending.wasSaved` (L2642), *after* the item is removed from `savedPapers`/etc.
- *Retried today?* **Never.** The item is gone from local state by definition (that's what unsave means), so the migration batch's "re-POST what's present" loop can't see it (§1aq CORRECTION, confirmed by feed-sync.tsx L201–209 never issuing a DELETE).
- *What a retry needs:* only `itemId` + `itemKind` — both recoverable from the pending key itself (`saved:<kind>:<id>`), same key `cloudSave` uses. **No payload.** Idempotency: `api/saved/route.ts` DELETE (L98–102) is `supabase.from("saved_items").delete().eq(user_id).eq(item_id)` — deleting 0 matching rows is not a Postgrest error, it returns `{ok:true}` same as deleting 1. An already-gone item is a silent no-op success, not a 4xx.

**3. `cloudMarkRead`** (POST `/api/read`, upsert — route.ts L60–88) — fired from `markRead` (L2435) after `readItems[id]=true`.
- *Retried today?* Yes, if still read at the next reload — batch re-POSTs every id currently in `local.readItems` (feed-sync.tsx L209).
- *What a retry needs:* only `itemId` (from the key, `read:<id>` has no kind segment). No payload — `POST /api/read`'s body is `{itemId}` only (route.ts L69).

**4. `cloudMarkUnread`** (DELETE `/api/read?itemId=` — route.ts L90–114) — fired from `markUnread` (L2451) after the id is removed from `readItems`.
- *Retried today?* **Never**, same reasoning as `cloudUnsave` — item absent from `local.readItems`, batch never issues the DELETE.
- *What a retry needs:* only `itemId` (from the key). Idempotency: same shape as `/api/saved` DELETE (route.ts L104–108) — 0 matching rows is a normal success, never a 4xx.

**5. `cloudFeedback`** (POST `/api/feedback`, **plain `.insert()`, append-only** — route.ts L77–92) — fired from `submitFeedback` (L2414), itself called by `savePaper`/`saveEvent`/`saveJob` (with feedback literal `"saved"`), `notInterestedPaper`/`Event`/`Job`, `moreLikePaper`/`Event`/`Job`, and `commitDismiss` (feedback `"notInterested"`).
- *Retried today?* **Never** — the migration batch's push loop only touches `savedPapers`/`savedEvents`/`savedJobs`/`readItems`, never `paperFeedback`/`eventFeedback`/`jobFeedback` (confirmed: `feed-sync.tsx` has no reference to any `*Feedback` field anywhere in the file).
- *What a retry needs — the value:* **yes, still stored locally**, but only the *classification*, not the full write. `paperFeedback`/`eventFeedback`/`jobFeedback` (`Record<string, ItemFeedback>`, persisted — `partialize` L2914–2916) hold the reader's **current** feedback status per item id, kept up to date by every action that touches it (`savePaper` L2067, `notInterestedPaper` L2090, `moreLikePaper` L2116, and the matching event/job actions) — this is exactly the "latest local state wins" value to resend.
  - **One pre-existing wrinkle, traced precisely because it affects retry correctness:** `savePaper` (L2054–2058) computes `savedFeedback` — normally `"saved"`, but *preserves* `"moreLikeThis"`/`"liked"` if that was the previous value — and stores `savedFeedback` into `paperFeedback[id]` (L2067). But the literal event value it sends via `submitFeedback` two lines later (L2073–2078) is hardcoded `"saved"`, **not** `savedFeedback`. So in that one rare path, `paperFeedback[id]` can already (today, pre-existing, unrelated to this item) diverge from the exact literal value the original `cloudFeedback` call attempted. A retry that resends `paperFeedback[id]` (the only sane "current truth" source) will in that rare case resend `"moreLikeThis"`/`"liked"`, not the literal `"saved"` the failed request carried — consistent with "never resurrect an old state," not a new bug this design introduces.
- *What a retry needs — the payload:* **no, not stored anywhere durable today.** `cloudFeedback`'s `payload` argument (optional) is always `feedbackSnapshotForPaper/Event/Job(item)` at the call site (`ledger.ts` L761–780) = `{title, concepts}`, computed from the **full item object**, not from the feedback value. Nothing persists this snapshot:
  - If the item is currently saved, the full object is available (`savedPapers`/etc., persisted) → recomputable.
  - `papers` (today's unsaved feed list) **is** persisted (`partialize` L2900, "so a hard refresh... finds a paper", bounded ~50, can go stale/be overwritten by the next fetch) → a not-guaranteed fallback for paper-kind only.
  - `events`/`jobs`/`eventPool`/`jobPool` (the unsaved event/job pools) are **not** persisted at all (absent from `partialize` L2891–2954; `resetLocal` L2817–2819 shows they're plain transient state, reset to `[]`). So a pending `feedback:event:<id>` or `feedback:job:<id>` key for an item that was never saved has **no** local source for the snapshot after a reload.
  - Consequence: a naive "recompute from current item" retry silently sends `payload: undefined` (→ stored as `null`, route.ts L75) for that case, dropping `title`/`concepts` from the stored row. Downstream cost, traced precisely: `positive-seeds.ts` `seedFromRow` (L428–439) reads `payload.title` for the resolved seed's display title and `payload.resolvedIds` — but `resolvedIds` is derived **server-side from `itemId`** (route.ts L72, independent of client payload) and merged in regardless, so only the `title` field is actually lost, not identity resolution. Low but real cost — see §2's design for the fix (capture the payload once, at the moment it's known, rather than trying to reconstruct it later).
- *Idempotency — "feedback sent twice":* `feedback_events` (`schema.sql` L213–221) has **no unique constraint** beyond its own `bigserial id` — a retried POST that actually lands twice (e.g. the original write succeeded server-side but its response never reached the client) creates two rows. The **only** current reader, `positive-seeds.ts`, already collapses to one row per `item_id` by taking the **most recent** row (`latestEventPerPaper`, doc'd L40–57) before classifying — so two identical-value rows for the same item are inert for this consumer (same classification either way), at the cost of one extra slot inside its bounded 200-row read window (`RESOLUTION_WINDOW_MULTIPLIER=20`, L142) — negligible per that same file's own disclosed-headroom reasoning. No other consumer of `feedback_events` exists in the repo today (grepped; only `positive-seeds.ts`, its test, and `route.ts` itself reference the table name).

### 1.2 Signed-out / owner isolation (context for §2)

`updateFeedPushFailedFlag` already refuses to touch anything when `authUserId` is null (L220–221). `pendingPushByOwner` is namespaced by `authUserId` end to end (set at L209/L214-216, read at feed-sync.tsx L195, cleared per-leaving-owner at L2810–2813) — never `currentOwnerKey()`/`entitlement.userId`, specifically to dodge a resolution-order gap between those two signals (documented at feed.ts L198–203). Any retry must reuse this exact signal, not invent a second "who am I" check.

## 2. Design

### 2.0 Summary

Add one new store action, `retryPendingPushes()`, that walks the signed-in owner's own persisted `pendingPushByOwner` record, decides — **per key, from current local state, never from what originally failed** — whether to resend a save, an unsave, a mark-read, a mark-unread, or a feedback POST, and lets the *existing* `cloudSave`/`cloudUnsave`/`cloudMarkRead`/`cloudMarkUnread`/`cloudFeedback` helpers do the actual HTTP + key-clearing exactly as they already do for an interactive click. Call it from the one place that already seeds the in-memory flag from this record on every natural sync point — `feed-sync.tsx` L193–197 — so it rides the *existing* reload/reconnect cadence with no new timer, schedule, or listener. One small new piece of persisted state is needed (§2.3) to make feedback retries carry their `{title, concepts}` payload reliably; everything else reuses machinery that already exists.

### 2.1 Direction: derive from current state, never store "which HTTP verb failed"

`saved:<kind>:<id>` is shared by `cloudSave` (POST) and `cloudUnsave` (DELETE) *by design* (§1aq point 1). The key alone can't say which direction to retry — and it must not: if it's pending because a save failed, and the reader has since unsaved, resending the save would resurrect a state the reader explicitly reversed. So direction is a **read of current local truth at retry time**, not a memory of the original failure:

- `saved:<kind>:<id>` → is `<id>` currently in `savedPapers`/`savedEvents`/`savedJobs` (pick the array by `<kind>`)? Present → call `cloudSave(id, kind, item)` with that array entry as payload (identical shape to what the migration batch already sends, feed-sync.tsx L206–208). Absent → call `cloudUnsave(id, kind)`.
- `read:<id>` → is `readItems[id]` currently truthy? Yes → `cloudMarkRead(id)`. No → `cloudMarkUnread(id)`.
- `feedback:<kind>:<id>` → is `<kind>Feedback[id]` currently defined? Defined → `cloudFeedback(id, kind, currentValue, payload)` (payload sourcing: §2.3). **Undefined → drop the key without any network call** (see §2.2 — this is the one case with no "current state" to assert).

This is the *entire* answer to "the item was changed again since": every dimension is re-derived from whatever local state says *right now*, at the moment retry actually runs, using the same fields the UI itself already treats as ground truth. There is no separate "was it a POST or a DELETE that failed" bit anywhere, so there's nothing that can go stale.

### 2.2 The one case with no current state: a moot feedback key

`unsavePaper`/`unsaveEvent`/`unsaveJob` delete `<kind>Feedback[id]` **only** when the current value was `"saved"` (feed.ts L2309–2310, L2334–2335, L2374–2375 — identical pattern all three places). So: save fails → `feedback:<kind>:<id>` pending, value `"saved"` → reader unsaves before any retry runs → local feedback entry for that id is deleted entirely. At that point there is no honest value left to send — the local state no longer asserts *any* feedback for that item. Resending the old `"saved"` would be exactly the "resurrect an old state" the brief warns against. Design: when `retryPendingPushes` finds a `feedback:` key whose `<kind>Feedback[id]` is currently `undefined`, it clears the key (in-memory `clearFeedPendingKey` + the owner's persisted entry, same two calls `updateFeedPushFailedFlag(true, key)` would make) **and clears its captured payload (§2.3)**, without ever calling `cloudFeedback`. This is the only branch retry adds beyond "call the existing helper with today's state."

(`saved:`/`read:` never hit this branch — "present or absent" is always a definite, retryable answer; only the three-way `defined notInterested/moreLikeThis/liked/saved` vs. `undefined` feedback case has a genuine "nothing to say" state.)

### 2.3 Feedback payload: capture once, at the moment it's known, not reconstructed later

§1.1 point 5 found the gap precisely: `<kind>Feedback[id]` (the *value*) survives a reload; the `{title, concepts}` *payload* snapshot does not, and for an unsaved event/job it cannot even be recomputed after a reload (the pool isn't persisted). Recomputing best-effort at retry time is a real fallback but a lossy one for exactly the cases that matter most (an item that was never saved).

Design: capture the payload **once, in `cloudFeedback`'s own catch branch**, where it is already a parameter in scope — zero recomputation, zero staleness risk, mirrors the "persist exactly the minimal data needed, at the moment of failure" philosophy `pendingPushByOwner` itself already established (its own doc comment, feed.ts L1236–1246).

- New `FeedState` field: `pendingFeedbackPayloadByOwner: Record<string /*ownerId*/, Record<string /*the feedback:<kind>:<id> key*/, unknown /*payload*/>>`. Same owner-namespacing shape as `pendingPushByOwner`, added to `partialize` alongside it — **no version bump needed**, same reasoning C already verified for `pendingPushByOwner` itself (feed.ts L2939–2952: brand-new key, safe `{}` default, zustand's default `merge` backfills an old blob fine).
- `cloudFeedback`'s catch branch (currently L300–302) additionally sets `pendingFeedbackPayloadByOwner[ownerId][key] = payload`. Its try branch (currently L296–299, on success) additionally deletes that entry. Neither touch is needed in the other 4 helpers — this map exists solely for the `feedback:` dimension.
- `resetLocal` additionally clears the **leaving** owner's `pendingFeedbackPayloadByOwner` entry, mirroring exactly how it already clears that owner's `pendingPushByOwner` entry (L2810–2813) and for the identical reason (the local data it would describe is about to be destroyed).
- Why a separate map rather than widening `pendingPushByOwner`'s value type from `true` to `true | {payload}`: fewer existing call sites to touch (that shared set's value is read/spread/deleted as bare `true` in `setPendingPushPersisted`, `applyMigrationPushResult`, and every existing test) versus one new field only `cloudFeedback` + the retry action + `resetLocal` + `partialize` need to know about. Smaller, more localized diff.
- Retry's payload lookup, in order: (1) `pendingFeedbackPayloadByOwner[ownerId][key]` if present (the normal case, going forward) → (2) best-effort recompute from `savedPapers`/`savedEvents`/`savedJobs` if the item is currently saved, else (paper-kind only) a match in the persisted `papers` list → (3) `undefined` (send no payload; matches today's total loss, only for a pending key that predates this fix — e.g. one persisted by an already-shipped build before the new capture-at-fail-time code exists to have written it). Layer (1) covers every *new* failure from the moment this ships; layers (2)/(3) are a safety net, not the primary path.
- Correctness note for whoever reviews this: the *captured* payload is content only (`title`/`concepts` from an immutable, already-fetched paper/event/job — never user-edited), so reusing a payload captured at first failure on a later retry attempt is always safe. Only the *feedback value itself* is time-varying, and that is always re-read fresh from `<kind>Feedback[id]` at the moment of each retry (§2.1) — never taken from the captured-payload map, which stores content, not status.

### 2.4 Idempotency

- **`cloudUnsave`/`cloudMarkUnread` retries (DELETE):** naturally idempotent — confirmed by reading both routes (`api/saved/route.ts` L98–102, `api/read/route.ts` L104–108): a Postgrest `.delete().eq(...)` matching 0 rows is a normal `{ok:true}`, not an error, not a 4xx. "A DELETE that is already gone" requires no client-side special-casing at all.
- **`cloudSave`/`cloudMarkRead` retries (POST):** both routes upsert on a real unique constraint (`onConflict: "user_id,item_id"`, route.ts L75/L81) — resending an already-applied save/read is a harmless no-op refresh, not a duplicate.
- **`cloudFeedback` retries (POST, append-only insert):** genuinely *not* idempotent at the DB layer (§1.1 point 5) — analyzed above: the only current reader already collapses same-item duplicates to "latest wins," so a duplicate of the identical value is inert in practice, at a small, bounded, disclosed cost. Not solved by a schema change here (see POLICY P6, §3).
- **Server 4xx for an item that no longer exists:** traced per route — neither `/api/saved` nor `/api/read` nor `/api/feedback` has any "does this item exist" check that a retry could trip (saved/read are pure ownership-scoped upsert/delete; feedback is a pure insert with no foreign key to any items table). The only 4xx path on any of the three routes is a missing required field (`itemId`/`itemKind`/`payload`-for-save/`feedback`), and retry — by construction (§2.1) — only ever fires with all of those already in hand. No new 4xx-handling branch is needed anywhere; every helper's existing "any failure (4xx, 5xx, or network) → still pending, try again next time" try/catch already covers it (this is also why retry calls the *existing* 5 helpers verbatim rather than writing new HTTP logic).

### 2.5 Signed-out reader / owner isolation

`retryPendingPushes` reads `useSyncGate.getState().authUserId` first and returns immediately if it's `null` — the same gate `updateFeedPushFailedFlag` already uses (feed.ts L220–221), so "never retries when signed out" falls out of reusing the identical signal rather than a new check to get wrong. It only ever reads/clears `pendingPushByOwner[ownerId]` and `pendingFeedbackPayloadByOwner[ownerId]` for that **one** `ownerId` — never all owners, never a different one — mirroring exactly how the existing seed call (feed-sync.tsx L194–196) and `cloudFeedback`'s own write path already scope themselves. No new cross-owner surface is introduced.

### 2.6 When it runs — no new schedule, no tight loop

Splice one call into `feed-sync.tsx`'s `onSession`, immediately after the existing seed block (L193–197), **before** the `didInitialSyncRef` early-return (L198) — i.e. it runs independently of, and every time, regardless of whether the once-per-mount migration batch itself runs:

```
if (userId) {
  replaceFeedPendingKeys(
    useFeedStore.getState().pendingPushByOwner[userId] ?? {},
  );
  void useFeedStore.getState().retryPendingPushes();
}
```

`onSession` already fires on: (a) mount / hard reload (L281–287), and (b) **every** Supabase `onAuthStateChange` event that carries a session (L289–292: `else if (session?.user) onSession(session.user.id);` — this is not limited to `SIGNED_IN`; it also catches `TOKEN_REFRESHED` and any other in-session event Supabase emits on its own cadence, roughly hourly by default). That second path is the "on reconnect" trigger the brief asks for — it already exists, today, unconditionally, for a reason unrelated to this item; this design adds nothing new to *how often* it fires, only *what happens* on the calls that were already going to happen. No `setInterval`, no new listener, no polling.

Bounding concurrency (not correctness-critical — see §2.7 — but cheap and consistent with the file's own idiom): mirror the existing `pendingAckInFlight` module-level guard (feed.ts L1458, checked L1505, set/cleared L1557–1560) with a new `pendingRetryInFlight: Promise<void> | null` so two overlapping `onSession` calls (e.g. a `TOKEN_REFRESHED` landing while the mount-time retry is still in flight) collapse into one outstanding batch rather than firing duplicate HTTP requests per key.

Retry count: unbounded over time, one attempt per currently-pending key per `onSession` call — the same "keep trying at every natural sync point, forever, until it succeeds or is superseded" shape the migration batch itself already has for the keys it *does* cover. No internal retry-with-backoff loop inside `retryPendingPushes` itself (each key gets exactly one `cloudX` call per invocation; the *next* natural sync point is the next attempt).

### 2.7 Disclosed, not solved: same-item race between a retry and a fresh interactive click

If `retryPendingPushes` reads "item X is currently saved" and starts `cloudSave(X)`, and the reader clicks unsave on X a moment later (starting its own `cloudUnsave(X)`) before the retry's request resolves, both are in flight for the same key at once; whichever response arrives last decides the key's final pending/cleared state, independent of which action is semantically "more current." This is not a new class of race — today, two rapid interactive clicks on the same item already resolve the same way (nothing in any of the 5 helpers sequences concurrent calls on one item) — retry only adds one more possible concurrent caller. Closing it properly needs per-item request sequencing (e.g. an abort/version-token per key), which is real scope beyond "retry the outbox" for keys that already aren't retried at all today. Recorded as accepted, same tolerance the codebase already has elsewhere for this class of race; flagged as POLICY P5 in case the manager wants it closed now instead.
