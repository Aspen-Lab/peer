DESIGN CHOICES (full):
1. **Structure:** `deliveredLocal: Record<string, string>` (paper id -> `localCalendarDate()` string, e.g. `"2026-09-24"`) chosen over an ordered list — a plain map keeps id-based lookup/overwrite O(1) and the date-string values are what both the cap-pruning and the before-today filter need directly; ordering for "most recent first" and "oldest first" is derived by sorting `Object.entries` by the date string (which sorts correctly lexicographically for YYYY-MM-DD) at the point of use, not maintained as a separate structure.
2. **Cap behaviour:** `DELIVERED_LOCAL_CAP = 5000`, enforced by `pruneDeliveredLocal` (mirrors the existing `pruneRecentlyShown` shape) every time `recordPendingLocalDelivery` writes. No TTL — the ONLY bound is size, per §1p.C.1's explicit "no TTL, local cap raised to 5,000". `DELIVERED_EXCLUDE_SEND_CAP = 800` matches the server's own `parseExcludeIds` cap exactly (`web/src/app/api/feed/route.ts`) so the client's own priority ordering — not an arbitrary server-side slice — decides what survives truncation.
3. **Persist version:** bumped 1 -> 2 (not left at 1). Justification, argued from first principles and cross-checked against the P4-S5a-FIX A review's own F-A-NEW-01 finding: zustand's `persist` middleware only invokes the configured `migrate` function when the STORED version differs from the CONFIGURED version. Every currently-shipped `localStorage` blob already has `version: 1` written into it (that has been the version since before this campaign). If this slice left `version` at 1, `migrate` would never be called at all for any real, already-hydrated browser — the deliveredLocal-seeding-from-recentlyShownIds step (design point 6 below) would be dead code that never executes outside a test harness calling `migrate` directly. F-A-NEW-01 flagged exactly this class of gap for `renderedBatchId` (added to `partialize` without a version bump) as safe-but-suboptimal; this slice does not repeat it for `deliveredLocal`, where skipping the bump would be worse (an inert seeding function, not just a delayed retry).
4. **Migration/seeding from `recentlyShownIds`:** on a version-1 blob rehydrating (i.e. `version < 2`) with no `deliveredLocal` key yet, seed it by converting every `recentlyShownIds` entry's stored ms timestamp to a local calendar date (`localCalendarDate(new Date(ts))`) and pruning to the same 5,000 cap. This is real evidence (an actual prior render timestamp this device recorded), never fabricated — entries `recentlyShownIds`' own 14-day TTL already dropped before this code ever runs are honestly absent from the seed, not guessed at, matching §1g's "cannot promise to reconstruct never-recorded history." Guarded by `!current.deliveredLocal` so it runs exactly once (a second rehydration of an already-version-2 blob has the key present and is left alone) and never overwrites a blob that's already been seeded or is genuinely fresh.
5. **Write timing / "exactly once per rendered set":** modeled as an explicit two-phase arm-then-record cycle, deliberately mirroring the existing `pendingBatchAck`/`acknowledgePendingBatch` idiom rather than inventing a new pattern: `papersLane`'s single `set()` call arms `pendingLocalDelivery` (to the rendered ids, or `null`) atomically with `papers`/`renderedBatchId` themselves — the same atomicity guarantee `renderedBatchId` already relies on, argued the same way in that field's own comment. The actual write into `deliveredLocal` happens only in `recordPendingLocalDelivery`, called from the hook only once its own `shouldRecordDeliveredLocal` predicate (cardsRendered && pendingLocalDelivery non-empty && visibilityState === "visible") is true — never from inside the `set` updater itself, per this campaign's standing STOP condition (`ABC-JEV-INTEGRATION.md`'s P4-S5 slice contract: side effects only in a component effect after mount, not inside a Zustand `set` updater). Because the action clears `pendingLocalDelivery` to `null` the moment it records, a repeat hook trigger (e.g. two `visibilitychange` events before a new load) is a structural no-op, not merely idempotent-by-coincidence — proven directly by the "second fire" test in `recordPendingLocalDelivery`'s describe block.
6. **Same-day stability (the manager's explicit refinement for this slice):** `deliveredBeforeLocalDate(map, today)` filters strictly to `date < today`, so an id stamped with TODAY's date is never in the excludeIds this same day, however many times the page reloads — a same-day reload cannot rotate the cards. This is the one point where this slice's contract differs from a literal reading of §1p.C.1 alone (which does not itself spell out the same-day carve-out) — implemented exactly as the manager's refinement (binding for this slice) states it.
7. **`resetLocal` (sign-out):** clears `pendingLocalDelivery` (a stale pointer into papers that are wiped in the same call) but deliberately leaves `deliveredLocal` itself untouched. Reasoning: this memory is framed as device-scoped, not account-scoped, by both the binding ruling (§1p.C.1: "weaker than the signed-in guarantee... signed-out users") and B's own guide (`P4-B` §3: "single device, cleared by clearing browser storage") — resetting it on sign-out would defeat its purpose for the common pattern of a user signing out/in repeatedly on the same browser. Named explicitly in REMAINING as the accepted cost on a genuinely shared device.
8. **`excludeIds` composition/priority:** `dismissedPaperIds` (explicit "not interested", highest priority) ++ `deliveredBeforeTodayIds` (most-recent-date-first) ++ `recentlyShownAndDisplayed` (only when `advanceHistory`, existing behaviour/order preserved) -> `Set`-deduplicated -> savedIds-filtered -> `.slice(0, 800)`. Unlike `recentlyShownIds`, the delivered-before-today source is NOT gated behind `advanceHistory` — it applies to every load, because 16a/16b ("batch excluded from tomorrow") must hold on an ordinary next-day visit, not only after an explicit refresh click. Verified this does not disturb the pre-existing "advances recently-shown only when explicitly requested" test (still passes unmodified — deliveredLocal is empty throughout that test, so the new source contributes nothing there); added a clarifying, non-assertion-altering comment next to its "no excludeIds on a plain load" assertion explaining precisely why it still holds.
9. **Batched responses:** a non-null `renderedBatchId` (a real `batchId` came back, meaning `PEER_DASHBOARD_LEDGER` is on and the signed-in server ledger owns delivery) arms `pendingLocalDelivery: null` unconditionally in the same `set()` call — explicitly, not merely "left alone" — so a PRIOR batchless load's un-recorded pending set can never be mistakenly credited once a batched response supersedes it. Directly tested ("clears a stale pendingLocalDelivery once a batched response supersedes it").
