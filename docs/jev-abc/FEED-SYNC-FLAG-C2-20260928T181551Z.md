## Step 1 — Reload-honesty investigation (DONE, §1aq point 2 — cite file:line)

**Question:** does a signed-in page reload re-push local-only saved/read/feedback items to the account?

**Answer: split by direction and by dimension — not a simple yes/no.**

1. A plain reload of an **already-signed-in** session DOES re-run the migration-push section, not just first sign-in:
   - `web/src/lib/feed/session-step.ts` L46-57 (`sessionStep`): returns `"sync"` whenever a real `userId` is present and either there was no prior sync OR `syncedUserId === userId` — true on every reload of an already-signed-in session, since `syncedUserId` is itself persisted (`web/src/store/feed.ts`, inside `partialize`).
   - `web/src/components/feed-sync.tsx` (pre-edit L126): `const didInitialSyncRef = useRef(false);` — a per-MOUNT ref, false again on every fresh page load.
   - `web/src/components/feed-sync.tsx` (pre-edit L148-154): `if (step === "keep") return;` (never true when signed in) then `if (!userId || didInitialSyncRef.current) return;` — on a fresh reload this does not return, so the push section runs again.
2. But the migration batch only **re-POSTs items CURRENTLY PRESENT in local state** — `feed-sync.tsx` (pre-edit L162-165): `for (const p of local.savedPapers) pushSaved(...)`, same for `savedEvents`/`savedJobs`/`readItems`. It never sends a DELETE. So a failed `cloudSave`/`cloudMarkRead` (item still present locally) **is retried**; a failed `cloudUnsave`/`cloudMarkUnread` (item already absent locally — that is what unsave/unread means) **is never retried by anything**.
3. **Feedback is never in the migration batch's scope at all** — read `feed-sync.tsx` in full; the push loop only touches `savedPapers`/`savedEvents`/`savedJobs`/`readItems`. A failed `cloudFeedback` is **never retried by anything** (matches §1aj finding (d), "feedback is push-only").
4. No other retry mechanism exists anywhere (A's own grep for `setInterval`/`retry`/`pushQueue`, corroborated by my own read of the 5-helper block).

**Conclusion: persist the whole pending set.** Retry-on-reload is not universal — never for unsave/mark-unread in either direction, never for feedback in either direction. Persisting the cases that DO get retried is harmless (the key is just cleared a moment sooner, by the retry's own success). This evidence is also written directly into `store/feed.ts`'s own "RELOAD HONESTY" code comment (above `cloudSave`) and `pendingPushByOwner`'s doc comment on `FeedState`, so it travels with the code.

## Step 2 — Design (DONE)

- **`web/src/lib/feed/sync-status.ts`** (full rewrite): `useFeedSyncStatus` now holds `{ pendingKeys: Record<string, true>; pushFailed: boolean }` (derived: non-empty set ⇒ true). Read shape for the two outside consumers (`account-section.tsx`, `app/profile/page.tsx`) is **unchanged** — both only ever select `.pushFailed`; neither file was touched. New exports: `markFeedPendingKey(key)`, `clearFeedPendingKey(key)`, `replaceFeedPendingKeys(next)`. Old no-arg `markFeedPushFailed`/`clearFeedPushFailed` removed (only ever called from `feed.ts`/`feed-sync.tsx`, both mine).
- **`web/src/store/feed.ts`**: key builders `pendingSavedKey` → `saved:<itemKind>:<itemId>`, `pendingReadKey` → `read:<itemId>`, `pendingFeedbackKey` → `feedback:<itemKind>:<itemId>`. `cloudUnsave` gained an `itemKind` parameter (round-1 had none) so an unsave's key matches the same item's save key exactly; all 4 call sites (`unsavePaper`/`unsaveEvent`/`unsaveJob`/`commitDismiss`) already had the kind available (`"paper"`/`"event"`/`"job"`/`pending.kind`). New persisted field `pendingPushByOwner: Record<string, Record<string, true>>`, keyed by `useSyncGate`'s `authUserId` directly (the same signal already gating these writes) — deliberately NOT `currentOwnerKey()`/`entitlement.userId`, to avoid a possible resolution-order divergence between the two signals. **No version bump** — verified directly against the installed zustand 5.0.12's actual default `merge` in `node_modules/zustand/esm/middleware.mjs` L333-336 (`{...currentState, ...persistedState}`): a brand-new key with a safe default (`{}`) backfills correctly for old blobs with no `migrate` step, unlike `deliveredLocalByOwner`'s v2→v3 bump, which was reshaping an EXISTING field's stored value.
- **Migration batch** (`feed-sync.tsx`): new store action `applyMigrationPushResult(ownerId, fullySucceeded)` — full success clears the WHOLE pending record for that owner, in-memory and persisted (§1aq: "may clear the whole set... it pushed everything"); any failure adds one coarse synthetic key `"migration"` (`MIGRATION_PENDING_KEY` in `feed.ts`) rather than attributing the failure to one specific item (§1aq: "a failed batch keeps/sets it as today" — deliberately not given the steady-state helpers' per-item precision; S1/S2 were about the steady-state helpers, not the migration batch).
- **Reload seeding**: `feed-sync.tsx`'s `onSession`, once `userId` is known (covers `"sync"` and `"reset-then-sync"`, placed right after the reset-handling block, before the `didInitialSyncRef` early-return), seeds the in-memory flag via `replaceFeedPendingKeys(useFeedStore.getState().pendingPushByOwner[userId] ?? {})`.
- **`resetLocal()`**: captures `get().syncedUserId` (the LEAVING owner) before wiping state, clears THAT owner's own `pendingPushByOwner` entry to `{}` (never a different owner's), and calls `replaceFeedPendingKeys({})` to clear the in-memory flag. This is a new requirement introduced BY persistence — round 1 had nothing to go stale; without it, a stale pending record from before sign-out would wrongly reappear as "you have unsynced changes" on a LATER sign-in of the same owner on this device, after `resetLocal` already destroyed the local data it was tracking.
- **Deliberately NOT done**: no owner-count bounding/eviction for `pendingPushByOwner` this round (unlike `deliveredLocalByOwner`'s `MAX_DELIVERED_LOCAL_OWNERS`). Named and reasoned in `pendingPushByOwner`'s own doc comment on `FeedState`: a pending-push entry is a handful of short strings, self-cleaning on the next matching success or the next fully-successful migration batch — a materially smaller, slower-accruing footprint than `deliveredLocalByOwner`'s real per-owner paper-id history, which is why THAT one needed a bound and this one, this round, does not. A deliberate, disclosed scope decision, not an oversight.
- **Also not done**: `commitDismiss`'s new `cloudUnsave(pending.id, pending.kind)` call site has no dedicated new test (the other 3 call sites — `unsavePaper`/`unsaveEvent`/`unsaveJob` — exercise the identical `cloudUnsave`/`pendingSavedKey` code `commitDismiss` also runs through; setting up `commitDismiss`'s own precondition, `pendingDismissal`, is unrelated machinery). Disclosed scope trim, not an oversight.

## Correction round (§1aq CORRECTION, manager) — DONE

The manager corrected §1aq point 1 after reviewing my own Step 1 reload-honesty finding above: a fully successful migration batch was ruled to "clear the whole set (it pushed everything)", but my own finding shows the batch only re-POSTs items CURRENTLY PRESENT locally (never a delete, never feedback) — so "it pushed everything" was never true for a pending unsave/mark-unread or any feedback key. Corrected ruling: `applyMigrationPushResult`'s full-success branch clears ONLY the keys the batch actually re-pushed, plus the coarse `"migration"` key; a pending unsave/mark-unread (item absent locally) and every feedback key survive a successful batch until their OWN dimension's later write succeeds. The failure branch is unchanged ("keeps/sets it as today").

### What changed

- **`web/src/store/feed.ts`**: `applyMigrationPushResult`'s signature gained a `pushed` parameter — `{ savedPapers: {id:string}[]; savedEvents: {id:string}[]; savedJobs: {id:string}[]; readIds: string[] }` — exactly what the calling batch attempted to push. The full-success branch now builds `pushedKeys` from `pushed` (via the SAME private `pendingSavedKey`/`pendingReadKey` builders the steady-state helpers use) and clears ONLY those keys + the coarse key, both in-memory and in the persisted `pendingPushByOwner[ownerId]` entry — never anything else. `FeedState`'s doc comments for `applyMigrationPushResult` and `pendingPushByOwner` rewritten to state the corrected behaviour and name "§1aq CORRECTION" with the reasoning.
- **`web/src/components/feed-sync.tsx`**: the call site now passes `{ savedPapers: local.savedPapers, savedEvents: local.savedEvents, savedJobs: local.savedJobs, readIds: Object.keys(local.readItems) }` — the exact same four sources `localPushes` was already built from moments earlier, so "what this batch pushed" can never drift from "what `pushed` says it pushed". Added a "§1aq CORRECTION" paragraph to the file's own FEED-SYNC-FLAG doc comment.
- **`web/src/store/feed.test.ts`**: the 3 existing `applyMigrationPushResult` tests updated to the new 3-arg call signature; the one that asserted "clears the WHOLE pending record" was **rewritten, not deleted**, with a comment naming "§1aq CORRECTION" — it now asserts an unsave-pending key and a feedback key both SURVIVE a full success that only pushed one (different) item.
