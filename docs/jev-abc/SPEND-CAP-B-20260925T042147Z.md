### 1.2 How the Jev budget and this budget relate (no double counting)

Verified structurally, not by convention: `decisions/broker-client.ts`'s `callJevViaBroker()` never imports or calls `resolveProvider`/`registry.ts` — it makes an authenticated HTTP request to the `jev-broker` Supabase Edge Function (`web/supabase/functions/jev-broker/index.ts`), which itself calls the external Jev API, not Gemini. `security/jev-broker-auth.ts`'s `reserveJevCall()` reserves against `jev:<owner>:<day>` / `jev:all:<day>` (count-based, one unit per Jev call, per §1p.H(1)). The Gemini decision-fallback (`decisions/gemini-fallback.ts`) reserves against a **third**, disjoint namespace, `jev-gemini:<owner>:<day>` / `jev-gemini:all:<day>` — and, per §0's escape-clause finding, is not reachable in production today, and even if it were, it takes an **injected capability** (`GeminiFallbackProviderCapability`), never a `resolveProvider()`-returned `DigestProvider`, so it does not pass through the hook point this guide designs (see the POLICY note on this).

**The relation, stated plainly for the readiness doc:** Jev's cap answers "how many Jev *calls* may happen" (a distinct external product, priced separately, $0.042/M input tokens per §1p.I, output free) and is entirely orthogonal to this ticket's cap, which answers "how many *dollars* may the shared Gemini key spend." A user could exhaust one without touching the other. They are two different meters on two different pipes; nothing here reads or writes `jev:*` or `jev-gemini:*` keys, and nothing in the Jev/broker path reads or writes the new `company_spend:*` keys this guide introduces.

## 2. Design

### 2.1 Schema (two tables, both authored-only, both matching `usage_counters`' RLS convention exactly)

```sql
-- Adjustable knob 1: the two dollar ceilings. One row per key; the user edits
-- amount_usd directly in the Supabase dashboard's table editor.
create table public.company_spend_caps (
  cap_key    text primary key,                  -- 'global_daily_usd' | 'per_user_daily_usd'
  amount_usd numeric(10,4) not null
    check (amount_usd >= 0 and amount_usd <= 100000),  -- rejects negative AND NaN (see note below)
  updated_at timestamptz not null default now()
);

-- Adjustable knob 2: per-model prices, one row per Gemini model id actually
-- reachable through resolveProvider's system branch.
create table public.company_model_prices (
  model_id                      text primary key,
  input_usd_per_million_tokens  numeric(10,4) not null check (input_usd_per_million_tokens >= 0 and input_usd_per_million_tokens <= 10000),
  output_usd_per_million_tokens numeric(10,4) not null check (output_usd_per_million_tokens >= 0 and output_usd_per_million_tokens <= 10000),
  -- Flat per-image token estimate for vision calls on this model, when it accepts images. NULL for non-vision models.
  vision_tokens_per_image       integer check (vision_tokens_per_image is null or vision_tokens_per_image >= 0),
  source_note                   text not null,   -- e.g. "PROPOSED, unsourced — verify" or "provider-models.ts comment, 2026-09-13"
  updated_at                    timestamptz not null default now()
);

alter table public.company_spend_caps   enable row level security;
alter table public.company_model_prices enable row level security;

-- No anon/authenticated policies — service-role only, same as usage_counters.
revoke all on table public.company_spend_caps   from anon, authenticated;
revoke all on table public.company_model_prices from anon, authenticated;
```

**Why two tables, not one JSONB config table:** caps need one number, prices need three (input, output, optional vision). Plain numeric columns are what the Supabase dashboard's table-editor grid does best — a JSONB value column would make the "user edits it in the dashboard" requirement harder, not easier. This mirrors the plain-column style already used by every other config-shaped table in this repo (`usage_counters`, `private_decisions`) rather than introducing a new convention.

**The NaN gotcha (why the bounds matter, not just a floor of 0):** Postgres's `numeric` type has a real `NaN` value with a defined total order in which **NaN compares as larger than every finite number, including when compared with `>=`**. A bare `check (amount_usd >= 0)` does **not** reject `'NaN'::numeric` (it evaluates true). Bounding the top end (`<= 100000` / `<= 10000`) closes this, because Postgres also defines NaN as failing a `<=` comparison against any finite number. This is a genuine, non-obvious constraint-design detail — flagged so C writes the RED test for it (§3) rather than assuming `>= 0` alone is enough. As defense in depth, the app-side reader (§2.2) must also call `Number.isFinite()` on every value it reads and treat a non-finite value exactly like a missing row (fall through to the documented default), never like a read failure.

### 2.2 Config read path: service-role client + ≤60s cache

No existing TTL-cache precedent exists in this codebase (searched `lib/` for `TTL|ttlMs|cacheMs|CACHE_TTL|memoiz|60_000` — the only hits are a memoize-forever singleton, `llm/client.ts:3`'s `let cached: Anthropic | null`, and unrelated test fixtures). Follow the **constructor-injection** convention `entitlement/resolve.ts` and `usage/counters.ts`'s `SupabaseCounterStore` already established instead: a narrow client interface, a `configuredAdminClient()` helper (same predicate: both `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` present), and `client?: X | null` injection (`undefined` = build the real client, explicit `null` = force "unreachable" for a test).

```ts
// web/src/lib/usage/company-budget.ts (new)
const CONFIG_CACHE_TTL_MS = 60_000;

interface CachedConfig {
  caps: { globalDailyUsd: number; perUserDailyUsd: number };
  prices: Map<string, { inputPerM: number; outputPerM: number; visionTokensPerImage: number | null }>;
  fetchedAtMs: number;
}
let cache: CachedConfig | null = null;

export function resetCompanyBudgetConfigCacheForTests(): void { cache = null; }
```

The read function takes an injectable `now` (matching `CounterStore.increment`'s own convention) so tests can assert "still cached at 59s" / "refetches at 61s" without real timers.

**The critical divergence from `resolveEntitlement`'s nearest-precedent shape:** `resolveEntitlement` does `if (error || !data) return freeFallback` — one branch for both "no row" and "Supabase errored." **This design must not do that.** Three distinct outcomes, three distinct behaviors:

| Outcome | Behavior |
|---|---|
| Table reachable, row present, value finite and in range | Use the stored value. |
| Table reachable, **row absent** (e.g. `per_user_daily_usd` never inserted) | Use the documented hardcoded default, log once at a low level. This is the **only** case the default applies. |
| Client not configured, RPC/query throws, or a present value is non-finite/out of range | **Treat exactly like a reservation-time cap-unreadable failure** (§2.3) — never substitute the default. This is what makes fail-closed real: an outage must not silently revert to "use the fallback number," because that fallback might be more permissive than whatever the operator intentionally set, and the user has no way to tell "the knob says $30" from "nobody could read the knob."

### 2.3 The reserve → call → settle algorithm

**Hook point: `web/src/lib/llm/providers/metered.ts`'s `meterCall`, not the 9 call sites.**

This is the single most important design decision in this guide, and it is not obvious from the spec text alone, so the reasoning is laid out in full:

1. `resolveProvider` must stay **synchronous** — its own doc comment states this explicitly ("eleven call sites use its result without `await`"), so a reservation (an async Supabase round trip) cannot live inside it.
2. Every one of the 9 call sites already funnels through `meterProvider()` (`registry.ts:199`, the single wrap point) → `meterCall()` (`metered.ts:56-109`), which **is** already async (`return async (...args: A): Promise<R> => {...}`) and already intercepts the exact arguments passed to `generateJsonText`/`generateVisionJsonText`/`generateDigest` — including `maxTokens`, `tier`, and the **already-fully-built** `userPrompt` string. This means the pre-call estimate can be computed from the **real** prompt length at the one chokepoint, rather than a hand-maintained ceiling duplicated at each of 9 call sites (which would drift the moment someone changes a `.slice(0, N)` at a call site and forgets the estimator).
3. `meterCall` already knows `ctx.byok` — gate the whole mechanism on `!ctx.byok`, so BYOK is untouched by construction, not by a second check someone could forget.
4. **Actual token usage is not visible at the call sites at all** — `generateJsonText` returns a bare `string`; only the provider adapter (`gemini.ts`) sees `result.usageMetadata` and passes it to `logLlmUsage()` (`llm/usage-log.ts`), which is called from *inside* the provider, several stack frames past where a call site's `try/catch` lives. This is why settlement **cannot** happen at the call sites either, no matter where reservation happens — `logLlmUsage()` is the only place both the usage numbers and (via `currentUsageContext()`, the same `AsyncLocalStorage` scope `meterCall` already sets with `withUsageContext`) the request's identity are simultaneously in scope.

So: **reserve inside `meterCall`, before `fn.apply(...)`; settle inside `logLlmUsage()`**, by attaching the reservation's details to the `UsageCallScope` object that already flows from one to the other via `AsyncLocalStorage`.

```
meterCall (metered.ts), for a non-BYOK ctx:
  1. estimate = estimateCost(method, args, provider.id)      // §2.4
  2. if estimate is null → FAIL CLOSED (price row missing/unreadable for this model — §0 escape clause direction)
  3. reservation = await reserveCompanySpend(ctx.userId, estimate, now)
  4. if !reservation.ok → throw CompanySpendCapRefusedError(reservation.reason)   // caught by the call site's EXISTING try/catch (§2.7)
  5. scope.companyReservation = reservation                   // added to UsageCallScope, carried by AsyncLocalStorage
  6. proceed exactly as today: withUsageContext(scope, () => fn.apply(provider, args))

logLlmUsage (usage-log.ts), unconditionally, at the end (unchanged position):
  1. ctx = currentUsageContext()
  2. if ctx?.companyReservation exists:
       if u.inputTokens and u.outputTokens are both present and finite:
         actualMicroUsd = priceFromCache(u.model, u.inputTokens, u.outputTokens + (u.thinkingTokens ?? 0))
         refund = max(0, reservation.reservedMicroUsd - actualMicroUsd)
         if refund > 0: fire-and-forget increment_usage_counter(reservation.perUserKey, ..., -refund) and (...globalKey, ..., -refund)
       else:
         // usage missing (provider errored before usageMetadata existed) — KEEP the full reservation. Do not refund on an unknown.
```

**Why settle by refunding a *delta* on the same keys, rather than a separate "settle" write:** this reuses `increment_usage_counter` (already supports negative `p_by`, confirmed in §0.ii) with **zero new SQL**. The reservation and its refund are two ordinary atomic increments on the same two keys (`company_spend:<owner>:<day>`, `company_spend:all:<day>`) — no new table, no reservation-id bookkeeping needed in Postgres at all. The `reservationId` only needs to exist in memory (the `AsyncLocalStorage` scope) for the duration of one request, to know *how much to refund*; it never needs to be looked up later.

**Atomicity at the cap boundary under concurrency:** identical to every existing breaker in this codebase — `increment_usage_counter` is one SQL statement (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`), so two concurrent reservations against the same key can never both observe a pre-increment value; the loser sees its own true post-increment value and refuses if it's over cap. **Order matters and must match `reserveJevCall`'s established pattern exactly** (`security/jev-broker-auth.ts:77-99`, itself a Round-3 fix for a real "budget griefing" bug): reserve the **per-user** key first, in isolation; only reserve the **global** key once the per-user reservation is confirmed within cap. A per-user refusal must never touch the shared global counter. This is not new design — it's copying a fix this codebase already had to make once.

**Release of over-reservation:** the settle step above *is* the release mechanism — no separate "release" code path exists or is needed, because "reserve, then refund the unused portion" and "reserve, then release the whole thing on failure" are the same operation with `actualMicroUsd = 0`.

**UTC day rollover:** reuse `endOfUtcDay(now)` and the day-segment-in-key convention verbatim (`usage/counters.ts:97-99,178-183`) — no new logic.

**Micro-dollar rounding:** convert to `Math.ceil(usd * 1_000_000)` at reservation time (round the reservation **up** — never under-reserve) and at settlement's actual-cost computation too (round the recorded actual spend **up** — never let the ledger under-state what was truly spent). Store as `bigint`, matching `usage_counters.value`.

**Behavior when usage is missing at settlement:** covered above — keep the full reservation, never refund. This is the direction explicitly named in the task's required RED-test list ("settle with missing usage keeps the reservation") and matches this codebase's own established fail-safe-toward-the-wallet direction (`breakerTripped()`'s whole existence).

### 2.4 The estimator

Lives in the new module, keyed off which method is being wrapped (the existing `fallbackPath` string `meterProvider` already passes per method: `"digest"`, `"json"`, `"vision"`) and the real args:

- **Input tokens**: `Math.ceil(text.length / charsPerToken)` where `text` = `args.systemPrompt + args.userPrompt` (or, for `generateDigest`, `JSON.stringify({papers, contextHint})` — measured directly from the intercepted args, not a hand-maintained per-call-site ceiling). `charsPerToken` should reuse the exact CJK-aware ratio already established in `decisions/jev-contract.ts` (`LATIN_CHARS_PER_TOKEN = 4`, `CJK_CHARS_PER_TOKEN = 1`, `isCjkHeavy()`) rather than inventing a second heuristic — this is a real, in-repo precedent for exactly this problem, already reasoned through once.
- **Output tokens**: reuse `gemini.ts`'s own `outputCap(modelId, maxTokens)` (exported or re-derived identically) — it already knows which models get `+THINKING_HEADROOM` (4096) and which don't (`GEMINI_NO_THINKING_CONTROL`), so the estimate matches exactly what's sent to the API, not a second guess at it. For `generateDigest`, `maxTokens` isn't passed by the caller — it's a hardcoded `1500` inside `gemini.ts:314`. Define `DIGEST_MAX_OUTPUT_TOKENS = 1500` in the new module with a comment pointing at the literal it must not drift from, and add a `spend-scans.test.ts`-style source-grep test asserting both files' literal `1500` stay equal (that file's own idiom for exactly this kind of "two numbers that must never silently diverge" risk).
- **Vision images**: `args.images.length × (price row's vision_tokens_per_image ?? FAIL — no honest estimate possible for an unconfigured vision model, fail closed)`.
- **Chain attempts**: `tier ? 2 : 4` for the current two Gemini chains (both are 2 small + 2 large). Do not hardcode this — export `GEMINI_API_MODEL_CHAIN`/`chainForTier` (or a thin `chainSizeForTier(tier)` helper) from `gemini.ts` so the estimator reads the real chain length rather than a second copy of "2 or 4" that could drift the day a fifth model is added to the chain.
- **Total reservation** = `sum over each candidate model in the chain of (inputTokens × model.inputPerM + outputCeiling × model.outputPerM) / 1_000_000`, i.e. the worst case if every model in the chain had to be tried. This matches §1.1's finding that `generateJsonText`/`generateDigest` internally loop the whole chain and each attempt bills separately.

**Documented, tested assumption:** the estimator assumes the resolved company-funded provider is always Gemini (`provider.id === "gemini"`), because `resolveSystemProvider()` has no other reachable branch today. If a future round adds a second company-funded provider and this assumption goes stale, the estimator must **fail closed** (refuse to reserve for an unrecognized `provider.id`) rather than silently mis-price it — this is a one-line defensive check, and its own RED test belongs in the required list (§3).

### 2.5 Why a sibling table, not a sibling RPC

`increment_usage_counter` already does everything the reservation/settlement arithmetic needs (§0.ii). The "justified sibling" the spec anticipates is the **two config tables** (§2.1), not a new counter RPC — `usage_counters` itself is reused unchanged, with a new key prefix (`company_spend:`) that is disjoint from every existing prefix (`rate:`, `deep:`, `forced_rebuilds_today:`, `jev:`, `jev-gemini:`).

## 4. Supporting investigation detail

### 4.1 `usage_counters` / `increment_usage_counter` — signature, atomicity, day boundary

`increment_usage_counter(p_key text, p_window_ends_at timestamptz default null, p_by bigint default 1) returns bigint` — one `INSERT ... ON CONFLICT (key) DO UPDATE SET value = c.value + excluded.value ... RETURNING c.value`, single statement, `not security definer` (caller already holds service role). `usage_counters.value bigint not null default 0` — no `CHECK`, so negative values (refunds) are accepted at the DB level without any migration change. Day boundary is entirely in the key string (`utcDaySegment`, `YYYY-MM-DD` from `toISOString().slice(0,10)`), exactly the pattern this design reuses.

### 4.2 Freemium entitlement tables

`profiles` table, columns `plan, trial_started_at, trial_ends_at`, read by `resolveEntitlement()`. Not touched by this feature — the reservation keys on `entitlement.userId` (already resolved upstream by `requireEntitledAiRequest`), never re-derives plan.

### 4.3 `web/src/lib/llm/usage-log.ts`

Already documented in §2.3/2.6 as the settlement hook point. Its existing contract ("never log API keys, prompt/response text... only numeric counts + model ids") is unaffected — settlement only reads `u.inputTokens`/`outputTokens`/`thinkingTokens`/`model`, all already-present fields, and writes nothing new to the log line itself (the counter refund is a separate, silent `increment_usage_counter` call, not a console line).

### 4.4 Existing TTL/cache-pattern search

Grepped `web/src/lib` for `TTL|ttlMs|cacheMs|CACHE_TTL|_TTL_|staleAfter|expiresAt|cachedAt|memoiz|60_000|60000` — 18+ files matched, but every real hit is either (a) a **duration** constant unrelated to a config cache (`feed/freshness.ts`'s staleness *ceiling* for papers, dashboard lease durations in tests), or (b) a memoize-forever singleton with no expiry (`llm/client.ts`, `usage/counters.ts`'s `defaultStore`). **No existing time-limited read-through cache exists in this codebase.** §2.2's design is new, following the nearest *structural* (not TTL) precedent, constructor injection.

### 4.5 Hand-rolled fake Supabase clients — the two distinct conventions in this repo

1. **Full-module `vi.mock`** (`company-spend.test.ts`): mocks `@/lib/supabase/server`'s `createClient` entirely, for routes that check `auth.getUser()`. Not the right pattern here — this feature never touches the *session* client, only the service-role admin client.
2. **Narrow injected interface** (`entitlement/resolve.ts`'s `EntitlementSupabaseClient`, `usage/counters.ts`'s `CounterSupabaseClient`): a hand-written interface exposing only the 1-2 methods actually called (`.from(table).select(cols).eq(...).maybeSingle()` or `.rpc(fn, args)`), passed as an optional constructor/function parameter. **This is the convention to follow** — it's what both of this feature's nearest siblings (`resolve.ts`, `counters.ts`) already do, and it keeps the test from needing to know anything about `@supabase/supabase-js`'s real shape.

### 4.6 UX precedent for "budget spent" — what main does today

- Rate limit (`ai-request.ts`, fails open): `429`, `{error: "AI request limit reached. Try again later."}`, `Retry-After` header, `Cache-Control: no-store`.
- Deep-report breaker (`deep-report-quota.ts`, fails closed): **no HTTP error at all** — `200` with the existing degraded payload (`generateShallowReport`'s output, or `noLlm: true`) plus an additive `quota: QuotaSignal` field; `quotaMessage()` renders plain English, distinguishing `reason: "exhausted"` (a real cap) from `"unavailable"` (an outage — deliberately promises no reset time, since none is known).
- Forced-rebuild breaker (`rebuild-breaker.ts`, fails closed): boolean `false`, caller serves the cached pool unchanged — no client-visible error surface at all.
- `company-spend.ts`'s existing (search-only, unrelated feature) stub: hard `503`, `{error: "Company-funded search is currently unavailable"}`.

This is why §2.7 recommends the *degrade-silently* precedent (deep-report/rebuild-breaker), not the *hard-503* precedent (`company-spend.ts`) — the 503 precedent belongs to a feature (search fan-out) that has never shipped and has no graceful fallback built into its one call site, whereas every one of this ticket's 9 real call sites already has a graceful, shipped, tested fallback. Reusing the fallback that already exists at each site is a more literal reading of "reuse main's existing limit UX" than importing the 503 pattern from an unrelated, never-launched feature would be.

### 4.7 Migration/rollback conventions

- Naming: `<UTC timestamp>_<name>.sql` in `web/supabase/migrations/`, same stem + `_rollback.sql` in `web/supabase/rollback/`.
- Rollback header must contain, verbatim: `NOT A MIGRATION — NEVER APPLIED AUTOMATICALLY` (checked by `rollback-parity.test.ts`'s exact string match — em dash, not a hyphen).
- Rollback body order: reverse dependency order (not relevant here — two independent tables, no FK between them or to anything else).
- `rollback-parity.test.ts` globs `2026092*.sql` — confirmed today's date (2026-09-25) matches; the new migration will be picked up automatically, no test change needed.
- `web/supabase/rollback/README.md` keeps a hand-maintained table (§"The seven files") ranking every rollback by data-loss severity. **C should add an eighth row** classifying `company_spend_caps`/`company_model_prices` as regenerable/low-stakes (they hold no user data, only operator-set numbers; losing them just means "next read falls back to code defaults until someone re-inserts rows") — this is documentation, not a test requirement, but keeps the README accurate rather than silently stale (exactly the kind of staleness FINAL-A-P2 flagged as a defect elsewhere in this campaign).
