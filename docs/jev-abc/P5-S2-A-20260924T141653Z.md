## NEW FINDINGS

**F-A-P5S2-01 (real, reproduced, narrow-scope defect).** `bootstrapInterval` has no validation on `options.iterations`.
- `bootstrapInterval(values, {iterations: 0, confidence: 0.95, seed: 1})` returns `{status:"ok", mean, low: undefined, high: undefined, n}` — the resampling loop never executes (`new Array(0)` is genuinely empty), yet `clampIndex(idx, 0)` computes `Math.min(Math.max(idx,0), 0-1)` = `-1` for any `idx>=0`, and `sampleMeans[-1]` is `undefined` on a plain JS array (negative indices are not special-cased). This violates the function's own declared TypeScript type — `BootstrapResult`'s `"ok"` variant declares `low`/`high` as `number`, never `number|undefined` — and is invisible to the type checker because `web/tsconfig.json` does not set `noUncheckedIndexedAccess` (only `strict: true`); confirmed `npx tsc --noEmit` is clean regardless of this gap.
- `bootstrapInterval(values, {iterations: -1, ...})` (or any negative value) THROWS a native `RangeError: Invalid array length` from `new Array(iterations)` — a genuine uncaught exception, directly contradicting this module's own file-header claim: "Every function here is pure, synchronous, and never throws on malformed input... never a thrown exception."
- Both reproduced by direct execution against the untouched out-of-repo snapshot (not speculation); reproduction script retained in the scratch dir (`own-fixtures.mjs` Fixture 5).
- **Why this does not block VERIFIED_OFFLINE_BOUNDED:** (1) confirmed via check 6 that nothing in production calls this function yet — no real caller exists today that could pass a malformed `iterations`; (2) no PINNED ruling specifies a minimum/valid iteration count — the pinned definitions govern the metric math (nDCG formula, duplicate-count rule, breakdown shape), not `BootstrapOptions`' own input validation; (3) the actual percentile-index math is provably correct for every valid (`>=1`) iteration count (check 3, fixture 6); (4) the fix is a one-line guard mirroring the pattern the function ALREADY uses for `values.length<2` (`if (!Number.isFinite(options.iterations) || options.iterations < 1) return {status:"insufficient", n, reason:"..."}`) — a completeness gap in an otherwise-correct function, not a design flaw.
- **Suggested next step for whichever C/writer next touches this file:** add that guard, plus one regression test for `iterations:0` and one for a negative value, before any real evaluation harness is wired to call `bootstrapInterval`/`perProjectBreakdown` with a caller-supplied (not hardcoded) iteration count.
