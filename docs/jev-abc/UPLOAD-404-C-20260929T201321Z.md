### Point 2 — unavailable upload not offered (§1bi.2)

Mechanism chosen: a tiny GET availability endpoint, NOT a NEXT_PUBLIC flag. Reasoning: both consumer pages (`app/page.tsx`, `app/papers/[id]/page.tsx`) are full Client Components with no server-side data fetching today; `hostedUploadsEnabled()` is a Node-only function (env + path) that cannot run in the browser. Converting either page into a server+client split just for this one flag is a much larger, riskier change than the ruling's "smallest safe way" asks for. A `NEXT_PUBLIC_*` variable is explicitly excluded (build-time inlined, can disagree with the server's own runtime `PEER_UPLOADS_ENABLED`/`PEER_PRIVATE_UPLOAD_DIR` reading). A tiny same-origin GET mirrors the server's own live `hostedUploadsEnabled()` call on every request, matches this codebase's existing pattern of small client hooks backed by a one-shot fetch (`useAuthUser`, `ProfileUploads`'s own upload-list fetch), and needs no new server infrastructure.

Plan:
1. New route `web/src/app/api/papers/upload-availability/route.ts` (a sibling of `upload/`, not nested under `upload/[id]/`, so there is no static/dynamic path ambiguity to reason about) — `GET` returns `{ enabled: hostedUploadsEnabled() }`, `dynamic = "force-dynamic"` (mirrors the existing upload route's own guard against build-time static optimization of an env-dependent answer). No cookies, no owner, no private data — same answer for every caller.
2. New hook `web/src/lib/papers/use-uploads-available.ts`: `useUploadsAvailable(enabled = true): "unknown" | "available" | "unavailable"`, first-paint value always `"unknown"` (server and client agree, no hydration mismatch), one-shot fetch on mount, fails closed (`"unavailable"`) on any error/non-2xx. Plus `uploadsReady(state): boolean` — the one predicate every call site uses; `"unknown"` reads the same as `"unavailable"` (false) on purpose: the ruling asks not to flash a button that then disappears, so nothing renders until the server has actually said yes. The opposite edge (the button appearing a beat after paint, in local dev where it is always enabled) is the accepted, cheaper-to-avoid direction of the trade-off — stated here as the explicit choice, not left silent.
3. Gate `<UploadButton />` on `uploadsReady(useUploadsAvailable())` at both existing call sites: `app/page.tsx` (home) and `app/papers/[id]/page.tsx` (`uploadAction` inside `Reader`, only reached when `!paper.id.startsWith("upload:")` already — the flag is a second, independent condition, not a replacement for that check).
4. Profile's uploads section (`components/profile-uploads.tsx`, rendered by `app/profile/page.tsx`): read fully — it is list/delete-only (`GET /api/papers/upload` + `PrivatePdfStatus`'s delete). It renders NO upload-creation entry point today (no `<UploadButton>` anywhere in that component or its only call site). Confirmed by grep across `src/` for `UploadButton` (3 hits total: its own file, `app/page.tsx`, `app/papers/[id]/page.tsx` — `profile-uploads.tsx` is not among them). Nothing to gate there; no edit planned for this file. Will restate this finding in the final report so the reviewer can re-check it.
