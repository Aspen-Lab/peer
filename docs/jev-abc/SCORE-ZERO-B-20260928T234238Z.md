## Summary

**Root cause: two independent, uncoordinated "deprioritize review/survey
papers" penalties fire on the same item, back to back, and the second one
floors the result at exactly 0 with `Math.max(0, ...)`.** Not one bug in one
place — a compounding interaction between three separate, individually
reasonable-looking commits, none of which reference each other:

1. `web/src/lib/scoring/combine.ts`'s `negativePenalty` (a **harsh, 85%-cut**
   multiplier meant for a reader's own explicit dislikes) is, for every
   request, ALSO fed the system's default "avoid reviews" word list
   (`review`/`survey`/`overview`/`broad survey`/`tutorial`) — not just genuine
   user-declared dislikes. It cuts these 3 items to 15% of their base score
   (`combine.ts:141-145`, fed via `web/src/lib/feed/pipeline.ts:1286-1301`).
2. `web/src/lib/feed/rerank.ts`'s `localScore` — a SEPARATE, purpose-built
   "avoid reviews" penalty (fixed −0.16 plus up to −0.2 more for word
   overlap) — then subtracts AGAIN from the already-85%-cut score, and
   **floors the result at exactly 0** (`rerank.ts:48,69-82`).
3. Until 2026-09-05, step 2 never ran for signed-out/keyless (Tier 0)
   readers at all — it was gated behind `requestedTier >= 1`. A commit that
   day removed that gate for an unrelated, legitimate reason (fixing
   under-diversified results for keyless users) and, as a side effect,
   exposed steps 1+2 stacking for every Tier-0 reader for the first time
   (`pipeline.ts:1971`, commit `f828ac32b`).

Confirmed by real, end-to-end execution against the unmodified shipped code
(Check 2): feeding the exact 3 live items through the real `scoreItems`
produces small but clearly nonzero scores (0.1195 / 0.0686 / 0.0320); feeding
that output through the real `applyTier1Rerank` turns all three into exactly
0 — byte-identical to the live observation.

**Intended or defect:** the POLICY (quietly rank reviews/surveys/tutorials

## Check 1 — path enumeration: every factor/branch from component scores to `combined`, and everything after that can rewrite it

Traced `web/src/lib/scoring/combine.ts`'s `scoreItems` (component scores in →
`combined` out) and then followed `combined`/`score` forward through
`web/src/lib/feed/pipeline.ts`'s `runFeedPipeline` to find anything AFTER
`scoreItems` that touches `.score`/`.scoreBreakdown.combined` before the
response is sent — the reviewer's "Aside" only ruled out two of the factors
inside `combine.ts` itself; the actual cause turned out to be one step later,
in a different file.

### Inside `combine.ts` (`scoreItems`, per item, lines 332-389)

```
base = w.keyword*kw.score + w.tfidf*tp + w.recency*rc + w.source*sr        (355)
combined = clamp01( base * policyPenalty * legacyPenalty * preference.penalty
                          * senseContextPenalty
                     + softBonus + preference.boost )                      (368-373)
```

| factor | range | can it alone reach exactly 0? | where |
|---|---|---|---|
| `kw.score`, `tp`, `rc`, `sr` | each `clamp01`-guarded, `[0,1]` | only if the paper genuinely has no signal on that axis — not this case (all 4 nonzero in the live data) | keyword.ts / combine.ts 333-335 |
| `senseContextPenalty` | `{0.25, 1}` (`kw.fullyDemoted ? 0.25 : 1`) | **no** — floors at 0.25 | combine.ts:368; **A2 already ruled this out** |
| `preference.penalty` | `[0.4, 1]` (`Math.max(1-0.6, 1-min(0.6,loss))`) | **no** — floors at 0.4; also `0` positional items here: signed-out request, empty ledger, short-circuits to exactly `{penalty:1, boost:0}` before this formula even runs | `web/src/lib/preferences/ledger.ts:648-656,732`; **A2 already ruled this out** |
| `policyPenalty` (`negativePenalty`) | `{0.15, 1}` | **no** — fixed 0.15, never 0 — **but A2 never checked this one**, and it IS live for these 3 items (see Check 2) | combine.ts:141-145 |
| `legacyPenalty` (`legacyDislikePenalty`) | `{0.65, 1}` | **no** — fixed 0.65, never 0; inert here (`legacyNegativeTopics` empty for a signed-out request) | combine.ts:147-158 |
| `softBonus` | `>= 0` | n/a (only adds) | combine.ts:354 |
| `preference.boost` | `>= 0` always (`Math.min(POSITIVE_BOOST_MAX, boost) + cappedFacetBoost`, both accumulate from 0 upward, never subtract) | **no** — cannot be negative, so cannot pull the sum below 0 | ledger.ts:661,695,730 |
| `clamp01`'s own floor/NaN guard | `Math.max(0, Math.min(1,n))`, `!Number.isFinite(n) -> 0` | **yes, in theory** (a NaN input, or a genuinely negative pre-clamp sum) | combine.ts:90-93 |

Given every multiplicative factor is individually bounded away from 0 (worst
case `0.25 * 0.4 * 0.15 * 0.65 ≈ 0.0098`, not 0) and `boost`/`softBonus` can
only add, **`combine.ts`'s own `combined` cannot land on exactly 0 while
`kw.score` is nonzero**, except via the NaN branch — which Check 2 rules out
by direct execution (the real pre-rerank values are ordinary finite floats).
So the "exactly 0" has to be introduced somewhere else. Two more branches
inside `combine.ts` are relevant but are KEEP/DROP filters, not
value-zeroing branches — they decide whether an item is shown at all, not
what number it's shown with:

- `if (... && kw.score === 0 && !admittedByNonLiteralChannel) continue;`
  (combine.ts:316) — drops the item from the array entirely. Not this case:
  `kw.score` is 0.4667/0.3267/0.3267, nonzero.
- `.filter((item) => shouldPushReviewPaper(item, profile.seedTexts))`
  (combine.ts:392, `review-policy.ts:111-117`) — drops a review-shaped item
  UNLESS it's a strong direct match to the reader's own declared project
  text (`isDirectProjectOrChallengeMatch`, `review-policy.ts:98-109`,
  threshold `seedOverlapScore >= 0.45`). Since all 3 items survive into the
  response, this filter judged all 3 to be strong direct matches — i.e. the
  code's OWN leniency rule says these are exactly the reviews worth keeping.

### After `combine.ts`: `web/src/lib/feed/pipeline.ts` / `web/src/lib/feed/rerank.ts`

`runFeedPipeline` (pipeline.ts) computes `scored = scorePaperCandidates(...)`
(pipeline.ts:1962, a private wrapper around `scoreItems`, shape at
pipeline.ts:1280-1309) and then, unconditionally:

```
const tier1Ranked = applyTier1Rerank(scored, brief);        // pipeline.ts:1971
```

`applyTier1Rerank` (`rerank.ts:85-102`) calls `localScore` per item
(`rerank.ts:41-83`) and **overwrites** `.score` and `.scoreBreakdown.combined`
with its result (`rerank.ts:88-95`) — this is "anything after [combine.ts]
that rewrites the score." Its own floor:

```
return Math.max(0, Math.min(1,
  item.score + focusBoost + methodBoost + citationBoost + sourceLaneBoost(item, brief)
    - avoid*0.2 - reviewPenalty - methodPenalty ));                 (rerank.ts:69-82)
```

`item.score` here is `combine.ts`'s already-computed `combined` (the small
positive number from the table above). `reviewPenalty` is
`brief.controls.avoidReviews && isReviewLike(item) ? 0.16 : 0` (rerank.ts:48,
`isReviewLike` in `review-policy.ts:88-96`) — a FIXED subtraction, not
proportional to anything. `avoid` (rerank.ts:47) is a 0-1 token-overlap score
against `brief.avoid` (the same 5-word list), subtracted at up to ×0.2. **This
`Math.max(0, ...)` is the only branch in the whole path that can turn a
genuinely nonzero, already-computed score into EXACTLY 0** — it fires whenever
the fixed+overlap subtraction exceeds `item.score` plus whatever boosts
applied, which for a short/generic-vocabulary review-shaped paper (small
`focusBoost`/`methodBoost`/`citationBoost`, since `mustInclude`/`niceToHave`/
`activeQuestions`/`methods` are all empty for this profile) is easy to reach.

Two facts about WHY this branch is live at all for a Tier-0/signed-out
request are the other half of the story (git-confirmed in Check 3):
`applyTier1Rerank` used to be skipped entirely at Tier 0 and was made
unconditional on 2026-09-05, and `negativePenalty`'s 0.15× is being fed the
system's own review-avoidance defaults, not only genuine user dislikes
(pipeline.ts:1287-1289,1300) — so for this exact request `policyPenalty` is
ENTIRELY a policy default, not user feedback.

Checked and ruled out as the cause (by reproduction in Check 2, not just by
reading): `applyRerankOrder` (pipeline.ts:1974, replays a Tier-2 LLM order —
a no-op at Tier 0, empty `aiOrder`), `applyJournalBoost` (pipeline.ts:1978,
adds for a matching preferred journal — `req.venues` is empty here so it
adds nothing), `diversify` (rerank.ts:119-142, reorders only, never touches
`score`/`scoreBreakdown`), and the `excludeIds`/ledger-exclusion filter
(pipeline.ts:2016-2025, a KEEP/DROP filter like the ones above, not a
value-rewrite). None of these needed to be individually exonerated by
inspection alone: the probe in Check 2 reproduces the exact live 0/0/0 using
only `scoreItems` + `applyTier1Rerank`, which is conclusive that nothing
after `applyTier1Rerank` changed these 3 items' value in the real run.

## Check 3 — intended vs. defect, what the reader sees, and when this shipped

**Is "deprioritize reviews" intended?** Yes, clearly and in multiple places:
`FeedControls.avoidReviews`/`avoidBroadSurveys` default `true`
(`profile-compiler.ts:57,59`), feed into `brief.avoid`
(`profile-compiler.ts:180-185`), and are read by name in both penalty sites.
This is a deliberate product policy, not a bug.

**Is "exactly 0, no visible relevance signal, while the card still claims a
match" intended?** No evidence it is. Specifically:

- The two penalty mechanisms do not reference each other. `combine.ts`'s
  `negativePenalty`/`legacyDislikePenalty` (combine.ts:141-158) and
  `rerank.ts`'s `localScore` review handling (rerank.ts:41-83) were both
  added in the **same original commit** (`cd1f65e26`, 2026-05-01,
  "update on searching structure (huge update) and AI infrastructure build
  up") but as two textually separate, non-cross-referencing functions in two
  different files — nothing suggests either author accounted for the other
  applying too.
- `combine.ts`'s own `shouldPushReviewPaper` (combine.ts:392,
  review-policy.ts:111-117) explicitly says a review paper that is a
  *direct, strong match* to the reader's declared project should be KEPT
  rather than dropped — the code already contains a stated leniency
  principle for exactly this shape of paper. The scoring path does not carry
  that same leniency: an item can pass the lenient KEEP filter and still be
  scored as if it had **no relevance at all**, using up one of the day's
  `topN` slots for a reader to see nothing explaining why it's there.
- The interaction was invisible to Tier-0/signed-out readers until
  **2026-09-05** (commit `f828ac32b`, "feat(feed): show each paper's figure,
  and ten different papers", author Aspen Labs). Before that commit,
  `pipeline.ts`'s read-time rerank call was `requestedTier >= 1 ?
  applyTier1Rerank(...) : scored` — Tier 0 requests (every signed-out reader,
  and every signed-in reader without their own model key) never ran
  `rerank.ts`'s review penalty at all, and would have seen the small-but-real
  0.12/0.069/0.032 scores from `combine.ts` alone (low-ranked, but not
  indistinguishable from zero relevance). The commit's own stated purpose was
  unrelated — fixing a genuine under-diversification bug ("a single author
  could take six of the ten slots") for keyless users — and its commit
  message never mentions review scoring; the exposure of this interaction to
  every Tier-0 reader looks like an unintended side effect of a correctly-
  motivated, unrelated change.
- No test anywhere exercises this: `grep` for `negativeTopics` across
  `web/src/lib/scoring` finds it only in `combine.ts`'s own implementation
  and `types.ts`'s type declaration — zero test files. `grep` for
  `review`/`avoid` in `web/src/lib/feed/rerank.test.ts` finds nothing —
  `reviewPenalty`/the `avoid` term are entirely untested there. No test in
  the repo runs `scoreItems` and `applyTier1Rerank` in sequence on the same
  item (only this investigation's now-deleted probe did). A defect that
  neither function's own tests, nor any integration test, could have caught.

**What the reader actually sees (traced through the real rendering code, not
guessed):**

- The card's relevance-dots badge, `<Relevance score={paper.relevanceScore}
  />` (`components/cards/paper-card.tsx:44`), is defined as `if (!score)
  return null;` (`components/ui.tsx:561`) — for `score === 0` it renders
  **nothing at all**, not "0 dots" or "0%". No relevance signal shows next to
  these 3 cards.
- The card's text, `{paper.relevanceReason}` (`paper-card.tsx:69`), still
  reads **"Matches your interest in electrolyte. 1 week ago."** — this text
  is generated once inside `combine.ts` (`generateReason`, combine.ts:387)

- Ranking: both `combine.ts` (line 393) and `rerank.ts` (`applyTier1Rerank`,

- Nothing on the card, anywhere, says "this looks like a review" or "shown
  lower because it's a survey." The demotion is real but silent.

## Check 4 — fix directions, costs, tests, and open policy questions

### Fix direction A — stop feeding the harsh user-dislike multiplier from the soft system policy list (recommended first move)

`pipeline.ts:1300` passes `policyAvoidTopics` (mostly `brief.avoid`'s
review/survey/overview/tutorial defaults, `pipeline.ts:1287-1289`) into
`combine.ts`'s `negativeTopics`, which drives the same 0.15× ("reader
explicitly dislikes this") cut a real dislike gets (combine.ts:141-145).
Stop doing that — feed only genuine user-declared dislikes there, and let
`rerank.ts`'s dedicated, already-purpose-built review penalty be the ONE
place "avoid reviews" is scored.
- **Cost:** small code change (pipeline.ts:1300, and decide what happens to
  the now-unused `policyAvoidTopics` variable), but needs an audit of every
  other `profile.negativeTopics` consumer to confirm nothing else expects the
  policy defaults to arrive there too (currently: only `negativePenalty`
  reads it). Needs new tests (below). Low regression risk to genuine
  user-dislike suppression, which is untouched.
- Still leaves `rerank.ts`'s own `Math.max(0, ...)` able to floor a small
  `combine.ts` score to 0 on its own for a sufficiently review-shaped item —
  smaller magnitude (no more double-cut), but Direction B is still worth
  deciding on.

### Fix direction B — don't let the rerank penalty floor an already-admitted item all the way to invisible

Replace `rerank.ts`'s unconditional `Math.max(0, ...)` (rerank.ts:69) with a
floor that keeps a demoted-but-shown item visibly nonzero — e.g. mirror
SENSE-CONTEXT's own precedent of a named, documented demotion floor
(`SENSE_CONTEXT_DEMOTED_GROUNDING = 0.25`, keyword.ts) rather than 0.
- **Cost:** one new named constant + guard, small. Requires a product
  decision on the floor's value (POLICY, below). No existing test currently
  depends on `localScore` reaching exactly 0 (rerank.test.ts has no
  review/avoid coverage at all), so low regression risk to existing tests —
  but C should still run `rerank.test.ts` after the change to confirm.

### Fix direction C — make the visible reason agree with the visible (or absent) relevance signal

When rerank meaningfully changes an item's score (especially toward 0),
either regenerate `relevanceReason` to say why it's demoted, or stop
reusing the pre-penalty text unchanged (`rerank.ts:96`).
- **Cost:** moderate — needs a copy/UX decision (POLICY), touches
  `rerank.ts` and possibly `generateReason` (combine.ts:19, `./reason`, not
  otherwise investigated here since it's outside this item's scope), needs
  new tests asserting text/score coherence.

### Secondary, optional hardening (not required to fix SCORE-ZERO, noted for completeness)

`topicMatchesItem`'s substring match (combine.ts:119-125, used by
`negativePenalty`/`legacyDislikePenalty`) does naive `.includes()`, not
word-boundary matching — unlike `review-policy.ts`'s own `REVIEW_PATTERNS`
(`\breview\b` etc.). `"review"` is a literal substring of `"preview"`, so any
paper whose abstract merely says "preview of results" would also take the
0.15× hit today, independent of this bug. Not the cause of THESE 3 items
(they are genuinely review-shaped, matched via `\breview\b`/`\boverview\b`
too), but the same mechanism, so worth fixing alongside if Direction A is
taken.

### Tests C must write (regardless of which direction the manager picks)

1. A `combine.ts` + `rerank.ts` **integration test** running the real
   `scoreItems` then the real `applyTier1Rerank` in sequence on a
   review-shaped, on-topic, keyword-matched fixture (this investigation's
   probe, productionized) — locks in that the end-to-end result stays
   coherent (nonzero if genuinely relevant, or demoted-but-still-visible per
   whichever floor the manager picks). No such test exists today.
2. A `negativePenalty`/`profile.negativeTopics` unit test in a scoring test
   file (currently zero coverage anywhere) — locks down which list(s) are
   allowed to reach the harsh 0.15× multiplier.
3. A `rerank.ts` test for `reviewPenalty`/`avoid` (currently zero coverage in
   `rerank.test.ts`) — locks down the review-demotion math on its own.
4. If Direction C: a test asserting `relevanceReason` and
   `relevanceScore`/the `Relevance` badge never disagree (a "matches your
   interest" reason should never co-occur with a fully-hidden badge).

### POLICY — manager decides

- Should a review/survey paper that already passed `shouldPushReviewPaper`'s
  leniency check (a *direct* match to the reader's own declared work) ever be
  allowed to reach a fully-invisible (0, no dots) relevance signal? Or should
  "shown" imply "at least some visible confidence"?
- Is "avoid reviews" meant to be ONE mechanism or deliberately two
  (a hard admission-adjacent cut plus a softer rerank nudge)? If deliberately
  two, what is the combined-effect budget, so they can't silently compound
  past a sane floor again?
- Should `profile.negativeTopics` (the reader's own explicit dislikes) ever
  carry system-policy defaults, or should those stay strictly separate from
  reader-declared signal? (Direction A above assumes "strictly separate.")
  Note `profile.legacyNegativeTopics` already exists as a genuinely-separate,
  reader-only channel (combine.ts:147-158) — the same separation could extend
  to the review-avoidance defaults.
- If Direction B: what floor value? (0.25, matching SENSE-CONTEXT's existing
  precedent? Something else?)
- If Direction C: what should the reason text say for a demoted review — and
  should the `Relevance` badge render *something* (e.g. a single dim dot)
  rather than nothing, so "demoted" and "no signal at all" are visually
  distinguishable to the reader?
