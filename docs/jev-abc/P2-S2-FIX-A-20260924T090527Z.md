## NEW FINDINGS (ranked)

**F-A-P2S2FIX-01 (MEDIUM — robustness gap, not currently reachable in production, no violation of §1p.B(2)'s numeric bound under any shipped configuration).** `runFeedPipeline`'s cache-hit block (`web/src/lib/feed/pipeline.ts:755`, `const retried = await retryFailedSources(...)`) has **no try/catch** around the call. If anything inside `retryFailedSources` throws — most plausibly `claimSourceRetry` (`pipeline.ts:458-489`) if a caller-supplied `CounterStore.increment`/`.read` REJECTS instead of resolving `{ok:false}` — the exception propagates all the way out of `runFeedPipeline`, crashing the entire feed response for a request that otherwise has a perfectly good, servable cached pool sitting right there. This is inconsistent with the same function's own established pattern immediately adjacent to it: the cache-hit write-back three lines later (`cache.set(key, pool)`, `pipeline.ts:767`) IS wrapped in try/catch, as is `cache.get()` inside `getOrBuildCachedPool` — both with an explicit comment that a store outage must degrade, never crash ("a cache outage is a miss, not a feed outage"). Confirmed this cannot fire with either shipped `CounterStore`: `InMemoryCounterStore` never throws (synchronous map mutation, no I/O), and `SupabaseCounterStore.increment`/`.read` both wrap their Supabase calls in their own try/catch and resolve `{value:0, ok:false}` on any error (`counters.ts`, read in full) — so today's two real implementations already satisfy the "never throw" contract the `CounterStore` interface documents. The gap only matters if a future or test-injected `counterStore` (a documented, first-class seam on `FeedPipelineOptions`, explicitly intended for tests to "simulate an outage") doesn't honor that contract. Reproduced directly: my own probe 3 (EVIDENCE #10) passed a `CounterStore` whose `increment`/`read` reject, and `runFeedPipeline` threw instead of returning a degraded-but-truthful response. Suggested minimal fix (not prescriptive): wrap `await retryFailedSources(...)` at `pipeline.ts:755` in the same try/catch pattern already used three lines below it, falling back to the pre-retry `pool` unchanged on any exception — one function, no new test infrastructure, consistent with every other external-effect call in this same code path. Not blocking this checkpoint's verdict: no reachable production configuration triggers it, and it is a narrower, additive concern to F-A-P2S2-01, not a recurrence of it.
