## New shared helper — `web/src/lib/email/send-failure.ts` (+ test)
`classifySendFailure(result)` → `"sender_not_verified" | "send_failed"`, gated on `result.errorCode === "validation_error"` AND the message matching one of three patterns (`/verify a domain/i`, `/domain is not verified/i`, `/testing emails?/i`); anything else (unrelated validation_error, thrown/network error with no errorCode, missing errorCode entirely) falls back to `"send_failed"`, never guessed further. `redactEmailAddresses(text)` replaces every email-like substring with `"[email]"` (tightened to `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` after a first draft over-matched surrounding parentheses/periods in provider prose — caught by its own test). `describeSendFailureForLog(result)` combines `errorCode`/`error` into one redacted log line, used identically by both routes. 11 new tests, all passing in isolation.

## page.tsx — testable mapping functions
`web/src/app/profile/page.tsx` — added two exported pure functions right before `EmailSettingsViewProps`:
- `confirmAddressMessage(status, body)` → `{message, confirmed, pending}`. Keys off status first (429/503/502/400/2xx), then `body.error`/`body.confirmed` only where the status alone is ambiguous (502's two reasons; 2xx's confirmed-vs-pending). Any unmapped status (including a genuine 500) falls back to "Couldn't send the confirmation link. Try again."
- `testSendMessage(status, body)` → `{message, success}`. Keys off `body.reason` alone (`unavailable`/`no_address`/`intent_required`/`rate_limited`/`sender_not_verified`/`send_failed`), falling back to the 2xx-and-`sent`-true success sentence, then to the same generic "Couldn't send the test email. Try again later." for anything unrecognized.

`handleAddressSubmit` and `handleSendTest` rewritten to call these instead of inlining the status/reason checks. This is also what fixes the doubled-period bug ("…first.."): the page no longer ever falls through to `` `Couldn't send: ${data.error}.` `` for a reason it already has a proper sentence for.
**One extra case handled beyond the literal happy path (documented, not silently added):** in `handleAddressSubmit`, if the reader retries confirming the SAME address that was already pending and that retry now fails to send (502), `pendingAddress` is cleared so the "Check `<address>` for a confirmation link…" line stops showing for a send that didn't go out — satisfies (f)'s "must NOT show the line" for the retry case, not just the first-submit case. An unrelated pending address (a different candidate) is left alone.

Tests added in `page.test.tsx`: 10 cases for `confirmAddressMessage` (every named status/reason + one unmapped-status fallback), 9 for `testSendMessage` (every named reason + success with/without an address + one unrecognized-shape fallback). All exact-`toEqual` against the verbatim sentences named in the ruling.
