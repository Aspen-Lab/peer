the binding text exactly rather than the non-binding sketch). A comment
above it in `layout.tsx` records why it lives there (Next's per-navigation
re-keyed Metadata component vs. this app's never-remounted root layout JSX)
and cites the exact mechanism.

**Why this placement is correct, verified against the installed Next docs
and the installed React source (not just B's prior citations — I re-checked
the specific claims myself since round 1 was burned by an unverified
assumption):**
- `web/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/layout.md`:
  "A **root layout**... is used to define the `<html>` and `<body>` tags
  **and other globally shared UI**." This is the documented basis for
  putting arbitrary persistent elements directly in this file's JSX.
- `web/node_modules/next/dist/docs/.../01-metadata/app-icons.md`: confirms
  `app/icon.svg` was purely file-based metadata (`Next.js will evaluate the
  file and automatically add the appropriate tags`) with no
  runtime/client-driven variant — moving the file out of `app/` is a
  complete, clean exit from that system, not a partial one.
- `web/node_modules/react-dom/cjs/react-dom-client.development.js`,
  `isHostHoistableType` (~line 23070): I traced the actual `link` branch
  myself. A `<link>` with a valid string `rel`/`href` and no
  `onLoad`/`onError` hits `switch(props.rel) { case "stylesheet": ...;
  default: return true }` — our `rel="icon"` link is `default: return
  true`, i.e. a plain **Hoistable**: React physically relocates it into
  `<head>` regardless of where in the tree it's written, but — unlike a
  `rel="stylesheet"` + `precedence` **Resource** — never deduplicates it
  against another such link anywhere else in the document. This confirms
  two things at once: (a) our tag can safely be written in `<body>`'s JSX
  next to `<TabIconSync />` and will still end up in `<head>`; (b) *this is
  exactly the same mechanism that let Next's stray re-inserted link coexist
  with ours in round 1* — so the fix cannot rely on React deduping anything;
  it has to rely on there being only one `rel="icon"` link anywhere in the
  render tree, ever, which moving the file out of `app/` guarantees.
  (Correction to B's own writeup: B's Option 2 analogy — "this file already
  relies on that exact behaviour today for its inline boot `<script>`" — is
  imprecise. I checked the `script` branch of the same function: a plain
  inline `dangerouslySetInnerHTML` script with no `async`+`src` is **not**
  Hoistable; it falls through to `break` and renders in ordinary document
  order. The boot script works for an unrelated reason — browsers execute a
  parser-inserted inline `<script>` synchronously in document order, which
  is why it's placed first in `<body>` — not because React hoists it. The
  conclusion Option 2 rests on on (our `<link>` **is** Hoistable) is correct
  and now independently re-verified; the analogy supporting it was not.)

### Deferral decision — tested by execution, removed

Round 1's two-rAF deferral existed because painting synchronously on mount
raced Next's own hydration/re-resolution of the **file-based metadata**
`<link>` (a Server-Component-rendered subtree). That subtree no longer
exists — the link is now plain JSX in `layout.tsx`, rendered once, with no
separate async re-resolution pass, the same as `ThemeSync`
(`components/theme-sync.tsx`) already does synchronously in a plain
`useEffect` with no timing guard at all, safely, today.

I edited `startTabIconSync` to paint synchronously (no rAF) and retested
live against the running dev server, own fronted tab, before touching the

Console checked after this sequence: no React hydration-mismatch warning,
