## GUIDE

### F-A-03A — required source display name

- **Reproduction**: see EVIDENCE §5 block 1. `VocabularyRecord`/`VocabularySourcePolicy` have no name/label field; `app/data-sources/page.tsx:19` renders `<h2 ...>{record.sourceId}</h2>` — the literal machine ID (`openalex`, `thesoz`, `stw`).
- **Classification**: real defect. The allowlist is exactly 3 machine slugs; two of them (`thesoz`, `stw`) are opaque abbreviations a reader cannot recognize. Acceptance-3 requires "visible required attributions" — an attribution a reader cannot parse does not meaningfully satisfy that criterion, even though the literal text of `docs/VOCABULARY-IMPORT-PROCEDURE.md` never uses the words "display name."
- **Cause**: `web/src/lib/vocabulary/catalog.ts:5-9` (`VocabularySourcePolicy` interface, `id`/`licenseName`/`licenseUrl` only) and `web/src/app/data-sources/page.tsx:19` (`{record.sourceId}` used directly as heading text).
- **Direction (recommended)**: add a **closed, compile-time-total map**, not a manifest field:
  ```ts
  // catalog.ts
  export const VOCABULARY_SOURCE_DISPLAY_NAMES = {
    openalex: "OpenAlex",
    thesoz: "TheSoz — Thesaurus for the Social Sciences",
    stw: "STW Thesaurus for Economics",
  } satisfies Record<VocabularySourceId, string>;
  ```
  `page.tsx` then renders `VOCABULARY_SOURCE_DISPLAY_NAMES[record.sourceId]` (indexed access on the closed union `VocabularySourceId`, so it is statically guaranteed defined — no `??` fallback, no branch where a machine ID could ever leak through as a "name"). Reasoning for closed-map over a required manifest field: the source allowlist is a genuinely finite, maintainer-owned set (`ALLOWED_VOCABULARY_SOURCE_IDS` is a 3-item literal tuple that only a code change can extend); a display name is a property of the **organization**, not of any one imported **release**, so it should not be re-typed (and risk drifting) in every future manifest record. `satisfies Record<VocabularySourceId,string>` makes TypeScript itself reject any future 4th source ID added to the allowlist without a matching display name — the guarantee is structural, not a runtime `if (!name)` check that a reviewer could forget.
- **Failing-before test**: in `page.test.tsx`, render `DataSourcesPageContent` with a record `sourceId: "thesoz"`; assert the `<h2` text is **not** the literal string `"thesoz"` and **is** the fixed display string. This fails today (current `h2` content is literally `thesoz`).
- **Callers/tests at risk**: none outside `web/src/lib/vocabulary/` and `web/src/app/data-sources/` (confirmed by repo-wide grep — zero other importers). `profile/page.test.tsx`'s `DataSourcesLink` test only checks the `href`, unaffected.
- **Empty/failure behaviour**: unchanged — an empty manifest still renders zero `<li>` rows and the honest empty-state message; a record the verifier rejects never reaches `DataSourcesPageContent` at all, so it can never display a missing/blank name. No record can reach the page with a `sourceId` outside the 3 allowlisted values (verifier already checks `vocabularySourcePolicy(candidate.sourceId)` first), so the display-name lookup can never actually be asked for an unknown key at runtime either.
- **Blast radius**: zero license/security impact — pure compiled string literals, no manifest field, no verifier change, nothing an unreviewed future manifest edit could spoof.

### F-A-03C — derived mapping provenance lacks release/modification basis

- **Reproduction**: see EVIDENCE §5 block 3. `MappingProvenance` (`schema.ts:7-12`) has exactly `relation`/`targetSourceId`/`targetId`/`evidence`; `verifier.ts:56-63` validates only those four fields.
- **Classification**: **spec ambiguity — needs a manager POLICY ruling, not a clear-cut defect.** The literal text of `docs/VOCABULARY-IMPORT-PROCEDURE.md` step 4 says a mapping must identify only "its relation ... target source/id, and evidence" — it does **not** literally require a release ID or modification flag on the mapping itself. The fresh A's finding is a defensible *reading between the lines* of "cannot identify the release/modification basis required by the import procedure," not a literal textual requirement. B's own assessment: this is a real robustness gap worth closing (a cross-source mapping recorded today could silently become wrong if the *target* source republishes with different term IDs, and nothing currently pins which target release the mapping was verified against), but it is optional-scope for this round because the production manifest stays `{"records":[]}` regardless and no real mapping will exist until an authorized import happens.
- **Cause**: `web/src/lib/vocabulary/schema.ts:7-12` (`MappingProvenance` interface) and `web/src/lib/vocabulary/verifier.ts:56-63` (mapping validation loop) do not require or check a target-release field.
- **Direction (B's recommendation, smallest safe addition)**: add exactly **one** new required field, `targetReleaseId: string` (non-empty, validated the same way `releaseId` already is), to `MappingProvenance`. Do **not** also add a mapping-level `modified` boolean: the enclosing record already carries `modified: boolean` + free-text `description`, and the mapping's own required `evidence` field can already describe a modification in prose; doubling the schema surface before any real import exists risks needing a second revision once real data actually arrives (the same "smallest safe direction" principle the original P1-03 B guide used). If the manager wants a stronger guarantee, the alternative is a second required field `evidence` must literally mention "modified" — B considers that fragile string-matching and does not recommend it.
- **Failing-before test**: in `verifier.test.ts`, add an `it.each` case whose `mappingProvenance` entry has the **current** shape (`relation`/`targetSourceId`/`targetId`/`evidence`, no `targetReleaseId`) and assert it is **rejected**. Run it first against today's code — it will **fail** (the record is currently approved, not rejected), which is the required red state. Then add the schema field + verifier check and rerun — it passes. The existing `fictionalRecord()` helper's one mapping entry must also gain a `targetReleaseId: "TARGET-TEST-RELEASE"` value, or the existing "approves only a complete fictional record" test breaks (expected, intentional tightening — not a test to weaken).
- **Callers/tests at risk**: only `web/src/lib/vocabulary/verifier.test.ts`'s existing fixture (must add the new field) — no other file constructs a `MappingProvenance` literal (grep confirmed).

- **Blast radius**: none beyond tightening; cannot weaken any existing guarantee. Requires a one-sentence wording addition to `docs/VOCABULARY-IMPORT-PROCEDURE.md` step 4 ("...target source/id, the exact release identifier of that target, and evidence...") so the operator procedure and the schema do not silently diverge — **only if the manager approves this finding's fix**; if deferred, the procedure doc needs no change and this finding is explicitly re-listed as open per §0b's exclusion-and-relisting rule rather than silently dropped.
