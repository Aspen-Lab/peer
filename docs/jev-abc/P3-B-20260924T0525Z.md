### §0. Provider broker boundary — Jev key isolation (added per mid-task manager instruction)

**§0.1 Where the raw key lives, and why nothing in `web/` may hold it.** The manager's instruction is a hard architectural constraint, not a preference: `JEV_API_KEY` (name TBD by manager) must exist ONLY as a Supabase server-side secret, never as a Vercel/Next environment variable, never in `web/.env.example` with a real value, never read by any file under `web/src/`. This mirrors the existing, hard-enforced boundary the build guard already polices for the five chat-completion providers (evidence #29) — except stricter: those five keys ARE allowed as local-dev/BYOK conveniences; Jev's key is never allowed in `web/` at all, in any runtime, because there is no BYOK shape for it (F-A-P3-08).

**§0.2 Edge Function secret vs Vault — compared from official docs (evidence #22), recommendation: Edge Function secret.**
- Edge Function secrets (`supabase secrets set`, read via `Deno.env.get`) are never queryable through any SQL/PostgREST surface — the secret literally does not exist anywhere a browser, an `anon`/`authenticated` role, or a misconfigured RLS policy could reach. The only stated caveat is organizational (dashboard "Developer" role can VIEW, not just Owner/Administrator) — an operational/access-control concern outside this campaign's scope, not a code-level risk.
- Vault stores ciphertext in a real table (`vault.secrets`) and decrypts it through a VIEW (`vault.decrypted_secrets`) at SQL query time. The official docs' own words — "you should ensure that you protect access to this view with the appropriate SQL privilege settings **at all times**" — mean Vault's safety is contingent on the operator getting a GRANT/RLS configuration right, forever, on every future migration. This is a strictly larger, self-inflicted attack surface than an Edge Function secret has by construction, for a functional need (an outbound HTTPS call from server code) that has no advantage from living in SQL at all — Vault is the right tool when a secret must be used INSIDE a Postgres function/trigger; Jev's key is used by an outbound `fetch()`, which is exactly what an Edge Function already does natively.
- **Recommendation: Edge Function secret.** This also matches what the Chinese plan (§6) already cited BEFORE the manager's update (`https://supabase.com/docs/guides/functions/secrets`) — so this is a confirmation of the original design intent, not a new direction.

**§0.3 Can the upstream `usage_counters` atomic increment serve as §1j's durable reservation? Yes, for a count-based (or estimated-token-based) cap, with one accepted limitation.**
- `usage_counters`'s `increment_usage_counter` SQL function (evidence #23, already-local, already-unapplied-migration) is a single `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, so the post-increment value it returns is genuinely atomic — two concurrent callers cannot both observe "59 of 60" and both proceed. This is the exact primitive `consumeDeepReport`/`consumeForcedRebuild` already use, live, elsewhere in this codebase (evidence #26), for the identical "reserve the spend before making the call, fail closed if it would exceed the cap" pattern §1j asks for. **Concretely:** before calling the broker, reserve against TWO keys — `jev:<ownerId>:<YYYY-MM-DD>` (per-user) and `jev:all:<YYYY-MM-DD>` (global) — using `getCounterStore().increment(key, endOfUtcDay(now), reserveAmount, now)`, and refuse the call (fail closed, mirroring `breakerTripped`'s existing direction) if either reading is `!ok` OR exceeds its configured cap. This requires ZERO new migration — `usage_counters` already has an arbitrary-`key`/arbitrary-`by` shape.
- **What "settlement" still means and what is genuinely missing:** `reserveAmount` must be chosen BEFORE the real call (since the real `usage.input_tokens` is only known from the response), so it is necessarily an ESTIMATE. Two honest options, both buildable on the existing function with no schema change:
  1. **Count-based (simplest, recommended default):** reserve `1` "call unit" per Jev request, cap = N calls/user/day and M calls/global/day. This is a close cousin of the existing `FORCED_REBUILDS_PER_DAY`/deep-report-count pattern (evidence #27) and needs no token-estimate logic at all. It under-specifies actual dollar cost (a "call" isn't a fixed price since abstract length varies), but bounds the NUMBER of Jev calls precisely, which is what the acceptance items (10, "≤50 shortlist incl. cached") already care about most directly.
  2. **Estimated-token-based (more precise dollar cap, more complex):** reserve `estimatedInputTokens` (a conservative pre-call estimate — e.g. the actual truncated `state` payload's measured length, or the 32k hard ceiling as a worst case) instead of `1`. This makes the daily counter a real (if conservative) dollar-budget proxy. **Accepted limitation, stated rather than hidden (matching this document's own house style for named trade-offs):** since there is no corrective "true-up" call after the real `usage.input_tokens` is known, a conservative estimate means the breaker can trip slightly BEFORE the true dollar spend reaches its nominal cap on a busy day (safe direction — under-admits, never over-admits) — unless a second, signed (positive-or-negative) `increment` call is added after each real response to true the counter up to actual cost, which IS possible with the same function (no schema change) but adds one extra round trip per Jev call and is NOT required for §1j's fail-closed bar to be met. **POLICY question below: which of (1)/(2), and whether to add the true-up call.**
- **Answering the manager's question directly: yes, the existing `usage_counters` atomic increment is sufficient to serve as the durable reservation §1j requires**, for either a count-based or a conservative-estimated-token-based cap, built entirely from code already present in this working tree. What is "still missing" is only the OPTIONAL precision of a post-call true-up, which is a refinement, not a blocker.

**§0.4 What is already integrated vs upstream-only (full inventory in EVIDENCE #28).** Already local and directly reusable with zero porting: `usage/counters.ts` (the reservation primitive itself), `entitlement/resolve.ts`/`types.ts` (to gate Jev on `userId !== null`, mirroring how `deepReportsBudget`/`systemSearchAllowed` are already zeroed for anonymous users). ### §1. `DecisionProvider` interface (`web/src/lib/decisions/`)

A `DecisionProvider` is deliberately NOT a `DigestProvider` and does not live in `web/src/lib/llm/providers/` (that directory is the closed, chat-completion-shaped world `registry.ts` already owns; mixing in a structurally different contract would force every one of the 11 existing `generateJsonText`/`generateDigest` call sites to newly consider a decision-shaped return value). Interface sketch (exact field names for C to finalize in P3-S1):

```ts
interface DecisionRequest {
  paperId: string;               // Peer's own id — Jev never echoes one (JEV CONTRACT)
  title: string;
  abstract: string | null;       // already truncated + the truncation itself logged
  venue?: string;
  intentCard: NormalizedFeedIntent;    // reused as-is from feed/intent.ts
  senseConcepts: SelectedSenseConcept[]; // reused as-is from feed/senses.ts
  questions: DecisionQuestionId[]; // which of the 5 dimensions to ask THIS paper (population/method-outcome gated by intent presence, per spec §4)
}
interface DecisionAnswer {
  questionId: DecisionQuestionId;
  kind: "choice" | "score";       // never "noul" — see §2
  value: string | number;         // choice key, or score value
  confidence: number | null;      // null only possible for a choice whose criteria included insufficient_information and it was NOT chosen... (see §2)
  unknown: boolean;                // the single, local, typed-unknown flag every combiner/consumer reads
}
interface DecisionResult {
  paperId: string;
  answers: DecisionAnswer[];
  usage: { inputTokens: number; latencyMs: number } | null; // null when degraded (F-A-P3-01 empty/failure behavior)
  modelId: string;                 // the ACTUAL echoed model id, for the cache key and cost log
}
interface DecisionProvider {
  decide(request: DecisionRequest): Promise<DecisionResult>;
}
```

### §2. Atomic questions, typed unknowns, strict validation

**Five dimensions, per §3c "Jev" and the Chinese plan §4, gated exactly as specified:** (1) sense match — always asked when `senseConcepts` is non-empty; (2) core-vs-background — always asked; (3) population match — **only** asked when the user's intent specifies a population (never asked otherwise, per spec: "没有说明就不问"); (4) method/outcome match — **only** asked when the user's intent specifies a method/outcome requirement; (5) project-help — always asked (project/challenge is primary per §1c).

**Type choice per dimension, and why (this round's key design correction — see JEV CONTRACT and F-A-P3-01):**
- Dimensions 1-4 → **Choice**, with criteria ALWAYS including an explicit `insufficient_information` (or equivalently named) option alongside the real answers (e.g. sense match: `{matches_target_sense, different_sense, insufficient_information}`). This gives Jev a real, typed escape hatch that satisfies §1d's "explicit unknown category, not low probability interpreted as absent evidence" using the ACTUAL contract (which has no native unknown field) rather than inventing one that doesn't exist. **Belt-and-suspenders:** even when Jev does NOT choose `insufficient_information`, if the returned `confidence` for the chosen option is below a PINNED threshold (default 0.5, per the official confidence-routing guidance's own "don't guess below 0.5" line — tunable per rubric version, never silently changed mid-version), the LOCAL wrapper still marks `unknown: true` regardless of which option was literally chosen. Both paths set the same local `unknown` flag; the combiner treats them identically.
- Dimension 5 (project-help) → **Score** (an ordered "how much does this help" scale, e.g. 3-5 levels from "not helpful" to "directly enables the project"). Score has no clean way to inject a non-ordered "unknown" level without corrupting the ordered/interpolatable scale, so its unknown derivation is confidence-threshold-ONLY (same 0.5 default). This is a real, load-bearing asymmetry between the Choice and Score dimensions — documented here so C does not try to force a fake unknown level into the Score criteria array.
- **Noul is never used** for any of the five dimensions: it returns no `confidence` field at all (JEV CONTRACT), so its ONLY unknown signal would be proximity to 0.5 in the raw probability — strictly weaker than Choice's explicit-option-plus-confidence combination, for a primitive that is otherwise interchangeable with a 2-option Choice.

**Strict schema validation (`jev-contract.ts`, P3-S1), on every response, before anything downstream ever sees it:**
1. Response's `model` field equals the exact pinned id requested (`jev-1.13.0`, never trust an alias echo).
2. `answers` keys are exactly the requested question ids — no missing, no unrecognized extra key silently used.
3. Each Choice answer's `choice` is a member of that question's own declared criteria keys; `probabilities` keys are the same set; `confidence` is finite and in [0,1].
4. Each Score answer's `score` is finite and within `[0, levels.length - 1]`; `legend`/`probabilities` keys match the declared level count; `confidence` finite in [0,1].
5. `usage.input_tokens`/`usage.output_tokens` are non-negative finite numbers (defends against a NaN/garbage cost log, directly satisfying "no arbitrary IDs/NaN scores" from §3b's P3 completion bar).
6. Anything failing 1-5 → the WHOLE response is rejected (not a partial accept — a malformed one answer is grounds to distrust the batch of questions for that paper) and the paper gets `{status: "unavailable"}` locally, never a crash, never a fabricated score.

**Truncation logging.** The 32k-token `state`+longest-question ceiling (JEV CONTRACT, VERIFIED) is the real constraint, not an arbitrary Peer number. `jev-contract.ts`'s request builder truncates `abstract` to a fixed character budget conservatively under that ceiling (leaving room for title/intent/sense text and the largest question's own instructions) and LOGS whenever truncation actually occurred (paper id + original length + truncated length, no abstract TEXT in the log — matches `usage-log.ts`'s existing "never log prompt/response text" contract). A missing abstract is passed as `null`/omitted, never fabricated, and per the brief's explicit instruction, a missing abstract can NEVER by itself justify a `different_sense`/excluded verdict — the combiner (§ below) must treat a paper with no abstract the same as a paper whose Jev call degraded: neutral, not penalized to zero, UNLESS the title alone is genuinely sufficient (a product/rubric judgment call left to the rubric definition, not hardcoded in the combiner).

### §3. Jev adapter behind a server-only flag, fixture-recorded contract, injected fetch

`web/src/lib/decisions/jev-client.ts` (pure, Deno-portable — no `next/*`, no `@/lib/supabase/*` imports) — `callJev(request, {apiKey, fetchImpl, timeoutMs})`, AbortController-based timeout (mirrors the existing provider adapters' pattern), maps every HTTP/network outcome to a typed, non-throwing result:

| Jev-side condition | Local result | Combiner treatment |
|---|---|---|
| 200, valid schema | `ok` | Used |
| 200, schema validation fails (rule 1-6 above) | `invalid_response` | Neutral, logged |
| 401 | `unauthorized` (config/key problem — logged loudly, this is an operator error, not a per-paper transient) | Neutral, logged |
| 422 | `invalid_request` (a Peer-side bug — our OWN request was malformed; should never happen if the builder is correct, but must not crash) | Neutral, logged |
| 429 | `rate_limited` | Neutral; caller may retry with backoff up to a small bounded number of attempts, never unboundedly |
| 529 | `overloaded` | Neutral; same bounded-retry treatment as 429 |
| timeout (AbortController) | `timeout` | Neutral, logged |
| network error / fetch throws | `network_error` | Neutral, logged |
| non-JSON body | `bad_json` | Neutral, logged |

No exception ever escapes `callJev` — every row above is a typed return value. Fixture-recorded tests (P3-S2) use the LITERAL worked example from JEV CONTRACT as the happy-path fixture (proves the validator accepts real Jev output verbatim) plus one synthetic fixture per row above.

### §4. Decision cache

Key = `sha256(canonical({ownerId, intentHash: serializeFeedIntent(intent), paperContentHash, provider: "typesafe", modelVersion: "jev-1.13.0", rubricVersion}))`, no date component (direct fix for F-A-P3-03). `paperContentHash` = hash of exactly what Jev SAW (title + truncated-abstract + venue) — deliberately NOT the same as the paper's canonical identity (`paper-identity.ts`) and NOT the paper's local retrieval score, so a local re-rank never invalidates a decision, but an intent/rubric/model/content change does, each independently (owner/project change → different `ownerId`/`intentHash`; content change, e.g. an abstract becomes available where it was missing → different `paperContentHash`; rubric or model bump → different `rubricVersion`/`modelVersion`). Storage: `PrivateDecisionCache` mirrors `PrivatePaperPoolCache` exactly (owner_id+scope_key upsert/select against a new `private_decisions` table, fail-soft try/catch-to-null/no-op); `InMemoryDecisionCache` for tests and unscoped/anonymous requests (mirrors `ephemeralPaperPoolCache`'s deliberate no-durable-cache-for-unscoped-requests policy — anonymous users never get Jev decisions at all per §0.5/entitlement gating, so this is mostly a test convenience, not a live path).

### §5. Bounded Gemini decision fallback

Reuses the EXISTING `DigestProvider`/`resolveProvider`/`generateJsonText` path (it is a real generative call, unlike Jev) but MUST emit the identical `DecisionAnswer` shape (§1) and go through the SAME `jev-contract.ts` validator's TYPE-LEVEL checks (rules 3-6 above apply verbatim to a Gemini-produced answer too) — this is the direct mechanism for §1d's "must not leak arbitrary generated prose into score fields": whatever Gemini returns is validated exactly as strictly as a real Jev response, and a validation failure degrades the SAME way (`invalid_response`, neutral, never crashes, never free text reaches a score field). Bounded to ≤5 candidates per run (a per-call cap, not a daily budget by itself — see POLICY for whether it additionally needs a daily breaker), default off (own flag, or folded into the same `PEER_JEV_SHADOW` flag — POLICY question), only invoked for candidates the local combiner calls "borderline" (exact definition is a POLICY question below, since a wrong definition risks the brief's explicit STOP condition: "a guard that would drop ordinary valid papers").
