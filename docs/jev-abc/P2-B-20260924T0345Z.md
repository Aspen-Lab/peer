### F-A-P2-02 — Source outage indistinguishable from empty day, cached as complete (acceptance 8-identity, cross-cutting 4g)

1. **Reproduction:** EVIDENCE #6 above — executed against the real `getOrBuildCachedPool`, confirmed.
2. **Classification:** INCORRECT/PRIVATE DATA — for a signed-in user this is a *durable*, Supabase-backed wrong answer that silently persists until the cache key naturally rotates (next local day), not a transient glitch.
3. **Cause, whole producing path:** Two independent defects compound. (a) **Silent-empty adapters**: every one of the five academic adapters (`openalex.ts` `fetchOne` L58–74, `semantic-scholar.ts` `fetchOne` L52–80 via `fetchSemanticScholar` which itself "Returns `null` on a network error (never throws)" by its own doc comment, and by extension arxiv/dblp/pubmed) catches its own errors and returns `[]`, so `Promise.allSettled` in `pipeline.ts` `buildPaperPool()` L129–189 sees `status: "fulfilled"` on a genuine timeout/5xx exactly as it would on a legitimately quiet day; `errors[sourceId]` (L217–220) is populated only when a promise itself *rejects*, which — given every adapter's internal catch — happens essentially never from a source's own fetch failure (it WOULD happen from `withSourceTimeout`'s own timeout rejection, which is a distinct, narrower case — confirmed by reading `opportunities/shared.ts`'s description in `pipeline.ts`'s comments L423–437, "same race, same error string"). (b) **Unconditional caching**: `pool-cache.ts` `getOrBuildCachedPool()` L211–216 calls `cache.set(key, pool)` after every `build()` with no check on `errors`/`fetched` completeness — and structurally *cannot* check it, because `CachedPaperPool` (L42–49) has no field for it at all: only `surface/items/aiOrder/aiReasons/generatedAt/localDate`. For a signed-in user `cache` is `PrivatePaperPoolCache` (`private-paper-cache.ts` L126–173), which durably `upsert`s into Supabase `private_paper_pools`; the next same-day read anywhere (browser reload, scheduled digest re-check, test-digest) hits `getOrBuildCachedPool`'s cache-hit path (L196–200 or L205–206) and **never retries** the failed source, because a cache hit skips `build()` entirely. This is true across all three producing paths identically, since they share one `runFeedPipeline`.
4. **Concrete fix direction:** (a) Give adapters an honest failure signal instead of swallowing it. Two options, pick one consistently: (i) have `fetchOne`/`fetchImpl` re-throw a typed `SourceFetchError` when the underlying `sourceFetch`/`fetchSemanticScholar` call itself failed (network error, non-2xx after retries, timeout) — reserve `[]` strictly for "the API answered 200 with zero results" — and let `Promise.allSettled` in `buildPaperPool` correctly populate `errors[sourceId]`; or (ii) keep adapters returning `[]` but have them also return a companion status object (`{ items: RawItem[]; ok: boolean; reason?: string }`) so a legitimate empty page (`ok: true, items: []`) is distinguishable from a caught failure (`ok: false`). B recommends (i): it is a smaller diff (adapters already have `try { ... } catch { return [] }` blocks — just re-throw instead of swallow in the `catch`, or add a second condition on non-ok HTTP status), and `Promise.allSettled` already exists specifically to catch per-source failures without one bad source killing the pool — the mechanism is already there, only the adapters are lying to it. (b) Add a completeness signal to the cached payload: extend `CachedPaperPool` with `sourceStatus: Partial<Record<SourceId, "ok" | "empty" | "failed">>` (or similar), populated from `buildPaperPool`'s existing `errors`/`fetched` maps, persisted into Supabase like every other field (it's just JSON). (c) Change the cache-write policy in `getOrBuildCachedPool` (or a thin wrapper `buildPaperPool` uses) to a **documented, explicit choice** rather than the current unconditional write — B recommends: cache normally, but tag the entry degraded, and on a degraded cache **hit** for a source that failed, kick off a bounded, best-effort background re-fetch of JUST the failed source(s) (not a full rebuild) the next time that scope is read, replacing `items` from that source only if the retry succeeds, and refreshing `sourceStatus`. A short-TTL-only alternative (don't cache degraded pools at all) is simpler but reintroduces "a page reload rebuilt the feed and re-spent the tokens" — the exact problem the pool cache's own doc comment says it was built to avoid (`pool-cache.ts` L26–32) — so B does not recommend it as the default, only as a fallback if the retry design proves too complex for one C slice.
5. **Failing-before/passing-after tests:** extend `paper-daily-cache.test.ts` (or a new `pool-cache-degraded.test.ts`) with: a fake `PoolCache` + a `build()` that simulates one source's adapter throwing → assert the persisted payload's `sourceStatus.<source> === "failed"` (fails today: no such field exists to assert on) → assert a second same-scope read either (i) retries only the failed source, or (ii) at minimum surfaces the degraded status in `FeedResponse.meta.errors` on a cache hit (today `meta.errors` is `diagnostics?.errors ?? {}` and `diagnostics` is `undefined` on any cache hit — `pipeline.ts` L401 — so a cache-hit response NEVER reports errors even when the cached pool WAS degraded; this alone is worth its own assertion). Also add an adapter-level test per source (`openalex.test.ts` etc. — check which already exist) asserting a network/non-2xx failure now throws/returns `ok:false` rather than a silent `[]`, without breaking the existing "legitimately zero results" test case for that adapter (must keep both cases distinguishable in the test suite itself).
6. **Callers/tests at risk:** every existing adapter test that currently expects `[]` on any thrown/rejected fetch (grep `mockRejectedValue\|mockImplementation.*reject` in `src/lib/sources/*.test.ts` before starting — these tests' *expectations* may need updating from "resolves to `[]`" to "the wrapped call in `buildPaperPool` sees a rejection", not a silent contract change without an item-ID-level regression test per §3a). `Promise.allSettled` callers elsewhere (events/jobs pools use an analogous pattern per the pipeline's own comments — do not change adapters those pools also import without checking `web/src/lib/events` and `web/src/lib/jobs` for reuse of the same source files; academic paper adapters are paper-only so this is likely fine, but B did not exhaustively verify events/jobs don't import `sources/openalex.ts` — C must grep first).

### F-A-P2-05 — No rank-fusion (RRF) module exists (acceptance 7a/7b/7e; 7c/7f already pass; 7d partial)
