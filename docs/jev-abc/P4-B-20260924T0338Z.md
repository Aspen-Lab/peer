This is flagged as a **HIGH RECONCILIATION RISK** file for the manager: if P2-B independently designs an incompatible canonical-key shape before P4-S1 lands, the manager must sequence one to adopt the other's module rather than let `dedup.ts` and `dashboard-ledger` diverge on what "the same paper" means (a paper excluded by the ledger under one key shape but re-admitted by dedupe under a different key shape would reintroduce F-A-P4-01 through the back door).
- **Callers/tests at risk:** none yet (new file); future risk is `dedup.ts` and the new module disagreeing.
- **Data/migration implications:** `dashboard_deliveries` rows are keyed by this canonical key (DESIGN §1) — if the key algorithm ever changes version, old ledger rows keyed under v1 must not silently stop matching newly-fetched v2-keyed candidates for the same real-world paper (alias table, DESIGN §1).
- **Security/expense blast radius:** none; pure function, no I/O.

### F-A-P4-07 — No durable queue/lease/fencing; digest double-send guard is a 6h time window only
- **Reproduction:** confirmed, `dispatch-digests/route.ts:204-216` (`recent` check, no unique constraint), grep for `cooldown|leaseUntil|fencing|pgmq` = zero matches, independently re-confirmed this round.
- **Classification:** CONCURRENCY BUG (INCORRECT DATA in the specific sense of "user gets two emails for one day") — not a full queue-infrastructure gap (that's F-A-P4-09/acceptance 13, a separate, larger, mostly-BLOCKED slice, P4-S8).
- **Cause:** the guard is `SELECT ... WHERE delivered_at >= now() - 6h LIMIT 1` then, if empty, proceed to `INSERT` — a classic read-then-write race: two concurrent cron invocations (e.g., a manual trigger overlapping the scheduled one, or two Vercel Cron regions/retries) can both pass the `SELECT` before either `INSERT`s.
- **Fix direction:** this narrow piece is fully fixable **offline**, independent of the larger queue infrastructure (F-A-P4-09), by adding a DB uniqueness constraint on `(user_id, local_date)` on a small new table or on `briefing_deliveries` itself (add a `local_date text` column derived from `delivered_at` at the user's `digest_timezone`, `unique(user_id, local_date)`), and changing the insert to `on conflict (user_id, local_date) do nothing returning id` — if no row comes back, a duplicate is in flight/already happened, skip email. This is the exact `usage_counters`-style atomic-insert pattern, applied here as "insert-or-detect-duplicate" rather than "insert-or-increment."
- **Failing-before test:** simulate two concurrent `dispatch-digests` GET calls (mocked admin client) for the same user/day; assert exactly one `briefing_deliveries` insert succeeds and exactly one email send is attempted — currently both would proceed (no test exists asserting this today at all, since the admin client isn't mocked in the current test file).
- **Callers/tests at risk:** `dispatch-digests/route.ts` only; `briefing_deliveries` schema change needs a data-shape check against `api/briefings/route.ts`'s `BriefingRow` select (currently selects `id, delivered_at, channel, item_ids, payload, opened_at` — adding a `local_date` column is additive, does not break that select).
- **Empty/failure behavior:** `on conflict do nothing` returning zero rows is the *intended* "someone else already sent it" signal, not an error — must not be logged into `failed[]`.
- **Data/migration implications:** additive column + unique index on an already-applied table (`briefing_deliveries` is real, unlike `private_paper_pools`) — this migration, once authored, is a genuine ALTER on a live-shaped table; flag for the manager that unlike P4-S1's brand-new tables, this migration touches an existing applied table's shape and needs extra review before any future "apply" authorization.
- **Security/expense blast radius:** directly closes a real duplicate-cost bug (double LLM/email send); no new exposure.

### F-A-P4-08 — No "final pool of 30" concept

This is a real, if modest, behavior change to `pipeline.ts` and must be flagged to P2 (shares the file).

- **Callers/tests at risk:** `pipeline.ts` (shared with P2's RRF/channel work — HIGH OVERLAP, flagged again in SLICES).
- **Data/migration implications:** the rollover table (DESIGN §6) stores this 30-item final pool's non-presented remainder; no migration for the 30-cap itself (it's a pure code constant, not persisted state, until rollover needs to persist "what didn't get shown").

### §0 — Canonical paper identity (dependency on P2, `docs/jev-abc/P2-B-*.md` not yet written)
Since P2-B has not published a guide, this specifies the exact interface P4-S1 will author as a **new, standalone module** (`web/src/lib/feed/canonical-identity.ts`) so the manager can point a later P2-C at adopting it (or explicitly rule that P2 needs something incompatible, in which case P4 must be told before P4-S2 ships).

```ts
// Inputs available on every candidate at the point pipeline.ts/dedup.ts see it
// (RawItem, web/src/lib/sources/types.ts:42-68):
interface CanonicalIdentityInput {
  doi?: string;                 // metadata.doi, may be a bare DOI or a doi.org URL
  sourceId: string;             // item.id — stable WITHIN one source/build, not across sources
  source: SourceId;             // "openalex" | "semantic_scholar" | "arxiv" | "dblp" | "pubmed" | "hn" | "web"
  semanticScholarId?: string;   // metadata.semanticScholarId, when the item came via/was matched to S2
  title: string;
  publishedAt: string;          // ISO date string
  authors: string[];
}

interface CanonicalIdentity {
  key: string;       // e.g. "doi:10.1000/xyz" | "s2:abc123" | "title:v1:<8-token-hash>:<year>"
  keyVersion: number; // bump when the algorithm changes shape
  aliases: string[]; // other keys this item is ALSO known by (e.g. a title-key fallback
                      // computed alongside a doi-key primary, so a future doi-less source
                      // hit can still be recognized as the same paper via the alias)
}

function canonicalPaperKey(input: CanonicalIdentityInput): CanonicalIdentity;
```
Priority: normalized DOI (strip `https://doi.org/` prefix, lowercase) is authoritative when present → else `semanticScholarId` → else the existing `dedup.ts` title-token algorithm plus published year (to reduce same-title-different-year collisions dedup.ts doesn't currently guard against, itself part of F-A-P2-01). Always compute and attach the title-based key as an **alias** even when a DOI/S2 key is primary, so a later re-fetch of the same paper from a DOI-less source (e.g. `hn`/`web`) can still match by alias. This directly answers §1g's "alias list/version policy" requirement for `dashboard_deliveries`.

### §1 — Ledger + batch tables
Two new tables, one migration file (`web/supabase/migrations/20260924000000_dashboard_delivery_ledger.sql`, authored-only, same "authored only; not applied by this campaign" header convention as the two existing 2026-09-22 migrations), following `usage_counters.sql`'s pattern of table + its own atomic function together:

```sql
-- dashboard_deliveries: owner-level, PERMANENT (no TTL/expiry column), keyed by
-- canonical paper identity, independent of project/source/device/daily cache.
create table if not exists public.dashboard_deliveries (
  owner_id       uuid not null references auth.users(id) on delete cascade,
  canonical_key  text not null,
  key_version    smallint not null,
  aliases        text[] not null default '{}',
  batch_id       uuid not null references public.dashboard_batches(id) on delete cascade,
  delivered_at   timestamptz not null default now(),
  primary key (owner_id, canonical_key)
);
create index if not exists dashboard_deliveries_owner_idx
  on public.dashboard_deliveries (owner_id);
-- Alias lookups: a GIN index lets "was this paper (under any of its known
-- aliases) ever delivered" be answered without an N-row scan per candidate.
create index if not exists dashboard_deliveries_aliases_idx
  on public.dashboard_deliveries using gin (aliases);

-- dashboard_batches: one row per (owner, local date) — the unit acknowledgment
-- operates on. Server-issued opaque id is the batchId returned in FeedResponse.meta.
create table if not exists public.dashboard_batches (
  id                uuid primary key default gen_random_uuid(),
  owner_id          uuid not null references auth.users(id) on delete cascade,
  local_date        text not null,              -- YYYY-MM-DD in the owner's resolved local day
  canonical_ids     text[] not null,             -- ordered, frozen at "prepared" time
  status            text not null default 'prepared'
                      check (status in ('prepared','presented_pending_ack','acknowledged')),
  intent_version    text,                        -- from NormalizedFeedIntent, for staleness checks
  created_at        timestamptz not null default now(),
  presented_at      timestamptz,
  acknowledged_at   timestamptz,
  unique (owner_id, local_date)
);
alter table public.dashboard_deliveries enable row level security;
alter table public.dashboard_batches enable row level security;
create policy "owners read their dashboard deliveries" on public.dashboard_deliveries
  for select using (auth.uid() = owner_id);
create policy "owners read their dashboard batches" on public.dashboard_batches
  for select using (auth.uid() = owner_id);
-- No insert/update policies for either table: both are server-side/service-role
-- writes only (mirrors briefing_deliveries' "reads allowed; writes are done by
-- ... service role" comment, schema.sql:266-268), reached through the atomic
-- RPC below rather than direct PostgREST writes — this closes the
-- "unforgeable from body/query values" requirement (§1j) for the ack surface.

-- Atomic, idempotent acknowledgment — same shape as increment_usage_counter.
create or replace function public.acknowledge_dashboard_batch(
  p_owner_id uuid,
  p_batch_id uuid
) returns text  -- 'acknowledged' | 'already_acknowledged' | 'not_found' | 'owner_mismatch'
language plpgsql
as $$
declare
  v_status text;
  v_owner  uuid;
  v_ids    text[];
begin
  select status, owner_id, canonical_ids into v_status, v_owner, v_ids
    from public.dashboard_batches where id = p_batch_id for update;
  if not found then return 'not_found'; end if;
  if v_owner <> p_owner_id then return 'owner_mismatch'; end if;
  if v_status = 'acknowledged' then return 'already_acknowledged'; end if;

  insert into public.dashboard_deliveries (owner_id, canonical_key, key_version, batch_id)
  select p_owner_id, unnest(v_ids), 1, p_batch_id
  on conflict (owner_id, canonical_key) do nothing;

  update public.dashboard_batches
    set status = 'acknowledged', acknowledged_at = now()
    where id = p_batch_id;
  return 'acknowledged';
end;
$$;
revoke all on function public.acknowledge_dashboard_batch(uuid, uuid)
  from public, anon, authenticated;
grant execute on function public.acknowledge_dashboard_batch(uuid, uuid) to service_role;
```
Justification: `for update` row lock on the batch makes concurrent double-ack (two devices posting at once) collapse to one winner deterministically; `on conflict (owner_id, canonical_key) do nothing` makes the delivery insert idempotent even if canonical keys somehow overlap with a prior batch (defensive — should not happen given `unique(owner_id, local_date)`, but a retried/duplicate ack call with the same batch id is now provably safe to replay). `key_version` hard-coded to `1` here reflects that P4-S1 ships version 1 of `canonicalPaperKey`; the function signature should accept `p_key_version` once P2 finalizes real dedupe so it isn't hidden inside SQL.

**Why not reuse `private_paper_pools`?** That table stores a *whole day's candidate pool payload* (`payload jsonb`, keyed by `owner_id, scope_key`) — a cache, evicted/rebuilt per day. The ledger is the opposite shape: one narrow row per delivered paper, permanent, queried by "is X in here" not "give me the whole blob." Reusing it would mean parsing/scanning JSONB payloads to answer a membership question that a plain indexed table answers in one lookup — not justified. **Why not extend `briefing_deliveries`?** Confirmed by F-A-P4-04's own analysis: that table is semantically "one dispatch attempt" (inbox history + email dedupe), a different lifecycle from "one paper was shown," and §1g/§7.3 explicitly require the two ledgers stay independent — merging them would make the exact bug F-A-P4-04 describes structural instead of accidental.

### §2 — Repository interface
```ts
// web/src/lib/dashboard/delivery-ledger.ts
export interface DashboardDeliveryLedger {
  /** All canonical keys (including aliases) ever delivered to this owner. */
  listDelivered(ownerId: string): Promise<Set<string>>;
  /** Today's batch row for this owner/local-date, if one already exists. */
  getBatch(ownerId: string, localDate: string): Promise<DashboardBatch | null>;
  /** Creates today's batch row (status 'prepared'); no-op-returns-existing on races. */
  prepareBatch(ownerId: string, localDate: string, canonicalIds: string[], intentVersion?: string): Promise<DashboardBatch>;
  /** Calls acknowledge_dashboard_batch; returns its status string. */
  acknowledgeBatch(ownerId: string, batchId: string): Promise<AckResult>;
}
```
`SupabaseDashboardDeliveryLedger implements DashboardDeliveryLedger` follows `PrivatePaperPoolCache`'s exact shape: a `configuredClient()` factory using `createAdminClient()` (service role — writes must go through the RPC/service role, never the anon client, matching the "no insert/update policies" design above), returns `null`/empty on missing env, every method wraps its Supabase call in `try/catch` degrading to "empty ledger"/"no batch found" rather than throwing (mirrors `PrivatePaperPoolCache.get`'s `catch { return null; }`).

**What does local development without a DB do?** Honestly: nothing persists. `listDelivered` returns an empty `Set` every time (no exclusion applied — the same "an unauthenticated or unscoped paper request must never turn into a durable... entry" no-op precedent `ephemeralPaperPoolCache` already sets, applied here as "an unconfigured environment never blocks a paper as delivered"). `prepareBatch`/`acknowledgeBatch` return a synthetic in-memory-only batch that is **never actually durable** — a local dev restart loses it. This must be stated in the module's top comment exactly as plainly as `private-paper-cache.ts`'s existing comments state its own degrade, so a future reader doesn't mistake "works in my local dev" for "the ledger is durable." A `MemoryDashboardDeliveryLedger implements DashboardDeliveryLedger` test double (not shared, defined per-test-file, matching the `MemoryPoolCache`-in-every-test-file convention already established) is what P4-S1's own tests and P4-S2's pipeline tests use.

### §3 — Anonymous (signed-out) users — POLICY, manager decides
No `owner_id` exists to key a server-side row to. Recommendation: keep the *existing* client-local `recentlyShownIds` mechanism as the anonymous user's entire delivery memory, but **remove its 14-day TTL and 1000-entry cap for the anonymous case specifically** (a signed-in user gets the real server ledger and doesn't need the client list to be permanent; an anonymous user has nothing else). This is explicitly weaker and should say so in the UI/empty-state copy if the manager wants that surfaced (out of scope for this guide to design UI copy) — single device, cleared by clearing browser storage, no cross-device coordination, no account-deletion-triggered cleanup story needed (there's no account). Alternative the manager might prefer instead: leave anonymous behavior exactly as today (14-day TTL) and treat "permanent lifetime exclusion" as a signed-in-only guarantee, with an explicit prompt-to-sign-in for users who want it — cheaper to build, arguably more honest about what a device-only record can promise. **B recommends the TTL-removal option** (closer to the product rule's spirit) but this is a product call, not an engineering one.

### §4 — Acknowledgment flow
`POST /api/feed/ack` (new route, colocated with `/api/feed`), body `{ batchId: string }`.
1. Auth via `createClient()` → `supabase.auth.getUser()` (same pattern as `/api/read`); `401` if absent — no anonymous ack (nothing to ack against).
2. Call `ledger.acknowledgeBatch(user.id, body.batchId)` → the RPC handles owner/membership validation and the transactional multi-row insert server-side (SQL `for update` lock — no read-then-write race in application code).
3. Map RPC result to HTTP: `'acknowledged'` or `'already_acknowledged'` → `200 { ok: true, alreadyAcknowledged: <bool> }` (both are success from the client's point of view — **idempotent and retryable** exactly as required); `'not_found'` → `404`; `'owner_mismatch'` → `403` (never leak whether the batch id exists for a different owner — return the same 403 either way, don't distinguish "not found" from "not yours" in the 403 case... actually distinguish is fine since not_found already covers nonexistent ids and owner_mismatch only fires for a real batch belonging to someone else; still, don't put the other owner's id in the response body).
- **Duplicate ack:** covered by `'already_acknowledged'` → `200`, not an error. Client just proceeds.
- **Two devices:** both POST the same `batchId`; the SQL row lock serializes them, second one gets `'already_acknowledged'`. No double-insert into `dashboard_deliveries` (the `insert ... on conflict do nothing` inside the function is redundant-but-safe here too).
- **Render succeeded but ack lost/offline:** the batch row stays `presented_pending_ack` (never auto-transitions to `acknowledged` without a successful POST). On the client's *next* load for the same local date, `getBatch` finds the existing pending batch (P4-S3's route logic, DESIGN §5) and the client should retry the ack for that SAME batch rather than treat it as new — this is why `prepareBatch` is idempotent per `(owner_id, local_date)` (the `unique` constraint) and the route must always check-before-create.
- **Cross-day late ack:** an ack POST arriving after local midnight for yesterday's `batchId` — the RPC doesn't care about "today," it only checks the batch's own stored state, so it still succeeds and still correctly marks yesterday's papers delivered (this is correct: the user DID see them yesterday; late confirmation shouldn't lose that). The *next* day's batch preparation is a separate, independent `prepareBatch` call keyed to the new local date — it must not be blocked waiting for yesterday's ack, but per DESIGN §5 it also must exclude anything already in `dashboard_deliveries`, so if the late ack lands AFTER today's batch was already prepared without it, today's batch could theoretically include a paper that should have been excluded. This is an accepted, named edge case (network partition spanning midnight) — not silently ignored: record it as a known gap in REMAINING, not fixed in P4's first slices.
- **Server failure (RPC throws / DB down):** route returns `503`; client keeps the batch pending and retries later (same idempotent path) — no special handling needed beyond "don't mark anything acknowledged locally until the server confirms."
- **Next.js route conventions applying here:** per the local docs read above, `POST` route handlers are **never cached by default** (only `GET` can opt into caching) — so this route needs no `export const dynamic = "force-dynamic"` for caching reasons, but the codebase's existing convention on every Supabase-touching route (`test-digest`, `dispatch-digests`) sets it anyway for explicitness/consistency; P4-S4 should match that convention rather than diverge. No special `RouteContext` typing needed (no dynamic segment). `Cache-Control: private, no-store` response header, matching `/api/feed`'s own `CACHE_HEADERS` constant — reuse it.
- **No per-card viewport tracking:** confirmed nowhere in this design — acknowledgment is batch-level only, fired once after the whole array commits to store state (DESIGN §5), never per-card intersection-observer logic.

### §5 — Selection (`pipeline.ts` / `POST /api/feed` / store)
1. In `route.ts`, when `privateScope` (owner) is present: after computing `localDate` (reuse `localCalendarDate`, already imported by `pool-cache.ts`), call `ledger.getBatch(ownerId, localDate)` **before** invoking `runFeedPipeline`.
   - If a batch already exists with status `presented_pending_ack` or `acknowledged`: **do not re-run selection at all** — fetch the pool (cache hit, cheap) and return exactly `batch.canonical_ids`, mapped back to the pool's items, in their originally-frozen order. This is the fix for the same-day-drift gap documented in EVIDENCE above (a `notInterested` click between two same-day loads can no longer change which papers are "today's batch" once it's been presented). Refresh/local reorder (advanceHistory) still only affects **future** unpresented candidates (§6.1 point 5 of the plan), never today's already-frozen batch.
   - If no batch exists yet (`status` absent, i.e., `getBatch` returns `null`): proceed with normal selection (existing `runFeedPipeline`, now also unioning the ledger's `listDelivered()` result into the exclude set at the `pipeline.ts:390-403` filter site — this is the "never trust client `excludeIds` alone" fix), then call `ledger.prepareBatch(ownerId, localDate, canonicalIdsOfReturnedItems, intent.version)` to freeze this call's result as today's batch (status starts `prepared`; route.ts flips it to `presented_pending_ack` — see below — or a single `prepareBatch` call can accept the target status directly, simpler).
2. `runFeedPipeline` itself gets one new, server-only `FeedPipelineOptions` field (never a `FeedRequest` field — matches the `paperCacheScope`/`companySpendCapability` "never parsed from HTTP requests" idiom already documented on the type): `ledgerExclusions?: ReadonlySet<string>` (canonical keys, pre-fetched by `route.ts` via `ledger.listDelivered`). Inside `pipeline.ts`, at the existing exclude-filter site (`pipeline.ts:390-403`), compute `canonicalPaperKey(item)` per candidate in `journalRanked` and additionally filter out anything whose key (or any alias) is in `ledgerExclusions`, unioned with the existing `req.excludeIds` filter (both apply — never replace one with the other, since `excludeIds` also carries the explicit-dismissal/refresh-history signal that isn't part of the permanent ledger).
3. `FeedResponse.meta` gains `batchId?: string` (only set when an owner-scoped batch exists/was created) and `batchStatus?: 'prepared' | 'presented_pending_ack' | 'acknowledged'`.
4. **Scarcity:** unchanged structurally — `fresh.slice(0, topN)` already never pads; the new ledger filter can only shrink the candidate set further, which is consistent with "smaller batch on scarcity, never padded" (already-PASS 16e must stay PASS — a regression test should assert `journalRanked.length < topN` still returns fewer than `topN` items, not backfilled from ledger-excluded candidates).
5. **Archive/past-batch access:** `api/briefings`-style read (a new/extended read of `dashboard_batches` by date, or extending the existing briefings UI) stays available regardless of ledger/ack state — out of scope to build the UI in P4-S1..S7, but the data model already supports it (`dashboard_batches` rows are never deleted by any of the above flows).

### §6 — Rollover
No "final pool of 30" exists today (F-A-P4-08) — minimal version: after computing the (now ledger-filtered) `journalRanked` list, take `finalPool = journalRanked.slice(0, FINAL_POOL_SIZE)` (constant `30`, a new sibling to `MAX_PAPER_POOL_ITEMS`). Store, alongside today's `dashboard_batches` row, the **non-presented remainder** of that final pool (`finalPool` minus the `topN` actually returned) as candidates eligible for tomorrow — a new small table or a JSONB column on `dashboard_batches` (`rollover_candidates jsonb`) is sufficient; a full separate `retrieval_pools`-style table is not justified for a same-shape, same-lifecycle sibling of data already being written in the same transaction as batch preparation. On the *next* local day's `prepareBatch` call (i.e., inside the "no batch exists yet" branch of §5 step 1), before calling `runFeedPipeline`'s normal source fetch, merge yesterday's stored rollover candidates back into the candidate set, **subject to current eligibility** (re-run them through the same date-window/exclusion/current-intent checks live candidates get — do not special-case them as pre-approved) and let them compete in the same RRF/ranking pass as newly-fetched candidates (this is P2's ranking module's job to accept a pre-fetched candidate list alongside freshly-sourced ones — flag as a P2/P4 seam, not something P4-S6 can finish alone if P2's RRF module doesn't exist yet either; P4-S6 can land the rollover *storage and re-eligibility-check* halves offline and stub the "merge into ranking" half behind whatever P2 ships).
Note the "30 minus 10 equals 20" arithmetic in the spec assumes the default 10-card display (`schema.sql:108-109` allows `paper_count in (5,10)`) — P4-S6 must compute the rollover remainder generically as `finalPool.length - actuallyPresentedCount`, not hardcode 20, so a `paper_count = 5` user correctly rolls over up to 25, not a hardcoded 20.
Retention: rollover candidates default to a 30-day storage window (a `created_at`/expiry check on the rollover storage, independent of and never touching `dashboard_deliveries` or `saved_items` — per §7.3, "旧候选只保留竞争资格" is a storage-cost decision, not a data-deletion-of-history decision).

### §7 — Existing client "recently shown" (`store/feed.ts`)
