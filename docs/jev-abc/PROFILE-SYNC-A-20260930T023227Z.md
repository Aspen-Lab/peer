## Check 4 — steady-state debounced push

Read (unchanged by this diff except one added line): the debounced-push
`useEffect` in `web/src/components/profile-sync.tsx` (lines ~456-484) still
diffs `remoteProfilePayload(profile)` against `lastPushedRef.current` and
sends only the diff — this mechanism (`diffPayload`, not exported) is
untouched by this item. The one addition, on the success path, is
`useProfileStore.getState().setLastSynced(singleValueSnapshot(profile))`,
using the SAME `profile` closure variable the payload was just built from —
so `lastSynced` and `lastPushedRef` always advance together, from the same
snapshot, at the same point; they cannot disagree on any field either
covers.

"A device edits a field and reloads before the debounce fires — does the
edit survive?" Traced by reading + confirmed by probe scenario 8 above:
zustand's `persist` middleware writes `profile` to `localStorage`
synchronously on every `set` (no throttle configured — confirmed by reading
the `persist(...)` config, no custom `storage`/throttle option present), so
the edit is on disk immediately regardless of whether the 700 ms debounced
network push ever fires. If it doesn't (reload), `lastSynced` never
advances for that field, so the next reconcile finds it dirty exactly as if
the push had simply not happened yet — proven directly by probe scenario 8.

**Structural limitation, pre-existing, not introduced by this diff, already
repeatedly disclosed elsewhere in this campaign:** this repo has no
`@testing-library/react`-style harness and no test mounts a live React
effect, so the debounce **timer** itself (the literal `setTimeout`/mount-
unmount interaction) cannot be executed in a test — only the pure decision
functions it calls can be, which is what the probe and the shipped tests
both do. Not a gap this diff introduces; stated for completeness.
