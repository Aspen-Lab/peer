### feedIntent report (§1al (b): "report — do NOT change")

**Finding: through Peer's own shipped client code, an invalid `feedIntent` can never reach `PUT /api/profile`.** Traced the only production call site: `web/src/components/profile-sync.tsx`'s `pushRemote` (l.193-205) is the **sole** place any code calls `PUT /api/profile` (confirmed by grepping every `method: "PUT"` site under `web/src`; the only other matches are this route's own tests). Every push — the initial post-sign-in migration push and the steady-state debounced diff push — sends `remoteProfilePayload(profile)` (or a diff of it), and `remoteProfilePayload` (profile-sync.tsx l.133-155) always derives its `feedIntent` field via `profileFeedIntentCard(profile)` (`web/src/lib/feed/intent.ts` l.239-268). That function's LAST step, on both its branches (a pre-existing `profile.feedIntent` card, or one freshly built from the legacy scalar fields), is `normalizePersistedFeedIntent(candidate)` — **the exact same validator** `PUT /api/profile` itself calls (route.ts l.261) to decide whether to 400. `profileFeedIntentCard` returns `undefined` (the key omitted from the payload entirely) whenever that validation fails, rather than passing the malformed value through. So a `feedIntent` the server would reject is, by construction, never attached to an outgoing PUT body in the first place — it disappears from the payload one step earlier instead, silently (no ignored/error surfaced for it, unlike digestEmail — worth noting as a smaller, separate observation, but out of scope for this item since I was told to report only, not change). This holds however a locally-corrupt or hand-edited profile (e.g. a restored backup file, per SIGNIN-MERGE/P4) got into the store: `remoteProfilePayload` re-derives and re-validates on every single push, so there is no path where stale bad state in `useProfileStore` reaches the wire unfiltered. The only way the server's `invalid_feed_intent` 400 actually fires (proven by the existing, untouched test `route.test.ts` l.112 "rejects an invalid supplied card before any upsert") is a request built outside Peer's own UI code — e.g. directly via `curl`/devtools — which is the validator doing its job, not a defect. **No code changed for this finding**, per the instruction.

## A mid-flight fix worth recording: mock typing, not behaviour

After the first full-gate pass, `npx eslint .` came back **153** warnings (baseline 151) — a regression against the "add none" gate. Root cause: to prove the dropped-field tests' security property I needed to read the exact row `stub.upsert` (in `route.test.ts`'s `fromStub` helper) was called with, and TypeScript infers a `vi.fn(() => ({...}))` factory's `.mock.calls` element type from its OWN zero-arg signature, not from how the real code actually calls it — `.mock.calls[0]` came back as the empty tuple `[]`, so casting it to `[Record<string, unknown>]` first tripped `tsc` (3 errors), and my first fix (naming the factory's own params `_row`/`_opts` to document them) traded those 3 `tsc` errors for 2 new `no-unused-vars` warnings instead (this repo's lint config does NOT suppress underscore-prefixed unused params — the 4 pre-existing `_omit`/`_venue`/`_when`/`_none` warnings already show that). Fixed by switching to this codebase's own established convention for exactly this situation — `vi.fn<Signature>(implementation)` with an explicit generic type argument instead of inferring from the implementation — already used and commented on in `web/src/app/api/jobs/dispatch-digests/route.test.ts` l.101-106 for the identical reason. Final state: `tsc` 0 errors, `eslint` 0 errors / 151 warnings (exact baseline), all tests green. No production code was affected by this detour — test-file typing only.
