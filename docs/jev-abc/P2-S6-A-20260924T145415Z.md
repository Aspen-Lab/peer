NEW FINDINGS:
1. (MEDIUM, flag-on only, dormant today) **RRF channel-balance silently
   degrades for id-less bridging records that only cross-link via dedupe's
   weak-link tier — inconsistent with dedupe despite both nominally sharing
   `clusterCanonicalWorks`.**
   Root cause: `toRRFCandidate()` in pipeline.ts (this slice's own new
   function) builds an `RRFCandidate` from only
   `{source, id, doi, title, externalIds}` — it never forwards
   `item.publishedAt`/`item.authors`. `RRFCandidate.year`/`.authors` exist
   specifically to feed the weak-link tier (rrf.ts's own doc comment says so
   explicitly, and C's own rrf.test.ts tests it — but only by hand-building
   `RRFCandidate`s directly, bypassing `toRRFCandidate` entirely). Meanwhile
   `dedup.ts` builds its `WorkMatchInput` with both fields populated
   (`publishedYearOf`/`firstAuthorSurnameOf`, reading the same
   `item.publishedAt`/`item.authors`). Net effect: dedupe can (correctly)
   merge a DOI-less/native-id-less record — `paper-identity.ts`'s own file
   comment names a dblp entry as exactly this case — into the same survivor
   as an ID-bearing copy from another channel, via title+year+author; but
   `fuseRankings`'s OWN clustering, fed only IDs/titles with no year/author
   through this wiring, can never weak-link the same two raw candidates, so
   it computes them as TWO separate fused work-groups. `applyRRFOrder`'s
   alias-based matching back onto the (already-merged) dedupe survivor then
   binds only whichever of those two fused entries it happens to encounter
   first, and silently drops the other's contribution from the reported
   `fusedScore`/`channels`. Reproduced end-to-end through the real
   `runFeedPipeline` (EVIDENCE #6), not just reasoned about. Not a crash, not
   a drop, not a duplicate, not a determinism break — the survivor still
   appears exactly once, deterministically, at a well-defined (if
   under-scored) position. It directly cuts against acceptance 7's
   "channel-balanced," and against C's own explicit (but, on this specific
   point, incorrect) claim that "no NEW limitation [is] introduced by this
   slice beyond what dedupe/channel-comparison already carry" — this IS a
   new limitation, since dedupe supports this fusion and RRF's WIRING (not
   its module — rrf.ts itself is fine) does not. Untested by both
   rrf.test.ts and pipeline.rrf.test.ts today (every pipeline.rrf.test.ts
   fixture is `source: "openalex"`, which always resolves a real
   `openalex:` id-form key, so the weak-link path is never exercised through
   the real wiring in either existing test file).
   Smallest consistent fix: make `toRRFCandidate` mirror `dedup.ts`'s own
   `publishedYearOf`/`firstAuthorSurnameOf` derivation and populate
   `RRFCandidate.year`/`.authors` from `item.publishedAt`/`item.authors[0]`.
   Small, mechanical, inside this slice's own allowed file (pipeline.ts),
   zero risk to the flag-off path (confirmed unreachable when off — see
   PER-CHECK VERDICT 1), directly verifiable with the same probe test that
   caught it.
   Severity: MEDIUM, not HIGH. Dormant today (flag off by default); no
   data-safety, duplication, or determinism impact; narrow candidate class
   (only a candidate with zero shared ID-form key across the channels that
   found it). But it is real, reproducible, and currently undocumented, in
   exactly the property this slice exists to deliver. Recommend fixing
   before or alongside the P5 default-flip, not necessarily before this
   flag-off slice is accepted.

2. (LOW-MEDIUM, flag-on only, dormant today) **RRF provenance (`meta.rrf`)
   is present ONLY on the exact request that triggers a fresh build; it is
   structurally absent — the key is missing, not empty — on every later
   same-day cache-hit read of that identical pool.** This is the exact
   question C's own checkpoint (DESIGN CHOICES 4 / REMAINING) explicitly
   flagged for a fresh reviewer to judge, and I can now answer it with
   direct evidence rather than reasoning about it. Root cause, traced in
   pipeline.ts: the object literal the `build()` callback hands to
   `getOrBuildCachedPool` (the object that actually gets persisted as the
   `CachedPaperPool`) is built from a fixed field list —
   `{surface, items, aiOrder, aiReasons, generatedAt, localDate,
   sourceStatus}` — which never included `rrf` in the first place, and
   `pool-cache.ts`'s own `CachedPaperPool` type has no `rrf` field to put it
   in even if it had been included. On read, `diagnostics = !loaded.cacheHit
   ? built : undefined`, and `meta.rrf` is spread only from
   `diagnostics?.rrf` — so a cache hit has no path to it at all, not even a
   stale/last-build copy. Reproduced directly (EVIDENCE #7): two sequential
   `runFeedPipeline` calls against the same cache/owner/day, flag on — call
   1 has `meta.rrf` populated, call 2 (confirmed cache hit: source-fetch
   call count unchanged, identical served item order) has no `rrf` key at
   all. To C's credit this is not a hidden gap: the same "structurally
   absent, not just undefined-valued" behavior is documented inline at the
   actual spread site in pipeline.ts itself, not only in the checkpoint —
   so this finding confirms and closes an already-flagged open question
   rather than surfacing a missed one. C's design-choice comment calls this "exactly as [fetched/
   beforeDedup/afterDedup] already work" — that's a slight overstatement
   worth correcting: those three fields are ALWAYS present in `meta` with a
   meaningful cache-hit FALLBACK value (`{}` for errors, `pool.items.length`
   for the two counts) — they degrade gracefully, they don't disappear.
   `meta.rrf` instead disappears as a key entirely on a cache hit, which is
   a materially different (weaker) consistency guarantee than the fields C
   compared it to, even though the underlying "diagnostics are build-only"
   spirit is the same and is a reasonable interpretation of "provenance
   rides on item metadata" given `sources/types.ts`/`scoring/types.ts` were
   correctly out of this slice's allowed-file list (C's restraint in not
   widening those files unilaterally was the right call).
   Impact: this is a pure observability/provenance gap — it never affects
   WHICH items are served or in what order (that's baked into `pool.items`
   at build time and served identically regardless of provenance
   visibility) — but it does mean acceptance 6d/"provenance reaches the API
   response" is only PARTIALLY true (true for the 1-in-N requests that
   happen to trigger a fresh build, silently false for the rest), and it
   means any P5 evaluation tooling that samples `meta.rrf` from live traffic
   will see it missing on most reads unless it already knows to only sample
   fresh-build responses.
   Smallest consistent fix (as the brief asks): add an optional `rrf` field
   to `CachedPaperPool` (pool-cache.ts) and include `built.rrf` in the
   object passed to `getOrBuildCachedPool`'s `build()` callback in
   pipeline.ts, then read `pool.rrf` on the response-assembly line instead
   of gating strictly on `diagnostics` — mirroring how `sourceStatus` already
   survives a cache hit today. This is additive and backward-compatible
   (old cached pools simply lack the field, the same pattern this campaign
   already uses for `sourceStatus` on pre-P2-S2 rows) but touches
   pool-cache.ts, which is OUTSIDE P2-S6's allowed-file list — so, like
   finding #1's fix, this is future-slice work, not something to do
   unilaterally inside this checkpoint.
   Severity: LOW-MEDIUM. Dormant today; no correctness/safety impact on
   served items; real impact on provenance completeness and on P5
   evaluation tooling if that tooling is built assuming full coverage.
   Recommend closing before P5's evaluation phase actually depends on
   `meta.rrf` coverage, not necessarily before the flag-off merge.
