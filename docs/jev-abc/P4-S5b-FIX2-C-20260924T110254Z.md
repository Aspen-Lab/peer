DESIGN CHOICES:
1. Root cause (confirmed by A's review + my own code reading): `currentOwnerKey()` (feed.ts:270-272) reads `entitlement?.userId ?? "anonymous"` — it cannot distinguish "confirmed signed out" from "signed in, entitlement not resolved yet", because both states have `entitlement` falsy/null. `useSyncGate` (profile-sync.tsx) is the one already-exported, already-precedented signal for "has the initial auth check settled" — never flips back to false once true, settles quickly (synchronously in effect) for signed-out/no-auth-configured. This fix uses it in TWO places, per the brief's explicit design:
   a. **Primary — web/src/app/page.tsx auto-load effect**: gate on `useSyncGate((s) => s.settled)` the same way `first-run.tsx` already gates its own auth-sensitive effects. Once true, the effect re-fires via its dependency array and loads normally — no separate "resume" logic needed.
   b. **Defense in depth — web/src/store/feed.ts loadFeed**: a new helper (name TBD at implementation time, e.g. `ownerKeyForThisLoad()`) wraps `currentOwnerKey()`: a real (non-"anonymous") owner id is never a guess and is used as-is regardless of `settled` (it can only be non-"anonymous" once `entitlement` actually resolved to a signed-in user, so there is nothing to wait for in that branch). Only when `currentOwnerKey()` fell back to `"anonymous"` AND `!useSyncGate.getState().settled` does this return `null` ("owner unknown for this load") instead of `"anonymous"`. `loadFeed` threads that `string | null` through its 3 real call sites (the MRU touch, the `ownerDeliveredLocal` read, and `papersLane`'s `pendingLocalDelivery` arm): `null` means skip the touch (leave `deliveredLocalByOwner`/`deliveredLocalOwnerOrder` untouched — no `"anonymous"` entry created), read `{}` for exclusions (no device-local ids from any namespace), and arm nothing (`pendingLocalDelivery: null`) even if the response had papers. This satisfies the brief's "if it must proceed... sends NO device-local delivered ids rather than the wrong owner's" — never partially-wrong, never the anonymous bucket's stale/irrelevant content presented as if authoritative.
2. Why gate on `settled` rather than e.g. delaying by a fixed timeout or checking `entitlement !== null` directly in page.tsx: `entitlement` starts `null` and CAN legitimately end up conveying "signed out" as `ANONYMOUS_CLIENT_ENTITLEMENT` (non-null) OR (in this test file's existing convention) tests leave it `null` to mean "signed out" — `entitlement`'s nullness alone is not a reliable "resolved" signal on its own (that ambiguity is exactly this bug). `useSyncGate.settled` is purpose-built for this and already load-bearing elsewhere (`first-run.tsx`), so reusing it is both correct and consistent rather than a new parallel mechanism.
3. Existing test-suite impact: the shared `feed.test.ts` `beforeEach` (166-244) resets `entitlement: null` and relies on that meaning "confirmed signed out" for every test that never signs a user in. Under the fix, `entitlement: null` alone no longer implies "confirmed" — `useSyncGate`'s module state must ALSO read `settled: true` for those pre-existing tests' anonymous-namespace assertions to keep holding. Plan: add `useSyncGate.setState({ settled: true })` to that SAME shared `beforeEach` (default = "auth already resolved", matching what every pre-existing test implicitly assumed) and only override to `settled: false` inside the new tests that specifically exercise the unresolved window. This is an ADDITION to setup, not a rewrite of any existing assertion, so it does not trip the "never delete a test; rewrite an assertion only with a tagged comment" constraint — no existing assertion text changes.
4. Tests that set `entitlement: signedInEntitlement("user-x")` (a real, non-"anonymous" id) are UNAFFECTED by `settled`'s value either way, per point 1b above — confirmed by re-checking each such test's owner id is always non-"anonymous".
