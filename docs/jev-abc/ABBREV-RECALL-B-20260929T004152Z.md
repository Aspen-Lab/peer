## Summary (written first, expanded below)

**The papers are lost at RETRIEVAL, not at scoring.** Every one of the five academic source adapters (`web/src/lib/sources/{openalex,semantic-scholar,arxiv,dblp,pubmed}.ts`) truncates its outgoing search-query list to a small fixed count (`MAX_QUERIES` = 3 for openalex/semantic_scholar/arxiv, 2 for dblp/pubmed), taking only the FIRST `MAX_QUERIES` entries of `brief.generatedQueries` whenever that array is non-empty. `web/src/lib/feed/profile-compiler.ts`'s `projectQueries()` builds that array with the reader's free-text project/challenge phrases FIRST and the Required tag itself (plus tag+phrase combinations) LAST. For a real profile (any non-trivial project text), a Required tag whose own words are not already echoed in that free text — "LCO" is a perfect example, since a reader states it as a separate structured tag, not as prose — never survives the truncation and is **never sent as a search term to any source.** Confirmed live today: for both `topics:["LCO"]` and `topics:["LFP"]` (same project-text fixture, same day), the actual per-source query lists were byte-identical (`fetched: {openalex:35, semantic_scholar:34, arxiv:34, dblp:0, pubmed:20}` for both), because the tag was in position 7 of 10 in `generatedQueries` and every source's cutoff is 2–3. The Required-gate scoring stage (T1–T4, `keyword.ts`/`combine.ts`) is not the cause — it is already tag-inclusive (formulas "licoo2"/"lifepo4" shipped today) and simply never receives a candidate worth admitting. This is a **defect**, confirmed by direct measurement that LiCoO2/"lithium cobalt oxide" papers are not scarce in the date window (28 and 20 hits respectively via direct, keyless OpenAlex search) — and it **pre-dates today's work** (every implicated file was last touched 2026-09-24, five days before any of today's SENSE-CONTEXT/REQUIRED-GATE/LCO-FORMULA/SCORE-ZERO changes).

## 5. Fix directions, costs, tests for C, POLICY list

The shared root cause is the interaction of two things: (a) `profile-compiler.ts`'s `projectQueries` orders `generatedQueries` with project-text phrases before the Required tag(s) and their combinations (§1 Step 2), and (b) all five source adapters independently truncate to the front of whichever array they use, favoring `queries` over `topics` wholesale (§1 Step 3). A fix needs to touch (a) and/or (b); it does not need to touch §1 Steps 4-8 (date window/dedupe/exclusions/gate), which are already correct.

**Direction F — reorder at the merge point (lowest cost, smallest blast radius).** In each adapter's `buildSearchQueries` (or, better, a single shared helper factored out of the five near-identical copies), put `topics` before `queries` when merging, e.g. `const source = [...topics, ...queries]` before dedupe+slice, instead of "prefer one array over the other wholesale." Guarantees every Required tag a query slot up to `MAX_QUERIES`, ahead of project-text phrases, with **zero new outbound HTTP calls** and no change to `MAX_QUERIES` itself.
- *Cost:* for a reader with several Required tags and a tight per-source budget (dblp/pubmed's `MAX_QUERIES=2`), reserving one slot per tag could crowd OUT the project-text-derived queries entirely — which is exactly what currently makes "solid state"/"electrolyte"-style recall work well (the fulltext-paragraph query surfaces papers beyond exact tag matches). Needs measurement across realistic tag counts (1/2/3+) to quantify this trade-off, not assumed.
- *Also consider:* combining every Required tag into ONE query (e.g. `"LCO" OR "LFP"`) to occupy a single reserved slot regardless of tag count — `openalex.ts`'s own `quoteImportantTerms` (136-142) already special-cases an `OR`-bearing search term, suggesting OpenAlex's `search` param already accepts boolean OR; arXiv and PubMed/Entrez both have native OR support in their own query syntax (not verified against these two adapters' current query-building code by this investigation — C must check). If this holds across adapters, the reserved-slot cost stops scaling with tag count.

**Direction B — raise `MAX_QUERIES`.** Increase the per-source cap (e.g., dynamically to `topics.length + 2`) so both the tag queries and the existing project-text queries fit without displacing each other.
- *Cost:* more outbound calls per source per request → more latency (today's fresh build already took ~3.05-3.07s per request; `Promise.allSettled` waits for the slowest) and, for sources with a budgeted/keyed tier (`OPENALEX_API_KEY`, the paid `web` source, etc.), more quota spent per request. `perQuery` (each adapter's per-query result cap) also shrinks as query count grows (`perQuery = ceil(min(limit,50)/searchQueries.length)`, e.g. openalex.ts:38) — more, shallower queries, a real trade-off against fewer, deeper ones.

**Direction D — a dedicated fetch pass for Required tags, separate from project-text discovery.** Always issue at least one query per Required tag (or per tag's canonical form, reusing `expandTerm`'s formula/synonym list from `term-expand.ts` so e.g. "LCO" and "LiCoO2" aren't two separate queries competing for budget) as an ADDITIONAL call on top of today's queries, rather than making tags and project-text phrases share one truncated list at all.
- *Cost:* highest of the three — outbound call count scales with `topics.length` per source per request; needs its own cap and needs the added latency/quota weighed explicitly against the recall guarantee. Architecturally the cleanest separation (retrieval-for-declared-tags vs. retrieval-for-declared-context stop competing for the same budget at all), but touches the widest surface.

**Not recommended:** doing nothing / calling this "expected." §3 directly measured that LCO/LiCoO2 papers are not scarce in-window; §4 shows the mechanism is structural, not a thin-week artifact, and would keep silently zeroing out the real user's own live "LCO" tag indefinitely.

**Tests for C (whichever direction ships):**
1. Unit test on `buildSearchQueries` (or its shared replacement) directly: given a `topics` array and a `queries` array shaped like a real `generatedQueries` output (project phrases first, tag near/at the truncation boundary), assert the RETURNED per-source query list contains a query that literally contains the tag (or one of its `expandTerm` forms) — pure function, no network, fast regression net for the exact defect in §1.
2. Multi-tag test: 3-5 Required tags + a long project text (reuse `BATTERY_PROJECT_TEXT` or similar) — assert every tag still earns at least one query slot (or, if the shipped direction caps at N tags, assert the documented cap explicitly rather than leaving it implicit).
3. Protective/no-regression test: the existing good cases must not get worse — assert "solid state"/"electrolyte"-shaped profiles (tag prominent in the project text) keep at least the same query set they have today (or an equivalent-or-better one).
4. Recall test using this investigation's own real evidence: replay the "LCO"/"LFP" saved OpenAlex candidates from `<scratchpad>/abbrev-recall/oa-1-licoo2.json` and `oa-3-licobaltoxide.json` (28 + 20 hits, real titles/ids) through the FIXED query-generation path and confirm at least some now reach `scoreItems` and qualify — closes the loop from "queries are structurally right" to "real candidates are actually retrieved," distinct from the already-proven-correct T1-T4 gate math (SENSE-CONTEXT-A2/LCO-FORMULA-A).
5. Mutation for the later A: revert the reorder/reservation — the multi-tag test (2) and the unit test (1) must both go red.

**POLICY — manager decides:**
1. Which direction ships (F / B / D / a combination) — a latency-and-outbound-call-count-vs-recall-guarantee trade-off, not a correctness question this investigation can settle alone.
2. If Direction F's OR-combining idea holds up under C's per-adapter check, whether to use it (one slot for all tags, unlimited tag count) versus a simpler "one slot per tag up to a cap" reservation.
3. Whether to also raise `MAX_QUERIES` (Direction B) alongside F/D to preserve today's project-text-driven discovery breadth, accepting the latency/quota cost, or accept some reduction in that breadth as the price of guaranteeing tag recall.

The manager may weigh cost/blast-radius reasons to scope it narrower anyway.
