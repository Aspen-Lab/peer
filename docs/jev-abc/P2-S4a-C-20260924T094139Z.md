## DESIGN CHOICES

- **Flags.** `PEER_CHANNEL_OPENALEX_SEMANTIC`, `PEER_CHANNEL_OPENALEX_TOPIC`, read directly via `process.env.<NAME>?.trim().toLowerCase() === "on"` inline in `pipeline.ts` (mirrors `dashboardLedgerEnabled()`'s exact semantics but not its file, since a new flag file isn't in my allowed list). Never added to `FeedRequest`/`ScoringProfile` — the only way a value can reach these flags is the server process's own env, which is what makes "request body flags cannot enable a channel" true by construction, not by a runtime check that could have a bug. `channels.test.ts`'s "no field on a FeedRequest body can enable either channel" case proves this by casting an object with invented flag-shaped fields through `unknown` and confirming the sentinel adapters still never fire.
- **Semantic query text.** Built in `pipeline.ts` from the compiled brief, project-first (`brief.project`, then `brief.challenge`, then `brief.coreTopics.join(" ")`, then `brief.generatedQueries.join(" ")`, filtered for blanks and joined with `". "`). Truncation to 2,000 chars happens deterministically INSIDE the adapter (`.slice(0, 2000)`, front-anchored), not in the caller, so the adapter's own contract (`truncateSemanticQuery`) is unit-testable in isolation from whatever `pipeline.ts` happens to feed it, and so "project text survives truncation" is true by construction (it's always first in the joined string).
- **Topic channel / `topicIds` source.** The adapter accepts `topicIds: string[]` and is fully built, fixture-tested, and wired behind its flag. Confirmed by reading `profile-compiler.ts`/`senses.ts` in full that NO OpenAlex topic id exists anywhere upstream today (`SearchBrief` has only free-text `coreTopics`; `SelectedSenseConcept` ids are Peer-authored local slugs, not OpenAlex `T`-ids — using one as a topic id would silently mis-filter, not genuinely explore a topic). Per this slice's own explicit STOP condition ("a topic-id source that would require inventing ids") — and independent of that, `profile-compiler.ts`/`feed/types.ts` are outside my allowed-file list regardless — `pipeline.ts` wires the channel behind its flag but passes an always-empty `topicIds` array, with an inline comment explaining why. The channel is flag-gated AND structurally inert (zero fetches even when flagged ON) until a real id source exists. This is a deliberate, disclosed, tested gap (see `channels.test.ts`'s "stays structurally inert" case), not a hidden shortfall.
- **`OPENALEX_API_KEY` header.** `sourceFetch` (`_fetch.ts`) cannot carry headers and `_fetch.ts` is outside the allowed-file list (see CONTRACT ASSUMPTIONS). Resolution shipped: a small file-local helper pair (`openAlexAuthHeaders` + `openAlexFetch`) in each of the 4 files that make an OpenAlex HTTP call (`openalex.ts`, `affiliation/openalex.ts`, `openalex-semantic.ts`, `openalex-topic.ts`). In the two PRE-EXISTING files, `openAlexFetch` delegates to the untouched `sourceFetch` whenever no key is configured — so the no-key path (every deployment today) is byte-identical to before this slice, including `sourceFetch`'s 429 retry-with-backoff — and only calls `fetch` directly (dropping that one retry nicety) on the opt-in, nothing-uses-it-yet keyed path. In the two NEW files there is no "before" behavior to preserve, so they always call `fetch` directly with a conditional header, keeping a single code path. This is disclosed duplication (4 small near-identical helper pairs) rather than a shared module or a `_fetch.ts` edit — the same accepted pattern this codebase already uses for its DOI-regex helper (§1p.B(4): "swapping the 6 existing call sites is a separate later cleanup slice, listed open"). A future slice that gets `_fetch.ts` added to its allowed-file list could fold all 4 copies into one additive `headers` option on `sourceFetch` and delete the duplication — flagged for the manager/fresh A, not done here.
- **No test file for `affiliation/openalex.ts`.** The allowed-file list granted this file "(same header only)" without "(+ test)", unlike the two brand-new adapters. Since no test file exists for this module today and creating one wasn't explicitly authorized, its 3 header call sites ship untested by a dedicated test — a real, disclosed coverage gap (the change itself mirrors the already-tested `openalex.ts` pattern exactly, so risk is low, but "low risk" is not "tested").
