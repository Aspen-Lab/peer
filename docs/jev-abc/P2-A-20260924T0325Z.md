F-A-P2-01 [INCORRECT DATA — acceptance 6b, 6a, 6d] Dedupe can silently merge two distinct papers into one, with no DOI check and no year/author check.
`web/src/lib/feed/dedup.ts` `dedupKey()` (L13–22) builds its merge key from ONLY the paper title: lowercase, strip punctuation, take the first 8 alphabetic tokens ≥3 chars, sort them, join. `dedupItems()` (L24–42) then keeps exactly one `RawItem` per key, picking the higher-`SOURCE_PRIORITY` one on a collision. `item.metadata.doi` (present on `RawItem`, `sources/types.ts` L61–71) is never read. Publication year (`publishedAt`) and `authors` are never read. Reproduction: two distinct papers — e.g. "Graph Neural Networks for Protein Structure Prediction" (2019, author A) and "Graph Neural Networks for Protein Structure Prediction in Sparse Data" truncated/reformatted by a source to the same first-8-token set (2024, author B) — hash to the same key and the 2019/author-A paper silently disappears from the pool; the surviving card shows one paper's title/URL/authors while the discarded paper's distinct identity is gone with no trace. This is the acceptance-6b failure mode by name ("same-title distinct works are NOT merged... checks year/authors"), it doubles as 6a (no DOI/source-ID pass exists at all — title-key dedup is the ONLY pass), and it also produces the 6d failure below since the discarded item's source/channel/rank is not preserved anywhere, merged or otherwise — it is simply gone. Zero test coverage exists for this module (no `dedup.test.ts` anywhere in the repo), so this defect is not caught by any current gate.

F-A-P2-02 [INCORRECT/PRIVATE DATA — acceptance 8-identity, cross-cutting to 4g] A source outage is indistinguishable from "no results today," and the resulting incomplete pool is durably cached as if complete — for signed-in users, in Supabase.
Every per-source adapter (`openalex.ts` `fetchOne` L58–74, `semantic-scholar.ts` `fetchOne` L60–79, and the arxiv/dblp/pubmed equivalents) catches its own network/HTTP errors internally and returns `[]`; none of them throw. In `pipeline.ts` `buildPaperPool()` (L129–221), `Promise.allSettled` therefore sees every source as `status: "fulfilled"` with an empty array on a real outage — `errors[sourceId]` (L217–220) is populated only on the rare case a promise itself rejects, which none of the adapters do. The built pool — indistinguishable from a legitimately empty day for that source — is then handed to `getOrBuildCachedPool` (`pool-cache.ts` L184–227), which unconditionally calls `cache.set(key, pool)` after every build (L213–214) with no check for degraded/partial fetch. For an authenticated user, `cache` is `PrivatePaperPoolCache` (`private-paper-cache.ts` L126–173), which durably `upsert`s the payload into Supabase `private_paper_pools`; the next read that day reuses it via `getOrBuildCachedPool`'s cache-hit path with no retry. Reproduction (construction, not live): stub `bySourceId.semantic_scholar.fetch` to reject/return `[]` as the real adapter would on a timeout, run `runFeedPipeline` twice same day with a `PrivatePaperPoolCache`-shaped scope — the second call is a cache hit that never re-tries the failed source, and nothing in the response (`meta.errors`) distinguishes "S2 had nothing today" from "S2 was down when we built this." This is exactly the risk the spec names explicitly (§3c "Partial success carries source status; outage not cached as valid all-day empty result") and the manager explicitly asked to check.
