## NEW FINDINGS (ranked)

**F-A-P2S2-01 (HIGH — behavior contradicts binding ruling §1p.B(2), under concurrency; not a data-correctness or privacy defect).** A degraded cache hit's self-heal retry (`pipeline.ts`'s `retryFailedSources`, called from `runFeedPipeline` at the `if (loaded.cacheHit)` block) has no single-flight/coalescing protection across concurrent requests for the same owner-scope+cache-key, unlike `getOrBuildCachedPool`'s build path (which correctly uses `pool-cache.ts`'s `inFlightByCache` `WeakMap`). Measured directly (EVIDENCE #13/#14, two independent runs, with and without simulated network latency): N concurrent retry-eligible requests trigger N independent fetches to the same already-failed source, not the 1 the ruling requires ("at most once per 30 minutes per owner-scope+source"). Root cause: each concurrent `runFeedPipeline` call does its own `cache.get()`, evaluates `isEligibleForRetry` against that independently-read (and, under concurrency, equally stale) snapshot, and independently fires `bySourceId[sourceId].fetch(...)` — a classic check-then-act race with no lock. Confirmed this is not just a test-double artifact: the production `PrivatePaperPoolCache.set()` is a plain Supabase `.upsert()` with no optimistic-concurrency/version check (EVIDENCE #15), so the same race applies in the real backend. A secondary effect: because the stored `retryCount` is overwritten (not incremented atomically) by whichever concurrent writer lands last, the daily cap of 3 retries can also be silently exceeded in aggregate across repeated concurrent bursts without the stored bookkeeping ever reflecting it. Realistic trigger: a signed-in user with more than one open tab/device, or an ordinary client-side request retry on a flaky connection, hitting the feed at/after the 30-minute mark. Scope is bounded to the signed-in private-cache path only — confirmed Tier 0/anonymous cannot trigger this at all (check 6, `ephemeralPaperPoolCache.get()` always returns null). Suggested fix direction (not prescriptive — C's call): wrap the retry decision+fetch+write-back in a per-process single-flight keyed by `(cache identity, key)`, reusing `pool-cache.ts`'s existing `inFlightByCache` pattern (e.g., export a small helper from `pool-cache.ts` that both the build path and a new retry path can share) rather than inventing a second, divergent mechanism — consistent with the B guide's own STOP condition ("do not invent a second limiter").

No other new findings. Every other measured behavior (adapter throw/resolve contract, all-failed-not-cached, meta.errors truthfulness on both build and cache-hit, sequential-access retry bounds, frozen-batch isolation, backward compatibility, Tier 0/anonymous isolation, events/jobs isolation) is independently confirmed correct by direct code reading, my own fresh probes, and passing gates.
