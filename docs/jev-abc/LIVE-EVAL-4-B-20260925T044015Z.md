## Finding C1 — the live-run pattern, and the sibling design for this evaluation

**Evidence.** The existing live-call pattern is three independent layers, all needed together:

1. **Exact-name allow-list + selector**, `web/vitest.env-allowlist.ts:18-43`. Exports
   `VITEST_INJECTED_ENV_NAMES = ["GOOGLE_VERTEX_PROJECT", "GOOGLE_VERTEX_LOCATION",
   "GOOGLE_APPLICATION_CREDENTIALS"]` and `selectLiveEventsEnv(source)`, which copies ONLY those
   exact keys out of whatever `loadEnv()` read from `.env.local`. The file's own header comment
   says this is deliberately "the only environment variables `vitest.config.ts` may copy" and
   warns "do not replace this with a prefix."
2. **A dedicated vitest config**, `web/vitest.live-events.config.ts:1-18`. Spreads
   `sharedVitestConfig` (so it keeps the same `resolve.alias`/`setupFiles`), then overrides
   `test.include` to ONE file (`["src/lib/events/benchmark.test.ts"]`, not a glob) and
   `test.env` to `{ ...selectLiveEventsEnv(loadEnv(...)), PEER_RUN_LIVE_EVENTS_BENCHMARK: "1" }`.
   The opt-in literal is set BY THE CONFIG FILE, not by the person running it — `npx vitest run
   --config vitest.live-events.config.ts` alone is sufficient.
3. **A gate function inside the test**, `web/src/lib/events/benchmark-live-gate.ts:1-7`.
   `canRunLiveEventsBenchmark()` requires the opt-in literal `"1"` AND a live project var
   (`GOOGLE_VERTEX_PROJECT`) — belt and suspenders, but note the opt-in literal is the load-bearing
   half; see Finding C1d below for why the second half doesn't carry over unchanged.
   `benchmark.test.ts:54-58` combines this with its own search-provider check into
   `hasLiveSearchPath`, and (elsewhere in that file, not re-read in full — outside this item's
   file list) presumably wraps its live assertions in `it.skipIf(!hasLiveSearchPath)` or
   equivalent, so under the DEFAULT config the test file is still collected and its top-level
   module code (reading `.local-data/profile.json`, computing booleans) still runs, but no
   network call happens — it skips.

A fourth, independent layer sits beside these three: `web/vitest.setup.ts:32-44`. Every config
that uses `sharedVitestConfig.test.setupFiles` (i.e. every config in this repo) runs
`deleteSpendableKeys()` before every test, unconditionally stripping `GOOGLE_API_KEY` and
`TAVILY_API_KEY` from `process.env`. Its own comment explains why this exists ALONGSIDE the
allow-list: it "also covers a developer shell that exported one, a CI runner with it in the
environment." Critically, this list is DISJOINT from `VITEST_INJECTED_ENV_NAMES` — the three
Vertex names are never deleted, so there is no collision between "the live config injects X"
and "the shared setup file deletes X."

**Finding C1a — why the second half of the existing gate does not carry over.** The Vertex
benchmark's gate checks BOTH the opt-in literal AND `GOOGLE_VERTEX_PROJECT`, because Vertex
genuinely cannot make any call without project config — requiring it is "free" extra safety.
S2 and OpenAlex are different: both `web/src/lib/sources/semantic-scholar-client.ts:26-29`
(unkeyed path, `UNKEYED_MIN_INTERVAL_MS`) and `web/src/lib/sources/openalex.ts:28-31`
(`openAlexAuthHeaders()` returns `undefined` when no key, and the call proceeds keyless) show
that BOTH providers serve a real, live, billable-on-OpenAlex's-side request with **zero**
credentials configured. A gate that also required a credential present would be wrong here — it
would make the runner falsely report "blocked" on a machine that has decided to test keyless.
**Design decision: the new gate is the opt-in literal alone.** Credential presence is reported
in the run's output (§1u.2 requires this) but does not gate whether a call is attempted, only
whether it is authenticated.

**Finding C1b — why this repo's default suite is "provider-silent" for S2/OpenAlex is a
different mechanism than for Gemini, and what that means for the second layer.** `GOOGLE_API_KEY`
is dangerous ambient-only because `resolveProvider()` is a registry OTHER, unrelated code calls
implicitly — any test that reaches it unmocked goes live the moment the key is present, key or
no `NODE_ENV=test` (per `env-isolation.test.ts:9-19`'s own comment). S2/OpenAlex have no such
auto-selecting registry: `openalex.fetch`, `semanticScholar.fetch`, `fetchOpenAlexSemantic`,
`fetchOpenAlexTopicField`, `fetchSemanticScholarRecommendations`, `fetchCitationNeighborhood`
only run when a test explicitly imports and calls them by name. Every existing fixture test for
these adapters (confirmed by reading `openalex-semantic.test.ts:20-41`) stubs
`globalThis.fetch = vi.fn(...)` — the mock wins regardless of whether a real key sits in
`process.env`, because the code path never reaches the network either way. So today's
"provider-silent by default" for these two providers is chiefly a property of "does every
existing test mock fetch," not "is a key absent" — a materially different, and honestly weaker,
guarantee than the Vertex case. This guide does not change that pre-existing property (out of
scope), but it means the NEW live-channel test file must not weaken it, and a second-layer lock
is still worth adding for defense in depth (Finding C1c) even though the primary risk it closes
is smaller than the Vertex case's.

**Finding C1c — recommended second-layer lock, conditioned so it cannot collide with the live
config.** Unlike Vertex, unconditionally adding `SEMANTIC_SCHOLAR_API_KEY`/`OPENALEX_API_KEY`/
`OPENALEX_EMAIL` to `vitest.setup.ts`'s `SPENDABLE_KEYS_FORBIDDEN_IN_TESTS` array would break the
live-channels config itself (the shared setup file runs under every config, so it would delete
the very credentials the live config just injected, every time, before every test). The correct
second layer is a CONDITIONAL deletion: delete these three names before every test UNLESS the
same opt-in literal the live-channels config sets is present. Concretely, in `vitest.setup.ts`,
add a second, separately-named function that checks
`process.env.PEER_RUN_LIVE_CHANNELS_EVAL !== "1"` before deleting
`SEMANTIC_SCHOLAR_API_KEY`/`OPENALEX_API_KEY`/`OPENALEX_EMAIL`, called from the same `beforeEach`.
This closes the "ambient shell export" gap the existing comment names, for these three names
too, without touching the disjoint Vertex/Tavily list and without breaking the new live config
(which sets the opt-in literal itself, so its own `beforeEach` never strips its own credentials).

**RawItem → ChannelComparisonItem mapping** (needed for every role): `id: item.id`,
`source: item.source`, `doi: item.metadata?.doi`, `title: item.title`,
`year: publishedYearOf(item.publishedAt)` (import from `@/lib/feed/paper-identity`),
`authors: item.authors`, `externalIds: item.metadata?.externalIds`, `rank: <1-based index in
that channel's own returned order>`. **Caveat found while confirming this**:
`openAlexWorkToRawItem` (`web/src/lib/utils/openalex.ts:164-185`) does NOT populate
`metadata.externalIds` at all — only `citationCount`/`doi`/`workType`/`preferenceSignals`. S2's
own mapping (`semantic-scholar.ts:122-135`, `semantic-scholar-recommendations.ts:140-149`) DOES
populate `metadata.externalIds = { doi, arxivId, pmid, s2Id }`. So the primary (often only)
cross-channel match key for an S2 item vs. an OpenAlex item of the same paper is the shared
`doi:` key (both sides carry `metadata.doi` at the top level, which `resolveIdentity` reads
directly, not only through `externalIds`) — when a paper has no DOI on either side, only the
title+year+author weak link (already implemented in `clusterCanonicalWorks`, reused unchanged
per §1p.G) can still merge it. This is a pre-existing, already-mitigated property of the shared
identity module, not a gap for C to fix — noted here so a fresh A doesn't mistake it for a bug
when interpreting an "S2-only" count for a no-DOI paper.

**Rate/backoff already built into every one of these seven, reused unchanged:**
- OpenAlex (`web/src/lib/sources/_fetch.ts:18-53`, `sourceFetch`): one retry on 429, honoring
  `Retry-After` capped at 1.5s, else a flat 500ms wait, then a second attempt; whatever the
  second attempt returns is final.
- S2 (`web/src/lib/sources/semantic-scholar-client.ts`): shared queue, concurrency 2,
  paced at 1500ms between call STARTS when `SEMANTIC_SCHOLAR_API_KEY` is set (350ms unkeyed,
  lines 19-21), plus up to three 429-retries at 1s/2s/4s (`RETRY_DELAYS_MS`, line 34) — by the
  time a caller sees a thrown "HTTP 429" from an S2-sourced adapter, this backoff is ALREADY
  exhausted, which is exactly what makes a single caught S2 429 equivalent to "repeated S2 429s
  after the client's existing backoff" (§1u.3's stop condition) — see Finding C4.

## Finding C4 — budget and stop rules

**Per-input call counts** (logical adapter calls — each row of Finding C2's table counts as one
call per invocation, regardless of `_fetch.ts`'s own internal 429-retry, which is not a separate
logical call for this counter):

| Input type | S2 keyword | OA keyword | OA semantic | OA topic (resolve + fetch) | S2 seed recs | OA seed similarity | OA citations | Seed resolution (one-time) |
|---|---|---|---|---|---|---|---|---|
| starter (1 topic, 0 seeds) | 1 | 1 | 1 | 1 + 1 | 0 | 0 | 0 | 0 |
| battery (2 topics, 3 seeds) | 2 | 2 | 1 | 1 + 1 | 1 | 3 | 1 | 6 (2 lookups × 3 seeds) |

- **First run, nothing cached**: 6 starters × 5 calls = 30, + battery 18 = **48 calls total**.
- **Repeat run** (topic ids + seed resolutions cached from the first run, per Finding C5 — the
  runner persists these to `output/live-eval/resolved-cache.json`, never to the input file
  itself): 6 starters × 4 + battery 11 = **35 calls total**.
- **Single-input smoke run** (C's allowance): the cheapest starter input, first run = 5 calls;
  the battery input, first run = 18 calls. Either is far under any reasonable ceiling.

**Cost** (OpenAlex only — S2 is $0 regardless of count, subject only to pacing/ToS):

| Cost class | Price | Calls (first full run) | Cost |
|---|---|---|---|
| search (OA keyword) | $1/1k | 6×1 + 1×2 = 8 | $0.008 |
| semantic (OA semantic + OA seed-similarity) | $1/1k | 7 + 3 = 10 | $0.010 |
| search (topic-id resolution) | $1/1k | 7 | $0.007 |
| list/filter (OA topic fetch) | $0.10/1k | 7 | $0.0007 |
| list/filter (OA citations) | $0.10/1k | 1 | $0.0001 |
| single-entity (OA half of seed resolution) | free | 3 | $0 |
| **OpenAlex subtotal** | | **8+10+7+7+1+3 = 36 calls** | **≈ $0.026** |
| n/a — S2 has no published fee, ever (keyword 8 + recs 1 + S2 half of seed resolution 3) | $0 always | 12 calls | $0 |
| **Grand total, first full run (36 OpenAlex + 12 S2)** | | **48 calls**, matching Finding C4's per-input table | **≈ $0.026** |
| **Total, repeat full run** (resolutions cached) | | 35 calls | **≈ $0.019** |

Both are roughly a quarter of the keyless daily allowance (~$0.10/day) and about 2% of the keyed
one ($1/day), leaving wide headroom for the smoke run plus the later full run plus normal manual
retries on the same day, without going near either published ceiling. This estimate is
arithmetic from the documented per-operation prices (§1t.3b) applied to the call counts derived
directly from each adapter's own hard-coded caps (Finding C2's table) — it is not a live
measurement.

**Wall time.** S2 calls are globally paced through one shared queue regardless of concurrency
(`semantic-scholar-client.ts:48-63` — `lastStart` is shared across all callers, so admission is
serialized to at least `minIntervalMs` apart even though `MAX_CONCURRENT=2` allows two in-flight
round trips). First-run S2 call count = 8 (keyword) + 1 (recs) + 3 (seed lookups, keyed path
1.5s apart) = 12 → roughly 11 × 1.5s ≈ 16.5s of pure pacing, plus per-call latency (typically
under 1s each) — call it 20-30s for the S2 portion alone. OpenAlex calls are not globally paced
(each adapter's own `Promise.allSettled`/`Promise.all` fans out concurrently within one leg), so
that portion is latency-bound, not pacing-bound — a handful of seconds per input if the network
behaves. **Recommend the runner processes inputs strictly sequentially** (not all 7 concurrently)
to keep peak request rate low, make a 429 easy to attribute to one specific call, and keep total
concurrent load polite on a free-tier IP. Estimate: **under 1 minute for the smoke run, on the
order of 2-4 minutes for the full 7-input run** — an estimate from the pacing constants above,
not a live measurement.

**Proposed hard per-run call ceiling: 150 logical calls** (~3x the 48-call first-run estimate).
Rationale: enough headroom that a normal run — including the one-time resolution calls, a couple
of per-leg partial retries the runner's own error handling might reasonably attempt, and possibly
re-running a subset after fixing an input — never bumps into the ceiling by accident, while
still being far below anything that could meaningfully stress either provider's free allowance
even if every single call were somehow the most expensive class. **This number is a proposal —
see POLICY list.**

**Stop-rule design** (offline-testable, Finding C6 item 7):
1. Maintain a mutable `callsMade` counter for the run. Before every planned call: if
   `callsMade >= ceiling`, mark every remaining not-yet-attempted (channel, input) pair
   `"not_run"`, reason `"call ceiling reached"`, and stop making calls — check BEFORE calling,
   never after.
2. Wrap every actual call in try/catch. On success: increment `callsMade`, record `"ok"` with
   the mapped items (even if the array is empty — that is a real "ok," not "not_run," per
   `channel-comparison.ts`'s own status contract). On thrown error: increment `callsMade`
   (the attempt happened and counts against budget), then classify:
   - Message matches `/HTTP 429/` and the failing call was OpenAlex-sourced → **stop the entire
     run immediately** (§1u.3: "first OpenAlex 429"). Mark that channel `"failed"`; mark every
     other not-yet-attempted (channel, input) pair `"not_run"`, reason `"stopped after first
     OpenAlex 429"`.
   - Message matches `/HTTP 429/` and the failing call was S2-sourced → **also stop the entire
     run immediately**, reason `"stopped after repeated S2 429s (client backoff already
     exhausted)"` — per Finding C2's rate-limiting note, a thrown S2 429 by construction already
     represents the paced client's 1s/2s/4s backoff having been exhausted, so there is no
     separate "count S2 429s across calls" logic to build; the first one caught already IS
     "repeated."
   - Any other error (non-429 HTTP status, network error, timeout) → record `"failed"` for that
     one channel only; **continue** the run — a single adapter's outage must not abort the whole
     comparison, matching the existing "one flaky query never takes a channel down, but total
     failure is a real outage" pattern already used throughout these adapters.
3. `searchHttpFailure` (`web/src/lib/sources/search-failure.ts:48-57`) is the ONLY place a
   status code becomes visible to a caller of these adapters, and it bakes the code into
   `error.message` as `"<provider> HTTP <status> — <body-snippet>"` — there is no typed status
   field to read instead. The regex match on `.message` is the correct, and only, mechanism
   available without editing production adapter code (out of scope for B/C here).

**Resolved-id cache (also never committed, same directory tree).**
`output/live-eval/resolved-cache.json` — persists the topic-id and seed-id resolutions from
Finding C3 so a repeat run doesn't re-spend the one paid (search-class) resolution call. Never

**Short numeric summary (may be committed later, by whoever runs the full evaluation — not this
agent, and not C beyond the smoke run).** Per input × channel: `status`, `resultCount`,
`latencyMs`, `requestCount`, `errorMessage` if failed. Plus the whole-run `compareChannels()`
output shape already defined by `channel-comparison.ts`: `perChannel`, `pairwiseOverlap`,
`exclusive`, `union.gainOverChannel`, and — once labels exist — the `relevance` breakdown. This
is "numbers + short identifiers only" (§1u.4) as long as the committed form carries canonical
keys/titles/years, never raw abstracts or long fetched text.

**Blinded label sheet.** Purpose: let the user (or any labeler) judge relevance without knowing
which channel(s) found a given paper, per §1u.5. Design:
- Pool candidate works: every `WorkEntry` from `compareChannels()`'s `works` array (each is
  already ONE canonical work, deduped across channels — the label sheet must label WORKS, not
  per-channel duplicates of the same paper).
- Sample **~30-40 items total**, stratified to sample fairly across channels: bucket works by
  which channel(s) contributed them (`WorkEntry.channels`), then sample roughly
  proportionally from each bucket (exclusive-to-S2, exclusive-to-OpenAlex, found-by-both, and,
  if role groups differ meaningfully, exclusive-to-seed vs exclusive-to-keyword) so no single
  prolific channel dominates the sheet and a labeler's judgments can actually populate
  `RelevanceLabelMap` entries useful to every pairwise comparison, not just the biggest channel.
  A fixed, documented seed (see below) makes the specific sample reproducible.
- **Deterministic seeded shuffle, no channel leakage**: assign each sampled work a stable,
  short, opaque item id (e.g. `item-01`...`item-40`, NOT its canonical key, which could hint at
  source — e.g. a `doi:`-keyed vs `openalex:`-keyed id would leak provenance) — shuffle the
  sampled list using the SAME `mulberry32` deterministic PRNG already in
  `web/src/lib/evaluation/metrics.ts:231-240` (`mulberry32(seed)`, reused, not reimplemented) so
  a given `(inputSet, sampleSeed)` pair always produces the same sheet, but the ORDER carries no
  information about which channel(s) found each item. The sheet shows: item id, title, year,
  venue, a DOI link if one exists — explicitly **no abstracts, no channel names, no provider
  names, no long fetched text** (§1u.4/§1u.5).
- **Label ingestion + metric computation**: a small command reads the user's filled-in labels
  (item id → relevant/not-relevant, or blank/unsure) back, maps item id → canonical key (kept in
  a SEPARATE, non-shown-to-the-labeler mapping file the runner wrote alongside the sheet), builds
  a `RelevanceLabelMap` (boolean) for `compareChannels({ relevanceLabels })`, and — separately —
  a `ReadonlyMap<string, number>` (0/1) for `web/src/lib/evaluation/metrics.ts`'s
  `precisionAtK`/`recallInJudgedSet`/`ndcgAtK` (these two label shapes are NOT interchangeable —
  `RelevanceLabelMap` is `Record<string, boolean>`, the metrics module wants a `Map<string,
  number>` with a `0|1|2` grade for `ndcgAtK` specifically — the ingestion command builds both
  from the one underlying yes/no answer rather than asking the labeler twice). Items never
  labeled surface as `unlabeledWorkCount` (channel-comparison side) / `unjudgedCount` (metrics
  side) — never silently folded into "not relevant," matching both modules' own stated contracts.
- Anything not labeled, or if the user declines to label at all: `relevance: "unlabeled"` from
  `compareChannels` (its own built-in honest default) and `NOT MEASURED` in the committed summary
  — never a guessed or LLM-generated label (§1u.5 is explicit that an LLM judge needs a separate
  manager ruling, not assumed here).

## Finding C6 — existing metrics code to reuse

`web/src/lib/evaluation/metrics.ts` (391 lines, pure, synchronous, never throws on malformed
input — its own file header states this explicitly and P5-S2's mutation-testing note at
lines 161-171 is evidence it was actually exercised against a hand-mutated build, not just
written and trusted):
- `precisionAtK(rankedIds, labels, k, relevantThreshold?)` — reuse per channel (treat one
  channel's ranked `items` as `rankedIds`) for a precision@10-style number per channel.
- `recallInJudgedSet(rankedIds, labels, k?)` — same per-channel reuse; note its denominator is
  EVERY judged-relevant item across the whole labeled set, not just what that one channel
  retrieved, so a channel's recall number is directly comparable across channels for the same
  label set — exactly the "seed-vs-keyword quality" comparison §1f asks for.
- `ndcgAtK(rankedIds, gradedLabels, k)` — usable if the blinded sheet's binary yes/no is encoded
  as grade 1 (relevant) / 0 (not relevant); `gradedLabels` accepts `0|1|2`, so a binary label set
  is a valid (if degenerate) input — no 2-graded judgment is being invented, this is a legitimate
  use of the existing type, not a misuse.
- `bootstrapInterval(values, options)` and `perProjectBreakdown(projects, options)` — the
  cleanest reuse: treat each **channel** as a "project" (`ProjectEvalInput.projectId = channel
  name`, `rankedIds` = that channel's ranked canonical keys, `gradedLabels` = the shared label
  map). `perProjectBreakdown` then produces exactly "every metric reported per project [here:
  per channel] ... with its n, never only a pooled average" (its own doc comment, lines 349-352)
  — which is precisely the per-channel, non-pooled-only reporting this comparison needs, with no
  new aggregation code required.
- **Nothing in `metrics.ts` needs to change.** It is pure evaluation tooling with no production
  caller today (its own header says so, line 27) — the runner becomes its first real caller,
  same relationship the runner has to `channel-comparison.ts`.

## POLICY — manager decides

1. **The exact call ceiling.** This guide proposes **150 logical calls per run** (~3x the
   48-call first-full-run estimate). The manager may tighten or loosen it.
2. **The input set.** This guide proposes the 6 warm-pool starter topics (as-is, unedited, from
   `.github/workflows/warm-pool.yml`) plus one battery-materials profile with 3 named-by-DOI
   seeds chosen by this agent for name-recognition confidence, not live-verified. The manager
   decides whether to include the user's own profile at all (a real product/privacy question,
   not a technical one — §1u.4 already limits what leaves the machine, but "should the user's
   real research identity be the live-eval subject at all, even locally" is a judgment call this
   agent should not make unilaterally), and whether these specific 3 DOIs are the right seeds
   (the user may prefer different landmark papers in their own sub-field).
3. **Whether the topic role runs at all for the 6 starter inputs.** It requires one paid
   (search-class) OpenAlex resolution call per input the first time, to make up for production
   never having wired a topic-id source (Finding C2 role 4). The manager may decide this one
   role is skippable for the starter inputs (keeping it only for the battery-materials input,
   where the user could supply a known topic id directly) to shave 6 calls and $0.006 off the
   first run — immaterial to budget, but worth a decision since it is inventing an input
   production doesn't have a path to yet.
