## DESIGN CHOICES

- **Cache-key decision (§1c: "decide and justify").** `opportunities/pool-cache.ts` (`derivePoolCacheKey`) is outside this slice's allowed-file list, so it cannot gain a seed-derived key component. Decision: seed-driven candidates are fetched at READ TIME inside `runFeedPipeline` — same placement and mechanism as the existing `rolloverCandidates` merge (after the cache load/retry, before `dropStale`/scoring, via the same `dedupItems` call) — and are NEVER written back via `cache.set`. Proven directly by 2 tests (channels.test.ts, EVIDENCE #8/step 6), not just asserted: a seed-driven item reaches the response but is absent from the persisted `MemoryPoolCache` entry, and a second read of the same cached pool with `positiveSeeds` omitted never inherits a prior read's seed-driven item. Named cost: every read (not just a cache miss) of a signed-in owner with a seed flag on pays a fresh fetch, rather than amortizing over the pool's cache lifetime — acceptable now since all three channels default off and live use is BLOCKED (§1o.5); revisit if/when live use is authorized and `pool-cache.ts` can be added to an allowed-file list.
- **Flag-getter placement.** The 3 flags + `anyPositiveSeedChannelEnabled()` live in `preferences/positive-seeds.ts`, not `pipeline.ts` (where P2-S4a's 2 flags live). Reason, confirmed by direct inspection of `route.test.ts`: that file already does `vi.mock("@/lib/feed/pipeline", () => ({ runFeedPipeline: mocks.runFeedPipeline }))` — a full module replacement with no other export. Importing a flag function from `pipeline.ts` into `route.ts` would have resolved to `undefined` in every one of that file's existing tests and crashed them. `pipeline.ts` imports the SAME getters from `positive-seeds.ts`, so there is exactly one source of truth.
- **Feedback-route payload capture, scoped to what's honestly possible.** The client (`store/feed.ts`, not edited) sends only `{title, concepts}` for a paper today — no DOI, no abstract. The route additively derives `resolvedIds` (openalexId/s2Id/arxivId/pmid) from `itemId` itself (already `"source:nativeId"`) and merges it into the stored payload. Byte-identical for every non-paper kind or unrecognized source prefix.
- **Resolver scope.** Positive seeds only (`saved`/`moreLikeThis`, most recent 10, de-duplicated by canonical identity). Negative-seed resolution (`notInterested` -> S2 `negative_paper_ids`) is not built — the brief's own 4-item channel list is positive-seed-only; the S2 adapter accepts an optional `negativePaperIds` parameter for contract completeness but `pipeline.ts` never populates it.
- **Self-exclusion.** One shared `Set` of every seed's canonical key + every alias, checked via the EXISTING `isDeliveredIdentity`/`identityForRawItem` helpers (the same ones P4's delivery-ledger exclusion uses) against the combined output of all three channels, applied once at the end of `fetchPositiveSeedCandidates`.
- **Per-channel caps.** S2 recommendations: limit 25 (guide's 20-30 band). OpenAlex seed-similarity: at most 5 seeds get their own call (one call per seed, small cap per the design brief), 10 results each. Citation neighbours: one call, limit 40 (the existing `fetchCitationNeighborhood`'s own internal 8-id cap applies unchanged).
- **Logging.** Only counts are ever logged (`+N candidates`) — never a seed id, title, or owner id. Proven by a dedicated resolver-level test spying on `console.log`/`.error`/`.warn` across both the normal and the repository-throws paths.
- **`resolveServedItems` not threaded with `positiveSeeds`.** route.ts's legacy batch-reconstruction fallback (only fires for a pre-P4-S3 row with no stored `servedItems`) still calls `runFeedPipeline` without `positiveSeeds`. A rare edge case (only affects reconstructing an old batch that happened to include a seed-driven item), disclosed rather than silently widening the diff to thread one more parameter through an already-complex function outside this slice's core scope.
