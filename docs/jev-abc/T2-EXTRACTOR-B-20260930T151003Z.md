- `"The interfacial catalytic activation of crystalline Li2C2O4 (LCO) for cathode prelithiation..."` →

names explicitly: *"Self-declared a pair for this tag, but no initials-spelling run found (e.g. a bare
chemical formula) -- not a declared DIFFERENT expansion."* This is not a bug or an edge case rule (c)
narrowly misses — it is the rule working exactly as designed, on a case it was never built to judge:
rule (c) answers "does this paper's own SPELLED-OUT NAME disagree with a known one," and a formula is not

simply does not happen to contain that initials sequence.

### The exact recommended shape — a closed set, and why

Two new patterns, added to the private `selfDeclaredAbbreviationPairs` list in `keyword.ts` alongside the
existing two:
- **comma-long-first**: `<long form>, <ABBR>` — e.g. `"(light cycle oil, LCO)"`
- **comma-abbr-first**: `<ABBR>, <long form>` — e.g. `"(LCO, light cycle oil)"`

both searched **inside an already-matched `(...)` span** (not anchored to the parenthesis boundary the
way the existing two are), reusing the EXISTING long-form phrase shape
(`(?:[A-Za-z][\w-]*\s+){1,5}[A-Za-z][\w-]*`, 2-6 whitespace-joined words) and the EXISTING abbreviation
shape (`[A-Z][A-Za-z0-9]{1,7}`) verbatim, unchanged. This is a closed set because punctuation inside one
parenthetical pair has exactly two orderings around one separator (long-first / abbr-first) and the
separator itself is the one new fact (comma) — no free-form scanning is introduced, and the same finite
character classes that already bound the shipped regexes bound these too. It also, for free, catches
`"(i.e. light cycle oil, LCO)"` (shape 5 — the `i.e.` prefix is simply text before the matched span that
the pattern was never anchored to skip in the first place) and the REAL semicolon-joined double-pair shape
found in the LFP sample (`"(local field potentials, LFP; electrocorticographical signals, ECoG)"` —
confirmed extracting BOTH pairs correctly, since each comma-pair is found independently within the same
parenthetical span; the semicolon needs no special handling, it simply isn't part of either match).

**Declined, with reasons:**
- **Shape 6, bare `LCO; light cycle oil` (no parens at all):** 0 real occurrences in 700 real items
  scanned this session (100 LCO + 600 across 6 other tags). Adding it would mean dropping the
  parenthesis anchor entirely for a semicolon-joined pair anywhere in a sentence — semicolons separate all
  kinds of unrelated clauses in ordinary scientific prose, so this is a materially larger false-positive
  surface for zero measured benefit. Recommend: do not add; revisit only if a real instance turns up.
- **`@`-coinage (shapes 7-9, `NCO@LCO` etc.):** Q3 showed by execution that widening the character class
  does not produce a usable pair (Level 1) and that even a hand-fed correct pair does not make rule (c)
  fire (Level 2, a bare formula has no multi-word initials to check). Not part of this recommendation;
  it needs a different, larger mechanism, out of scope here (POLICY, Q5).

## Q5. Severity + POLICY list

### Severity, in plain words

A paper that explains its own short name in ONE particular writing style — the long description and the
short form together, separated by a comma, inside one pair of parentheses, like `"(light cycle oil,
LCO)"` instead of the more common `"light cycle oil (LCO)"` — is invisible to the one check whose whole
job is: "does this paper mean something different by this short form than the reader does?" When that
happens on a paper that genuinely means something different (this investigation found two real ones — one
about petroleum, one about a brain-signal measurement — both borrowing short forms a battery reader also
uses), that one check simply never fires, as if the paper had said nothing about its own meaning at all.

There is a second, statistics-based check that usually catches the same paper anyway, by comparing its
general vocabulary to what the reader has written about their own work. But that backup only runs when the
reader has actually written something else — a project summary, methods, anything beyond the bare short
tag itself. A reader who has added only the tag and nothing else gets no protection from either check, and
that is a normal, common way to use the product, not an edge case. For that reader, today, one of these
wrong-meaning papers can appear at full strength, claiming to match their interest.

How often the writing style itself shows up: rare — about 1 in 100 real papers sampled use this exact
comma-inside-parentheses style at all, and most of those are either a genuine match (harmless either way)
or an unrelated list of abbreviations that only looks similar at a glance. But when it does show up on a
genuinely wrong-meaning paper, the miss is total, not partial.

Separately, the much odder case of two DIFFERENT short forms glued together with an `@` sign (like
`"NCO@LCO"`) is not a writing-style problem at all — it is two different chemical compounds that happen to
share a nickname in one specific paper. No amount of "read one more punctuation style" fixes that; it
would need the product to actually know chemistry, which is a much bigger, separate piece of work, and the
prior investigation already showed that no simple statistical cutoff can catch it either without also
throwing out most of the genuine matches.

**Bottom line: narrow, well-understood, and now measured — not an emergency, but a real, confirmed gap
with two concrete real-world examples, cheap to close for the comma style, not worth chasing for the `@`
style.**
