## 1. Root cause (as confirmed by B, restated for this checkpoint)

`mergeProfileAtSignIn`'s single-value merge rule ("non-empty beats empty,
else local wins once") cannot tell "a human genuinely set this on this
device" apart from "this device has never been touched and is still showing
`defaultProfile`'s own non-empty placeholder" (`displayName` "Peer Member",
`careerStage` "PhD Year 3", `industryVsAcademia` "both", `phdYear` 3,
`colorTheme` "system:ember", `digestHourLocal` 8, `digestChannel` "inapp",
`digestFrequency` "daily"). `profile-sync.tsx`'s `onSession` runs this merge
on **every full page load** (`didInitialPullRef` is an in-memory `useRef`,
not persisted) and then PUTs the **whole profile**, so any device that loads
— fresh or merely stale — can overwrite the account's real values with its
own copy. Two sub-cases, same mechanism: a brand-new device overwrites with
factory defaults; a stale-but-real device overwrites a newer edit made
elsewhere (ping-pong).

## 2. Ruled design (§1bk, restated precisely)

Persist per device a `lastSynced` snapshot of the 14 single-value fields
next to `profile` (store version 4 → 5; the migration adds none — bootstrap
rule). A field is **dirty** when it differs from `lastSynced`, or — no
`lastSynced` entry yet — when it differs from `defaultProfile`. Dirty → this
device's value wins the merge. Not dirty → the account's value wins outright
if the account has one, else keep local. List fields keep today's union.
Dirtiness is **derived by comparison** — confirmed below that all 14 fields
are plain scalars (string | number | undefined | a fixed string-literal
union), so comparison expresses every case; **no per-setter bookkeeping
added anywhere** (see §6, "why no setter changes").

The reconcile push (right after the sign-in merge) carries **only** the
dirty single-value fields, plus list fields whose union actually added
something new — never the whole profile. The steady-state debounced push
keeps sending changed fields only; its "last pushed" baseline is kept
consistent with the persisted `lastSynced` (design note in §4.3 below on how
I implement "moved onto lastSynced" without duplicating bookkeeping). After
every successful push, **and** after a pull that needed no push,
`lastSynced` becomes the resulting full 14-field snapshot. A failed push
leaves `lastSynced` untouched (fields stay dirty, retry next time; existing
failure notice unchanged).

3. New exported function `dirtySingleValueFields`:

   ```ts
   /**
    * PROFILE-SYNC (§1bk) — which of the 14 single-value fields THIS DEVICE
    * is the source of truth for right now: local's current value has moved
    * on from what it last confirmed with the account (`lastSynced`), or —
    * with no confirmation yet — from `defaultProfile`'s own value (the
    * bootstrap rule: a truly untouched device is never "dirty" merely for
    * holding the factory default). Pure comparison, no side effects; every
    * one of the 14 fields is a plain scalar (string | number | undefined |
    * a fixed string-literal union), so `!==` after normalizing
    * undefined/null expresses every case — no field needs per-setter
    * bookkeeping instead.
    */
   export function dirtySingleValueFields(
     local: UserProfile,
     lastSynced: Partial<UserProfile> | null | undefined,
   ): Set<SingleValueField> {
     const dirty = new Set<SingleValueField>();
     for (const key of SINGLE_VALUE_FIELDS) {
       const localValue: unknown = local[key];
       const hasBaseline =
         lastSynced != null && Object.prototype.hasOwnProperty.call(lastSynced, key);
       const baseline: unknown = hasBaseline
         ? (lastSynced as Record<string, unknown>)[key]
         : defaultProfile[key];
       if ((localValue ?? null) !== (baseline ?? null)) {
         dirty.add(key);
       }
     }
     return dirty;
   }
   ```

4. New exported function `singleValueSnapshot` (the "resulting snapshot" §1bk
   ruling 3 says `lastSynced` becomes):

   ```ts
   /** The full 14-field single-value snapshot to persist as the new
    *  `lastSynced` baseline once a sync (push or no-push-needed pull) is
    *  confirmed — §1bk ruling 3, "becomes the resulting snapshot" (the
    *  WHOLE 14-field set, not just whichever fields happened to be dirty:
    *  that is what lets the NEXT load recognize "nothing changed here
    *  since" for every field, dirty or not). */
   export function singleValueSnapshot(profile: UserProfile): Partial<UserProfile> {
     const snapshot: Record<string, unknown> = {};
     for (const key of SINGLE_VALUE_FIELDS) snapshot[key] = profile[key];
     return snapshot as Partial<UserProfile>;
   }
   ```

5. New exported function `listUnionChanged` (for the reconcile push filter):

   ```ts
   /** True when the union produced something beyond remote's own list —
    *  i.e. local genuinely contributed a new entry (§1bk ruling 2, "list
    *  fields whose union changed"). `unionStrings` always puts remote's own
    *  list first, unchanged, then local's new entries, so "nothing added"
    *  is exactly "same length, same order as remote's own (deduped) list". */
   export function listUnionChanged(remoteValue: unknown, unionedValue: unknown): boolean {
     const remoteList = asStringArray(remoteValue);
     const unionedList = asStringArray(unionedValue);
     if (remoteList.length !== unionedList.length) return true;
     return remoteList.some((value, index) => value !== unionedList[index]);
   }
   ```

6. `mergeSingleValue` — add an `isDirty` parameter, drop the old
   `isEmptyValue(localValue)`/`remoteValue === localValue` branches (both
   subsumed correctly — see checkpoint reasoning in §6):

   ```ts
   /**
    * PROFILE-SYNC (§1bk) — supersedes the bare "non-empty beats empty, else
    * local wins once" rule. `isDirty` is now the ONLY way local wins a real
    * conflict: a genuine pending edit (differs from what this device last
    * confirmed, or from the factory default with no confirmation yet), not
    * an untouched or stale copy. Not dirty → the account's value wins
    * outright whenever it has one; "remote is empty" is the only case
    * local's value (dirty or not) survives, which is also what keeps a
    * still-blank field blank on both sides.
    */
   function mergeSingleValue(remoteValue: unknown, localValue: unknown, isDirty: boolean): unknown {
     if (isDirty) return localValue;
     if (isEmptyValue(remoteValue)) return localValue;
     return remoteValue;
   }
   ```

7. `mergeProfileAtSignIn` — add an optional third parameter; compute `dirty`
   inside the `remote` truthy branch only (see §6 for why the early return's
   shape stays byte-identical); pass `dirty.has(key)` into `mergeSingleValue`:

   ```ts
   export function mergeProfileAtSignIn(
     local: UserProfile,
     remote: Partial<UserProfile> | null,
     lastSynced?: Partial<UserProfile> | null,
   ): ProfileMergeOutcome {
     if (!remote) {
       return { patch: {} }; // unchanged shape — see §6
     }

     const dirty = dirtySingleValueFields(local, lastSynced);
     const patch: Partial<UserProfile> = {};
     let touchedIntentInputs = false;

     for (const key of LIST_FIELDS) {
       if (!Object.prototype.hasOwnProperty.call(remote, key)) continue;
       (patch as Record<string, unknown>)[key] = unionStrings(remote[key], local[key]);
       if (INTENT_LIST_FIELDS.has(key)) touchedIntentInputs = true;
     }

     for (const key of SINGLE_VALUE_FIELDS) {
       if (!Object.prototype.hasOwnProperty.call(remote, key)) continue;
       (patch as Record<string, unknown>)[key] = mergeSingleValue(remote[key], local[key], dirty.has(key));
       if (INTENT_SINGLE_FIELDS.has(key)) touchedIntentInputs = true;
     }

     if (Object.prototype.hasOwnProperty.call(remote, "preferenceLedger")) {
       patch.preferenceLedger = mergePreferenceLedger(remote.preferenceLedger, local.preferenceLedger);
     }

     if (touchedIntentInputs) patch.feedIntent = undefined;

     return { patch };
   }
   ```

   `ProfileMergeOutcome`'s shape is NOT extended with the dirty set (kept as
   `{ patch }` only) — see §6 for why, and how callers get the dirty set
   without it.

`mergeProfileFromBackup` (P4) is untouched — a deliberately different merge
direction, out of this item's scope, and already correct (dirty-tracking is

### 4.2 New exported pure functions (placed beside `remoteProfilePayload`/`diffPayload`)

```ts
/**
 * PROFILE-SYNC (§1bk ruling 2) — what the reconcile push (right after the
 * sign-in merge) actually sends: the dirty single-value fields plus any
 * list field whose union genuinely added something new. Every other field
 * `remoteProfilePayload` would include (preferenceLedger, feedIntent, the
 * feed-tuning knobs like feedFocus/paperCount/feedAvoidReviews, etc.) is
 * left exactly as `remoteProfilePayload` computes it — unconditionally
 * included, matching today's behaviour. `defaultProfile` gives none of
 * THOSE fields the placeholder-shaped default that causes this bug, and
 * §1bk.5 scopes this item to `lib/profile/merge.ts` + this file + the
 * store's persist/migrate — widening the filter to every field in the
 * payload was considered and deliberately not done; flagged in the
 * phase-1 message as a scope decision, not left silently.
 */
export function reconcilePushPayload(
  merged: UserProfile,
  remote: Partial<UserProfile> | null,
  dirty: ReadonlySet<SingleValueField>,
): Partial<UserProfile> {
  const payload = remoteProfilePayload(merged) as Record<string, unknown>;
  for (const key of SINGLE_VALUE_FIELDS) {
    if (!dirty.has(key)) delete payload[key];
  }
  for (const key of LIST_FIELDS) {
    if (!listUnionChanged(remote?.[key], merged[key])) delete payload[key];
  }
  return payload as Partial<UserProfile>;
}

export interface ReconcilePlan {
  /** Apply to the local store exactly as `mergeProfileAtSignIn`'s patch. */
  patch: Partial<UserProfile>;
  /** Send to `PUT /api/profile` — empty means nothing needs sending. */
  pushPayload: Partial<UserProfile>;
  /** `local` with `patch` applied. The caller uses this to build the new
   *  `lastSynced`/`lastPushedRef` baseline once (if `pushPayload` is
   *  non-empty) the push is confirmed. */
  merged: UserProfile;
}

/**
 * The entire sign-in reconcile decision, pure and headless — `onSession`
 * becomes a thin wrapper that applies `patch`, awaits `pushRemote(
 * pushPayload)` when non-empty, and advances `lastSynced`/`lastPushedRef` on
 * success. Lives here (not in lib/profile/merge.ts) because it needs
 * `remoteProfilePayload`'s credential redaction + feedIntent computation.
 * `dirtySingleValueFields` is computed here (once) from `local`/`lastSynced`
 * regardless of whether `remote` is null — it does not depend on `remote` —
 * and reused for both the merge decision (inside `mergeProfileAtSignIn`,
 * recomputed there identically and cheaply — pure, deterministic, no
 * drift risk) and this payload filter.
 */
export function planReconcile(
  local: UserProfile,
  remote: Partial<UserProfile> | null,
  lastSynced: Partial<UserProfile> | null,
): ReconcilePlan {
  const dirty = dirtySingleValueFields(local, lastSynced);
  const { patch } = mergeProfileAtSignIn(local, remote, lastSynced);
  const merged: UserProfile = { ...local, ...patch };
  const pushPayload = reconcilePushPayload(merged, remote, dirty);
  return { patch, pushPayload, merged };
}
```

### 4.3 `onSession` — replace the merge/push section

Replace from `const local = useProfileStore.getState().profile;` through
`didInitialPullRef.current = true;` with:

```ts
        const local = useProfileStore.getState().profile;
        const lastSynced = useProfileStore.getState().lastSynced;

        // SIGNIN-MERGE (§1af/§1ah/§1aj) + PROFILE-SYNC (§1bk) — planReconcile
        // computes the entire decision in one pure call (unit-tested
        // headlessly, same convention as mergeProfileAtSignIn itself): which
        // fields this device's own edit wins outright (dirty), and exactly
        // what — if anything — needs to reach the account for them.
        const { patch, pushPayload, merged } = planReconcile(local, remote, lastSynced);
        if (Object.keys(patch).length > 0) {
          useProfileStore.setState((s) => ({ profile: { ...s.profile, ...patch } }));
        }

        // Reconcile the account to whatever this merge just decided. A push
        // can only ever ADD to the account, never discard anything (P3), so
        // attempting one whenever there is a real account row to reconcile
        // against is safe. When there is no account row at all yet (brand
        // new — or the pull itself failed, §1's `remote === null`), only
        // attempt when local actually has something worth carrying up.
        const shouldAttemptSync = remote ? true : hasAnySignal(local);
        if (shouldAttemptSync) {
          if (Object.keys(pushPayload).length === 0) {
            // PROFILE-SYNC (§1bk ruling 3) — "a pull that needed no push":
            // every dirty field already agreed with the account and no list
            // union added anything new. Still a successful, confirmed sync.
            useProfileStore.getState().setLastSynced(singleValueSnapshot(merged));
            lastPushedRef.current = remoteProfilePayload(merged);
            clearProfilePushFailed();
          } else if (await pushRemote(pushPayload)) {
            useProfileStore.getState().setLastSynced(singleValueSnapshot(merged));
            lastPushedRef.current = remoteProfilePayload(merged);
            clearProfilePushFailed();
          } else {
            // P3 — leaving lastSynced/lastPushedRef unset means the dirty
            // fields stay dirty and the next local edit's diff still
            // includes them: the retry P3 requires, no extra bookkeeping.
            markProfilePushFailed();
          }
        }
        didInitialPullRef.current = true;
```

### 4.4 Steady-state debounced push — one addition on the success path

```ts
      if (await pushRemote(patch)) {
        lastPushedRef.current = { ...lastPushedRef.current, ...patch };
        // PROFILE-SYNC (§1bk ruling 3) — "after every successful push...
        // lastSynced becomes the resulting snapshot." Uses the `profile`
        // this effect closed over (the same snapshot `payload` was built
        // from), restricted to the 14 single-value fields, so a reload
        // correctly remembers this push even though the reconcile-cycle
        // update in onSession only fires once, at sign-in.
        useProfileStore.getState().setLastSynced(singleValueSnapshot(profile));
        clearProfilePushFailed();
      } else {
        markProfilePushFailed();
      }
```

**Design note — "baseline moved onto lastSynced" without a second bookkeeping
mechanism:** I read this as the ruling's INTENT (a reload must not resend
everything because of a purely-in-memory baseline that never got seeded),
not a literal instruction to make the debounced push read `lastSynced`
directly as its baseline. `lastPushedRef` continues to be the diff baseline
for the FULL payload (list/ledger/feed-tuning knobs included — fields
`lastSynced` does not cover). The concrete fix is: `lastPushedRef` is now
ALWAYS refreshed after every non-null-remote reconcile (§4.3, both the
"nothing to push" and "push succeeded" branches) — today it is only set when
`shouldPush` was true AND the push succeeded, so a "quiet" reconcile (remote
non-null, nothing dirty, no list changed) used to leave it `null` for the
rest of the session, and the FIRST edit after that would resend the entire
payload via `diffPayload(next, null)`. Since the debounced-push effect
cannot fire before `didInitialPullRef` is true (i.e., before the reconcile
above has already run), this single fix is sufficient — no code path can
observe a stale/null `lastPushedRef` that my change didn't just refresh.
`lastSynced` and `lastPushedRef` are set from the SAME `merged` value at the
SAME moment in §4.3, so they cannot disagree on the 14 fields either covers.
I considered ALSO seeding `lastPushedRef` from persisted `lastSynced` at
mount (belt-and-suspenders), and rejected it: it would be dead code (the
reconcile always runs first and overwrites it before the debounce effect can
fire), adding complexity with no observable behavior change. Flagged in the
phase-1 message in case the manager wants the literal wiring anyway.

## 6. Design decisions worth the manager/A's attention (not silent)

1. **No per-setter bookkeeping — confirmed, not assumed.** All 14
   `SINGLE_VALUE_FIELDS` are plain scalars (`string`, `string | undefined`,
   `number | undefined`, or a fixed string-literal union type) — verified by
   reading `web/src/types/index.ts`'s `UserProfile` interface field by
   field. `dirtySingleValueFields`'s `!==` comparison (after normalizing
   `undefined`/`null` to one value) expresses every one of them exactly;
   there is no field where "differs from the baseline" needs anything a pure
   comparison cannot say. Confirmed further by checking every OTHER code
   path that writes `profile.<single-value field>` — `importProfile`
   (backup restore) and `hydrateFromRemote` (an older, unrelated path) both
   go through the same `profile` object the next sync reads from, so they
   need zero additional wiring either; dirtiness is detected automatically
   on the next sync regardless of which setter (or non-setter path) changed
   the field.
2. **`ProfileMergeOutcome` shape is unchanged (`{ patch }` only).** Test 1 in
   the existing suite (`expect(mergeProfileAtSignIn(local, null)).toEqual({
   patch: {} })`) checks the WHOLE return value, not just `patch` — adding a
   `dirtySingleValueFields` field to the return object would silently break
   that exact-equality check. `dirtySingleValueFields` is called
   independently by `planReconcile` instead (cheap, deterministic, zero
   drift risk between the two call sites), so this existing test needs no
   edit at all.
3. **`preferenceLedger` and the feed-tuning knobs (feedFocus, paperCount,
   feedAvoidReviews, digestEnabled, etc.) keep today's unconditional
   inclusion in the reconcile push.** §1bk ruling 2's literal text is "dirty
   fields (plus list fields whose union changed)" — two named categories,
   not "every field". These other fields are outside §1aj's single-value
   list (the merge doesn't touch them at all, unchanged pre-existing
   behavior), have no placeholder-shaped default that causes this bug class,
   and touching their push behavior would widen the blast radius past
   §1bk.5's named scope (`merge.ts` + this file + the store's
   persist/migrate). Kept as today: always sent on every reconcile.
4. **`digestTimezone` is NOT special-cased**, even though B's guide noted its
   old-rule behavior ("keep this device's own timezone") was "arguably
   correct" and did not list it among the 8 originally-broken fields. It IS
   one of the 14 `SINGLE_VALUE_FIELDS`, and §1bk's ruling applies the same
   dirty rule uniformly with no named exception. Net effect: a genuinely
   fresh device (whose resolved IANA zone trivially equals
   `defaultProfile.digestTimezone`, since both are computed identically at
   load) now defers to the account's existing digest timezone rather than
   silently overwriting it with this device's own — arguably closes a
   related latent issue B chose not to escalate, but it IS a behavior change
   outside the "8 fields" the bug report centered on. Flagged, not hidden.
5. **`logOut()` now also clears `lastSynced`.** Not explicitly named in
   §1bk's ruling text (which only names `merge.ts`, `profile-sync.tsx`, and
   the store's persist/migrate). Necessary for correctness: without it, a
   stale `lastSynced` from before a "Reset profile to defaults" (or, on a
   shared computer, a different person signing in next) would make every
   default look dirty relative to it, reintroducing this exact bug through
   sign-out/sign-in instead of a fresh device. A plain "Sign out" (confirmed
   by reading account-section.tsx) does NOT call `logOut()` and does not
   touch `profile` either — `lastSynced` staying intact across a plain
   sign-out is symmetric with `profile` itself staying intact, both by
   design.
6. **Residual, pre-existing, out-of-scope characteristic — stated for
   completeness:** the local profile store is not account-scoped (one
   `peer-profile` localStorage slot per browser, shared by whichever account
   is currently signed in). A different person signing in on a shared
   computer WITHOUT clicking "Reset profile to defaults" first would see the
   previous person's `profile` and `lastSynced` momentarily, exactly as they

### 7.5 Mutation proof plan (the 3 named mutations)

1. **Treat every field as dirty** (mutate `dirtySingleValueFields` to

### 11.3 Step 3 — preferenceLedger and feedIntent, stated precisely

**preferenceLedger — merge.** `mergePreferenceLedger(remote, local)`
(unchanged code) starts from `{ ...remoteClean }` — every one of the
account's own entries is in the output BEFORE local's entries are even
considered — then walks `local`'s entries and only ever ADDS a key remote
lacks, or REPLACES a shared key's entry with whichever side's timestamp is
genuinely more recent (else local). There is no code path in this function
that deletes a key present in `remoteClean`. **This makes "the merge output
loses one of remote's keys" true by construction, not just by testing** —
proven anyway by a new test (§11.5) merging a stale/incomplete local ledger
against a richer remote one and asserting every remote key survives.
**preferenceLedger — push.** Round 1 left it in the "everything else, sent
unconditionally" bucket. This round extends the same "only when it actually
changed" treatment `listUnionChanged` already gives list fields: a new
`preferenceLedgerChanged(remote, merged)` (merge.ts) returns true only when
the merged ledger's entries differ from remote's own (sorted-by-key
structural comparison — see the function's own doc comment for the one
named simplification: entries are compared via `JSON.stringify`, which is
sensitive to a change in an ENTRY's own internal key order; every entry in
this codebase is built by the same handful of functions in
`lib/preferences/ledger.ts` with a fixed literal shape, so this is a
practical non-issue, and erring toward "detected as changed" — an
unnecessary resend — is the safe direction, never the unsafe one).
`reconcilePushPayload` now drops `preferenceLedger` from the payload when
this returns false.
**feedIntent — merge.** Never merged as its own nested structure (unchanged,
pre-existing, correct): `mergeProfileAtSignIn` clears it
(`patch.feedIntent = undefined`) whenever an intent-input field was
touched, forcing a fresh recompute from the JUST-merged flat fields on the
next read, rather than trusting either side's stale cached blob.
**feedIntent — push.** `remoteProfilePayload` recomputes it fresh via
`profileFeedIntentCard(merged)` and includes it only when that computation
is non-null (unchanged). **Why no new filtering is needed:** feedIntent is
100% derived from fields this round (plus round 1) already makes safe —
`requiredConcepts`/`preferredConcepts`/`exclusions` are `researchTopics`/
`softTopics`/`dislikedTopics` (union, monotonic, can't shrink) and
`project`/`challenge` are `currentProject`/`currentChallenges` (now
correctly dirty-tracked, so a stale device's OWN stale project text no
longer wins over the account's newer one). Since every input is safe, the
recomputed feedIntent inherits that safety; adding a SEPARATE "has
feedIntent itself changed" filter would compare a value that already only
changes when its (safe) inputs change — redundant, and a second place to
get a comparison subtly wrong. Documented, not filtered; proven by test
that a stale device's feedIntent reflects the reconciled (not the stale
local) project text (§11.5).
