## 2. Part (a) — pool-independent context measure

### 2.1 Why today's measure is pool-relative, precisely

`simContextStripped` is a cosine between two TF-IDF vectors built from `combine.ts`'s `index =
buildIndex(items)` (line 162 of the current uncommitted `combine.ts`). `tfidf.ts`'s `buildIdf` computes,
for every token, `idf = log((N+1)/(d+1))+1` where `N` = the number of items in `items` (the day's fetched
candidate pool) and `d` = how many of THOSE items contain the token. Both `N` and `d` change every time
the surrounding pool changes size or composition — confirmed by reading `tfidf.ts` in full this session
(unchanged, read-only). A fixed real paper's cosine to a fixed real context text therefore has no reason
to be stable across days, queries, or source-fetch luck. This is the exact, re-confirmed mechanism behind
fresh A's FINDING 1.

### 2.2 Two alternatives designed and measured, plus the combination that beat both alone

**Option 1 — IDF from a fixed reference corpus, built once, shipped with the app, independent of any
day's pool.** Same cosine/strip mechanism as today (`senseContextGate`'s existing shape: strip the tag's
own tokens from both sides, TF-IDF-weight, cosine), but every weight comes from a STATIC token→IDF table
computed ahead of time from a large, fixed, multi-domain document sample — never from `buildIndex(items)`.
Implementation: `gateFixedReference` in `sc2-lib.mjs` (ported for measurement; production shape in §1.1).

**Option 2 — raw token overlap, no corpus statistic at all.** Strip the tag's own tokens (same
`expandTerm`-based strip set as today) from both sides, then compare the two token SETS directly — no
IDF, no pool, nothing built from any corpus. Measured as an overlap coefficient (`|A∩B| / min(|A|,|B|)`),
using the ALREADY-SHIPPED `tokenize.ts` STOPWORDS list plus (optionally) the ALREADY-SHIPPED
`GENERIC_TERMS` set to drop uninformative-but-common words before comparing.
**Flagged, as instructed: `GENERIC_TERMS` (11 words: materials, energy, transport, modelling, simulation,
interface, design, analysis, systems, data, characterization) is a CLOSED, hand-maintained list over an
OPEN class of "generic-but-common scientific words" — it will always miss some (e.g. "results", "method"
are already `tokenize.ts` STOPWORDS so are fine, but a word like "properties" or "performance" is neither
listed nor stopword-filtered and would count as a full-weight overlap token even though it is nearly as
uninformative). This is a real, inherent limitation of Option 2, not a bug — recorded as POLICY 8.3.**
Implementation: `gateRawOverlap`/`gateRawOverlapJaccard` in `sc2-lib.mjs` (Jaccard variant measured too,
see §7.3 — the overlap-coefficient beat it and is what's reported below).

**Both were also tried COMBINED** (pass requires clearing BOTH gates; fail either → demote) after
discovering the two designs have DIFFERENT blind spots on real data (§2.5) — this combination is the
actual recommendation (§7), reported alongside each standalone option for a complete comparison.

### 2.7 Production design for Option 1's reference corpus (as instructed: how built, how big, licence, how current)

**How built.** An OFF-PATH, scheduled script (never on the request path) samples a large, stratified set
of real academic titles/abstracts from the SAME keyless sources Peer already calls at runtime (OpenAlex,
arXiv, PubMed) — but instead of scoring them, it computes ONE static `{token: idfWeight}` table
(`buildIdf`, unchanged algorithm) and ships ONLY that derived numeric table, never the source text itself.
This measurement's own stand-in reference corpus (561 real documents already fetched and saved by this
investigation across battery/materials, condensed-matter physics, petroleum engineering, and clinical
medicine — deliberately multi-domain, since a reference corpus must be broad enough that domain-specific
words keep meaningful IDF while cross-domain scientific boilerplate does not) already demonstrates the
approach works at this scale (§2.5's numbers); production should sample MORE broadly across many more
fields the app's users might declare (not just materials science), likely in the low thousands of
documents — diminishing returns past a point, size is not the limiting factor once domain breadth is
adequate.

**Licence of the source text.** Flagged, not resolved — this is a product/legal call, not an engineering
one (POLICY 8.1). The key distinction that makes this tractable: Peer already fetches and processes this
exact content, from these exact sources, at runtime, for every live request (that is what the whole
scoring pipeline does today) — shipping a STATIC, DERIVED, AGGREGATE statistic (a token→float weight
table with no reconstructable source text, computed once and thrown away the source documents after) is a
strictly SMALLER exposure than what the product already does continuously, not a new category of one.
OpenAlex's structured metadata is CC0; arXiv and PubMed/NCBI's own terms permit this kind of derived,
non-redistributive processing (the same basis the live pipeline already relies on) — but whether legal
wants a written sign-off before shipping a STATIC snapshot (vs. today's per-request, non-persisted use) is
the manager's/product owner's call, explicitly not mine.

**How it stays current.** A scheduled, MANUAL or CI-triggered re-run of the build script (e.g. quarterly —
vocabulary drift for this kind of check is slow; a new abbreviation or subfield emerging takes far longer
than a quarter to matter) regenerates and replaces the static asset, checked into the repo like any other
static data file (the same pattern `ABBREVIATION_GROUPS` already sets, just generated rather than
hand-written). Explicitly NOT a runtime rebuild — that would silently reintroduce the exact pool-dependence
this whole item exists to remove. Someone (a named owner) needs to actually run it periodically — flagged
as POLICY 8.2, not assumed to happen on its own.

## 3. Part (b) — DROP / no-pad for fully-demoted items

### 3.1 Two design options measured, against real data, under the part-(a) design

Both named in the assignment, measured on THIN real pools using the fixedRef@0.02 gate (§2) so demotion
status is reliable first (a thin pool is exactly where pool-size sensitivity would otherwise confound this
measurement):

- **DROP-ALL** — a fully-demoted item is filtered out of `scored` entirely before ranking (§1.2's

  literally: nothing demoted ever appears, full stop.
- **EPSILON** — the §1ap AMENDMENT's own original design lead: a second, lower threshold; below it, drop;
  between it and the floor, demote as today (kept, ranked low). Measured at epsilon=0.005 (chosen from
  §2.5's fixedRef sweep: 0.005 already rejects 75-90% of real negatives on its own, leaving genuine room
  below the 0.02 floor for a "clearly off-topic vs merely low-context" split).

Compared against **PAD** (today's shipped behaviour — a demoted item competes on score like anything else
and can fill unused return slots).

### 3.3 What the table actually shows — read carefully, both ways

**DROP-ALL reliably removes wrong-domain fillers (1-3 of 3 confirmed cases across scenarios, the 1 miss in
scenario 1 is fixedRef's own known residual, §2.6/§3.2 — the COMBINED gate closes it, re-verified: with
the combined gate, BOTH wrong-domain items in scenario 1 are below floor, so DROP-ALL removes 2 of 2) —
but it is not free.** Scenario 3 shows a REAL, substantial cost with ZERO malicious content anywhere in
the pool: 6 of 10 genuine electrolyte matches vanish from the returned list entirely (not ranked low —
GONE), purely because they are naturally low-context (a real electrolyte paper whose abstract happens not
to share much OTHER vocabulary with the reader's declared project). Scenario 4 shows the same cost
alongside the benefit: 3 wrong-domain papers removed, but so are 4 genuine ones — a returned list that
shrinks from 10 to 3.

**EPSILON, at epsilon=0.005, removed ZERO wrong-domain items across every scenario tested.** This is not
a tuning accident to paper over — it is a structural property worth stating plainly: EPSILON only removes
the WORST offenders (near-zero similarity). An item sitting BETWEEN epsilon and the floor is still
"demoted," not dropped — and a demoted item still competes for return slots exactly as it does today, so
it can STILL pad the list whenever there are fewer than `topN` full-context matches. **EPSILON does not
actually satisfy "never let fully-demoted items fill the returned list" — only DROP-ALL does, by
construction.** A higher epsilon would remove more wrong-domain items, but would then also start
reproducing DROP-ALL's own genuine-loss cost for whatever now falls below it — there is no epsilon value
that gets DROP-ALL's protection without DROP-ALL's cost; they converge as epsilon rises toward the floor.

### 3.4 Recommendation for this part

**DROP-ALL, scoped to items where `kw.fullyDemoted` is true under the COMBINED gate (§2.6) — not the
weaker EPSILON variant, and not applied to a merely-demoted-on-one-of-several-tags item (fullyDemoted
already means "every Required-tag match this item has failed its context check," round-1's own existing
definition, unchanged).** Reasoning: EPSILON does not achieve the assignment's own stated goal in this
measurement; DROP-ALL does, at a real and now-quantified cost. That cost is smaller than it looks in
isolation for two reasons re-confirmed by this section's own data: (1) it only ever removes items that
would otherwise be UNRANKED FILLER — a genuine full-context match is never affected, at any pool size,

## 4. Part (c) — self-declared different expansion

### 4.1 The exact rule

For a Required tag with a catalogued abbreviation group (`ABBREVIATION_GROUPS`, `term-expand.ts` —
11 groups: li-ion, LCO, NMC, LFP, SSB, EIS, XRD, TEM, XPS, DFT, in-situ), reuse the item's own
ALREADY-EXTRACTED self-declared pairs (`selfDeclaredAbbreviationPairs`, `keyword.ts`, already private,
already used by T2) and check: does any pair whose SHORT side matches this tag have a LONG side that does
NOT match any of the tag's own known long-form expansions (`expandTerm(tag)`'s multi-word members)? If
yes, the item has told us, in its own words, that its abbreviation means something else — this tag is the
WRONG SENSE for this paper, regardless of what any statistical context check says.

```
function selfDeclaresDifferentSense(item, tag):
  if tag has no ABBREVIATION_GROUPS entry: return {applies: false, differs: false}   // nothing to disagree with
  knownLongForms = expandTerm(tag) filtered to multi-word entries
  for each {longForm, abbr} in selfDeclaredAbbreviationPairs(item.title + " " + item.abstract):
    if canonicalize(abbr) does not match this tag: continue
    if canonicalize(longForm) matches any knownLongForm: continue          // agrees — not a conflict
    return {applies: true, differs: true}                                  // self-declared, disagrees
  return {applies: declaredAny, differs: false}
```

**Where it plugs in**: `keyword.ts`'s `scoreKeyword`, inside the per-topic loop, at the SAME point the
SENSE-CONTEXT stripped-cosine gate already runs (§1ap.3/4) — this check runs FIRST (it is higher-precision:
an explicit self-declaration beats a statistical proxy). If `differs` is true, treat the match as WRONG
SENSE outright (§4.3), independent of `simContextStripped`. If `differs` is false (including when the tag
has no known expansion at all, or the item declares no pair for this tag), fall through to the ordinary
SENSE-CONTEXT gate exactly as today — this rule only ever ADDS a stronger, narrower signal for the ~11
tags that have a catalogued abbreviation; it never replaces the general check for anything else.

**When the tag has NO known expansion** (not in `ABBREVIATION_GROUPS` — this covers the large majority of
Required tags, including both other measured tags in this investigation, "electrolyte" and "solid
state"): `hasKnownAbbreviationExpansion` returns false immediately, the function returns `{applies: false,
differs: false}` unconditionally, and the item falls through to the ordinary context-floor check
untouched. Confirmed by direct execution, not just reasoning (§4.2).
