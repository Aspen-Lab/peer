NEW FINDINGS (false-merge risks first):

1. [FALSE-MERGE, HIGH, confirmed by real-code execution and by mutation] A weak-link chain with NO id-form key on ANY member fully collapses into one survivor, regardless of how many years it spans. Reproduced with my own 5-member chain (2020..2024, identical title/author, zero ids anywhere): `dedupItems` returns 1 item, not 5. Root cause: `pairConflicts` requires BOTH compared items to carry a real id-form key of the SAME type before it can even ask whether they satisfy `weakPairMatch`; with no ids at all, `idTypesOf(...).size === 0` short-circuits every pair to "no conflict," so nothing ever blocks the transitive weak-link chain from collapsing — the exact transitivity bug the ruling's Round 3 correction (§1p.G(2)) and this narrowed-conflict rule were both meant to close, simply undetected here because there is no id evidence to compare. This is not a rare shape: any record whose adapter didn't resolve a DOI/S2/OpenAlex/arXiv/PMID id (title+author-only, which is precisely when the weak-link tier is needed in the first place) is exposed to it.
2. [FALSE-MERGE, HIGH, confirmed by real-code execution and by mutation] A hub {P1,P2}+Z (P1,P2 share one DOI despite unrelated titles; Z matches P1 only, by title/year/author) collapses all three into one survivor whenever Z itself carries NO id. Reproduced directly. This is the exact hub false-merge the ruling's Finding 2 named — the fix works only because the tests built to prove it (both C's own and, before this review confirmed the gap, the natural reading of the ruling) happen to give Z its own DOI of the SAME type as {P1,P2}'s shared type. A weak-linking record with no id at all — again, the ordinary case for something that only ever matches by title — gets no protection.
3. [FALSE-MERGE, MEDIUM, confirmed by real-code execution] Same hub shape, but Z carries an id of a DIFFERENT type than {P1,P2}'s shared type (e.g. an arXiv id where P1/P2 share a DOI). `pairConflicts` requires the SAME type on both sides to fire at all, so this also merges all three, even though Z demonstrably has independent, verifiable identity information that simply doesn't happen to overlap in type with the cluster it's being checked against.

[Suggested direction, UNVERIFIED beyond this review's own hand-derivation — offered for the next ruling/B/C, not a mandate] All three findings above share one root cause: detecting "conflict" via id-TYPE comparison is fundamentally blind whenever id evidence is thin or absent on one side.
