## P11 — batch date alignment (the most consequential finding of this pass)

Traced the exact call chain BEFORE writing any due-selection code:
- `web/src/app/api/feed/route.ts:258` — a real visit's `runLedgerAwareFeed` computes
  `const localDate = localCalendarDate(now)` (imported from
  `@/lib/opportunities/pool-cache`, itself re-exporting
  `web/src/lib/local-calendar-date.ts`). `localCalendarDate` uses
  `now.getFullYear()/getMonth()/getDate()` — the SERVER runtime's own local zone (UTC on
  Vercel), with NO reference to the owner's `digest_timezone` anywhere in that call.
- `web/src/lib/dashboard/timezone.ts`'s own `dateInTimezone` doc comment already says
  this explicitly: "Deliberately NOT a reuse of .../local-calendar-date.ts's
  `localCalendarDate`: that helper reads the SERVER's own local zone... which is the
  wrong value here."
- `web/src/lib/dashboard/prepare-worker.ts`'s `runPrepareJob` passes `job.localDate`
  straight through, unmodified, to both `ledger.getBatch(job.ownerId, job.localDate)`
  and `ledger.prepareBatch(job.ownerId, job.localDate, ...)`. `job.localDate` is
  whatever string the ENQUEUE call put there — opaque to the worker/repository/ledger
  (`delivery-ledger.ts`'s own header: "`localDate` is opaque to this module").

The B guide's own §2.4 design (`localDate: dateInTimezone(now, row.digest_timezone)`
used AS the job's stored `local_date`) reproduces exactly the bug P11 warns about.
Worked counter-example (now a permanent regression test,
`web/src/lib/dashboard/due-owners.test.ts` "P11 batch date alignment" describe block):
`digest_timezone = "Asia/Tokyo"` (UTC+9, no DST), `digest_hour_local = 8`, a run at
`now = 2026-09-24T19:00:00.000Z`.
- `dateInTimezone(now, "Asia/Tokyo")` = `"2026-09-25"` (already Sept 25 in Tokyo).
- Target check-in: 08:00 JST on 2026-09-25 = **2026-09-24T23:00:00.000Z**.
- A real visit AT that instant computes `localCalendarDate(2026-09-24T23:00:00.000Z)` =
  **"2026-09-24"**.
- The B design would have stored the batch under `"2026-09-25"` — a full day off. A
  batch minted there would never be found by the real visit's
  `getBatch(ownerId, "2026-09-24")` lookup.

**Fix** (`web/src/lib/dashboard/due-owners.ts`, `isOwnerDueForPrepare`): the local date
computed via `dateInTimezone(now, tz)` is used ONLY as an input to
`utcInstantForLocalWallClock` (to pick WHICH day's target hour to compute). The value
actually returned as `batchLocalDate` — and the only value the new route ever writes
into `EnqueuePrepareJobParams.localDate` (`web/src/app/api/jobs/prepare-dashboards/
route.ts`'s `runDueSelectionAndEnqueue`) — is `localCalendarDate(checkinInstant)`: the
SAME function a real visit uses, fed the check-in instant instead of the request
instant. This makes the two paths agree by construction, regardless of what zone the
Node runtime is actually configured with (never hard-codes "UTC" as a literal).

**Escape-clause check (performed before writing due-owners.ts, not after):** does this
touch an already-VERIFIED contract? No. Read `prepare-due.ts`, `prepare-worker.ts`,
`prepare-job-repository.ts`, and `delivery-ledger.ts` in full — all four treat
`localDate` as an opaque caller-supplied string; none of their existing tests assert
any particular derivation of it. `computePrepareDueAt` returns only a `Date` (`dueAt`),
never a date string, so it has no opinion on this question either. The fix is confined
entirely to new code (`due-owners.ts`, the new route) that did not exist before this
item. Zero changes to any of those four files. No STOP was needed.

Proof: `due-owners.test.ts`'s "P11 batch date alignment" tests (2 cases: the
disagreeing Tokyo case above, and a same-day Chicago case proving the fix doesn't
change anything when the two values happen to already agree) plus an orchestration-
level pin in `prepare-dashboards/route.test.ts` ("DST-edge wiring") confirming the
route wires `PREPARE_LEAD_MINUTES`/`PREPARE_LOOKAHEAD_MS`/`batchLocalDate` through
correctly end to end.

## P8 — what a Tier-2 visit does with a Tier-0 prepared batch (recorded by execution, not changed)

Traced `web/src/app/api/feed/route.ts`'s `runLedgerAwareFeed`, the existing-batch
branch (lines ~275-292, unedited by this item):

```
const existing = await ledger.getBatch(ownerId, localDate);
if (existing) {
  if (existing.status === "prepared") { await ledger.markServed(ownerId, existing.id); }
  ...
  return { response: frozenFeedResponse(existing, status, items, reconstructed, startedAt) };
}
```

This branch is **unconditional**: it never inspects what `aiTier` (or intent, or
anything else) the batch was originally built at, and never compares that to the
current visitor's own `pipelineReq.aiTier`. There is no tier-comparison logic anywhere
in this function, and `resolveServedItems` (the only other thing this path calls) is
documented as "a REPLAY of papers already decided for this exact batch, not a
re-decision of membership" — it never re-runs the pipeline at a different tier either.

**Finding: a Tier-2-entitled visitor who finds a Tier-0 prepared batch already sitting
for today is served that Tier-0 batch completely unchanged.** The visit does not
detect the tier mismatch, does not refresh, does not upgrade it. This is a real,
observable product trade-off — exactly the one P8 anticipated and pre-approved ("an
AI-entitled user who opens a prepared batch sees a non-AI-ranked batch that day") — not
a bug this item introduced or is responsible for fixing. It is also consistent with
this codebase's own pre-existing, already-documented rule for a same-day mint: "same
papers, same order, even after feedback, refresh or an intent change that day"
(`runLedgerAwareFeed`'s own JSDoc, predates this item). Recorded here by tracing actual
code, not changed — per the manager's explicit instruction.

## Design decisions recorded (not POLICY stops — within C's authority, per the guide's own "C picks" language)

1. **`buildPool`'s pipeline call (`web/src/lib/dashboard/prepare-pool.ts`) is an
   INDEPENDENT small reimplementation of `runLedgerAwareFeed`'s "no batch yet" ~15
   lines (exclusions read, `runFeedPipeline` call, `PaperIdentity` mapping), not an
   extraction of a shared helper out of `feed/route.ts`.** The guide's own §3 Step 2
   explicitly names both as acceptable, "C picks based on how live route.ts is at
   pickup time." `feed/route.ts` is a large, heavily-tested file (P4-S3/P4-S6/
   P4-S6-FIX/P4-S9 all touched it) outside this item's assigned scope, and not in
   either parallel writer's stated file list either — the lower-risk path is zero
   changes to it. Verified via `git status` at finish: `feed/route.ts` was never
   modified by this item.
2. **`.github/workflows/digest-cron.yml`'s EXISTING top-level `concurrency: {group:
   digest-cron}` block was left untouched**; the new `prepare` job gets its OWN
   job-level `concurrency: {group: dashboard-prepare-cron}`, exactly matching the
   guide's own illustrative YAML. Named trade-off recorded in the workflow file's own
   comment and here: GitHub Actions' workflow-level concurrency setting serializes
   entire RUNS (both jobs together) across scheduled triggers, so a slow `dispatch` run
   could still delay the NEXT trigger's `prepare` job from starting, despite the new
   job's own independent group. This costs timeliness only, never correctness (the
   debounced, idempotent enqueue design self-heals against a delayed run by
   construction). Not fixed because doing so would mean restructuring the EXISTING,
   live `dispatch` job's setup, which is outside this item's additive scope — flagging
   for A/the manager to decide whether it's worth a follow-up.
3. **The per-run ceiling + wall-clock guard (P2) is implemented as a loop in the new
   orchestration function calling `drainPrepareQueue` with `maxJobs:1` per iteration**,
   checking `elapsedMs() >= wallClockBudgetMs` before each claim, rather than adding an
   optional parameter to `drainPrepareQueue` itself. Zero changes to
   `prepare-worker.ts`. Functionally identical to one call with `maxJobs:10` whenever
   the wall-clock budget is never hit; strictly safer when it is. Tested directly
   (`prepare-dashboards/route.test.ts`, "drain ceiling and wall-clock guard (P2)").
4. **"A reports the backlog left after each run" (P2) is satisfied via a truthful
   `stopped_reason`/`backlog_likely_remaining` field in the JSON response**, not a
   separate DB count query — the existing `DashboardPrepareJobRepository` interface has
   no non-mutating "how many are due" method, and adding one would touch an
   already-VERIFIED interface for a reporting-only convenience. `backlog_likely_
   remaining` is `true` whenever the drain stopped for any reason other than an empty
   queue.
5. **Due-selection's per-row filter reuses ONLY the SQL pre-filter
   (`digest_enabled=true AND digest_frequency != 'off'`, P3) — it does NOT also
   re-apply `frequencyAdmitsToday`'s weekday check the way `dispatch-digests` does for
   the email digest.** The guide's own §2.4 design never mentions re-applying it for
   prepare-ahead either. Reasoning: prepare-ahead is about the DASHBOARD visit
   experience (gated on `PEER_DASHBOARD_LEDGER`), which is unrelated to email cadence —
   a "weekly"-email-digest user can still visit the dashboard any day and should still
   get a prepared batch. Minor, reversible if the manager disagrees.
6. **`GET`'s `createAdminClient()` call (and the whole deps-construction-and-run) is
   wrapped in a try/catch** so an unconfigured environment (no Supabase env vars,
   `createAdminClient()` itself throws — unlike `SupabaseDashboardPrepareJobRepository`/
   `SupabaseDashboardDeliveryLedger`, which check the same env vars themselves and
   degrade internally) returns 200 with an honest `"admin_unavailable"` reason instead
   of a 500. This is a NEW protective requirement for this route (guide §3 item 13) —
   `dispatch-digests/route.ts` has the same unguarded call and was not asked to change.
