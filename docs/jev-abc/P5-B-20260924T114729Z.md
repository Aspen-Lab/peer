### 2.2 Per-migration rollback SQL design (for C to author as files — NEVER applied by anyone in this campaign)

Repo-wide finding (confirmed, spot-check 6): **no migration in this repository, old or new, has ever had a paired down-migration.** This campaign's own instruction (§3e, verbatim) is: *"Rollback falls back to privacy-safe deterministic pipeline/snapshots, NEVER resurrects old cross-user mixed pools. Do not drop old tables until a separately approved retention/migration plan; snapshots and stored reading history preserved."* So the SQL rollback files below are a **new** convention for this campaign, not a continuation of an existing one — C should say so plainly in the folder's README rather than imply this repo already had a rollback practice.

**Folder convention (for C):** `web/supabase/rollback/`, sibling to (never inside) `web/supabase/migrations/`, so no Supabase CLI migration runner ever discovers or auto-applies these files. Filename mirrors the forward migration's timestamp+name with a `_rollback` suffix, e.g. `web/supabase/rollback/20260924000000_dashboard_delivery_ledger_rollback.sql`. Every file's header must state, verbatim in structure: (1) NOT A MIGRATION — never applied by any automated runner; (2) exactly what is destroyed; (3) whether the destroyed data is regenerable (cache-like) or carries a user-facing guarantee (the delivery ledger's whole purpose); (4) that it needs a separately approved retention/backup plan before it is ever run by a human, per §3e.
