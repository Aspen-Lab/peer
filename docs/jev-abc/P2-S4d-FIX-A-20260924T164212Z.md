## NEW FINDINGS

**Finding (LOW severity, not blocking VERIFIED status) — corrupt-payload "self-heals" is conditional on a successful `cache.set()`, not unconditional, and is not bounded by the per-leg retry claim.** C's own doc comment (channel-candidate-cache.ts L158-165) frames a corrupt/stale-shape row's reclassification to `miss` as self-healing ("the next live fetch overwrites the row with a valid payload"). This is true only if the subsequent `cache.set()` write succeeds. Both `set()` call sites in `resolveChannelCandidates` (pipeline.ts L1728-1734, L1781-1786) and `PrivateChannelCandidateCache.set()` itself are fail-soft (silent catch). If writes are asymmetrically broken while reads keep succeeding — a narrower failure shape than a full outage — the corrupt row is never overwritten, and every subsequent request for that owner+signature re-takes the full "fetch every enabled leg live" branch. This is genuinely NOT bounded by `claimSourceRetry`/`isEligibleForRetry` (confirmed by reading the hit-branch, L1739-1787): that mechanism bounds re-fetching a previously-FAILED LEG inside an existing cache HIT, an orthogonal axis to a MISS-driven full rebuild, which has no analogous circuit breaker. Important scoping that keeps this LOW rather than MEDIUM: (a) this cache is brand-new this round, so no legacy/incompatible-schema rows exist yet in production — currently a purely theoretical, forward-looking precondition, not a live bug; (b) the underlying mechanism ("a miss stays uncached forever if writes never succeed") is not unique to corrupt payloads — it is an inherent, already-accepted property of this fail-soft-write cache design, shared by the pre-existing day-pool cache (`private-paper-cache.ts`), which the manager's own ruling already places out of scope for this fix; (c) choosing the alternative (classifying corrupt payload as `unavailable` instead of `miss`) would trade this bounded, request-volume-scaling cost for an unbounded, silent, permanent closure of a signature's live legs until manual intervention — arguably the worse failure mode, so C's choice is still the right one on balance. Recommend: no code change required now; record as an open item alongside the already-accepted day-pool cache write-fail-soft convention, revisit only if real corrupt/legacy rows are ever observed in production alongside a write-path outage.
