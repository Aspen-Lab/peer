## 2. Tokenizer/canonicalize handling of the named spellings

Two different, independently-verified pipelines matter, and **a third, upstream one dominates both**: every adapter (`arxiv.ts`, `openalex.ts` via `web/src/lib/utils/openalex.ts`, `semantic-scholar.ts`) already runs `title`/`abstract`/`tags` through `web/src/lib/text/clean.ts`'s `cleanDisplayText` at ingestion — *before* either `canonicalize` (term-expand.ts, used by T1/T2/T3) or `tokenize` (tokenize.ts, used by the SENSE-CONTEXT strip-set and the reference-IDF build) ever sees the text. (`pubmed.ts` is the one exception: its `esummary.fcgi`-based adapter never populates `abstract` at all — only `title` participates for PubMed items, pre-existing and unrelated to this fix.)

I ported `cleanDisplayText`, `canonicalize`, and `tokenize` verbatim into a scratchpad script and ran the brief's named spellings through the **real, full ingestion-to-matching pipeline** (not just `canonicalize` in isolation — an earlier draft of this check skipped `cleanDisplayText` and overstated the gap). Executed results, matched against a hypothetical `"licoo2"` group entry:

| Spelling | After `cleanDisplayText` | Canonical (T1 path) | Matches `"licoo2"`? |
|---|---|---|---|
| `LiCoO2` (ASCII) | `LiCoO2` | `licoo2` | **Yes** |
| `LiCoO₂` (Unicode subscript) | `LiCoO2` | `licoo2` | **Yes** — `cleanDisplayText`'s `normalizeUnicodeSymbols` maps `₂→2` explicitly, and `canonicalize`'s own `.normalize("NFKC")` would independently do the same if it somehow arrived unclean |
| `LiCoO<sub>2</sub>` (HTML) | `LiCoO2` | `licoo2` | **Yes** — `stripHtmlTags` removes `<sub>`/`</sub>` and keeps the inner "2" inline |
| `LiCoO$_2$` / `LiCoO_2` (LaTeX, plausible in raw arXiv summaries) | `LiCoO2` | `licoo2` | **Yes** — `normalizeLatex` strips the subscript markup |
| `LiCoO 2` (spaced, a PDF-extraction artifact) | `LiCoO2` | `licoo2` | **Yes** — `normalizeChemistryAndOperators`'s `([A-Z])\s+(\d)` rule closes the gap |
| `layered LiCoO2-based cathodes` (trailing hyphen) | unchanged | `layered licoo2 based cathodes` | **Yes** — the hyphen sits *after* the intact "licoo2" run |
| **`Li-CoO2`** (hyphen *inside* the formula) | unchanged (`cleanDisplayText` never touches ASCII hyphens) | `li coo2` (two tokens) | **No** — `canonicalize`'s dash-collapse (`\p{Pd}` → space) splits the token in two. This is a genuine, real residual gap, not covered by adding the plain formula string. It is also unusual, non-standard notation (chemists do not normally hyphenate inside a formula); not measured as materially common in the real samples below. |

Same pattern holds for `LiFePO4`/`LiFePO4-based` (matches) vs `Li-FePO4` (does not).

**SENSE-CONTEXT/tokenize.ts path**, run through the same cleaned input: `tokenize.ts` does **not** collapse hyphens (unlike `canonicalize`, which explicitly does) and does **not** call `.normalize("NFKC")`. In practice this is masked by `cleanDisplayText` already having normalized subscripts/HTML/LaTeX before either function runs, so for the 6 "Yes" rows above `tokenize("LiCoO2") = ["licoo2"]` too — same coverage as T1. One narrow, honest residual: `tokenize("LiCoO2-based") = ["licoo2-based"]` as **one** token (tokenize doesn't split internal hyphens the way `canonicalize` does), which is not equal to the strip-set's `"licoo2"` token — so in that one specific phrasing, T1 correctly admits the paper, but the SENSE-CONTEXT strip set leaves the hyphen-suffixed compound unstripped from the item side. Low practical impact (both sides of the context comparison are affected symmetrically by the same tokenizer, and this is the same *class* of pre-existing, accepted gap as the already-documented `TOKENIZE-PLURALS` item, not a new one) — noted for completeness, not proposed as in-scope work here.

**Bidirectional bonus, verified by re-reading `expandTerm`:** a reader who types their *own* Required tag as `"LiCoO2"` (instead of `"LCO"`) benefits too. `ABBREVIATION_INDEX` maps every literal form in a group to the whole group, so after the fix `expandTerm("LiCoO2")` resolves to the full `["lco", "lithium cobalt oxide", "licoo2"]` set and such a reader's tag would now also match papers that only ever say "LCO" or spell out "lithium cobalt oxide" — consistent with the module's own stated "bidirectional" design intent, not a special case.

## 4. Design

### What to add, and where

`ABBREVIATION_GROUPS` in `web/src/lib/scoring/term-expand.ts`, one literal lowercase string appended to each existing group (matching the file's existing lowercase-literal convention — `canonicalize` is idempotent on these anyway):

```ts
["lco", "lithium cobalt oxide", "licoo2"],
["lfp", "lithium iron phosphate", "lifepo4"],
["nmc", "nickel manganese cobalt oxide", /* see POLICY below */],
```

**LCO and LFP are clean, low-risk wins** — measured, real, double-digit-percent marginal recall gains, zero measured false positives across 300 cross-domain negative real papers plus the item's own original petroleum-collision adversarial set, and a mechanically verified reason the formula can never be ambiguous with an unrelated field (it is a specific compound name, not a common word). Recommend shipping both without further debate.

**NMC is a different *kind* of case, not just a smaller number**, and deserves an explicit decision rather than a silent default: `LiCoO2`/`LCO`/`lithium cobalt oxide` are three spellings of **the same one compound** — a pure synonym relationship, which is exactly what `ABBREVIATION_GROUPS`' symmetric, bidirectional `expandTerm` mechanism is built for. `"NMC811"`/`"NMC622"` are specific **stoichiometries** (hyponyms) of the NMC family, not alternate spellings of one fixed thing. Because grouping is symmetric, adding `"nmc811"` to the `"nmc"` group is a **two-way** door: it correctly makes a reader's generic "NMC" tag catch papers that only say "NMC811" (the measured 92% win) — but it also means a reader who deliberately types **"NMC811"** as their *own* tag (because they only care about the high-nickel chemistry) would now *also* match papers that only ever say generic, unspecified-stoichiometry "NMC" — a real, if narrow, precision cost with no clean way to make it one-directional inside the existing mechanism. This tension does not exist for LCO/LFP. See POLICY 3 below for the options with numbers attached.

### Tests C must write

1. **Zero new test code needed** for the basic bidirectional-expansion property: `term-expand.test.ts`'s existing `it.each(ABBREVIATION_GROUPS.map(...))` parameterized test (line 119) already asserts every member of every group expands to every other member — the moment the literal is added to the array, this test automatically covers `expandTerm("licoo2") ⊇ {"lco","lithium cobalt oxide"}` and the reverse, with no edits.
2. **New real-paper regression tests** (pattern: `required-gate.test.ts`'s existing `item()` fixture helper and `BATTERY_PROJECT_TEXT` constant) using the two confirmed-genuine LCO gains and the two confirmed-genuine LFP gains from §3 above as fixtures (title/abstract text is short enough to inline; do not re-fetch) — assert `scoreKeyword`/`scoreItems` now qualifies them for tag "LCO"/"LFP" where a same-shaped baseline test (formula stripped from the fixture text) still shows 0.
3. **Protective test:** the internally-hyphenated `"Li-CoO2"` spelling from §2 still does **not** match `"licoo2"` after the fix — documents the one honest residual rather than leaving it silently undiscovered.
4. **Rule (c) non-regression:** re-run (don't just trust) the existing `sense-context.test.ts:594-603` protective assertions (`"high-voltage LiCoO2 (LCO)"` etc. → `differs: false`) after the group change — they should need no edits, but must actually go green under the new group, not just under the old one.
5. **`upload-concepts.ts` regression:** whatever test file covers `KNOWN_SINGLE_TOKEN_TERMS`/its extraction candidates should be checked for a frozen-list assertion that would need the new literal added; if none exists, add one asserting `"licoo2"` is now an extractable single-token concept (ties the §1 path-table claim to an executable check rather than a comment).
6. **Mutation-style protective test for T2** (cheap, closes a gap this investigation found but didn't need to lean on): assert `selfDeclaredAbbreviationPairs("LiCoO2 (LCO)")` (bare one-word long form) returns no pair — pins down the "T2 is inert for formulas" claim in §1 as an executable fact, not just a regex read.
7. If NMC ships any formula (POLICY 3): the same shape of test as 2, using the measured real NMC811/NMC622 titles in §3.

### Reference-IDF table and cache version

- **Reference-IDF table: no rebuild.** Confirmed by reading the shipped table directly — it is sampled independently of `ABBREVIATION_GROUPS`, and none of the new formula tokens (nor, already today, `lco`/`lfp`/`nmc` themselves) are keys in it; the designed-for out-of-table fallback (`REFERENCE_IDF_MAX_WEIGHT`) is the semantically correct treatment for a specific compound formula anyway.
- **`PAPER_CACHE_KEY_VERSION`** (`web/src/lib/opportunities/pool-cache.ts`, currently `9`): bump to **`10`**, same reasoning and same mechanism as every prior Required-gate/SENSE-CONTEXT admission change in this loop (§1ao.9, AMENDMENT 4.10) — a pool cached under the old table must not keep serving a reader an empty "LCO" feed after this ships.

## 5. POLICY — manager decides

1. **Ship LCO (`"licoo2"`) and LFP (`"lifepo4"`) now.** Both measured clean: double-digit-to-majority marginal recall gain, zero false positives across every real negative set checked (300+ cross-domain papers plus the item's own petroleum-collision adversarial set), no interaction with rule (c)/T2 (formulas can't form a self-declared pair), no reference-table rebuild needed. Recommend: yes, no open question.
2. **NMC — pick one, with numbers attached (§3/§4):**
   - (a) **Add `"nmc811"` only** — highest measured marginal recall (92%), matches the brief's own named example, but is a hyponym-into-family grouping with the one-way/two-way precision trade-off described in §4 (a reader tagging "NMC811" specifically would also start matching generic-NMC papers).
   - (b) **Add `"nmc811"` and `"nmc622"`** — same trade-off as (a), twice over, for the two best-measured stoichiometries (92% and 64% marginal gain respectively); breaks the letter of "one canonical formula family per group" in exchange for a second, still-bounded, still-curated win.
   - (c) **Add the generic `"LiNixMnyCozO2"` only** — stays a pure family-name synonym (no hyponym/precision issue, same *kind* of relationship as LCO/LFP's formula) but measured a **weak 4% marginal gain**, because papers using the generic notation overwhelmingly already say "NMC" too.
   - (d) **Ship nothing for NMC this round**, leave it a named, explicit residual (parallel to how `TOKENIZE-PLURALS`/`T2-COMMA-PAREN` are already tracked in this loop) until a decision is wanted on the one-way-expansion question generally.
   - Not recommending a default — this is a real product-judgment call about whether a reader's specific-stoichiometry tag should silently widen to the whole family, which the investigation surfaced but the brief's own "curated, not open-ended" constraint doesn't resolve by itself.
3. **The internally-hyphenated `"Li-CoO2"`/`"Li-FePO4"` spelling stays an unfixed residual.** Real-sample frequency wasn't separately measured (it's non-standard chemistry notation; none of the ~450 real papers read in this investigation used it) — worth a cheap protective test (§4.2.3) but not, on current evidence, worth chasing further.
4. **Spurious inflection is cosmetic, not a defect — confirm no action wanted.** Because `"licoo2"`/`"lifepo4"`/`"nmc811"` are 6+ characters, `term-expand.ts`'s `KNOWN_SHORT_FORMS` threshold (`length <= 4`) does not exempt them from `inflectedForms`, so `expandTerm` will also generate a harmless, never-matchable `"licoo2s"`-shaped plural. No real text will ever contain it; flagged only so it isn't later "discovered" as unexplained. No code change proposed.
