## NEW FINDINGS (frozen-batch and cost risks first)

**Finding 1 — ledger-mode reconstruction can reach the topic leg (frozen-batch / cost risk, first as required).** Confirmed real by independent re-derivation (EVIDENCE above), matching what C proactively disclosed. Severity: **LOW.** Requires ALL of: `PEER_DASHBOARD_LEDGER` on (itself default off), `PEER_CHANNEL_OPENALEX_TOPIC` on (default off), a legacy batch row with no stored `servedItems` (only possible for rows written before the `servedItems` column existed — dead weight on any system that has always had it), and the owner having qualifying positive `openalex_topic` ledger entries. Even then: no new paper can enter a frozen batch's output (proven above, not merely asserted), and the extra cost is one bounded OpenAlex call subject to the same per-owner daily cache this slice built. Recommend: record as an open item, no code change required — fixing it would mean either passing `channelCandidateCache`/seeds into the reconstruction call (widens an already-legacy-only path) or stripping `preferenceLedger` before the reconstruction spread (a `route.ts` change, out of this slice's allowed-file list, correctly not attempted by C).

**Finding 2 — "cache unreadable → skip legs" is untested against real failure behavior (cost risk).** `resolveChannelCandidates`'s defensive `try/catch` around `cache.get()` (pipeline.ts L1639-1647) is correct, deliberate, and disclosed in its own comment ("a state today's shipped classes never actually produce, since they swallow their own errors to a clean null miss") — this is not a hidden defect. But independently confirmed by full reads of both shipped classes: `PrivateChannelCandidateCache.get()` (channel-candidate-cache.ts L102-119) and `MemoryChannelCandidateCache.get()` (L154-156) both wrap every failure mode in an internal try/catch and always resolve to `null` — **neither can ever reject**. The one test exercising this path (`channels.test.ts:1388-1410`) uses `vi.spyOn(channelCandidateCache, "get").mockRejectedValue(...)` to force a rejection no real instance produces. Net effect: a genuine Supabase outage during a channel-cache read is indistinguishable from an ordinary first-time miss and will silently take the "fetch every enabled leg live" branch — exactly the unbounded-per-open-call pattern F-M-P2-02 exists to close — rather than the safer skip+truthful-error branch the acceptance criterion calls for. This mirrors a **pre-existing** convention (`PrivatePaperPoolCache.get()`, private-paper-cache.ts L133-155, has the identical ambiguity) — not a new mistake introduced carelessly, and B's own guide (D-ADD.3 point 4) flagged the ambiguity explicitly without closing it either. Severity: **MEDIUM-but-inert-until-flags-flip** — same class as F-M-P2-02 itself: today, all 4 channel flags are off, so this gap has zero live effect. Once any flag flips, the practical cost of the gap is bounded (a live Supabase outage would degrade to today's pre-P2-S4d behavior for the affected owner, not something newly broken — no data leak, no wrong exclusion). Recommend: either (a) accept as a known, disclosed, bounded gap (consistent with how the identical ambiguity in `PrivatePaperPoolCache` is already accepted), or (b) a future slice makes the two `get()` implementations distinguish "row absent" from "query failed" (e.g. rethrow on a Supabase `error`, only swallow on the not-configured/wrong-prefix early-outs) — a real, if small, design change, out of scope for this review.

**Finding 3 — minor stale doc-comment phrasing (cosmetic, not functional).** `buildRRFChannels`'s original P2-S6 doc comment (pipeline.ts ~L126-135) still describes `"topic-field"` in the present tense as one of "the three non-source channels `buildPaperPool` also fetches," immediately followed by a P2-S4c-1 paragraph correcting this. The function body itself is already correct (confirmed — no `topicFieldItems` parameter). A future reader skimming only the first paragraph could be briefly misled. No functional impact; not worth a special writer turn on its own, but worth folding into whatever slice next touches this comment block.
