B5. **What happens if the SAME key is reused with a DIFFERENT payload.**
VERIFIED -- **rejected**, not silently accepted and not silently ignored: HTTP 409, error code `invalid_idempotent_request`: "this idempotency key has already been used on a request that had a different payload. Retrying this request is useless without changing the idempotency key or payload." Source: https://resend.com/docs/dashboard/emails/idempotency-keys (2026-09-24T11:38Z). B6. **Concurrent/simultaneous requests with the same key.**
VERIFIED -- also rejected, distinctly from B5: HTTP 409, error code `concurrent_idempotent_requests`, meaning another request with that key is still in flight; described as "safe to retry later." Source: https://resend.com/docs/dashboard/emails/idempotency-keys (2026-09-24T11:38Z). Corroborated in the SDK: `'concurrent_idempotent_requests'` is a literal member of `RESEND_ERROR_CODE_KEY` (`node_modules/resend/dist/index.d.mts:116`). This means two genuinely concurrent retries for the same user/day cannot both cause a real send -- one gets the real result, the other gets a safe, retryable 409, never a duplicate delivery.

B7. **Key format limits and recommendations.**
VERIFIED. 1-256 characters, must be unique per API request (i.e. per distinct logical operation -- reused deliberately for a retry, not per HTTP call); a key outside that length raises HTTP 400, error code `invalid_idempotency_key` (also a literal `RESEND_ERROR_CODE_KEY` member, `index.d.mts:116`). Recommended format: `<event-type>/<entity-id>`, e.g. `welcome-user/123456789`. Source: https://resend.com/docs/dashboard/emails/idempotency-keys (2026-09-24T11:38Z).

**C1. Two layers of idempotency, working together (the central idea).**
Today there is one layer: the DB claim (who gets to attempt today's digest at all). This design adds a second, independent layer: a deterministic Resend `Idempotency-Key` on the send itself (is this exact email allowed to actually go out more than once). The two layers answer different questions and neither can substitute for the other:
- The DB claim prevents two overlapping cron/manual invocations from BOTH deciding to build and attempt today's digest for the same user (already solved).
- The Resend key prevents the SEND ITSELF from ever duplicating, even across multiple attempts spread over hours, multiple processes, or a crash between "Resend said yes" and "our DB recorded that fact" (not solved today -- this is the gap).
The second layer is what makes local bookkeeping (see C4) only an optimization rather than a safety requirement: **Resend itself is the actual source of truth for "was this exact email already sent," for 24 hours.** Even if Peer's own status tracking is lost, stale, or racy, calling Resend again with the same key and the same payload cannot produce a second delivery -- worst case it wastes one redundant network round-trip.

**C2. The deterministic key.**
```
import { createHash } from "node:crypto";

function digestIdempotencyKey(userId: string, localDate: string): string {
  const material = `peer-digest-email:v1:${userId}:${localDate}`;
  const hash = createHash("sha256").update(material).digest("hex");
  return `peer-digest-email/${hash}`;
}
```
- **Owner**: `userId` (`row.user_id`, already a UUID, already the first column of the DB claim's own unique key -- same identity, same source).
- **Local date**: `localDate` (the SAME string `dateInTimezone(now, row.digest_timezone)` already computed for the claim RPC at `route.ts:299` -- reusing it, not recomputing a second notion of "today").
- **Digest kind**: the literal `"peer-digest-email:v1"` prefix. Currently a constant (Peer has exactly one kind of scheduled digest email today), included so the key can never collide with any unrelated FUTURE idempotency-keyed Resend call Peer might add (a welcome email, a password reset, a weekly-summary variant, etc.) and so the scheme can be versioned (`v1` -> `v2`) later without silently colliding with old-format keys.
- **No personal data in clear**: neither the raw `userId` nor the raw `localDate` nor the recipient's email address ever appears as a literal substring of the key sent to Resend -- only their SHA-256 digest does. (The recipient's address obviously still appears in the `to` field of the payload itself, unavoidably and unrelated to this key -- "no personal data in clear" is read here as being about the KEY specifically, per the brief's own phrasing, not about the email payload as a whole, which necessarily contains the address it is being sent to.)
- **Collision-resistant by construction**: SHA-256 gives a 256-bit output space; for any realistic user/day volume the chance of two different `(userId, localDate)` pairs hashing to the same key is negligible, so -- unlike the DB claim key -- this key needs no database uniqueness CONSTRAINT to be safe; determinism (same inputs -> same key, always) is the only property actually required, and a pure hash function gives that for free.
- **Length**: `"peer-digest-email/"` (18 chars) + 64 hex chars = 82 characters, well inside Resend's 256-character cap (B7), and matches Resend's own recommended `<event-type>/<entity-id>` shape (B7) with the hash standing in as the entity-id.
- Recommended home: inline in `dispatch-digests/route.ts`, next to the existing small pure helpers (`dateInTimezone`, `hourInTimezone`, `weekdayInTimezone`, `isDigestDedupeEnabled`) that already live there rather than in a separate module -- this matches the file's own established local convention. A separate `web/src/lib/email/digest-idempotency.ts` module is an equally valid alternative if C prefers isolating it for unit tests without importing a route file (this file's own existing tests already import pure helpers straight from the route, so that is not itself a blocker either way).

**C3. The non-obvious correctness trap: the digest template is not byte-deterministic, and B5 punishes that.**
`web/src/lib/email/digest-template.ts` renders the recipient-facing "today" date **inline in the content itself**, independently, in all three exported render functions, each calling `new Date()` fresh:
- `renderDigestSubject` -- `const today = new Date();` at line 57, formatted into the subject line (e.g. "... · Peer briefing Sep 24").
- `renderDigestPlaintext` -- `const today = formatDate(new Date());` at line 70, formatted into the first body line ("PEER BRIEFING -- September 24, 2026").
- `renderDigestHtml` -- `const today = formatDate(new Date());` at line 142, same content, HTML body.
(All three are called only from `web/src/lib/email/send-digest.ts` -- confirmed by repo-wide grep, zero other callers -- so changing their signatures, if that route is chosen, has a single, known blast radius.)
Because of this, even holding `{to, firstName, items, originUrl}` perfectly stable across a retry, the RENDERED `subject`/`html`/`text` bytes can still differ between the original attempt and a retry made later (different clock reading -> different formatted date string, possibly a different calendar date entirely near a UTC boundary) -- which is **exactly** the condition B5 says Resend will reject with 409 `invalid_idempotent_request`. A naive "just add the idempotency key" implementation would work perfectly in same-second tests and then silently fail every real retry that happens more than a few seconds after the original attempt -- the single most important thing this investigation surfaces beyond the literal "does Resend support this" question.
Two ways to close this, both viable; **recommended: (b)**:
- **(a) Make the templates take a stable date instead of reading the clock.** Thread the already-computed `localDate` (or the original attempt's `now`) into `renderDigestSubject`/`renderDigestPlaintext`/`renderDigestHtml` as an explicit parameter, replacing their internal `new Date()` calls. Pro: fixes the root cause; the templates become properly pure functions of their inputs, which is good practice independent of this feature. Con: touches a shared template file (even though it has only one real caller today), and requires re-auditing the templates for any OTHER hidden non-determinism (locale/timezone-dependent formatting quirks, etc.) beyond the three known `new Date()` sites.
- **(b) Persist the fully-rendered `{subject, html, text}` at first-attempt time; replay them verbatim on any retry, never re-render.** The claimed row's JSONB `payload` (see C4) stores the exact strings that were (or were about to be) sent to Resend the first time; a retry reads them back and passes them straight to `client.emails.send({from, to, subject, html, text}, {idempotencyKey})` without calling the template functions again at all. Pro: touches zero shared template code; trivially, unconditionally byte-identical by construction (it is the same string, not a re-derivation that happens to match); defends against ANY future non-determinism in the templates, known or not, without needing to find and fix each instance. Con: stores a redundant copy of rendered HTML (typically a few KB) inside the DB row for as long as a retry might still be useful.
Recommended because it is the smaller, lower-blast-radius change on a multi-writer branch, and because "replay the exact bytes" is a strictly stronger guarantee than "re-derive and hope nothing else was non-deterministic." Listed as POLICY question 3 below since it is a real, disclosed trade-off, not a purely technical call.

**C4. What gets persisted, and where.**
No NEW migration is required. The already-authored (not yet applied) `20260924000300_briefing_deliveries_dedupe.sql` added `local_date text` and the claim RPC; the existing `payload jsonb not null` column (present since the ORIGINAL `briefing_deliveries` table, `schema.sql:243-269`, per A's evidence) can hold an additive sub-key with no schema change at all. Recommended shape (only present for `channel in ('email','both')`; absent/untouched for `inapp`-only rows):
```
payload: {
  items: freshItems,              // unchanged, existing shape
  email: {
    idempotencyKey: string,       // the deterministic key used for this row's attempts
    status: "sent" | "failed",    // absent/undefined = never attempted yet
    messageId?: string,           // Resend's id, once sent
    error?: string,                // last failure message, if status is "failed"
    to: string, firstName?: string, originUrl: string,  // exact inputs used
    subject: string, html: string, text: string,          // exact rendered bytes used (per C3-b)
    attemptedAt: string,           // ISO instant of the most recent attempt
  }
}
```
This sub-object is written (a) once at claim time with `status` absent (attempt about to happen), and (b) again immediately after the send call resolves, with `status` set from its outcome. Both writes are plain `UPDATE ... SET payload = $1 WHERE id = $2` calls through the existing `createAdminClient()` service-role client (already used for every other write on this table) -- **not** a new RPC. Unlike the INSERT-vs-upsert question the original C already solved (which needed an RPC specifically because a PARTIAL unique index's `ON CONFLICT` arbiter cannot be expressed through `supabase-js`'s plain `.upsert()` -- see the existing migration's own header), a plain `UPDATE` by primary key has no such subtlety: it is a standard, unconditional row write, already well inside what `supabase-js`'s query builder does correctly (recommend C still spot-check `node_modules/@supabase/postgrest-js`'s `.update()` path directly rather than assume, consistent with this campaign's "verify the exact client API" convention -- cheap, and this document has not itself re-verified that specific method).
This UPDATE does not need `security definer` or new grants, for the same reason the existing migration's RPC does not: the only caller already holds the service-role key, which already bypasses RLS on this table (established by prior evidence in this campaign for this same admin client -- not re-verified fresh in this session, since Supabase RLS mechanics are outside this item's EMAIL-PROVIDER remit).

**C5. The claim -> send -> record flow, changed.**
Today (flag on, post P4-S7-C): compute `freshItems` fresh every invocation -> attempt claim -> on success, `dispatched.push` then attempt email once, using the in-memory `freshItems` -> on claim conflict, unconditionally `skipped`, email code path never reached again, ever, for that (user, local_date).
New (flag on, this item's addition):
1. Compute `localDate` (unchanged) and `idempotencyKey = digestIdempotencyKey(row.user_id, localDate)` (new, before attempting the claim -- needed either way below).
2. Attempt the claim RPC (unchanged signature, unchanged SQL).
3. **Claim succeeds** (first-ever attempt for this user/day): proceed exactly as today through `dispatched.push`, EXCEPT the email call now also passes `{ idempotencyKey }` as a second argument, and after the call resolves (success or failure), the row's `payload.email` sub-object is written with the outcome (C4). This is the only change on the "happy path" -- one new argument to the send call, one new UPDATE afterward.
4. **Claim conflicts** (0 rows -- a row for this user/day already exists): instead of unconditionally skipping, first check the row's OWN CHANNEL is email/both at all (an `inapp`-only row has no email step, so skip exactly as today, unconditionally -- no behavior change for that case). For an email/both row, SELECT the existing row's `id` and `payload.email` (a plain read, already well inside what this route's admin client does elsewhere).
   - If `payload.email?.status === "sent"`: skip -- **this is the true "nothing to do" case, and this is the ONLY case that should still produce a bare, final `"digest already claimed for this local date"`-style skip** (recommend renaming this specific reason to something like `"digest already sent for this local date"` so the two skip reasons are distinguishable in the response and in any future operator-facing log).
   - If `payload.email?.status !== "sent"` (i.e. `"failed"`, or the sub-object is entirely absent because the process crashed between claim and the first status write): this is exactly the F-A-P4S7-01 case. Recompute the SAME deterministic `idempotencyKey` (pure function, no DB read needed for the key itself), reuse the row's persisted `to`/`firstName`/`originUrl`/`items` (or persisted `subject`/`html`/`text`, per C3-b) VERBATIM -- never recomputed from a fresh pipeline run or a fresh `new Date()` -- and call `sendDigestEmail`/the Resend client again with the identical key and identical payload. On resolution, write `payload.email` again with the new outcome (C4). `dispatched`/`failed` bookkeeping in the JSON response is unaffected by this branch (the row was already counted as `dispatched` at its original claim time); only `emailsSent`/`emailsFailed` gain the retry's own outcome.
5. **Why reusing the frozen claim-time content, not a fresh pipeline run, is correct and not a violation of "stale job cannot overwrite new intent":** the CLAIM step already freezes "today's digest content" the moment it succeeds -- this is the existing, already-accepted P4-S7-C/A design, consistent with the campaign's own dashboard-batch philosophy (§1p.C.5: "One batch per owner per local date, frozen once served"). A SEND retry is retrying delivery of what was already decided for today, not re-deciding what today's digest should contain. If the user's intent genuinely changes, that takes effect starting the NEXT local date, which always re-runs the pipeline fresh via a brand-new claim (a different `local_date`, a different row, a different idempotency key) -- it is never silently overwritten by a stale job, because there is no mechanism here by which an OLD day's frozen content could ever be applied to a NEW day's claim.

**C6. Flag behaviour.**
`PEER_DIGEST_DEDUPE` off (default): **byte-identical to today, unconditionally.** `sendDigestEmail` is called with no second argument at all (exactly today's single-argument call, `send-digest.ts:51-57`, `client.emails.send({from, to, subject, html, text})`); the plain-insert path is used; no idempotency key is ever computed or attached; no new SELECT/UPDATE on `briefing_deliveries` ever runs. This item's entire design sits strictly behind the SAME flag check (`isDigestDedupeEnabled()`, `route.ts:129-131`) that already gates the claim RPC -- see POLICY question 1 for whether the manager wants a second, narrower flag instead.

**C7. Why this satisfies "no chance of a double send," including under real concurrency.**
Two overlapping retries for the same (user, local_date) (e.g. an operator manually retries twice, or a future sweep and a manual retry overlap): both independently compute the IDENTICAL deterministic key (pure function of user_id + local_date) and, per C3-b, the IDENTICAL persisted payload (read from the same row, never freshly re-rendered) -- so per B4/B6, Resend's own server-side arbitration guarantees at most one of them causes a real send; the other gets either the safe 409 `concurrent_idempotent_requests` (if truly simultaneous) or the cached original result (if slightly staggered) -- never a second delivery. This holds **even if** Peer's own local SELECT-then-UPDATE bookkeeping (C4) has its own race (e.g. two retries both read `status: "failed"` before either one's UPDATE lands) -- that race can, at worst, cause both to call Resend, which is exactly the case B4/B6 already make safe. **This is the core reason this design is robust without needing the local bookkeeping itself to be race-free or transactionally atomic** -- unlike the original CLAIM step (which genuinely needed a DB-level atomic arbiter, hence the RPC + partial unique index), the SEND-retry bookkeeping only needs to be eventually-consistent, because the actual safety authority has moved to Resend for this specific, narrow slice of the problem.

**C8. What happens after the 24-hour window expires.**
Per B3, Resend stops recognizing the key after 24 hours; calling send again with the "same" key at that point is treated as a genuinely new, first-time send (a real new email goes out). This is judged a non-issue for this design: the claim is already scoped to a single calendar day (`local_date`), the dispatch cron runs hourly, and any retry attempt for "today's" digest realistically happens within hours of the original attempt, not 24 hours later -- by the time 24 hours have passed, `local_date` for that row is necessarily over, and any legitimate later attempt is for a NEW day (a new claim, a new row, a new key), not a retry of the old one. The 24-hour boundary therefore naturally coincides with "this day's digest is no longer meaningfully retryable anyway," which is the right place for the safety net to end. Recorded here explicitly so a future reader does not mistake 24 hours for "too short."
