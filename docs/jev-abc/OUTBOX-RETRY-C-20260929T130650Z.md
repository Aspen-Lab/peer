## PLAN

**Why `cloudFeedback`'s own catch branch changes (not just `retryPendingPushes`):** the brief says "reuse the existing cloud* helpers unchanged" AND separately requires point 2 (payload capture) to live "inside cloudFeedback's own failure branch" — so cloudFeedback is not byte-frozen, only its HTTP-calling contract is. `cloudFeedback` returns `Promise<void>` and never exposes the failure's status code to its caller, so a 4xx-vs-5xx distinction can only be made inside cloudFeedback itself, not by `retryPendingPushes` after the fact. Folding both point 2 (capture) and point 3 (4xx give-up) into the same already-being-edited catch branch avoids duplicating status-detection logic and applies uniformly whether the failing call was interactive or a retry — checked against every existing test above, this changes no observed behavior for any status code already exercised (all 500/401).
