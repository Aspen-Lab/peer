### Ranked findings

**MEDIUM — the P6 "feed push has failed" signal only covers the one-time initial sign-in migration batch, not steady-state saves during a normal signed-in session; C's checkpoint should have disclosed this per the ruling's own escape clause and did not.**
Evidence: `web/src/components/feed-sync.tsx` sets/clears `useFeedSyncStatus.pushFailed` in exactly one place (L162-168), inside `onSession`'s one-time-per-sign-in batch push (`didInitialSyncRef` guarded). Grepped the whole `web/src` tree for `markFeedPushFailed`/`clearFeedPushFailed` — no other call site exists. A signed-in reader's ordinary, everyday saves go through a completely separate path, `web/src/store/feed.ts`'s `cloudSave`/`cloudUnsave`/`cloudMarkRead`/`cloudMarkUnread` (L102-142) — each swallows a failed push with only `console.warn(...)`, never touching `useFeedSyncStatus`. Concretely: a signed-in user saves a paper mid-session, the save silently fails (network blip, server hiccup), they sign out — `feedPushFailed` is still `false`, so no warning shows, and per feed-sync's own `resetLocal()` on `SIGNED_OUT`, that save is gone. This is precisely the scenario P6 was written to stop.
Why MEDIUM not HIGH: the binding ruling text names two SPECIFIC, pre-existing flags to read ("useProfileSyncStatus.pushFailed" and "feed-sync's flag") — C read exactly those, correctly, and the mechanism built on top of them (show/hide/no-re-arm) is fully correct and mutation-tested. This gap is in the flag's own underlying coverage, which predates this item, lives entirely outside the 6 change-list files, and was already named as an accepted trade-off in SIGNIN-MERGE's own VERIFIED review ("feed migration-push batch has no retry queue"). It is not a case of the shipped code failing to do what §1al (c) literally specifies.
Why still a real finding: §1al (c)'s escape clause is binding text, not a suggestion — "if detecting unsynced feed data needs more than exporting an existing flag, build it for what exists and STOP-report the rest." Fully detecting unsynced feed data genuinely does need more than exporting the existing flag (the flag misses an entire class of failures), so the clause's premise is true and its "STOP-report the rest" instruction applied. C's checkpoint instead states "the escape clause's trigger condition... does not fire" — reasoning only about whether the flag was already *exported* (yes), not whether its *coverage* was adequate (no) — so the required disclosure never happened.
Recommendation for the manager: treat this as a named, accepted trade-off (matching SIGNIN-MERGE's own precedent) and record it explicitly in the §5 ledger, or open a small follow-up item to route `store/feed.ts`'s four cloud-push failures through `markFeedPushFailed`/a shared flag too. Not a blocker for committing POLISH-1-SYNC's own 6 files — this is a pre-existing gap POLISH-1-SYNC correctly built on top of, not one it introduced.

No other findings — (b), (d), (h) and the rest of (c) had no gaps found across code review, live execution, and adversarial mutation testing.
