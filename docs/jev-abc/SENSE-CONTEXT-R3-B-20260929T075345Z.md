`selfDeclaresDifferentSense` (rule c) returns `{applies:false, differs:false}` for all three — rule (c) never even sees a candidate for #1/#2 (no abbreviation pair is self-declared at all), and for #3 it sees no candidate either (§2 explains why).

**#1 and #2 (solid state) — a strip-set bug, not a calibration problem.** `senseContextStripSet` (private, keyword.ts) builds the set of tokens to remove from both sides from `tokenize(variant)` for every `variant` in `expandTerm("solid state")`. `expandTerm` canonicalizes first, and `canonicalize` turns hyphens into spaces — so every variant it produces is **space-joined** ("solid state", "solid states"), and the strip set ends up as `{"solid","state","states"}`. But `tokenize()` (run on the *raw* item/context text, never canonicalized first) does **not** split on hyphens — it only splits on whitespace. The ordinary English adjective "**solid-state**" (as in "solid-state materials", "solid-state platform" — how both physics papers, and the reader's own project text, actually write it) therefore survives tokenization as **one token, `"solid-state"`**, which is not a member of `{"solid","state","states"}` and is never stripped. It leaks through as ordinary shared vocabulary.

The probe's own diagnostic (real `expandTerm`/`tokenize`, not reimplemented) confirms this is the dominant signal, not a footnote: `"solid-state"` is the **single highest-reference-weight token** (7.072, the corpus-rarity weight from the shipped `reference-idf.json`) among the shared tokens for *both* papers — item #1 has only 2 shared tokens at all (`solid-state`, `materials`); item #2 has 3 (`solid-state`, `focused`, `while`).

I tested this as a counterfactual through the REAL `senseContextGate`, not just by inspecting the code: with every occurrence of the literal substring `"solid-state"` in both the item text and the context text replaced by `"solid state"` (so it now DOES land in the existing strip set — same shape, same length, no other change), both items flip:

- #1: `fixedSim` 0.11035 → 0.03672, `overlapSim` 0.04348 → 0 → **gate now fails → correctly demoted.**
- #2: `fixedSim` 0.08690 → 0.02508, `overlapSim` 0.13043 → 0.09091 (now under the 0.10 floor) → **gate now fails → correctly demoted.**

Both residuals are fully explained and fully fixed by this one, general, mechanical gap. It is not specific to "solid state" — any multi-word Required tag whose natural English surface form is normally hyphenated (e.g. a reader's own "machine learning" tag written as "machine-learning" in a paper) has the identical latent leak, because the bug is in how the strip set is built, not in this one tag's spelling.

**#3 (LCO) — not a strip-set leak; a same-field-different-compound confusion.** The shared tokens driving `fixedSim = 0.202` are `cathode` (7.189), `batteries` (7.189), `battery` (7.072), `interfacial` (6.871), `interfaces` (6.63), `improving` (4.925), `stability` (4.644), `materials` (4.151) — eight ordinary battery-domain words, none of them a disguised form of "LCO"/"lithium"/"cobalt"/"oxide"/"licoo2". Li₂C₂O₄ (lithium oxalate) is genuinely used, in this real paper, *as a battery-cathode prelithiation additive* — the abstract is honestly, densely about batteries and cathodes, just the wrong compound. No context-similarity statistic can be expected to separate "battery paper about compound X" from "battery paper about compound Y that happens to share an abbreviation," because the wrong-compound paper is not a topical outlier at all — it sits comfortably inside the reader's own vocabulary. §3 quantifies why no floor fixes this.

Why rule (c) never gets a chance at #3: the paper's own text never writes "Li₂C₂O₄ (LCO)" or "LCO (Li₂C₂O₄)" — it writes a **joint, two-abbreviation coinage**, "a composite NiCo₂O₄@Li₂C₂O₄ prelithiation agent (**NCO@LCO**)". `selfDeclaredAbbreviationPairs`'s regexes require the parenthesized abbreviation to be a plain `[A-Z][A-Za-z0-9]{1,7}` run — the `@` character is outside that character class, so neither regex matches "(NCO@LCO)" at all. Zero pairs are extracted for this tag on this paper; rule (c) is not narrowly failing here, it is structurally never invoked.

## §2. The Li₂C₂O₄ formula-extension — design and measurement

Per the brief: rule (c) deliberately ignores single-token formulas (a run shorter than the abbreviation's letter count can't spell it). Now that `"licoo2"` is a known LCO expansion (§1au LCO-FORMULA), I designed and measured a **separate, additional** hard-non-match check, layered next to rule (c), not replacing it: a Required tag with a known single-token formula (LCO → `licoo2`; LFP → `lifepo4`, same mechanism, free) contributes nothing for a paper that self-declares a pair whose long-form's **last word** (the word immediately next to the parenthesis — the same position rule (c) already scans) is shaped like a chemical formula and is **not** one of the tag's own known formulas.

**How "looks like a chemical formula" is detected** (prototype, in the now-deleted probe — not shipped code): the *raw*, not-yet-canonicalized captured word must (a) decompose entirely into element-like segments — one uppercase letter, one optional lowercase letter, then digits (`/^(?:[A-Z][a-z]?\d*)+$/`) — **and** (b) contain at least one digit. The digit requirement is what tells a formula ("LiCoO2", "Li2C2O4") apart from a bare multi-letter abbreviation with the identical case shape but no digit ("NCO", "LCO" itself) — abbreviations coined in running prose vastly outnumber genuine zero-digit formulas (formulas without any explicit subscript, like "NaCl", exist but are not the shape this rule needs to catch). This is a shape heuristic, not real chemistry parsing — stated as a limitation, not hidden.

**Doped/variant safety — verified structurally, not just hoped.** The escape clause's own example, `"LiCo0.98Mg0.02O2 (LCO)"`, must not fire. I did not rely on a special case for this: I traced, then *empirically confirmed by execution* (not just by hand, after catching myself getting the §1 context reconstruction wrong once already this session — hand-derivation of this exact regex grammar is exactly where the manager's own AMENDMENT 4 correction on rule (c) originally went wrong too), that the shared T2 extractor's `(?:[A-Za-z][\w-]*\s+){1,5}[A-Za-z][\w-]*` grammar requires its final word to be immediately preceded by whitespace and immediately followed by `\s*\(`. A decimal point is in neither `[\w-]` nor `\s`, so it hard-breaks that word boundary — a period anywhere inside what a chemist would call one formula token means **no pair is extracted at all**, for either regex direction, regardless of where the period falls. Tested directly: `"we synthesized doped LiCo0.98Mg0.02O2 (LCO) as the cathode material."` and the same string sentence-initial both give `applies:false` (no pair found), same as the real residual's own "NCO@LCO" text. This protection is a structural consequence of the *existing, unmodified* T2 grammar, not a new special case my rule adds — so it costs nothing and cannot regress independently of that grammar.

**Measured** (real saved sets, `<scratchpad>/r3-lco-positives.json` / `r3-lco-negatives.json`, 50+50 items):

- **Real LCO positives: 0/50 fire.** 8/50 self-declare *some* pair for LCO at all (all of the shape "…Lithium Cobalt Oxide (LCO)…" or "…Doping of Lithium Cobalt Oxide (LCO)…" — multi-word, already agrees via the existing rule (c) `windowAgrees` check, never reaches the new formula branch). **Escape clause holds.**
- **Real LCO negatives (the 50 petroleum "light cycle oil" papers): 0/50 fire** (15/50 declare a pair, all "Light Cycle Oil (LCO)" — multi-word, already correctly caught by the *existing* rule (c), not this extension — this rule adds nothing here, which is expected: it targets a different failure shape).
- **8 constructed protective/target strings, 8/8 behave as intended:**
  - `"high-voltage LiCoO2 (LCO)"`, `"layered LiCoO2 (LCO)"`, `"composite lithium cobalt oxide cathodes (LCO)"` (the three strings the manager's own past false-positive check and AMENDMENT 4 ruling 4 protect) — still do **not** fire.
  - `"a novel crystalline Li2C2O4 (LCO) prelithiation compound…"` — **fires** (`differs:true`, `rawLastWord:"Li2C2O4"`), the intended catch, long-first direction.
  - `"LCO (crystalline Li2C2O4) was used…"` — **fires**, same catch, abbr-first direction.
  - `"LCO (Li2C2O4) was used…"` (bare, nothing else inside the parens) — does **not** fire, correctly: `applies:false`, because — confirmed by running the real regex grammar, not assumed — **neither T2 regex can ever match a bare single-word pair in either direction**; both require at least 2 whitespace-separated words on the long-form side (the `{1,5}` repetition needs ≥ 1 rep before the mandatory final word). This is a pre-existing, general T2 limitation, not something this rule introduces or can fix.
  - The two doped-variant escape-clause strings — do **not** fire (§ above).
  - The real residual's own full abstract text ("…NCO@LCO…") — does **not** fire. **This extension would not have caught the actual paper under investigation.** It targets a real, generalizable gap (a paper that cleanly writes "Formula (LCO)"), but this specific live paper's joint two-abbreviation coinage is a different, narrower gap (§1, §5 POLICY 5).
